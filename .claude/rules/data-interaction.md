# 데이터 · 상태 변수 · Interaction 규칙

> 공통 규칙 (문서 정본 · 편집 파이프라인 · 히스토리 · 금지 패턴) 은 [state-management.md](state-management.md) 가 정본이다 (절 번호 §4 · §5 · §6 은 그 파일에서 이어진다) — shared `interactions` · `collections` · `state` 와 `preview` 파일은 이 파일만 로드된다. 새 데이터 · interaction 파일이 생기면 frontmatter 에 등재.

## 4. 데이터 — Collections (ADR-132 · ADR-152 v2)

- **문서의 바인딩**: `NodeEntry.binding: DataBindingRef` (`catalog/document/types.ts` — `collectionId` · `fieldMap`, 선택 `key` · `view` · `viewId`). 변환 `catalogBindingRef` (`dataBinding.ts`), 편집 명령 `catalogBindingCommand` (`dataBindingCommand.ts`, Properties 의 binding 키는 `catalogPropertiesPatchCommand` 가 이쪽으로 가른다).
- **한 항목 바인딩 `binding.key` (`useListData.getItem`)**: key (리터럴 · `{{ }}`) 는 compositionRoot 의 `rows` 감싸개가 `catalogBindingKey` (`stateTemplate.ts` — 노드 페이지 · 프로젝트 변수 · `params`) 로 한 번 풀어 두 소비자에 같이 준다 — 풀리지 않으면 (Canvas) 첫 항목 표본. resolver 는 key 바인딩의 항목을 `row` 로 자손에게 (컨테이너의 `{field}`), 목록은 그 하나만 반복. key 가 읽는 이름이 바뀌면 `refreshState` 가 그 collection 의 `refreshRows`.
- **행 읽기는 한 길**: Canvas · Preview · Publish 의 바운드 행은 composition root 의 `rows` 감싸개 → resolver → record 로 온다 — 행 source 는 Canvas 가 문서 (`catalogDataRead.ts`), Preview · Publish 가 세션 (`boundRows`), 둘 다 `catalogBoundRows` (`dataBinding.ts`). resolve 는 `resolveBoundCollection` (id 우선, `name` 은 옛 값 폴백), `{field}` 는 resolver 가 푼다 (행 템플릿 편집은 `rowTemplate.ts`). `fieldMap` 값과 `{#<fieldId>}` 토큰은 `DataField.id` (key 아님). `useCollectionData` → `useResolvedCollectionItems` (`packages/shared/src/hooks/`) 는 옛 shared 컴포넌트 안쪽 경로다 (catalog DOM runtime 은 `dataBinding` 을 넘기지 않는다) — 새 소비처는 record 를 읽는다.
- **데이터 편집 = `DataChange`**: collection 생성 · 삭제 · schema · 행 · source 는 `useDataStore.applyDataChange(change)` (`stores/utils/dataChange.ts` — `reduceDataOps` 순수 적용기, all-or-nothing, inverse 동시 산출) 하나 — 결과는 sink 를 지나 문서 명령 한 step (ADR-286). `create/update/deleteCollection` 은 `collectionUpdateToOps` diff 의 얇은 wrapper. mock 행은 collection 당 1,000 행 상한 (`CATALOG_COLLECTION_ROW_LIMIT` — 검증 `COLLECTION_ROW_LIMIT`). **금지**: `set()` 으로 `collections` 직접 변경 · 히스토리 없는 데이터 편집 · `remove_field` / `remove_rows` 를 AI 에 노출 (`HUMAN_ONLY_DATA_OPS`).
- API 결과 (`runtimeData`) 는 문서 밖이다 — Builder 는 `executeApiEndpoint` 결과를 data store 에 두고 Canvas 에는 `refreshRows`, Preview 에는 `CATALOG_DATA` 로 보낸다 (Publish 는 세션이 부른다 — reference §13). useEffect + 로컬 state 로 결과를 들고 있지 않는다.
- Preview · Publish 의 데이터 정의는 `catalogRuntimeData` (`runtime/catalogData.ts`) 가 문서 entry 에서 투영한다 (schema 필드 `id` · `keyField` 포함).
- 이름: 저장 · 내부 타입은 `collections` (`CollectionState` · `targetCollection`), 사용자에게 보이는 UI 심볼 `DataTable*` (`panels/datatable/`) 은 유지.

- **행 진입 · 값 표현 · key 필드 (ADR-313)**: 행이 들어오는 모든 길 (생성 붙여넣기 · 파일 · 기존 표로 가져오기 · Builder API 실행 · Preview/Publish 조회 · 격자 입력 · 행 양식 · Form 값 · AI 붙여넣기) 은 shared `collections/intake` 의 변환기 하나 (`normalizeRows` — Builder 는 `utils/intakeRows.ts`, 조회는 `intake/queryItems.ts` `intakeQueryItems`) 를 지나고, 진입이 원본 종류 (`json` · `text`) 를 알려 준다 — 값을 보고 추측하지 않는다. JSON 원본은 필드의 값 표현 (`CatalogDataField.encoding` — `flag` · `numberText` · `epochMs` · `epochSec` · `compactDate` · `compactDateTime` · `dateParts` · `bigInt`) 을 선언한 필드만 읽고, 선언 없는 값은 바꾸지 않는다 (타입과 다르면 「타입과 다른 셀」 로 셀 뿐). 글자 원본 (CSV · 탭 · 격자 · Form) 은 선언의 표기 → 열 타입의 글자 읽기 (`readTextCell`) 이고, 표 · CSV 셀은 파서가 타입을 정하지 않는다 (열 감지 `detectColumns(rows, source)`). 수로 정확히 옮겨지지 않는 숫자 글자는 읽기 실패 (근삿값 금지). JSON 원문은 `parseJsonLossless` (2^53 을 넘는 정수 literal = 글자) — 진입 경로에서 `JSON.parse` · `response.json()` 을 직접 부르지 않는다. 나가는 값 (보기 조건 쿼리 · body · `targetCollectionId` 가 있는 Form 제출) 은 같은 선언으로 되돌리고 (`outgoingFieldValue` · `outgoingRecord`) body 는 `stringifyJsonLossless` (큰 정수 = 따옴표 없는 literal). 항목 key = 바인딩 `fieldMap.value` → collection `keyField` (필드 id) → `id` · `key` · `value` → `row-N` (`resolveFieldRoles(dataBinding, schema, keyField)` · 세션 `treeFieldKeyOf`). 정적 게이트 `intake/__tests__/adr313Wiring.static.test.ts` — 새 진입 · 출구를 만들면 그 목록에 넣는다. 변환기는 Builder 첫 화면에 싣지 않는다 (실행기 · API 실행이 실행할 때 lazy import, 문서 검증은 `encodingKinds.ts` 만). **Why (2026-11-17)**: 같은 JSON 의 `"Y"` 가 기존 표로 가져올 때만 `true` 가 되고, Java `Long` PK 가 다섯 진입에서 근삿값이 됐으며, 서버로 나가는 조건 값은 저장 값의 글자였다.
- **비활성 항목 `disabledKeys` (S2 체크리스트 부록 D.3 2단계, 2026-11-23)**: 그룹이 항목 key 를 저장하고 (ADR-308 모양 — Design 패널은 항목 체크 목록, `catalogGroupKeysFields`), 연결된 목록은 바인딩 `fieldMap.disabled` (boolean 필드) 가 `true` 인 행의 key 를 `catalogBoundRows` 가 모든 행에서 세어 (`CatalogBoundRows.disabledKeys`) resolver 가 그룹 record 의 `disabledKeys` 에 합친다 — 문서에는 작성 key 만. Canvas (`catalogItemKeyDisabled` — 항목의 `catalogSelectionGroupOf`) · DOM (RAC 그룹 prop) · dispatcher guard 가 그 record 하나를 읽는다. 대상 목록 = `CATALOG_DATA_DISABLED_TYPES`.
- **데이터 보기 (ADR-284)**: 바인딩은 내장 보기 (`binding.view` — 조건 트리 · 정렬) 또는 공유 보기 (`binding.viewId` → `ViewEntry`, 원본 사슬의 collection = 바인딩의 `collectionId`) 를 읽는다. compositionRoot 의 행 감싸개가 보기 사슬과 `!var` 값을 한 번 풀어 (`catalogBindingQuery`) 행 소스에 넘기고, `catalogBoundRows` 가 **표시 투영 전** 원본 전체에 `runViewQueries` (`collections/view/evaluate.ts`) 를 실행한다 — Canvas · Preview · Publish 가 같은 모듈 (`oneEvaluator.static.test.ts`). 변수 쓰기 → `refreshState(names)` 가 그 변수를 읽는 보기의 collection 을 다시 읽는다. 필드 · 참조가 없는 조건은 건너뛰고 `rows.view.broken` 으로 낸다 (조용한 통과 금지 — 패널이 표시). 공유 보기 삭제는 읽는 곳이 있으면 `VIEW_IN_USE`, 파생 보기는 목록의 내장 보기를 `promoteBindingView` 로 승격한 뒤 가리킨다 (조건 사본 금지). 파생 보기 (`source.viewId` — 결과 수 · 묶기 · kanban 열) 는 마지막으로 읽던 노드와 함께 지워진다 (`removeWithReferrers` → `removeUnreadDerivedViews`) — collection 위의 보기 (이름 붙인 · 승격한) 는 남는다. **Why (2026-10-27 live)**: 결과 수 Text 를 지워도 보기가 남아 「read by N」 이 부풀고 원본 보기 삭제가 `VIEW_IN_USE` 로 막혔다. 「적용 조건 수」 (결정 3) 는 집계 `applied` — 원본 보기 사슬에서 적용된 최상위 조건 수 (「또는」 묶음 = 하나), 서버가 답한 보기는 그 보기 조건에서 읽는다 (행 수와 무관).
- **계산 필드 (ADR-291)**: schema 필드의 `formula` (json-formula 식 — 필드 **id** 로 저장 `'f-price' * 'f-qty'`, 패널 · 코드 보기는 key 로 표시 `names.ts`) 와 결과 `type`. 셀은 행을 읽는 단계에서 원본 행의 사본에 쓰인다 (`withComputedCells` — 보기의 조건 · 묶기 · 정렬 · 템플릿 · 보기 없는 바인딩 · 서버가 답한 행 · 필터 패널 판정 `explainViewRow` 모두 같은 셀). 정의 오류는 쓰기 거절, 행 오류는 그 셀만 `null` + `formulaCellErrors`. 엔진 · 실행 모듈은 식이 있는 문서를 처음 읽을 때 함께 lazy 로드 (`engine.ts` 로더 → `instance` · `computeCells` · `validate`; 첫 화면 모듈은 값 import 금지 — `lazyBoundary.static.test.ts`), 로드 전 읽기는 `FORMULA_ENGINE_NOT_READY` 대체 → `onFormulaEngineLoaded` 가 다시 읽는다 (Builder 는 표 목록을 **문서**에서 — store 투영은 첫 화면 뒤). 셀은 원본 행 배열 × 실행 키 (schema · 식이 읽는 `$var` · today · 언어) 와 원본 행마다 캐시 (`now()` 제외). **계산 셀을 읽어 결과를 memo · 렌더하는 새 소비처는 엔진 로드를 구독한다** — 패널은 `useFormulaEngine(schemaHasFormula(schema))` (DataGrid · 필터 패널 `ConnectionRun`), 실행 memo 는 키에 로드 여부 (`dataBinding.ts` `pending`); 구독이 없으면 로드 전 `null` 셀 판정이 남는다 (2026-10-29 `ConnectionRun`). **Why (2026-10-29)**: 보기 실행마다 셀을 새로 만들어 4x · 1만 행 × 식 5 의 변수 변경이 268 ms → 캐시 5 ms; 보기 memo 키에 엔진 로드 여부가 없어 프로젝트를 열면 계산 필드 조건의 표가 0 행이었다. 표시용 (보기 · 템플릿) 과 조회용 (서버 전송) 의 구분: 계산 필드를 조건 · 정렬 · 묶기 · 집계에 쓰는 보기는 서버로 보내지 않고 (`COMPUTED`) 1만 행까지 불러와 여기서 돈다 (`VIEW_LOCAL_LOAD_CAP`).

## 5. 상태 변수 (ADR-214)

- **날짜 편집은 ISO 원본을 보존한다 (2026-11-02)**: 선택기용 날짜·시각은 저장 값이 아니라 투영이다. 변수 격자·State·데이터 격자·RowForm은 shared `dateValueFromNativeInput`으로 원본의 시간대·초·소수초와 편집 부분을 합쳐 기존 명령에 넘긴다. 무편집은 원문을 유지하며 DST의 없는 시각·offset 없는 중복 시각은 검증에서 거절한다. **Why**: `nativeDateInputOf`의 분 단위 `slice`와 host `Date` 변환 때문에 `10:30:15.500Z`를 편집하면 초·시간대가 사라졌다 (원복 RED 2건, 명령·Undo·IndexedDB 회귀).
- **날짜 · 시각 값은 문서가 저장하고 읽는 함수는 하나다 (ADR-309, 2026-11-12)**: 날짜 계열 6종 (DateField · TimeField · DatePicker · DateRangePicker · Calendar · RangeCalendar) 의 `value` 는 ISO 글자 (범위 `{start, end}` · Calendar 다중 선택은 날짜 목록) 이고, DOM · Canvas (입력 글자 · 달력 모델) · dispatcher 시작 상태가 `catalog/runtime/dateValueRead.ts` 하나를 읽는다 — 시작 값 = `value`, 없으면 `defaultValue` (실행 중 값은 키 유무 — 지운 `null` 은 시작 값으로 돌아가지 않는다), 날짜만 있는 값 + 시각 단위 = 자정, Calendar 는 선택 모드에 맞춰 읽고 RAC 의 변경을 ISO 목록으로 쓴다 (빈 목록은 RAC 에 `null`). Canvas DateInput 은 owner 의 값을 파생 값 `_dateValue` 로 받아 owner 편집 때 다시 그려진다 (날짜만 있는 값을 시각 단위 field 에 그대로 주면 RAC 가 렌더 중 예외를 던진다).
- **날짜 runtime 파서도 값 모양을 따른다 (2026-11-02)**: RAC DateValue prop은 `parseDateValue`의 date/dateTime/zoned 분기를 쓰고, time-only는 날짜 컴포넌트에 넘기지 않는다 (날짜 전용 `parseDate` 는 시각이 붙은 값에서 파싱 오류를 낸다). 두 bullet 의 Why: [reference/rac-s2-integrations.md](../skills/composition-patterns/reference/rac-s2-integrations.md) §13.

- **모델**: `VariableDef` (`packages/shared/src/state/`). 소유자별 저장 —
  - 프로젝트 = 문서의 `ProjectVariableEntry { kind:"projectVariable", name, valueType, defaultValue, persist }` (`ProjectEntry.projectVariableIds` — ADR-286). 편집은 store 의 `define_variable` op (`createVariable` / `updateVariable` / `deleteVariable`) → sink → 문서 명령, 읽기는 store 투영 · Canvas 는 `catalogProjectVariableDefs`
  - 페이지 · 요소 = 문서의 `StateVariableEntry { kind:"stateVariable", ownerId, name, valueType, defaultValue }` (`ProjectEntry.stateVariableIds`). 노드에 `state` 필드는 없다. 편집은 `stateVariables.ts` 의 record 명령 (UI: `CatalogStateSection.tsx`)
- **가시성 · 이름 충돌 · 사용처** (Builder): `catalogVisibleVariableEntries` · `catalogVariableNameConflict` · `catalogVariableUsageCount` (`stateVariables.ts`, `dataVariables.ts`). 사슬은 요소 → 조상 → 페이지 → 프로젝트, 이름은 사슬 안에서 고유 (프로젝트 변수는 모든 사슬의 끝 — 충돌 검사가 포함한다, ADR-288). 소유자 이동은 `catalogLegacyVariableMove` (`dataVariables.ts`).
- **이름 변경은 참조까지 한 step (ADR-288, 2026-10-28)**: 세 소유자 · 코드 보기 · data sink 가 shared 명령 `renameVariable` (`commands/variables.ts`) 하나를 지난다 — entry `name` 과 함께 그 변수를 **런타임이 해소하는** `{{ old }}` 를 재작성한다. 판정 모듈 `catalog/runtime/variableReferences.ts` 는 필드마다 런타임 규칙을 따른다: string prop (instance patch props 포함) = 노드 사슬 → 페이지 → 프로젝트 (`catalogRecordVariables`), `binding.key` = 페이지 → 프로젝트 (`catalogBindingKey`), endpoint 의 `baseUrl` · `path` · `queryParams[].value` · `headers[].value` · `bodyTemplate` = 프로젝트만 (Preview `endpointTemplateFor`). `\{{` · `env` 제외, `params` 는 변수로 해소될 때만. 사용처 세기 (`catalogVariableUsageCount` · `catalogVariableUsageCounter`) 가 같은 모듈을 읽는다. 거절: `VARIABLE_NAME_SHADOWS` (새 이름이 기존 `{{ 이름 }}` reader 를 가로챔) · `VARIABLE_NAME_CONFLICT` (보이는 범위에 이름 있음) — `operationNotice.ts` 가 안내. **타입 변경 규칙 하나** `variableDefaultForType` (`catalog/runtime/variableTypeChange.ts`, 사용자 결정 2026-10-28): 새 타입에 맞는 값은 변환해 두고 아니면 비움 — `setType` (페이지 · 요소) 과 `define_variable` 적용기 (프로젝트) 가 같이 쓴다. 변수 UI 는 `components/variables/VariableTable.tsx` 하나 (Data 패널 · Design State 절).
- **읽기 `{{ name }}`**: `resolveStateTemplate` (string prop 만, 깊이 6). **Canvas 는 기본값 env · Preview / publish 는 런타임 env** — 설계된 비대칭이라 `/cross-check` 에서 결함으로 판정하지 않는다. collection 행 템플릿은 `{{ }}` 먼저 → `{field}` 나중. 미해결 이름 · `{{ env.X }}` 는 원문, `\{{` 는 리터럴 (`hasStateTemplateSyntax`).
- **경로 param `{{ params.<이름> }}`**: Preview · publish 세션이 보이는 경로의 `:param` 값을 `CatalogStateSource.params` 로 준다 (`stateTemplate.ts` `CATALOG_PARAMS_ROOT`, 같은 이름 변수가 이김). 경로가 바뀌면 `refreshState({"params"})`. Canvas 는 원문 — 설계된 비대칭. 항목 · 행 · Link 의 `href` 는 `CatalogPreviewView` 의 RAC `RouterProvider` 가 세션 `navigateTo` 로 보낸다.
- **런타임 값**: `createRuntimeState` (shared) — Preview (`catalogPreviewSession.ts`) 와 publish 에만 있다. 값 키는 `VariableDef.id`, scope `project` / `page:${pageId}` (진입 리셋) / `element:${instanceKey}`. persist 는 project 만 (`composition:runtime-state:v1:${projectId}`). 값 변경은 세션이 `subscribe` 로 바뀐 변수를 받아 `refreshState(names)` 로 그 독자만 다시 해석한다 — 전체 revision 구독 금지.
- **쓰기 액션**: 문서에는 `InteractionEntry.actions[] { opcode:"setState" }`, 실행은 shared `dispatcher` → `DispatchDeps.writeState`.
- **컴포넌트 입력 변수 (ADR-294)**: `variable` property 의 변수 (`StateVariableEntry.input` — template 루트 소유) 는 값이 없다 — 그 원본을 품은 instance 가 넘긴 값 (리터럴 · `!var` 참조) 이고, 없으면 기본값. 읽는 곳 넷 (`{{ }}`·PropVar env · 보기 `!var` · 규칙 `!var` · 패널) 이 `runtime/inputVariable.ts` `resolveInputVariable` 하나를 지난다 (경계 = record 의 `componentBoundariesOf` 또는 해석 경로의 `instancePathBoundaries`). runtimeState 는 `derive` 로 읽고 쓰기를 `input-read-only` 로 거절, 문서는 Set state 를 `INPUT_VARIABLE_READ_ONLY` 로 거절. 부모 변수 쓰기는 `refreshState` 가 `inputVariableDependencies` 로 전이 폐쇄해 안쪽 독자까지 다시 읽는다 — 새 독자를 만들면 이 함수를 지나게 한다 (기본값을 직접 읽으면 instance 값이 빠진다).

`showWhen`·`presentWhen`·RAC render props 값과 상태 주체 주소는
[RAC 조립 계약](../skills/composition-patterns/rules/domain-rac-composition.md)을 따른다.
상태 변수 `{{ }}`와 구분하고 owner 변경 뒤 consumer 재평가·저장 주소 보존을 확인한다.

## 6. Interaction (ADR-131 의 events / actions 를 대체)

- 문서 정본은 `InteractionEntry { kind:"interaction", ownerId, address?, trigger, actions }` (`ProjectEntry.interactionIds`) — interaction 이 자기 소유 노드를 가리킨다 (노드가 `props.onPress: "ev1"` 로 가리키지 않는다). 편집은 `catalogRuntime/interactions.ts` 의 명령.
- **Do 목록 (ADR-284, contract 50)**: `actions` 는 순서대로 실행되고 실패한 Do 에서 멈춘다 (dispatcher `executeInteractionRule` — 「Do N: 사유」). Preview 변환 (`ruleOf` → `actionOf`) 은 한 Do 라도 그 record 에서 풀리지 않으면 규칙을 내지 않는다 — 뒤 Do 가 앞 Do 를 전제한다. Do 를 읽는 곳 (색인 · 복사 · detach · createComponent · swap · 변수 이동 · Canvas 대상 지정) 은 모든 Do 를 돈다 — 첫 Do 만 보면 뒤 Do 의 page · 변수 · 대상이 dangling 이 된다. 조건부 실행 · 분기는 없다. **안쪽 Do (2026-10-31)**: toast Do 의 `onAction` (S2 `ToastOptions.onAction` — 버튼을 누르면 실행, 바깥 event 를 읽는다) 은 Do 목록을 품는다 — Do 를 읽는 곳은 `document/interactionActions.ts` (`catalogActionsDeep` · `mapCatalogActionsDeep` · `filterCatalogActionsDeep`) 로 안쪽까지 돈다. `rule.actions` 를 직접 돌면 안쪽 Do 의 참조가 빠진다.
- **컬렉션 drag & drop (ADR-284 Phase 5)**: ListBox · GridList · Tree · Table 의 drag When (`onReorder` · `onMove` · `onInsert` … — 목록은 `concepts/collectionDragDrop.ts`) 은 `useDragAndDrop` 옵션이다 (인자는 이벤트 객체의 필드, `argFields`). Preview 는 그 규칙이 있는 목록만 lazy `catalogDragAndDrop.components.tsx` 로 `dragAndDropHooks` 를 준다 — drag type 은 바인딩 collection (같은 collection 의 목록끼리만 받음), 다른 목록에서 온 drop 의 `keys` 는 drag data 에서 다시 읽는다. 놓은 쪽은 move Do 의 `dropPosition` 값 (`!event.target.dropPosition`), 열 값 쓰기는 update Do 의 `field` — 조건부 Do 없이. 세션의 Tree 역할 (`fieldMap.value` · `children` · `parentId`) 은 Tree 바인딩에서만 읽는다 — 개수 머리 Text 의 `value` 가 항목 key 를 바꾸던 결함 (2026-10-27).
- **등록표는 손으로 쓰지 않는다 (ADR-280)**: `CAPABILITY_REGISTRY` · `IMPLICIT_STATE_SOURCES` 는 RAC 개념 파일 (`packages/shared/src/interactions/concepts/*.ts` — RAC 문서 절 하나 = 개념 하나, 이름마다 설치 d.ts `satisfies`) 과 컴포넌트 spec (`componentInteractionSpecs.ts` — 유일한 손 입력) 에서 `deriveRegistry` 가 만든다. 새 컴포넌트의 When · Do 는 spec 한 줄 (개념 · owner) 이고, type 마다 쓰는 이름이 그 RAC props 에 없으면 `RAC_SURFACE_CHECK` 가 컴파일을 막는다. 개념 표는 RAC 의 절 구조를 옮긴 묶음일 뿐 새 어휘가 아니다 (사용자 원칙 2026-10-22). **유도 Do 층 (ADR-287)**: 그 위에 `withReferenceCapabilities` 가 catalog binding `accepts` 에서 prop 마다 Do 를 유도해 얹는다 (`referenceCapabilities.ts` — 값 prop `set<Prop>` · boolean `<prop>On` · `<prop>Off` · `toggle<Prop>`, 이벤트 · aria · `default*` · DOM 전역은 제외). 개념 Do 의 prop · id 가 이긴다. 레퍼런스 API 표 (로컬 skill 의 `<Component>.md`) 는 정본이 아니라 게이트 oracle 이다 (`referenceCapabilities.static.test.ts` — 행마다 유도 Do 또는 보류 사유). 노드 자기 `isDisabled` · `isReadOnly` Do 는 조상만 막는다 (`inherited:*` guard).
- **Preview/Publish 의 상태는 첫 render 부터 controlled**: running Preview (`setRuntimeProps` 가 있는 렌더) 의 binding 은 상태 prop 을 `catalogControlledProps` (`catalog/runtime/runtimeStateProps.ts`) 로 넘긴다 — 값은 항상 정의 (`undefined` 로 uncontrolled 에 떨어지는 render 금지 — react-stately 는 `value !== undefined` 로 판정), RAC 의 변경은 record 의 runtime 값으로, `default*` 와 controlled prop 을 같이 넘기지 않는다, key 에 상태값을 넣지 않는다 (remount 금지). 현재 값은 `catalogRuntimeStateOf` 하나 (runtime override ?? 시작 상태 — 그룹이 저장한 선택 · 펼침, ADR-308) 를 렌더와 dispatcher 가 같이 읽는다. Why: rac-s2-integrations.md §13.
- **ComboBox 는 선택과 입력 글자를 둘 다 controlled 로 받는다 — 글자는 `CatalogComboBox` 가 쓴다**: RAC 는 `selectedKey` · `inputValue` 가 둘 다 controlled 면 글자 동기화를 쓰는 쪽에 맡긴다 (`useComboBoxState` — 레퍼런스 「Fully controlled」). `onSelectionChange` 가 key 와 그 항목 글자를 한 번에 쓰고 (blur 의 같은 key 호출 = 글자 되돌림, `null` = `allowsCustomValue` 의 custom 값이라 글자를 둔다), 다른 곳의 선택 (규칙 · load) 과 늦게 온 항목 글자는 `ComboBoxStateContext` 를 읽는 자식 effect 가 쓴다. 항목 글자는 `selectionManager.collection` (전체) 에서 — `state.collection` 은 닫혀 있을 때 마지막으로 보인 목록이다. 글자를 쓰는 render 는 `menuTrigger: "manual"` 이다 (닫힌 · focus 된 칸에 글자가 오면 RAC 가 타이핑으로 보고 다시 연다). Why: rac-s2-integrations.md §13.
- **open 은 trigger 의 것**: overlay 본체 (`CATALOG_OPEN_BODY_TYPES`) 의 자기 `isOpen` 은 trigger context 를 이긴다 (설치 RAC `Modal.mjs:88-90`) — 본체를 controlled 로 두면 trigger press 가 본체를 못 연다. 그래서 trigger (`CATALOG_OPEN_TRIGGER_TYPES`) · picker (`CATALOG_OPEN_PICKER_TYPES` — ComboBox 포함) 가 `isOpen` 을 받고, 본체에 건 open 규칙은 dispatcher 의 `stateOwnerOf` 가 trigger 로 보낸다. 본체는 trigger 없이 서거나 자기 `isOpen` · `defaultOpen` 을 작성했을 때만 자기 open 을 갖는다 (`catalogOpenOwnerOf` → `undefined`). 「아무도 제어하지 않음」 (`null` — `CATALOG_UNCONTROLLED_OPEN_TYPES` 안) 은 그것과 구별한다. Design 패널도 trigger · picker 안 본체의 Open · Initially open 을 내지 않는다 (`catalogOwnerDecidedProps` — `catalogOpenHostOf`, 사용자 결정 2026-11-11). **Why (2026-10-23)**: `!owner` 로 읽어 ComboBox 의 Popover 가 `isOpen=false` 로 고정, Preview · publish 에서 목록이 열리지 않았다.
- **capability 쓰기 순서**: 값 해소 (`!param` · `!event.<arg>` · 리터럴) → 현재 유효 상태 → 결과 (`op` add · remove, single 은 교체) → RAC 제약 (`guards` — disabled · readOnly · 빈 선택 금지 · selectionMode · disabledKeys, 그룹이 내려주는 disabled · readOnly 포함) → 결과 전체 쓰기. 막히면 report (조용한 no-op 금지). 범위는 RAC 가 clamp 하므로 guard 없음. 래퍼 (`I18nProvider` · `display: contents` marker · calendar picker) 는 `withRuntime` 이 준 핸들러를 안의 RAC 요소에 넘긴다 (`ForwardingI18nProvider` · `ForwardingMarker` · `catalogForwardHandlers`).
- **Form submit · reset 은 DOM ref**: dispatcher `invokeImperative` → `requestSubmit()` (RAC validation 을 거친다) · `reset()` (controlled field 는 `useFormReset` 으로 첫 값). 작성한 목적지가 없는 Form (`action` 없음 · `method` ≠ `dialog`) 만 `onSubmit` 에서 `preventDefault` — 목적지가 있으면 HTML 제출 그대로.
- **패널은 RAC 가 지금 받는 것만 (ADR-281)**: When · Do 선택지는 `exposure.ts` (`exposedTriggerGroups` · `exposedCapabilities`) 가 고르고, 판정은 dispatcher 의 첫 검사와 같은 `declaredRefusal` (`constraints.ts`) 이다 — 패널과 실행이 다른 답을 내지 않는다. 예외 하나: `selectionMode: "none"` 대상의 선택 Do 3 (선택 · 해제 · 전체 해제) 은 패널이 모두 숨기고 안내하지만 (`hiddenBySelectionMode` · ADR-287 사용자 결정 3), dispatcher 는 추가만 막는다 — 해제 · 전체 해제는 RAC 가 받는 상태 초기화다 (ios-list 의 Cancel 이 모드를 끄고 선택을 비운다). 막힌 규칙은 지우지 않고 표식만. When 라벨 키는 등록표 그룹에서 유도 (`interactions.trigger.<개념>.<callback>`), `!event` 인자 이름은 개념의 `args` (`eventArgNames`).
- **조상 상속 (ADR-281)**: page 루트 · frame 의 `isDisabled` · `isReadOnly` · `isRequired` · frame 의 `locale` (+ page 루트 `colorScheme`), 로딩 중인 Skeleton · SkeletonCollection 의 `isDisabled` (ADR-314 — `CATALOG_SKELETON_DISABLED_TYPES` 만 받는다) 는 `runtime/inheritedProps.ts` 하나를 DOM (`CatalogDomNode` — RAC `Provider` 표 `providerContexts.ts` + `I18nProvider`) · Canvas (`presence.ts` 파생 `isDisabled` · `isReadOnly`) · guard (`getConstraintContext().inherited`) 가 읽는다. page 루트의 `locale` 은 작성 값이 아니라 사이트 언어 (`ProjectEntry.site.lang`) 다 — composition root 가 `body` record 에 넣고 (`siteLocale`), Canvas 의 환경 locale 도 같은 값이다 (ADR-286, 사용자 2026-10-28 「page 에서 제거하고 사이트 설정에」). 받는 쪽 flag 는 OR (조상의 `true` 가 이김) — palette 원본이 `isDisabled: false` 를 기본값으로 실어 record 가 작성한 `false` 와 구별하지 못한다. **Why (2026-10-22)**: RAC 규칙 (자식 자기 값 우선) 만 따르면 상속이 어떤 palette 컴포넌트에도 닿지 않았다. `colorScheme` 은 Do 전용 (`editorHidden`) → 세션 `setColorScheme` 이 `applyTheme` 을 그 색 모드로. page 루트의 flag 3 과 frame 의 `isRequired` 도 Do 전용이다 (사용자 결정 2026-11-11 — page 는 자신이 disabled · required 일 수 없어 Behavior 구획이 page 의 상태로 읽혔다). frame 의 Disabled · Read only 만 패널에서 작성한다.
- **원본 규칙의 instance 상속 (ADR-281)**: 원본 template 노드의 규칙은 모든 instance 에서 실행되고, instance 는 자리 patch 의 `interactions` 맵 (원본 규칙 → `"off"` \| 자기 규칙) 으로 끄거나 바꾼다. 패널 (`catalogInheritedInteractionsOf`) 과 Preview (`recordsOfOwner`) 는 `effectiveInteractionsOf` (`catalog/resolution/effectiveInteractions.ts`) 하나를 읽는다 — 한쪽만 바꾸면 「안 보이는데 실행」 이 돌아온다. ADR-262 반영 · Reset all 이 맵을 다룬다.
- **capability 대상 = 장소 참조, 실행한 record 기준 해소 (ADR-283)**: `action.target` 은 `{ nodeId }` (page 노드 · 같은 template 의 규칙만 template 노드 — 그 밖은 `TARGET_IN_TEMPLATE`) · `{ address }` (page instance 안 자리) · `{ local }` (규칙 주인이 든 원본 template 의 자리 — 주인이 template 노드일 때만) · `{ unset: true }` (swap · detach 로 자리가 사라진 규칙 — 남기고 패널 「대상 없음 · 다시 지정」, Publish 경고) — `CatalogNodeRef` 를 `showWhen` 의 상태 주체 참조와 공유. 실행 record → 대상 record 는 `resolveCapabilityTarget` (`catalog/runtime/capabilityTarget.ts`) 하나를 Preview 변환 (`catalogPreviewInteractions.ts` `ruleOf`) 과 패널 (「이 자리에서는 대상에 닿지 않음」) 이 읽는다 — 행 record (`rowIndex`) 는 실행 record 와 공유해야 하고, 참조가 이름 붙인 instance 단계는 후보의 조상에 있어야 하며, `local` (과 같은 template 의 `nodeId`) 은 실행 record 체인에서 규칙 주인의 원본 루트 (`catalogOriginRootOf` — `templatePath[0]` 이 아니다: `local.instances` 가 있으면 가장 안쪽 정의 기준) 를 그리는 record 아래만. 참조 색인 (`graph.ts` `referencedIds`) 은 주소의 모든 project id 를 든다 — 중간 instance 의 swap · 추출 · 삭제가 규칙을 찾는다. 대상 참조를 지나는 명령: clone (`mapNodeRefIds` — `local` 도) · detach (`reanchorInteractions` — 사본 `{ nodeId }`, 못 옮기면 `unset`) · createComponent (`rewriteTargetsIntoComponent` · `rewriteAddressesThroughExtracted`) · swap (`remapThrough`, 없으면 `unset` + 보고 `targetsUnset`) · 구조 이동 (transaction 이 옮겨진 subtree 의 규칙을 다시 검증). **Why (2026-10-26)**: 대상이 `recordsOfSource(targetId)[0]` 이라 원본 규칙 · 행 규칙이 눌린 instance · 행이 아니라 첫 것을 바꿨다 (G0 RED).
- **규칙 값 = 리터럴 또는 값 전체 참조 (Value 칸 「값 고르기」, 2026-10-26)**: `!event.<인자>[.경로]` (RAC 콜백 인자) · `!item.<key 인자>[.필드]` (owner 가 묶인 collection 에서 그 key 의 항목 — `useListData.getItem`, `key` 또는 single 선택이면 한 항목, 아니면 배열) · `!var.<변수 id>[.경로]`. 해석은 `interactions/valueRef.ts` `resolveRuleValue` 하나를 dispatcher 의 모든 값 칸 (setState · capability · body · 목록 데이터) 이 쓰고, 항목은 Preview 세션 `itemsByKeys` (보이는 항목 — 편집 기록 포함), 변수는 `readVariable` (writeState 와 같은 scope). 패널 선택지는 `valueOptions.ts` 가 When 의 `args` · owner 바인딩 schema · 보이는 변수에서 유도 — 컴포넌트별로 손으로 적지 않는다. 문서 검증 (`graph.ts` STATE_VALUE_TYPE) 은 참조 값을 건너뛴다. **Why**: Set state 만 값을 해석하지 않아 사용자가 적은 `selectedKeys.name` 이 글자 그대로 Text 에 나왔다.
- **`append` · `update` · `remove` 는 세션의 편집 기록 (`useListData`) (ADR-281 결정 3 의 2차)**: 규칙의 편집은 `CatalogPreviewSession` 이 collection id 별로 순서대로 들고 Builder 의 항목 위에 다시 적용한다 (`itemSources` → `replayItemEdits` — `catalogBoundRows` 가 읽는 것). 항목 key 는 바운드 목록과 같은 `getItemKey` (§4 「행 진입」 의 key 순서). data store · 문서는 바뀌지 않는다 (편집 기록은 Preview 실행 상태). Canvas 는 작성 데이터를 그린다 — Preview 와 항목 수가 다른 것은 설계된 비대칭.
- **`useListData` 위치 편집**: `insert` · `insertBefore` · `insertAfter` · `prepend` 는 세션 `insert(collectionId, CatalogListPosition, value)`, `move` · `moveBefore` · `moveAfter` 는 `move(collectionId, keys, to)` — 편집 기록 `insert` · `move` 를 `replayItemEdits` 가 적용 (`positionIndex`). `removeSelectedItems` 는 dispatcher 가 `selectedKeysOf` (그 collection 에 묶인 record 들의 `catalogRuntimeStateOf(…, "selectedKeys")` 합집합) 로 `remove`.
- **`reload` (`useAsyncList.reload`)**: 세션이 collection 을 채우는 조회 endpoint (`targetCollection` — `catalogData.ts` 가 문서 entry 의 `targetCollectionId` 에서 붙인다) 를 진행 중 제출 (`trackSubmit`) 뒤에 실행하고, 결과를 `reloadedItems` 로 Builder 항목 대신 쓴다 — 그 collection 의 편집 기록은 지운다, Builder 가 다른 `runtimeData` 를 보내면 그쪽이 이긴다.
- **조회 endpoint 의 `{{ }}` (한 건 조회 — router loader)**: 경로 · query 의 템플릿은 세션의 `endpointTemplateFor` (프로젝트 변수 · `params`, 빈 값 = 미해결) 로 풀고, 템플릿 endpoint 가 채우는 collection 은 풀린 URL 이 마지막 읽기와 다를 때만 `loadRouted` 가 `reload` 한다 (navigate · 데이터 수신 때). 풀리지 않는 템플릿은 보내지 않는다 — shared 실행기 · Builder `executeApiEndpoint` 둘 다 거부.
- **읽는 중 상태 (`useAsyncList.loadingState`)**: 세션의 `loadingStates` (`reload` 가 `loading` → `idle` · `error`) 를 `boundRows` 가 바인딩 행 결과 (`CatalogBoundRows.loadingState`) 에 싣고, resolver 가 그 owner record 의 `loadingState` (`LOADING_STATE_TYPES` — instance → template root 로 넘김) 로 바꾼다. Skeleton 은 연결이 없다 — 안쪽에 연결된 노드 중 하나라도 `loading` 이면 `isLoading` (없으면 작성값, `skeletonContentLoading` · 갱신 영역 `planBindingOwners`). DOM TableBody 는 `loading` + 빈 본문에서 S2 진행 원. Canvas 의 rows 는 상태를 싣지 않는다 — 작성 값 그대로 (설계된 비대칭).
- **load 인자 (`useAsyncList.load({cursor, filterText, sortDescriptor})`)**: 세션 `loadArguments` 가 collection 별로 들고 `endpointTemplateFor` 가 endpoint 템플릿에 넣는다 (빈 값의 쿼리는 뺀다 — `ENDPOINT_LOAD_ARGUMENTS`). `reload` = 첫 페이지 (cursor 지움), `loadMore` = `cursor` 로 다음 페이지를 보이는 항목 뒤에, `setFilterText` · `sortCollection` = 그 값으로 `reload`. 다음 cursor 는 `loadCollectionEndpoint` 가 `responseMapping.cursorPath` 에서. 바운드 Table 정렬은 endpoint 가 `sortDescriptor` 를 읽으면 `serverSort` (열 → 필드 key) — 그 Table 은 `serverSortedTables` 라 resolver 가 클라이언트 정렬을 하지 않는다. Builder 실행은 load 인자를 빈 값으로.
- **「더 보기」 표시 창 (ADR-310 Phase 1, 2026-11-15)**: 세션이 연결된 목록마다 (collection + 연결 노드 id) 표시 창을 갖고 100 에서 시작한다 (`displayWindows`). 끝 sentinel 은 불러온 행이 창 밖에 남았거나 (`session.moreLoaded`) 다음 페이지가 있을 때 나오고, `showMore` 가 창을 늘리거나 다음 cursor 로 받은 뒤 늘린다 — cursor 가 없으면 아무것도 하지 않는다. `reload` (검색 · 정렬 포함) 는 창을 처음으로. 표본 대상 (ADR-157) 의 `rowCount` · `rowsShown` 으로 sentinel 을 판정하지 않고, 다음 페이지가 불러오는 중이거나 새 행 없이 끝났을 때도 창을 늘리지 않는다 (아니면 sentinel 호출이 끝없이 돈다). 상세 · Why: [reference/row-repeat.md](../skills/composition-patterns/reference/row-repeat.md) 「표시 창 · 쪽 · Tabs 항목 노드」.
- **반복 표시 `repeat` · 반복 구간 · Code 보기 (ADR-310 Phase 3 · 5 · 6, contract 67)**: 연결된 목록은 `NodeEntry.repeat: true` 항목 하나를 데이터 행마다 반복하고, 표시 없는 항목은 고정 항목으로 제자리 (앞 · 뒤) 에 그린다. resolver 의 세 경로가 `repeats(id)` 하나로, 행이 닿는 항목 단계는 shared `catalogRowItemGroups` 로 판정한다. 표시는 명령만 붙이고 뗀다 (`markRowTemplates` · `setRowTemplate` · `clearRowTemplates` · `rowTemplateInsert`). 반복 구간의 행은 resolver `repeatRows` 가 처음 맞는 곳에서 읽는다 — 그 노드 자신의 `binding` (key 없는) → Select 값 모양 (`selectValueRows`) → 바깥 행의 하위 행 (`fieldMap.children`) → owner 의 행 → Pagination 쪽 번호 (`paginationRows`) → Table 열 선택 메뉴 (`chooserRows`). 구간마다 자기 `LoadMoreItem` 을 둔다. 반복 행 안 편집은 행 record id 가 아니라 템플릿 자리로 적는다. Code 보기는 반복 항목을 렌더 함수로 쓰고 그 본문은 읽기 전용이다. 상세 (Table 템플릿 Cell · 그룹 항목 key · key 중복 경고 · 끌기 경계 · Why): [reference/row-repeat.md](../skills/composition-patterns/reference/row-repeat.md) — 반복 · 고정 항목 · 구간을 고치기 전에 읽는다.
- **표시 방식 「페이지」 · 조회 단위 (ADR-310 Phase 7, 2026-11-15)**: 목록 노드의 `rowDisplay` (`pages` · `size`) 를 세션이 읽어 쪽 목록마다 조회 단위 (`pageUnits` — collection + 목록 노드) 를 둔다. 원격 단위의 응답 (`loadPageUnit`) 은 그 목록에만 싣는다 — collection 의 불러온 항목 · 편집 기록은 건드리지 않는다. Pagination 은 `pagesOf` 로 목록을 가리키고 번호는 `repeatRows` 의 `paginationRows` (row source 의 `pages` 속성, Builder 에는 없음) 다. 쪽 바꾸기는 목록과 그 Pagination 을 다시 해석한다 (`refreshNodes`). Why: row-repeat.md 「표시 창 · 쪽 · Tabs 항목 노드」.
- **Table 실행 — 가상 스크롤 · 행 창 · 표 상태 (ADR-310 Phase 8 · ADR-315)**: 행 record 아래 React key 는 템플릿 자리다. 가상 Table 은 정렬 뒤 행 중 창만 record 를 만든다 — record 를 읽는 새 소비처는 모든 행에 record 가 있다고 가정하지 않고, 창 이동은 「다른 것은 바뀌지 않았다」 가 전제다 (데이터 · 정렬 · 문서 변경은 `refreshRows` · `refreshNodes`). 실행 상태는 세션의 표 상태 하나 (`runtime/tableState.ts` — 세션의 `tables` 가 갖는다, `runtime/catalogTableController.ts`), 쓰기는 `session.tables.setTableState` 하나 — 데이터 조각만 행을 다시 읽고 열 조각은 행 source 를 부르지 않는다. 정렬 · 거르기 · 집계는 보기의 구현 하나 (`viewSortOrder` · `viewRowsPassing` · `viewAggregateOf`) — 새 비교 · 집계를 따로 만들지 않는다. 표 상태 → 요청은 번역 하나 (`runtime/tableStateQuery.ts` — `view/serialize` 를 값으로 import 하지 않는다), 서버가 쪽을 나누는 표는 요청이 조각 전체를 담을 때만 맡긴다 (`catalogTableSliceServable` — 줄여 보내지 않는다, 아니면 `VIEW_LOCAL_LOAD_CAP` 까지 불러와 로컬). 열 투영은 resolver 한 곳 (`resolution/tableColumns.ts`), 칸 병합 판정은 `runtime/tableCellMerge.ts`, 칸 범위 선택은 `runtime/tableCellSelection.ts` (D1 예외 — [ssot-hierarchy.md](ssot-hierarchy.md) §1). 편집 격자 (ADR-317): reference 「편집 격자」 절. Worker 는 두지 않는다 (ADR-315 Phase 7 판정). 상세 (묶음 · 계층 · 상세 행 · 행 고정 · 서버 선언 조회) · Why · 실측: [reference/table-data-grid.md](../skills/composition-patterns/reference/table-data-grid.md) · ADR-315 breakdown §9.
- **Tabs 항목 = 노드 (ADR-310 Phase 2, 2026-11-15 · contract 67)**: Tab 과 TabPanel 은 key (Tab `id` ↔ TabPanel `itemId`) 로 짝인 노드다 — Tabs 의 `items` 배열은 없다. 놓은 Tabs 는 원본의 루트 slot 으로 TabList · Tab · TabPanel 을 모두 자기 노드로 갖는다. Tab 의 삭제 · 복제는 같은 명령에서 짝 TabPanel 을 지우거나 새 key 로 복제한다 (`catalogPairedTabPanels` → `removeTargets` · `duplicateNodes`), 「+」 는 Tab + TabPanel 을 한 명령으로 넣는다. Why: row-repeat.md 「표시 창 · 쪽 · Tabs 항목 노드」.
- **목록 끝 · 입력 검색 (S2 자동 연결)**: 연결된 ListBox · GridList · Table · Tree · Menu 는 「더 보기」 조건 (창 밖 행 또는 `session.pages`) 이면 DOM 이 끝에 RAC `*LoadMoreItem` (`catalogLoadMoreItem`) 을 두고 세션 `showMore` 를 부른다 (picker 안 ListBox 는 picker 의 바인딩 — `boundOwnerOf`). 바운드 ComboBox · Autocomplete 의 목록이 `{{ filterText }}` endpoint 면 (`session.serverFilterOf`) 입력이 `setFilterText` 로 가고 클라이언트 필터를 끈다 — 서버 필터가 문서 `defaultFilter` (`contains` · `startsWith`) 를 이긴다. 같은 collection 의 늦은 응답은 `loadSequence` 로 버린다. 바운드 Select · ComboBox 의 로딩 스피너는 `catalogPickerSpinner`. 상세 (`defaultFilter` 함수 · 스피너 자리): rac-s2-integrations.md §13.
- **트리 데이터 (`useTreeData`)**: 바인딩 `fieldMap.children` (중첩 배열) 또는 `fieldMap.parentId` (평면 행의 부모 key) 를 Tree에서 고른다. `catalogBoundRows` 는 평면 행일 때 전체 목록을 부모 key로 색인한 다음 루트 행에 `children` 을 싣고, resolver 가 바운드 Tree 의 행 TreeItem 안에 같은 행 template 을 하위 행마다 다시 놓는다 (`nestTreeRows` — template 의 표본 하위 TreeItem 은 빠진다, instance 「TreeItem/Default」 는 template 루트로 내려가서). TreeItem 은 `CATALOG_ROW_ITEM_TYPES` 다 (Why: row-repeat.md 「트리 행」). Preview 세션은 중첩 배열에는 `replayItemEdits`, 평면 행에는 `replayFlatTreeEdits` 를 사용한다 — `append` · `insert` · `prepend` 의 `parent`, `move` 의 `toParent` (`null` = 맨 위), key 를 받는 편집은 트리 어느 단계든 찾는다.
- **Tree 선택 스타일**: TreeItem origin 의 `TreeItemContent` 첫 자식은 `Checkbox[slot=selection]` 이고, `selectionStyle=checkbox` 와 선택 가능한 `selectionMode` 에서만 Canvas presence · DOM 에 나타난다. Tree의 스타일 변경은 하위 selection Checkbox 의 presence 를 갱신한다. 노드가 없는 행에 붙는 자동 체크박스는 공용 `Tree` 의 데이터 행 경로에만 둔다 (`autoSelectionCheckbox` — 늘 그리면 DOM 에만 체크박스가 생긴다). Why: [reference/rac-s2-integrations.md](../skills/composition-patterns/reference/rac-s2-integrations.md) §13.
- **보기를 요청에 싣기 (ADR-284 Phase 2)**: endpoint 의 `querySerialization` (`suffix` · `body` · `none`) 이 있고 그 collection 을 읽는 바인딩들의 보기가 정의 기준 하나면 세션 `serverView` 가 `serializeViewQueries` 결과를 `loadCollectionEndpoint` 의 `extra` 로 넘긴다 (건너뛴 조건은 파라미터 없음). 그 응답은 보기의 결과다 — `boundRows` 가 `query.served` 를 붙이고 `catalogBoundRows` 는 다시 거르지 않는다 (못 보낸 조건 수 = `unsent`). total 은 응답의 `totalPath` 이고 첫 페이지마다 지운다. 변수 쓰기 (`reloadForVariables` — 글자 비교면 300 ms) · 문서 변경 (receiver 구독) 이 `loadRouted("filtering")` 을 부르고, `loadPage` 는 collection 별 `AbortController` 로 앞 요청을 끊는다. 보기가 빠진 collection (`viewLoaded`) 은 서버가 거른 행을 버린다. serializer 는 `collections` barrel 로 내보내지 않는다 — **Why**: barrel 로 내보내자 Preview initial 이 +3,685 B (세션은 lazy chunk 인데 serializer 가 initial 공용 chunk 로 옮겨갔다).
- **load 반환 선택 (`useAsyncList` load `selectedKeys`)**: `loadCollectionEndpoint` 가 `responseMapping.selectedKeysPath` (key 배열 · `"all"`) 를 읽고, 세션 `onLoadedSelection` → `CatalogPreviewInteractions.selectLoaded` 가 그 collection 에 묶인 record 의 runtime 선택에 쓴다 — `reload` 는 교체, `loadMore` 는 합침 (레퍼런스 reducer), Select · ComboBox 는 첫 key 의 `selectedKey`, `selectionMode: single` 목록은 하나만. 반환이 없으면 선택은 그대로. endpoint 편집기는 `cursorPath` · `selectedKeysPath` 를 draft 로 보낸다 (`toEndpointDraft` — `""` = 지움). Why: rac-s2-integrations.md §13.
- **입력 변수의 occurrence 값과 서버 응답 (ADR-294 수리, 2026-10-31)**: 입력 prop은 instance 원본 `props`에 그 발생 경로의 descendant override를 기존 resolver 순서로 합친 값이다. override의 `!var`도 갱신 의존성에 포함한다. 서버 보기 요청은 실제 그려진 instance 경로로 해석하고, 응답의 `served` 판정은 query 구조와 해석된 참조값을 함께 비교한다. 같은 collection의 instance 입력이 다르면 전체 행을 기존 상한까지 로드해 각 보기에서 평가한다. **Why**: 중첩 role override가 저장돼도 `admin`으로 표시됐고, 기본값 `male` / instance `female`에서 `/users?gender=male` 요청과 남성 행이 표시됐다 — 두 통합 반례 및 경로별 원복 RED로 확인했다.

- **컴포넌트 event (ADR-294)**: 원본 규칙의 Do `emit { propertyKey, value }` 는 그 규칙 노드를 담은 정의 (`emitDefinitionOf`) 의 경계로 나가고, instance 규칙의 When `property:<key>` (인자 `!event.value`) 가 받는다. 받는 쪽은 RAC 핸들러가 아니라 수신 색인 (`catalogEventReceivers` — 경계 `occurrence` = 그 instance 를 그리는 record id + 층 id → key → 규칙) 이고, 실행은 누른 record 의 경계를 안쪽부터 (`componentBoundariesOf` — record 부모 사슬 × 접힌 층) 걸어 같은 정의의 첫 경계. 받는 규칙 0 = 성공 `listeners: 0`. 같은 Outer 둘 안의 같은 J · 행마다 instance 가 record id 로 갈린다 — 식별자를 문서 id 로 줄이면 합쳐진다 (원복 RED).
- **`callEndpoint` 는 제출 전용 실행기 (ADR-281)**: `submitApiEndpoint` → `submitCollectionEndpoint` — 요청 공유 0 (조회의 `createCollectionEndpointExecutor` 는 endpoint id 로 진행 중 요청을 공유해 둘째 body 를 버린다), 성공 = `response.ok` (204 · 빈 본문 · 비 JSON 도 성공), 실패는 Preview runtime 이 `[interactions]` 경고 + toast. body 는 `!event.formData` (form 요소 `FormData`, 같은 name 여러 값은 배열) 또는 리터럴. **필드 오류 · 뒤 Do (S2 체크리스트 부록 D.3 2단계, 2026-11-23)**: endpoint 의 `responseMapping.errorsPath` 가 있으면 거절 응답 (과 오류를 담은 정상 응답) 의 필드 오류를 `EndpointSubmitError.validationErrors` 로 받아 규칙 주인의 Form (자신 또는 가장 가까운 Form) 의 실행 값 `validationErrors` 로 쓴다 (S2 Form — 같은 `name` 필드, 칸 확정 때 RAC 가 지움, 성공이 비움, 그때는 toast 없음). callEndpoint 는 `settled` 를 돌려주고 dispatcher 가 남은 Do 를 응답 뒤에 이어 실행 · 실패면 멈춘다 (사용자 결정 1 — 「저장됨」 toast 가 필드 오류 위에 뜨지 않게). Do 목록을 실행하는 새 호출부는 `catalogFinalOutcome` 으로 끝 결과를 받는다 — 첫 결과만 보면 응답 뒤의 실패를 놓친다.
- **필드 검증 규칙 `validate` (S2 체크리스트 부록 D.3 2단계, 2026-11-23 — 사용자 결정: 함수가 아니라 조건 규칙)**: 15종 필드의 `validate` prop = `[{id, when: ViewCondition | ViewConditionGroup, message}]` (`catalog/document/validationRules.ts`, 값 종류 `validationRules`). 조건의 필드는 `data:field:$value` (자기 값 — DateRangePicker 는 `$end` 도) 또는 같은 Form 의 `name`, 값은 리터럴 또는 `!form.<name>`. DOM 은 `fieldValidation.ts` 가 데이터 보기 평가기 (`explainViewRow`) 로 판정하는 RAC `validate` 함수를 준다 — 새 비교를 따로 만들지 않는다. 다른 칸을 읽는 규칙은 그 칸 record 를 구독해 (`watchesChildren`) 다시 판정한다. Canvas 는 그리지 않는다 (검증은 실행 상태).
- **Select 값 모양 (S2 `renderValue`, S2 체크리스트 §9.3 — 2026-11-23 저장 모양 사용자 확인)**: SelectValue 의 자식 노드가 값 모양이고 (원본 SelectValue = slot `value`), `repeat` 노드는 그 Select 의 항목마다 반복된다 — resolver `repeatRows` 가 노드 자신의 binding 다음으로 `selectValueRows` (Select 바인딩의 행, 정적 Select 는 항목의 `id` · `label`) 를 읽고 사본마다 행 key 를 붙인다 (`selectValueRuns` — 첫 행도). 판정 `document/selectValueShape.ts` `catalogInSelectValue` 를 graph 검증 (`repeat` 허용) · 「행 템플릿으로 사용」 · Code 보기가 같이 쓴다. 보이는 것: Canvas 는 저장 선택 (`selectValueTemplate.ts` — `catalogValueTemplateHidden`, SelectValue 파생 `_valueTemplate` 이 글자 대신 상자), DOM 은 RAC SelectValue `state` 의 key (`CatalogSelectValueRowGate`). 새 소비처는 이 두 판정을 읽는다.
- **고를 수 없는 날짜 `isDateUnavailable` (S2 체크리스트 부록 D.3 2단계, 2026-11-23 — 사용자 결정: 요일 · 날짜 목록 · 데이터 표)**: 날짜 컴포넌트 5종 (`CATALOG_UNAVAILABLE_DATE_TYPES`) 의 prop `{weekdays, dates}` (`catalog/document/unavailableDates.ts`) 와 노드 자신의 binding (`fieldMap.unavailable` · `unavailableEnd`, 조건은 binding 의 보기) — `catalogBoundRows` 가 보기를 통과한 모든 행의 날짜를 `unavailableDates` (기간 = ISO 구간 `start/end`) 로 내고 resolver 가 record 의 `_unavailableDates` 로 싣는다 (template 루트로 넘기는 내부 값 — 문서에는 없다). DOM (RAC `isDateUnavailable` 함수) · Canvas 달력 모델이 `runtime/unavailableDates.ts` `catalogUnavailableDateTest` 하나를 읽는다. picker 의 달력은 picker 의 것 (`CATALOG_PICKER_CALENDAR_PROPS`).
