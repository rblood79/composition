# 상태 관리 규칙

> **2026-10-04 Publish 후속**: Preview/Publish 실행 세션·DOM·상태·테마의 공용 구현은 `packages/shared/src/catalog/runtime`이다. Publish는 검증한 catalog 파일에서 독립 세션을 만들고 Builder store를 import하지 않는다. Builder iframe 동기화는 origin/source를 검증하는 기존 postMessage 경계를 유지한다.

> **2026-10-04 전면 개정**: ADR-248 Phase 4 (2026-10-03 main 병합) 로 Builder 의 문서 · 선택 · 히스토리 · 저장이 Zustand canonical store (`elements` / `elementsMap` / `childrenMap` · `_rebuildIndexes` · `runCanonicalMutation` · `historyActions` · `instanceActions`) 에서 **catalog runtime** (`apps/builder/src/builder/catalogRuntime/**` + `packages/shared/src/catalog/**`) 으로 옮겨졌고, 옛 store 와 그 규칙의 대상 파일은 `0b0eaea28` (Phase 4e-13-3) 에서 삭제됐다. 옛 규칙 본문은 git 이력에 있다.
>
> 공식 결정: [ADR-248](../../docs/adr/completed/248-unified-catalog-document.md). `composition-patterns` skill 의 규칙 · reference 는 2026-10-04 catalog runtime 기준으로 개정했다 (`zustand-*` 는 남은 UI store 한정). 옛 store 만 다루던 문서 4개 (`zustand-childrenmap-staleness` · `inspector-inline-styles` · `reference/state-details` · `reference/runtime-contracts`) 는 같은 날 삭제했다. skill 문서가 이 문서와 충돌하면 이 문서가 우선.

## 2. 편집 파이프라인 (순서 필수 보존)

문서를 바꾸는 길은 **명령 하나**다 — `CatalogCommand` (`packages/shared/src/catalog/commands/**`: `setFields` · `insertNodes` · `moveNodes` · `pasteNodes` …) 를 `workspace.execute(command)` 에 넘긴다. 패널은 `useCatalogCommandRunner` (hook) · `runCatalogCommand` (workspace 를 prop 으로 받는 곳) (`catalogRuntime/commandRunner.ts`) 가 거부를 안내로 (`notifyEditRefusal`), 그 밖의 실패를 toast 로 바꿔 준다 — 패널 코드에서 `workspace.execute` 를 직접 try/catch 하지 않는다. graph 를 직접 고치거나 op 를 손으로 만들어 `runtime` 에 넣지 않는다.

1. `CatalogWorkspace.execute` (`workspace.ts`) — 자동 HTML id · origin view 재작성 → `root.execute` → 정의 view 후처리 · 선택 (`plan.selectAfter`)
2. `CatalogCompositionRoot.execute` (`compositionRoot.ts`) — 현재 revision 에 대해 명령을 계획하고 `runtime.dispatch`. `REVISION_CONFLICT` 면 한 번 다시 계획한다
3. `CatalogRuntime.step` (`controller.ts`):
   1. `applyCatalogTransaction` (`transaction.ts`) — project id · `expectedRevision` · history 의도 · 빈 op 검사 → staging → entry · 구조 검증 → inverse → `graph.commit` (revision + 1)
   2. **consumer** (compositionRoot 의 Canvas · DOM record 갱신 · 레이아웃) — 던지면 `graph.revertCommit` 후 `CatalogStepAbortedError`. 문서와 화면은 같이 바뀌거나 같이 안 바뀐다
   3. 저장 대기열에 변경 entry **전체 JSON** 추가 (`expectedDurableRevision = revision − 1`)
   4. 히스토리 기록 → resolved 캐시 무효화 → field 구독자 → step listener (session reconcile · read model · autosave · preview) → consumer 의 deliver
   5. 구독자 · listener 오류는 모아서 `CatalogSubscriberError` — 이때 step 은 이미 커밋돼 있다 (되돌리지 않는다)
4. `CatalogAutosave` — 기본 `queueMicrotask` 로 `runtime.save` → `CatalogStorage.commit` 이 저장된 revision 이 `expectedDurableRevision` 이고 새 revision 이 +1 일 때만 쓴다 (아니면 `REVISION_CONFLICT` / `UNSUPPORTED_PROJECT_FORMAT`)
5. Preview — `workspace.attachPreview` 의 `CatalogPreviewChannel` (`previewChannel.ts`) 이 step 의 바뀐 · 지운 id 를 모아 `CATALOG_DELTA`, 준비 · 프로젝트 전환 때 `CATALOG_SNAPSHOT`. Preview 는 복제본에 `runtime.sync` (history skip `"sync"`, 저장 없음). 데이터 정의는 문서 delta 로 같이 가고, `CATALOG_DATA` (`CatalogPreviewFrame.tsx`) 는 API 결과 `{ id, runtimeData }` 만 (ADR-286 R7)

## 3. 핵심 규칙

- **히스토리 의도는 필수**: `applyCatalogTransaction` 은 `history: { kind: "record", label }` 또는 `{ kind: "skip", reason }` 없이는 `HISTORY_INTENT_REQUIRED` 로 거부한다. skip 사유는 `project-create` · `load` · `fixture` · `sync` 넷뿐 — 사용자 편집은 늘 기록된다 (ADR-185 의 「조용한 생략 금지」 가 타입 · 검증으로 옮겨 왔다).
- **히스토리는 프로젝트당 한 스택**: undo / redo 는 entry 의 `inverse` / `forward` 를 기록된 step 으로 다시 돌리고 바깥 효과 (`external`) 를 뒤따라 실행한다. 페이지별 스택 · `migrateEntryToPage` 는 없다. AI 묶음은 `mergeHistory` 로 한 entry.
- **데이터 편집도 문서 명령 하나 (ADR-286)**: `useDataStore.applyDataChange` 는 reduce 결과를 sink (`setDataDefinitionSink` — `bindCatalogDataStore`, `catalogDataStore.ts`) 로 넘기고 sink 가 `setDataEntries` (+ 바인딩 · 문서 명령) 를 `composeOver` 로 묶어 `workspace.execute` 한 step 으로 실행한다 — history · 저장 · 프로젝트 파일이 하나. store 의 정의 Map 은 step 마다 문서에서 다시 투영된다 (직접 set 금지 — `adr286G1` 정적 검사). 옛 `recordExternal` 데이터 경로 (`dataHistory.ts`) 는 삭제됐다.
- **컴포넌트 원본은 정의가 소유하는 template 이고 Local page 가 그것을 그린다 (ADR-279, 2026-10-21 — ADR-260 의 참조 모양 폐기)**: `createComponent` 는 정의 (`templateRootId` 소유 edge) 가 노드를 넘겨받고 부모 child list 의 그 자리에 새 instance 를 둔다 — 위치 키 (`POSITION_LAYOUT_KEYS`) 는 base · `responsive[bp]` 층마다 instance 의 같은 층으로 (`splitPositionLayers`), 중첩 추출 (Local 카드 안 노드) 은 바깥 instance 의 `descendantOverrides` · interaction · `showWhen` 주소를 같은 transaction 에서 새 instance 를 지나도록 재작성 (`rewriteAddressesThroughExtracted`, 바깥 정의의 property target 은 뺀다). 원본 판정은 `componentOriginOf` (= `definitionOfTemplateRoot` 가 component 정의) — 역색인은 소유 template 에도 같다. `dissolveComponent` = instance 전부 detach + 정의 · template 삭제, `duplicateDefinition` = ◆ ⌘D, 복사한 template 루트의 붙여넣기 = instance. Create component 의 이름은 `utils/componentNamePrompt.ts` (host 없으면 동기 기본 이름). **Why (2026-10-21)**: 기본 원본이 Library page 에 사는데 사용자 원본만 page 에 남아 비대칭 (사용자 「잘못된 선택」) — ADR-260 의 `originRef` 세 모양 · Restore · 숨은 template 은 모두 삭제, contract 46.
- **Components 탭의 Library · Local page 는 문서의 page 다 (ADR-282 Phase 3, 2026-10-25)**: `ProjectEntry.componentPageIds` (라우트 · Pages 목록 · Preview · publish 밖 — `withoutComponentPages`), 처음 열 때 runtime `load` step (History 없음) 으로 만든다. ◆ 칸은 원본을 `NodeEntry.originOf` 로 참조하고, Builder 가 그 원본 (표본 view entry 또는 정의 · override 소유 template 루트) 을 `graph.setViewChildren` 으로 그 칸의 `children` 앞에 그린다 — 저장 · export · 색인에는 없다. 명령 · transaction 은 `graph.commandReader` (그리는 자식 없는 graph) 로 읽고 stage 가 쓰기 · inverse 에서 그 id 를 지운다. **Why**: 그리는 자식을 명령이 보면 칸을 걷는 명령 (해제의 주소 재작성) 이 view 표본을 쓰려 했다 (`INVALID_ID`). 사용자에게 보이는 instance 수는 page 의 ◇ 를 빼고 센다 (`projectInstancesOf`). 저장 노드 id 는 `project:node:cp-<역할>-<hash>` (`componentPageNodeId` — 역할 `card` · `inst` · `theme` · `origin` · `local` 을 pick · hover helper 가 id 로 읽는다), body 는 3 열 grid 에 카드 직속, 카드는 제목 바로 뒤에 ◆ (와 slot 을 채운 ◇) 를 직접 담고 (Origin 줄 없음 — 그리는 위치는 `setViewChildren` 의 `at`), 그 뒤 줄은 grid 하나 — 컴포넌트 카드는 캡션 없이 샘플만 (◆ · ◇ 는 Layers 가 표시, 사용자 2026-10-25), theme 카드는 샘플 행 + 캡션 행 (값 이름 · 값). **Why (2026-10-25)**: 경로형 id (평균 99 B, 부모 `children` 이 반복) 와 Column · 줄 · 칸 frame 으로 Library page 가 867 KB 였다 (사용자 「Library 가 왜 1mb」) → 464 KB. page 가 만든 값 (body grid · gap · padding …) 은 그 노드의 기본값 — Styles dirty · Reset 은 `catalogComponentPageBaseline` (`workspace.componentPageBaseline`) 과 비교하고 되돌린다 (사용자 보고 2026-10-25 「리셋 시 초기화」). `componentPageIds` 는 History 밖 load step 만 쓴다 — undo · redo 는 그 목록을 지금 값으로 둔다 (`withCurrentComponentPages`), 남아 있는 page 를 목록에서 빼는 step 은 `UNOWNED_ENTRY` 로 거부된다. **Why (2026-10-27)**: Library 를 처음 열기 전에 기록된 step 의 undo 가 프로젝트 옛 사본으로 목록을 지워, 재열기 · Publish 가 `UNOWNED_ENTRY` 로 실패했다 (283 live 관찰). Library 가 잠긴 동안 (기본 — `workspace.setLibraryUnlocked`) 그 page 의 노드 · 표본 · 해제 사본은 어떤 편집도 받지 않는다 (`originView.ts` `catalogOriginEditCommand` → `LIBRARY_LOCKED` 안내). **Why (2026-10-25)**: Phase 3 로 page 노드가 문서 노드가 되자 잠금이 사본만 막아 「잠금해제 하지 않아도 수정 가능」 했다.
- **template 노드 자신의 override 도 instance 에 투영된다 (ADR-260 Decision 11)**: 투영 자리의 override 는 「투영 경로의 owner 들 (바깥 instance → 안쪽 project template 노드), 바깥이 이김」 으로 읽는다 — `resolution/templateOwners.ts` (`overridesAt` · `layeredOverride` · `innerOwnerPlace`) 를 resolver · positions · fieldSource 가 같이 쓴다. template 노드의 `fillSlot` · `replace` 자식은 바깥 instance 의 template 자리 (`templatePath` 가 그 노드의 owned children 으로 들어간다 — `address.ts`) 이고 detach 는 사본으로 물질화한다. 한쪽 소비자만 바꾸면 Canvas · Layers · 패널 값이 갈린다.
- **원본 instance 인 template 자리는 자기 값을 안쪽 원본의 루트로 넘긴다** (`resolver.ts` `instanceRoot(...)` — Menu 의 Button 자리는 Button 원본의 instance 라 record 는 Button 원본의 루트다). 넘기는 visual 키 목록 · layout 에 그 자리 patch 의 breakpoint 층 (`patchLayers` · `templateLayers`) 과 patch layout 을 넣는다. **Why (2026-10-15)**: 목록이 base `visual` 키만 들고 layout 은 patch 를 뺀 `authoredLayout` 이라, Mobile 에서 쓴 Menu Button 의 border 와 desktop margin 이 문서에만 있고 화면에 없었다 (사용자 보고).
- **바뀐 데이터를 Canvas 에 알리기**: 정의 (mock 행 · schema · 프로젝트 변수 시작값) 는 문서 step 이라 consume plan 이 그것을 읽는 root 를 다시 그린다 (`compositionRoot.ts` `dataReaderRoots` — ADR-286 R8, store 구독 없음). API 결과 (`runtimeRows`) 만 `CatalogBuilderCore.tsx` 의 store 구독이 `workspace.refreshRows(changedRuntimeCollectionIds(...))` 로 알린다. mount 는 root 가 읽은 행 (`rowsSource`) 과 다른 것만 — 무조건 `refreshRows()` 를 부르지 않는다. **Why (2026-10-21)**: boot 가 data store 초기화를 await 한 뒤 root 를 만들어 행이 이미 있는데 mount 가 바인딩 page root 전부를 다시 해석했다 (22 페이지 문서 첫 프레임의 ~1/4, 4x 에서 ~~520 ms). `refreshRows` 1회는 page root 전부 재 flatten + 장면 전체 재 bind 라 (324~~370 ms · 4x 1.3 s) 호출 수가 곧 비용이다.
- **구독은 field 단위**: 패널 · 오버레이는 `runtime.subscribeEntryField` / `subscribeResolvedField` 나 `useCatalog*` hook 으로 읽는다. step 전체를 구독해 매번 다시 계산하지 않는다 (`subscribeSteps` 는 read model 처럼 집계가 필요한 곳만). 집계 읽기는 손으로 구독하지 않고 `useCatalogStepReading(workspace, read)` (JSON 이 같으면 같은 값) · `useCatalogRevision(workspace)` (문서 전체를 읽는 view — Code 보기 · Interactions 규칙 목록) 로 한다 (`catalogRuntime/react.runtime.ts`, 정적 게이트 `panels/core/panelStepReading.static.test.ts`).
- **Zustand 규칙은 남은 store 에만**: StateCreator 팩토리 · 슬라이스 파일 분리, selector 는 개별 값 단위로 쓰고 배열 / 객체가 필요하면 ref 캐싱 (Zustand v5 는 `equalityFn` 을 무시 · 그룹 selector 와 `useShallow` 는 로컬 ESLint 금지 — `apps/builder/eslint-local-rules/index.js`), `setTimeout` / `queueMicrotask` 안에서는 `get()` 으로 최신 값.

## 4. 데이터 — Collections (ADR-132 · ADR-152 v2)

- **문서의 바인딩**: `NodeEntry.binding: DataBindingRef { collectionId, fieldMap? }` (`catalog/document/types.ts`). 변환 `catalogBindingRef` (`dataBinding.ts`), 편집 명령 `catalogBindingCommand` (`dataBindingCommand.ts`, Properties 의 binding 키는 `catalogPropertiesPatchCommand` 가 이쪽으로 가른다).
- **한 항목 바인딩 `binding.key` (`useListData.getItem`)**: key (리터럴 · `{{ }}`) 는 compositionRoot 의 `rows` 감싸개가 `catalogBindingKey` (`stateTemplate.ts` — 노드 페이지 · 프로젝트 변수 · `params`) 로 한 번 풀어 두 소비자에 같이 준다 — 풀리지 않으면 (Canvas) 첫 항목 표본. resolver 는 key 바인딩의 항목을 `row` 로 자손에게 (컨테이너의 `{field}`), 목록은 그 하나만 반복. key 가 읽는 이름이 바뀌면 `refreshState` 가 그 collection 의 `refreshRows`.
- **DOM · Preview · publish 의 읽기**: `useCollectionData({ dataBinding })` → `useResolvedCollectionItems` 하나 (`packages/shared/src/hooks/`). resolve 는 `resolveBoundCollection` (id 우선, `name` 은 옛 값 폴백), 옛 `{ type:"collection", config }` 는 `normalizeDataBinding` 이 읽기 경계에서 v2 로. `fieldMap` 값과 `{#<fieldId>}` 토큰은 `DataField.id` (key 아님).
- **Canvas 의 읽기**: `catalogBoundRows` (`dataBinding.ts`) 가 바인딩된 행으로 record 를 만든다 (행 템플릿 편집은 `rowTemplate.ts`). 행 템플릿 해석 (`resolveFieldRoles` · `interpolateCollectionRowTemplate`) 은 shared DOM 쪽 함수다 — Canvas 와 DOM 의 결과가 같은지는 `/cross-check` 로 본다.
- **데이터 편집 = `DataChange`**: collection 생성 · 삭제 · schema · 행 · source 는 `useDataStore.applyDataChange(change)` (`stores/utils/dataChange.ts` — `reduceDataOps` 순수 적용기, all-or-nothing, inverse 동시 산출) 하나 — 결과는 sink 를 지나 문서 명령 한 step (ADR-286). `create/update/deleteCollection` 은 `collectionUpdateToOps` diff 의 얇은 wrapper. mock 행은 collection 당 1,000 행 상한 (`CATALOG_COLLECTION_ROW_LIMIT` — 검증 `COLLECTION_ROW_LIMIT`). **금지**: `set()` 으로 `collections` 직접 변경 · 히스토리 없는 데이터 편집 · `remove_field` / `remove_rows` 를 AI 에 노출 (`HUMAN_ONLY_DATA_OPS`).
- source = `"api"` 는 `useAsyncList.load` 안에서 `executeApiEndpoint` → `collections.runtimeData` → `list.items`. useEffect + 로컬 state 로 결과를 들고 있지 않는다.
- publish snapshot 은 `toRuntimeCollection(table)` (`{ id, name, schema, mockData, useMockData }`). `ExportedProjectSchema` 는 schema 필드 `id` 를 통과시킨다.
- 이름: 저장 · 내부 타입은 `collections` (`CollectionState` · `targetCollection`), 사용자에게 보이는 UI 심볼 `DataTable*` (`panels/datatable/`) 은 유지.

- **데이터 보기 (ADR-284)**: 바인딩은 내장 보기 (`binding.view` — 조건 트리 · 정렬) 또는 공유 보기 (`binding.viewId` → `ViewEntry`, 원본 사슬의 collection = 바인딩의 `collectionId`) 를 읽는다. compositionRoot 의 행 감싸개가 보기 사슬과 `!var` 값을 한 번 풀어 (`catalogBindingQuery`) 행 소스에 넘기고, `catalogBoundRows` 가 **표시 투영 전** 원본 전체에 `runViewQueries` (`collections/view/evaluate.ts`) 를 실행한다 — Canvas · Preview · Publish 가 같은 모듈 (`oneEvaluator.static.test.ts`). 변수 쓰기 → `refreshState(names)` 가 그 변수를 읽는 보기의 collection 을 다시 읽는다. 필드 · 참조가 없는 조건은 건너뛰고 `rows.view.broken` 으로 낸다 (조용한 통과 금지 — 패널이 표시). 공유 보기 삭제는 읽는 곳이 있으면 `VIEW_IN_USE`, 파생 보기는 목록의 내장 보기를 `promoteBindingView` 로 승격한 뒤 가리킨다 (조건 사본 금지). 파생 보기 (`source.viewId` — 결과 수 · 묶기 · kanban 열) 는 마지막으로 읽던 노드와 함께 지워진다 (`removeWithReferrers` → `removeUnreadDerivedViews`) — collection 위의 보기 (이름 붙인 · 승격한) 는 남는다. **Why (2026-10-27 live)**: 결과 수 Text 를 지워도 보기가 남아 「read by N」 이 부풀고 원본 보기 삭제가 `VIEW_IN_USE` 로 막혔다. 「적용 조건 수」 (결정 3) 는 집계 `applied` — 원본 보기 사슬에서 적용된 최상위 조건 수 (「또는」 묶음 = 하나), 서버가 답한 보기는 그 보기 조건에서 읽는다 (행 수와 무관).
- **계산 필드 (ADR-291)**: schema 필드의 `formula` (json-formula 식 — 필드 **id** 로 저장 `'f-price' * 'f-qty'`, 패널 · 코드 보기는 key 로 표시 `names.ts`) 와 결과 `type`. 셀은 행을 읽는 단계에서 원본 행의 사본에 쓰인다 (`withComputedCells` — 보기의 조건 · 묶기 · 정렬 · 템플릿 · 보기 없는 바인딩 · 서버가 답한 행 · 필터 패널 판정 `explainViewRow` 모두 같은 셀). 정의 오류는 쓰기 거절, 행 오류는 그 셀만 `null` + `formulaCellErrors`. 엔진 · 실행 모듈은 식이 있는 문서를 처음 읽을 때 함께 lazy 로드 (`engine.ts` 로더 → `instance` · `computeCells` · `validate`; 첫 화면 모듈은 값 import 금지 — `lazyBoundary.static.test.ts`), 로드 전 읽기는 `FORMULA_ENGINE_NOT_READY` 대체 → `onFormulaEngineLoaded` 가 다시 읽는다 (Builder 는 표 목록을 **문서**에서 — store 투영은 첫 화면 뒤). 셀은 원본 행 배열 × 실행 키 (schema · 식이 읽는 `$var` · today · 언어) 와 원본 행마다 캐시 (`now()` 제외). **Why (2026-10-29)**: 보기 실행마다 셀을 새로 만들어 4x · 1만 행 × 식 5 의 변수 변경이 268 ms → 캐시 5 ms; 보기 memo 키에 엔진 로드 여부가 없어 프로젝트를 열면 계산 필드 조건의 표가 0 행이었다. 표시용 (보기 · 템플릿) 과 조회용 (서버 전송) 의 구분: 계산 필드를 조건 · 정렬 · 묶기 · 집계에 쓰는 보기는 서버로 보내지 않고 (`COMPUTED`) 1만 행까지 불러와 여기서 돈다 (`VIEW_LOCAL_LOAD_CAP`).

## 6. Interaction (ADR-131 의 events / actions 를 대체)

- 문서 정본은 `InteractionEntry { kind:"interaction", ownerId, trigger, actions }` (`ProjectEntry.interactionIds`) — interaction 이 자기 소유 노드를 가리킨다 (노드가 `props.onPress: "ev1"` 로 가리키지 않는다). 편집은 `catalogRuntime/interactions.ts` 의 명령.
- **Do 목록 (ADR-284, contract 50)**: `actions` 는 순서대로 실행되고 실패한 Do 에서 멈춘다 (dispatcher `executeInteractionRule` — 「Do N: 사유」). Preview 변환 (`ruleOf` → `actionOf`) 은 한 Do 라도 그 record 에서 풀리지 않으면 규칙을 내지 않는다 — 뒤 Do 가 앞 Do 를 전제한다. Do 를 읽는 곳 (색인 · 복사 · detach · createComponent · swap · 변수 이동 · Canvas 대상 지정) 은 모든 Do 를 돈다 — 첫 Do 만 보면 뒤 Do 의 page · 변수 · 대상이 dangling 이 된다. 조건부 실행 · 분기는 없다.
- **컬렉션 drag & drop (ADR-284 Phase 5)**: ListBox · GridList · Tree · Table 의 When `onReorder` · `onInsert` · `onRootDrop` · `onItemDrop` · `onDragEnd` 는 `useDragAndDrop` 옵션이다 (`concepts/collectionDragDrop.ts` — 인자는 이벤트 객체의 필드, `argFields`). Preview 는 그 규칙이 있는 목록만 lazy `catalogDragAndDrop.components.tsx` 로 `dragAndDropHooks` 를 준다 — drag type 은 바인딩 collection (같은 collection 의 목록끼리만 받음), 다른 목록에서 온 drop 의 `keys` 는 drag data 에서 다시 읽는다. 놓은 쪽은 move Do 의 `dropPosition` 값 (`!event.target.dropPosition`), 열 값 쓰기는 update Do 의 `field` — 조건부 Do 없이. 세션의 Tree 역할 (`fieldMap.value` · `children` · `parentId`) 은 Tree 바인딩에서만 읽는다 — 개수 머리 Text 의 `value` 가 항목 key 를 바꾸던 결함 (2026-10-27).
- **등록표는 손으로 쓰지 않는다 (ADR-280)**: `CAPABILITY_REGISTRY` · `IMPLICIT_STATE_SOURCES` 는 RAC 개념 파일 (`packages/shared/src/interactions/concepts/*.ts` — RAC 문서 절 하나 = 개념 하나, 이름마다 설치 d.ts `satisfies`) 과 컴포넌트 spec (`componentInteractionSpecs.ts` — 유일한 손 입력) 에서 `deriveRegistry` 가 만든다. 새 컴포넌트의 When · Do 는 spec 한 줄 (개념 · owner) 이고, type 마다 쓰는 이름이 그 RAC props 에 없으면 `RAC_SURFACE_CHECK` 가 컴파일을 막는다. 개념 표는 RAC 의 절 구조를 옮긴 묶음일 뿐 새 어휘가 아니다 (사용자 원칙 2026-10-22). **유도 Do 층 (ADR-287)**: 그 위에 `withReferenceCapabilities` 가 catalog binding `accepts` 에서 prop 마다 Do 를 유도해 얹는다 (`referenceCapabilities.ts` — 값 prop `set<Prop>` · boolean `<prop>On` · `<prop>Off` · `toggle<Prop>`, 이벤트 · aria · `default*` · DOM 전역은 제외). 개념 Do 의 prop · id 가 이긴다. 레퍼런스 API 표 (로컬 skill 의 `<Component>.md`) 는 정본이 아니라 게이트 oracle 이다 — `referenceCapabilities.static.test.ts` 가 표의 행마다 유도 Do 또는 보류 사유 (`deferredReferenceProps.ts`) 를 요구한다. 노드 자기 `isDisabled` · `isReadOnly` Do 는 조상만 막는다 (`inherited:*` guard).
- **Preview/Publish 의 상태는 첫 render 부터 controlled**: running Preview (`setRuntimeProps` 가 있는 렌더) 의 binding 은 상태 prop 을 `catalogControlledProps` (`catalog/runtime/runtimeStateProps.ts`) 로 넘긴다 — 값은 항상 정의 (`undefined` 로 uncontrolled 에 떨어지는 render 금지 — react-stately 는 `value !== undefined` 로 판정), RAC 의 변경은 record 의 runtime 값으로, `default*` 와 controlled prop 을 같이 넘기지 않는다, key 에 상태값을 넣지 않는다 (remount 금지). 현재 값은 `catalogRuntimeStateOf` 하나 (runtime override ?? 시작 상태 — 항목이 선언한 선택 포함) 를 렌더와 dispatcher 가 같이 읽는다. **Why**: 항목 집계를 `defaultSelectedKeys` 로 넘기던 ListBox · GridList 는 규칙이 쓴 선택이 RAC 에 닿지 않았고, dispatcher 는 집계를 몰라 다중 선택의 `selectItem` 이 기존 선택을 지웠다 (ADR-280 Phase 0 RED).
- **ComboBox 는 선택과 입력 글자를 둘 다 controlled 로 받는다 — 글자는 `CatalogComboBox` 가 쓴다**: RAC 는 `selectedKey` · `inputValue` 가 둘 다 controlled 면 글자 동기화를 쓰는 쪽에 맡긴다 (`useComboBoxState` — 레퍼런스 「Fully controlled」). `onSelectionChange` 가 key 와 그 항목 글자를 한 번에 쓰고 (blur 의 같은 key 호출 = 글자 되돌림, `null` = `allowsCustomValue` 의 custom 값이라 글자를 둔다), 다른 곳의 선택 (규칙 · load) 과 늦게 온 항목 글자는 `ComboBoxStateContext` 를 읽는 자식 effect 가 쓴다. 항목 글자는 `selectionManager.collection` (전체) 에서 — `state.collection` 은 닫혀 있을 때 마지막으로 보인 목록이다. 글자를 쓰는 render 는 `menuTrigger: "manual"` 이다. **Why (2026-10-23)**: 항목 action (virtual 클릭) 은 목록을 먼저 닫고 선택을 알린다 — 닫힌 · focus 된 칸에 글자가 오면 RAC 가 타이핑으로 보고 다시 열었다 (live 재현).
- **open 은 trigger 의 것**: overlay 본체 (Modal · Popover · Tooltip) 의 자기 `isOpen` 은 trigger context 를 이긴다 (설치 RAC `Modal.mjs:88-90`) — 본체를 controlled 로 두면 trigger press 가 본체를 못 연다. 그래서 MenuTrigger · DialogTrigger · TooltipTrigger · ContextualHelp · picker 가 `isOpen` 을 받고, 본체에 건 open 규칙은 dispatcher 의 `stateOwnerOf` 가 trigger 로 보낸다. 본체는 trigger 없이 설 때만 자기 open 을 갖는다. 「아무도 제어하지 않음」 (`catalogOpenOwnerOf` → `null` — ComboBox · SubmenuTrigger 안) 과 「trigger 없음」 (`undefined`) 을 구별한다. **Why (2026-10-23)**: `!owner` 로 읽어 ComboBox 의 Popover 가 `isOpen=false` 로 고정, Preview · publish 에서 목록이 열리지 않았다.
- **capability 쓰기 순서**: 값 해소 (`!param` · `!event.<arg>` · 리터럴) → 현재 유효 상태 → 결과 (`op` add · remove, single 은 교체) → RAC 제약 (`guards` — disabled · readOnly · 빈 선택 금지 · selectionMode · disabledKeys, 그룹이 내려주는 disabled · readOnly 포함) → 결과 전체 쓰기. 막히면 report (조용한 no-op 금지). 범위는 RAC 가 clamp 하므로 guard 없음. 래퍼 (`I18nProvider` · `display: contents` marker · calendar picker) 는 `withRuntime` 이 준 핸들러를 안의 RAC 요소에 넘긴다 (`ForwardingI18nProvider` · `ForwardingMarker` · `catalogForwardHandlers`).
- **Form submit · reset 은 DOM ref**: dispatcher `invokeImperative` → `requestSubmit()` (RAC validation 을 거친다) · `reset()` (controlled field 는 `useFormReset` 으로 첫 값). 작성한 목적지가 없는 Form (`action` 없음 · `method` ≠ `dialog`) 만 `onSubmit` 에서 `preventDefault` — 목적지가 있으면 HTML 제출 그대로.
- **패널은 RAC 가 지금 받는 것만 (ADR-281)**: When · Do 선택지는 `exposure.ts` (`exposedTriggerGroups` · `exposedCapabilities`) 가 고르고, 판정은 dispatcher 의 첫 검사와 같은 `declaredRefusal` (`constraints.ts`) 이다 — 패널과 실행이 다른 답을 내지 않는다. 예외 하나: `selectionMode: "none"` 대상의 선택 Do 3 (선택 · 해제 · 전체 해제) 은 패널이 모두 숨기고 안내하지만 (`hiddenBySelectionMode` · ADR-287 사용자 결정 3), dispatcher 는 추가만 막는다 — 해제 · 전체 해제는 RAC 가 받는 상태 초기화다 (ios-list 의 Cancel 이 모드를 끄고 선택을 비운다). 막힌 규칙은 지우지 않고 표식만. When 라벨 키는 등록표 그룹에서 유도 (`interactions.trigger.<개념>.<callback>`), `!event` 인자 이름은 개념의 `args` (`eventArgNames`).
- **조상 상속 (ADR-281)**: page 루트 · frame 의 `isDisabled` · `isReadOnly` · `isRequired` · frame 의 `locale` (+ page 루트 `colorScheme`). page 루트의 `locale` 은 작성 값이 아니라 사이트 언어 (`ProjectEntry.site.lang`) 다 — composition root 가 `body` record 에 넣고 (`siteLocale`), Canvas 의 환경 locale 도 같은 값 (ADR-286, 사용자 2026-10-28 「page 에서 제거하고 사이트 설정에」) 는 `runtime/inheritedProps.ts` 하나를 DOM (`CatalogDomNode` — RAC `Provider` 표 `providerContexts.ts` + `I18nProvider`) · Canvas (`presence.ts` 파생 `isDisabled` · `isReadOnly`) · guard (`getConstraintContext().inherited`) 가 읽는다. 받는 쪽 flag 는 OR (조상의 `true` 가 이김) — palette 원본이 `isDisabled: false` 를 기본값으로 실어 record 가 작성한 `false` 와 구별하지 못한다. **Why (2026-10-22)**: RAC 규칙 (자식 자기 값 우선) 만 따르면 상속이 어떤 palette 컴포넌트에도 닿지 않았다. `colorScheme` 은 Do 전용 (`editorHidden`) → 세션 `setColorScheme` 이 `applyTheme` 을 그 색 모드로.
- **원본 규칙의 instance 상속 (ADR-281)**: 원본 template 노드의 규칙은 모든 instance 에서 실행되고, instance 는 자리 patch 의 `interactions` 맵 (원본 규칙 → `"off"` \| 자기 규칙) 으로 끄거나 바꾼다. 패널 (`catalogInheritedInteractionsOf`) 과 Preview (`recordsOfOwner`) 는 `effectiveInteractionsOf` (`catalog/resolution/effectiveInteractions.ts`) 하나를 읽는다 — 한쪽만 바꾸면 「안 보이는데 실행」 이 돌아온다. ADR-262 반영 · Reset all 이 맵을 다룬다.
- **capability 대상 = 장소 참조, 실행한 record 기준 해소 (ADR-283)**: `action.target` 은 `{ nodeId }` (page 노드 · 같은 template 의 규칙만 template 노드 — 그 밖은 `TARGET_IN_TEMPLATE`) · `{ address }` (page instance 안 자리) · `{ local }` (규칙 주인이 든 원본 template 의 자리 — 주인이 template 노드일 때만) · `{ unset: true }` (swap · detach 로 자리가 사라진 규칙 — 남기고 패널 「대상 없음 · 다시 지정」, Publish 경고) — `CatalogNodeRef` 를 `showWhen` 의 상태 주체 참조와 공유. 실행 record → 대상 record 는 `resolveCapabilityTarget` (`catalog/runtime/capabilityTarget.ts`) 하나를 Preview 변환 (`catalogPreviewInteractions.ts` `ruleOf`) 과 패널 (「이 자리에서는 대상에 닿지 않음」) 이 읽는다 — 행 record (`rowIndex`) 는 실행 record 와 공유해야 하고, 참조가 이름 붙인 instance 단계는 후보의 조상에 있어야 하며, `local` (과 같은 template 의 `nodeId`) 은 실행 record 체인에서 규칙 주인의 원본 루트 (`catalogOriginRootOf` — `templatePath[0]` 이 아니다: `local.instances` 가 있으면 가장 안쪽 정의 기준) 를 그리는 record 아래만. 참조 색인 (`graph.ts` `referencedIds`) 은 주소의 모든 project id 를 든다 — 중간 instance 의 swap · 추출 · 삭제가 규칙을 찾는다. 대상 참조를 지나는 명령: clone (`mapNodeRefIds` — `local` 도) · detach (`reanchorInteractions` — 사본 `{ nodeId }`, 못 옮기면 `unset`) · createComponent (`rewriteTargetsIntoComponent` · `rewriteAddressesThroughExtracted`) · swap (`remapThrough`, 없으면 `unset` + 보고 `targetsUnset`) · 구조 이동 (transaction 이 옮겨진 subtree 의 규칙을 다시 검증). **Why (2026-10-26)**: 대상이 `recordsOfSource(targetId)[0]` 이라 원본 규칙 · 행 규칙이 눌린 instance · 행이 아니라 첫 것을 바꿨다 (G0 RED).
- **규칙 값 = 리터럴 또는 값 전체 참조 (Value 칸 「값 고르기」, 2026-10-26)**: `!event.<인자>[.경로]` (RAC 콜백 인자) · `!item.<key 인자>[.필드]` (owner 가 묶인 collection 에서 그 key 의 항목 — `useListData.getItem`, `key` 또는 single 선택이면 한 항목, 아니면 배열) · `!var.<변수 id>[.경로]`. 해석은 `interactions/valueRef.ts` `resolveRuleValue` 하나를 dispatcher 의 모든 값 칸 (setState · capability · body · 목록 데이터) 이 쓰고, 항목은 Preview 세션 `itemsByKeys` (보이는 항목 — 편집 기록 포함), 변수는 `readVariable` (writeState 와 같은 scope). 패널 선택지는 `valueOptions.ts` 가 When 의 `args` · owner 바인딩 schema · 보이는 변수에서 유도 — 컴포넌트별로 손으로 적지 않는다. 문서 검증 (`graph.ts` STATE_VALUE_TYPE) 은 참조 값을 건너뛴다. **Why**: Set state 만 값을 해석하지 않아 사용자가 적은 `selectedKeys.name` 이 글자 그대로 Text 에 나왔다.
- **`append` · `update` · `remove` 는 세션의 편집 기록 (`useListData`) (ADR-281 결정 3 의 2차)**: 규칙의 편집은 `CatalogPreviewSession` 이 collection id 별로 순서대로 들고 Builder 의 항목 위에 다시 적용한다 (`itemSources` → `replayItemEdits` — `catalogBoundRows` 가 읽는 것). 항목 key 는 바운드 목록과 같은 `getItemKey` (`id` · `key` · `value` 필드, 없으면 `row-N`). data store · 문서는 바뀌지 않는다 (편집 기록은 Preview 실행 상태). Canvas 는 작성 데이터를 그린다 — Preview 와 항목 수가 다른 것은 설계된 비대칭.
- **`useListData` 위치 편집**: `insert` · `insertBefore` · `insertAfter` · `prepend` 는 세션 `insert(collectionId, CatalogListPosition, value)`, `move` · `moveBefore` · `moveAfter` 는 `move(collectionId, keys, to)` — 편집 기록 `insert` · `move` 를 `replayItemEdits` 가 적용 (`positionIndex`). `removeSelectedItems` 는 dispatcher 가 `selectedKeysOf` (그 collection 에 묶인 record 들의 `catalogRuntimeStateOf(…, "selectedKeys")` 합집합) 로 `remove`.
- **`reload` (`useAsyncList.reload`)**: 세션이 collection 을 채우는 조회 endpoint (`targetCollection` — Builder Preview 는 `endpointWithTarget`, 파일은 내보내기가 싣는다) 를 진행 중 제출 (`trackSubmit`) 뒤에 실행하고, 결과를 `reloadedItems` 로 Builder 항목 대신 쓴다 — 그 collection 의 편집 기록은 지운다, Builder 가 다른 `runtimeData` 를 보내면 그쪽이 이긴다.
- **조회 endpoint 의 `{{ }}` (한 건 조회 — router loader)**: 경로 · query 의 템플릿은 세션의 `endpointTemplate` (프로젝트 변수 · `params`, 빈 값 = 미해결) 로 풀고, 템플릿 endpoint 가 채우는 collection 은 풀린 URL 이 마지막 읽기와 다를 때만 `loadRouted` 가 `reload` 한다 (navigate · 데이터 수신 때). 풀리지 않는 템플릿은 보내지 않는다 — shared 실행기 · Builder `executeApiEndpoint` 둘 다 거부.
- **읽는 중 상태 (`useAsyncList.loadingState`)**: 세션의 `loadingStates` (`reload` 가 `loading` → `idle` · `error`) 를 `boundRows` 가 바인딩 행 결과 (`CatalogBoundRows.loadingState`) 에 싣고, resolver 가 바운드 Table 의 `loadingState` (instance → template root 로 넘김) · 바운드 Skeleton 의 `isLoading` 으로 바꾼다. DOM TableBody 는 `loading` + 빈 본문에서 S2 진행 원. Canvas 의 rows 는 상태를 싣지 않는다 — 작성 값 그대로 (설계된 비대칭).
- **load 인자 (`useAsyncList.load({cursor, filterText, sortDescriptor})`)**: 세션 `loadArguments` 가 collection 별로 들고 `endpointTemplateFor` 가 endpoint 템플릿에 넣는다 (빈 값의 쿼리는 뺀다 — `ENDPOINT_LOAD_ARGUMENTS`). `reload` = 첫 페이지 (cursor 지움), `loadMore` = `cursor` 로 다음 페이지를 보이는 항목 뒤에, `setFilterText` · `sortCollection` = 그 값으로 `reload`. 다음 cursor 는 `loadCollectionEndpoint` 가 `responseMapping.cursorPath` 에서. 바운드 Table 정렬은 endpoint 가 `sortDescriptor` 를 읽으면 `serverSort` (열 → 필드 key) — 그 Table 은 `serverSortedTables` 라 resolver 가 클라이언트 정렬을 하지 않는다. Builder 실행은 load 인자를 빈 값으로.
- **목록 끝 · 입력 검색 (S2 자동 연결)**: 페이지를 넘기는 collection (`session.pages`) 에 묶인 ListBox · GridList · Table · Tree · Menu 는 DOM 이 끝에 RAC `*LoadMoreItem` (`catalogLoadMoreItem`) 을 두고 `runtime.loadMore` → 세션 `loadMore`. 바운드 ComboBox · Autocomplete 의 목록이 `{{ filterText }}` endpoint 면 (`session.serverFilterOf`) 입력이 `setFilterText` 로 가고 클라이언트 필터를 끈다. 같은 collection 의 늦은 응답은 `loadSequence` 로 버린다. 바운드 Select · ComboBox 도 `loadingState` 를 받아 (resolver `LOADING_STATE_TYPES`) DOM 이 S2 자리에 스피너를 둔다 — Select trigger 의 chevron 앞 (`loading`, 닫혀 있을 때) · ComboBox Group 의 버튼 앞 (`loading` · `filtering` 500ms 뒤) — `catalogPickerSpinner`. picker 안 ListBox 의 끝은 Popover 너머 picker 의 바인딩으로 더 불러온다 (`boundOwnerOf`).
- **트리 데이터 (`useTreeData`)**: 바인딩 `fieldMap.children` (중첩 배열) 또는 `fieldMap.parentId` (평면 행의 부모 key) 를 Tree에서 고른다. `catalogBoundRows` 는 평면 행일 때 전체 목록을 부모 key로 색인한 다음 루트 행에 `children` 을 싣고, resolver 가 바운드 Tree 의 행 TreeItem 안에 같은 행 template 을 하위 행마다 다시 놓는다 (`nestTreeRows` — template 의 표본 하위 TreeItem 은 빠진다, instance 「TreeItem/Default」 는 template 루트로 내려가서). **Why (2026-10-23)**: `children` 배열만 읽으면 일반적인 `id`·`parentId` 테이블의 관계가 모두 한 단계로 표시된다. TreeItem 은 `CATALOG_ROW_ITEM_TYPES` 다 (2026-10-23 전에는 빠져 바운드 Tree 가 행을 반복하지 않았다). Preview 세션은 중첩 배열에는 `replayItemEdits`, 평면 행에는 `replayFlatTreeEdits` 를 사용한다 — `append` · `insert` · `prepend` 의 `parent`, `move` 의 `toParent` (`null` = 맨 위), key 를 받는 편집은 트리 어느 단계든 찾는다.
- **Tree 선택 스타일**: TreeItem origin 의 `TreeItemContent` 첫 자식은 `Checkbox[slot=selection]` 이고, `selectionStyle=checkbox` 와 선택 가능한 `selectionMode` 에서만 Canvas presence · DOM 에 나타난다. Tree의 스타일 변경은 하위 selection Checkbox 의 presence 를 갱신한다. **Why (2026-10-23)**: `checkbox → RAC selectionBehavior=toggle` 변환만으로는 행에 Checkbox DOM·Canvas 노드가 생성되지 않아 Property 값이 시각적으로 무효였다. 노드가 없는 행에 붙는 자동 체크박스는 공용 `Tree` 의 데이터 행 경로에만 둔다 (`autoSelectionCheckbox`). **Why (2026-10-24)**: 공용 `TreeItemContent` 가 늘 자동 체크박스를 그려, 내용 노드 없는 TreeItem 은 DOM 에만 체크박스가 생기고 Canvas 에는 없었다 (ADR-256 후속 16 비대칭의 재발).
- **보기를 요청에 싣기 (ADR-284 Phase 2)**: endpoint 의 `querySerialization` (`suffix` · `body` · `none`) 이 있고 그 collection 을 읽는 바인딩들의 보기가 정의 기준 하나면 세션 `serverView` 가 `serializeViewQueries` 결과를 `loadCollectionEndpoint` 의 `extra` 로 넘긴다 (건너뛴 조건은 파라미터 없음). 그 응답은 보기의 결과다 — `boundRows` 가 `query.served` 를 붙이고 `catalogBoundRows` 는 다시 거르지 않는다 (못 보낸 조건 수 = `unsent`). total 은 응답의 `totalPath` 이고 첫 페이지마다 지운다. 변수 쓰기 (`reloadForVariables` — 글자 비교면 300 ms) · 문서 변경 (receiver 구독) 이 `loadRouted("filtering")` 을 부르고, `loadPage` 는 collection 별 `AbortController` 로 앞 요청을 끊는다. 보기가 빠진 collection (`viewLoaded`) 은 서버가 거른 행을 버린다. serializer 는 `collections` barrel 로 내보내지 않는다 — **Why**: barrel 로 내보내자 Preview initial 이 +3,685 B (세션은 lazy chunk 인데 serializer 가 initial 공용 chunk 로 옮겨갔다).
- **load 반환 선택 (`useAsyncList` load `selectedKeys`)**: `loadCollectionEndpoint` 가 `responseMapping.selectedKeysPath` (key 배열 · `"all"`) 를 읽고, 세션 `onLoadedSelection` → `CatalogPreviewInteractions.selectLoaded` 가 그 collection 에 묶인 record 의 runtime 선택에 쓴다 — `reload` 는 교체, `loadMore` 는 합침 (레퍼런스 reducer), Select · ComboBox 는 첫 key 의 `selectedKey`, `selectionMode: single` 목록은 하나만. 반환이 없으면 선택은 그대로. endpoint 편집기는 `cursorPath` · `selectedKeysPath` 를 draft 로 보낸다 (`toEndpointDraft` — `""` = 지움). **Why (2026-10-23)**: draft 에 `dataPath` 만 있어 편집기의 두 칸이 store 에 닿지 않았다 (입력칸의 지역 값만 보였다).
- **`callEndpoint` 는 제출 전용 실행기 (ADR-281)**: `submitApiEndpoint` → `submitCollectionEndpoint` — 요청 공유 0 (조회의 `createCollectionEndpointExecutor` 는 endpoint id 로 진행 중 요청을 공유해 둘째 body 를 버린다), 성공 = `response.ok` (204 · 빈 본문 · 비 JSON 도 성공), 실패는 Preview runtime 이 `[interactions]` 경고 + toast. body 는 `!event.formData` (form 요소 `FormData`, 같은 name 여러 값은 배열) 또는 리터럴.

## 7. Styles · Properties 패널 입력

- 구조 편집으로 template 부품이 owned node가 된 field의 Content 패널은 실제 부품 값을 읽고,
  부모의 의미 속성 편집·Reset과 부품 쓰기를 한 명령으로 적용한다. **Why (2026-10-14)**:
  Prefix 추가 시 고정된 Label·Input을 둔 채 부모 label/placeholder만 바꾸면 패널과 두 renderer가
  달라진다. 부품 직접 편집과 Undo도 패널 구독 대상에 포함한다.

- 놓은 원본 instance 의 slot 기본 내용은 놓는 순간 소유 노드 (`fillSlot`) 다 — `insertNodes` · 컬렉션 "+" 가 `ownSlotContents` (`commands/materialize.ts`) 를 부른다. 선언된 slot 외에 항목을 담은 자리 (Menu) 와 중첩 원본 slot 의 항목 채움 (Select · ComboBox 의 ListBox) 도 같다. ListBox · GridList · TagGroup · Breadcrumbs (와 picker 의 ListBox) 는 resolver 가 첫 소유 항목을 행마다 반복하고, `{prop}` 에 묶인 slot 만 템플릿 자리로 둔다. 한 주소의 override 는 하나라서 `fillSlot` 이 그 자리의 prop · style 쓰기 (`DescendantPatchFields`) 도 담는다 — patch 를 읽는 곳은 `descendantPatchOf` 로 읽는다. **Why (2026-10-14, 같은 날 둘째)**: patch 가 `fillSlot` 을 덮어 Card Content · TabList · Menu 의 style 한 번이 `UNOWNED_NODE` 로 거부됐다. 조상 타입은 원본 이름이 아니라 루트 타입으로 읽는다 (`ancestorTypes`) — 「TreeItem/Default」 안의 TreeItem 이 컬렉션 밖으로 보여 원본의 selected 표시 상태가 선택으로 샜다. **Why (2026-10-14)**: 템플릿 자리 항목은 detach · create component · ID 가 없어 "+" 로 넣은 항목과 다른 객체였다 (사용자 「slot 호스트 전부」). 그전 resolver 는 `fillSlot` 이면 행을 버렸다 ("+" 로 항목을 넣은 bound ListBox 의 행이 사라짐).

- 렌더 중 ref 를 갱신하지 않는다 — 렌더가 소비하는 입력·헤더 스냅샷은 state 또는 외부 구독으로 읽고, 최신 이벤트 콜백은 commit 에서 연결한다. **Why (2026-10-12 lint 수리)**: 렌더 중 ref를 갱신하면 아직 commit되지 않은 렌더의 콜백이 네이티브 이벤트 경로로 유출될 수 있다. 렌더가 소비하는 입력·헤더 스냅샷은 state 또는 외부 구독으로 읽고, 최신 이벤트 콜백은 commit에서 연결한다. 이전 consumer의 cleanup은 새 consumer를 끊지 않아야 한다.

- `PropertyUnitInput`: focus 때 선택 id 를 ref 로 잡고 blur 때 비교 — 다르면 onChange 를 건너뛴다. **Why**: mousedown → blur 순서라 blur 시점에 이미 새 요소가 선택돼 있다.
- Styles 값은 `catalogStylesHost.ts` 가 선택 record 의 typed field 를 읽어 `SelectedElement` 로 만든다 (옛 `buildSelectedElement` · `SyntheticComputedStyle` 은 없다). 편집은 `catalogSemanticPatchCommand` → `setFields` 한 step.

## 금지 패턴

- ❌ `setTimeout` 안에서 바깥에서 잡은 store 값 사용 (남은 Zustand store — `get()` 필수)
