# Blink LayoutNG 대조 — composition 레이아웃 엔진 (block · inline-block · flex · grid · 박스 모델 · position) 의 수동 구현 재점검

> **작성일**: 2026-10-16
> **목적**: composition 이 CSS 명세와 Chrome 실측으로 수동 구현한 레이아웃 (Rust `packages/engine/src/{block,flex,grid,tree,display,style,cascade}.rs` + TS 직렬화 `packages/shared/src/catalog/runtime/compositionRoot.ts` `styleOf`) 을 **Chromium Blink 의 실제 알고리즘 소스** 와 함수 단위로 다시 대조한다. 앞선 [CHROMIUM_CC_BLINK_PAINT_DELTA_2026-10.md](CHROMIUM_CC_BLINK_PAINT_DELTA_2026-10.md) 가 페인트 축이었다면 이 문서는 레이아웃 축이다.
> **방법**: 영역별 4개 병렬 감사 (block · flex · grid · 박스 모델) 가 Blink `main` 소스를 받아 (`chromium.googlesource.com` · `raw.githubusercontent.com`) composition 소스와 줄 단위로 대조했고, 아래 표의 production 재현 가능 항목은 메인 세션이 composition 쪽 file:line 을 직접 다시 열어 확인했다. Blink 파일 경로는 `third_party/blink/renderer/` 기준.
> **판정 기준**: "격차" 는 양쪽 코드가 다른 결과를 내는 것. 엔진 모듈 헤더가 **미구현** 이라 선언한 것 (float · writing-mode · subgrid 등) 은 격차로 세지 않고 §6 에 모았다. 생성 CSS · Styles 패널이 그 입력을 만들 수 없으면 "재현 불가" 로 적었다.
> **3-domain**: D3 Builder consumer (레이아웃 엔진) 내부. D1 · D2 · catalog 무변경. 판정 oracle 은 Blink 코드가 아니라 **Chrome 픽셀 · `getBoundingClientRect`** (ADR-156 차등 oracle) 다 — 코드 대조는 어디를 재야 하는지 가리키는 수단이다.

## 결론 우선

**수동 구현의 큰 틀 (margin collapse · BFC · shrink-to-fit · min/max clamp 순서 · flex 동결 기계 · grid fr 가상 크기 루프 · auto-repeat · absolute inset 해소) 은 Blink 와 같다.** 격차는 두 종류다.

1. **회귀 — 엔진은 받는데 production 이 보내지 않는 입력 3가지.** `78469745d` (2026-10-05 옛 TS 파이프라인 삭제) 가 `leafBaseline` · `strutBaseline` · `lineHeight` 공급자 (`f1ec24e53` · `3a1b3200d`) 를 같이 지웠고 catalog 경로 `styleOf` 에 다시 연결되지 않았다. `position: sticky` · `fixed` 도 `styleOf` 가 떨어뜨려 in-flow static 이 된다. 이것은 알고리즘 문제가 아니라 **배선 문제** 라 가장 먼저 닫는다.
2. **알고리즘 격차 — Blink 가 명세의 한 절을 구현했고 composition 이 근사한 자리.** production 에서 흔한 입력으로 드러나는 것 12 건, 드문 입력 24 건.
