# Canvas 최적화 분석 · 설계 — 문서 크기 비례 비용 (2026-11-11)

> **작성일**: 2026-11-11
> **위상**: catalog 단일화 (ADR-248) · 1차 기능 구현 뒤의 최적화 착수 분석. 10월 성능 작업 (스냅 · ADR-263 ~ 273 · 10-21 레버 2a/3a/4a) 다음 단계의 출발점.
> **코드**: HEAD `850e98a60` (production 빌드 `pnpm perf:build-dist`, dirty = `.agent/task-state.json` 뿐)
> **원자료**: `.agent/runs/2026-11-11-canvas-perf-scaling/` (local-only)
> **전제 (사용자)**: 빌더는 서비스 실행 환경이 아니라 디자인 도구다 (Figma · Framer · pen.dev 와 같은 용도). 대상 문서는 엔터프라이즈 CMS · SaaS — 수십 페이지, 입력 폼 · 레이아웃 · 대시보드가 많다.

## 1. 결론

1. **그리기는 병목이 아니다.** 66 페이지 · record 18,798 · CPU 4x 에서도 pan · zoom · hover · marquee · Layers 스크롤은 프레임 예산 안이다 (gap p95 ≤ 19.3 ms, long task 0). Skia 캐시 · 부분 갱신 · viewport 실행은 10월 작업으로 화면 넓이에 묶였다.
2. **병목은 「문서 전체 크기에 비례하는 일」 이 상호작용 경로에 남아 있는 것이다.** 페이지를 3배로 늘리면 같은 입력의 V8 호출 수가 pan 2.5배 · 페이지 전환 2.3배 · 패널 열기 2.4배 · drag 2.0배 · 편집 1.9배가 된다 (§3). 디자인 도구의 비용은 **화면에 보이는 것** 또는 **바뀐 것** 에 비례해야 하고, 문서 전체에 비례하면 안 된다.
3. **가장 큰 것은 프로젝트 열기다.** 66 페이지 cold 로드 2.66 s (4x 10.3 s), 그중 한 덩어리 동기 작업이 1.9 s (4x 7.6 s). 페이지 수에 선형이라 CLAUDE.md 의 「초기 로드 < 3초」 는 약 75 페이지에서 깨진다 (1x 기준).
4. **선택은 문서 크기와 무관하지만 상수가 크다.** 선택 1회에 V8 호출 약 20만 (production), 4x 에서 p95 51 ~ 56 ms · 프레임 20 % 가 25 ms 초과 — Design 패널의 React · RAC 재마운트다.
5. **Rust 이관 근거는 여전히 없다.** 로드에서 엔진 `computeLayout` 은 4.6 % (131 / 2,826 ms). 10-16 판정 ([CANVAS_RUST_DECISION_2026-10.md](CANVAS_RUST_DECISION_2026-10.md)) 그대로다.

## 2. 측정 조건

- 하니스: `perf-baseline.mjs --lane frame` (부류당 3 초) · `--cold-entries 3` · `--fixed-inputs --call-counts` (결정적 호출 수).
- 문서: `many-pages` fixture — `app-pages` 생성기 (flex 중첩 뼈대 + 팔레트 원본 instance) 를 22 장 · 66 장으로. 22 장 = 노드 3,317 · record 6,317, 66 장 = 노드 9,828 · record 18,798. **합성 문서다** — 실사용 문서의 분포 (페이지당 폼 밀도 · instance 재사용 비율) 는 재지 않았다.
- 빌드: 프레임 · 로드는 production (`--serve-dist`), 함수별 호출 수는 dev (production 은 번들 경로라 앱 함수 분류가 0).
- 환경: headless Chrome · 60 Hz · SwiftShader · 1440 × 900 · DPR 1. CPU throttle 1x 와 4x (사용자 Chrome 조건). 절대값이 아니라 같은 조건끼리의 비교치다.
- 콘솔 · 페이지 오류 0. 프레임 run 은 조건당 1회 (wall-clock 은 회차 폭이 있다 — 판정은 호출 수 차등과 long task 유무로 했다), cold 로드는 3회 (폭 ±1 %).

## 5. 방법론

### 5.1 원칙 — 비용 계약 3 종

모든 상호작용 경로를 아래 셋 중 하나로 분류하고, 계약을 깨는 자리를 순서대로 없앤다.

| 계약      | 뜻                                     | 대상                                                  |
| --------- | -------------------------------------- | ----------------------------------------------------- |
| 화면 비례 | 비용 ∝ 화면 안 요소 수                 | pan · zoom · hover · 그리기 · overlay · 헤더 · 눈금자 |
| 변경 비례 | 비용 ∝ 바뀐 record 수                  | 편집 · drag · 선택 · undo · 글꼴 동기 · History       |
| 문서 비례 | 허용하되 **시간을 쪼갠다** (동기 금지) | 열기 · breakpoint · 테마 전환 · 미리 기록             |

### 5.2 게이트 — 「3배 문서에서 호출 수 배율」

- 같은 fixture 를 N 장 · 3N 장으로 `--fixed-inputs --call-counts` 측정 → 부류별 V8 호출 수 배율. 결정적이라 회차 폭이 없다 (ADR-246 ratchet 과 같은 종류의 값).
- 목표: 화면 비례 · 변경 비례 부류 (pan · zoom · select · edit · page-switch · drag) 배율 **≤ 1.2**. 지금 값은 §3.2.
- 함수별 차등 (dev) 이 원인 목록을 준다 — 호출 수가 페이지 수만큼 느는 함수가 곧 계약 위반 자리다. 지금 하니스는 상위 20 함수만 남겨서 이번 측정은 임시로 150 까지 넓혔다 → `--top-fn N` 옵션으로 넣는다.
- 로드는 `--cold-entries` 의 ready 와 가장 긴 동기 작업 (long task max) 을 기록한다.
- 유리한 경우만 재지 않는다: 페이지 수 축 외에 **페이지당 밀도** (폼 필드 200 개 한 장) · **instance 재사용** (같은 컴포넌트 500 instance) fixture 를 추가한다.

### 5.4 하지 않는 것

- Canvas 코어 Rust 통합 · 그리기 명령의 wasm 이전 — 근거 없음 (§1-5).

- 빌더 안에서 실행되는 서비스 성능 (데이터 조회 · 런타임 상태) — 빌더는 디자인 도구라 Preview · Publish 의 몫이다.
