# Collection 변경분의 수동 서버 저장

2026-11-26 · 외부 자료 조사 및 상세 설계 초안

> **2026-11-26 개정 안내** · 이 문서는 ADR-324 처음 초안의 조사 기록이다. 그 뒤 편집 상태는 [ADR-325](../../adr/325-collection-runtime-store-three-layers.md) (행 저장소 · 조회 결과 · 미저장 변경) 로 나뉘었고, [ADR-324](../../adr/324-collection-manual-batch-save.md) 는 「연결이 선언한 능력에 맞춰 보낸다」 로 개정됐다 — 아래의 영수증 조회 · 요청 압축 · 본문 서명은 필수 계약이 아니라 선택 능력이거나 범위 밖이다. 지금의 계약은 두 ADR 의 상세 설계가 정본이다.

사용자가 표의 셀을 고치면 같은 Collection을 보는 컴포넌트에 즉시 반영한다. 사용자가 **변경사항 저장**을 눌렀을 때만 이번에 수정한 행의 수정한 필드를 전송한다. 첫 설계 대상은 원격에 이미 존재하는 행의 셀 수정이다. 아래 HTTP 예시는 이 계약을 구현할 수 있는 고객 서버 또는 자체 서버를 가정한다. 현재 Composition에는 이 저장 서비스를 연결해야 한다.

## 3. Builder와 실행 세션

작성자는 Collection에 저장 endpoint, 서버 행 ID 필드, 행 버전 필드, 수정 가능한 필드 매핑을 설정한다. 일반 Button의 누르기 동작에 **Collection 변경사항 저장**을 연결한다. 작성자가 배치 본문이나 재시도 규칙을 직접 만들 필요는 없다. 기존 프로젝트의 즉시 제출 규칙은 계속 해석한다. 수동 저장으로 전환하는 Collection은 같은 목적지에 연결한 기존 셀 제출 규칙을 함께 점검해 이중 쓰기를 막는다.

세션은 사용자·테넌트·프로젝트·Collection·연결 환경이 같은 편집을 공유한다. 조회 필터나 페이지 이동은 같은 데이터 원본에서 보는 범위만 바꾼다. 연결 환경이나 사용자가 바뀌면 기존 편집을 새 대상으로 전송할 수 없게 격리한다. 원격 저장에 사용할 키는 서버가 인정한 고유 ID다. 현재 UI에서 허용하는 위치 기반 `row-N`은 정렬이나 페이지 이동 후 다른 행을 가리킬 수 있다. [현재 행 키 해석](../../../packages/shared/src/collections/resolveCollectionItems.ts#L340)

| 동작                                | 화면과 저장 상태                                                                                                                                                                                                               |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 조회 후 첫 편집                     | 처음 수정한 필드의 서버 값과 행 버전을 기억한다. 아직 보내지 않은 값은 행 ID·필드별로 한 개만 유지한다. `3 → 5 → 8`은 8 한 건이고, 보내기 전에 3으로 되돌리면 0건이다.                                                         |
| 정렬·필터·다음 페이지               | 서버 응답은 조회 결과만 바꾼다. 같은 ID에 미전송 값을 다시 적용하고 화면 밖의 수정도 저장 개수에 포함한다. 조회 버전이 달라진 행에는 충돌 가능성을 표시한다. 필터에서 사라졌다는 이유로 삭제됐다고 판단하지 않는다.            |
| 저장 클릭                           | 해당 Collection에서 요청 하나만 진행한다. 대상·행 버전·필드값·편집 순번·요청 ID를 그 시점에 고정한다. 이후 편집은 다음 저장에 속한다. 쓰기 요청을 진행하는 동안에도 편집할 수 있다.                                            |
| 성공 확인                           | 요청 ID, 대상 행 ID 집합과 새 버전을 검증한다. 서버가 보정한 값을 기준값에 반영하고 **보낸 뒤 다시 편집하지 않은 셀만** 저장 완료로 바꾼다. 영향받은 계산 열·정렬·그룹 합계가 있으면 필요한 행이나 뷰를 다시 조회한다.         |
| 저장 뒤 원래 값으로 재편집          | 원래 수량 3을 8로 보낸 뒤 응답 전에 다시 3으로 바꿨다면, 첫 저장 성공 뒤 서버 기준은 8이고 다음 변경은 3이다. 요청이 확실히 거절돼 서버 기준이 3이라면 남은 변경은 0건이다. 응답 전에는 사용자의 두 번째 편집 의도를 보존한다. |
| 타임아웃·연결 끊김·성공 형식 불일치 | `결과 확인 중`으로 표시한다. 같은 요청의 결과 조회나 동일 요청 재시도로 확인한다. 더블 클릭이나 자동 새로고침으로 새 쓰기 ID를 만들지 않는다.                                                                                  |
| 버전 충돌·검증 실패                 | 미전송 값을 유지한다. 서버에서 다시 읽은 값과 수정 전·후 값을 대조한다. 행 버전만으로 어느 열이 바뀌었는지 알 수 없으므로, 사용자에게 보여줄 필드를 실제로 비교한다. 사용자가 해결하고 저장하면 새 ID와 최신 기준 버전을 쓴다. |

기본 초안에서는 보내기 전 수정값을 실행 세션 메모리에 둔다. 새로고침이나 탭 종료까지 초안을 복구하려면 별도 보관 정책이 필요하다. 제출 결과를 재접속 후에도 확인하려면 요청을 보내기 **직전**에 사용자·대상과 요청 ID를 묶어 영수증 조회에 필요한 최소 정보만 기록한다. 영수증으로 복구할 수 있는 범위는 서버에서 처리한 요청의 결과까지다. 개인 데이터가 든 초안을 기존 조회 캐시에 함께 넣는 일은 별도 설계 대상으로 둔다. [OWASP 브라우저 저장소 지침](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#indexed-databases)

## 4. 참조 HTTP 계약

조회 응답은 화면에 필요한 필드와 함께 영구 행 ID와 서버 발급 버전을 내려준다. 버전은 클라이언트가 대소를 해석할 필요 없는 문자열로 취급한다. 서버는 같은 행의 수명 동안 과거 버전을 재사용하지 않으며, 삭제 후 재생성한 행도 이전 쓰기와 구분한다. 데이터 원본이 버전을 제공하지 않으면 동시 수정 검출 가능 여부를 따로 표시한다.

**요청 예시** · `POST /v1/collections/orders/rows:batchUpdate`

```json
{
  "requestId": "31f947aa-55cb-46d1-a09e-34f8881c6eb4",
  "updates": [
    { "id": "ord-42", "baseVersion": "v17", "set": { "quantity": 8 } },
    { "id": "ord-91", "baseVersion": "v4", "set": { "note": null } }
  ]
}
```

`quantity`와 `note`만 대입한다. 빈 문자열·0·false·null을 각각 보존하고, 본문에 생략된 필드에는 쓰지 않는다. 배열·객체 셀을 지원할 경우 1차 계약은 그 셀 값 전체의 교체다. 각 행의 `set`에 컬렉션 스키마의 전송값 변환을 적용한 뒤 배치 전체를 한 번 직렬화한다. 기존 `outgoingRecord`는 단일 레코드를 처리하며 `stringifyJsonLossless`는 큰 정수의 표기를 보존한다. [필드 변환](../../../packages/shared/src/collections/intake/outgoing.ts#L29) · [JSON 직렬화](../../../packages/shared/src/collections/intake/parseJsonLossless.ts#L127)

**성공 응답 예시** · `200 OK`

```json
{
  "requestId": "31f947aa-55cb-46d1-a09e-34f8881c6eb4",
  "updated": [
    { "id": "ord-42", "version": "v18" },
    { "id": "ord-91", "version": "v5" }
  ]
}
```

서버가 필드값을 정규화하면 해당 행에 보정된 필드와 값을 추가한다. 같은 행이 두 번 나오거나 요청한 행의 새 버전이 빠진 응답은 결과 확인 대상으로 둔다. 위 계약에서 ID와 버전은 문자열이다. 기존 외부 API가 다른 자료형을 요구하면 어댑터가 손실 없이 변환한다.

| 응답 또는 상황              | 처리 계약                                                                                                                                                                                                         |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `409` 버전 충돌             | 배치 전체를 롤백한다. 읽기 권한 범위에서 충돌한 행을 식별하고 최신 값을 다시 조회한다. 단일 행에 HTTP `If-Match`를 쓰는 외부 API는 `412`를 같은 화면 상태로 매핑한다.                                             |
| `409` 요청 ID와 내용 불일치 | 고정한 본문을 위반한 요청을 거절한다. 버전 충돌과 다른 문제 유형을 반환한다.                                                                                                                                      |
| `422` 입력 오류             | `application/problem+json`의 확장 필드에 오류 위치를 담는다. 예를 들어 `#/updates/0/set/quantity`는 전송 시점의 배열을 통해 `ord-42`의 수량 셀에 표시한다. 현재 화면의 0번째 행을 사용하면 정렬 후 잘못 표시된다. |
| `401/403`                   | 재인증 또는 권한 변경으로 처리한다. 권한이 사라진 행의 값이나 예전 성공 응답을 노출하지 않는다.                                                                                                                   |
| `413/415/429`               | 각각 크기 상한, 인코딩·미디어 타입, 호출량 제한을 안내한다. 요청 압축 미지원이 명확할 때만 같은 요청 ID와 JSON 바이트로 비압축 재시도한다. `429`의 `Retry-After`가 있으면 따른다.                                 |

원 서버를 제어할 수 있는 배포에는 `GET /v1/collections/{id}/saves/{requestId}`로 권한이 있는 사용자가 자신의 저장 결과를 확인하는 방법을 제안한다. 응답 유실 후 새로고침한 경우에 특히 유용하다. 결과 기록 보관 기간이 지나 조회할 수 없으면 화면은 해당 행을 다시 읽고 사용자에게 확인을 받는다. 값이 우연히 같다는 이유로 과거 요청의 처리를 단정할 수는 없다.

## 5. 서버가 보장할 순서

1. 사용자·테넌트·대상을 인증 문맥으로 식별한다. 요청 본문에서 테넌트나 쓰기 권한을 정하게 두지 않는다. 요청 수와 압축 전송량, **풀면서 센 바이트 수**, 행·필드 수를 제한하고 스키마를 검증한다. 중복 행 ID·중복 JSON 키·계산 필드·수정 불가 필드는 거절한다.
2. 행과 필드에 대한 현재 권한을 확인한다. 요청 식별 범위는 **테넌트 + 인증 주체 + 대상 연결/Collection + 작업 + 요청 ID**로 둔다. 같은 범위의 처리 기록을 반환할 때도 현재 권한을 적용한다. [OWASP 객체 권한](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/) · [필드 권한](https://owasp.org/API-Security/editions/2023/en/0xa3-broken-object-property-level-authorization/)
3. 최초 전송 때 고정한 **압축 전 JSON의 UTF-8 바이트**를 재시도에도 그대로 쓴다. 서버가 해제한 바이트에서 직접 계산한 지문으로 같은 ID의 내용 일치를 확인한다. 이 지문은 중복 판별용이다. gzip 설정 차이, 큰 정수의 부동소수점 반올림, JSON 재생성에 따른 차이를 피할 수 있다. [기존 정밀도 회귀 조건](../../../packages/shared/src/collections/intake/__tests__/adr313Exits.test.ts#L114)
4. 이미 커밋한 같은 요청이면 과거 결과를 먼저 반환한다. **그 뒤에** 신규 요청의 행 버전을 비교한다. 이 순서가 뒤집히면 응답을 잃은 사용자가 자신의 첫 저장 때문에 버전 충돌을 받는다. 동시 중복 요청은 저장소의 유일성 제약과 트랜잭션으로 직렬화한다.
5. 신규 요청은 모든 행에 대해 권한 범위와 `baseVersion`을 **실제 쓰기의 조건**으로 적용한다. 별도 조회에서만 버전을 검사하면 조회와 쓰기 사이에 다른 사용자의 변경이 들어올 수 있다. 하나라도 실패하면 전부 롤백한다. 성공한 배치의 최소 결과·요청 지문과 데이터 변경을 같은 트랜잭션으로 커밋한다. [AWS의 트랜잭션 설계](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/)

이 원자성은 실제 데이터를 소유한 서버의 보장이다. 외부 API 호출이 성공한 직후 Composition 중계 서버가 멈추면, 중계 서버의 DB 기록만으로 외부 변경의 성공을 판정할 수 없다. 커넥터는 원본 API가 제공하는 멱등 키·버전 조건·결과 조회를 연결해야 한다. 원본이 이 보장을 제공하지 않으면 결과 미확인 상태에서 사용자에게 확인 경로를 제공한다. 배치 크기 상한을 넘어 여러 요청으로 나누는 경우에는 배치 간에 일부만 반영될 수 있다는 점을 UI에 표시해야 한다. [AWS의 여러 시스템 쓰기 분석](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html) · [Google 배치 수정 지침](https://google.aip.dev/234)

## 6. 보안과 압축

| 보호할 대상             | 1차 적용안                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                    |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 전송값과 로그인 세션    | 운영 쓰기는 HTTPS를 사용하고, TLS 0-RTT로 들어온 쓰기는 처리 전 거절하거나 핸드셰이크 이후에 처리한다. 동일 출처의 쿠키 세션을 쓰면 `Secure`·`HttpOnly`와 배포에 맞는 `SameSite`, CSRF 토큰·허용 Origin 검증을 적용한다. OAuth를 쓰는 연결은 대상 API·쓰기 범위·만료를 제한한다. [RFC 8470](https://www.rfc-editor.org/rfc/rfc8470.html#section-5.2) · [OWASP CSRF](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html) · [OAuth 보안 권고](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)                       |
| 토큰 탈취와 메시지 변조 | 토큰 탈취가 중요한 OAuth 배포는 인증 서버와 API 양쪽이 지원할 때 DPoP 등 발신자 키에 묶인 토큰을 검토한다. DPoP가 증명하는 범위에는 편집 본문이 포함되지 않는다. 신뢰 경계를 넘는 중계에서 원문 무결성 검증이 별도로 필요하면 서버 간 HTTP 메시지 서명에 대상·메서드·본문 다이제스트를 포함하고 nonce·만료를 검증한다. 기밀성까지 요구하면 최종 복호화 주체와 키 관리부터 별도로 정한다. [RFC 9449의 보호 범위](https://www.rfc-editor.org/rfc/rfc9449.html#section-11) · [RFC 9421 서명 재사용](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.2.2)                   |
| Preview와 외부 자격증명 | 새 저장 기능은 Preview의 테스트 연결과 Publish의 운영 연결을 명시해 Builder 작성자의 자격증명이 배포 앱 사용자에게 승계되지 않게 한다. 서버 비밀키가 필요한 연결은 서버에서 해석한다. 중계 서버는 테넌트에 등록된 연결을 찾아 허용 목적지·메서드·리디렉션을 제한한다. 교차 출처 직접 연결은 고객 API가 허용한 Origin·메서드·요청 헤더를 사용한다. [OWASP 서버측 요청 지침](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html) · [Fetch CORS 규약](https://fetch.spec.whatwg.org/#http-cors-protocol)                     |
| 조건부 gzip             | 수신 endpoint가 gzip **요청**을 지원하고, 본문이 임계값 이상이며, 실제 압축 결과가 작을 때만 사용한다. `4 KiB`는 측정 후보값이다. 서버 응답이 gzip이라는 사실만으로 요청 지원을 추정하지 않는다. 압축 관련 `415`의 `Accept-Encoding` 응답 헤더를 해석한다. 압축을 풀 때의 바이트 상한과 처리 시간·배치 연산 수 상한도 적용한다. 비밀 토큰을 사용자 편집값과 같은 압축 본문에 섞지 않는다. [RFC 7694](https://www.rfc-editor.org/rfc/rfc7694.html#section-3) · [OWASP 자원 사용 제한](https://owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/) |
| 장애 조사와 개인정보    | 운영 감사에는 요청 ID, 주체 식별자, 연결, 수정 행·필드 수, 결과와 소요 시간을 기록한다. 토큰·세션 쿠키·셀의 원문·새 값/옛 값 전체는 기본 운영 로그에서 제외한다. 요청 ID만 알아도 다른 사용자의 결과를 열람할 수 없도록 영수증에도 접근 제어와 보관 기간을 둔다. [OWASP 로깅 지침](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet.html#data-to-exclude)                                                                                                                                                                                                   |

**같은 저장의 재시도와 탈취한 자격증명의 재사용은 따로 검증한다.** 예를 들어 메시지 서명을 쓰는 커넥터에서 응답이 끊기면 업무 요청의 ID와 본문은 유지하되, 새 전송 시도는 새 nonce로 서명할 수 있다. 첫 번째 값은 중복 저장을 막고 두 번째 값은 이전 서명의 재사용을 찾는다. 토큰과 함께 해당 브라우저에서 실행할 권한까지 장악된 경우에는 DPoP도 사용자의 의도를 증명할 수 없다. [RFC 9421 §7.2.2](https://www.rfc-editor.org/rfc/rfc9421.html#section-7.2.2) · [RFC 9449 §11.4](https://www.rfc-editor.org/rfc/rfc9449.html#section-11.4)

**추가 본문 암호화에는 압축 정책도 따로 둔다.** TLS로 전송해도 관찰자는 패킷 길이를 볼 수 있다. 사용자가 바꿀 수 있는 텍스트와 비밀값이 같은 압축 단위에 있고 결과 길이를 반복 관찰할 수 있는 배포라면 그 본문의 압축을 끈다. 최종 서버만 열 수 있는 JWE 같은 암호화 메시지를 별도로 채택할 때도 일반 JSON의 gzip 설정을 그대로 적용하지 않는다. JWT 보안 권고는 암호화 입력을 미리 압축하는 방식의 길이 노출을 명시한다. [TLS 트래픽 길이](https://www.rfc-editor.org/rfc/rfc8446.html#appendix-E.3) · [JWT 보안 권고 §3.6](https://www.rfc-editor.org/rfc/rfc8725.html#section-3.6) · [JWE](https://www.rfc-editor.org/rfc/rfc7516.html)

## 7. 첫 구현의 통과 조건

| 시나리오                                                      | 기대 결과                                                                                                |

| 서로 다른 두 페이지에서 편집한 뒤 필터 변경·조회·저장         | 쓰기 요청은 저장 클릭 때 한 번이다. 화면 밖 행까지 포함하고 바뀐 필드만 전송한다.                        |
| 두 컴포넌트가 같은 셀을 편집하고 일부를 원복                  | Collection 기준으로 합쳐지고, 원복한 필드는 사라진다. 다른 사용자·데이터 원본의 같은 ID는 섞이지 않는다. |

| DB 커밋 직후 응답 유실, 동시 재시도 두 번                     | 실제 반영 한 번, 같은 결과 반환. 같은 ID로 본문을 바꾸면 거절한다.                                       |
| 두 사용자가 같은 버전의 행을 편집, 또는 한 행만 검증 실패     | 원자적 endpoint에서는 두 번째 배치가 일부만 반영되는 일이 없다. 권한 내에서 충돌·오류 위치를 알려준다.   |
| 200 응답에 실패 행 포함, 행 버전 누락, 또는 외부 결과 불명    | 계약에 따라 개별 결과를 판독하거나 결과 미확인으로 남긴다. 전체 편집 표시를 지우지 않는다.               |
| 테넌트·필드 권한 변경, 로그아웃 후 다른 계정으로 로그인       | 남의 행·과거 영수증·미전송 초안을 보거나 새 계정으로 제출할 수 없다.                                     |
| `null`·0·false·빈 문자열·64비트 정수, gzip 지원·미지원        | 서버 값이 의도대로 보존된다. gzip 여부가 달라도 같은 요청의 재시도는 중복 쓰기를 만들지 않는다.          |
| 크기·행 수 제한 초과, 오래된 영수증, 운영 연결이 없는 Preview | 데이터 쓰기를 중단하고 원인과 남은 편집을 표시한다. 타임아웃만 보고 새 ID의 쓰기를 시작하지 않는다.      |

**권장 착수 범위**는 기존 행 수정, 사용자가 누르는 저장과 취소, 원자적 배치와 행 버전을 지원하는 endpoint 한 종류다. 행 추가·삭제, 부분 성공형 외부 API, 재시작 후 초안 복구는 각각 별도 계약으로 확장할 수 있다. 배치·보관 기간·압축 임계값은 실제 첫 데이터 원본의 제약과 지연 측정으로 정한다.

**검증 범위**는 공식 문서와 현재 소스 대조, Builder의 `dataActions.runtimeCache`와 `sourceRev` 테스트 2개 파일 15건 통과다. 원격 저장 프로토콜·인증 인프라·운영 성능은 이 문서의 제안 및 향후 검증 대상이다.
