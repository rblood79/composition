## 2. Phase 1 — 이름 변경 참조 유지 · 타입 규칙 (G1)

- `packages/shared/src/catalog/commands/variables.ts` (새) — `renameVariable(reader, variableId, name)`: 새 이름 검사 → entry `name` 교체 + 재작성. 재작성 대상 = Phase 0 1a 의 필드 목록, 판정 = 새 모듈 `catalog/runtime/variableReferences.ts` (`variableReferenceSites(graph, variableId)` → `{ entryId, field: "prop" | "bindingKey" | "viewCondition", path, name }[]`): 자리마다 **그 필드의 런타임 해소** 로 이 변수인지 판정 — `prop` 은 `catalogRecordVariables` 의 요소 사슬 (record 가 아니라 문서 노드의 조상 사슬로 근사 — instance 안 노드는 instance 경로의 소유자, Phase 0 에서 `catalogVisibleVariableEntries` 와 런타임 결과가 같은지 fixture 로 고정), `bindingKey` · `viewCondition` 은 `pageAndProjectStates`. `\{{` 리터럴 · `env` root 제외, `params` 는 변수로 해소될 때만 (route fallback 자리 제외 — `stateTemplate.ts:202`). `catalogVariableUsageCount` · `catalogVariableUsageCounter` 가 같은 모듈을 읽도록 바꾼다 (세기와 재작성이 한 판정 — 지금은 두 카운터가 각각 interaction 만 · props 만 센다, 리뷰 H2).
- 새 이름 검사 (리뷰 H3): (i) `catalogVariableNameConflict` 를 `projectVariableIds` 까지 보게 확장 (ii) 변경 뒤 소유자 범위의 기존 `{{ new }}` 자리 (`variableReferenceSites` 를 이름으로 역조회) 가 이 변수로 해소되면 `VARIABLE_NAME_SHADOWS` 거절 — 명령이 던지고 `commandRunner` 가 안내로. 세 호출 경로 (패널 · 코드 보기 · data sink) 가 같은 명령이라 검사 자리 1.
- 호출 교체: `stateVariables.ts:329` `rename` · `codeView.ts:163` `renameVariable` · `dataChange.ts` `define_variable` 의 이름 변경 (sink 가 `renameVariable` 을 `composeOver` 로 묶는다 — 286 의 `setDataEntries` 와 같은 step).
- 타입 변경: 사용자 결정 1 → `catalogVariableTypeChange(type, value)` 하나를 `setType` · `define_variable` · `VariableTable` 이 쓴다.
- 테스트: `commands/__tests__/renameVariable.test.ts` — 프로젝트 · 페이지 · 요소 × (참조 Text · `binding.key`) · 가림 · **prop ≠ key 같은 노드** · 리터럴 · `env` · `params` (변수 있음 → 재작성 / route 만 → 무변경) · `VARIABLE_NAME_SHADOWS` 거절 · Undo · 코드 보기 golden. 원복 RED = G0 ① ② ⑤ ⑥.
