# ADR-296 Design Breakdown — 코드 보기 투영 수리 + 프로젝트 가상 파일 트리

> 본문: [296-code-view-project-file-tree-projection.md](../296-code-view-project-file-tree-projection.md). 연구 입력: [CODE_EDITOR_FULL_SCOPE_DESIGN_2026-10](../../explanation/research/CODE_EDITOR_FULL_SCOPE_DESIGN_2026-10.md) §1 ~ §2 · §9. 선행 구현: ADR-284 (생성기 · 레퍼런스 fixture) · 285 (왕복 · anchor · baseline · 거절) · 286 (데이터 · 사이트 정의 entry 와 명령) · 281 (상속 규칙 끄기 · 대체) · 294 (컴포넌트 property 어휘 2 행).

## 1. 전제 lock-in (fork 4 질문 — ADR-294 breakdown §1 에서 가져옴, 사용자 confirm 2026-10-30 「둘 다 한다」)

1. **base / 응용**: ADR-294 = base (문서 스키마 · 실행기 · 패널 · 어휘 2 행). **ADR-296 = 응용** — 그 스키마와 다른 모든 entry 를 파일로 투영한다. 296 의 스키마 변경 0 · 새 명령 0.
2. **schema 직교성**: 296 은 스키마를 더하지 않으므로 specialization 도 아니다. 읽는 쪽 (생성기 · 역문법) 만 는다.
3. **선행 ADR 전제 reverse 검증**: 285 (코드 → 문서 명령, 정본 = 문서) · 286 (정의 = 문서 entry) · 282 (Library 읽기 전용 · unlock) · 281 (상속 규칙 끄기 · 대체 = instance 의 descendant patch) 의 의존 방향은 그대로 — 296 은 네 결정의 소비자다. 뒤집는 것은 **286 Decision 8 (사이트를 코드에 내지 않음)** 하나뿐이고 이는 의존 방향이 아니라 투영 범위이며 사용자 결정 2 로 묻는다.
4. **판독 전 전제**: 위 세 줄이 이 문서에 있으므로 판독 (phase 당 1 + 수리 1) 은 본문 정합만 본다.

## 4. 설계 요소

### 4a. 프로젝트 세션과 Apply 순서 (`catalogRuntime/codeView.ts` 확장 — 리뷰 h3)

- `CatalogCodeViewSession = {projectId, baselineRevision, files: Map<path, {result, draft?}>, open: path[]}` — 285 Decision 4 의 `{pageId, baselineRevision, baselineResult, draft}` 를 파일 맵으로. 첫 입력 때 baseline 을 잡고 (프로젝트 revision), 입력 전에는 문서가 바뀔 때마다 열린 파일을 다시 생성해 다른 줄만 써 넣는다 (지금 page 와 같음).
- **Apply 는 다섯 단계** — 지금 planner (`codeViewEdit.ts:249-274` — 파일 하나를 baseline reader 로 해석 · 그 stage 에서 재생성 대조 · 명령 반환) 를 파일마다 돌리고 합치는 것이 **아니다**:
  1. **파싱**: 초안이 있는 모든 파일을 lezer 로 읽는다 (오류 노드 = `unparsable`, 전체 0).
  2. **선언 수집**: 정의 파일 (`data/` · `api/` · `state/` · `components/` · `theme.css` · `App.tsx` 의 route 항목) 에서 새 선언 · 이름 변경 · 삭제를 모아 **공통 심볼 표** (이름 → entry id; 새 것은 임시 id, 이름 변경은 옛 이름 · 새 이름 둘 다) 를 만든다. 심볼 표는 baseline 심볼 (`codeViewEdit.ts:305-307` 의 `symbols`) 위에 얹는다.
  3. **stage 해석**: `stageOver(baseline)` 하나를 만들고 **정의 파일의 명령을 먼저** 계획 · 적용한다 (심볼 표의 임시 id 가 실제 id 로 확정). 그 뒤 **사용처 파일** (`pages/*.tsx` · `*.css` · `App.tsx` 의 element) 의 역문법은 **stage reader + 심볼 표** 로 참조를 검사한다 — 같은 Apply 에서 추가한 collection · 컴포넌트 · page · 바뀐 이름을 사용처가 바로 쓴다. 사용처 명령도 같은 stage 에 적용한다.
  4. **트랜잭션**: 모은 명령 전부를 `compose` 한 트랜잭션 · `expectedRevision = baselineRevision` 으로 실행 계획을 만든다 (`composeCommands` 가 실행 때 다시 stage 를 만드는 것은 그대로 — 3 단계의 stage 는 **해석용**, 4 단계의 stage 는 **실행용**이고 둘의 결과가 같아야 5 단계가 통과한다).
  5. **재생성 대조**: 최종 stage 에서 **초안이 있던 모든 파일을 다시 생성해** 각 편집본과 비교한다 (285 `compareRegenerated` — 파일마다). 하나라도 다르면 그 줄 거절 · 전체 0.
- 하나라도 거절이면 전체 0 (R4). 순서가 결과를 바꾸지 않도록 하는 것이 2 · 3 단계의 목적이다 — 「같은 트랜잭션이라 순서 무관」 이 아니라 **정의 먼저 해석해야 사용처가 읽힌다**.
- Apply 뒤의 이름 변경 (다른 Apply) 은 문서 rename 명령 하나 (`renameVariable` · `renameDefinition` · `renameNode` …) 이고 모든 열린 파일을 재생성한다 — 코드가 참조를 따라가지 않는다.

### 4c. 스타일 사상 (`styles.ts`, 결정 1 · 6 — 리뷰 h2)

- 클래스 = 노드 이름 kebab-case (`hero-title`) · 같은 이름이면 문서 순서로 `-2` · `-3` (결정적). page 파일의 요소에 `className="hero-title"` 를 낸다 — 사용자 `metadata.className` 이 있으면 뒤에 붙인다 (`"hero-title custom"`). anchor 가 identity 라 class 이름을 바꿔도 노드는 같다 (이름 변경 = `renameNode`). instance 안쪽 노드의 스타일 patch 는 `.<instance 이름> .<노드 이름> {…}` (descendant patch 의 visual · layout · sizing · fills · responsive · stateRules).
- 필드 ↔ 속성 1:1 표 (Phase 0 freeze): `VisualField` (color · background · border · radius · shadow · opacity · font …) · `LayoutField` (display · flex · grid · gap · padding · position …) · `SizingField` (width · height · min · max) · `fills` → `background: layer1, layer2` (레이어 순서 = 문서 순서) · `TokenUse` → `var(--<token>)`. 값은 문서 단위 그대로 (px · % · token). 변환 없는 1:1 이라 왕복이 결정적이다.
- 선택자: base `.c` → desktop · `@media (max-width: <tablet>)` → `responsive.tablet` · `@media (max-width: <mobile>)` → `responsive.mobile` (cascade = Canvas 와 같은 순서 — Phase 0 에서 `types.ts:826-837` 와 compositionRoot 를 대조) · `.c[data-hovered]` 등 = `stateRules` (RAC data 속성 이름 그대로 — D1).
- **`themeOverride` = 노드에 강제하는 `{mode?, tint?}`** (`types.ts:910-913`) — 조건부 스타일이 아니다. base 블록 안의 선언 둘로 낸다: `color-scheme: dark | light` (= `mode`) · `--theme-tint: <ThemePreset tint 이름>` (= `tint`). 역문법: 둘 중 있는 것만 모아 `setWholeField({field: "themeOverride", value: {mode?, tint?}})`, 둘 다 없으면 `value: undefined` (해제). `[data-theme=…]` 조건 선택자는 **노드 CSS 파일 어휘에 없다** (`outsideVocabulary`) — 테마 정의 (`theme.css`) 에서만 테마 이름이 선택자로 나온다.
- 재현 불가 값 (mesh fill · Skia 전용 효과 — 있으면 Phase 0 목록) → `/* composition: <field> — Design 패널 */` 표지 + anchor.
- 역문법: 선택자 → (노드 · breakpoint · state · instance 경로), 선언 → `setFields` · `setWholeField` 입력. 모르는 속성 · 선택자 · 단위는 `outsideVocabulary`. oracle (G3) = compositionRoot 해석 출력 동일 (`styleOf` `compositionRoot.ts:990` 는 비공개 — Phase 0 에서 공개 진입점 고정: export 또는 테스트 전용 접근자).

### 4d. 컴포넌트 파일과 instance `overrides` (`component.ts` · `generate.ts`, Phase 5 — 리뷰 h1)

- `export function <Name>({label, isActive, team, onPick, children, header}: <Name>Props)` — props = `DefinitionEntry.properties` (text · boolean · instance · variable · event — 294) + slots (`children` = 기본 slot, 이름 붙은 slot = ReactNode prop). `<Name>Props` 타입은 파생 줄.
- 본문 JSX = template 노드 트리 (page 생성기와 같은 `writeNode`) — 요소마다 `className="<노드 이름>"` (이 이름이 `overrides` 의 키), property 바인딩 자리는 `{label}` · `isDisabled={!isActive}` · `role={team}` (294 `componentPropertyCodeName`), event 는 `props.onPick?.(value)` (294 `writeAction` 그대로). **원본 규칙 = 이름 붙은 handler 함수** (`function onSaveButtonPress() {…}`, E9 모양) — 함수 이름이 규칙 id 의 결정적 이름이고 anchor 가 id 를 가진다. 이 파일의 편집은 원본 명령 — 모든 instance 에 미친다.
- page 파일의 instance: `<UserPicker team={roleFilter} onPick={setPicked} />` — `typeOf` 가 definition 이름을 돌려주고 (지금 `definitionTypeName` 은 루트 type), import 는 `./components/UserPicker`. 루트 prop = `setInstanceProperty`, slot 채움 = children / 이름 붙은 prop, 루트 자신의 instance 규칙 = 지금처럼 `onX={…}`.
- **안쪽 노드의 instance 몫** 은 `overrides` 객체 prop 하나:

  ```tsx
  <UserPicker
    team={roleFilter}
    overrides={{
      "save-button": {
        isDisabled: true, // DescendantPatchFields.props
        onPress: rules({
          inherited: {
            onSaveButtonPress: "off",
            onSaveButtonPress2: () => {
              setPicked(null);
            },
          }, // 규칙 id → off | 대체 (page 변수 참조 가능)
          own: [
            () => {
              toasts.add({ title: "A only" });
            },
          ], // 이 instance 의 address 규칙 (B 에 없다)
        }),
      },
    }}
  />
  ```

  - 키 = **안쪽 경로** `'<중첩 instance 이름>/…/<노드 이름>'` = `InstanceAddress` 전체 (리뷰 round 2 h1). `instances[1..]` (바깥 instance 아래의 중첩 template instance) 는 각각 **그 template 안의 노드 이름** 으로, 끝은 `templatePath` 의 대상 노드 이름으로 — `/` 로 잇는다. 직접 자식은 `'save-button'`; 바깥 instance 안에 같은 UserPicker 원본이 `left-picker` · `right-picker` 로 둘 있으면 `'left-picker/save-button'` · `'right-picker/save-button'` 이 서로 다른 키다 (L = `{instances: [outer, left-picker], templatePath: [root, save-button]}`). 각 segment 는 그 template 안에서 유일 (동명 `-2`) 하므로 경로 전체가 `InstanceAddress` 와 1:1 로 복원된다. 같은 경로 키가 둘이면 `ambiguousAddress` 거절. 중첩 instance 자신 (segment 끝이 instance) 에 대한 patch 는 `'left-picker'` 키.
  - `inherited` 키 = 원본 handler 이름 = `DescendantPatchFields.interactions` 의 규칙 id. `'off'` → `catalogInheritedRuleEnabledCommand` (`catalogRuntime/interactions.ts:895`), 함수 → `catalogReplaceInheritedRuleCommand` (`:920`). 같은 trigger 의 원본 규칙 둘 중 하나만 끄거나 대체할 수 있다.
  - `own` = `InteractionEntry {ownerId: instance, address}` (E5) — 지금 instance 요소 handler 로 잘못 나오던 것. 다른 instance 에 없다.
  - 스타일 patch 는 CSS 파일 — 선택자 = 같은 경로를 class 체인으로 (`.outer-1 .left-picker .save-button {…}` · 직접 자식은 `.user-picker-1 .save-button {…}`). 역문법은 이 체인을 **위치 경로** 로 읽는다 (CSS 매칭 의미가 아니라 `InstanceAddress` 복원 — 체인 길이가 다르면 다른 위치라 `.outer-1 .save-button` 과 `.outer-1 .left-picker .save-button` 은 겹치지 않는다). `enabled: false` (slot 끄기) 는 `overrides` 의 `hidden: true`.
  - 역문법은 `overrides` 를 **instance 명령으로만** 읽는다 — descendant patch 쓰기 · 상속 규칙 둘 · address 규칙. `pushInstanceOverrides` (`instanceOverrides.ts:362` — 원본에 밀어 넣기) 는 부르지 않는다. 원복 RED: `overrides` 를 원본 명령으로 읽게 바꾸면 G4 의 「B 무변화」 가 RED.
  - `rules()` · `overrides` 는 `endpoint()` · `secret()` 과 같은 **composition 고정 도우미** — 레퍼런스 앱에 없지만 문서 모델 (`address` · 규칙 id 맵) 을 담는 최소 닫힌 어휘다. 임의 JS 가 아니다.

- Library 원본 = `node_modules/@composition/library/<Name>.tsx` 읽기 전용. Library instance 의 `overrides` 는 허용 (instance 몫). Local override (`DefinitionOverrideEntry`) 가 있으면 `components/<Name>.tsx` 가 바뀐 부분만 담고 나머지는 Library 파일을 import 하는 모양 — Phase 0 에서 282 `templateMap` 과 대조해 고정.

### 4e. page 파일 수리 (Phase 1 어휘)

- E9 handler 함수: `function on<Node><Event>() { …Do… }` 를 page 함수 안, 규칙마다 하나 · anchor = 규칙 id. 속성은 `onPress={() => { a(); b(); }}` (규칙 1 이면 지금처럼 `onPress={a}` 또는 setter 단축 유지 — golden 변화 최소).
- E4 대상 참조: Do 인자 둘째에 `{target: <nodeName>}` (address) · `{target: 'local'}` · 없으면 unset — 283 의 세 종류와 1:1.
- E5 임시: Phase 5 전까지 instance 안 `address` 규칙은 instance 요소 handler 출력을 **중단** 하고 읽기 전용 표지 `/* composition: instance rule at <address> — Phase 5 */` 로 낸다 (지우면 거절) — 원본으로도 instance 루트로도 읽지 않는다.
- E13 표지 · E12 값 표기 · E10 `parentKey` · E3 `formRef` · E2 capability id · E1 숨김 When — 각각 어휘표 행 + golden 조각 + read 테스트 (G1 read 실증).

### 4f. 식별자 규칙 (한 곳 — `codeView/names.ts`)

- 컴포넌트 함수 · 파일 = PascalCase(definition 이름); RAC export 이름 (`Button` · `Dialog` …) 과 같으면 `<Name>Component`; 같은 이름 둘 = 문서 순서 `2`.
