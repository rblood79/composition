# ADR-294 Design Breakdown — 사용자 컴포넌트의 event · variable property

> 본문: [ADR-294](../completed/294-component-event-variable-properties.md). 이 문서는 구현 상세 (Phase · 파일 · 체크리스트 · 코드 모양) 다. `docs/adr/evidence/` 는 gitignore 라 inventory · 실측의 결론은 여기 §2 에 둔다. 리뷰 Round 1 (2026-10-30, [reviews/294.md](../reviews/294.md)) 의 HIGH 3 을 §3 · §3a · §6 에 반영했다.

## 1. ADR 분리 4 질문 (lock-in)

1. **base / 응용**: ADR-294 = base (문서 스키마 · 실행기 · 패널 두 곳 · code view 어휘 2 행). ADR B (code view 투영 수리 + 가상 파일 트리, 연구 §0 ~ §8) = 응용 — 이 스키마를 `components/*.tsx` 파일로 투영한다. B 의 스키마 변경 0.
2. **schema 직교성**: B 는 스키마를 더하지 않는다. 294 가 더하는 것은 `ComponentPropertyKind` 2 · opcode 1 · trigger 접두 1 · `StateVariableEntry.input` 표지 1 — B 의 어떤 결정도 이것의 specialization 이 아니다.
3. **선행 ADR 전제**: ADR-261 (property = instance 루트 props 의 key → 원본 노드 투영) · 281 (원본 규칙은 모든 instance 에서 실행 · 대체 맵) · 283 (대상은 장소 참조 · template 밖 금지) · 288 (변수 가시성 = 소유자 사슬 → page → 프로젝트) 의 방향을 그대로 둔다. grep 확인: `TARGET_IN_TEMPLATE` (`graph.ts:1927`) · `ownerChain` (`stateVariables.ts:75-87`) 무변경.
4. **판독**: phase 당 판독 1 + 수리 검증 1. 전제 검증은 이 §1 로 끝낸다. Round 1 은 소스 반례 4 로 설계 셋을 고쳤다 (§3 · §3a · §6).

## 3. Phase 1 — 스키마 · 검증 · 실행 (contract 52)

- `ComponentPropertyKind` += `"event" | "variable"`. `ComponentProperty` 에 `valueType?` (event) · `variableId?` (variable). `StateVariableEntry.input?: { propertyKey: string }`.
- **prop 계약 (h2)**: `componentPropertyAccepts(properties, lookupVariable)` 가 variable key → 변수의 `valueType` 을 prop `ValueType` 으로 — string · number · boolean 그대로, date → `string`, object · array → `string` (참조 문자열만 담는다). `validatePropWrites` 셋째 예외: key 가 정의의 variable property 이고 값이 `"!var.<id>"` 면 — 참조 변수 존재 (`DANGLING_VARIABLE`) · 그 instance 노드에서 보임 (shared `visibleVariableIdsOf(graph, nodeId)` — `catalogVisibleVariableEntries` 의 술어를 shared 로 옮겨 Builder 가 같은 것을 import) · 타입 같음 (`STATE_VALUE_TYPE`) 일 때 통과. variable key 에 object · array 리터럴 (JSON 문자열 포함) 은 `PROP_TYPE_MISMATCH` · date 리터럴은 `isDateValueText`. `referencedIds` 가 그 참조 id 를 든다.
- `validation.ts`: event · variable 은 `targets.length === 0` 요구 · `variableId` 는 `stateVariable` · `ownerId === definition.templateRootId` · `input.propertyKey === key`.
- `InteractionAction` += emit. `graph.ts` 검증: `emit` → 주인의 정의 (`catalogOriginRootOf`) 의 properties 에 event `propertyKey` (없으면 `DANGLING_PROPERTY`) · `property:<key>` trigger → 주인 노드가 project 정의 instance 이고 그 정의에 event key (없으면 `UNKNOWN_TRIGGER_ID` 그대로) · `setState` 의 `variableId` 가 `input` 변수면 `INPUT_VARIABLE_READ_ONLY`.
- 정의 property 삭제 명령: 그 key 를 쓰는 `emit` Do · `property:` 규칙 · variable 이면 변수 entry 와 instance 루트 props 의 key 값을 함께 지운다 (ADR-288 의 「사용처가 같이 간다」) — 사용처 수를 Properties 행에 표시.
- **경계 함수 (h1 · Round 2)** `componentBoundariesOf(record, graph)` (`catalog/runtime/componentBoundaries.ts`): `record.instancePath` 의 각 id 와 `record.collapsedSourceIds` 의 각 id 중 `getEntry(id).kind === "node"` 이고 `definitionId` 가 `project:` composite 인 것을 **바깥 → 안쪽** 순서 (`instancePath` 먼저, 그 다음 접힌 층 순서) 로 `{ instanceId, definitionId, occurrence }` — `occurrence` = 그 경계까지의 instance id 들을 `/` 로 이은 경로 + (`record.rowIndex` 가 있으면 `@<rowKey>`). 예: I1 안 J 는 `I1/J`, I2 안 J 는 `I2/J`, 행 3 안 instance K 는 `L@row-3/K`. 문서 `instanceId` (J) 는 graph 조회 (정의 · props) 에만 쓴다. 안쪽 record 의 `instancePath` 가 접힌 instance 를 이미 포함하면 (§2d) 중복 id 는 한 번.
- `DispatchDeps.emit(propertyKey, value, context)` → 세션: 실행 record 의 경계 사슬을 안쪽부터 → 규칙 주인의 정의 D 와 `definitionId === D` 인 첫 경계 (주인이 D 의 instance 노드 자신이면 그 경계는 건너뜀 — wrapper 재발행) → 수신 색인 `receivers.get(boundary.occurrence)?.get(key)` → 각 규칙을 `executeInteractionRule(rule, deps, { ...context, event: { value } })` — 진행 중 집합에 `(occurrence, key)` 가 있으면 `{ ok: false, reason: "EMIT_REENTRANT" }` · 결과 `{ ok: true, kind: "emit", listeners: n }`. 수신 색인은 `catalogPreviewRules` 변환 때 `property:` 규칙을 핸들러 색인 대신 여기에 — 규칙은 지금처럼 record 마다 변환되고 (`recordsOfOwner` · capability 대상도 그 record 문맥으로 해석), 그 record 의 경계 중 owner instance 에 해당하는 경계의 `occurrence` 로 등록된다 (I1 안 J 의 규칙 → `I1/J`, I2 안 → `I2/J`).
- 테스트: `adr294Schema.test.ts` (shared — 검증 9 · R7 prop 계약 반례 전수 · contract) · `adr294Emit.test.ts` (세션 — G1 실행 반례 9: instance 2 · 접힌 중첩 + 같은 이름 재발행 · **같은 Outer 둘 안의 같은 J (I1 emit → I1/J 만 1회, I2/J 0, 대상 record 도 I1 쪽)** · 행 안 · ◆ 직접 · off · 재진입 · 끈 규칙 · 대체 규칙) · RED ② ④a ④d ⑤ GREEN · 원복 RED 2 (경계 함수를 `instancePath` 만으로 → 중첩 반례 RED · 키를 `instanceId` 로 → I1 · I2 반례 RED).

### 3a. Phase 1 · 4 — 입력 변수의 해석 · 갱신 (h3)

- **해석 함수** `resolveInputVariable(graph, variableId, boundaries, env)` (`catalog/runtime/inputVariable.ts`):
  1. `variable.input.propertyKey` · 소유 template 루트의 정의 D → `boundaries` 에서 `definitionId === D` 인 가장 안쪽 경계 B (없으면 ◆ 직접 — 기본값).
  2. B 의 instance 노드 (행이면 그 행 override 를 지난 record props — resolver 가 instance 루트 props 를 record 에 싣는다) 의 `props[key]`: 없으면 기본값 · 리터럴이면 그 값 (date 는 ISO 글자 그대로) · `"!var.<id>"` 면 `env.read(id, scopeOf(id, B 바깥 경계들))` — 참조 변수가 또 입력 변수면 재귀 (경계 수로 유한), page · project 변수면 그 scope 의 값 (Canvas env 는 기본값 · Preview env 는 runtime).
- **독자 넷**:
  - `catalogStateEnv` (`stateTemplate.ts:196-219`): `byId` · `get` 이 `input` 변수면 `read` 대신 해석 함수. env 생성자에 `boundaries` 가 들어온다 — compositionRoot 의 record 별 env (이미 record 마다 `stateSource` 를 만든다 — `:2087` 인근) 에 `componentBoundariesOf(record)` 를 싣는다. Canvas 는 그대로 기본값 env 라 참조 변수의 기본값이 나온다 (Decision 5).
  - 보기: `pageAndProjectStates` → `visibleStatesAt(graph, ownerId, source, boundaries)` — 소유자 사슬에서 **template 루트** (어떤 정의의 `templateRootId`) 를 만나면 그 루트 소유 `input` 변수를 `{ scope: { kind: "element", instanceKey } }` 로 더한다 (값은 해석 함수). `catalogBindingQuery(graph, binding, sourceId, source, boundaries?)` — 행 감싸개가 record 의 경계를 넘긴다.

## 5. Phase 3 — code view (page 파일)

- 생성: instance 요소 속성 `on<Name>={(value) => { … }}` — 본문은 기존 `handlerCode` (Do → 문장) 재사용, 인자 이름 `value` (타입이 object 면 `item`). `variable` property 는 `<key>={리터럴}` 또는 `<key>={변수 코드 이름}` (`!var.<id>` 참조 ↔ 그 변수의 `useState` 이름 — 이미 어휘표에 있는 변수 이름 slot).
