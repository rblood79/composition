# ADR-324 상세 설계 · Collection에서 편집한 필드의 수동 서버 저장

[ADR 본문](../324-collection-manual-batch-save.md) · [원본 코드와 외부 사례 조사](../../explanation/research/COLLECTION_REMOTE_SAVE_2026-11.md)

작성 기준은 2026-11-26, HEAD `39b277f95`다. 아래 요청·응답·상태 전이와 G0~G5는 구현할 계약이다. 크기 기준선만 로컬에서 측정했다.

## 작성자가 설정하고 앱 사용자가 저장하는 흐름

1. 작성자는 Builder의 Collection 설정에서 **조회 endpoint**와 **수동 저장 endpoint**를 각각 선택한다. 저장 쪽은 기존 `keyField`, 서버 버전을 읽을 필드, 쓰기가 가능한 필드 매핑을 확인해야 활성화된다. 조회 정책의 `manual`은 조회 시점을 뜻한다. 저장 정책과 별개로 설정한다. [현재 문서 타입](../../../packages/shared/src/catalog/document/types.ts#L1700) · [조회 연결 처리](../../../apps/builder/src/builder/stores/utils/dataChange.ts#L845)
2. 작성자는 기존 Button에 **Collection 변경사항 저장** 또는 **미전송 변경 취소** 동작과 대상 Collection을 연결한다. 새 저장은 사용자가 지정 버튼을 마우스·터치·키보드로 실행할 때 시작한다. 조회 완료·타이머·셀 변경 규칙에 이 동작을 연결하면 작성 검증과 실행 경로에서 거절한다. 무변경 또는 같은 범위에서 제출 중이면 저장을 비활성화하되 편집은 허용한다. 폼에서 셀 값을 확정하면 로컬 변경 건수가 늘어난다. Preview 테스트 연결을 구성하지 않았으면 이유를 표시한다.
3. 사용자가 같은 Collection을 보는 두 컴포넌트에서 편집하면 양쪽에 즉시 반영된다. 저장 버튼은 필터로 숨겨진 행까지 포함한 변경 행·필드 수를 표시한다. 취소는 아직 보내지 않은 변경만 되돌린다. 전송 중·결과 확인 중에 전체 취소를 눌러 이미 제출한 요청까지 되돌렸다고 표시하는 일은 막는다.
4. 성공하면 서버가 보정한 값과 새 버전을 보여준다. 충돌하면 읽을 권한이 있는 범위에서 **수정 전 값 / 내 값 / 현재 서버 값**을 비교한다. 사용자가 선택한 결과를 최신 버전으로 다시 저장한다. 서버에서 행을 삭제했거나 권한을 회수했다면 이유를 권한 범위 안에서 표시한다. 상태 알림은 기존 접근성 경로로 전달하고 실패 후에도 현재 셀과 키보드 초점을 찾을 수 있어야 한다.

## 편집 상태와 응답 순서

**식별 범위**는 인증 주체·테넌트·프로젝트·실행 환경·원본 연결·Collection이다. 정렬·필터·페이지·Table 인스턴스는 같은 범위의 편집을 공유한다. 같은 Collection이 파라미터에 따라 다른 데이터 집합을 가리키고 행 ID가 겹칠 수 있으면 해당 데이터 집합의 식별자도 범위에 넣는다. 대상 또는 로그인 주체 변경 시 진행 요청을 새 범위로 넘기지 않는다. 오래된 응답은 이전 범위에만 귀속하고 로그아웃 시 초안과 접근 가능한 영수증 정보를 폐기한다.

조회에는 권한 있는 필드와 함께 불변의 서버 행 ID·불투명 버전이 필요하다. 표시용 `fieldMap.value`, 순번, `row-N`, 집계·합계 행은 쓰기 식별자로 사용할 수 없다. API가 문자열·안전 범위 밖 정수 등으로 키를 주면 계약에 맞춰 손실 없이 정규화한다. 중복·결측 ID/버전은 해당 연결이나 행을 편집 불가로 표시한다. 원본은 삭제 후 재생성까지 포함해 이전 버전 토큰을 재사용하지 않는다. [현재 표시 키 우선순위](../../../packages/shared/src/collections/resolveCollectionItems.ts#L340)

Builder의 `collection_runtime` 복원은 프로젝트로 행을 찾아 설정 지문을 대조한다. 이 지문만으로 현재 로그인 주체의 읽기 권한을 판정할 수 없다. 수동 저장용 인증 연결은 현재 범위와 읽기 권한이 확인된 응답만 화면·편집 기준값에 사용한다. 이 구분이 없는 영속 캐시는 해당 연결에서 읽기와 적재를 모두 건너뛴다. [캐시 복원](../../../apps/builder/src/builder/stores/utils/dataActions.ts#L109) · [설정 지문 입력](../../../apps/builder/src/builder/panels/datatable/utils/sourceRev.ts#L124)

**순서 검증 예** · 서버 수량 3을 8로 저장하고 응답 전에 다시 3으로 편집한다. 첫 요청이 성공하면 기준 8·초안 3·다음 전송 1건이다. 원본이 확실히 거절하고 기준이 3이면 다음 전송 0건이다. 응답을 잃으면 원래 요청을 확인할 때까지 두 가능성을 유지한다. 페이지를 바꾸거나 다른 Table에서 두 번째 편집을 해도 동일하다.

미전송 값은 메모리에 둔다. 재접속 복구를 제공하는 연결은 **전송 직전** 권한 범위·요청 ID·시각 등 영수증 조회에 필요한 최소 식별 정보만 기록한다. 저장소를 사용할 수 없으면 복구 보장을 표시하기 전에 이를 알리고, 그 보장이 필수인 연결은 전송을 막는다. 브라우저 재시작 후 본문이 사라졌으면 영수증 조회만 가능하다. 이때는 서버가 기록한 결과를 보여주고 허용된 행을 다시 읽는다. 사라진 로컬 편집 순번에 완료 표시를 소급하지 않는다. 만료·권한 소실·조회 불능 시 읽을 수 있는 행을 다시 확인하고 사용자 판단을 받는다. 값 일치만으로 과거 요청이 처리됐다고 판정하지 않는다. [OWASP 브라우저 저장소 지침](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html#indexed-databases)

## 참조 HTTP 계약

기존 읽기 endpoint는 원본이 지원하는 페이지·필드 선택을 사용한다. 편집 가능한 행은 필요한 화면 필드 외에 ID·버전을 함께 얻어야 한다. 미조회 필드에는 쓰지 않는다. 아래 쓰기 endpoint는 원자적 처리, 대상·인증, 한도, 요청 인코딩, 중복 방지 기간 및 영수증 조회를 계약으로 공개한다. URL은 참조 규격이며 고객 API는 같은 의미를 제공하는 경로에 매핑할 수 있다.

**요청** · `POST /v1/collections/orders/rows:batchUpdate` · `Content-Type: application/json`

```json
{
  "requestId": "31f947aa-55cb-46d1-a09e-34f8881c6eb4",
  "updates": [
    { "id": "ord-42", "baseVersion": "v17", "set": { "quantity": 8 } },
    { "id": "ord-91", "baseVersion": "v4", "set": { "note": null } }
  ]
}
```

**성공 응답** · `200 OK` · `updated`의 순서는 자유이고 행 ID 집합은 요청과 정확히 일치한다.

```json
{
  "requestId": "31f947aa-55cb-46d1-a09e-34f8881c6eb4",
  "updated": [
    { "id": "ord-91", "version": "v5" },
    { "id": "ord-42", "version": "v18" }
  ]
}
```

`set`은 스키마에 허용된 필드의 대입이다. `null`·`false`·`0`·빈 문자열과 생략을 구별한다. 배열·객체형 셀은 전체 값 교체다. `set`에 들어간 필드만 기존 타입·encoding 계약으로 변환한 뒤 외부 필드명으로 매핑하고 전체 배치를 lossless JSON UTF-8로 한 번 직렬화한다. 스키마가 바뀔 때 필드 ID·외부 키·인코딩 색인을 준비한다. 저장 시에는 행의 `set`에 등장한 필드 정의만 색인에서 찾아 평평한 레코드용 `outgoingRecord`에 넘긴다. 매 행마다 전체 스키마를 순회하거나 변환 과정에서 생략 필드를 추가하는 일을 막는다. 서버가 값을 보정했다면 해당 행에 선택적 `canonical`을 반환한다. 예를 들어 공백을 다듬은 이름은 `"canonical": {"name":"Kim"}`으로 알려준다. [나가는 필드 변환](../../../packages/shared/src/collections/intake/outgoing.ts#L29) · [손실 없는 직렬화](../../../packages/shared/src/collections/intake/parseJsonLossless.ts#L127)

### 원본 서버 처리 순서

1. 인증 문맥에서 테넌트·주체·원본·작업을 결정한다. 미디어 유형·요청 수·압축 바이트·해제 중 누적 바이트·연산 수·시간을 제한한다. 파싱 시 중복 JSON 키·중복 행·빈 변경·수정 금지 필드·기대하지 않은 타입을 거절한다. 필드 매핑은 원본 허용 목록을 기준으로 검사한다.
2. 현재 행·필드 권한을 확인한다. `테넌트 + 주체 + 원본 연결/Collection + 작업 + requestId`를 중복 확인 범위로 쓴다. 서버에서 **압축 해제된 원래 UTF-8 바이트**의 지문을 계산한다. 클라이언트가 보낸 지문을 신뢰하거나 숫자를 파싱한 뒤 다시 만든 JSON을 사용하지 않는다.
3. 같은 범위·ID가 이미 커밋됐으면 지문 일치와 **현재** 권한을 확인해 보관한 결과를 반환한다. 다르면 요청 ID 내용 불일치로 거절한다. 중복 확인은 신규 요청의 행 버전 검사보다 먼저 한다. 유일성 제약이나 동등한 직렬화 수단으로 동시에 도착한 동일 ID도 한 번만 반영한다.
4. 신규 요청은 모든 행을 권한 범위와 `baseVersion` 조건으로 갱신하고 새 버전을 발급한다. 권한·버전 검사와 실제 쓰기 사이에 권한 철회나 다른 트랜잭션이 끼어도 잘못된 갱신이 커밋될 수 없도록 원본에서 보장한다. 성공 행과 최소 결과·지문을 같은 트랜잭션으로 커밋한다. 하나라도 실패하면 모든 행을 되돌린다. 외부 HTTP 호출과 중계의 별도 DB 기록은 이 트랜잭션을 대신할 수 없다. [AWS 멱등 요청](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) · [Google 동기 배치](https://google.aip.dev/234)

처리를 시작한 요청이 버전 충돌 등으로 **확정 거절**되면 행 변경 전부를 취소하고 그 ID의 지문·거절 결과만 확정한다. 같은 ID를 기다리던 요청도 같은 결과를 받는다. 인증 실패·지원하지 않는 인코딩처럼 업무 처리 전 거절한 요청은 영수증을 만들지 않는다. 영수증의 서버 보존 기간 안에 여유를 둔 재시도 기한을 두고, 매번 재전송할 때 기한을 다시 시작하지 않는다. 이 기한 안에서만 중복 방지를 보장한다.

## 본문 크기 기준선

1,000개 행(`i=0…999`)에 순서대로 `id="ord-"+i`, `version="v1"`, 숫자 열 `c1…c998`을 둔다. `cj=i×1000+j`다. `ord-17`의 `c2=8`·`c9=0`, `ord-843`의 `c31=5`를 대입한 뒤 측정했다. 전체와 두 행은 행 배열이며, 배치는 위 예시의 UUID와 `requestId, updates[{id,baseVersion,set}]` 순서다. 한 셀 비교는 `ord-17.c2`만 포함한다. Node 24.22.1에서 공백 없는 JSON UTF-8 바이트와 zlib gzip level 6 바이트를 측정했다. HTTP 헤더·TLS·인증·실제 서버 지연은 포함하지 않았다.

| 본문                              |         JSON |        gzip |
| --------------------------------- | -----------: | ----------: |
| 전체 1,000행 × 1,000열            | 13,784,992 B | 2,568,728 B |
| 수정한 두 행의 모든 열            |     26,781 B |     7,588 B |
| 두 행의 세 필드 + ID·버전·요청 ID |        173 B |       139 B |
| 한 행의 한 필드 + ID·버전·요청 ID |        114 B |       123 B |

한 셀 예시는 gzip이 9 B 더 크다. 운영 임계값은 실제 텍스트·숫자·긴 값의 분포와 브라우저 CPU로 정한다. 초기 조회와 사용자가 누른 저장은 각각 소요 시간과 바이트를 기록한다. 저장 비용에는 변경한 필드의 개수뿐 아니라 그 값을 직렬화하는 바이트 수도 포함한다.
