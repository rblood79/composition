# ADR-324 상세 설계 · Collection에서 편집한 필드의 수동 서버 저장

[ADR 본문](../completed/324-collection-manual-batch-save.md) · 바탕: [ADR-325](../completed/325-collection-runtime-store-three-layers.md) ([상세](325-collection-runtime-store-three-layers-breakdown.md)) · [처음 조사 문서](../../explanation/research/COLLECTION_REMOTE_SAVE_2026-11.md)

2026-11-26 개정. 편집 상태 · 조회와의 공존은 ADR-325 가 소유한다 — 이 문서는 그 위의 저장 설정 · 요청 · 결과 판정 · 작성 표면이다. 아래 형 · 표 · Phase 는 구현할 계약이고, 크기 기준선만 로컬에서 측정했다. 2026-11-27 에 리뷰 round 1 (HIGH 6 — [기록](../reviews/324.md)) 을 반영했다: 2xx 의 뜻과 넣은 행의 서버 key, 응답 유실 판정의 고침 · 지우기 분리, 기준 버전, 즉시 저장 규칙과의 동시 구성 거절, 서버 식별자 없는 행, 행 전체 전송.

## 작성자가 설정하고 앱 사용자가 저장하는 흐름

1. 작성자는 Data 패널의 Collection 설정 「저장」 구획에서 「모아서 저장」 을 켠다. 쓰기 연결을 고른다 — 묶음 endpoint 하나, 또는 고침 · 넣기 · 지우기 endpoint 를 각각. 충돌 감지 (버전 필드 · 저장 전 확인 조회 · 없음) 를 고른다. 구획은 지금 연결의 보장 수준을 한 줄로 보인다.
2. 켜면 그 Collection 에 연결된 편집 가능한 Table 에 저장 막대 (미저장 N 건 · 저장 · 취소) 가 연결된 채 들어간다 (사용자 결정 5). 다른 자리에 두려면 Button 에 Do 「변경 저장」 · 「변경 취소」 를 잇는다.
3. 앱 사용자가 칸을 고치면 같은 Collection 을 보는 컴포넌트에 바로 반영되고 미저장 건수가 는다 (ADR-325). 페이지를 넘기거나 정렬해도 남는다. 저장을 누르면 변경분이 나가고, 진행 중에는 저장이 비활성이지만 편집은 계속할 수 있다.
4. 결과 — 성공한 변경은 표시가 사라지고, 실패한 행은 사유와 함께 남는다. 충돌은 내 값과 서버 값을 같이 보이고 사용자가 고른다 (사용자 결정 4). 결과 알림은 기존 Toast 로 낸다.
5. 미저장 변경이 있는 채 탭을 닫거나 새로 고치면 브라우저 경고가 뜬다.

## 문서 계약

Collection 에 선택 설정 하나, Interaction 에 Do 둘. 설정이 없으면 지금 동작이다. 계약 번호는 구현 시점의 정본에서 올린다 (작성 시점 79).

```ts
interface CollectionEntry {
  // …
  /** ADR-324 — 모아서 저장. 없으면 규칙이 편집마다 보낸다 (지금 동작). */
  save?: {
    /** 묶음: 변경 목록을 받는 endpoint 하나. 행별: 변경마다 한 요청. */
    send:
      | {
          shape: "batch";
          endpointId: DataEndpointId;
          atomic: boolean;
          /** 서버가 gzip 요청 본문을 받는다 — 본문이 임계값 이상이고 줄 때만 압축한다. */
          gzip?: boolean;
        }
      | {
          shape: "rows";
          /** 없는 종류의 변경은 보낼 길이 없다 — 남고 사유를 센다. */
          update?: { endpointId: DataEndpointId; body: "changed" | "full" };
          create?: { endpointId: DataEndpointId };
          remove?: { endpointId: DataEndpointId };
        };
    /** 충돌 감지. 없으면 바뀐 필드만 덮어쓴다. */
    conflict?:
      | { by: "version"; fieldId: string; send: "body" | "ifMatch" }
      | { by: "recheck"; endpointId: DataEndpointId };
    /** 넣기의 중복 방지 키 — 있을 때만 응답을 잃은 넣기를 다시 보낸다. */
    idempotency?: { in: "header" | "body"; name: string };
  };
}

/** 미저장 변경을 그 Collection 의 저장 설정대로 보낸다. 설정이 없으면 작성 검증이 거절한다. */
interface SaveChangesAction {
  kind: "saveChanges";
  collectionId: string;
}
/** 미저장 변경을 버린다 (ADR-325 `discardChanges`). `keys` 가 없으면 전부. */
interface DiscardChangesAction {
  kind: "discardChanges";
  collectionId: string;
  keys?: unknown;
}
```

- 행별 요청의 주소는 endpoint 의 경로 템플릿이 행의 key 를 읽는다 (`/orders/{{ key }}`) — 서버 식별자가 있는 행만이다 (아래 「서버 식별자가 없는 행」). 묶음 본문 · 행별 본문은 저장 동작이 만든다 — `bodyTemplate` 은 쓰지 않는다.
- 저장 · 취소 Do 는 RAC · S2 에 없는 이름이라 composition 확장으로 등록표에 출처를 적는다 (지금의 `Cells change` 와 같다). 미저장 건수 · 저장 상태 (대기 · 보내는 중 · 결과 확인 필요) 는 변수처럼 읽는 값이다 — 저장 막대의 글자와 비활성이 그 값을 읽는다.
- 검증 — 아래는 오류다 (명령 · 로드 · Publish 가 거절한다): 가리킨 endpoint · 필드가 없다 · 고침 · 지우기를 보내는 연결 (행별 `update` · `remove`, 묶음) 을 둔 Collection 에 key 필드가 없다 (`keyField` 선언도 schema 의 `id` · `key` · `value` 도 없다) · 묶음에 `ifMatch` 버전 (`If-Match` 하나는 행마다의 조건을 나타내지 못한다) · 연결의 method 가 그 작업의 것이 아니다 (고침 PATCH · PUT, 넣기 POST, 지우기 DELETE, 묶음 POST — 아래 「요청 모양」. 패널 선택지 · 문서 검증 · 전송이 표 하나 `CATALOG_SAVE_METHODS` 를 읽는다, round 3 h9) · 즉시 저장 규칙이 같이 있다 (다음 항목). 경고: 넣기 규칙이 있는데 넣기 연결이 없다.
- **즉시 저장 규칙과 같이 켤 수 없다.** 두 위치를 알리는 것만으로는 첫 편집에서 그 규칙이 실행돼 HC1 (편집 중 원격 쓰기 0 회) 이 깨진다. 「모아서 저장」 Collection 에서 아래 두 형태의 규칙은 검증 오류다 — 지금 runtime 이 「저장 규칙이 보낸 편집」 을 정하는 기준 ([이벤트가 실은 편집 · 규칙의 Do 가 만든 편집](../../../packages/shared/src/interactions/bindings.ts#L119)) 과 같은 둘이다.
  1. 그 Collection 에 연결된 컴포넌트의 편집 이벤트 (`Cells change` · 칸 Form 의 submit) 에 걸려 있고, Do 목록 (이어진 Do 포함) 에 쓰기 `callEndpoint` (GET · HEAD 가 아닌 endpoint) 가 있는 규칙.
  2. Do 목록에 그 Collection 을 편집하는 Do 와 쓰기 `callEndpoint` 가 같이 있는 규칙 — Form 의 submit 이 서버에 넣고 목록에도 더하는 흐름이다. 더한 행이 미저장 변경이 되어 저장 때 한 번 더 나간다.

  「모아서 저장」 을 켜는 명령과 그런 규칙을 더하는 명령이 같은 사유로 거절된다. 패널은 스위치 옆에 그 규칙들의 위치를 보이고 「규칙을 지우고 켜기」 를 준다 (한 명령 — undo 하나로 되돌아간다).

- **서버 식별자가 없는 행.** key 필드가 있어도 그 값이 빈 행은 ADR-325 의 `isServerKey` 가 false 다 (키가 위치로 만든 것 — `row-1`). 그 행의 고침 · 지우기는 보내지 않는다 — 요청 0, 변경은 남고 저장 결과가 사유 「key 없음」 과 건수를 보인다. `/orders/row-1` 같은 주소로 나가 404 가 되거나 이름이 같은 다른 서버 행에 쓰는 일을 막는다. 넣기는 key 없이 나간다. ADR-325 사용자 결정 1 (키 없는 원격 Collection 의 로컬 편집) 은 그대로다.
- 왕복: 명령 (`setDataEntries`) · undo/redo · 저장/로드 · 프로젝트 파일 · Code 보기 · Preview delta · Publish. Collection · endpoint · 필드의 이름 변경 · 삭제 · 복제에서 참조를 지킨다.

## 연결 능력과 보장

| 연결이 가진 것        | 저장 동작                                                                                    | 보장 (화면 문구의 기준)                                                                                         |
| --------------------- | -------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| 묶음 · 원자적         | 변경 목록 한 요청                                                                            | 전부 반영되거나 전부 남는다                                                                                     |
| 묶음 · 원자적 아님    | 변경 목록 한 요청, 응답의 항목별 결과를 읽음                                                 | 항목마다 반영 여부가 다를 수 있다                                                                               |
| 행별                  | 변경마다 한 요청 (순서: 지우기 → 고침 → 넣기, 동시 요청 상한)                                | 행마다 반영 여부가 다를 수 있다                                                                                 |
| 버전 필드             | 고침 · 지우기에 처음 고칠 때의 버전을 실음 (ADR-325 `baseRow`)                               | 다른 사람이 먼저 바꾼 행은 서버가 거절한다 — 편집 뒤 재조회가 와도 같다. 같은 요청이 다시 가도 두 번 반영 안 됨 |
| 저장 전 확인 조회     | 보내기 직전 key 로 읽어 수정 전 값과 대조. 「행 전체」 는 읽은 행 위에 바뀐 필드만 덮어 보냄 | 읽은 뒤 보내는 사이의 변경은 잡지 못한다                                                                        |
| 충돌 감지 없음        | 바뀐 필드만 보냄. 「행 전체」 는 보이는 행 전체                                              | 마지막에 쓴 값이 남는다 — 다른 사람의 같은 칸 편집을 덮을 수 있고, 「행 전체」 는 다른 칸까지 덮는다            |
| 중복 방지 키          | 넣기에 요청마다 같은 키를 실음                                                               | 응답을 잃은 넣기를 다시 보낼 수 있다                                                                            |
| 요청 압축 받음 (묶음) | 본문이 임계값 이상이고 압축 결과가 더 작으면 `Content-Encoding: gzip`                        | 보장은 같다 — 큰 붙여넣기의 전송량만 준다                                                                       |

처음 초안의 계약 (원자적 묶음 + 버전 + 요청 ID) 은 이 표의 가장 높은 조합이다. 고객이 endpoint 를 새로 만들 때 권하는 모양으로 남긴다.

## 요청 모양

**묶음 (참조 모양)** — `POST` · `Content-Type: application/json`. 고객이 새로 만드는 endpoint 용이다.

```json
{
  "updates": [
    { "id": "ord-42", "version": "v17", "set": { "quantity": 8 } },
    { "id": "ord-91", "version": "v4", "set": { "note": null } }
  ],
  "creates": [{ "ref": "new-1", "values": { "name": "Kim", "quantity": 1 } }],
  "deletes": [{ "id": "ord-7", "version": "v2" }]
}
```

성공 응답은 반영한 항목과 새 버전, 넣은 행의 서버 key 를 돌려준다. 순서는 자유다. 원자적이 아닌 묶음은 받지 않은 항목을 `failed` 에 싣는다 — `{ "id": "ord-91", "errors": { "note": ["too long"] } }` (넣기는 `ref`), `errors` 는 `errorsPath` 와 같은 모양 (필드 이름 → 문구) 이다.

```json
{
  "updated": [
    { "id": "ord-42", "version": "v18" },
    { "id": "ord-91", "version": "v5" }
  ],
  "created": [{ "ref": "new-1", "id": "ord-120", "version": "v1" }],
  "deleted": [{ "id": "ord-7" }]
}
```

- `set` 은 필드 대입이다. `null` · `false` · `0` · 빈 문자열과 생략을 구별한다. 배열 · 객체 칸은 값 전체를 바꾼다. 필드 이름은 schema 의 key, 값은 필드의 값 표현 선언으로 되돌린 것이다 (`outgoingRecord` 를 바뀐 필드에만 — 보내지 않은 필드를 더하지 않는다). 큰 정수는 따옴표 없는 literal (`stringifyJsonLossless`). [나가는 값 변환](../../../packages/shared/src/collections/intake/outgoing.ts#L29) · [직렬화](../../../packages/shared/src/collections/intake/parseJsonLossless.ts#L127)
- `version` 은 충돌 감지가 버전 필드일 때만 싣는다 — 처음 고칠 때의 행에서 읽은 값이다 (아래 「기준 버전」). 버전 값은 뜻을 읽지 않는 글자로 다룬다.
- 서버가 값을 고쳐 받았으면 (공백 다듬기 등) 그 행에 `values` 를 더해 돌려준다. 클라이언트는 그것을 확인된 값으로 쓴다.
- 중복 방지 키를 선언한 연결은 선언한 자리 (헤더 · 본문 필드) 에 요청마다 만든 키를 싣는다. 같은 변경을 다시 보낼 때 같은 키다.
- 요청 압축을 선언한 연결은 직렬화한 본문이 임계값 이상이고 gzip 결과가 더 작을 때만 `Content-Encoding: gzip` 으로 보낸다 (브라우저 `CompressionStream`). 임계값 후보는 2 KiB — 그 아래는 줄어도 수백 B 다 (아래 재확인 표), G0 에서 확정한다. 본문에는 편집 값 · key · 버전만 있고 인증 값은 헤더에 있다. 교차 출처 요청이면 서버의 CORS 허용 헤더에 `Content-Encoding` 이 있어야 한다. 행별 요청은 압축하지 않는다.

**행별** — 기존 REST endpoint 용이다.

| 변경   | 요청                                                                                                                                                                      |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 고침   | 고침 연결의 method (PATCH · PUT) 와 경로 (`{{ key }}`). 본문 = 바뀐 필드, 선언이 「행 전체」 면 아래 「행 전체를 보내는 연결」 의 본문. 버전은 본문 필드 또는 `If-Match`. |
| 넣기   | 넣기 연결 (POST). 본문 = 넣은 행. 서버 key 는 응답의 행 (`responseMapping.dataPath`) → `Location` 헤더 순으로 읽는다 (아래 「넣은 행의 서버 key」).                       |
| 지우기 | 지우기 연결 (DELETE) 과 경로의 key. 버전은 `If-Match` 또는 쿼리.                                                                                                          |

## 결과 판정

저장 요청은 저장 전용 실행기로 보낸다 — 응답의 status · 헤더 · 본문을 그대로 돌려준다. 지금의 제출 실행기는 본문만 돌려주어 빈 202 · 빈 204 · `Location` 만 있는 201 이 모두 `undefined` 다 ([제출 실행기](../../../packages/shared/src/collections/executeCollectionEndpoint.ts#L243) — Form 의 submit 은 그대로 쓴다). 보낼 때 ADR-325 `beginSend` 로 스냅샷을 찍고, 아래 판정을 행마다 `settleSend` 에 넘긴다 — `confirmed` (반영됨) · `rejected` (반영 안 됨, 변경은 남는다) · `unknown` (모른다, 티켓에 남는다).

**2xx 의 뜻** — 2xx 를 모두 「저장됨」 으로 읽지 않는다.

| status                          | 뜻                                                                                                                    |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| 200 · 201 · 204 · 205           | 처리가 끝났다 — 아래 「처리가 끝난 응답」 으로 행마다 판정한다.                                                       |
| 202                             | 접수했을 뿐 끝나지 않았다 (RFC 9110 §15.3.3) — 그 요청의 행은 모두 `unknown` 이고 「처리 중」 으로 보인다. 아래 참고. |
| 그 밖의 2xx (203 · 206 · 207 …) | 뜻을 정할 수 없다 — `unknown` (「결과 확인 필요」).                                                                   |

**처리가 끝난 응답** — status 보다 먼저 응답 본문의 필드 오류 (`responseMapping.errorsPath`) 를 읽는다. 2xx 여도 그 자리에 오류가 있으면 서버가 그 값을 받지 않은 것이다 — 지금의 제출 실행기도 HTTP 200 과 `{errors: {quantity: [...]}}` 를 거절로 읽는다 ([필드 오류 판정](../../../packages/shared/src/collections/executeCollectionEndpoint.ts#L254)). 행별 요청은 그 행이 `rejected` 이고 칸에 오류가 보인다. 묶음 요청의 최상위 `errorsPath` 오류는 어느 행의 것인지 알 수 없으므로 그 요청의 행을 모두 `rejected` 로 두고 저장 결과에 오류를 보인다 — 행마다의 오류는 응답의 `failed` 항목이 싣는다 (위 참조 모양).

| 요청 · 응답                                | 판정                                                                                                                                                                               |
| ------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 묶음 · 항목 결과가 요청과 맞음             | 항목마다 `confirmed` (응답의 값 · 버전으로). 넣은 행은 응답의 서버 key 로 바꾼다.                                                                                                  |
| 묶음 · 본문 없음 또는 항목이 빠짐          | 원자적 선언: 고침 · 지우기는 보낸 값으로 `confirmed` (버전 연결이면 그 행들을 다시 읽어 버전을 얻는다), 넣기는 아래 「넣은 행의 서버 key」. 원자적이 아니면 빠진 항목은 `unknown`. |
| 묶음 · 성공과 실패가 섞임                  | 원자적 선언이면 선언과 어긋남 — 전부 `unknown` 으로 두고 다시 읽는다. 아니면 항목별로 `confirmed` · `rejected`.                                                                    |
| 행별 고침 · 지우기                         | 그 행 `confirmed`. 응답에 행이 있으면 그 값으로, 없으면 보낸 값으로. 버전 연결은 응답의 버전 (본문 필드 · `ETag`) 을 읽고, 없으면 그 행을 다시 읽는다.                             |
| 행별 넣기                                  | 아래 「넣은 행의 서버 key」.                                                                                                                                                       |
| 409 · 412 (버전 불일치)                    | `rejected` + 충돌. 그 행을 다시 읽어 서버 값을 변경에 적는다.                                                                                                                      |
| 필드 오류 (`errorsPath`) — 2xx · 422 · 400 | `rejected` — 그 행 · 칸에 오류를 표시한다.                                                                                                                                         |
| 415 (압축해 보낸 묶음 요청)                | 처리 전 거절 — 같은 본문을 압축 없이 한 번 다시 보내고 그 세션에서 압축을 끈다. 그 밖의 거절은 아래 줄대로.                                                                        |
| 401 · 403                                  | `rejected` — 남은 요청을 보내지 않고 사유를 알린다.                                                                                                                                |
| 404 (고침 · 지우기 대상 없음)              | `rejected` — 서버에서 지워진 행, 충돌로 보인다.                                                                                                                                    |
| 429 · 5xx · 시간 초과 · 연결 끊김          | `unknown` — 아래 「응답을 잃었을 때」.                                                                                                                                             |

**넣은 행의 서버 key** — 넣기를 임시 key 로 확정하면 다음 고침 · 지우기가 없는 주소로 나간다. 위에서부터 처음 맞는 것을 쓴다.

1. 응답 본문의 행 (`responseMapping.dataPath`) 에 key 필드가 있다 — 그 key 다. 보낸 행에 key 값이 있었어도 응답의 것이 이긴다: 서버가 key 를 새로 매길 수 있다 (저장소의 CRUD 대역에 `id=draft-42` 를 보내면 `u4` 가 만들어지고, 단건 조회는 `draft-42` 가 404 · `u4` 가 200 이다).
2. `Location` 헤더가 있다 — 그 주소의 마지막 경로 조각이 key 다. 교차 출처 요청은 서버가 `Access-Control-Expose-Headers` 에 `Location` 을 넣어야 읽힌다 — 읽지 못하면 없는 것이다.
3. 어느 것도 없다 — 서버는 행을 만들었지만 key 를 모른다. 보낸 행에 key 값이 있어도 같다: 서버가 그 key 를 그대로 썼는지 알 수 없고, 단건 조회로 그 key 의 행이 읽혀도 전부터 있던 다른 행일 수 있다 — 조회 결과는 key 의 근거가 아니라 아래의 선택 후보일 뿐이다. 넣기를 `confirmed` 로 닫고 (ADR-325 `serverKey: null` — 다시 보내지 않는다) 그 Collection 의 조회를 다시 실행한다. 아래 「key 를 모르는 넣기의 뒤 편집」.

**key 를 모르는 넣기의 뒤 편집** — 보낸 뒤 그 행을 다시 고치지 않았으면 임시 행은 빠지고 서버가 준 행으로 보인다 (새 행이 지금 조회의 범위 밖이면 보이지 않는다). 다시 고쳤거나 (이름 A 로 보낸 뒤 B 로) 지우기를 예약했으면 그 편집은 버리지 않는다 — ADR-325 의 `unlinked` 로 남고, 행은 「저장됨 · 서버 행과 연결 필요」 로 보이며 미저장 건수에 든다. 보낼 수는 없다 (서버 식별자가 없다).

- 연결은 사용자가 고른다 — 자동으로 잇지 않는다 (사용자 결정 2026-11-27). 후보가 하나뿐이어도 그 행이 내 행이라는 근거가 없다: 내 행은 다음 페이지에 있고, 다른 사람이 같은 값으로 만든 행만 지금 페이지에 있을 수 있다.
- 조회 결과는 선택 후보로만 쓴다. 후보 = 다시 조회한 결과에서 보낸 필드의 값이 모두 서버가 받은 값 (`sent`) 과 같은 행, 그리고 보낸 key 가 있었으면 그 key 의 행. 사용자가 후보 하나를 고르면 (「이 행에 적용」) `linkUnlinked` 로 잇고, 뒤 편집이 그 key 의 고침 · 지우기가 되어 다음 저장에 나간다.
- 고르기 전에는 후보가 0 개 · 1 개 · 여러 개 어느 경우든 그 편집의 고침 · 지우기 요청을 보내지 않는다 (0 회). 편집은 `unlinked` 로 남는다 — 다시 조회 · 페이지 이동 · 정렬에도. 사용자가 그 편집을 버릴 수도 있다.

**접수만 된 저장 (202)** — 그 행들은 「처리 중」 으로 티켓에 남는다. 편집은 되고, 그 행은 다음 저장에서 빠진다 (다른 행은 나간다). 판정은 사용자의 「결과 확인」 (아래 다시 읽기) 으로 한다 — 내 값이면 (지우기는 대상 없음이 보증되면) `confirmed`. 수정 전 값이면 그대로 둔다: 아직 처리 전일 수 있어 「미반영」 으로 읽지 않는다. 사용자가 「다시 저장」 을 고르면 `rejected` 로 닫고 다음 저장에 넣는다 — 두 번 반영될 수 있음을 문구로 밝힌다 (버전 연결은 서버가 막는다). 넣기는 대조할 수 없어 사용자가 확인한 뒤 닫는다.

**응답을 잃었을 때** — 자동으로 다시 보내지 않는다. 고침 · 지우기는 다시 읽어 판정한다. 읽는 길은 둘이고 보증이 다르다.

- 단건 확인 조회 — 충돌 감지에 고른 확인 조회 연결 (key 로 한 행을 읽는다). 대상이 없으면 404 또는 빈 응답이라 「없다」 를 보증한다.
- 목록 재조회 — 확인 조회 연결이 없을 때 그 Collection 의 조회를 다시 실행한다. 응답에 그 행이 있을 때만 값을 대조할 수 있다. 응답에 없다는 것은 그 행이 페이지 · 조건의 범위 밖이라는 뜻일 수 있다 (2 쪽의 행을 고치고 1 쪽에서 저장한 경우) — ADR-325 의 `complete` 인 목록 (조건 없는 조회를 끝까지 모음) 에 없을 때만 「없다」 로 읽는다.

| 다시 읽은 결과                                                                   | 고침                                       | 지우기                                               |
| -------------------------------------------------------------------------------- | ------------------------------------------ | ---------------------------------------------------- |
| 행이 있고 바뀐 필드가 모두 내 값                                                 | `confirmed`                                | —                                                    |
| 행이 있고 수정 전과 같다 (바뀐 필드가 모두 수정 전 값 · 버전 연결은 버전도 같음) | 미반영 — `rejected`, 「다시 저장」 을 제안 | 미반영 — `rejected`, 지우기는 남는다                 |
| 행이 있고 그 밖 (일부만 · 다른 값 · 다른 버전)                                   | `rejected` + 충돌                          | `rejected` + 충돌 (지우려던 행을 다른 사람이 고쳤다) |
| 「없다」 가 보증됨 (단건 조회의 404 · 빈 응답, `complete` 인 목록에 없음)        | `rejected` + 충돌 (서버에서 지워짐)        | `confirmed` — 목적 상태에 이르렀다                   |
| 행을 찾지 못했지만 보증이 없다 (목록의 범위 밖일 수 있음) · 읽을 길이 없다       | `unknown` — 「결과 확인 필요」             | `unknown` — 「결과 확인 필요」                       |

넣기는 넣은 행에 key 값이 있으면 그 key 로 다시 읽는다 — 그 key 의 행이 보낸 값을 그대로 들고 있을 때만 `confirmed` 다. 찾지 못했거나 값이 다르면 `unknown` 으로 남긴다: 서버가 key 를 새로 매겼을 수 있어 (위 「넣은 행의 서버 key」 — `draft-42` → `u4`) 「없다」 는 미반영의 근거가 아니고, 미반영으로 닫으면 다음 저장이 같은 행을 한 번 더 만든다 (round 3 h11 — 처음 설계의 「없다가 보증되면 미반영」 을 고쳤다). 서버가 key 를 만드는 넣기는 대조할 행을 찾을 수 없다 — `unknown` 으로 남기고, 중복 방지 키가 있는 연결만 같은 키로 다시 보낸다.

단건 확인 조회의 응답이 어느 행인지 알려 주지 못하면 (여러 행인데 그 key 의 행이 없다 · 한 행인데 key 가 다르다) 「없다」 가 아니라 근거 없음이다 — 여러 행 중 그 key 의 행이 하나 있으면 그 행이다 (round 3 h12).

`unknown` 인 행은 판정될 때까지 다음 저장에서 빠진다 — 그 행의 뒤 편집은 판정 뒤에 나간다 (ADR-325 판정 표). 다른 행의 저장은 막지 않는다. 「결과 확인 필요」 에서 사용자는 「결과 확인」 (다시 읽기 — 「저장」 이 먼저 한다) · 「다시 저장」 (`saveChanges` 의 `scope: "pending"` — 기다리던 전송을 미반영으로 닫고 다시 보낸다) · 「취소」 (`discardChanges` 의 `scope: "pending"` — 기다림을 끝내고 그 변경을 버린다) 를 고른다. 저장 결과 문구는 기다리는 행 수를 그대로 센다 (「결과 확인 필요 N건」 — round 3 h13).

버전 조건이 붙은 고침은 같은 요청이 다시 도착해도 두 번 반영되지 않는다 (첫 반영이 버전을 올려 조건이 거짓이 된다 — RFC 9110 §13.1.1). 대신 응답을 잃은 뒤의 재시도는 「충돌」 로 돌아온다. 그래서 다시 읽어 「내 값이면 완료」 로 판정한다. 수정 전 값 대조만으로는 값이 A → B → A 로 돌아온 경우를 가리지 못하므로 다시 읽기 전에는 보내지 않는다. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) · [Azure API 지침 — 버전 ETag 와 재시도](https://raw.githubusercontent.com/microsoft/api-guidelines/vNext/azure/Guidelines.md)

## 충돌 처리

**기준 버전** — 버전 연결에서 고침 · 지우기가 싣는 버전은 ADR-325 변경의 `baseRow` (처음 고칠 때의 행) 에서 읽는다. 행 저장소의 지금 행에서 읽지 않는다 — v17 에서 지우기를 예약한 뒤 주기 조회가 다른 사람의 수정본 v18 로 행을 바꿨을 때, 지금 행의 버전으로 보내면 서버가 받아들여 그 수정본을 지운다. `beginSend` 가 `baseRow` 를 티켓에 복사하므로 보내는 요청의 버전도 처음 고칠 때의 것이다.

- 보내기 직전에 행 저장소의 지금 버전이 `baseRow` 의 버전과 다르면 보내지 않고 충돌로 보인다 — 서버가 거절할 요청이다.
- `baseRow` 에 버전 값이 없으면 (조회 응답이 버전 필드를 주지 않았다) 고침 · 지우기를 보내지 않는다 — 조건 없는 요청이 되어 다른 사람의 변경을 덮는다 (round 3 h10). 행은 「기준 버전 없음」 으로 남고, 버전이 든 행을 다시 읽으면 충돌로 바뀌어 「내 값으로 다시 저장」 이 그 버전으로 보낸다.
- 묶음은 항목마다 본문의 `version`, 행별은 본문 필드 또는 그 요청의 `If-Match` 다. `If-Match` 하나는 묶음 안 행마다의 조건을 나타낼 수 없다 — 묶음 + `ifMatch` 는 검증이 거절한다.
- `If-Match` 의 값은 버전 값이 따옴표로 싸여 있지 않으면 `"…"` 로 싼다 (entity-tag 문법 — RFC 9110 §8.8.3).
- 기준이 바뀌는 길은 둘뿐이다 — 저장 확정 (`settleSend`), 그리고 아래 「내 값으로 다시 저장」 (`rebaseChange`).

**행 전체를 보내는 연결** (`body: "full"`) — 화면의 행 전체를 그대로 보내면, 사용자가 수량만 고친 사이 다른 사람이 바꾼 메모까지 옛 값으로 되돌린다. 바뀐 필드만 대조하는 확인 조회는 이것을 잡지 못한다.

| 충돌 감지         | 본문                                                                                    | 다른 칸                                                                 |
| ----------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------- |
| 버전 필드         | 보이는 행 전체 + 처음 고칠 때의 버전                                                    | 다른 사람이 어느 칸이든 바꿨으면 서버가 거절한다                        |
| 저장 전 확인 조회 | 확인 조회가 방금 돌려준 행 (값 표현을 바꾸기 전의 값) 위에 바뀐 필드의 나가는 값만 덮음 | 방금 읽은 서버 값이 그대로 돌아간다 — schema 에 없는 필드도             |
| 없음              | 보이는 행 전체                                                                          | 덮을 수 있다 — 설정 구획과 저장 막대가 「다른 칸까지 덮는다」 고 밝힌다 |

충돌한 행은 ADR-325 의 변경이 수정 전 값 · 내 값 · 서버 값을 든다. 화면은 그 행에 표시를 하고 칸에 내 값과 서버 값을 같이 보인다. 사용자는 행 단위로 고른다 (사용자 결정 4).

- 「내 값으로 다시 저장」 — ADR-325 `rebaseChange` 로 다시 읽은 서버 행을 새 기준으로 삼고 (버전도 그 행의 것) 내 값을 다음 저장에 넣는다.
- 「서버 값 받기」 — 그 행의 변경을 버린다.

다른 사람의 변경을 모르는 채 버전만 올려 다시 보내는 일은 하지 않는다. 서버에서 지워진 행은 「지워짐」 으로 보이고 변경을 버리거나 새 행으로 넣기를 고른다.

## 저장 막대와 상태

- 저장 막대 = frame 안의 Text (미저장 N 건) · Button (저장) · Button (취소) — 그리고 행 선택용 「내 값으로 다시 저장」 · 「서버 값 받기」 · 「이 행에 적용」 · 「다시 저장」 · 「대기 취소」 (기다리는 행이 있을 때만 활성 — `hasPending`). 기존 원본을 놓고 Do 와 값 읽기를 연결한 것이다 — 새 컴포넌트가 아니다. 미저장 0 이면 숨는다 (기존 `showWhen`).
- 저장 요청이 나가 있는 동안 저장 Button 은 비활성이다. 「처리 중」 · 「결과 확인 필요」 인 행이 있어도 다른 행의 변경은 저장할 수 있고, 그 행들은 다음 저장에서 빠진다. 취소는 「보내지 않은 변경만」 버린다.
- 결과 알림은 Toast 다 (성공 · 실패 수 · 충돌 수). 실패 · 충돌 행은 Table 의 편집 표시 (ADR-317 `showEditMarks`) 에 상태를 더해 보인다 — 색만으로 알리지 않는다.
- 닫기 경고는 실행 runtime 이 `beforeunload` 에 거는 것 하나다 (미저장 변경이 있는 Collection 이 하나라도 있을 때). Builder 의 Preview iframe 에는 걸지 않는다.

## 조건부 요청 압축 (사용자 결정 1 — 재확인)

사용자 결정 1 은 「재확인 뒤 판단」 이었다. 2026-11-26 에 다시 재고 문서를 다시 읽었다.

**크기** — 개정한 참조 모양 (`{updates:[{id, version, set}]}`) 으로 Node 24.22.1 · zlib gzip level 6. 붙여넣기 행은 행마다 다섯 칸 (숫자 다섯, 또는 한글 이름 · 부서 · 메모 · `Y`/`N` · 짧은 글자) 인 합성 값이다 — 규모만 본다.

| 본문                           |                  JSON |                gzip |      절감 |
| ------------------------------ | --------------------: | ------------------: | --------: |
| 한 행 한 칸                    |                  59 B |                79 B |     −34 % |
| 두 행 세 칸                    |                 114 B |                97 B |      15 % |
| 10 행 × 5 칸 (숫자 · 한글)     |         962 · 1,576 B |         287 · 423 B | 70 · 73 % |
| 20 행 × 5 칸 (숫자 · 한글)     |       1,929 · 3,147 B |         470 · 624 B | 76 · 80 % |
| 100 행 × 5 칸 (숫자)           |               9,761 B |             1,856 B |      81 % |
| 1,000 행 × 5 칸 (숫자 · 한글)  |    98,687 · 157,027 B |   16,970 · 13,798 B | 83 · 91 % |
| 10,000 행 × 5 칸 (숫자 · 한글) | 993,676 · 1,570,188 B | 165,993 · 129,634 B | 83 · 92 % |

압축 시간은 Node 에서 1,000 행 0.5 ms · 10,000 행 4.8 ms 였다 (브라우저 `CompressionStream` 은 G0 에서 잰다). 작은 편집은 줄지 않거나 커지고, 큰 붙여넣기는 크게 준다 — 조건부로만 뜻이 있다. 처음 초안의 「4 KiB 후보」 와 개정 직후의 「이득 없음」 은 둘 다 한쪽만 본 것이다.

**서버** — 공식 문서를 다시 읽은 결과 (요약 도구의 요약을 원문 구절과 대조했다).

**판단** — 요청 압축은 범위에 남기되 필수 계약이 아니라 연결이 선언하는 선택 능력이다. 기본은 꺼짐이고, 고객 서버가 해제 필터 · handler 를 넣고 CORS 로 헤더를 허용한 묶음 연결에서만 켠다. 처음 초안의 서버 쪽 검사 (압축 해제 상한 등) 는 고객 서버의 일이라 통과 조건에 넣지 않는다.

## 본문 크기 기준선

1,000 개 행 (`i=0…999`) 에 순서대로 `id="ord-"+i`, `version="v1"`, 숫자 열 `c1…c998` 을 둔다 (`cj=i×1000+j`). `ord-17` 의 `c2=8` · `c9=0`, `ord-843` 의 `c31=5` 를 대입한 뒤 측정했다. 변경분 본문은 요청 ID 와 `updates[{id, baseVersion, set}]` 순서였다 (처음 초안의 모양 — 개정한 참조 모양의 값은 위 「조건부 요청 압축」 표에 있다). Node 24.22.1 에서 공백 없는 JSON UTF-8 바이트와 zlib gzip level 6 바이트. HTTP 헤더 · TLS · 서버 지연은 포함하지 않았다.

| --------------------------- | -----------: | ----------: |
| 전체 1,000 행 × 1,000 열    | 13,784,992 B | 2,568,728 B |
| 고친 두 행의 모든 열        |     26,781 B |     7,588 B |
| 두 행의 세 필드 + 식별 정보 |        173 B |       139 B |
| 한 행의 한 필드 + 식별 정보 |        114 B |       123 B |

판독 기록 [reviews/324.md](../reviews/324.md) round 3. 건마다 반례 테스트를 먼저 실패로 재현하고 고쳤다 (대역 서버의 행 · 요청 기록이 oracle).

- **h9 고침 연결에 DELETE**: 작업별 method 표 `CATALOG_SAVE_METHODS` (`document/collectionSave.ts` — 고침 PATCH · PUT, 넣기 POST, 지우기 DELETE, 묶음 POST) 를 패널 선택지 · 문서 검증 (`SAVE_ENDPOINT_METHOD`) · 전송 (`saveMethod` — 맞지 않으면 요청 0 · 행 「보낼 연결 없음」) 이 같이 읽는다. 전에는 검증이 「GET 이 아님」 만 봤다.
- **h10 버전 값 없는 행**: `planSave` 가 기준 행에 버전 값이 없는 고침 · 지우기를 보내지 않는다 (`noVersion` — 행별 · 묶음 모두). 버전이 든 행을 다시 읽으면 기준 버전 대조가 충돌로 바꾸고 「내 값으로 다시 저장」 이 그 버전으로 보낸다.
- **h11 넣기 유실 뒤 중복**: `judgeRecheck` 의 넣기는 보낸 key 의 행이 보낸 값일 때만 확정, 그 밖은 `unknown`. 설계의 「없다가 보증되면 미반영」 문장을 고쳤다 (위 「응답을 잃었을 때」).
- **h12 확인 조회의 여러 행**: `readSavedRow` 가 key 필드로 그 행을 가린다 — 그 key 의 행이 하나면 그 행, 가리지 못하면 근거 없음 (보내지 않고 「확인 조회 실패」). 빈 응답 · 404 만 「없다」.
- **h13 끝낼 수 없는 대기**: Do 의 `scope: "pending"` (문서 타입 · 검증 · dispatcher · Code 보기) — `saveChanges` = 「다시 저장」 (기다리던 전송을 미반영으로 닫고 다시 보냄), `discardChanges` = 「대기 취소」 (닫고 그 변경을 버림). 저장 막대에 두 버튼 (`hasPending`), 저장 결과는 열린 전송의 행 수를 센다 (「결과 확인 필요 N건」 — 전에는 「저장할 변경이 없습니다」). contract 는 올리지 않았다 — library 의 실행 어휘는 그대로이고 80 문서는 그대로 열린다.
- **m14 끌 수 없는 스위치**: 끄기 명령이 만든 그대로인 저장 막대 (그 collection 의 저장 · 취소 규칙 주인과 건수 Text 만 든 frame) 와 다른 곳의 「변경 저장」 규칙을 같이 지운다 (`catalogSaveDependents` — 한 undo). 작성자가 고친 막대 (다른 노드가 든 frame) 는 규칙만 지우고 노드는 둔다.
- **m15 서버 key `row-1`**: ADR-325 `isServerKey` 가 key 의 출처로 판정한다 (저장소가 만든 자리 key 목록).
- **이 ADR 의 커밋이 남긴 정적 게이트 실패 3 (전체 스위트에서 확인 — HEAD 도 실패)**: `placeholderMessages` (`barUnsaved` 는 명령이 `{count}` 를 바꿔 쓰는 문구 — 허용 목록에), `sharedActionVocabulary` (영어 `Send` · `Create` · `Discard` 가 다른 한국어와 겹침 → `Send as` · `Add` · `Cancel`), `domainPredicateRatchet` (`planSave` 의 `=== "body"` 3 곳 → `versionAsHeader`).
