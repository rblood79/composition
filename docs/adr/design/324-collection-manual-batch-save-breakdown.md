# ADR-324 상세 설계 · Collection에서 편집한 필드의 수동 서버 저장

[ADR 본문](../324-collection-manual-batch-save.md) · 바탕: [ADR-325](../325-collection-runtime-store-three-layers.md) ([상세](325-collection-runtime-store-three-layers-breakdown.md)) · [처음 조사 문서](../../explanation/research/COLLECTION_REMOTE_SAVE_2026-11.md)

2026-11-26 개정. 편집 상태 · 조회와의 공존은 ADR-325 가 소유한다 — 이 문서는 그 위의 저장 설정 · 요청 · 결과 판정 · 작성 표면이다. 아래 형 · 표 · Phase 는 구현할 계약이고, 크기 기준선만 로컬에서 측정했다.

## 작성자가 설정하고 앱 사용자가 저장하는 흐름

1. 작성자는 Data 패널의 Collection 설정 「저장」 구획에서 「모아서 저장」 을 켠다. 쓰기 연결을 고른다 — 묶음 endpoint 하나, 또는 고침 · 넣기 · 지우기 endpoint 를 각각. 충돌 감지 (버전 필드 · 저장 전 확인 조회 · 없음) 를 고른다. 구획은 지금 연결의 보장 수준을 한 줄로 보인다.
2. 켜면 그 Collection 에 연결된 편집 가능한 Table 에 저장 막대 (미저장 N 건 · 저장 · 취소) 가 연결된 채 들어간다 (사용자 결정 5). 다른 자리에 두려면 Button 에 Do 「변경 저장」 · 「변경 취소」 를 잇는다.
3. 앱 사용자가 칸을 고치면 같은 Collection 을 보는 컴포넌트에 바로 반영되고 미저장 건수가 는다 (ADR-325). 페이지를 넘기거나 정렬해도 남는다. 저장을 누르면 변경분이 나가고, 진행 중에는 저장이 비활성이지만 편집은 계속할 수 있다.
4. 결과 — 성공한 변경은 표시가 사라지고, 실패한 행은 사유와 함께 남는다. 충돌은 내 값과 서버 값을 같이 보이고 사용자가 고른다 (사용자 결정 4). 결과 알림은 기존 Toast 로 낸다.
5. 미저장 변경이 있는 채 탭을 닫거나 새로 고치면 브라우저 경고가 뜬다.

## 문서 계약

Collection 에 선택 설정 하나, Interaction 에 Do 둘. 설정이 없으면 지금 동작이다. 계약 번호는 구현 시점의 정본에서 올린다 (작성 시점 79).

```ts
interface CollectionEntry {
  // …
  /** ADR-324 — 모아서 저장. 없으면 규칙이 편집마다 보낸다 (지금 동작). */
  save?: {
    /** 묶음: 변경 목록을 받는 endpoint 하나. 행별: 변경마다 한 요청. */
    send:
      | {
          shape: "batch";
          endpointId: DataEndpointId;
          atomic: boolean;
          /** 서버가 gzip 요청 본문을 받는다 — 본문이 임계값 이상이고 줄 때만 압축한다. */
          gzip?: boolean;
        }
      | {
          shape: "rows";
          /** 없는 종류의 변경은 보낼 길이 없다 — 남고 사유를 센다. */
          update?: { endpointId: DataEndpointId; body: "changed" | "full" };
          create?: { endpointId: DataEndpointId };
          remove?: { endpointId: DataEndpointId };
        };
    /** 충돌 감지. 없으면 바뀐 필드만 덮어쓴다. */
    conflict?:
      | { by: "version"; fieldId: string; send: "body" | "ifMatch" }
      | { by: "recheck"; endpointId: DataEndpointId };
    /** 넣기의 중복 방지 키 — 있을 때만 응답을 잃은 넣기를 다시 보낸다. */
    idempotency?: { in: "header" | "body"; name: string };
  };
}

/** 미저장 변경을 그 Collection 의 저장 설정대로 보낸다. 설정이 없으면 작성 검증이 거절한다. */
interface SaveChangesAction {
  kind: "saveChanges";
  collectionId: string;
}
/** 미저장 변경을 버린다 (ADR-325 `discardChanges`). `keys` 가 없으면 전부. */
interface DiscardChangesAction {
  kind: "discardChanges";
  collectionId: string;
  keys?: unknown;
}
```

- 행별 요청의 주소는 endpoint 의 경로 템플릿이 행의 key 를 읽는다 (`/orders/{{ key }}`). 묶음 본문 · 행별 본문은 저장 동작이 만든다 — `bodyTemplate` 은 쓰지 않는다.
- 저장 · 취소 Do 는 RAC · S2 에 없는 이름이라 composition 확장으로 등록표에 출처를 적는다 (지금의 `Cells change` 와 같다). 미저장 건수 · 저장 상태 (대기 · 보내는 중 · 결과 확인 필요) 는 변수처럼 읽는 값이다 — 저장 막대의 글자와 비활성이 그 값을 읽는다.
- 검증: 가리킨 endpoint · 필드가 있는가, 「모아서 저장」 Collection 에 key 필드가 있는가 (없으면 ADR-325 사용자 결정 1 의 동작과 함께 경고), 같은 Collection 으로 보내는 `callEndpoint` 규칙이 편집 이벤트에 걸려 있는가 (두 위치를 알림), 넣기 규칙이 있는데 넣기 연결이 없는가.
- 왕복: 명령 (`setDataEntries`) · undo/redo · 저장/로드 · 프로젝트 파일 · Code 보기 · Preview delta · Publish. Collection · endpoint · 필드의 이름 변경 · 삭제 · 복제에서 참조를 지킨다.

## 연결 능력과 보장

| 연결이 가진 것        | 저장 동작                                                             | 보장 (화면 문구의 기준)                                                            |
| --------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 묶음 · 원자적         | 변경 목록 한 요청                                                     | 전부 반영되거나 전부 남는다                                                        |
| 묶음 · 원자적 아님    | 변경 목록 한 요청, 응답의 항목별 결과를 읽음                          | 항목마다 반영 여부가 다를 수 있다                                                  |
| 행별                  | 변경마다 한 요청 (순서: 지우기 → 고침 → 넣기, 동시 요청 상한)         | 행마다 반영 여부가 다를 수 있다                                                    |
| 버전 필드             | 고침 · 지우기에 그 행의 버전을 실음                                   | 다른 사람이 먼저 바꾼 행은 서버가 거절한다. 같은 요청이 다시 가도 두 번 반영 안 됨 |
| 저장 전 확인 조회     | 보내기 직전 key 로 읽어 수정 전 값과 대조                             | 읽은 뒤 보내는 사이의 변경은 잡지 못한다                                           |
| 충돌 감지 없음        | 바뀐 필드만 보냄                                                      | 마지막에 쓴 값이 남는다 — 다른 사람의 같은 칸 편집을 덮을 수 있다                  |
| 중복 방지 키          | 넣기에 요청마다 같은 키를 실음                                        | 응답을 잃은 넣기를 다시 보낼 수 있다                                               |
| 요청 압축 받음 (묶음) | 본문이 임계값 이상이고 압축 결과가 더 작으면 `Content-Encoding: gzip` | 보장은 같다 — 큰 붙여넣기의 전송량만 준다                                          |

처음 초안의 계약 (원자적 묶음 + 버전 + 요청 ID) 은 이 표의 가장 높은 조합이다. 고객이 endpoint 를 새로 만들 때 권하는 모양으로 남긴다.

## 요청 모양

**묶음 (참조 모양)** — `POST` · `Content-Type: application/json`. 고객이 새로 만드는 endpoint 용이다.

```json
{
  "updates": [
    { "id": "ord-42", "version": "v17", "set": { "quantity": 8 } },
    { "id": "ord-91", "version": "v4", "set": { "note": null } }
  ],
  "creates": [{ "ref": "new-1", "values": { "name": "Kim", "quantity": 1 } }],
  "deletes": [{ "id": "ord-7", "version": "v2" }]
}
```

성공 응답은 반영한 항목과 새 버전, 넣은 행의 서버 key 를 돌려준다. 순서는 자유다.

```json
{
  "updated": [
    { "id": "ord-42", "version": "v18" },
    { "id": "ord-91", "version": "v5" }
  ],
  "created": [{ "ref": "new-1", "id": "ord-120", "version": "v1" }],
  "deleted": [{ "id": "ord-7" }]
}
```

- `set` 은 필드 대입이다. `null` · `false` · `0` · 빈 문자열과 생략을 구별한다. 배열 · 객체 칸은 값 전체를 바꾼다. 필드 이름은 schema 의 key, 값은 필드의 값 표현 선언으로 되돌린 것이다 (`outgoingRecord` 를 바뀐 필드에만 — 보내지 않은 필드를 더하지 않는다). 큰 정수는 따옴표 없는 literal (`stringifyJsonLossless`). [나가는 값 변환](../../../packages/shared/src/collections/intake/outgoing.ts#L29) · [직렬화](../../../packages/shared/src/collections/intake/parseJsonLossless.ts#L127)
- `version` 은 충돌 감지가 버전 필드일 때만 싣는다. 버전 값은 뜻을 읽지 않는 글자로 다룬다.
- 서버가 값을 고쳐 받았으면 (공백 다듬기 등) 그 행에 `values` 를 더해 돌려준다. 클라이언트는 그것을 확인된 값으로 쓴다.
- 중복 방지 키를 선언한 연결은 선언한 자리 (헤더 · 본문 필드) 에 요청마다 만든 키를 싣는다. 같은 변경을 다시 보낼 때 같은 키다.
- 요청 압축을 선언한 연결은 직렬화한 본문이 임계값 이상이고 gzip 결과가 더 작을 때만 `Content-Encoding: gzip` 으로 보낸다 (브라우저 `CompressionStream`). 임계값 후보는 2 KiB — 그 아래는 줄어도 수백 B 다 (아래 재확인 표), G0 에서 확정한다. 본문에는 편집 값 · key · 버전만 있고 인증 값은 헤더에 있다. 교차 출처 요청이면 서버의 CORS 허용 헤더에 `Content-Encoding` 이 있어야 한다. 행별 요청은 압축하지 않는다.

**행별** — 기존 REST endpoint 용이다.

| 변경   | 요청                                                                                                                                              |
| ------ | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 고침   | 고침 연결의 method (PATCH · PUT) 와 경로 (`{{ key }}`). 본문 = 바뀐 필드, 선언이 「행 전체」 면 보이는 행 전체. 버전은 본문 필드 또는 `If-Match`. |
| 넣기   | 넣기 연결 (POST). 본문 = 넣은 행. 응답의 행에서 서버 key 를 읽는다 (`responseMapping.dataPath`).                                                  |
| 지우기 | 지우기 연결 (DELETE) 과 경로의 key. 버전은 `If-Match` 또는 쿼리.                                                                                  |

## 결과 판정

| 응답                                  | 판정                                                                                                                                 |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| 묶음 2xx · 항목 결과가 요청과 맞음    | 확정 (ADR-325 `confirmChanges` — 응답의 값 · 버전으로). 넣은 행은 서버 key 로 바꾼다.                                                |
| 묶음 2xx · 본문 없음 또는 항목이 빠짐 | 원자적 선언이고 버전이 없으면 보낸 값으로 확정. 버전 연결이면 그 행들을 다시 읽어 버전을 얻는다. 원자적이 아니면 「결과 확인 필요」. |
| 묶음 2xx · 성공과 실패가 섞임         | 원자적 선언이면 선언과 어긋남 — 「결과 확인 필요」 로 두고 다시 읽는다. 아니면 항목별로 확정 · 남김.                                 |
| 행별 2xx                              | 그 변경 확정. 응답에 행이 있으면 그 값으로.                                                                                          |
| 409 · 412 (버전 불일치)               | 충돌. 변경은 남는다. 그 행을 다시 읽어 서버 값을 변경에 적는다.                                                                      |
| 422 · 400 과 필드 오류 (`errorsPath`) | 그 행 · 칸에 오류를 표시한다. 변경은 남는다.                                                                                         |
| 415 (압축해 보낸 묶음 요청)           | 처리 전 거절 — 같은 본문을 압축 없이 한 번 다시 보내고 그 세션에서 압축을 끈다. 그 밖의 거절은 아래 줄대로.                          |
| 401 · 403                             | 저장을 멈추고 사유를 알린다. 변경은 남는다.                                                                                          |
| 404 (고침 · 지우기 대상 없음)         | 서버에서 지워진 행 — 충돌로 보인다.                                                                                                  |
| 429 · 5xx · 시간 초과 · 연결 끊김     | 결과를 모른다 — 아래 「응답을 잃었을 때」.                                                                                           |

**응답을 잃었을 때** — 자동으로 다시 보내지 않는다. 고침 · 지우기는 key 로 다시 읽는다 (확인 조회 연결 → 없으면 그 Collection 의 조회를 다시 실행해 불러온 범위에서 찾는다).

| 다시 읽은 값                       | 판정                                                             |
| ---------------------------------- | ---------------------------------------------------------------- |
| 바뀐 필드가 모두 내 값             | 완료 — 확정                                                      |
| 바뀐 필드가 모두 수정 전 값        | 미반영 — 변경은 남고 「다시 저장」 을 제안                       |
| 그 밖 (일부만 · 다른 값 · 행 없음) | 충돌로 보인다                                                    |
| 읽을 길이 없다                     | 「결과 확인 필요」 — 사용자가 확인한 뒤 다시 저장하거나 취소한다 |

넣기는 서버가 key 를 만들면 대조할 행을 찾을 수 없다 — 「결과 확인 필요」 로 남기고, 중복 방지 키가 있는 연결만 같은 키로 다시 보낸다. 판정이 끝나기 전에는 그 Collection 의 새 저장을 막는다 (편집은 된다).

버전 조건이 붙은 고침은 같은 요청이 다시 도착해도 두 번 반영되지 않는다 (첫 반영이 버전을 올려 조건이 거짓이 된다 — RFC 9110 §13.1.1). 대신 응답을 잃은 뒤의 재시도는 「충돌」 로 돌아온다. 그래서 다시 읽어 「내 값이면 완료」 로 판정한다. 수정 전 값 대조만으로는 값이 A → B → A 로 돌아온 경우를 가리지 못하므로 다시 읽기 전에는 보내지 않는다. [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1) · [Azure API 지침 — 버전 ETag 와 재시도](https://raw.githubusercontent.com/microsoft/api-guidelines/vNext/azure/Guidelines.md)

## 충돌 처리

충돌한 행은 ADR-325 의 변경이 수정 전 값 · 내 값 · 서버 값을 든다. 화면은 그 행에 표시를 하고 칸에 내 값과 서버 값을 같이 보인다. 사용자는 행 단위로 고른다 (사용자 결정 4).

- 「내 값으로 다시 저장」 — 서버 값을 새 기준으로 삼아 (버전도 다시 읽은 것으로) 내 값을 다시 보낸다.
- 「서버 값 받기」 — 그 행의 변경을 버린다.

다른 사람의 변경을 모르는 채 버전만 올려 다시 보내는 일은 하지 않는다. 서버에서 지워진 행은 「지워짐」 으로 보이고 변경을 버리거나 새 행으로 넣기를 고른다.

## 저장 막대와 상태

- 저장 막대 = frame 안의 Text (미저장 N 건) · Button (저장) · Button (취소). 기존 원본을 놓고 Do 와 값 읽기를 연결한 것이다 — 새 컴포넌트가 아니다. 미저장 0 이면 숨는다 (기존 `showWhen`).
- 저장 중 · 결과 확인 필요 상태에서 저장 Button 은 비활성, 취소는 「보내지 않은 변경만」 버린다.
- 결과 알림은 Toast 다 (성공 · 실패 수 · 충돌 수). 실패 · 충돌 행은 Table 의 편집 표시 (ADR-317 `showEditMarks`) 에 상태를 더해 보인다 — 색만으로 알리지 않는다.
- 닫기 경고는 실행 runtime 이 `beforeunload` 에 거는 것 하나다 (미저장 변경이 있는 Collection 이 하나라도 있을 때). Builder 의 Preview iframe 에는 걸지 않는다.

## 범위에서 뺀 것 (사용자 결정 1)

| 항목                         | 근거                                                                                                                        |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------------------- |
| TLS 초기 데이터 (0-RTT) 검사 | 서버 쪽 설정이다. 브라우저의 `fetch` 는 이를 정하지 못하고 클라이언트에서 검사할 수 없다.                                   |
| 본문 서명 · 메시지 암호화    | 키를 보관하고 검증할 서버가 있어야 한다. 브라우저가 고객 API 를 직접 부르는 지금 구조에서는 endpoint 에 적은 헤더가 전부다. |
| 요청 ID 영수증 조회          | 중복 방지 키를 받는 연결의 선택 능력으로 내렸다. 응답 유실은 다시 읽기로 판정한다.                                          |
| 실제 고객 서버 검증          | 저장소가 가진 것은 클라이언트다. 고객 서버의 보장은 연결의 선언이고, 화면 문구가 그 선언 수준임을 밝힌다.                   |

## 조건부 요청 압축 (사용자 결정 1 — 재확인)

사용자 결정 1 은 「재확인 뒤 판단」 이었다. 2026-11-26 에 다시 재고 문서를 다시 읽었다.

**크기** — 개정한 참조 모양 (`{updates:[{id, version, set}]}`) 으로 Node 24.22.1 · zlib gzip level 6. 붙여넣기 행은 행마다 다섯 칸 (숫자 다섯, 또는 한글 이름 · 부서 · 메모 · `Y`/`N` · 짧은 글자) 인 합성 값이다 — 규모만 본다.

| 본문                           |                  JSON |                gzip |      절감 |
| ------------------------------ | --------------------: | ------------------: | --------: |
| 한 행 한 칸                    |                  59 B |                79 B |     −34 % |
| 두 행 세 칸                    |                 114 B |                97 B |      15 % |
| 10 행 × 5 칸 (숫자 · 한글)     |         962 · 1,576 B |         287 · 423 B | 70 · 73 % |
| 20 행 × 5 칸 (숫자 · 한글)     |       1,929 · 3,147 B |         470 · 624 B | 76 · 80 % |
| 100 행 × 5 칸 (숫자)           |               9,761 B |             1,856 B |      81 % |
| 1,000 행 × 5 칸 (숫자 · 한글)  |    98,687 · 157,027 B |   16,970 · 13,798 B | 83 · 91 % |
| 10,000 행 × 5 칸 (숫자 · 한글) | 993,676 · 1,570,188 B | 165,993 · 129,634 B | 83 · 92 % |

압축 시간은 Node 에서 1,000 행 0.5 ms · 10,000 행 4.8 ms 였다 (브라우저 `CompressionStream` 은 G0 에서 잰다). 작은 편집은 줄지 않거나 커지고, 큰 붙여넣기는 크게 준다 — 조건부로만 뜻이 있다. 처음 초안의 「4 KiB 후보」 와 개정 직후의 「이득 없음」 은 둘 다 한쪽만 본 것이다.

**서버** — 공식 문서를 다시 읽은 결과 (요약 도구의 요약을 원문 구절과 대조했다).

| 서버             | 요청 본문 gzip 해제                                                                                                                                            | 근거                                                                                                                                                   |
| ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Tomcat 10.1 · 11 | 없다 — 연결 설정의 `compression` 은 응답용이고, 요청 본문을 푸는 속성도 내장 필터 (14 종) 도 없다                                                              | [연결 설정](https://tomcat.apache.org/tomcat-11.0-doc/config/http.html) · [내장 필터](https://tomcat.apache.org/tomcat-11.0-doc/config/filter.html)    |
| Spring Boot      | 기본 지원 없음 — `server.compression.enabled` 는 응답 압축이고, 요청 해제 요청 (이슈 11827) 은 2018-04 「기본 지원할 가능성이 낮다 · 컨테이너의 일」 로 닫혔다 | [웹 서버 how-to](https://docs.spring.io/spring-boot/how-to/webserver.html) · [이슈 11827](https://github.com/spring-projects/spring-boot/issues/11827) |
| Jetty 12         | `GzipHandler` 를 넣으면 된다 (기본으로 켜져 있는지는 문서에 없음)                                                                                              | [HTTP 서버 가이드](https://jetty.org/docs/jetty/12/programming-guide/server/http.html)                                                                 |
| Undertow         | `RequestEncodingHandler` 를 넣으면 된다 (문서가 「HTTP 표준 밖의 확장」 이라고 적는다)                                                                         | [문서](https://undertow.io/undertow-docs/undertow-docs-2.1.0/index.html)                                                                               |
| 브라우저         | `CompressionStream` 은 2023-05 부터 널리 쓸 수 있다. `Content-Encoding` 은 CORS 안전 목록의 요청 헤더가 아니다                                                 | [MDN](https://developer.mozilla.org/en-US/docs/Web/API/CompressionStream) · [Fetch](https://fetch.spec.whatwg.org/#cors-safelisted-request-header)     |

확인하지 못한 것 — 실제 Tomcat 에 압축 요청을 보내 보는 실험 (이 기기에 Java 실행 환경이 없다). 위 판정은 문서 근거다.

**판단** — 요청 압축은 범위에 남기되 필수 계약이 아니라 연결이 선언하는 선택 능력이다. 기본은 꺼짐이고, 고객 서버가 해제 필터 · handler 를 넣고 CORS 로 헤더를 허용한 묶음 연결에서만 켠다. 처음 초안의 서버 쪽 검사 (압축 해제 상한 등) 는 고객 서버의 일이라 통과 조건에 넣지 않는다.

## 본문 크기 기준선

1,000 개 행 (`i=0…999`) 에 순서대로 `id="ord-"+i`, `version="v1"`, 숫자 열 `c1…c998` 을 둔다 (`cj=i×1000+j`). `ord-17` 의 `c2=8` · `c9=0`, `ord-843` 의 `c31=5` 를 대입한 뒤 측정했다. 변경분 본문은 요청 ID 와 `updates[{id, baseVersion, set}]` 순서였다 (처음 초안의 모양 — 개정한 참조 모양의 값은 위 「조건부 요청 압축」 표에 있다). Node 24.22.1 에서 공백 없는 JSON UTF-8 바이트와 zlib gzip level 6 바이트. HTTP 헤더 · TLS · 서버 지연은 포함하지 않았다.

| 본문                        |         JSON |        gzip |
| --------------------------- | -----------: | ----------: |
| 전체 1,000 행 × 1,000 열    | 13,784,992 B | 2,568,728 B |
| 고친 두 행의 모든 열        |     26,781 B |     7,588 B |
| 두 행의 세 필드 + 식별 정보 |        173 B |       139 B |
| 한 행의 한 필드 + 식별 정보 |        114 B |       123 B |
