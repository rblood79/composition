# ADR-280 design breakdown — RAC 표면에서 유도하는 등록표와 controlled 배관

> 본문: [../280-interactions-rac-surface-registry-controlled-runtime.md](../280-interactions-rac-surface-registry-controlled-runtime.md). 연구 정본: [INTERACTION_REDESIGN_RAC_S2_2026-10](../../explanation/research/INTERACTION_REDESIGN_RAC_S2_2026-10.md) (§3 매트릭스 · §4 gap · 부록 A/B). `docs/adr/evidence/` 는 로컬 전용이라 실측 결론은 여기에 둔다.

## 0. 전제 lock-in (fork 4 질문 — 사용자 결정 Q4 「2 개 — base + 응용」, 2026-10-22)

1. **base / 응용**: 이 ADR (A) 이 base — 등록표의 모양 (개념 표 · spec · `deriveRegistry`) 과 실행이 RAC 에 닿는 조건 (controlled · override 우선 · 래퍼 전달 · owner). ADR B (응용) 는 그 등록표를 **소비** 하는 패널 어휘 · `!event` UI · Provider 상속 · instance 규칙 상속 · Form 제출 목적지 — A 의 spec 필드 (`exposed` · `s2Exceptions` · owner 종류) 가 없으면 B 의 패널이 설 자리가 없다. 의존 방향 158 → 248 · 250 · 256 → **280 → B**.
2. **schema 직교성**: 문서 schema (`InteractionEntry`) · 실행 schema (`InteractionRule`) 무변경. `!event.<arg>` 는 `params.value` 의 문자열 표기. B 가 더할 수 있는 것 (상속 prop · instance 규칙 override 층) 은 A 와 직교 — A 의 등록표는 「무엇이 있나」, B 는 「어디에 보이고 누가 물려받나」.
3. **선행 전제 reverse 검증**: ADR-158 의 전제 「capability = RAC controlled prop 1 개 patch · G1 근거 없는 등재 금지」 는 그대로 valid — 이 ADR 은 그 근거를 문자열 `racRef` 에서 d.ts `satisfies` 로 **강화** 한다. ADR-158 R1 이 상정한 「uncontrolled 렌더 컴포넌트 → 등재 보류」 는 사용자 결정 Q1 (controlled 공급 = D1 안) 으로 해소 — 보류의 사유가 사라졌으므로 deferred 를 비운다. ADR-214 R6 (변수 관찰은 주입 0) 은 변수 경로에 한정된 것이라 그대로. ADR-250 Decision B (runtime only) · R2 (선언 변경 시 폐기) 그대로.
4. **판독**: 사용자가 요청할 때 `/review-adr 280`. phase 당 판독 1 + 수리 검증 1.

### 1b. RED 3 — 재현 테스트 (수정 전 RED, Phase 2 뒤 GREEN)

1. **ListBox capability 미도달**: fixture ListBox (항목 3, 선언 선택 0) 에 규칙 `Button.onPress → ListBox.selectItem(item-2)` → Preview render 뒤 RAC ListBox 의 `selectedKeys` 가 `{item-2}` 여야 한다 — 지금은 `defaultSelectedKeys` 가 집계 `[]` 로 고정돼 RED. 같은 형태로 GridList.
2. **withI18n When 유실**: `locale: "ko-KR"` 인 Slider 에 규칙 `Slider.onChangeEnd → toast` → `fireEvent` 뒤 toast 0 회면 RED (locale 없는 Slider 는 1 회 — 대조군).
3. **Menu owner 미등재**: MenuTrigger 노드에 `onOpenChange` 트리거 규칙을 걸 수 없고 (`resolveTriggers("MenuTrigger")` = `[]`), Menu 노드에 건 `open` capability 는 실행 시 report — 둘 다 현재 동작을 고정하는 RED.
4. **제약 우회** (review round 1 h2 · round 2 h1): 반례 7 — (a) `isDisabled` Checkbox ← Button `check` · (b) `isDisabled` CheckboxGroup 안 Checkbox ← `check` · (c) `isReadOnly` TextField ← `setValue` · (d) `disallowEmptySelection` ListBox 의 마지막 선택 ← `clearSelection` · (e) `disabledKeys` 에 든 항목 ← `selectItem`. 각 규칙 실행 뒤 RAC 요소 상태가 **바뀌면** RED (지금은 (a) 가 `isSelected=true` 로 바뀜 — `dispatcher.ts:187-219`). Phase 2 뒤에는 상태 무변경 + report 1 로 GREEN. (c) 는 TextField 전환 전이라 지금 key remount 경로로 재현한다. (f) · (g) 유효 상태 (review round 2 h1): 항목 A 를 Selected 로 작성한 multiple ListBox (override 없음) ← `selectItem(B)` → RAC 선택이 {A, B} 가 아니면 RED (지금 `getElement` 에 집계 선택이 없어 `!param` 이 집합을 통째로 바꾼다 — `dispatcher.ts:85-109`) · 같은 목록 + `disallowEmptySelection` ← `deselectItem(A)` → 선택이 비면 RED.
5. **Form 미실행** (h3): Form 안 field 1 + 밖 Button 의 규칙 `Button.onPress → Form.submit` 과 Form `onSubmit → toast` → toast 0 회 · report 「imperative capability 미지원」 1 회면 RED. 대조군 3 (지금 동작 기록, round 2 h2): action 없는 Form 안 `type="submit"` Button → iframe 다시 읽힘 여부 · `action` 을 작성한 Form → 그 목적지로 이동 (보존 대상) · `method="dialog"` Form → dialog 닫힘. 지금 Preview Form 에 `onSubmit` 처리가 없고 `action` · `method` · `encType` · `target` 은 그대로 RAC Form 에 간다 (`delegatedDom.runtime.ts:2691-2707`).

측정 조건 (measurement-validity §1): browser vitest (`vitest.browser.config.ts`), 설치 RAC 1.22.1, 합성 fixture 는 규모가 아니라 **도달 여부** 만 묻는다 (Q1 — 분포 지표 인용 없음).

### 1c-2. controlled 고정 규칙 (병렬 연구 §3-4 · §3-5 — I1)

- helper 는 `X = override ?? 선언값 ?? 개념의 빈 값` 으로 **첫 render 부터 정의된 값** 을 넘긴다 (string `""` · number `NaN` · Set `new Set()` · boolean `false` · Key `null` · DateValue `null`).
- `default*` 와 controlled prop 을 같이 넘기지 않는다 — 집계 (`catalogCollectionSelectedKeys` · Radio · Tab · DisclosureGroup 자식) 는 controlled 초기값으로 옮긴다.
- 소유 모드 전환 0: dev 모드 콘솔 「A component changed from uncontrolled to controlled」 0 을 하니스가 단언 (G2). record 자체가 바뀌는 경우 (origin → instance 파생) 만 `key` remount.

### 2b. 유도 규칙

- events = 개념 events 의 합 (owner 가 `item` 이면 상태 개념의 callback 제외 · `exposed: false` 개념은 `events` 에 넣되 `hidden` 표식).
- capabilities = 상태 개념마다 `set` (valueType 으로 param 종류 — `itemKey` · `value` · `text` · `number`) · boolean 이면 `toggle` · 빈 값 상수가 있으면 `clear` · Set 이면 `selectItem` · `deselectItem` (expansion 은 `expand` · `collapse`). 이름은 현 등록표의 키를 그대로 쓴다 (`check/uncheck/toggleCheck` · `selectItem/clearSelection` · `expand/collapse` · `open/close` · `setValue/clear` · `selectTab` · `setInput` · `sort`).
- racRef = `"<개념 파일> satisfies <d.ts 타입> · <RAC md>"` — G1 의 문자열 요건 유지.
- prop = 개념의 **controlled** prop (`state.prop`) — `default*` (`state.defaultProp`) 는 capability prop 이 되지 않는다. 손 등록표의 `default*` 5 행은 G1 의 전환 표로만 대조한다.
- guards = 개념 `conditions` 의 RAC 제약 (`isDisabled` · `isReadOnly` · `disallowEmptySelection` · `selectionMode` · `disabledKeys` · Phase 0 결과에 따라 범위) 을 capability 별로 — 「값 쓰기」 는 disabled · readOnly, 「집합에서 빼기」 는 빈 선택 금지 추가, 「집합에 넣기」 는 selectionMode · disabledKeys 추가. owner `group` 개념의 항목 type 은 그룹 context 제약도 읽는다.
- imperative = spec `imperative: ["submit", "reset"]` (Form 만) → def `imperative: true` · guard 없음 (RAC validation 이 제출을 막는다).
- deferred = spec 에 `deferred: [..]` 가 있을 때만 (Phase 2 뒤 0).
- owner `trigger` 인 개념은 trigger type 의 등록표에 들어가고 본체 type 에는 들어가지 않는다.
