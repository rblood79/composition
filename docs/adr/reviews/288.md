### H1 — 공용 Object/Array 시작값 편집은 contract 51에서 저장할 수 없다

- 위치: `docs/adr/288-data-panel-single-surface-column-popover-variable-table.md:111`, `docs/adr/design/288-data-panel-single-surface-breakdown.md:45` (schema 무변경 선언: breakdown:8).
- 입력·상태 → 잘못된 결과: 페이지 또는 요소의 Object 변수에 `{"id":1}`, Array 변수에 `[1,2]`를 JSON 팝오버로 입력하면 `stateVariable.defaultValue` 검증이 `DEFAULT_VALUE_TYPE`으로 거절한다. UI 분기를 옮기는 것만으로는 G2의 세 소유자 JSON 시작값 편집을 제공할 수 없다.
- 근거: `packages/shared/src/catalog/document/types.ts:1165`는 structured default를 빈 문자열로 정의한다. `packages/shared/src/catalog/document/validation.ts:1853`은 Object/Array에 `""`만 허용한다. `apps/builder/src/builder/catalogRuntime/stateVariables.ts:343`의 `setDefault`도 Scalar만 받는다. `packages/shared/src/catalog/runtime/stateTemplate.ts:74`는 이 빈 문자열을 null로 해석한다.
- 해결 방향: contract 51을 유지한다면 공용 표에 소유자별 편집 가능 계약을 두고 페이지·요소 structured 시작값은 기존 빈 값 계약을 명시한다. 세 소유자 모두 JSON 시작값을 지원하려면 타입·저장 검증·명령·런타임 및 contract/호환 정책을 함께 설계한다.
- 실행 근거: page/element × object/array 4개 입력에서 실제 `validateCatalogEntry`의 오류 코드 확인.

### H2 — prop의 가시 사슬을 binding.key에도 적용하면 다른 변수의 참조를 바꾼다

- 위치: `docs/adr/288-data-panel-single-surface-column-popover-variable-table.md:112`, `docs/adr/design/288-data-panel-single-surface-breakdown.md:38`.
- 입력·상태 → 잘못된 결과: 프로젝트 변수 `a = "GLOBAL"`를 만든 뒤 요소에도 `a = "LOCAL"`를 두면 같은 요소의 prop `{{ a }}`는 LOCAL을 읽지만 `binding.key = "{{ a }}"`는 GLOBAL을 읽는다. 요소 a → renamed 때 prop용 판정으로 binding까지 재작성하면 프로젝트 참조였던 key가 미해결이 된다. 반대로 프로젝트 a의 이름을 바꿀 때 요소 a가 가린 것으로 판단하여 key를 남기면 실제 프로젝트 참조가 끊긴다.
- 근거: `packages/shared/src/catalog/runtime/stateTemplate.ts:120`의 prop 해소는 record 요소 사슬을 읽는다. `stateTemplate.ts:319`와 `:346`의 binding key 해소는 페이지·프로젝트만 읽는다. 재사용 대상으로 적은 `apps/builder/src/builder/catalogRuntime/dataVariables.ts:123`은 node.props만 스캔하고 `:155`에서 요소 사슬을 쓴다. `stateVariables.ts:149`의 다른 카운터는 interaction referrer만 센다. 두 카운터 어느 쪽도 범용 필드 해소의 정본이 아니다.
- 해결 방향: 참조 site에 필드 종류와 소비 문맥을 보존하고, prop은 실제 record/instance 사슬, binding.key는 page/project 사슬로 해소하도록 명시한다. 한 모듈을 공유하되 필드별 runtime 해소 계약을 유지한다. G1에 같은 노드에서 prop과 key가 서로 다른 변수를 읽는 입력을 추가한다.
- 실행 근거: 실제 `CatalogGraph`와 `catalogRecordVariables`/`catalogBindingKey`로 LOCAL/GLOBAL의 차이 및 key를 renamed로 바꿨을 때 undefined를 확인했다. 미래 rename 명령 자체를 실행한 것은 아니다.

### H3 — 기존 이름 충돌 검사 유지로는 새 이름이 다른 참조를 가로채는 것을 막지 못한다

- 위치: `docs/adr/288-data-panel-single-surface-column-popover-variable-table.md:112`의 「이름 충돌 검사는 지금 그대로」.
- 입력·상태 → 잘못된 결과: 프로젝트 a = GLOBAL, 페이지 x = LOCAL, Text `{{ a }}`인 상태에서 페이지 x → a를 요청한다. 기존 `catalogVariableNameConflict`는 허용한다. 이 Text는 x의 사용처가 아니므로 제안한 재작성은 건드리지 않지만, 이름 변경 후에는 페이지 a를 읽어 GLOBAL → LOCAL로 바뀐다. 이름 변경 대상과 무관한 참조가 조용히 바뀐다.
- 근거: `apps/builder/src/builder/catalogRuntime/stateVariables.ts:134`는 `project.stateVariableIds`만 검사하고 projectVariable entry는 보지 않는다. `packages/shared/src/catalog/runtime/stateTemplate.ts:149` 이후에는 페이지 변수가 프로젝트 변수보다 앞서며 `:187`에서 첫 이름이 이긴다. 프로젝트 변수 쪽 `stores/utils/dataChange.ts:216`의 충돌 검사는 별도 경로라 페이지 rename을 막지 못한다.
- 해결 방향: 공용 rename 명령에서 새 이름의 해소 결과까지 검사한다. 적어도 페이지·요소 rename이 보이는 프로젝트 이름과 충돌하는 경우를 거절하고, 명령 경계에서 패널·코드 보기·data sink에 동일하게 적용한다. 의도적으로 shadowing을 허용하려면 기존 참조를 어떻게 보존할지 별도 계약이 필요하다.
- 실행 근거: 실제 graph에 대한 conflict 결과 undefined, rename 전·후에 동일한 Text 원문이 GLOBAL/LOCAL로 달리 해소됨을 확인했다.
