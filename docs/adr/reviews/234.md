### h1 — HIGH: raw diff로는 기존 모양을 보존할 수 없음

- 대상 결정: breakdown:64의 `(복제본 − origin) diff (F12)` 재사용과 본문:34의 이관 전후 Canvas 동일.
- 현재 seed는 default의 root style을 제거해 변형에 `style:{}`를 넣는다 (`stateVariantOrigins.ts:131-151`). `diffPropsAgainstOrigin`은 복제본에 존재하는 키만 비교한다 (`originChildRefs.ts:75-88`). resolver는 원본 style 위에 patch를 병합한다 (`instanceResolver.ts:35-46`).
- 최소 반례: origin `{style:{color:"red",padding:24}}`, 기존 복제본 `{style:{}}`. 지정한 diff 유틸 결과는 `{}`이고 병합 후에는 `color:red,padding:24`가 나타난다. 부재 보존 assertion **RED**. 이는 아직 없는 234 migration 구현에 대한 실패 판정이 아니라, 명시한 기존 유틸의 재사용만으로는 보존 계약을 만족하지 못한다는 반증이다.
- 영향: Components 변형의 기존 모양과 runtime 상태 모양이 달라질 수 있다. 기존에 무시되던 변형 padding을 새 모델에서 활성화하는 것 역시 무조건적인 이전 픽셀 동일과 충돌할 수 있다.
- 해결 방향: 저장된 raw 객체 차분과 기존 consumer가 실제 그린 상태 차분을 구분하고, 부재/상속/명시 제거(빈 fills 포함)의 뜻을 정한다. catalog fallback 복원, 상태별 유효값의 보존, 불가능한 가족의 원자적 보류 범위를 이관 계약에 넣는다. 단순히 빈 객체를 patch로 쓰지 않는다.

### h2 — HIGH: 변형 subtree 교체 시 기존 descendants 경로가 끊김

- 대상 결정: breakdown:53,64의 master 선해소 및 복제본→ref 전환. 본문:35는 사용자 저작 노드 Δ0도 요구한다.
- `cloneVariantChildren`은 `${variantId}__n`으로 자식 ID를 바꾼다 (`stateVariantOrigins.ts:107-121`). Tab origin도 default/selected에 서로 다른 `__label` ID를 만든다 (`tabsTemplateOrigins.ts:29-35,63,84`). Preview descendants는 ID path 또는 segment path에 정확히 매칭한다 (`resolvers/canonical/index.ts:269-280`).
- 최소 반례: 기존 variant의 `variant-label`을 instance의 `descendants`에서 `Custom`으로 편집한다. variant를 base의 ref로 바꾸고 Phase 1에서 제시한 대로 중간 master를 먼저 연 결과를 사용하면, 자식 ID는 `base-label`이 되고 같은 instance는 `Base`를 표시한다. 편집 보존 assertion **RED**. 실제 Phase 1 코드가 이미 구현되었다는 뜻은 아니며, 제안된 선해소 절차를 기존 resolver 두 호출로 구성한 반례다.
- 해결 방향: old child ID/경로→새 origin 경로 대응표를 만들고, 직접 ref·중첩 ref·descendants 안 ref 및 이름 기반 경로의 재매핑 범위를 명시한다. 사용자 ref를 재직렬화한다면 Δ0 수식도 수정한다. 사용자 저작을 그대로 보존해야 한다면 안정 ID/alias를 유지하는 대안을 정한다. root ref ID만 유지하는 것으로는 부족하다.

### m3 — MEDIUM: 상속한 enabled:false의 복구 표현이 없음

- 본문:91 및 breakdown:54는 `enabled?: false`, breakdown:55는 필드 부재=표시를 제안한다. 기존 ref 병합은 `{...master,...ref}`로 부재 필드를 상속한다 (`canonicalRefResolution.ts:224-226`, Preview `resolvers/canonical/index.ts:170-172`).
- 시나리오: reusable origin 또는 중간 변형이 자식을 숨긴 뒤, 마지막 instance에서 그 자식만 다시 표시한다. 마지막 patch에서 `enabled`를 지우면 upstream `false`를 상속하고, `true`는 제안 타입상 저장할 수 없다. 반대로 ref의 필드 부재를 무조건 표시로 읽으면 upstream 숨김 자체가 상속되지 않는다.
- 해결 방향: 필드명은 사용자 확정대로 유지하면서 `enabled?: boolean`의 부재=상속/최종 기본 true, false=숨김, true=표시로 정하거나, 별도의 명시 reset 규칙을 정한다. 조상 subtree 자체의 숨김과 자식 자신의 표시 override는 구분한다. 이 항목은 신규 UI 결함을 실측했다는 주장이 아니라 저장 계약의 표현력 문제다.

### m4 — MEDIUM: 상태 diff와 instance override의 충돌 순서가 미정

- 본문:88과 breakdown:61은 상태 간 우선순위만 규정한다. 현행 규칙은 `instance 명시 > disabled > selected > baseline`이며 Canvas는 `instanceOwned`를 제외한다 (`stateVariantResolution.ts:182-197`). 인접 테스트:141-147이 명시 color/opacity 보호를 확인한다.
- 시나리오: instance가 color를 파랑으로 편집하고 disabled 변형은 회색이다. ref를 먼저 해소한 뒤 RAC 활성 상태 diff를 얹는 순서면 회색이 최종값이다. 현행은 파랑을 유지한다. 두 순서 중 어떤 것을 새 계약으로 삼을지 현재 Decision만으로 결정할 수 없다.
- 해결 방향: base→선택/휴지 및 상호작용 상태→instance 명시 patch 등 최종 순서를 root와 descendants 모두에 선언한다. 상속으로 얻은 값과 instance가 직접 소유한 patch를 구별하고, 선택된 변형 ref 자체의 patch를 runtime 상태보다 우선할지까지 명시한다. 이는 기존 테스트를 더 늘리라는 요청이 아니라 230 대체 시 계승할 동작을 확정하라는 요청이다.

### l5 — LOW deferred: geometry 및 전체 비용 관측

### h1 — HIGH: patch 합성 중 삭제 표기를 제거하면 원본 값이 되살아남

**수리 계약의 문제 위치:** `docs/adr/design/234-variant-instances-and-slot-filled-collections-breakdown.md:57`은 `mergePropsWithStyleDeep` 한 곳에서 병합 후 null을 제거해 두 leg로 전달하지 않기로 정한다. 이 helper는 최종값을 만드는 곳뿐 아니라, 원본을 아직 읽지 않은 **patch와 patch의 합성**에도 쓰인다.

- Preview: `apps/builder/src/resolvers/canonical/index.ts:349-359`에서 내부/외부 descendants patch를 먼저 합치고, `:368`에서 실제 master를 해소한다.
- Canvas: `apps/builder/src/adapters/canonical/canonicalRefResolution.ts:329-340`의 `getStackedDescendantPatch`에서 patch 스택을 먼저 합치며, `:440-454`에서 그 결과를 원본 props에 적용한다.
- 공용 helper: `apps/builder/src/adapters/canonical/instanceResolver.ts:35-46`.

**최소 입력:**

```json
{
  "masterLabel": {
    "id": "label",
    "props": { "children": "Text", "style": { "color": "red" } }
  },
  "innerRefDescendants": { "label": { "style": { "color": "blue" } } },
  "outerRefDescendants": { "inner/label": { "style": { "color": null } } }
}
```

문서 구조는 `outer → host → inner(ref → master) → label`이다. 바깥 patch가 최종 삭제를 요청하므로 **기대값**은 label props `{children:"Text",style:{}}`이며 이후 catalog fallback을 읽어야 한다.

**실제 결과(제안한 null 제거 계약을 모형화한 기존 resolver):**

1. 내부 blue patch + 외부 null patch를 공용 helper로 합친다.
2. 병합 직후 null 제거로 합성 patch가 `{style:{}}`가 된다.
3. 원본 `{style:{color:"red"}}`에 이를 적용하면 `{style:{color:"red"}}`가 남는다.
4. 출력은 `{children:"Text",style:{color:"red"}}` — 삭제 기대 assertion **RED**.

임시 probe는 제품 소스를 수정하지 않고 Vitest 모킹으로 기존 helper 결과에 제안된 null 정리를 추가했다. `resolveCanonicalRefProps`/`resolveCanonicalDescendantOverride`도 같은 정리 결과를 반환하도록 해, 실제 `resolveCanonicalDocument`의 중첩 분기와 helper 호출 순서를 실행했다. 아직 구현되지 않은 ADR-234의 production 버그를 실측했다는 주장이 아니라, **명시된 helper 변경만 적용할 때 기존 production 호출 경로가 만드는 반례**다. Canvas 쪽은 같은 사전 합성 호출을 코드로 확인했고 별도 전체 scene 실행은 하지 않았다.

**필요한 계약 보완:** patch 합성 중에는 삭제 표기를 보존하고, 원본/상태/instance 층을 모두 적용하여 소비자에 넘길 유효값을 확정하는 지점에서 제거해야 한다. patch 합성 함수와 최종 적용 함수를 구분하거나 helper의 합성/최종화 모드를 명시할 수 있다. `null` 대신 다른 sentinel을 쓰더라도 최종 적용 전 제거하면 같은 반례가 남는다. 부재=상속 규칙은 유지한다.

### null 경계와 기존 문서 중단 기준

- 단일 최종 병합 `{style:{color:"red",padding:24}} + {style:{color:null,padding:null}}`에서 `{style:{}}`가 되는 계약 모형은 **PASS**다. h1을 다시 여는 이유는 이 단일 반례가 아니라 중간 patch 합성이다.
- root/descendants props의 최종 병합 경로가 공용 helper로 연결된 것은 확인했다. 따라서 최종 적용 시 정리한다면 null을 Canvas/Preview 소비값에 남기지 않는 방향은 성립한다. 다만 현재 문구대로 모든 helper 호출에서 제거하는 방식으로는 보존과 비노출을 동시에 만족하지 못한다.
- breakdown:58,106은 기존 null 발견 시 Phase 1 착수 전에 sentinel 변경 및 본문 개정을 요구하므로 **설계상 중단 기준은 충분**하다. 기존 문서에 실제 null이 0개인지는 Phase 0 실행 근거이며 이번에 실측하지 않았다. sentinel 충돌 검사는 이번 중첩 합성 문제를 해결하지 않는다.
