- 최소 입력: owner `value:["a"]` 또는 `selectedKeys:["a"]`, 자식 node id=`node-1`, 자식 `props.value/id="a"`, `isSelected:false`.

- 해결 방향: 양쪽 선택 key reader와 owner/자식 상태 우선순위를 함께 정의한다. 기존 자식 `isSelected` 문서의 BC, Preview 초기값·상호작용 writeback·재마운트까지 포함해 같은 key를 쓰도록 계약을 보강한다. 단순히 controlled props를 전달하면 현재 runtime store 경로와 충돌할 수 있으므로 기존 uncontrolled 동작도 보존해야 한다.

Canvas의 `apps/builder/src/adapters/canonical/canonicalRefResolution.ts:1110-1114`도 patch/source의 enabled만 보고 생성을 건너뛴다. 이 조건에 `isExpanded:false`는 관여하지 않는다.
- **반례 3**: origin의 header/content → collapsed ref → `isExpanded:true` instance. Round 1처럼 `descendants.content.enabled:false`를 주입하면 현재 코드에서도 content가 제거된다. 그러나 새 설계는 바로 그 입력을 상태 변형에서 금지한다. 이를 새 계약대로 `props.isExpanded:false` 및 구조를 바꾸지 않는 style patch로 바꾸면 content의 enabled는 false가 되지 않아 자식이 남는다.
- 표시 경로: Canvas는 `apps/builder/src/builder/workspace/canvas/layout/engines/implicitStyles.ts:3855-3868`에서 유효 접힘일 때 content에 display:none을 주입한다. Preview는 `packages/shared/src/renderers/LayoutRenderers.tsx:1802-1842`에서 남은 content를 Disclosure에 전달한다. 따라서 반대 상태로 전환했을 때 "표시할 자식 자체가 없음"이라는 원래 실패는 새 설계 입력에서 성립하지 않는다.
- 왜 기존 지적이 해소되는가: 상태 층이 제거된 자식을 복원하게 만드는 대신 상태 변형에서 제거 원인을 만들지 않는다. 구조 patch가 코드 전역에서 사라졌다는 주장은 아니다. 지목된 resolver는 여전히 일반 enabled patch를 처리하며, 상태 변형 쓰기 거부는 Phase 2의 구현 계약이다.
- **outcome: fixed 유지** — 설계 수리 확인. seed·쓰기 거부 및 실제 왕복 완료는 이번 정적 검증의 결론에 포함하지 않는다.

### m1 — MEDIUM (기존 이슈): 그룹 유효 펼침 상태 소비 계약 확인

- 계약: `docs/adr/237-origin-instance-slot-extension.md:90,116`과 `docs/adr/design/237-origin-instance-slot-extension-breakdown.md:40,82`의 우선순위는 **Components 변형 자신 강제 상태 → isDisclosureExpandedInContext**다. 강제 상태를 모두 없앤다는 뜻이 아니다.
- 코드: `packages/shared/src/utils/disclosureGroupExpansion.ts:41-44`는 명시 false 외에는 펼침, :58-69는 직접 자식 Disclosure 중 펼침 후보를 순서대로 모아 단일 펼침일 때 첫 후보만 유지한다. :81-91은 부모가 DisclosureGroup이고 자식 목록이 주어지면 이 집합에 포함되는지 판정하고, 아니면 자기 prop으로 돌아간다.
- **반례 4**: `allowsMultipleExpanded:false`, 자식 순서 [A,B], A/B 모두 `isExpanded:true`, 일반 사용자 instance에 강제 metadata 없음 → 후보 [A,B] → 유효 집합 {A} → B=false. raw=true는 여전히 사실이지만 새 상태 층 계약도 B=false를 읽으므로 원래의 펼침 모양/접힌 본문 불일치는 성립하지 않는다.
- 실제 호출: Canvas layout은 `apps/builder/src/builder/workspace/canvas/layout/engines/implicitStyles.ts:3847-3868`, chevron은 `apps/builder/src/builder/workspace/canvas/skia/buildSpecNodeData.ts:790-804`에서 이 함수를 호출한다. Preview는 같은 함수 이름을 직접 호출하지 않고 `packages/shared/src/renderers/LayoutRenderers.tsx:1716-1723`에서 그 내부 공용 함수 `resolveGroupExpandedDisclosureIds`를 호출해 초기 keys를 만든다. F13의 "같은 판정"이라는 의미는 맞는다.
- 구현 경계: 현재 `apps/builder/src/adapters/canonical/canonicalRefResolution.ts:1301-1307,1346-1350`의 상태 층에는 expanded가 없고, `apps/builder/src/builder/components/stateVariantLayers.ts:228-247`의 강제 상태에도 없다. 따라서 **이미 expanded 층까지 함수가 연결됐다는 구현 확인은 아니다**. Proposed Phase 2가 기존 layout/chevron과 같은 판정을 새 층에 연결하도록 수정된 것을 확인했다.
- **outcome: fixed 유지** — 기존 반례 해소를 위한 계약과 함수 동작 일치. 미구현 자체를 새 이슈로 올리지 않는다.

### h3 — HIGH: Radio는 자식 선택을 유지하고 value만 유일하게 배정해도 두 leg가 일치하지 않는다

- 설계 위치: `docs/adr/237-origin-instance-slot-extension.md:15,35,88`, `docs/adr/design/237-origin-instance-slot-extension-breakdown.md:65,74`. 선택 origin 추가 시 새 자식에 isSelected:true와 유일한 Radio value를 쓰면서 현행 두 leg가 동일하다고 전제한다.
- **반례/재현 방법**: 일반 RadioGroup의 value가 없고 기존 Radio A=`{value:"a",isSelected:true}`인 상태에서 Slot "+"로 선택 origin B를 추가한다. 새 계약대로 B=`{value:"b",isSelected:true}`가 되고 value는 서로 다르다. 강제 상태 metadata는 없는 일반 사용자 instance를 기준으로 한다.
- **정적 결과**: Canvas 상태 층은 `apps/builder/src/adapters/canonical/canonicalRefResolution.ts:1270-1283`에서 각 자식의 true를 독립적으로 받아 A/B 모두 selected=true다. 실제 Radio 표시도 `apps/builder/src/builder/workspace/canvas/skia/buildSpecNodeData.ts:1154-1169,1747-1754`에서 그룹 value가 없으면 각 자식 값을 보존한다. 반면 Preview는 `packages/shared/src/renderers/FormRenderers.tsx:947-953`의 find로 A만 고르고 :968에서 defaultValue="a"를 넘긴다. 자식 Radio value는 같은 파일 :865-872에서 전달되므로 B는 비선택이다. wrapper도 `packages/shared/src/components/RadioGroup.tsx:323-345`와 `packages/shared/src/components/Radio.tsx:19-31`에서 해당 props를 RAC에 전달한다.
- 추가 확인: 그룹 value가 있으면 실제 Canvas Radio 표시 reader는 이를 **자식보다 먼저** 쓴다(`buildSpecNodeData.ts:1165-1169`). 예를 들어 그룹 value="b", A=true/value="a", B=false/value="b"이면 Canvas 표시는 B, Preview 초기 선택은 A다. F6의 상태 층 reader만으로 "Canvas 전체도 자식이 정본"이라고 단정할 수 없다.
- 왜 틀렸는가: 유일한 value는 key 충돌만 막는다. 새 자식의 선택과 기존 자식의 선택을 함께 정규화하지 않으면 단일 선택이 보장되지 않는다. Preview 클릭 후의 정규화(`FormRenderers.tsx:987-1006`)는 추가 직후의 불일치를 예방하지 않는다.
- 해결 방향: Radio 삽입 시 유지/전환할 단일 선택과 기존 형제 isSelected·기존 그룹 value의 일관된 갱신을 명시하고 실제 Canvas 표시 reader까지 대조한다. 선택된 A가 있는 그룹에 선택 B를 추가하는 입력을 G1에 넣는다. 범위상 지원하지 않을 경우 `docs/adr/design/237-origin-instance-slot-extension-breakdown.md:113`의 중단 기준에 따라 해당 선택 후보를 제외한다.
- **outcome: pending** — 사용자에게 보이는 선택 불일치가 새 삽입 계약으로 재현 가능하므로 수리 필요.

### l1 — LOW: ToggleButtonGroup의 그룹 값 writeback 설명이 코드와 다르다

- 문구: `docs/adr/237-origin-instance-slot-extension.md:15`와 `docs/adr/design/237-origin-instance-slot-extension-breakdown.md:38,74`는 그룹 값을 클릭 writeback 거울로 일반화하고 ToggleButtonGroup도 같은 구조라고 설명한다.
- 코드/재현 방법: `packages/shared/src/renderers/CollectionRenderers.tsx:738-750`의 onSelectionChange에 keys={node-1}을 전달하면 batch에는 자식 isSelected 변경만 들어가고 그룹 id에 대한 selectedKeys/value 갱신은 없다. Checkbox는 `packages/shared/src/renderers/FormRenderers.tsx:783-802`에서 그룹 value와 자식 값을 둘 다 쓴다.
- 왜 틀렸는가: 선택 초기값과 key 계약은 같지만 writeback 대상까지 같지는 않다. 문구를 "Checkbox/Radio는 그룹 value와 자식 상태, ToggleButton은 자식 상태만 갱신"으로 구분해야 한다.
- 영향: 이 문구만으로 production 선택 실패는 재현되지 않는다. ToggleButton의 정본과 key는 계속 자식 기반이므로 원래 h1의 해소 판정을 뒤집지 않는다.
- **outcome: deferred** — 문서 정밀화. 별도 라운드 재개나 승인 차단 사유로 삼지 않는다.
