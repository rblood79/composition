# ADR-240 Review Log

## Round 1 — 2026-09-24 (reviewer: codex)

병합 차단 문제 4건입니다. 정적 코드 추적으로 확인했으며, 브라우저·테스트 실행과 Phase 닫힘 판정은 하지 않았습니다. 파일 변경은 없습니다.

1. **[severity HIGH] [category: other] DialogFooter 채우기와 고정 `close` 보존·이관 계약이 충돌합니다.**

   - **근거:** [본문:86](/Users/admin/work/composition/docs/adr/240-named-regions-free-content-slots.md:86)은 DialogFooter를 slot host로 지정하지만, [본문:88](/Users/admin/work/composition/docs/adr/240-named-regions-free-content-slots.md:88)은 `close`를 영역 밖에 둡니다. 현재 `close`는 [OverlayComponents.ts:99](/Users/admin/work/composition/apps/builder/src/builder/factories/definitions/OverlayComponents.ts:99)의 DialogFooter 자식입니다. mode C는 [resolver:481](/Users/admin/work/composition/apps/builder/src/resolvers/canonical/index.ts:481)에서 자식을 통째로 교체합니다. 그런데 [이관 계약:70](/Users/admin/work/composition/docs/adr/design/240-named-regions-free-content-slots-breakdown.md:70)은 Description 경로만 옮깁니다.
   - **실패 시나리오:** 현재 구조를 유지하고 footer를 Button으로 채우면 기존 Close가 사라집니다. 반대로 Close를 영역 밖으로 옮기면, 기존 instance의 `…/DialogFooter/Close` override가 옛 경로에 남아 사용자 편집을 잃습니다. Description 전치만으로는 두 계약을 함께 만족할 수 없습니다.
   - **해결 방향:** 고정 Close와 교체 가능한 action 영역의 최종 트리를 확정하고, 이동하는 모든 노드의 override 경로를 BC 수식·G4에 포함해야 합니다.

2. **[severity HIGH] [category: other] 문서만 이관하면 영속 history의 Undo/Redo가 옛 Description 경로를 복원합니다.**

   - **근거:** [본문:89](/Users/admin/work/composition/docs/adr/240-named-regions-free-content-slots.md:89)와 [G4:113](/Users/admin/work/composition/docs/adr/240-named-regions-free-content-slots.md:113)은 instance 경로 전치와 재hydration만 다룹니다. 실제 synthetic 편집은 [inspectorActions.ts:929](/Users/admin/work/composition/apps/builder/src/builder/stores/inspectorActions.ts:929)에서 instance 전체의 교체 history를 기록합니다. [historyIndexedDB.ts:306](/Users/admin/work/composition/apps/builder/src/builder/stores/history/historyIndexedDB.ts:306)은 저장된 이벤트를 그대로 복원하고, [canonicalHistoryEvents.ts:322](/Users/admin/work/composition/apps/builder/src/builder/stores/history/canonicalHistoryEvents.ts:322)는 이벤트의 노드를 다시 삽입합니다.
   - **실패 시나리오:** 이관 전 Dialog Description을 A→B로 편집하고 저장 → 240 이관 후 B가 정상 표시 → Undo 실행 → 옛 경로를 가진 instance 스냅샷이 복원되어 A 대신 origin 기본 문구가 표시됩니다. Redo도 옛 경로를 되살립니다. 문서 재hydration Δ0 검사는 이 실패를 검출하지 못합니다.
   - **해결 방향:** 문서와 영속 history의 노드 스냅샷에 같은 경로 이관을 적용하거나, 호환되지 않는 history의 명시적인 무효화 정책을 정해야 합니다. 기존 history를 보유한 문서의 이관→Undo→Redo를 BC 조건에 포함해야 합니다.

3. **[severity HIGH] [category: evidence-missing] ADR-229의 synthetic 편집 경로는 mode C로 채운 노드를 편집하는 근거가 되지 않습니다.**

   - **근거:** [breakdown:77](/Users/admin/work/composition/docs/adr/design/240-named-regions-free-content-slots-breakdown.md:77)은 일반 노드 편집을 ADR-229 경로에 맡깁니다. 그러나 [inspectorActions.ts:493](/Users/admin/work/composition/apps/builder/src/builder/stores/inspectorActions.ts:493)은 편집을 바깥 instance의 `descendants[전체 경로]`에 기록합니다. Canvas의 [materializeOverrideChildren:772](/Users/admin/work/composition/apps/builder/src/adapters/canonical/canonicalRefResolution.ts:772)는 채움 배열 내부 노드의 props를 읽고, Preview의 [mode C 분기:485](/Users/admin/work/composition/apps/builder/src/resolvers/canonical/index.ts:485)도 바깥의 하위 경로 patch를 전달하지 않습니다.
   - **실패 시나리오:** `descendants.Content.children`에 Text `t`, 문구 A를 저장 → Properties에서 B로 변경 → `descendants["Content/t"]`에는 B가 기록되지만 두 해석기는 채움 배열의 A를 계속 읽습니다. 저장된 편집이 화면에 반영되지 않습니다.
   - **해결 방향:** 채운 노드의 편집을 mode C 배열 내부 canonical 노드에 직접 쓰거나, 두 해석기가 바깥 descendant patch를 적용하도록 소유권·우선순위를 명시해야 합니다. G2에서는 실제 Properties/Styles 쓰기가 만든 payload로 편집·저장·Undo/Redo를 검증해야 합니다.

4. **[severity MEDIUM] [category: other] Popover·Tooltip root의 저장 계약이 본문과 구현 상세에서 다릅니다.**

   - **근거:** [본문:84](/Users/admin/work/composition/docs/adr/240-named-regions-free-content-slots.md:84)는 채우기를 mode C로 통일하지만, [breakdown:66](/Users/admin/work/composition/docs/adr/design/240-named-regions-free-content-slots-breakdown.md:66)은 두 root를 “instance 자기 자식”으로 정의합니다. 현재 [resolver:214](/Users/admin/work/composition/apps/builder/src/resolvers/canonical/index.ts:214)는 `descendants`를 master의 **자식부터** 적용하고, [resolver:237](/Users/admin/work/composition/apps/builder/src/resolvers/canonical/index.ts:237)는 instance 자기 자식을 inherited 자식 뒤에 덧붙입니다.
   - **실패 시나리오:** 본문대로 root를 `descendants[""]` 또는 root ID의 mode C로 채우면 대응 대상이 없어 내용이 나타나지 않습니다. 구현 상세대로 `ref.children`에 넣으면 기존 Heading·Description 뒤에 추가됩니다. 두 방식은 교체·상속·Clear 결과가 서로 다릅니다.
   - **해결 방향:** 두 컴포넌트는 자기 자식 추가 방식의 예외인지, root 내용 교체 방식인지 결정해야 합니다. 선택한 방식에 맞춰 본문·UI·Clear·두 leg gate를 일치시켜야 합니다.
