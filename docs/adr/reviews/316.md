# ADR-316 Review Log

## Round 1 — 2026-11-24 (reviewer: codex)

**판정은 승인 보류다.** 닫힌 7개 태그와 기본값 div, 그룹의 사용자 이름, Nav 유지 방향은 타당하다. Decision 2와 G2에는 재현 가능한 문제가 있다.

- **인스턴스 이름**. 실제 Builder의 Calendar 월 목록 frame에서 Design의 HTML tag를 header로 골랐다. 필드와 해석된 값은 header이고 같은 화면의 제목은 Frame이었다. 같은 템플릿을 쓴 workspace → Preview 검증에서도 DOM은 HEADER, Layers 행은 Frame이었다. R3의 보류 근거가 깨진다. 두 이름 소비처가 선택한 위치의 유효 prop을 읽고 기존 이름·슬롯 우선순위를 보존해야 한다.
- **G2 판정**. 실행용 사본에서 클릭할 옵션 이름만 존재하지 않는 값으로 바꿨다. 실제 Chrome에서 클릭이 timeout 되고 직접 명령 경로를 탄 뒤에도 2번 항목과 전체 7/7이 통과했다. UI 선택 실패는 G2 실패로 기록하고 후속 소비처 검사는 독립적으로 집계해야 한다.

기존 frameElementType 테스트 2파일 5개 통과. 위 두 반례는 HEAD 34173e06f의 미커밋 구현에서 확인했다. HC2의 일곱 태그별 상자 좌표·크기 동등성은 UNVERIFIED다. 기존 live는 section의 h1 글꼴을 비교한다. G3 번들과 G4 사용자 확인은 미결이다. ADR-304의 main 추가 여부는 별도 결정이다.

## Round 2 — 2026-11-24 (reviewer: codex)

1차 m1과 m2의 원래 반례는 모두 해소됐다. frame 테스트 2파일 6개가 통과했다. 실제 Builder에서 Calendar 안 frame의 태그를 header로 고르면 Layers 행과 Design 제목은 header, Publish는 <header>였다. 정상 실행은 11/11과 종료 코드 0, 옵션을 없는 값으로 바꾼 사본은 2a만 실패해 10/11과 종료 코드 1이었다. 같은 내용의 일곱 태그 상자 실측은 Canvas와 Publish에서 각각 1920 × 48이었다. 스크립트는 양쪽 간 높이를 단언하며 너비는 각 소비자 내부의 일치만 단언한다.

**m3 (MEDIUM)**. 실제 Builder에서 Popover를 배치하고 Layers의 content 행을 클릭한 뒤 Design의 HTML tag에서 header를 골랐다. 같은 선택에서 Layers 행은 content를 유지했지만 Design 제목은 header가 됐다. Decision 2를 충족하려면 두 소비처가 사용자 이름과 슬롯 이름을 포함한 표시 이름 우선순위를 공유해야 한다.

1차 이슈 2건 fixed, 슬롯 이름 이슈 1건 pending. G3 번들과 G4 사용자 확인은 미결이다.

## 종결 — 2026-11-24 (실행자 선언)

m3 수리: Design 패널 제목이 Layers 와 같은 이름 순서 (사용자 이름 → slot 이름 → 태그 → 「Frame」) 를 `catalogRuntime/frameName.ts` 한 곳에서 읽는다. 근거 — 단위 테스트 「a slot frame keeps its slot name over its element」 (수정을 되돌리면 RED) · live 10 (Popover 의 content slot 을 패널에서 header 로 → 값 header, Layers 행 · 제목 둘 다 content) · live 전체 12/12, 종료 코드 0.
