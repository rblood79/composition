## Round 1 — 2026-11-10 (reviewer: codex)

판정: **설계 보완 필요 — HIGH 1 / MEDIUM 1 / pending 2**. HEAD `53dd1ff77`, Proposed 본문과 breakdown의 설계 리뷰다. 제품 구현 결함 판독이나 착수 승인이 아니다.

### h1 — HIGH: 동기 요청 채움과 프레임 예산의 실패 대안이 양립하지 않는다

- 위치: `docs/adr/307-staged-document-open-page-shells.md:127-129,166,178`; `docs/adr/design/307-staged-document-open-page-shells-breakdown.md:40,53,65`.
- 입력·상태 → 결과: idle 채움 중 축소하여 미채움 page 여러 장이 화면에 들어오거나, 미채움 page의 큰 subtree를 선택한다. Decision 3은 각 요청을 page 전체가 채워질 때까지 동기로 처리한다. 프레임당 page 개수 제한은 한 page의 비용을 제한하지 않는다. 한 page의 큰 Table/중첩 instance가 예산을 넘으면 요청이 반환되기 전까지 입력·그리기가 기다린다.
- R6/G4의 대안인 ‘root 직계 자식 단위’도 같은 동기 호출 안에서 전부 처리하면 양보가 아니다. 직계 자식 하나가 큰 subtree인 경우에도 비용 상한이 없다. 실제로 yield하면 public 상태 둘(틀/채워짐) 외에 비공개 준비 상태와 재개·취소·문서 변경 처리가 필요하다. 현행 `flatten`은 재귀 전체 순회 (`compositionRoot.ts:3132-3135`), `apply`는 `computeLayout`·rewrap까지 동기로 처리한다 (`:6640-6653`). 선례 `nodePictureWarmup.ts:181-185`는 deadline을 확인하며 작업을 재개하는 방식이므로 page 전체 동기 호출에 idle 예약만 붙여 같은 계약을 얻지는 못한다.
- 해결: 화면 진입은 시간 예산 내 비동기 준비 요청으로 분리하고, 준비 중 root 교체·revision 변경 시 폐기/재시작과 완료 publish 경계를 정한다. 명시적 page 전환·명령의 동기 완료를 유지한다면 그 경로의 지연 허용 조건을 HC4/G4와 맞춘다. 또는 Phase 0에서 요청 경로까지 포함한 최악 조각 비용을 먼저 검증하여 이 계약을 유지할 수 있는 입력 한계를 확정한다. 단일 큰 직계 자식과 여러 page의 동시 진입을 포함해야 한다.
- 검증 한계: 본문의 95.5 ms는 두 문서 열기 시간의 기울기이며 실제 `fillPage` 1회 지연 측정값이 아니다. 새로운 채움의 실제 long task·p95 초과는 **UNVERIFIED**. 이 이슈는 그 수치를 실측 지연으로 간주해서가 아니라 동기 완료와 yield 대안의 계약 충돌에 근거한다.

### m1 — MEDIUM: refreshRows의 journal은 전달 실패까지 틀로 복구하지 않는다

- 위치: `docs/adr/307-staged-document-open-page-shells.md:130,162`; `docs/adr/design/307-staged-document-open-page-shells-breakdown.md:40`.
- 입력·상태 → 결과: 채움의 apply가 성공한 뒤 Canvas 구독자/전달 단계가 실패한다. 제안한 선례를 그대로 따르면 예외를 호출자가 받아도 root의 새 record는 남는다. 이때 상태만 틀로 바꾸면 record·엔진·Canvas와 채움 상태가 서로 어긋나고, 상태를 유지하면 ‘실패하면 그 page만 틀로 되돌림’과 달라진다.
- 근거: `compositionRoot.ts:2524-2532`는 apply 구간만 journal로 원복하고 `finally`에서 journal을 제거한 뒤 deliver한다. `:6660-6685`의 deliver는 구독 오류를 모아 반환한다. `workspace.ts:602-610`은 이를 `CATALOG_ROWS_DELIVERY`로 던질 뿐 원복하지 않는다. 기존 runtime의 정상적인 publish 이후 오류 경계이며 기존 코드 자체의 결함이라는 판정이 아니다.
- 실행 확인: `.agent/runs/2026-11-11-review-adr307/failureBoundary.test.ts`에서 실제 CatalogWorkspace와 엔진을 사용했다. ① runtime row 변경 + Canvas 구독자 오류 → `CATALOG_ROWS_DELIVERY`, 변경 record 유지, revision 불변. ② 엔진 computeLayout 1회 오류 → record 원복, revision 불변. **2/2 PASS**. 로그: `.agent/runs/2026-11-11-review-adr307/artifacts/failure-boundary.log`.
- 해결: 채움의 실패를 prepare/apply와 publish 이후 전달/Canvas 반영으로 구분한다. 전자는 shell 복구, 후자는 filled 유지+consumer 재동기화/재시도 등 정책을 명시하거나, 전달 후까지 복구해야 한다면 이미 통지받은 consumer에 대한 보상 동기화까지 설계한다. G2에 그 정책을 검증할 오류 주입을 둔다.

### h1 — fixed (설계)

- 본문 `:127-131`에서 공개 미완료 상태에 일부 반영된 page를 포함하고, 한 region의 반영을 한 task에서 끝낸 뒤 다음 단위 사이에 양보하도록 바꿨다. 화면 진입은 큐 우선순위만 올리는 비동기 요청, page 내용이 필요한 사용자 동작은 남은 단위를 동기로 채우는 요청이다.
- 이어 갈 비공개 준비물 대신 현재 문서와 반영된 record로 다음 단위를 구하는 대안을 채택했다. 이전 리뷰의 비공개 준비 상태는 비동기 준비를 선택할 때의 필요사항이었으며, 반드시 그 구현만 쓰라는 요구가 아니다. 반영된 단위만 유지하는 현재 대안은 원래의 동기 완료/yield 충돌을 해소한다.
- HC4, R6, G0 ⑥(`:179`), G4(`:183`)가 실제 단위·최악 단위·page 동기 채움을 구분하고, 큰 단위는 행 창 등 추가 분할로 대응한다. 동기 경로의 절대 상한은 실측 후 사용자 결정으로 남아 있다. breakdown `:36,43,56,68,78`에서 계측·fillNext/fillPage·스케줄러·Canvas·하니스에 연결된다.
- 실제 성능은 UNVERIFIED다. ‘이미 반영한 단위가 빠지므로 일괄 빌드 비용 이하’라는 본문 `:131`의 예상은 반복 해석·computeLayout 비용 때문에 자동으로 성립하는 보장이 아니다. G0/G4의 실제 측정 결과로 판정하며, 이 문구를 Gate 통과 근거로 사용하지 않는다.
