### H1 — 이전 프레임의 unsafe paint를 버리면 효과 제거 뒤 잔상이 남는다 (open)

- 대상: `docs/adr/design/263-render-command-patch-execute-cost-breakdown.md:42`, `:47`; 본문 R1/HC4.
- Phase 3은 patch 결과의 hit-bounds damage와 **패치 후** `damageUnsafeElementIds` 검사만 재연결한다. 그러나 `subtreeCommandPatch.ts:575`는 이전 unsafe 표시를 지우고 `:609`에서 replacement의 표시만 넣는다. `getSubtreeDamageBounds`는 이전·이후 hit bounds만 합치며, `renderCommands.ts:1891`은 현재 Set만 검사한다.
- 입력 → 결과: x=100, 폭=80인 요소에 dx=-40의 바깥 그림자를 그리고 그림자를 제거한다. 실제 commit patch 실행 결과는 `applied:true, damageBounds:{x:100,y:100,width:80,height:40}`, unsafe Set은 빈 집합, damage sequence 생성은 성공이다. 이전 그림자의 중심 x=60은 renderer가 비우는 영역 밖이다 (`SkiaRenderer.ts:674`의 safety 확장으로도 포함되지 않음). 이 배선대로면 기존 그림자가 남는다.
- 해결 방향: patch **전후** unsafe 여부를 결과에 보존하고, snapshot 이후 아직 그리지 않은 변경들을 full-required로 누적한다. 이전 paint bounds를 정확히 소유하지 않는 효과 제거·삭제·transform 원복은 full로 보낸다. G3에 safe→unsafe뿐 아니라 unsafe→safe와 unsafe 요소 삭제를 넣는다.
- 증거: 로컬 `probe.test.ts` 첫 테스트는 실제 stream build/commit patch/sequence 함수를 호출했다. 실제 GPU 픽셀 잔상 촬영은 UNVERIFIED.

### H2 — full 무효화 뒤 damage 무효화가 오면 full 요구가 사라진다 (open)

- 대상: `docs/adr/design/263-render-command-patch-execute-cost-breakdown.md:43`.
- breakdown은 rebound는 인자 없는 full, patch는 damage로 보내면 충분하다고 전제한다. 현재 `SkiaRenderer.ts:349`는 full 요청을 `pendingDamage=null`로 표현하고, 뒤따르는 damage 요청은 `:357`에서 이를 작은 rect로 덮는다. `canRenderDamage` (`:635`)에는 full 요청이 남아 있었는지 검사하는 조건이 없다.
- 입력 → 결과: 기존 ping-pong snapshot이 준비된 상태에서 장면 rebind/full 요청 → 다음 rAF 전에 작은 paint patch/damage 요청. 실제 renderer 메서드 프로브에서 `pendingDamage={x:100,y:100,width:80,height:40}`, `canRenderDamage=true`가 됐다. 전체 장면을 바꾼 첫 요청의 영역은 복원되지 않는다. 이미지 로드·root 교체·거부된 splice 뒤 같은 프레임의 후속 편집도 이 순서를 만들 수 있다.
- 해결 방향: clean/damage/full을 구분하고 full 요청은 실제 full 재기록이 끝날 때까지 우선하게 한다. full→damage, damage→full, full→여러 damage 순서를 G3에 고정한다.
- 증거: constructor/GPU 부팅 없이 실제 prototype 메서드와 snapshot 준비 상태로 순서를 실행했다. 실제 Builder 이벤트 타이밍과 픽셀은 UNVERIFIED.

### M1 — 서브트리 점프만으로 가시 요소 수 비례 계약을 충족할 수 없다 (open)

- 대상: `docs/adr/design/263-render-command-patch-execute-cost-breakdown.md:36`, `docs/adr/263-render-command-patch-execute-cost.md:44`, `:127`.
- 제안은 offscreen ELEMENT_BEGIN에서 그 서브트리 끝으로 점프한다. 화면과 교차하는 큰 부모 안에 leaf 형제가 N개면, 다음 형제가 보이는지 알기 위해 각 BEGIN을 여전히 읽어야 한다. 이는 줌·cleanup full 재기록의 최소 O(N) 비용이다.
- 입력 → 결과: 같은 viewport에서 가시 leaf 1개를 유지하고 나머지를 아래에 배치했다. 실제 command stream에 제안된 점프 규칙을 적용한 시뮬레이션은 N=600에서 605회, N=5,000에서 5,005회 방문했다. 가시 수는 두 경우 모두 1이다. G2/HC3의 약속과 맞지 않는다.
- 해결 방향: 가시 후보와 조상 context를 공간 질의로 선택하는 경로까지 포함하거나, HC3/G2를 실제로 보장할 수 있는 “컬링된 subtree 내부 명령 방문 생략”으로 한정한다. hard constraint 축소는 기존 사용자 목표와 구분해 판단한다.
- 증거: 현행 stream 생성 + 제안 알고리즘 시뮬레이션. 아직 구현되지 않은 Phase 2의 실제 executor 성능으로 주장하지 않는다.

### M2 — 새 카운트를 --update만 하면 회귀를 차단하지 않는다 (open)

- 대상: `docs/adr/design/263-render-command-patch-execute-cost-breakdown.md:32`, `:65`; 본문 HC5/G0/G5.
- `perf-ratchet-gate.mjs:249`의 `applyUpdate`는 새 지표를 B에 넣는다. 값 0인 새 지표는 `:206`의 조건 때문에 등록하지도 않는다. `:223`의 `decide`는 A 초과가 없으면 통과하므로, G0에서 2회 동일한 값을 관찰했다는 것만으로 차단 지표가 되지는 않는다.
- 입력 → 결과: 기존 A 지표는 동일하게 두고 새 방문 수 100, Proxy 접근 0으로 `--update`와 같은 함수를 실행했다. 방문 수는 B에 등록되고 Proxy 지표는 빠졌다. 이후 방문 수 1,000, Proxy 접근 5,000으로 회귀시켜도 `overA:[], overB:[...], newKeys:[...], decision:"pass"`였다.
- 해결 방향: 두 번 동일성을 확인한 새 카운트를 기존 기준을 보존하며 A로 등록하는 절차와 0 상한의 명시 등록을 설계한다. G1/G2/G4 원복 RED는 unit 실패와 별도로 **실제 pre-push 판정 함수의 block**을 확인해야 한다.
- 증거: 현행 `judge → applyUpdate → judge → decide` 직접 실행. 결과는 로컬 `ratchet-probe.json`에 보존했다.

### LOW deferred — offset 컨테이너의 자손

- 대상: breakdown §3:40 · §4:53의 offset 후보 보강과 G2 offset fixture.
- 실제 `buildDamageRenderCommandSequence`는 후보의 **조상**을 연결하지만 컨테이너 후보의 모든 **자손**을 자동 포함하지 않는다 (`renderCommands.ts:1961`의 relevantChildren만 재귀).
- 명령 소비 프로브: body 안 group(x=0)과 leaf(x=10), group에 sibling offset dx=1000, viewport x=1000..1200. 정적 bounds 질의의 후보 body에 group만 보강하면 현행 선형 executor의 box draw 1회가 compact executor에서는 0회가 됐다. renderBox는 spy로 대체했으며 실제 executor의 분기·offset·컬링과 sequence 함수는 실행했다.
- 다만 **현재 Builder production 결함으로 판정하지 않는다**. `CatalogCanvas.tsx` showDrag는 drag offset 설정 뒤 scene.refresh로 top-layer를 다시 만들고 (`:1236`), 이 상태는 `renderCommands.ts:1426`에서 unsafe에 들어간다. 실제 stream build 프로브에서도 unsafe=[group,leaf], compact sequence=null로 full fallback했다. 별도 프로브가 만든 unsafe 없는 sibling-offset 상태를 현재 Builder drag 흐름과 동일하다고 주장하지 않는다.
- 구현 시 offset을 상속하는 자손까지 보강하거나 offset 컨테이너는 full fallback한다. 기존 global unsafe guard를 후보 한정 검사로 축소하지 않는다. G2/G3 offset fixture에 컨테이너+자손을 포함하는 권고이며, production 재현 없는 coverage 항목이므로 LOW deferred다. Round 1을 다시 여는 근거로 쓰지 않는다.
