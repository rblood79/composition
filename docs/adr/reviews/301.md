1. **HIGH h1 — 요소 삭제와 재생성 동일 조건이 양립하지 않는다.** ADR Decision 4 (`301-code-view-library-instance-expansion.md:92,95`), breakdown:91. template 요소 전체를 지우면 편집본에는 그 요소가 없지만, 설계가 지시한 enabled:false patch의 재생성본에는 `{false && <X/>}`가 남는다. 기존 `apps/builder/src/builder/catalogRuntime/codeViewEdit.ts:3504-3525`는 자식 수와 visibleState를 비교하므로 `notInCode`로 거절한다. slot 소유 노드의 removeTargets와 구분되는 template 자리(예: OverlayArrow) 삭제로 재현 가능하다. 자리 키의 deterministic 여부로는 해결되지 않는다. 해결: 삭제 입력을 숨김 표현으로 정규화하는 명시적 계약과 비교 단계를 설계하거나, 삭제 대신 false wrapper 편집만 지원하도록 사용자 결정·G2를 맞춰야 한다. 단순히 재생성 검사를 우회해서는 안 된다.

2. **HIGH h2 — 기존 patch가 있는 바인딩 자리는 root prop 쓰기로 편집할 수 없다.** ADR Decision 4 (`301-code-view-library-instance-expansion.md:90`), R2 및 G2. Popover root props.size=L이고 overlay 자리에 기존 descendant props.size=S patch가 있으면 생성 값은 S다. 이를 M으로 편집할 때 설계대로 root props.size=M만 쓰면 기존 patch가 계속 S로 덮어써 Apply가 거절된다. `packages/shared/src/catalog/resolution/resolver.ts:2241-2243`의 바인딩보다 `2261-2269`의 patch가 뒤이며, 기존 `apps/builder/src/builder/catalogRuntime/codeViewEdit.ts:1641-1687`의 planOverrides는 이 patch를 생성할 수 있다. 해결: template 바인딩 유무 외에 유효 값의 작성 주체와 우선순위를 판정하고, 기존 patch 수정/해제 정책을 확정해야 한다. root 값과 patch가 동시에 있는 문서에서 편집·제거·Undo 및 패널 동일성 반례를 G2에 넣는다.

3. **MEDIUM m3 — slot 클래스와 CSS 경로가 서로 다르다.** ADR Decision 1 (`301-code-view-library-instance-expansion.md:86`), breakdown의 styles 무변경 행 및 예제:78,86. Popover content frame에 시각 patch를 작성하면 기존 `packages/shared/src/codeView/files/styles.ts:679-688`은 codeViewAddressKey를 사용해 `.popover .frame`을 출력한다. 반면 제안된 JSX는 `<div className="content">`다. `packages/shared/src/codeView/files/overrides.ts:127-142`는 이 차이를 명시적으로 구분한다(codeViewAddressKey=frame, codeViewSlotKey=content). 따라서 CSS와 JSX가 같은 자리를 가리킨다는 주장이 성립하지 않는다. 해결: slot 표시 이름과 스타일 identity를 구분해 frame 클래스를 함께 유지하거나, CSS emit/read와 위치 anchor를 같은 규칙으로 변경한다. content frame patch의 CSS selector가 생성 JSX에 매칭하고 CSS 편집이 같은 주소로 왕복하는 조건을 gate로 고정한다.
