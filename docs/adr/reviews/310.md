## 판정

**보완 필요 — HIGH 2건, pending 2건.** 검토 기준은 main `e7e9fc035`와 작업 시작 시 미커밋인 ADR-310 본문·breakdown이다. 반복 표시를 항목에 두고 Graph를 문서 정본으로 유지하는 방향 자체는 성립하지만, 현재 문서가 유지한다고 한 runtime 경로로는 아래 두 사용자 동작을 만족하지 못한다. 제품 코드 변경·ADR 상태 승격·commit/push는 하지 않았다.

### H1. 고정된 첫 100행과 loadMore만으로는 마지막 행에 도달하지 못한다

- **문서 위치:** `docs/adr/310-collection-item-repeat-marker.md:131` (Decision 10), `:180` (G5). 지금의 행 창 100과 더 불러오기로 처리한다고 명시하면서 마지막 행 도달을 요구한다.
- **반례:** ListBox에 페이지 1의 100행을 표시하고 페이지 2의 1행을 `loadMore`한다. 서버 요청은 `/users` → `/users?page=2`, 세션 데이터는 **101행**이지만 RAC Preview DOM의 option은 **100개**, `Person101`은 없다. 기존 Preview session·workspace·channel·resolver·RAC를 사용하는 jsdom 통합 probe로 실행했다.
- **원인:** `catalogPreviewSession.ts:1523-1529`는 기존 행 뒤에 새 행을 붙인다. 그러나 `:1688`은 기본 limit으로 `catalogBoundRows`를 호출하며, `dataBinding.ts:179-183`, `:486-488` → `resolveCollectionItems.ts:102-106`은 매번 `[0, 100)`만 전달한다. 현재 세션 경로에는 다음 100개를 보여 주는 offset 또는 limit 확장이 없다. 별도로 존재하는 `CollectionWindow` 계산기는 이 호출에 연결돼 있지 않다.
- **영향:** 101행 이상인 연결 목록은 끝까지 불러와도 뒤쪽 행을 볼 수 없다. 이는 단순 미측정 항목이 아니라 Decision 10의 수단과 G5의 결과가 양립하지 않는 실행 반례다.
- **해결 방향:** Virtualizer 제외 결정은 유지할 수 있다. 대신 명시적 페이지 이동/이동 창/불러온 행까지 DOM 투영 확대 중 한 방식을 결정하고, Builder 표본·서버 cursor·DOM 표시 범위를 구분한다. G5에는 100행 경계를 넘는 실제 DOM 도달 조건을 넣고, 선택한 방식에 맞춰 G4의 DOM 규모·성능 조건을 조정한다.

### H2. 항목 자체 binding을 허용하면서 owner 기반 로딩 경로를 그대로 유지할 수 없다

- **문서 위치:** `docs/adr/310-collection-item-repeat-marker.md:123` (Decision 2), `:196` (로딩·더 불러오기·서버 정렬·Quick Connect 무변경 주장), `docs/adr/design/310-collection-item-repeat-marker-breakdown.md:129` (두 번째 데이터).
- **반례:** ListBox owner는 원격 A, 두 번째 반복 항목은 원격 B에 연결하고 두 소스 모두 다음 페이지를 가진다. 현재 `catalogLoadMoreItem`에 그 consumer/Graph 입력을 주면 sentinel은 **1개**, callback 호출은 **A 한 번**, B는 호출되지 않는다. owner에 binding 없이 항목/section의 자체 binding만 있는 경우에도 이 owner 조회 경로는 항목들을 탐색하지 않는다.
- **원인:** `delegatedDom.runtime.ts:374-386`의 `boundOwnerOf`는 현재 목록 또는 picker만 찾는다. `:450-464`는 그 binding 하나에서 collectionId를 얻어 `__load-more` 하나를 만들며, 실제 ListBox caller `:2058-2064`도 목록 node만 넘긴다. `collectionEntries`가 여러 반복 구간을 판정하더라도 이 런타임 소비자를 그대로 두면 두 번째 구간의 로딩을 전달하지 못한다.
- **영향:** A와 B의 첫 페이지가 표시되는 G5 예제는 통과할 수 있어도 B의 다음 페이지와 로딩 상태를 소비할 수 없다. 단일 owner binding을 유지하는 것은 가능하지만, owner가 모든 구간의 데이터 소유자를 대표한다는 기존 가정은 유지할 수 없다.
- **해결 방향:** 저장 binding을 일괄 이동할 필요는 없다. 반복 구간별 실제 binding/source와 로딩 상태·cursor를 조회하고, 각 구간의 sentinel이 해당 source를 호출하도록 runtime 범위를 명시한다. 서로 다른 두 원격 소스의 페이지 진행을 분리해 확인한다. 선택·삭제·정렬도 동일한 source 구분으로 감사하되, 이번 probe가 이 동작들의 실패까지 증명한 것으로 확대하지 않는다.
- **증거의 한계:** H2는 새 repeat 모델 전체를 구현한 테스트가 아니라, ADR이 보존한다고 한 **현재 production helper**에 제안된 다중 소스 입력을 준 함수 실행 반례다. 새 모델의 저장/로드·전체 DOM 통합은 UNVERIFIED다.

## 신규 차단 이슈

### H1. owner별 원격 페이지와 collection별 응답 저장이 충돌한다

- **문서 위치:** `docs/adr/310-collection-item-repeat-marker.md:136-138`; `docs/adr/design/310-collection-item-repeat-marker-breakdown.md:168`, `:190`, `:214`.
- **왜 문제인가:** `page`는 owner마다 두고 원격에서는 해당 페이지만 받도록 새로 결정했지만, 불러온 항목·cursor는 collection별로 유지하며 새 상태는 표시 창뿐이라고 설명한다. 서로 다른 목록은 같은 collection을 사용할 수 있으므로 owner별 현재 페이지 숫자만 분리해서는 각 목록의 행을 유지할 수 없다. 한 목록 안의 반복 구간을 하나로 제한하는 조건도 이 경우를 막지 않는다.
- **입력 → 잘못된 결과:** 같은 원격 Users를 읽는 목록 A/B를 두고 A는 1페이지, B는 3페이지를 선택한다. 현재 collection별 응답 저장 경로에 B의 41–60번째 행이 들어오면 A의 1–20번째 행도 교체된다. A의 페이지 표시는 1인데 행은 B의 페이지가 되거나, 이후 표시 창을 다시 자르면 빈 목록이 될 수 있다. `more` 목록과 `pages` 목록이 같은 source를 쓰는 경우에도 페이지 응답 교체가 다른 목록이 불러온 행을 지운다.
- **현재 코드 근거:** `catalogPreviewSession.ts:475`의 `reloadedItems`, `:492-504`의 `loadArguments`·`loadSequence`·`loadControllers`·`loadTotals`가 모두 collection id로 저장된다. `:1215-1221`은 같은 collection의 새 요청이 이전 요청을 취소하며, `:1452-1463`의 `showLoaded`는 collection 행을 교체하고 그 collection을 읽는 모든 root를 갱신한다. `:854-861`의 `itemSources`도 모든 owner에 동일한 응답 배열을 제공한다.
- **실행 근거:** 기존 workspace → Preview channel → session → resolver → RAC DOM 하니스로 같은 Users에 ListBox 두 개를 연결했다. 첫 응답은 `u1..u20`, 다음 응답은 `u41..u60`으로 제공하고 public `reload("users")`를 호출했다. 결과는 **두 목록 모두 `u41..u60`**이었다. 1 test PASS는 이 공유 상태를 확인한 characterization 결과다.
- **증거의 범위:** 새 `rowDisplay`/Pagination/page 요청 인자는 구현하지 않았다. 이 probe는 현재의 collection별 응답 저장 경로가 서로 다른 페이지를 보존하지 못함을 실행으로 확인한다. 이 경로를 유지하면서 owner별 페이지를 추가하면 계약을 만족하지 못한다는 것이 설계 판정이며, 미구현 페이지 UI의 실제 실패를 검증했다고 주장하지 않는다.
- **해결 방향:** collection은 데이터 정체성으로 유지하되, 원격 조회의 요청 인자·응답 페이지·cursor 이력·loading·total·취소/순서 상태를 목록의 실행 인스턴스/반복 구간별 조회 단위로 둔다. 동일 요청의 데이터 캐시는 공유할 수 있지만 독립적인 page 선택이 다른 목록의 응답이나 요청을 덮어쓰면 안 된다. G7은 같은 collection을 읽는 A 1페이지/B 3페이지 동시 표시와 pages/more 공존을 확인한다. 기존 데이터 편집 명령은 collection/key 정체성을 보존하도록 별도로 연결한다. 세 표시 방식 지원 결정은 유지한다.
