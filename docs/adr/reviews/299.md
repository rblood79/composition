### H1 — 서식 경계가 변수 템플릿을 쪼개면 참조와 치환이 사라진다

- 위치: `docs/adr/299-text-range-formatting-runs.md:110` (Decision 1: run마다 변수 수집·해석), `docs/adr/design/299-text-range-formatting-breakdown.md:93` (`applyMarks`는 임의 UTF-16 구간을 쪼갬).
- 입력·상태 → 잘못된 결과: `Hello {{ userName }}!`, 변수 `userName = guest`에서 이름 부분만 굵게 하면 `Hello {{ ` / `userName`(bold) / ` }}!`의 세 run이 된다. 명시한 run별 해석은 이를 `Hello {{ userName }}!` 그대로 표시하고 참조 목록을 `[]`로 만든다. 서식만 바꿨는데 값 표시·변수 변경 반응·이름 변경 참조 추적이 깨진다. 같은 mark 병합은 서로 다른 mark로 나뉜 토큰을 복원하지 못한다.
- 확인: 현재 실제 공용 `resolveStateTemplateProps`와 `collectPropsStateRefs`로 실행했다. 문자열 입력은 `Hello guest!`, refs `[userName]`; 분할 run 입력은 원문, refs `[]`. 근거 `packages/shared/src/state/template.ts:65`, `packages/shared/src/state/template.ts:98`, `packages/shared/src/state/stateDependencies.ts:28`, `packages/shared/src/catalog/runtime/variableReferences.ts:216`. 실행 결과 `.agent/runs/2026-11-02-adr299-review/template-split.json`.
- 해결 방향: 템플릿을 논리 문자열 전체에서 먼저 토큰화하고 run 경계를 가로질러 참조·치환·rename할 계약을 정하거나, 템플릿 토큰을 편집기의 원자 단위로 정해 서식 경계가 내부에 생기지 않게 한다. 치환 결과 길이가 달라질 때 mark를 어느 구간에 적용할지도 정한다. `{{ }}` 내부 일부에 mark를 적용하는 왕복·변수 rename fixture를 G3/G4에 넣는다.

### H2 — 부모의 text-decoration을 span의 mark로 덮을 수 없다

- 위치: `docs/adr/299-text-range-formatting-runs.md:117` (Decision 2: 노드 스타일은 바깥 요소, span은 mark만), 같은 문서 `:109`~`:110` (구간 값이 노드 값에 우선).
- 입력·상태 → 잘못된 결과: 노드가 `textDecoration: underline`, `color: red`이고 일부 구간이 `textDecoration: none`이면 DOM은 `<Text style=underline><span style=none>…</span></Text>`가 된다. 부모 밑줄은 해당 구간에도 남는다. Canvas가 실효 run의 장식선만 그리면 DOM과 다르다. 같은 부모 아래 blue 구간에 underline을 주어도 부모의 red 밑줄이 함께 남을 수 있다.
- 확인: 현재 DOM은 노드 요소에 장식선을 쓴다 (`packages/shared/src/catalog/runtime/domBinding.runtime.ts:705`). CSS의 장식선은 일반 상속과 달리 자식으로 전파되며 자식 `none`으로 지울 수 없다. [CSS Text Decoration Level 3 §2](https://www.w3.org/TR/css-text-decor-3/#line-decoration)의 전파 규칙 및 색상 예제 확인. 새 run DOM의 브라우저 픽셀 재현은 미실행이다.
- 해결 방향: rich text에서는 바깥 요소의 장식선을 억제하고 mark 없는 구간까지 포함한 각 span에 실효 장식선·색을 적용한다. 노드/상위 컴포넌트 장식선의 전파 경계도 함께 정한다. 코드 보기 투영·PM 편집 DOM도 같은 의미를 보존해야 한다. G2에 부모 underline + 일부 none/색 변경 fixture를 둔다. inline-block으로 격리하면 run 안 줄바꿈 계약이 깨지므로 그대로 대안이 되지 않는다.

### H3 — blur 커밋을 유지하면 Design 패널에서 선택 구간을 바꿀 수 없다

- 위치: `docs/adr/299-text-range-formatting-runs.md:127` (기존 커밋 유지), `:133` (편집 중 패널 쓰기는 PM transaction), breakdown `:99`~`:110` (입력 층 계약).
- 입력·상태 → 잘못된 결과: 편집기에서 단어 선택 → Typography의 Font Size 입력 또는 색상 팝오버 클릭 → 편집기에 blur → 기존 `commit()`이 `save()` 후 `session.endTextEdit()` → 패널이 값을 쓰는 시점에는 편집 세션/PM view가 사라진다. Decision 5의 비편집 분기로 들어가 선택 단어 대신 노드 전체에 적용하거나, 보관하지 않은 PM 선택 때문에 쓰지 못한다. 툴바를 제외한 설계라 색·크기 서식의 핵심 입력 경로다.
- 확인: 현재 `CatalogTextEditor.tsx:222`~`:228`, `:376`은 blur에 편집 세션을 끝낸다. `catalogRuntime/session.ts:238`은 textEditing을 지운다. `TypographySection.tsx:181` 이후 Font Size 입력과 PropertyColor는 별도 focus 표면이다. 기존 동작과 제안된 유지 조건의 정적 충돌을 확인했으며, 미구현 PM/패널 결합을 실브라우저로 재현한 것은 아니다.
