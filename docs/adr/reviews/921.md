### 근본 반론 (hate)

- **load-bearing 가정**: renderer-neutral scene 의 편익은 두 번째 consumer (native renderer / read-only SDK / Rust compiler) 가 존재할 때 실현된다 (`ADR:28` "native renderer나 read-only SDK를 추가하려면", `ADR:185-186` "contract 의 소비 후보이지 자동 구현 범위가 아니다 … 미도입이 정상", Consequences Negative "native/SDK가 실제로 필요하지 않으면 다중 backend의 제품 이점은 당장 나타나지 않는다").
- **root** (공격 축: **조건부 편익** + analogy≠isomorphism): 편익의 실현 조건을 ADR 스스로 선택적 (G-R / G-N, 별도 ADR) 이라 선언했는데 비용 — Phase 0~~3 · G0~~G6 · `RenderSceneSnapshot` schema/conformance fixture 지속 관리 — 는 지금 전부 지불한다. OpenPencil 의 derived scene + shared backend 는 web + native **두 host** 가 있어 성립하는 구조이고 (`ADR:33-37`), composition 은 CanvasKit host 하나 + HC11 이 CanvasKit 교체를 금지한 DOM Preview/Publish 다. 두 번째 consumer 없이 남는 단독 편익은 R1 (scene truth 3개 단일화) 뿐인데, 그 손실의 실측 근거가 없다 — `scene/buildSceneSnapshot.ts` · `renderers/rendererInput.ts` · `skia/skiaFramePipeline.ts` 의 2026-05 이후 fix/revert 커밋 8건 (`git log --since=2026-05-01`) 중 scene truth 발산에 기인한 것은 0건 (page drag 복원 · 조상 clip hit · fills 파이프라인 복원 · ADR-172/173/144 revert).
- **first nail**: 제품 결정 1건 — "native/SDK 또는 Rust compile 의 확정 요구가 로드맵에 있는가?" (코드 0, 답 1개) + 위 30분 grep (완료, 0/8). 요구가 없으면 Decision 은 대안 A + R1 국소 수리 (snapshot/rendererInput 중복 필드 제거) 로 축소 가능하다. 비용: < 1h vs 프로그램 4 phase · 7 gate.
- **판정**: 어느 Gate 도 진입 조건으로 묻지 않는다 (G-R/G-N 은 확장 조건, G0 는 baseline freeze 만 — `ADR:219`) → 이슈 **m1 (MEDIUM, evidence-missing, deferred → Phase 0 진입 조건)**. root 가 전제 수준이므로 **재질문하지 않는다** (round 1 승인 기록 = 전제 확정, CLAUDE.md §전제·관점 종결 계약) — 재개는 사용자 재제기 경로.

### 렌즈 대조 (prism) — HIGH 6건 → 실행

| 렌즈 (failure mode)   | 판정    | load-bearing 이유                                                                                                                                                                                                                                                                                 |
| --------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 정합성 / dual SSOT    | pass    | HC1·HC2 + G3 가 canonical resolver 를 그대로 두고 projected ID 누출 0 을 게이트로 잰다 (`ADR:57-60`, `ADR:223`)                                                                                                                                                                                   |
| 비용 / 성능           | unclear | G4 의 +5% p95 는 목표이지 근거가 아니다 — snapshot compile 의 프레임 비용 측정치가 아직 없고 Phase 0 baseline 은 현행 경로만 잰다 (`breakdown:229-236`)                                                                                                                                           |
| 측정 무결성 (oracle)  | fail    | G2 "non-text pixel diff 0" 의 oracle 은 현행 CanvasKit 자신인데, 같은 입력을 2회 실행해 checksum 이 재현되는지 검증하는 항목이 ADR·breakdown 어디에도 없다 (grep 재현/repeat/determin = 0건). 재현되지 않으면 G2 는 통과 불가능하거나 설계자가 그린 mask 로 통과한다 (measurement-validity #3·#5) |
| 되돌림 / rollout      | pass    | 단일 rollout flag (featureFlags registry) + current oracle 복귀 (G6, `breakdown §8`)                                                                                                                                                                                                              |
| 편익 실현 ("왜 지금") | fail    | 편익이 조건부 후속에만 실현 (`ADR:185-186`) + R1 단독 손실 실측 0/8 (위 hate)                                                                                                                                                                                                                     |

- **수렴**: **불일치** — 구조·되돌림 렌즈 (pass) vs 편익·측정 렌즈 (fail) · 비용 (unclear). 구조는 건전하고 되돌릴 수 있지만, 왜 지금 하는지와 통과 판정이 가능한지가 미증명.
- **해결 질문 1**: **"native/SDK 또는 Rust compile 의 확정 요구가 제품 로드맵에 있는가?"** — 예 → Phase 0 착수 (단, m2 oracle 재현성 검사를 G0 에 추가) / 아니오 → 대안 A + R1 국소 수리로 축소, owner = 사용자. hate 의 first nail 과 같은 질문으로 수렴.
