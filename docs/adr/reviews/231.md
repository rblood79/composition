# ADR-231 Review Log

## Round 1 — 2026-09-22 (reviewer: codex)

## 판정: 수정 후 재검토 필요

HEAD `a74700961`의 ADR-231 Proposed 초안과 breakdown을 현재 코드에 대조했다. HIGH 2건, MEDIUM 1건이며 모두 pending이다. 제품 구현의 결함 확정이 아니라 제안된 설계와 수용 조건의 충돌 판정이다.

### H1 — 내용 높이와 breakpoint 높이 불변의 충돌

본문 36–38행은 전환 시 frame height Δ0, origin의 activeBreakpoint 표시, 내용 전체 노출을 동시에 요구한다. breakdown 35행은 실제 발행 body 높이로 frame을 만든다. 현재 `useLayoutPublisher.ts:150-190`은 origin의 responsive 값을 해소해 레이아웃 시그니처에 넣고, `layoutCache.ts:255-261`은 그 시그니처로 캐시를 검증한다.

반례: origin 하나의 mobile height 또는 paddingTop을 기존 내용 높이보다 충분히 크게 저장한 뒤 desktop↔mobile을 전환한다. 제안대로라면 내용과 frame 높이가 달라진다. 따라서 breakdown 38행의 “입력 상수화 → breakpoint 캐시 miss 0”도 일반적으로 성립하지 않는다. 기존 responsive 해소를 제거하면 보존하기로 한 저작 채널을 깨뜨린다.

수정 방향: “breakpoint viewport 치수에 직접 종속되지 않음”으로 중립의 의미를 한정하고 origin의 반응형 내용 변화에 따른 frame 높이 변화는 허용할지 결정한다. 전환 시 높이 불변이 반드시 필요하다면 별도 높이 산정 정책이 필요하다. G2에는 미리 저장한 geometry override를 가진 origin의 왕복 전환을 넣는다.

### H2 — auto 배치의 수평 충돌이 해결되지 않음

breakdown 45행은 pageSizes 전달과 Components 위치 교체 제외를 해결책으로 제안한다. 그러나 `elements.ts:642-663`은 auto 열 간격을 breakpoint pageWidth로 고정하고 pageSizes에서는 높이만 읽는다.

코드 산술 반례: Components가 첫 칸 x=0인 상태에서 mobile 최초 진입, pageWidth=390, gap=80, availableWidth=1000이면 열 수는 floor(1080/470)=2다. 사용자 페이지는 x=470에 배치된다. Components의 [0,1920]과 사용자 페이지의 [470,860]이 겹친다. Components 좌표를 0으로 보존해도 동일하며 pageSizes 전달도 x 식에 영향을 주지 않는다. 이는 실제 배치 함수의 정적 계산이고 브라우저 실측은 아니다.

수정 방향: Components가 차지하는 영역을 예약해 사용자 페이지를 배치하는 정책을 명시한다. 고정 Components 위치, 기존 사용자 좌표 보존, 무겹침이 충돌할 때의 우선순위도 필요하다. auto 2열 이상 첫 진입과 기존 스냅샷 복원을 검증한다.

### M1 — authored body height 예외가 없음

본문 40행은 기존 body Size 우선을 보장하면서 38행과 G1은 스크롤 0을 무조건 요구한다. breakdown 37–40행은 bodyViewportHeight 미설정과 body layout height 발행만으로 해결된다고 한다.

반례: 기존 Components body가 height:1080, overflow:auto이고 자식 extent가 3000인 문서. `fullTreeLayout.ts:2884-2899`는 authored height를 보존하므로 bodyViewportHeight 미설정으로 height가 auto가 되지 않는다. Step 5 보고값도 제한된 body 높이이며 GAP 4는 계속 양의 scroll 범위를 계산한다. frame의 max(authored height, published body height)도 내용 extent를 얻지 못한다.

수정 방향: 사용자 고정 height/maxHeight/overflow를 예외로 인정하고 gate를 제한하거나, canonical 저작값 보존과 별개인 Components 전용 레이아웃 투영 정책을 명시한다. 고정 높이 보존과 모든 내용 노출 중 우선 계약을 먼저 정한다.

### 검증 범위와 한계

읽은 경로: breakpoint 전환 → responsive layout 해소 → 캐시 입력 → body layout/scroll extent → frame 크기 → 위치 스냅샷과 Δ reflow, viewport store. 현 HEAD와 문서의 기준 SHA는 일치한다. 코드·수식 기반 설계 리뷰만 수행했고 Builder live, 엔진 fixture 실행, G0–G4 성능/BC 통과는 주장하지 않는다. 제품 코드, ADR 본문과 상태, 기존 dirty 파일은 수정하지 않았다. 외부 도구 관례는 이번 판정의 근거로 사용하지 않았다.

### H1 — 시스템 열의 높이 변화가 사용자 페이지로 전파된다

breakdown 47행은 Components 발행 높이 변화에도 기존 Δ reflow를 변경하지 않겠다고 명시한다. 반면 본문 Negative 절은 왼쪽 시스템 열로 분리하면 사용자 페이지를 밀지 않아 첫 로드 reflow가 소멸한다고 주장한다.

현재 `computePageFrameReflow`는 vertical/auto에서 다른 페이지의 y가 더 크면 x와 무관하게 이동시킨다 (`pageFrameReflow.ts:53-66`). 호출자도 모든 페이지 위치를 그대로 넘기고 이동 결과를 적용한다 (`BuilderCanvas.tsx:695-710`). 따라서 새 열 위치만으로 전파가 차단되지 않는다.

실행 반증: 저장소의 실제 `normalizePageLayoutDirection`와 `computePageFrameReflow` 소스를 Node 24 `stripTypeScriptTypes`로 실행했다. 동작 본문은 변경하지 않았고 의존 import만 두 순수 함수 연결로 대체했다. 입력은 Components=(-2000,0), Home=(0,0), P2=(0,1160), Components 크기 1920×1080 → 1920×3000. 결과는 vertical과 auto 모두 `[{pageId:"p2",x:0,y:3080}]`이다. 의도한 사용자 페이지 이동 0을 위반한다. 같은 breakpoint에서 origin 편집으로 내용이 커지거나 최초 높이가 발행될 때 이 경로가 사용된다. 호출 결과는 `elements.ts:2641-2652`에서 canonical 위치와 DB에 저장된다.

수정 방향: reflow를 시스템 열과 사용자 격자 단위로 분리한다. 시스템 높이 변화는 뒤의 시스템 페이지에만 전파하고 사용자 페이지는 제외한다. 시스템 열은 전역 배치 방향이 horizontal이어도 세로라는 점을 반영해야 한다. 반대로 사용자 페이지 크기 변화가 시스템 열을 밀지 않도록 양방향 경계를 정한다. 이 실행 반례를 G1에 고정한다.

### M2 — breakpoint 전환 시 시스템 위치의 우선순위가 상충한다

본문 36행은 x/y Δ0, 39행은 드래그 좌표 보존 및 align 때만 시스템 열 복귀, 60행은 breakpoint 교체 대상에서 제외를 요구한다. 하지만 breakdown 46행은 첫 진입에 새 배치 산술을 적용하고 기존 스냅샷을 복원하도록 한다. 현재 `elements.ts:2521-2546`도 대상 snapshot 또는 firstEntryPositions가 currentPositions보다 우선이다.

반례 1: desktop에서 Components를 (-2500,200)으로 드래그한 뒤 저장된 mobile 스냅샷 없이 처음 진입한다. 새 배치 산술은 (-2000,0)을 반환해 align 없이 위치가 바뀐다. 반례 2: 기존 문서의 desktop/mobile Components 좌표가 다르면 각 breakpoint snapshot 보존과 전환 x/y Δ0은 동시에 성립할 수 없다.

수정 방향: 사용자 페이지에만 대상 breakpoint snapshot/최초 배치를 적용하고 시스템 페이지는 현재 공통 위치를 우선하도록 명시한다. 초기 hydration에서 기존 여러 시스템 좌표 중 어떤 것을 공통 위치로 선택하는지, 드래그/align/저장/재열기에서 그 값을 어떻게 유지하는지 함께 정한다. 사용자의 왼쪽 시스템 열 정책을 재논의할 필요는 없다.

### 검증 범위
