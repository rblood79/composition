### H1. variant·size choice의 선택지 출처가 잘못됨

- 위치: `docs/adr/287-interactions-do-from-reference-api.md:96`.
- 입력·상태 → 잘못된 결과: Badge의 variant 정하기 또는 Meter의 size 정하기를 선택 → `accepts.options`가 undefined여서 choice가 비거나 유도에서 누락된다. G2의 Badge variant 변경도 진행할 수 없다.
- 코드 근거: `packages/shared/src/catalog/types.ts:212`는 variant·size에 options를 두지 않는다고 명시한다. `packages/shared/src/catalog/outputs/editFields.ts:200`·`:206`의 기존 `deriveOptions`는 rule.sizes·rule.variants를 읽는다. 실행 probe로 두 accepts.options 부재와 rule 기반 선택지 존재를 확인했다.
- 해결: 유도 입력을 accepts + 기존 catalog 선택지 해소 계약으로 명시하고, choice의 실제 옵션이 비어 있지 않으며 기준 API literal을 벗어나지 않는 것을 G1에 넣는다. accepts에 D3 선택지를 중복 저장하지 않는다.

### H2. override 합성 한 곳만 추가해도 template-bound 표시 값은 바뀌지 않음

- 위치: `docs/adr/287-interactions-do-from-reference-api.md:98`, breakdown Phase 2.
- 입력·상태 → 잘못된 결과: 팔레트 Meter의 runtime record에 `label: 'Updated meter label'`을 쓰기 → 자식 Label은 계속 `Storage`를 표시한다. 이 ADR은 label도 Do로 유도하지만 G2가 value·variant·직접 children만 보면 이 실패를 놓친다.
- 코드 근거: `packages/shared/src/catalog/runtime/domBinding.runtime.ts:2933`의 `withOverride`는 이미 모든 non-style override를 병합하며 `domBinding.components.tsx:428`에서 실제 호출된다. `catalogPreviewInteractions.ts:849`·`:867`은 override 저장 뒤 수신자만 touch한다. Meter 자식은 `document/generated/reusableOriginLibrary.ts:5228`의 `{label}` 템플릿을 읽으며 runtime-local 병합으로는 문서 projection의 바인딩 해소가 갱신되지 않는다.
- 해결: Preview runtime 값이 composite의 template binding 및 의존 자식에 전달·무효화되는 경로를 설계에 포함하고 Meter.label 같은 실제 바인딩 자식을 G2에 추가한다. 문서 저장값은 변경하지 않는다.
- G0/R1 전제 정정: Meter.value override는 현재도 실제 Preview DOM의 `aria-valuenow=50`에 도달했다. 미등록 Do와 DOM override 소비 결손을 분리해서 RED를 정의해야 한다. 이번 probe는 공개 runtime write→jsdom DOM 경로이며 미구현 Do의 패널 등록을 검증한 것은 아니다.

### H3. enum·variant 변수 바인딩의 저장 계약 수리가 빠짐

- 위치: `docs/adr/287-interactions-do-from-reference-api.md:101`, breakdown Phase 3.
- 입력·상태 → 잘못된 결과: 기본값 `positive`인 string 변수를 Meter.variant에 `catalogPropFollowCommand`로 연결 → 실제 `workspace.execute`가 `PROP_CHOICE_MISMATCH`를 던져 저장하지 못한다. number value 바인딩은 같은 경로에서 성공했다.
- 코드 근거: `packages/shared/src/catalog/document/library.ts:142`의 `instanceContract`가 원본 root의 propChoices를 상속하고 `graph.ts:1565`·`:1583`이 동적 참조도 리터럴 choices.includes로 검사한다. scalar 타입의 `PropVar` 허용과 choice 검증은 별개다.
- 해결: propFollow UI 확장에 더해 동적 enum 참조의 graph/document 검증·runtime 값 검증 정책을 명시한다. 허용 enum 값 연결은 저장·재로드·코드 역변환에 성공하고 허용 집합 밖 값은 정한 정책대로 처리하는 gate를 추가한다.

### M4. guards 없음은 자기 disabled와 inherited disabled를 함께 우회한다

- 위치: `docs/adr/287-interactions-do-from-reference-api.md:98`·`:111`, `docs/adr/design/287-interactions-do-from-reference-api-breakdown.md:52`.
- 입력·상태 → 잘못된 결과: frame의 `disableAll`이 켜진 상태에서 frame 밖 Button이 자식 Button의 자기 `isDisabled=false` Do를 실행 → 제안한 `guards: []`로는 `inherited.isDisabled=true`여도 거절하지 않고 runtime override를 쓴다. 이는 사용자 결정 1의 “조상 inherited는 그대로 거절”과 다르다. DOM은 OR 상속 때문에 당장은 disabled로 보일 수 있지만, 거절되어야 할 자기 상태 쓰기가 남아 frame 해제 뒤 드러난다.
- 코드 근거: `packages/shared/src/interactions/constraints.ts:72`의 `guards.includes("isDisabled")` 한 분기 안에서 own과 inherited를 함께 검사한다. `dispatcher.ts:746`은 이 함수의 결과만으로 거절하며 독립적인 inherited 거절은 없다. `exposure.ts:112`도 같은 함수로 선택지를 거른다.
- 실행 반증: `checkCapabilityConstraints({ prop: "isDisabled", value: false, guards: [] }, ...)`는 own=true에서 허용되고, 여기에 inherited=true를 추가해도 여전히 허용된다. 대조군 `declaredRefusal(["isDisabled"], {}, {isDisabled: true})`만 거절한다. **Vitest 1/1 PASS**로 이 분기 차이를 확인했다.
