# ADR-243 Review Log

## Round 1 — 2026-09-27 (reviewer: codex)

## 판정 기준과 범위

- 범위: 실제 입력으로 구동하는 단발 7종과 burst, production Chrome 4x/1x 및 WebKit 1x, 600/5k 규모, canonical/history 순서, 응답 지연과 완료 시간. 팬·줌·스크롤, Preview/publish는 범위 밖이다.
- 기준: G0의 4x 600 p95 100ms·5k p95 200ms 초과 시 후보화, 다음 paint에 불필요한 작업 30% 이상인 경계만 검토, G2 대상 ratio 0.8 이하와 절대 기준 이내, 완료 시간 1.10 이하, WebKit 비악화. 이 수치는 기술 가설로 유지하고 실제 사용자 허용치 승인은 별도다.

## Findings

1. **HIGH — 완료 시간 비교 종점이 다르다.** breakdown 243:48-51은 Phase 0을 ‘rAF 2회 + 대기 persist 0’으로 근사하고 Phase 1 이후 새 scheduler continuation 카운터를 도입한다. 현재 `BuilderCore.tsx:391-397`의 microtask persist와 `canonicalMutationRunner.ts:168,177-181`의 fire-and-forget persist는 그 카운터에 포함되지 않는다. 따라서 persist 시작을 paint 뒤로 옮긴 변경이 미완료 작업을 숨겨도 G2의 +10%를 통과할 수 있다. before/after 공통 완료 표식으로 동일한 persist/continuation 추적을 먼저 계측하고 실제 마지막 작업 후 paint를 재야 한다.
2. **MEDIUM — Event Timing 표본 탈락을 처리해야 한다.** breakdown 243:48은 `durationThreshold:16` 관측 항목만 모은다. 브라우저의 최소 threshold가 16ms이므로 개선 뒤 빠른 입력이 사라지면 종류별 p95와 ratio는 전체 30회 입력의 p95가 아니다. 각 입력 ID와 관측 여부를 함께 기록하고, 누락 표본의 상한 처리 또는 별도 전체 입력 측정으로 분모를 고정해야 한다. [MDN PerformanceObserver](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceObserver/observe).

## 검증 범위

ADR·breakdown·현재 persist/runner 코드와 브라우저 API 문서를 대조했다. 하니스, production 브라우저 수치, LoAF 귀속은 아직 없으므로 G0~G4는 UNVERIFIED다. 제품 코드와 ADR Status는 변경하지 않았다.
