# ADR-227 Review Log

## Round 1 — 2026-09-20 (reviewer: codex)

판정: **설계 보완 필요 — HIGH 3 / MEDIUM 1**. Proposed 유지. 리뷰 기준 HEAD `a7c85b70f`; 본문과 breakdown, 현재 production 코드 대조. 제품 코드 수정·구현 gate 통과 판정 없음.

### H1 — 테마 델타의 실제 소비 경로와 CSS 명명 계약 누락

위치: `docs/adr/design/227-multi-theme-token-set-collection-breakdown.md:73-74`.

색상 맵 위에 델타를 덮는 설계는 typography/radius/shadow/focus까지 포함한 Decision 3을 충족하지 못한다. `packages/specs/src/renderers/utils/tokenResolver.ts:35-53`는 color 외 축을 각각 독립 primitive 객체에서 읽고, 실제 catalog Skia adapter는 `packages/shared/src/catalog/outputs/toSkiaStyle.ts:73`에서 이 함수를 호출한다. `resolveCanonicalToken`은 현재 선언·re-export 외 production 호출자가 없어 그 함수 변경 자체가 소비 배선은 아니다.

DOM도 `color.accent`를 `--accent`, neutral을 `--fg`, typography를 `--text-*`로 해석한다(`tokenResolver.ts:87-101,231-243`). 설계 예시의 `--color-accent`를 주입해도 기존 Button CSS는 읽지 않는다. hover/pressed는 현재 color-mix 표현식이므로 해당 토큰을 개별 편집할 때의 우선순위도 정의해야 한다.

해결: 카테고리별 runtime map·CSS 매핑·값 단위·파생값 우선순위를 하나의 계약으로 명시하고 production 소비자까지 연결한다. G2에 accent뿐 아니라 typography/radius/shadow/focus를 비기본값으로 편집한 Canvas/Preview/Publish 확인을 넣는다. 단순히 기본 테마끼리 같음을 확인하는 것으로 이 채널의 전달을 증명할 수 없다.

### H2 — border 참조화는 리터럴 sweep만으로 성립하지 않는다

위치: `docs/adr/design/227-multi-theme-token-set-collection-breakdown.md:80`.

`packages/specs/src/types/spec.types.ts:997`는 `borderWidth?: number`다. `CSSGenerator.ts:777-785,1003-1004`는 무조건 px를 붙여 TokenRef 투입 시 `border-width: {border.width.thin}px`처럼 유효하지 않은 CSS를 낸다. `tokenResolver.ts:35-55`에는 border 분기도 없다.

그리기 adapter를 고쳐도 레이아웃은 별도다. `apps/builder/src/builder/workspace/canvas/layout/engines/implicitStyles.ts:437-450`는 number만 받아 box model에 넣으며, 같은 디렉터리 `utils.ts:3333,3528`는 비숫자일 때 1로 fallback한다. thin을 3으로 편집하면 paint와 layout의 border가 달라질 수 있다.

해결: 타입·토큰 검증/resolve·CSS 생성·implicit layout·크기 산식 소비자를 Phase 3 파일 경계에 포함한다. G3은 리터럴 복원 RED와 기본값 Δ0에 더해 thin=3 같은 비기본 폭에서 양 leg의 외곽 및 content box를 검증해야 한다.

### H3 — 구 프로젝트의 실제 테마를 migration이 읽지 않는다

위치: `docs/adr/design/227-multi-theme-token-set-collection-breakdown.md:52,66`.

현행 초기 문서(`apps/builder/src/dashboard/createInitialProjectDocument.ts:35-56`)는 themes 없이 생성된다. 사용자의 tint 변경은 `themeConfigStore.ts:178-196`에서 localStorage로 저장되고, 프로젝트 재진입은 `BuilderCore.tsx:635-659`에서 이를 복원한다. 문서 적용은 flag 뒤다.

따라서 themes 없는 기존 프로젝트에서 tint=red를 저장한 사용자를 설계대로 migration하면 DEFAULT_THEME_SELECTION으로 바뀐다. 문서에 stale 프리셋이 있는 경우에도 새 write-through가 기존 실효값을 덮을 수 있다. `baseTypography`는 localStorage에 저장되지만(`themeConfigStore.ts:100-110,304-307`) 구 ThemeSnapshot 4필드에는 없으므로 캐시 축소 전에 승계해야 한다.

해결: 초기 1회 migration에 프로젝트별 legacy 설정을 입력으로 전달하고 문서/legacy 값의 충돌 우선순위를 확정한다. 문서 저장 성공 후 migration 완료를 표기하고 이후부터 문서를 정본으로 삼는다. G1에 themes 부재+비기본 localStorage, stale 문서와 legacy 충돌, 사용자 typography, 설정 없는 import를 분리한다. 현 사용자 데이터의 실제 분포는 조사하지 않았으며, 여기서는 코드상 가능한 재현 조건을 판정했다.

### M4 — G4 Undo와 G5 무기록 조건을 함께 만족할 수 없다

위치: `docs/adr/227-multi-theme-token-set-collection.md:114-115`.

HC 쓰기 계약과 breakdown Phase 1은 활성 전환의 History 등록을 요구하고 G4는 Undo 복귀를 요구한다. 같은 사용자 전환을 G5에서 history 길이 무변화로 검사하면 정상 구현도 실패한다.

해결: 사용자 전환은 의도한 History entry 1건, Components 재렌더·origin 갱신 부작용은 추가 entry 0건으로 나눈다. children 배열은 무변화로 유지한다.

### 검증 범위와 한계

- VERIFIED: 위 production 소비 경로, 초기 저장/로드 경로, 설계의 상충 조건을 현재 소스에서 확인했다.
- UNVERIFIED: 구현 전 ADR이므로 신규 migration, 픽셀 parity, 600요소 프레임 예산, 실제 Undo 및 Publish 동작은 실행·통과를 주장하지 않는다.
- 문서가 제시한 외부 선례는 방향 참고로만 인정한다. [Figma 모드](https://help.figma.com/hc/en-us/articles/15343816063383-Modes-for-variables)는 레이어/프레임 적용을 포함하고, [Framer Styles](https://www.framer.com/developers/styles)는 프로젝트 내 color/text style을 설명한다. 이 자료가 Composition의 프로젝트 단위 활성 하나나 프레임 예산을 입증하지는 않는다.
- ADR-228과 schema 선행 의존을 강제할 근거는 발견하지 못했다. origin 확장 뒤 227 G5를 다시 수행한다는 현 계획은 합리적이다.
