### H1 — 핵심 ListBox 입력은 position 필터보다 앞에서 누락됨 (fixed — 설계 반영)

- 위치: `design/267-sticky-fixed-position-canvas-engine-breakdown.md:27-30`.
- 입력·상태 → 잘못된 결과: 높이가 제한된 단독 ListBox > ListBoxSection > Header를 스크롤한다. 계획에 적힌 position/inset 필터만 확장하면 ListBox의 `top` 규칙이 엔진 입력에 들어오지 않아 헤더가 계속 흘러간다. Header 자체의 root sticky는 inset이 없으므로 설계대로 constraints 없음이 되어 대체하지 못한다.
- 근거: `componentRulesTable.ts:6844-6904`의 유효 입력은 `rootSelectors['&:not(.react-aria-Popover *)'].nested['.react-aria-ListBoxSection .react-aria-Header']`다. `compileRulePartRules`의 블록 수집(`rulePartRules.ts:1717-1760`)은 archetype/staticSelectors/sizeSelectors/delegation뿐이다. `parseSimple`(`:244-254`)도 해당 descendant 조합을 받지 않는다. part compiler에 다른 Header 규칙은 존재하나 이 nested 규칙의 도달을 의미하지 않는다.
- 실행: 실제 `compileRulePartRules('ListBox')` 호출. nested 규칙의 position을 이미 지원하는 relative로, padding을 99px로 메모리에서 바꾸어도 컴파일 결과가 완전히 같았다. 변경은 finally로 복원했다. 기존 출력에 Header insetTop 없음도 확인했다.
- 해결 방향: standalone/Popover 조건과 ListBoxSection 경유 selector를 표현하는 규칙 생산 경로를 Phase 1-a에 명시한다. token/calc inset 해소까지 포함해 실제 catalog → resolver → styleOf 입력에 `sticky`와 수치 inset이 도착하는 RED를 둔다. 일반 필터 unit만으로 종결하지 않는다.

### H2 — 화면에 붙은 헤더가 선택·hit 질의에서는 사라짐 (fixed — 설계 반영)

- 위치: `design/267-sticky-fixed-position-canvas-engine-breakdown.md:44-49`.
- 입력·상태 → 잘못된 결과: 목록 scrollTop=100에서 헤더를 화면 y=0으로 붙인다. 기존 consumer는 header bounds를 y=-100으로 유지하며 hit 영역은 clip 밖이라 제거한다. 자손 label의 공간 좌표도 y=-96으로 남는다. 보이는 헤더를 클릭할 수 없고 선택 오버레이·공간 질의도 화면과 어긋난다.
- 근거: `renderCommands.ts:1633-1644`가 bounds/hit를 먼저 만들고 이후 renderRelX/Y만 바꾼다. 자손 clip 및 parentAbs(`:1800-1837`)도 정적 abs를 사용한다. SpatialIndex는 hitBoundsMap을 받으므로 full repaint/unsafe 분류 유지로 해결되지 않는다.
- 실행: 실제 `buildRenderCommandStream`에 dormant sticky consumer를 활성화하는 격리 입력을 제공했다. 아직 production emitter가 없는 점을 분리하기 위해 stickyTop=100으로 +100 paint 이동을 만들었다. paint y=0, header bounds y=-100, header hit 없음, label bounds y=-96, label hit 없음이 모두 재현됐다. 이는 전체 Builder의 live 재현이 아니라 소비자 함수 실행 반례다.
- 해결 방향: 정적 layout은 유지하되 sticky delta를 화면 bounds/hit/clip과 자손 build context에 일관되게 전달하도록 계약을 추가한다. 전체/서브트리/self 재빌드 및 캐시된 문맥 소비에도 같은 좌표 규약을 적용하고, G1/G2에서 보이는 위치의 hit·선택을 확인한다.

### M3 — overflow:hidden도 sticky scroll container임 (fixed — 설계 반영)

- 위치: `design/267-sticky-fixed-position-canvas-engine-breakdown.md:35`.
- 입력·상태 → 잘못된 결과: outer ListBox overflow:auto > section overflow:hidden > sticky Header, outer scrollTop=100. 문서의 auto/scroll 탐색은 hidden section을 건너뛰고 outer를 owner로 골라 헤더를 y=0에 붙인다. Chrome은 hidden section을 owner로 삼아 헤더가 outer와 함께 y=-100으로 움직인다.
- 실행: headed Chrome 155, visible, DPR 2에서 독립 DOM fixture 실측. outer scrollTop=100 고정 시 section overflow hidden의 header y=-100, visible/clip 대조군은 y=0. `catalogOverflowScrolls('hidden')`는 false인 것도 실제 함수 호출로 확인했다.
- 근거: 기존 Rust `tree.rs:6264-6282`는 hidden을 포함한 CSS scroll container 술어를 이미 갖는다. `catalogOverflowScrolls`는 Canvas 스크롤 UI용으로 더 좁다. [CSS Overflow 3 hidden 정의](https://www.w3.org/TR/css-overflow-3/#valdef-overflow-hidden)와도 대조했다.
- 해결 방향: scroll owner 탐색은 CSS scroll container 판정(hidden 포함, clip 제외)을 사용한다. scrollbar/사용자 스크롤 가능성은 별도로 유지하고 hidden 경계 fixture를 G1에 넣는다.

### H1 — selector 경로는 반영됐지만 라이브러리 검증에서 sticky가 거부됨 (open)

- 위치: `design/267-sticky-fixed-position-canvas-engine-breakdown.md:34-38`. `validation.ts` 변경은 여전히 Phase 2(:78, 파일 표 :99)에만 있다.
- 확인된 수리: `manualBoxRules.ts:346-376`의 Header part(`via: ListBoxSection`)가 실제 경로인 점, nested 블록을 정본으로 읽을 계획, calc/token 해석 실패 시 throw, catalog → resolver → styleOf 단언이 명시됐다. 이 부분은 기존 H1을 정확히 보완한다.
- 남은 입력·상태 → 잘못된 결과: 계획대로 manual Header part가 `position: sticky`와 `insetTop: -0.5px`를 내보내면, `buildCodeCatalogLibrary` → `buildCatalogLibrary` → `validateLibraryDefinition` → `ruleOutput` → `layoutValues`에서 **`INVALID_LAYOUT_VALUE`, `library.definition.partRules[0].layout.position`**가 발생한다. resolver/styleOf에 닿기 전에 코드 라이브러리 생성이 실패하며 Builder의 프로젝트 열기 경로(`apps/builder/src/builder/catalogRuntime/library.ts:10`)도 이 빌더를 쓴다. 이대로 구현하면 헤더뿐 아니라 라이브러리 전체가 열리지 않는다. `typedCanvasBox`의 루트 Header sticky도 `library.definition.layout.position`에서 같은 오류다.
- 원인: `validation.ts:195`의 position 선택지는 노드 저작 값만 제한하지 않는다. `layoutValues`(:599-606)를 library definition(:1574-1575)과 part rule(:1594-1625, `ruleOutput` :841-846)도 사용한다. authored `layoutWrites`(:609-619)도 같은 선택지를 사용하므로 단순 공용 확장은 사용자 결정 1 전 저작 비허용 정책까지 바꾼다.
- 실행 반례: 현재 `buildCodeCatalogLibrary()`로 만든 실제 definitions를 메모리에서 복제하고, ListBox의 해당 Header part에 제안된 layout만 적용해 실제 `buildCatalogLibrary()`로 다시 조립했다. `relative` + 동일 inset 대조군은 PASS, `sticky`는 위 정확한 code/path로 거부됐다. 루트 Header에 sticky를 전달한 arm도 공용 validator에서 거부됐다. 제품 파일은 바꾸지 않았다. 이는 미래 구현의 계획된 입력을 실제 검증 경계에 넣은 실행 반례이며 현재 배포 제품이 이미 고장났다는 뜻은 아니다.
- 해결 방향: **Phase 1에서 라이브러리 내부 rule layout의 sticky 허용과 노드 저작 검증을 분리**하도록 설계를 보완한다. 저작 sticky/fixed 허용 및 패널 노출 결정은 계속 사용자 결정 1에 둔다. H1 end-to-end 게이트에는 코드 라이브러리의 실제 build/validation 단계를 포함한다. 작성된 스키마 불변 조건과 내부 허용 범위도 일치시킨다.
- 상태 반영: Round 1 h1의 `outcome`을 pending으로 되돌리고 부분 수리 근거를 기록했다. Round 1 본문은 보존했다.
