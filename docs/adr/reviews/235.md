# ADR-235 Review Log

## Round 1 — 2026-09-23 (reviewer: codex)

판정: **수정 후 재검토 — HIGH 3건 / MEDIUM 2건 pending**. 저장 형식과 자산 분리는 타당한 방향이지만, 현재 명시된 commit 순서와 GC root 집합으로는 데이터 보존 계약을 충족하지 못한다. ADR 상태는 Proposed를 유지한다. 제품 구현·ADR 본문·breakdown은 수정하지 않았다.

### h1 · HIGH — manifest를 마지막에 써도 프로젝트 저장은 원자적이지 않다

- 대상: [breakdown §2](../design/235-local-project-storage-v2-breakdown.md:18), [쓰기 순서](../design/235-local-project-storage-v2-breakdown.md:30), [Decision 3](../235-local-project-storage-v2-asset-store-directory-format.md:99).
- 실패 조건: revision 1의 문서·collections가 있는 상태에서 새 collection B와 이를 참조하는 문서를 저장한다. 새 `document.json`의 `close()` 직후, `collections.json`/manifest를 쓰기 전에 중단한다. 다시 읽으면 manifest는 revision 1, document는 revision 2, collections는 revision 1이다. 기존 document 바이트가 사라졌으므로 이전 세대로도 복원할 수 없다. 새 자산을 썼다면 구 manifest가 이를 무시하는 규칙과도 충돌한다.
- 근거: [File System Standard §createWritable](https://fs.spec.whatwg.org/#api-filesystemfilehandle-createwritable)는 stream을 닫을 때 **그 파일**을 반영한다. 프로젝트 단위 트랜잭션은 아니다. 현행 정적 HTML 선례도 `export.utils.ts:1518-1538`에서 파일마다 close하며 다중 파일 복구를 구현하지 않는다. API 보장과 제안된 순서에서 도출한 반례이다.
- 수정 방향: document·collections·fonts를 immutable revision 경로에 먼저 쓰고 검증한 뒤 manifest 하나가 해당 세대를 가리키도록 전환한다. 또는 동등한 복구 journal/이전 세대 보존 방식을 명시한다. manifest 교체 전후의 모든 중단점에서 세대가 섞이지 않는 것을 G6 판정 기준으로 삼는다.

### h2 · HIGH — GC가 undo/redo에만 남은 자산을 삭제한다

- 대상: [R2](../235-local-project-storage-v2-asset-store-directory-format.md:119), [Phase 2](../design/235-local-project-storage-v2-breakdown.md:39).
- 실제 소비 경로: `historyIndexedDB.ts:49-51`은 `history-entries`와 `snapshots`를 구분한다. `saveEntry` (`:211-228`)는 canonical event를 보관하고, `getEntriesByPage` (`:296-314`)로 복원한다. `canonicalHistoryEvents.ts:34-60`의 삭제 node 및 update의 prevProps/nextProps에 이미지 참조가 남으며, `:327-334`가 undo 시 이를 다시 삽입/적용한다.
- 실패 조건: asset A를 사용하는 이미지를 삭제한다. 이후 정상 편집·저장으로 5세대 백업에서 A가 밀려나고 A를 포함하는 사용자 스냅샷도 없지만, 삭제 history entry는 아직 보존되어 있다. 유예가 끝난 GC는 명시된 root 집합에서 A를 찾지 못해 바이트를 지운다. undo는 node와 asset 문자열만 복원하여 이미지가 깨진다. history entry 보존과 GC 유예 사이의 안전 조건도 정해져 있지 않다.
- 수정 방향: 살아 있는 history entry의 undo/redo payload와 메모리 history를 root로 포함한다. history 폐기와 함께 참조를 해제하고, mark 이후 새 참조가 생기는 경우에도 삭제되지 않게 한다. G3에 **백업·스냅샷에는 없고 history에만 남은 자산 → GC → undo/redo**를 추가한다.

### h3 · HIGH — reader보다 writer를 먼저 바꾸는 Phase 순서

- 대상: [Phase 1–3](../design/235-local-project-storage-v2-breakdown.md:38), [G2](../235-local-project-storage-v2-asset-store-directory-format.md:133), [G5 fallback](../235-local-project-storage-v2-asset-store-directory-format.md:136).
- 실패 조건: Phase 1에서 이미지를 업로드하거나 Phase 2에서 기존 dataURL을 `asset:`으로 치환한다. 명시된 consumer 전환은 Phase 3이다. 현행 `imageCache.ts:389`는 URL을 바로 fetch하고 `fillAdapter.ts:171`은 그대로 CSS `url()`에 넣는다. resolver를 정의하는 것만으로 이 호출이 연결되지는 않는다. 이 순서에서는 이관 직후 이미지가 표시되지 않아 Phase 2 종료의 시각 동일성 G2도 만족하지 못한다.
- 추가 영향: 현행 v1 serializer (`export.utils.ts:861-877`)는 document를 그대로 JSON에 넣는다. 자산화 후 G5 실패로 v1을 유지하면 asset 참조만 든 파일을 다른 브라우저로 옮길 수 있다. 해당 IDB가 없는 곳에서는 바이트를 복구할 수 없다.
- 수정 방향: dual-read consumer와 독립 export를 먼저 준비하고 검증한 다음 새 참조 writer 및 이관을 활성화한다. 준비 단계에서는 기존 dataURL 쓰기를 유지한다. v1 fallback을 계속 제공한다면 export 경계에서 자산 바이트를 인라인하는 계약을 추가한다. Phase별 활성화 경계를 명시한다.

### m1 · MEDIUM — 별도 DB는 캐시 우선 퇴거 보장이 아니다

- 대상: [Decision 5](../235-local-project-storage-v2-asset-store-directory-format.md:101), [Positive](../235-local-project-storage-v2-asset-store-directory-format.md:151).
- 근거: [Chrome Storage Buckets 공식 문서](https://developer.chrome.com/docs/web-platform/storage-buckets)는 기존 저장소의 persistence가 하나의 bucket에 적용되며, named bucket을 도입해야 독립 삭제가 가능하다고 설명한다. 같은 origin에서 DB 이름을 달리하는 것만으로 브라우저 퇴거 우선순위를 만들 수 없다. QueryPersister는 이미 `composition-query-cache`라는 별도 DB이다 (`QueryPersister.ts:51-55`).
- 실패 조건: Buckets 미지원 환경에서 별도 DB fallback을 택하고 persistence가 허용되지 않은 상태로 저장소 압박이 발생하면, 캐시보다 원본을 보호한다는 정책을 브라우저에 전달하지 못한다. DB 분리만으로 "캐시부터 비워진다"는 결론은 성립하지 않는다.
- 수정 방향: named bucket 경로와 fallback의 보장을 구분한다. fallback은 앱이 수행하는 캐시 상한·선제 정리·quota 실패 시 정리 후 재시도로 설명하고, persistence 거부 상태 및 원본과 캐시가 함께 퇴거될 수 있음을 명시한다. bucket 사용 시 persist 대상도 명확히 한다.

### m2 · MEDIUM — 현재 페이지가 v2 왕복에서 유실된다

- 대상: [v2 레이아웃](../design/235-local-project-storage-v2-breakdown.md:18).
- 근거: 기존 `ProjectExportData.currentPageId` (`export.utils.ts:115`)는 `:869`에서 저장된다. Builder는 `BuilderCore.tsx:1295-1300`에서 해당 페이지를 활성화하고 publish는 `App.tsx:329-344`에서 초기 페이지 모델에 사용한다. 없으면 `export.utils.ts:821-824`에서 첫 페이지로 fallback한다. v2 manifest/문서/sidecar 목록에는 이를 저장할 필드가 없다.
- 실패 조건: 문서 순서가 A, B이고 현재 페이지가 B인 프로젝트를 v2로 내보내고 새 프로젝트로 가져오거나 기본 URL로 publish한다. document·assets가 같아도 현재 페이지가 A로 바뀐다.
- 수정 방향: manifest 또는 별도 editor/runtime metadata에 `currentPageId` 매핑과 유효성 검증을 정의한다. G5 왕복에서 canonical document 외에 기존 export envelope의 필요한 필드도 비교한다.

### h2 · HIGH — 두 번째 mark 이후 기존 자산을 다시 참조하면 sweep이 살아 있는 바이트를 삭제한다

- 대상: [breakdown Phase 3](../design/235-local-project-storage-v2-breakdown.md:62), [R2](../235-local-project-storage-v2-asset-store-directory-format.md:126), [G3](../235-local-project-storage-v2-asset-store-directory-format.md:146).
- 반영 확인: history entry payload·메모리 history·진행 중 transaction이 root에 추가됐으며, history 전용 자산 → GC → undo/redo도 G3에 들어갔다. 이 부분은 해소됐다.
- 남은 실패 순서: (1) 오래된 자산 A가 첫 GC에서 미참조 후보가 됨 → (2) 유예 경과 → (3) 두 번째 mark에서도 미참조 → (4) sweep 전에 사용자가 A의 기존 `asset:` URL을 이미지에 적용해 문서와 history에 참조를 추가 → (5) sweep은 이전 mark 결과로 A를 삭제한다. A의 바이트를 다시 저장하지 않았으므로 “mark 시작 후 저장된 자산 제외” 조건은 작동하지 않는다. 두 번의 mark와 유예 기간 모두 충족하면서 현재 문서의 이미지가 유실된다.
- 현재 입력 경로: `apps/builder/src/builder/panels/styles/components/ImageFillEditor.tsx:52-65`의 `handleUrlCommit`은 입력 문자열을 `onUpdateEnd({ url })`로 보내며, `FillSection.tsx:243-252`는 이를 `updateFill`로 적용한다. 참조 문자열 변경이 새 자산 업로드·바이트 저장을 반드시 거친다는 계약은 없다.
- 반증 실행: `pnpm exec node /private/tmp/adr235-repair-gc-interleaving.mjs`에서 개정 Phase 3의 조건으로 위 순서를 실행했고 `referenced: true, bytesPresent: false`를 확인했다. **설계 알고리즘의 실행 모델이며 제품 GC 또는 브라우저 재현이 아니다.**
- 수정 방향: 자산 바이트 저장과 별개로 **모든 참조 추가와 sweep 삭제가 공유하는 직렬화·pin/epoch 계약**을 정의한다. 참조 추가가 후보를 무효화하고, 삭제는 같은 보호 범위에서 최신 참조 상태를 확인한 뒤 확정해야 한다. 원자성 없는 세 번째 조회만으로는 같은 틈이 다시 생긴다. G3의 “mark 이후 참조”는 **기존 후보 자산의 바이트를 재저장하지 않은 참조 추가를 두 번째 mark와 실제 삭제 사이에 삽입**하는 케이스로 고정한다.
- 이는 테스트 개수 부족 지적이 아니라 명시된 삭제 알고리즘이 참조 중인 자산을 삭제할 수 있는 반례다. G3 통과 전 GC 비활성 fallback은 유효하지만, 설계 수리 완료 판정을 대신하지는 않는다.

## h2 수리 응답 — 2026-09-26 (executor: codex)

사용자 요청 “1건 수정해”에 따라 round 2 h2를 설계에서 수정했다. 새 판독 라운드는 추가하지 않았다. round 1·2의 h2 outcome은 `fixed`로 갱신하며, 과거 판정 본문은 기록 당시 내용대로 보존한다. **미해결 설계 리뷰 이슈 HIGH 0건으로 설계 수리를 종결한다.** ADR은 Proposed이고 제품 구현·G0–G6 승인과는 별개다.

- **계약 수정**: [breakdown §3.1](../design/235-local-project-storage-v2-breakdown.md#31-gc-참조-공개와-삭제의-순서-round-2-h2-수리)에 `asset_gc` 메타데이터와 참조 공개 전 pin을 명시했다. 모든 탭의 참조 준비·pin 해제·삭제가 같은 `assets`·`asset_gc` readwrite 트랜잭션 범위를 사용한다. GC는 최종 트랜잭션에서 pin 없음과 현재·mark·후보 epoch 일치를 확인한 뒤 삭제한다. 일반 편집은 이미 확보한 pin을 재사용하고 기존 상태 파이프라인을 보존한다.
- **양쪽 순서 처리**: 기존 자산의 URL 재적용이 먼저 pin을 확보하면 삭제를 취소한다. 삭제가 먼저 끝나면 참조 준비의 바이트 존재 확인이 실패해 참조 공개를 거부한다. 원본 바이트가 있는 업로드는 바이트·pin을 함께 저장할 수 있다. 자산을 다시 저장했는지는 보호 조건으로 삼지 않는다.
- **pin 해제와 중단**: 관련 durable root 저장의 transaction complete 뒤 pin을 해제하면서 epoch를 증가시켜 오래된 mark를 무효화한다. 메모리 전용 history·미완료 저장·소유 상태가 불명확한 중단 세션의 pin을 시간만으로 지우지 않는다. 참여하지 않는 writer나 메타데이터 오류가 있으면 sweep을 끈다.
- **R2·G3와 Phase 배선**: Phase 0에서 참조 공개 경로 목록을 고정하고 Phase 1에 pin 준비를 배선한다. G3는 두 번째 mark와 삭제 사이의 기존 자산 재참조를 pin 선행·삭제 선행 양쪽으로 검증하며, pin 해제에 따른 epoch 변경도 포함한다.
- **설계 실행 근거**: `pnpm exec node docs/adr/design/235-gc-reference-admission-model.mjs` — 기존 반례, pin 선행 보존, 삭제 선행 참조 거부, 영속화 후 pin 해제, 중단 pin 보존, 계속 미참조인 후보 삭제의 6개 순서 assertion 통과. [실행 모델](../design/235-gc-reference-admission-model.mjs)은 원자적인 보호 트랜잭션의 순서만 모델링한다. 실제 IndexedDB 원자성·여러 탭의 배선·브라우저 GC를 실행한 증거가 아니며, 제품 G3는 **UNVERIFIED**이다.
