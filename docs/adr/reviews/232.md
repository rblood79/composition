# ADR-232 Review Log

## Round 1 — 2026-09-22 (reviewer: codex)

판정: **설계 보완 후 재검토 필요 — HIGH 2 / MEDIUM 4, 모두 pending.**

검토 기준은 HEAD `f258286efd665d6bb47c0ed36147d86b8ffdc4b5` 및 현재 untracked ADR/breakdown이다. 기존 Dialog/Modal 관련 dirty 변경은 보존했다. 제품 코드 수정과 ADR 상태 승격은 하지 않았다.

1. **[HIGH h1] 부분 absolute 이관은 나머지 페이지의 좌표를 바꾼다.** 본문 Decision 6 (`232-page-placement-as-layout-derivation.md:71-74`)과 breakdown `:58`은 기존 격자와 일치하는 페이지는 흐름에 남기고 불일치 페이지만 absolute로 승격한다. 그러나 현행 엔진은 absolute 자식을 흐름에서 제거한다 (`packages/engine/src/tree.rs:1683-1700`). 너비/높이 100, gap 10, 3열, 순서 A/B/C에서 저장 좌표가 A=(0,200), B=(110,0), C=(220,0)이면 A만 absolute가 된다. 현재 로컬 WASM 실행 결과 B=(0,0), C=(110,0)으로 각각 110px 이동했다. 이는 Decision 3의 빈 칸 채우기와 일관되지만 G4의 픽셀 Δ0과 충돌한다. **해결 방향:** 실제 최종 파생 결과를 전체 페이지 벡터로 검증한 후 불일치 전파를 닫거나, 혼합 문서의 해당 tier를 통째로 absolute로 승격하는 보수적 정책을 정한다. 일부 페이지 고정으로 보존한다면 해당 정책을 명시한다. G4에 혼합 배치, 여러 행, 불규칙 크기 fixture를 필수로 넣는다. 단순히 이관 전 격자와 페이지별 한 번 비교하는 것으로는 부족하다.

2. **[HIGH h2] 롤백 데이터가 첫 이관 저장에서 사라진다.** 본문 `:60,71-74,103`은 `pagePositions`의 한 major 보존을 HIGH 위험 수용 근거 및 G4 실패 시 복구 수단으로 삼는다. 반면 breakdown `:58`은 “이관 후 pagePositions 필드 삭제 (persist 1회)”를 요구한다. 다음 행에서 스키마를 읽기용으로 남겨도 이미 지운 좌표 데이터는 복원되지 않는다. **해결 방향:** 실제 원본 데이터를 문서 또는 별도 원자적 백업에 보존하는 위치·수명·복구 절차를 확정하고 본문/Phase 3/G4를 일치시킨다. 이관 후 저장·reload·롤백의 원본 좌표 보존을 검증해야 한다. 새 placement 편집 이후 롤백이 이관 시점으로 돌아가는지까지 범위를 명시한다.

3. **[MEDIUM m3] F11의 재사용 가능 범위가 실제 허용 키보다 넓다.** breakdown `:28,43-54`는 `resolveResponsiveLayoutNode`를 재사용해 페이지 칸과 direction을 breakpoint별로 적용한다. 하지만 실제 resolver는 `isResponsiveEligibleStyleProp`이 false면 skip한다 (`resolveResponsive.ts:58-64`). 현재 shared 함수를 직접 실행한 결과 `gridColumn=false`, `gridRow=false`, `gridAutoFlow=false`; `gridTemplateColumns=true`, `gridColumnStart=true`, `position=true`였다 (`responsive.types.ts:192-223`). 따라서 root 열 수만 검증하는 G1(d)는 페이지 칸 override 누락을 잡지 못한다. **해결 방향:** placement를 허용된 start/end longhand로 정규화하고 direction의 대응 키를 정의하거나, 필요한 eligibility 확장을 ADR 범위·변경표·테스트에 포함한다. mobile 칸 이동 및 horizontal↔vertical override의 실제 resolver 결과를 gate로 고정한다.

4. **[MEDIUM m4] snapshot→cascade 이관에는 상속을 차단하는 명시 값이 필요하다.** Decision 6 및 breakdown `:58`의 “base는 desktop, 다른 breakpoint는 값이 다를 때만 override”는 차분 기준을 명시하지 않는다. 현재 resolver는 mobile에서 tablet 값을 먼저 상속한다 (`responsive.types.ts:438-464`). 예를 들어 절대 좌표 x가 desktop=100, tablet=200, mobile=100인 기존 문서를 desktop과의 차이만 저장하면 `{tablet:200}`이 되어 mobile 결과도 200이다. 이 값은 shared 함수를 직접 실행해 확인했다. desktop만 absolute이고 mobile은 기존 격자와 일치하는 경우에도 mobile에 아무것도 쓰지 않으면 base의 `position:absolute`가 상속되어 흐름에 복귀하지 않는다. **해결 방향:** 각 tier의 목표 유효 style과 이전 tier의 cascade 결과를 비교해서 명시 reset까지 기록한다. position/static, grid line/auto, left/top 정리와 partial snapshot의 fallback을 정의하고 G4에 A→B→A 및 absolute→flow→absolute 행렬을 추가한다.

5. **[MEDIUM m5] 칸 고정 페이지끼리의 드롭 충돌 정책이 빠졌다.** breakdown `:51-52`는 드롭 대상 칸에 gridColumn/gridRow를 기록하면 뒤 페이지가 재흐름한다고 설명한다. 현재 엔진의 명시 row/column 배치는 이미 점유된 칸이어도 같은 좌표를 허용한다 (`packages/engine/src/grid.rs:1190-1210`). B를 2열 1행에 고정한 뒤 A도 그 칸에 놓는 입력을 현재 WASM에 주면 A/B 모두 (110,0)에 놓였다. 이는 엔진 결함이 아니라 명시 grid 배치의 계약이다. **해결 방향:** 고정된 칸에 대한 드롭은 거부/교환/밀기 중 어떤 동작인지 정하고 영향을 받는 placement를 history 한 건으로 처리한다. 의도적으로 겹침을 허용한다면 G2의 재흐름 보장과 위험 설명을 그에 맞게 좁힌다. 기존 absolute 겹침 위험 R5는 이 in-flow 충돌과 별개다.

6. **[MEDIUM m6] G3는 변경된 위치로 인한 후단 비용 증가를 놓친다.** 본문 G3 `:102`와 breakdown `:65`의 통과 조건은 `scene.build`/`layout.publish` 및 메모 hit 카운터이다. 재사용할 ADR-231 하니스는 `render.frame`/total도 수집하지만 (`adr231-frame-decomp-ab.mjs:37-48,95-116`) 실제 조작은 Home 요소 및 Components Button 폭 편집 두 종류이다 (`:190-220`). 페이지 Body 크기·열 수·순서·breakpoint 변경으로 배치 root가 invalidation되고 보이는 여러 페이지가 이동하는 경우는 이 조작 목록으로 검증되지 않는다. 따라서 렌더 캐시 재생성 비용이 커져도 명시된 두 stage gate는 통과할 수 있다. **해결 방향:** 기존 frame 크기 불변 편집 대조군을 유지하고, 30페이지에서 Body 높이/열 수/breakpoint 변경을 포함한 A/B 및 `render.frame` 또는 총 프레임 비용 상한을 추가한다. 기기·DPR·visibility·warmup 조건과 합성 600요소의 규모 전용 용도를 gate에 연결한다. 현재 성능 회귀를 관측했다는 판정은 아니며, `.agents/rules/measurement-validity.md` Q2/Q3의 측정 범위 누락이다.

2. **[MEDIUM m2] legacy 복귀 모드에 좌표가 없는 페이지의 정책이 필요하다.** Decision 6′은 모든 페이지를 저장 좌표 absolute로 두고, 페이지 추가는 “흐름 끝”이라고 한다. 그러나 pagePositions는 원래 lazy-write `Partial<Record<BreakpointName,...>>`이고 (`composition-document.types.ts:1124-1132`), 현재 hydration은 미기록 페이지를 따로 채운다 (`elements.ts:2712-2737`). 더 직접적인 재현은 232 이관 완료 → derived에서 새 페이지 추가 → legacy로 복귀이다. ADR의 pagePositions 쓰기 0 계약 때문에 새 페이지에는 복구 좌표가 없다. legacy에서 직접 페이지를 추가하는 경로도 문서가 명시적으로 허용한다. 기존 페이지가 전부 absolute이면 이들은 flow에 참여하지 않으므로 새 flow 페이지는 기존 배치의 끝이 아니라 첫 칸에 놓인다 (`tree.rs:1683-1700`). 로컬 엔진 실행에서 Home=(0,0), A=(110,0)을 absolute로 둔 부모에 새 flow leaf를 넣자 새 페이지도 (0,0)이 되어 Home과 겹쳤다. **해결 방향:** 복구 snapshot에 없는 page/tier를 어떻게 다룰지 정의한다. 예를 들어 복귀 전 유효 좌표를 별도 복구 입력으로 확보하거나, 미기록 페이지를 겹치지 않는 명시적 위치로 배치하는 규칙을 둔다. legacy에서 추가를 막는 정책을 택해도 derived에서 이미 추가한 페이지 및 기존 partial tier의 처리까지 필요하다. 원본 pagePositions 바이트 보존과 새 좌표의 소유권을 함께 정한다. 단순 테스트 커버리지 지적이 아니라 실제 허용된 생성→복귀 경로의 입력 누락이다.

3. **[LOW l3, deferred] 이전 설명 문구를 최신 Decision과 맞춘다.** 대안 C `:42`는 여전히 max-content, breakdown `:59`는 placement 부재 시 legacy 읽기라고 적는다. G5 `:108`도 legacy adapter가 좌표를 읽어야 하는 새 계약에서 무조건 pagePositions 참조 0을 요구한다. Decision 2/6′을 정본으로 삼아 고정 track·placementModel 기준·허용된 이관/legacy read 외 참조 0으로 정리하면 된다. 이 문구 정리만으로 별도 리뷰 라운드를 다시 열 필요는 없다.
