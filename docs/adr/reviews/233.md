### H1 — 독립 Radio origin이 Preview를 크래시시킨다

본문 Decision은 `buildCatalogOrigin("Radio")`와 상태 seed 입력만 추가하고 두 leg 해소는 무변경이라고 한다. 하지만 Components 페이지의 독립 Radio/상태 origin에는 RadioGroup 조상이 없다. 현행 `CanonicalNodeRenderer`는 Radio를 catalog RAC primitive로 직접 렌더한다(:574-644). `FormRenderers.renderRadio`의 고아 Radio용 그룹 fallback(:868)은 이 경로에서 실행되지 않으며, `ORPHAN_ITEM_HOST`(:136-142)도 Radio를 다루지 않는다.

현재 `getCatalogCutoverTypes()`를 사용한 production renderer 진단에서 독립 Radio가 `TypeError: Cannot read properties of null (reading 'isDisabled')`로 실패했다. 대조 독립 Tab은 렌더 통과했다. 이는 새 origin을 Components에 보충한 뒤 해당 페이지를 Preview로 표시하는 입력이다. 그룹 안 ref 실체화만으로 이 실패를 막지 못한다.

**해결 방향:** canonical 트리는 보존하면서 독립 Radio origin에 render-only RAC RadioGroup 호스트를 제공하는 계약을 추가한다. Selected origin은 자식 `isSelected`만으로 처리하지 말고 호스트 value와 연결해야 한다. 기존 그룹 안 instance에는 호스트를 중복 생성하지 않는다. G0/G1에 production catalog 경로의 독립 default/selected/disabled 및 그룹 안 ref 입력을 넣는다. binding 변경 없이 가능한 renderer 경계 수리로 명시한다.

### M2 — slot 보충과 BC 불변 조건 충돌

breakdown:47은 `component-tabs.slot = [default, selected]` 보충을 요구하지만 :68 및 본문 G4:109는 기존 노드 직렬화 불변을 요구한다. slot이 없는 기존 component-tabs에 이 필드를 추가하면 동일 노드 JSON은 필연적으로 달라진다. 선례 `tagGroupTemplateOrigins.ts:163-165`도 실제로 기존 root의 slot을 보충한다. 따라서 설계대로 구현하면 G4가 실패하거나, G4를 지키면 기존 Tabs origin에 Slot 편집 표면이 생기지 않는다.

**해결 방향:** 기존 사용자 저작 불변과 기존 시스템 root의 허용 보충을 구분한다. 부재 slot만 보충하고 사용자 slot은 보존하는 정책, 허용 Δ필드/Δbyte, 추가 origin 노드 수, 재hydration Δ0를 각각 명시한다. 3.3 KB는 추정치로 유지하고 G0에서 실제 직렬화 측정값을 확정한다.

### L3 — 성능 측정 명세 보완 (deferred)

### H1 — Radio/Selected fills의 두 leg 시각 계약 미충족

재현 입력: `component-radio--selected.fills = #ff0000`, value `r`인 선택 Radio instance. production `buildStateVariantProjection`→`buildSpecNodeData`와 `collectStateVariantCss`→catalog `CanonicalNodeRenderer` 경로를 동일 입력으로 실행했다.

- Canvas: root는 빨강 배경이 아니고, ring은 빨강 alpha 0, **8×8 선택 점만 빨강 alpha 1**이다.
- DOM: 실제 Radio 요소에 `data-state-origin="component-radio"`와 `data-selected`가 붙고, production CSS는 그 **Radio root에 `background-color:#FF0000`**를 출력한다.
- 동일 영역 적용 기대는 RED. 원시 결과의 Canvas root RGB는 `[0,0,0]`, dot RGBA는 `[1,0,0,1]`이다. 전체 브라우저 픽셀 비교가 아닌 production draw data/CSS target 비교임을 구분한다.

`skiaPrimitives.ts:1157-1200`과 `stateVariantResolution.ts:243-246,328-331`이 각 의미를 결정한다. 기제가 233 이전부터 있었다는 실행 기록은 맞지만, 새 Radio origin의 상태 편집을 두 leg에 같은 모습으로 반영하겠다는 이번 Hard constraint를 충족한 것은 아니다. breakdown Phase 3의 `Radio/Selected fills` 입력은 실제 G2 하니스에서 **opacity 0.2**로 바뀌었다(:562-581). opacity 전파 PASS는 이 차이를 해결하지 않는다.

해결 방향: Radio root 배경과 indicator 색의 D3 소유권을 확정하고 두 leg가 같은 영역을 칠하도록 연결한다. 새 상태 origin의 selected·unselected 및 instance override를 동일 fill 입력으로 검증한다. 의도적으로 후속으로 남길 경우 현재 Hard constraint/G2와 완료 범위를 함께 수정해야 하며, 기존 완료 기록만으로 해소 처리할 수 없다.

### M2 — 사용자 Tabs slot이 Preview에서 무시된다

재현 문서: 표준 `component-tabs.slot`의 default paddingLeft=20과 별개로, plain Tabs root의 `slot[0]`을 paddingLeft=47인 사용자 Tab origin으로 지정한다.

- Canvas `buildCanvasSceneGraph`는 해당 owner slot을 읽고 Tab 행 paddingLeft=47을 생성했다.
- Preview `App.tsx`의 **실제 templateSlotCompositions memo body**를 source에서 추출·실행하자 paddingLeft=20을 생성했다. 이 전역 template을 `renderTabs`가 모든 Tabs에 사용하므로 해당 Tabs도 20으로 렌더된다.
- 양 leg 동등 기대는 **20 ≠ 47 RED**. memo 알고리즘을 재구현한 mock이 아니라 현행 소스를 transpile해 호출했다. 전체 App mount/iframe live는 수행하지 않았다.

원인: Canvas `resolveTabTemplateOriginIds`는 owner/ownerRef 단위지만 Preview `App.tsx:451`은 항상 `byId.get("component-tabs")`만 읽고, `LayoutRenderers.tsx:124`는 `context.tabTemplate` 하나를 사용한다. 표준 원본만 쓰는 기존 테스트 2개는 이 입력을 다루지 않는다.

해결 방향: Preview에서 owner 또는 master별 slot을 같은 규칙으로 해소하고, 같은 문서 안 서로 다른 두 Tabs의 template/style이 독립적으로 선택되도록 전달한다. 사용자 slot 저장 보존(G4)과 실제 소비(G2)를 함께 검증한다.

### L3 — placeable 결정 문서 불일치 (deferred)

본문 Decision/G1은 Radio reusable `placeable:false`를 요구하지만 구현은 `reusableEntry`의 true를 사용한다. `adr233RadioOrigin.test.ts`도 true를 기대한다. breakdown 실행 기록은 AI의 기존 Radio 생성 경로를 보존하기 위한 판단이라고 설명하고, PALETTE_ORDER에는 여전히 없어 팔레트 비노출은 유지된다. 따라서 이를 제품 결함이나 팔레트 노출 회귀로 단정하지 않는다. 다만 설계대로 구현됐다고 할 때는 본문·G1을 실제 채택한 의미에 맞춰 정리해야 한다.
