## Round 3 — 2026-09-26 (reviewer: codex)

**판정: 설계 보완 필요 — HIGH 2건 pending.** 2026-09-26 재작성 본문과 breakdown의 round 3 리뷰다. 기준 HEAD는 `4d0e5bc3a`이며, 제품 코드·ADR 본문·상태는 변경하지 않았다. 이전 round 1·2는 7월의 구설계에 대한 기록으로 유지한다.

### h1 — HIGH: 더블클릭 입력에서 데이터 행 자식 경로가 먼저 사라진다

- 설계 위치: [breakdown §4](../design/150-rac-pencil-residual-interaction-execution-breakdown.md#4-phase-2--a3-데이터-행-origin-진입), 48–49행. 해석기는 hit 노드와 행 projection을 요구하지만 진입점은 `handleElementDoubleClick(elementId)`로 지정한다.
- 실제 경로: `resolveCanvasInteractionTarget.ts:160-164`가 collection projection을 owner id로 바꾼다. `useCentralCanvasPointerHandlers.ts:394-397`은 그 id만 남기고, 두 double-click 분기 `:430`, `:476-494`가 같은 id를 후단에 넘긴다. `useCanvasElementSelectionHandlers.ts:293-302`에도 raw hit 인자는 없다.
- 반례: production `buildCanonicalSceneModel`로 만든 펼친 GridList 카드의 서로 다른 Text 자식 `projection:gridlist-row:grid:a/heading`, `.../detail`을 각각 hit한 뒤 실제 target resolver와 double-click target 함수를 적용하면 모두 `grid`가 나온다. 후단에서는 어느 자식을 눌렀는지 구분할 수 없다. 이 상태에서 handler에만 새 해석기를 붙이면 G2(a)의 대응 자식 선택이 성립하지 않는다.
- 해결 방향: 단일 클릭·드래그의 owner 선택 계약은 유지하고, 선택 ID와 별개로 raw hit/projection을 double-click 경로에 보존하는 계약을 설계에 넣는다. 두 pointer 분기 모두 연결하고, 서로 다른 자식 두 개가 서로 다른 origin 자식으로 해석되는 경로로 확인한다. raw id는 해석 입력으로만 쓰며 selection에는 넣지 않는다.

### h2 — HIGH: 단일 줄이어도 ListBox 행 높이는 균일하지 않다

- 설계 위치: breakdown §3 32행은 높이 목록의 production 사용을 ADR-162 Phase 4로 미루고 이번 phase에서는 계약과 unit만 둔다. 39행과 본문 R1은 가변 높이를 wrap 문제로 다룬다.
- 실제 경로: `collectionVirtualization.ts:365-386`은 첫 행의 description만 읽어 ListBox 전체 rowHeight를 정한다. scene은 각 행의 description을 `canvasSceneNode.ts:1358-1368`에서 만들고, layout은 `utils.ts:2955-3001`에서 행별 description 유무로 높이를 계산한다.
- 반례: 폭 1000px, 높이 400px, overflow auto인 ListBox 100행에 짧은 label과 description 유무를 교대로 넣었다. production scene 행을 production `calculateContentHeight`로 계산한 높이는 32px와 50px, 합계는 4100px이다. resolver는 첫 행 32px × 100 = 3200px다. 줄바꿈과 gap을 제외하고도 900px 차이가 있어 gap·공통 metric만 정렬해도 offset 및 스크롤 범위 불일치가 남는다. 이 수치는 엔진/browser 실측이 아니라 현재 production layout helper의 실행값이다.
- 후속 책임도 비어 있다: ADR-162 본문 46행은 ListBox를 범위 밖으로 두고, breakdown 88–96행은 접힌 카드의 균일 stride를 유지하며 펼친 GridList에만 실측 높이를 공급한다. 따라서 그 phase가 이 ListBox 반례를 해소하지 않는다.
- 해결 방향: description·선택 스타일 등 layout 전에 알 수 있는 행별 차이는 150에서 실제 높이 목록에 공급하고, 동일 높이가 확인된 경우에만 균일 경로를 사용한다. wrap처럼 실측이 필요한 입력은 지원 범위·후속 owner 또는 hold 조건을 정확히 명시한다. 단일 줄 제약만으로 HC2의 행 위치 정합을 충족한다고 보지 않는다.

### h1 — HIGH: 서로 다른 데이터 카드 두 번 클릭 시 origin 페이지로 잘못 이동

- 입력·상태 → 결과: 펼친 GridList 카드 A의 제목 Text를 한 번 클릭하고 200ms 뒤 같은 GridList 카드 B의 설명 Text를 한 번 클릭한다. `resolveCanvasInteractionTarget.ts:160-164`는 두 hit를 동일 owner `grid`로 바꾼다. production `isPointerDoubleClick(commitPointerClick("grid",1000),"grid",1200)`는 `true`를 반환했다 (`pointerSession.ts:8-22`). 선택 경계 밖 `useCentralCanvasPointerHandlers.ts:418-430`과 선택 경계 안 `:476-499` 모두 owner 키를 쓰므로 두 번째 단일 클릭이 더블클릭 handler에 들어간다.
- 수리안 `breakdown:60`은 두 번째 클릭의 raw hit를 origin 해석에 쓰므로, 구현되면 사용자의 의도와 달리 카드 B의 origin 자식을 선택하며 Components 페이지로 이동한다 (`ADR-150 Decision:126`, `breakdown:62`). 기존 owner 진입의 오판이 페이지 이동으로 커진다. 본문 R7(`:154`)이 이 조건을 이미 식별하지만 owner 키 유지를 대응으로 두고, G2(`:164`)에는 서로 다른 카드의 연속 단일 클릭이 없다.
- 해결 방향: collection projected 자식에는 owner와 별도의 double-click 연속성 키(최소 raw hit 노드 ID 또는 행 key+자식 경로)를 사용한다. owner ID는 선택·드래그용으로 유지한다. 서로 다른 카드 두 번 클릭은 페이지 유지, 같은 카드 같은 자식의 두 번 클릭은 대응 origin 이동을 G2 negative/positive로 고정한다. 두 pointer 분기에 같은 판정을 적용한다.
