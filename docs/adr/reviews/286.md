# ADR-286 Review Log

## Round 1 — 2026-10-27 (reviewer: codex)

## 판정

HIGH 1 · MEDIUM 2 · pending 3. 단일 catalog 이관 방향 자체를 기각하는 것이 아니라 아래 계약을 실행 계획에 보강해야 합니다. 제품 코드·ADR 본문·Status는 변경하지 않았습니다.

### H1 — Canvas 데이터 consumer 갱신

데이터 정의를 catalog selector hook으로 옮겨도 기존 Canvas는 `CatalogBuilderCore.tsx:538-558`의 Zustand 구독으로만 행·프로젝트 변수 변경을 알게 됩니다. 공용 `compositionRoot.ts:4844-4863`은 stateVariable·view만 별도 무효화합니다. 제안한 projectVariable put을 현재 planner에 전달한 명세 probe에서 affected roots 0, 화면 문자열 Before 잔존을 확인했고 refreshState를 부르면 After로 바뀌었습니다. Phase 1에 collection·projectVariable의 consumer 무효화와 행 편집·변수 시작값·Undo의 Canvas↔Preview 검증을 추가해야 합니다. 구독 사후 갱신이 아니라 consumer 단계에서 처리해야 문서·화면 원자성도 지킵니다 ([상태 관리 규칙](../../../.claude/rules/state-management.md#L43-L45)).

### M2 — 보호 페이지 삭제

보호 목록에 넣은 페이지를 삭제하는 기존 removePage 명령은 ProjectEntry를 spread하고 pageIds만 바꾸며, removeWithReferrers도 project의 참조를 정리하지 않습니다. project를 referrer로 알려주는 reader로 실제 명령을 계획·적용해도 삭제된 id가 protectedPageIds에 남았습니다. Phase 1의 존재 검증이 추가되면 이 삭제는 거부됩니다. removePage에서 같은 트랜잭션으로 목록을 정리하고 Undo 복원·저장/재열기를 확인해야 합니다.

### M3 — RED가 현재 계약과 갈리지 않음

G0의 collection 추가 → Undo 한 번 → 문서·저장·프로젝트 파일 원상 시나리오는 현재 외부 history 구현에서도 성립합니다. 현재 createApplyDataChangeAction + dataChangeEffect + CatalogRuntime.undo를 실행한 probe에서 메모리 collection 0, DB adapter의 durable map 0, 문서 원상, pendingCount 0을 확인했습니다. 따라서 이 시나리오만 it.fails로 만들면 기대한 RED가 아니라 unexpected pass로 게이트가 실패합니다. Undo 전 collection 정의가 graph·저장 큐·내보낸 document 안에 있음을 검사하여 이관 계약이 실제로 갈리는 RED로 바꿔야 합니다.

## 실행 근거·한계

## Round 2 — 2026-10-27 (reviewer: codex)

수리 검증 1회. 미해소 HIGH 0 · MEDIUM 1 · pending 1. h1과 m3은 설계 반영을 확인했다. m2는 같은 트랜잭션에서 정리한다는 목표는 반영됐으나, 지정한 말단 블록에만 필드를 더하는 계획은 아래 조건에서 여전히 정리를 건너뛴다. 제품 코드 및 ADR 본문·Status 변경 없음.

### M2 — 빈 보호 페이지는 지정한 project 정리 위치에 도달하지 않음

breakdown:52는 `removeWithReferrers` 끝의 project 정리(1177~1182)에 site 참조를 더하도록 지정한다. 그러나 바로 앞 `if (!removedRelated.length) return`(1175) 때문에 상태 변수·인터랙션이 없는 보호 페이지 삭제는 그 블록에 도달하지 않는다. 또 `gone = new Set(removedRelated)`는 페이지·자산 ID를 담지 않는다. 이 조건을 유지한 채 site 필드만 추가하면 protectedPageIds가 남고 계획한 존재 검증이 삭제를 거부한다.

`.agent/runs/2026-10-27-review-adr286/repair-probe.test.ts`는 제안 site 필드를 가진 reader로 현행 removePage를 실행했다. 빈 보호 페이지 삭제 시 project()는 removePage 안에서만 1회 호출되고 말단 정리 블록은 실행되지 않았으며 보호 목록에 삭제 ID가 남았다(Vitest 1/1 PASS). 미래 schema를 commit한 제품 테스트는 아니다.

해결: site 참조 정리를 removedRelated 조건과 분리해 페이지만 지워도 실행하고, 실제 삭제 전체 ID 또는 draft.removed로 필터링한다. RED 7의 입력을 상태 변수·인터랙션 없는 빈 페이지로 두면 이 분기가 드러난다. 기존 m2의 보강 사항이며 새 감사 범위가 아니다. 추가 판독 라운드를 종결 조건으로 요구하지 않으며 실행자가 보강과 종결을 판단한다.

### 자산 삭제 경로 확인

자산 바이트 삭제는 `apps/builder/src/lib/assets/assetGc.ts`의 sweepOne에 있다. Builder의 `catalogRuntime/assetGc.ts:64-66,101-107`은 catalog 저장 entries·스냅샷과 메모리 payload를 root로 넘긴다. collector는 중첩 객체/배열도 걷고(`lib/assets/assetGc.ts:60-75`) 참조 중인 해시는 삭제 후보에서 제외한다(241-248). 따라서 현재 GC는 사이트 문서 참조가 남은 자산을 강제로 삭제하는 경로가 아니다. 문서의 자산 entry를 명시적으로 삭제하는 명령은 이번 조사에서 발견하지 못했다. 이는 정적 확인이며 실제 GC/IndexedDB 실행은 하지 않았다.

### 검증 범위

문서 수리 검증으로 h1/m3의 미래 제품 동작을 PASS로 판정하지 않는다. type-check·Builder live·미래 schema transaction·저장/재열기·성능·번들은 미실행 또는 UNVERIFIED. 기존 Round 1 반영 절은 실행자의 당시 보고로 보존한다.
