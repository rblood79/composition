### H1 — CardView에 존재하지 않는 loadingState를 자리 항목의 표시 원천으로 사용

- 위치: `docs/adr/design/314-skeleton-s2-wrapper-breakdown.md:62-65` (§3.4), 본문 Decision 7 / G4.
- 설계는 우선 지원 대상으로 CardView를 정하고 collection의 `loadingState`로 SkeletonCollection을 표시한다. 그러나 기존 resolver의 `LOADING_STATE_TYPES`에는 CardView가 없다 (`packages/shared/src/catalog/resolution/resolver.ts:390-399`). 실제 상태 전달은 이 목록으로 제한된다 (`:2069-2076`). §3.5는 Skeleton의 기존 등록 유지만 지정한다. 따라서 기존 collection 로딩 기구가 CardView에도 이미 전달된다는 전제는 성립하지 않는다.
- 재현: 하나의 Users collection에 Skeleton, Table, CardView를 연결하고 Preview session에서 `reload("users")`를 실행해 fetch를 미완료 상태로 둔다. 실제 Preview record는 Skeleton `isLoading=true`, Table `loadingState="loading"`, CardView `loadingState=undefined`다. 이 CardView 값에 제안한 표시 조건을 적용하면 최초 로딩 중에도 자리 항목이 나타나지 않는다.
- **실행 확인:** 기존 `openAdr280Preview` → catalog 명령 → Preview channel/session → consumer record 경로를 사용하는 임시 Vitest 프로브가 위 세 값을 assert했다. 이는 현재 전제의 반증이며 미구현 SkeletonCollection의 실행 결과를 주장하는 것은 아니다.
- 해결 방향: Phase 4에 CardView owner binding 및 ADR-310 반복 run의 조회 단위에서 loadingState를 해석해 placeholder까지 전달하는 계약을 명시한다. 단순 collection 전역 상태로 우회하지 않고 해당 owner/query의 상태를 사용해야 한다. G4는 authored loadingState를 직접 주입하지 않고 실제 collection 요청을 보류한 상태에서 검증한다.
- 함께 확정할 연결 경로: 현재 CardView nesting은 Card만 허용 (`packages/shared/src/domain/componentTraits.ts:466`), DOM도 직접 자식 Card만 render (`packages/shared/src/catalog/runtime/delegatedDom.runtime.ts:3886-3893,3930`). 새 definition을 실제 collection entry로 연결하는 변경을 명시해야 한다. 설치본 S2의 반복 개수는 `SkeletonCollection.tsx:24-43`의 type=skeleton node를 `CardView.tsx:347`의 Virtualizer 및 GridLayout/WaterfallLayout이 펼치는 결과다. 현 non-virtual grid 및 `CatalogWaterfallGrid`에 그 구현이 자동으로 적용되지는 않는다. 이는 별도 HIGH를 늘리는 근거가 아니라 Phase 4의 소비 경로를 구체화할 사항이다.

### M2 — loadingMore에서 SkeletonCollection을 제거하여 S2의 추가 로딩 표시를 누락

- 위치: `docs/adr/design/314-skeleton-s2-wrapper-breakdown.md:63`.
- 재현 상태: CardView가 기존 카드를 표시하고 ADR-310의 더 보기로 다음 페이지를 요청하여 `loadingState="loadingMore"`가 된다. 제안된 `=== "loading"`은 false이므로 자리 항목이 사라지고 기존 카드 뒤에 로딩 카드를 표시할 수 없다.
- 근거: 공식 S2 CardView 비동기 예제는 loading과 loadingMore 모두에서 SkeletonCollection을 렌더하며, loadingMore에는 기존 카드를 유지한다 ([Adobe CardView](https://react-spectrum.adobe.com/CardView), 로컬 공식 snapshot `.claude/skills/react-spectrum/references/components/CardView.md:433-452`). 설치본 S2 `CardView.tsx:305-307`도 두 상태를 로딩으로 취급한다. 현 제품도 `delegatedDom.runtime.ts:3931-3938`에서 더 보기 sentinel을 사용한다. 따라서 존재하지 않는 후속 기능에 대한 커버리지 지적이 아니다.
- 해결 방향: 일반 Skeleton의 기존 바인딩 동작(F13)과 별개로 SkeletonCollection의 상태 표를 정한다. loading은 최초 자리 항목, loadingMore는 기존 항목 뒤 자리 항목, idle/error는 자리 항목 제거를 명시하고 G4에서 두 요청 상태를 구분한다.
- 검증 수준: 공식 소스/예제 및 현 더 보기 경로의 정적 대조. 새 SkeletonCollection의 live 동작은 미구현으로 UNVERIFIED.

### M4 — waterfall의 자리 수를 GridLayout과 같게 만드는 계약은 레퍼런스와 충돌

- 위치: `docs/adr/design/314-skeleton-s2-wrapper-breakdown.md:90-93`, `docs/adr/314-skeleton-s2-wrapper.md:111,159` (Decision 7 / G4). 상태 표 `breakdown:81`의 “지금 행 끝 + 한 행”도 모든 배치 경로에 공통인 S2 규칙은 아니다.
- 새 §3.4는 waterfall의 대응 규칙을 언급하면서도 비가상 두 경로가 같은 개수 계산을 쓰고 모든 결과를 GridLayout과 같게 검사하도록 한다. 하지만 GridLayout은 행 단위로, WaterfallLayout은 **모든 열에 자리 항목이 최소 하나 들어가고 화면 높이를 채울 때까지** 반복한다. 둘은 같은 입력에도 개수가 다르다.
- **실행한 반례:** viewport 420×100, 카드 200×200, 간격 10×10, 기존 카드 1개 + type=skeleton + loader (`loadingMore`)의 동일한 RAC BaseCollection을 실제 설치본 GridLayout/WaterfallLayout에 전달했다. GridLayout은 자리 항목 **1개** `(213,10)`, WaterfallLayout은 **2개** `(213,10), (7,220)`를 만들었다. 외부 layout을 재작성한 계산기가 아니라 설치본을 직접 실행했다.
- 실제 제품 입력: 2열 waterfall CardView에서 기존 카드 1개를 유지하며 다음 페이지를 요청. 제안한 GridLayout 개수를 그대로 적용하면 왼쪽 열 아래의 두 번째 로딩 카드가 누락된다. 반대로 올바른 WaterfallLayout 결과를 구현하면 G4의 GridLayout 동일성 검사가 실패한다. 이것은 테스트 수 부족 지적이 아니라 서로 양립하지 않는 동작/판정 계약이다.
- 원인 근거: 설치 `react-stately` 3.51.0의 `dist/private/layout/GridLayout.mjs:60-115`와 `WaterfallLayout.mjs:98-112`; 현 `packages/shared/src/catalog/runtime/waterfall.ts:32-54`도 최단 열을 따라 배치한다.
- 해결 방향: **grid/flex 계열은 GridLayout, waterfall은 WaterfallLayout**을 oracle로 분리한다. 순수 함수 하나를 유지해도 되지만 layout 종류에 따른 계산과 waterfall의 열별 누적 높이(또는 기존 카드별 높이)를 입력/계약에 포함해야 한다. “지금 행 끝 + 한 행”을 일반 규칙으로 고정하지 않고 각 레퍼런스의 종료 조건으로 적는다. auto-height의 추가 행 정책은 Composition 자체 정책으로 별도 구분한다.
- 재현물: `.agent/runs/2026-11-18-adr314-review-round2/layout-probe.mjs`, 결과 `layout-probe-result.json`. 실행: `node .agent/runs/2026-11-18-adr314-review-round2/layout-probe.mjs` — assertions PASS (Grid 1 / waterfall 2).

### Phase 4에 남긴 두 구현 판단

- **Canvas 템플릿 숨김 수단:** Canvas는 템플릿 하나를 편집 대상으로 유지한다는 상태 계약이 있으므로 구체적인 UI 수단은 Phase 4에서 정해도 된다. 설계 차단 이슈 아님.
- **RAC GridList로 loadingState 전달 여부:** resolver 상태 원천 및 자리 항목/빈 상태 계약은 이미 정해졌다. Table도 `domBinding.runtime.ts:3026-3035`에서 root prop을 제거하고 body의 빈 상태를 별도 처리한다. GridList 전달 여부는 설치 RAC의 실제 소비 계약에 따라 Phase 4에서 결정할 구현 사항이며, prop 전달 자체가 목표가 아니다. 실제 aria-busy/빈 상태 동작은 그때 검증한다.
