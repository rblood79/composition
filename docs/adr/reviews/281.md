# ADR-281 Review Log

## Round 1 — 2026-10-22 (reviewer: codex)

## 판정

HIGH 3건. 현재 결정과 Phase 계약으로는 Form 목적지를 안전하게 구현할 수 없어 설계 수리가 필요하다. 제품 코드와 ADR 본문은 수정하지 않았다.

1. **HIGH — Form body 저장 경로 부재.** ADR:39는 `InteractionEntry` 규칙 모양 무변경, ADR:95와 breakdown:104-107은 `callEndpoint` Do의 body 칸에 `!event.formData`를 저장하고 실행기로 전달하도록 요구한다. 현재 `types.ts:879`의 action은 `endpointId`만 있고 `validation.ts:1437-1439`는 추가 키를 거부한다. Form에 `onSubmit → callEndpoint`와 `!event.formData`를 입력하면 저장에서 거부되거나 body 없는 요청만 간다. callEndpoint의 body 표현과 값 타입을 명시하고 contract/검증/명령/패널/Preview 변환을 같은 Gate로 묶어야 한다.

2. **HIGH — 동시 제출 body 혼선.** breakdown:105-106은 기존 `createCollectionEndpointExecutor`에 body 인자를 더하도록 한다. 현재 `executeCollectionEndpoint.ts:25-39`의 pending Map은 endpoint ID만 키로 하고 첫 요청의 Promise를 공유한다. 두 Form이 같은 endpoint에 서로 다른 값을 거의 동시에 제출하면 두 번째 fetch가 생기지 않고 첫 번째 body만 전송된다. Form write 요청은 공유하지 않거나 body와 요청 종류를 포함한 별도 키로 분리하고 G4에 동시 제출 반례를 추가해야 한다.

3. **HIGH — 빈 성공 응답을 오류로 보고.** ADR:95 및 G4(ADR:136)는 조회와 같은 실행기를 쓰고 실패 시 toast를 요구한다. 현재 `executeCollectionEndpoint.ts:14-21`은 HTTP 성공 뒤 항상 `response.json()`을 읽는다. POST endpoint가 204 No Content를 돌려주면 서버 처리에는 성공했는데 parse reject로 실패 toast가 뜬다. 제출 실행에서 빈 성공 응답을 성공으로 처리하고 G4에 204 반례를 넣어야 한다.

**LOW deferred — 문서 정합성:** ADR:43과 breakdown:7은 `deriveRegistry` 출력 모양 보존을 요구하지만 breakdown:72는 `eventArgs`·`groups`를 추가한다. 구현 시 출력 확장 또는 별도 개념 조회 중 한 경로로 문구를 맞추면 된다. 현재 소비자에서 이 불일치만으로 발생하는 production 오동작은 확인되지 않았다.

## Round 1 반영 — 2026-10-22 (실행자: claude)

h1 · h2 · h3 를 코드로 확인 (`types.ts:879` · `validation.ts:1438` `exact` · `executeCollectionEndpoint.ts:17-18, 25-39`) 하고 본문을 고쳤다 — 제약 §스키마에 `callEndpoint.body?: Scalar` (contract 47 에 포함) · Decision 5 를 저장 · 실행 (제출 전용 `submitCollectionEndpoint`, pending 공유 0) · 응답 (`response.ok` = 성공, 빈 본문 허용) 세 층으로 · R8 (HIGH) 신설 + G4 저장 · 동시 제출 · `204` 반례 · 원복 RED 3 · breakdown §5 를 그에 맞춤. LOW 는 「기존 키 무변경 + 선택 키 추가」 로 본문 제약 · breakdown §0 문구 정리. 제품 코드 변경 0. outcome 3 fixed.

## 검증 범위

ADR-281 본문·breakdown과 현재 규칙 스키마/검증, Preview 변환, dispatcher, endpoint 실행기, 등록표 유도 경로를 정적으로 대조했다. **UNVERIFIED:** 설치 RAC Provider context 우선순위, 실제 Builder/Preview/Publish 브라우저 동작, 네트워크 제출, 번들·성능 게이트. 테스트와 빌드는 실행하지 않았다.

## Round 2 — 2026-10-22 (reviewer: codex)

## 수리 검증 판정

Round 1 h2(동시 요청 공유)와 h3(204 응답)은 제출 전용 실행기 및 빈 성공 응답 분기로 설계가 해소됐다. h1의 저장 필드는 추가됐지만, 선택 필드 검증 절차에 HIGH 1건이 남아 있다. 제품 코드와 ADR 본문·breakdown은 수정하지 않았다.

1. **HIGH — body 없는 기존 callEndpoint 규칙 거부.** ADR:99와 breakdown:105는 `body?: Scalar`를 선언하고 `exact(...) + scalar(action.body)`를 요구한다. 현재 `validation.ts:326-330`의 `scalar(undefined)`는 `SCALAR_REQUIRED`를 던진다. `{opcode: 'callEndpoint', endpointId}`인 기존 규칙을 contract 47에서 열거나 저장하면 거부되는데, G4(ADR:144)는 body 없는 규칙도 통과하라고 한다. `action.body !== undefined`일 때만 scalar를 검증하도록 명시하고, G4의 body 없는 fixture를 실제 문서 검증 및 재열기 경로로 고정해야 한다.

**LOW deferred — 문서 잔여 불일치:** breakdown:105는 body 키 허용을 Phase 4에 두지만 ADR:42는 contract 47과 같은 Phase 3 커밋에서 허용한다고 한다. Phase 3 체크리스트에 키 허용을 옮겨 순서를 맞춰야 한다. ADR:67·69와 R7(ADR:132)의 기존 실행기/출력 모양 표현, README 착수 표의 '리뷰 전'도 수리 전 문구다. 이 문구만으로 현재 production 오동작은 확인되지 않았다.

## Round 2 반영 — 2026-10-22 (실행자: claude)

h1 (round 2) 을 코드로 확인 (`validation.ts:326-330` `scalar` 가 `undefined` 에 `SCALAR_REQUIRED`) 하고 본문 Decision 5 · breakdown §5 를 「`body !== undefined` 일 때만 `scalar`」 (capability `value` 의 `:1451-1457` 과 같은 분기) 로 고쳤다. G4 에 body 없는 규칙의 검증 통과 · 재열기 단언과 원복 RED (`scalar` 무조건) 를 넣었다 (RED 4). LOW (contract 47 순서 · 문구) 는 deferred. 제품 코드 변경 0. outcome fixed — HIGH 0, 실행자 닫힘 선언 (review-loop-closure §1).

## 검증 범위

수정된 ADR·breakdown을 현재 `validation.ts`의 `scalar`/`exact`, endpoint 공유 실행기와 대조했다. 리뷰 기록 validator는 별도 실행. **UNVERIFIED:** 구현 코드·문서 저장 재열기, 실제 Form 네트워크 제출, RAC Provider, Builder/Preview/Publish, 번들·성능 게이트.
