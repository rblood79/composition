### H1. CSS 출력 순서만으로 트리의 부모 우선순위를 구현할 수 없다

- 대상: `docs/adr/297-rule-state-condition-tree-single-priority.md:115`, `:127`; `docs/adr/design/297-rule-state-condition-tree-breakdown.md:121-123`.
- 입력 → 잘못된 결과: `borderColor = { isQuiet: { isHovered: red }, isInvalid: blue }`에서 quiet·hover·invalid가 동시에 참이면 evaluator는 나중 부모 조건인 blue를 골라야 한다. 제안된 raw selector 맵대로 출력하면 `.react-aria-Input[data-quiet][data-hovered]`의 specificity는 0-3-0, 뒤의 `.react-aria-Input[data-invalid]`는 0-2-0이다. CSS는 앞의 red를 유지한다. Phase 3에서 `legacyOrder`를 지우는 것만으로 같은 트리의 의미가 같아지지 않는다. quiet+hover+invalid는 기존 Input/DateInput이 이미 지원하는 조합이다 (`componentRulesTable.ts:3770-3787`, `quietStyles.ts:17-29`).
- 실행 근거: 격리 Chromium에서 위 CSS를 적용한 계산값은 raw `rgb(255, 0, 0)`, 조건을 `:where()`로 정규화한 대조군은 `rgb(0, 0, 255)`였다. 이 실행은 제안된 compiler 계약의 반례이며 현 Builder의 새 구현 결함 재현으로 취급하지 않는다.
- 근본 원인: S2는 단순한 selector 출력 순서만 사용하지 않는다. 설치본 `style-macro.ts:471-474, 575-591, 995-1019`에서 layer priority와 역순 조건 분기/class 선택을 함께 사용한다. 이 구현을 근거로 삼으면서 해당 의미를 보장할 대체 계약을 빠뜨렸다. CSS도 specificity를 source order보다 먼저 비교한다 ([W3C CSS Cascade](https://www.w3.org/TR/css-cascade-5/#cascade-sort)).
- 해결 방향: compiler가 같은 layer·target 안에서 조건 specificity를 정규화하거나 순서를 표현하는 priority layer/배타 selector를 생성하도록 계약을 확정한다. `domOnly`, 기존 수동 CSS, authored state `!important`와의 상대 우선순위도 정하고, 부모/자식 깊이가 다른 겹침 조합에서 evaluator와 실제 computed style을 대조하는 gate를 둔다.

### h3 HIGH — domOnly와 공통 트리의 같은 속성 전면 금지는 기존 focus 스타일을 표현하지 못한다

- 대상: `docs/adr/297-rule-state-condition-tree-single-priority.md:117`, `:169` (G3 (e)); `docs/adr/design/297-rule-state-condition-tree-breakdown.md:125`.
- 소스 반례: Input의 `&[data-invalid]`는 `border-color: var(--negative)` (`componentRulesTable.ts:6695-6698`)이고 Decision 1 (`본문:108`)에 따라 공통 `isInvalid` 트리로 옮긴다. 같은 Input의 `&:is([data-focused], [data-focus-within])`도 `border-color: var(--accent-content)` (`componentRulesTable.ts:6688-6693`)를 쓴다. `isFocused`/`isFocusWithin`은 닫힌 조건 어휘에 없고 `:focus-within`은 DOM 전용이라고 명시되어 있으므로 이 focus 분기는 domOnly로 보존해야 한다. DateInput도 `:3741-3751`에서 동일하다.
- 입력 → 잘못된 결과: 유효한 Input에 마우스로 포커스를 주는 상태 (`data-focused`, `data-focus-visible` 없음)는 기존 focus 테두리를 적용한다. 새 G3 (e)를 만족하려고 domOnly의 `border-color`를 제거하면 기본 테두리로 남는다. 그 선언을 보존하면 같은 rule의 `isInvalid` 트리와 같은 속성이라는 이유로 G3 (e)가 실패한다. `isFocusVisible`로 바꾸면 마우스 포커스를 보존하지 못한다. 이는 기존 지원 상태를 새 형식으로 옮길 수 없는 계약 충돌이며, 누락된 테스트만의 문제가 아니다.
- 실행 확인: 실제 `COMPONENT_RULES_TABLE`을 로드한 진단에서 Input·DateInput 모두 공통 invalid 선언과 DOM focus 선언의 `border-color` 교집합을 확인했다 (1/1 PASS). 기존 Input focus 선언을 추출한 축소 Chromium fixture에서는 focus 테두리가 `rgb(0, 68, 255)`, 충돌한다고 금지된 DOM 선언만 제거한 arm에서는 기본 `rgb(80, 80, 80)`였다. 새 G3 구현은 아직 없으므로 진단은 **문서 제약의 반례**다.
- 해결 방향: 같은 속성 자체를 금지하지 말고 DOM 전용 상태가 덮는 속성·대상·우선순위를 명시한 override를 허용한다. G3 (e)는 미선언/모호한 교차 override를 거부하도록 좁힌다. 현재의 domOnly 경계를 유지하면서 기존 focused·focus-within의 border-color를 보존하고, 이 경우는 evaluator 동일값 대조와 구분해 DOM oracle로 검증한다.
