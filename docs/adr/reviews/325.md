# ADR-325 Review Log

## Round 1 — 2026-11-26 (reviewer: codex)

설계 승인 보류. HIGH 6건이 남았다. 검토 기준은 `da32fc4e2`이다.

### H1. 편집 번호 하나로는 여러 행 붙여넣기의 일부 성공을 확정할 수 없다

Table의 updateMany 한 번은 두 행에 같은 seq를 준다. 행 A가 204, B가 422일 때 confirmChanges([seq])는 성공한 행만 지정할 수 없다. 빈 204에는 이를 보완할 서버 행도 없다.

저장 확인 입력에 Collection·행 키·보낸 필드와 편집 번호를 묶는다. 한 paste에서 A만 확정되고 B의 값·오류·미저장 표시가 남는 경우를 325 G2와 324 G3에서 같은 입력으로 확인한다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:99`, `packages/shared/src/catalog/runtime/catalogPreviewSession.ts:1595`이다.

### H2. 저장 응답을 기다리는 동안 원래 값으로 되돌리면 최신 편집이 사라진다

3에서 5로 바꿔 전송한 뒤 응답 전에 3으로 되돌리면 합치기 규칙이 필드와 최신 seq를 지운다. 서버가 5를 확정한 뒤 다음 저장에서 3을 보낼 근거가 사라진다. 전송 중인 신규 행을 삭제할 때도 insert와 remove가 상쇄된다.

전송 시점의 변경 스냅샷과 이후의 사용자 의도를 결과 판정까지 구분한다. 성공이면 확인값 위에서 이후 편집을 다시 계산하고, 거절이면 기존 기준에서 상쇄한다. 성공·거절·응답 유실과 서버 생성 키가 있는 넣기 뒤 삭제를 G2에 둔다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:89`, `docs/adr/design/324-collection-manual-batch-save-breakdown.md:248`이다.

### H3. 조회별 순번은 서로 다른 조회가 공유하는 행의 역행을 막지 못한다

보기 A에서 id=42의 이전 값을 읽은 요청이 지연되고 보기 B가 같은 id의 새 값을 먼저 받는다. 두 응답이 각각 자기 조회의 최신이므로 A의 늦은 응답도 rows[42]를 교체해 B까지 예전 값을 보인다. 결과·변경 revision만으로 메모하면 반대로 갱신을 놓칠 수도 있다.

결과의 키 목록을 채택하는 규칙과 공유 행의 값을 교체하는 규칙을 구분한다. 행 버전이나 명시한 요청 세대 규칙으로 오래된 쓰기를 막고, 실제로 바뀐 행을 읽는 보기의 캐시를 무효화한다. 두 조회에 같은 키·다른 값을 넣고 응답 순서를 뒤집어 G3에서 확인한다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:109`, `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:97`이다.

### H4. 키 없는 원격 목록 두 개가 같은 위치 키를 공유한다

조건이 다른 두 목록의 첫 행은 둘 다 row-1이다. Collection 단위 rows와 changes에 같은 키를 넣으면 뒤 응답이 앞 목록의 행을 바꾸거나 한쪽 편집이 다른 쪽에 보인다. 재조회 때 편집을 버리는 U1로는 동시에 열린 두 목록을 격리할 수 없다.

안정 키가 없는 행은 조회 결과와 그 세대 안에서만 유효한 내부 식별자로 격리한다. U1 검증에 동시에 열린 두 결과를 넣는다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:105`, `packages/shared/src/collections/resolveCollectionItems.ts:340`이다.

### H5. URL cursor를 그대로 따라가는 다음 페이지가 첫 페이지와 같은 조회 키를 쓴다

cursor 템플릿이 없는 /orders에서 다음 URL /orders?next=k2를 받으면 fetch 대상은 달라진다. ADR이 재사용하는 resolvedEndpointUrl은 두 번 모두 /orders?를 돌려준다. 그 키로 결과를 공유하면 다음 요청을 생략하거나 첫 페이지 키 목록을 교체한다.

최종 fetch 대상 URL과 실제 본문을 요청 생성 시 한 번 계산해 조회 키에도 쓴다. 별도로 페이지들을 어느 목록에 이어 붙이는지 기록한다. G1/G3에서 첫 페이지·다음 URL의 요청 2건과 양쪽 행을 검증한다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:107`, `packages/shared/src/collections/executeCollectionEndpoint.ts:146`이다.

### H6. cursor가 없는 번호 페이지를 전체 데이터로 재사용할 수 있다

기존 번호 페이지 fixture는 전체 250행에서 20행과 total=250만 돌려준다. cursor가 없다는 조건으로 전체 조회 완료로 처리하면 2쪽 이후에만 있는 행을 찾는 다른 보기가 서버에 요청하지 않고 빈 결과를 낸다.

페이지 범위와 전체 수집 완료를 별도로 표현한다. 조건·원본이 같은 전체 범위의 수집을 확인한 경우에만 로컬 평가로 대체하고, 완료 여부를 모르면 서버에 요청한다. G3에 번호 페이지와 total 미제공 사례를 추가한다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:109`, `apps/builder/src/preview/catalog/__tests__/adr310Pages.test.tsx:219`이다.

### 검증 범위

현재 요청 함수를 fetch 대역으로 실행했다. 기본 URL과 URL cursor의 fetch 대상은 서로 달랐고 resolvedEndpointUrl은 같았다. items 한 행과 total=13을 받은 조회 결과에는 cursor가 없었다. 기존 Vitest 5파일 29건에서 여러 행 쓰기·편집 표시·즉시 저장 확인·번호 페이지·URL cursor 경로를 확인했다. 제안된 저장소·수동 저장·Publish 브라우저 동작·고객 서버 및 성능 Gate는 UNVERIFIED다.

## Round 2 — 2026-11-27 (reviewer: codex)

설계 승인 보류. 기존 h1·h2·h3·h4·h5 수리 확인, h6 부분 수리, 신규 h7·h8. 현재 HIGH 3건이다.

Round 1 h1·h2의 두 행 부분 성공과 3→5 전송 뒤 3으로 원복하는 세 판정을 대입했다. h3은 살아 있는 공유 행에서 출발 순번과 모든 읽는 결과의 revision으로 원래 반례를 막는다. 출발 순번은 서버 버전의 순서를 보장하지 않으며 다음 조회가 실제로 실행됐을 때 재동기화된다. h4의 요청·세대·위치 조합과 h5의 최종 fetch 주소·method·본문 기반 키 및 ListKey 분리도 원래 반례를 막는다. 새 h7은 삭제, h8은 겹치는 즉시 저장의 판정 순서에 해당한다.

### H6. 페이지 선언과 total이 없는 제한 응답도 전체로 확정한다

조회 함수에 조건·페이지 인수 없는 /orders를 주고 서버가 기본 20행만 반환하게 했다. 실제 결과는 20행, cursor·total 모두 undefined였고 같은 서버의 필터 조회는 id=250을 반환했다. 명시된 마지막 분기는 첫 응답을 complete로 판정해 필터 조회를 생략한다. 324의 삭제 확인에도 잘못된 부재 근거가 된다.

서버가 한 응답에 전체를 제공한다는 보장이나 수집 종료 근거가 없으면 complete를 false로 둔다. 기본 상한이 있는 동일 서버에서 필터 요청 1회와 범위 밖 삭제 미확정을 검증한다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:214`이다.

### H7. 삭제 확정과 함께 순번도 사라져 이전 조회가 행을 다시 넣는다

CRUD 대역에서 u4가 들어 있는 목록 응답을 잡아 두고 DELETE를 실행했다. DELETE는 204, 이후 단건 GET은 404였다. 설계대로 행과 키 목록을 제거한 뒤 앞선 목록 응답을 적용하면 비교할 StoredRow.at가 없어 u4가 다시 들어간다. 시간 역순으로 서버가 읽는다는 가정도 필요하지 않다.

삭제 확정 순번을 삭제된 키에 보존하거나 이전 요청을 무효화한다. 먼저 출발한 조회가 행 값과 목록 멤버십 양쪽에서 삭제를 되돌리지 못해야 한다. 관련 규칙은 상세 설계 179·189~191행이다.

근거는 `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:175`이다.

### H8. 기존 즉시 저장의 성공 응답이 역순이면 먼저 보낸 값이 다시 확정된다

현재 createElementHandlers로 같은 행을 5(seq 1), 8(seq 2) 순으로 두 번 저장하고 응답만 뒤집었다. 성공 콜백은 [2], [1] 순이었다. 서버가 5, 8 순으로 적용했어도 새 규칙은 판정 순간마다 새 순번을 주므로 마지막 콜백이 깨끗한 행을 5로 되돌릴 수 있다.

같은 행·필드의 저장 요청과 확정을 직렬화하거나, 이미 확정한 후속 편집 번호를 기록해 이전 티켓이 역행시킬 수 없도록 한다. 서버 적용 순서가 불명확한 연결은 원본을 다시 읽는 판정을 분리한다. 현행 성공 배선은 packages/shared/src/interactions/bindings.ts:147이다.
