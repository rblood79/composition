# ADR-218 Review Log

## Round 1 — 2026-09-12 (reviewer: codex)

검토 기준: HEAD `723339712`, 작업 시작 시 clean worktree. 본문과 breakdown 전체 및 현재 실행·영속·동기화 소비 경로를 정적 대조했다. 결론은 **수정 후 재리뷰 — HIGH 2, MEDIUM 3**. ADR-152 후속으로 분리한 범위와 ADR-212 종결은 유지한다. 저장소 분리 대안 B 자체를 기각하는 판정은 아니다.

### 발견 사항

1. **[HIGH h1] 캐시가 현재 스키마·소스에 유효한지 판정할 계약이 없다.**
   본문 45–53행은 collectionId 키의 별도 store를 정하고 R1/G1(96/108행)은 삭제 시 정리만 요구한다. 하지만 `apps/builder/src/builder/stores/utils/dataChange.ts:679-687`의 필드 rename은 runtimeData 행 key도 변경한다. API 응답 캐시 저장 → 필드 rename → reload 시, 캐시가 같이 변환되지 않으면 현재 schema와 옛 key의 응답이 섞인다. Settings의 endpoint 교체나 responseMapping 변경 후 같은 collectionId로 이전 결과를 복원하는 경우도 빠져 있다. 캐시의 source/schema revision 또는 변환·무효화 규칙, hydration 적용 순서, Undo/Redo 시 처리까지 정하고 G1에 rename→reload / 소스 교체→offline reload를 넣어야 한다. 이는 새 기능 구현이 아직 없다는 지적이 아니라 분리한 두 저장소가 일치해야 하는 시점의 계약 누락이다.

2. **[HIGH h2] 타이머 정리만으로 늦은 응답의 덮어쓰기를 막을 수 없다.**
   breakdown 50행과 본문 98/110행은 interval 정리 후 timer 0만 요구한다. 현재 `apps/builder/src/builder/stores/utils/dataActions.ts:543-561`은 loadingApis를 조회한 뒤 중복 차단 없이 추가하며, 680–693행의 AbortController는 함수 내부 timeout 전용이다. 722–745행은 완료 시점에 collection을 찾아 응답을 쓴다. 요청 A가 느리고 이후 B가 먼저 성공하면 A가 최신 값을 덮어쓸 수 있고, 페이지 전환·정책 변경 후에도 이미 시작한 요청은 완료될 수 있다. 영속화를 붙이면 다음 세션까지 오래된 값이 남는다. single-flight 또는 세대별 응답 수용 규칙, 정지 시 취소/완료 무시, hydration과 새 응답의 우선순위를 정해야 한다. G3에는 A/B 역순 완료와 정지 후 완료 검사를 추가해야 한다.

3. **[MEDIUM m3] endpoint picker가 바꿀 정본 관계와 역연산이 없다.**
   breakdown 45–46행은 picker와 applyDataChange만 요구한다. 현재 `apps/builder/src/builder/stores/utils/dataChange.ts:785-798`은 endpointId가 들어오면 throw한다. `apps/builder/src/builder/main/BuilderCore.tsx:897-911`은 endpoint.targetCollectionId/이름을 역조회해 첫 항목을 실행한다. 따라서 선택 UI만 연결하면 오류가 나거나 이전 endpoint가 계속 선택될 수 있다. collection당 연결 cardinality, 기존 연결 해제, endpoint 재사용/삭제, Undo/Redo를 정의하고, `set_source` 확장인지 `define_endpoint` 묶음인지 지정해야 한다. 정책 쓰기 역시 DataOp 스키마·역연산·persistablePatch(동 파일 1020–1026행) 배선을 변경표에 명시하면 HC2를 검증할 수 있다.

4. **[MEDIUM m4] auto의 Preview 실행 소유자와 경계가 불명확하다.**
   본문 12행/인벤토리 23행의 “Send 클릭만, refreshInterval/setInterval 0”은 전체 코드 사실과 다르다. `apps/builder/src/services/agent/dataAgentCommands.ts:96`과 BuilderCore 911행도 실행하며, `packages/shared/src/hooks/useCollectionData.tsx:517-530`에는 legacy API binding용 interval이 있다. 이것이 collection-level executionPolicy가 이미 있다는 뜻은 아니다. 두 정책의 적용 범위를 구분해야 한다. breakdown 50행은 미리보기 열 때 auto를 요구하지만 본문 16행은 사용자 표면인 Settings UI에 Preview 대응물이 없다고 설명하고, 변경표에는 Preview 소비 경로가 없다. `packages/shared/src/collections/collectionSnapshot.ts:35-45`는 allowlist projection이고 56–69행은 Preview/Publish 공용 서비스다. 본문 47행의 정책 export를 충족하려면 이 전달 경로도 다뤄야 한다. Builder가 Preview 열기 전에 실행하는지 Preview가 직접 실행하는지, 편집기를 닫았을 때 interval이 계속되는지, 기존 binding 정책과 Publish의 적용 범위를 명시해야 한다. G3은 실제 헤더 Preview 진입과 endpoint 호출 수로 검증해야 한다. raw response postMessage는 `dataChange.ts:113-123`에 이미 존재하므로 export 제외와 postMessage 제외를 같은 정책으로 취급해서도 안 된다.

5. **[MEDIUM m5] 성능 Gate를 동일 조건으로 재현할 기준이 없다.**
   본문 G0/G3(107–110행), breakdown 28/35/69–71행은 크기 실측·대용량·interval 누적·initial 증가 0을 요구하지만 표본 수/행·byte 규모, 이전 arm, visible 상태, 측정 조건, latency/저장 비용 기준이 없다. `.claude/rules/measurement-validity.md` §1의 표본 대표성·불리 케이스·대조군·측정 조건 요구에 미달한다. Phase 0에서 freeze할 fixture/규모, 동일 build 설정의 기준 SHA와 initial 집계 단위, 반복 주기/실행 시간, IDB 저장 및 복원 비용 판정 기준을 정해야 한다. 수치 실측은 Phase 0에서 수행해도 되며 현재 리뷰에서 성능 FAIL을 주장하는 것은 아니다.
