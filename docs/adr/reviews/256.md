### h1 — HIGH · 가장 가까운 상태 조상 하나로 고정하면 Disclosure trigger 안의 펼침 표시를 표현할 수 없다

- 대상: `docs/adr/256-rac-composition-level.md:131-134` (Decision 7), 같은 파일 `:175` (G3).
- 입력 → 결과: `Disclosure(isExpanded=true) > Heading > Button(slot=trigger) > Icon(showWhen=isExpanded)`에서 ADR의 가장 가까운 상태 주체는 Button이다. 설치 RAC Button render props에는 `isExpanded`가 없으므로 조건은 성립하지 않거나 미지원으로 거부된다. 반면 실제 RAC 조립은 바깥 Disclosure render callback의 `isExpanded`를 Button 안에서 읽어 펼침 아이콘을 그릴 수 있다. 따라서 G3의 펼침 아이콘 동등성을 정해진 규칙으로 달성할 수 없다.
- 추가 확인: Decision 7은 Group을 상태 없는 통과 노드로 규정하지만 RAC Group은 자체 `isInvalid`, `isDisabled`, `isHovered`, `isFocusVisible` 등을 제공한다. `CheckboxField(isInvalid=false) > Group(isInvalid=true)`의 두 값은 실제로 false/true다. Group을 무조건 통과시키면 Group 자신의 상태도 표현할 수 없다.
- 근거: `packages/shared/node_modules/react-aria-components/dist/private/Button.mjs:42-56`, `Disclosure.mjs:89-96`, `Group.mjs:37-45`. production RAC 1.21.0 SSR에서 Disclosure `outerExpanded=true`, Button `isExpanded=undefined`; Group 자체 invalid=true 확인.
- 해결 방향: 노드 표시 조건이 참조하는 상태 소유자를 표현하거나, 조건 키별 제공자 해석과 명확한 shadow 규칙을 정한다. 서로 다른 조상의 동명 상태를 구분할 수 있어야 한다. Group은 실제 상태 제공자로 취급하되, 바깥 상태 참조도 유지할 수 있어야 한다. 임의 표현식 언어 도입은 필요하지 않다.

### h2 — HIGH · 이름 있는 slot 계약이 실제 RAC 제공자와 다르고, slot 없는 자유 Text도 throw 한다

- 대상: `docs/adr/256-rac-composition-level.md:127` (Decision 4), `:165` (R10).
- 입력 → 결과 1: 문서가 허용 예로 적은 `Tag > Text(slot=label)`을 `TagGroup > TagList` 안에서 렌더링하면 `Invalid slot "label". Valid slot names are "description" and "errorMessage".`가 발생한다. Tag는 Text label slot을 제공하지 않으므로 바깥 TagGroup의 TextContext를 읽는다. 같은 위치의 plain span은 정상이다.
- 입력 → 결과 2: `TextField > Input + Text("Extra")`에서 Decision 4의 "slot을 주는 부모 안의 Text는 RAC Text"를 적용하면 `A slot prop is required`가 발생한다. `Text(slot=null)`로 context를 끊는 대조군은 정상이다. R10이 오류를 인지하고 있어도 제공자 유무만으로 분기하는 Decision 4에는 slot 미지정/제거 시의 정상 출력 경로가 없다. 오류 경계는 누락 없이 그리는 목표를 대신하지 못한다.
- 표의 다른 오류: `remove`의 ButtonContext 제공자는 TagGroup이 아니라 각 Tag이고, `chevron`은 Tree가 아니라 TreeItem, `selection` CheckboxContext는 toggle이 아니라 GridListItem/TreeItem 등 collection item에서 제공한다. 이 표를 그대로 삽입/slot UI의 정본으로 사용하면 올바른 조립은 빠지고 잘못된 조립이 노출된다.
- 근거: `packages/shared/node_modules/react-aria-components/dist/private/utils.mjs:76-91` (`useSlottedContext`의 context별 조회와 slot=null opt-out), `Text.mjs:19-27`, `TagGroup.mjs:123-129,228-247`, `GridList.mjs:373-390`, `Tree.mjs:591-620`. 위 두 오류는 production RAC 1.21.0 SSR 재현, 각각 정상 대조군 확인.
- 해결 방향: 제공자 표를 실제 consumer context(Text/Button/Checkbox 등)별로 정정한다. 제공자 경계·중간 노드 통과·기본 slot·명시 opt-out을 구분하고, slot이 없는 자유 Text 및 사용자가 slot을 지운 경우의 plain 요소/context opt-out 경로를 결정한다. `props.slot` 저작 모델에 null을 넣을지 별도 모드로 나타낼지도 명시한다.

### m1 — MEDIUM · boolean 상태만 받는 showWhen으로 빈 description/label 조건을 대체할 수 없다

### h1 — HIGH · 미지정 slot을 null로 바꾸면 유효한 기본 slot과 이름 없는 context를 끊는다

- 위치: `docs/adr/256-rac-composition-level.md:129` (Decision 4), `:168` (R10), `docs/adr/design/256-rac-composition-level-breakdown.md:58`.
- 왜 틀렸는가: 설치 RAC `utils.mjs:77-91`은 slot이 없으면 `DEFAULT_SLOT`을 찾고, `slots` 표가 없는 context는 그대로 사용한다. 오류는 해당 기본 slot이 없는 slotted context에서만 발생한다. 수정 문장은 미지정·제거를 모두 slot=null로 바꾸므로 이 두 정상 경로를 무효화한다. slot=null이 Text/Button/Heading 모두에서 throw 없이 context를 건너뛴다는 사실은 확인했지만, 모든 미지정 slot에 적용해도 된다는 뜻은 아니다.
- 재현 A: `ListBox > ListBoxItem > Text("Alpha")`. 원본 RAC는 기본 Text slot에서 id를 받아 option의 aria-labelledby가 Text를 가리킨다. 수정 규칙에 따라 `Text slot={null}`로 바꾸면 Text의 id가 사라져 aria-labelledby의 대상이 없어진다. 예외는 발생하지 않는다.
- 재현 B: `Select(isDisabled=true) > Button("Open")`. 원본 Button에는 disabled, aria-haspopup=listbox, aria-expanded=false가 있다. slot=null 대조군은 세 속성을 모두 잃고 focus 가능한 독립 버튼이 된다. Select의 ButtonContext는 이름 목록이 없는 일반 context다 (`Select.mjs:155-173`). Decision 5의 필수 trigger context 관계 및 Decision 11의 ARIA 구조 동등성과 직접 충돌한다.
- 제공자 표 잔존 오류: `TagGroup → remove`가 아니라 Tag가 ButtonContext.remove를 제공한다. `Tree → chevron/drag`는 TreeItem, `Table → chevron/drag`는 Row가 제공한다. SSR context 관찰과 `TagGroup.mjs:228-247`, `Tree.mjs:591-620`, `Table.mjs:1103-1137`을 대조했다. Text 표의 ListBoxItem/MenuItem/GridListItem/Dialog/Toast 및 field·Calendar slots와 Dialog Heading slots는 확인 범위에서 소스와 일치한다.
- 해결 방향: (1) 명시 null opt-out, (2) 유효한 명시 이름, (3) 생략 시 DEFAULT_SLOT, (4) slots 표가 없는 일반 context를 구분한다. 실제 잘못된 이름/기본 slot 부재만 연결 안 됨으로 처리하고, 필수 trigger의 연결을 끊는 편집은 Decision 5와 같은 검증을 거친다. 제공자 표는 실제 context를 제공하는 노드 이름으로 정정한다.

### h2 — HIGH · 빈 바인딩 노드의 일괄 생략이 RAC validation 메시지와 비텍스트 자식을 제거한다

- 위치: `docs/adr/256-rac-composition-level.md:135` (Decision 7), `docs/adr/design/256-rac-composition-level-breakdown.md:59`.
- 재현 A: 사용자 errorMessage 바인딩은 빈 문자열이고, Form의 `validationErrors.email="Server rejected email"`인 `TextField(name=email, validationBehavior=aria) > Input + FieldError`를 마운트한다. 원본 RAC는 invalid 상태에서 자체 validationErrors를 기본 자식으로 사용해 메시지를 출력한다. ADR의 빈 바인딩 규칙으로 FieldError 자체를 생략하면 메시지와 그 id가 사라진다. invalid 판정을 RAC에 맡겨도 FieldError가 마운트되지 않으므로 복구할 수 없다.
- 현재 경로: `delegatedDom.tsx:364-366`은 빈 문구여도 FieldError 노드를 넘기고, `domBinding.tsx:642-648`은 빈 children을 undefined로 넘겨 RAC fallback을 유지한다. `FieldError.mjs:21-41`은 validationErrors를 defaultChildren으로 사용한다. 따라서 `presence.ts:233-237`의 저장값 기준 Canvas 판정만 일반화하면 현재 Preview의 동작을 빠뜨린다. 본문의 "지금 조건부 부품을 이 규칙 하나로 옮긴다"가 성립하지 않는다.
- 재현 B: `NumberField > Button(slot=decrement, aria-label=Decrease, children="{label}") + Input`, Button 안에 svg 자식이 있고 label=""인 조립은 RAC에서 유효한 아이콘 버튼이다. 글자 바인딩이 빈 것만으로 노드 전체를 지우면 svg 및 증감 버튼을 함께 없애 Decision 5의 필수 부품 존재와 충돌한다. 이는 Decision 12의 값 바인딩을 표시 정책으로 확대해서 생긴 문제다.
- 해결 방향: 바인딩 값 치환과 노드 존재 조건을 분리한다. 원래 조건부인 label/description에 한정한 명시적 존재 조건을 두거나 부품별 예외를 선언하고, FieldError는 RAC의 기본 validation 내용을 평가할 수 있도록 유지한다. 비텍스트 자식·필수 부품이 있는 노드를 단지 텍스트 바인딩이 비었다는 이유로 제거하지 않는다.

### m1 — MEDIUM · from:type은 같은 type의 조상이 겹칠 때 어느 상태를 뜻하는지 정하지 못한다

- 위치: `docs/adr/256-rac-composition-level.md:133-134` (Decision 7), `:169` (R12).
- 기존 수리 확인: Disclosure > Button의 isExpanded 키별 검색과 ListBoxItem(isDisabled=true) > Group(isDisabled=false)의 가까운 키 shadow는 설치 RAC values에 맞다. Checkbox/Button 양쪽 모두 isPressed를 제공하는 것도 확인했다. 서로 다른 type은 from을 이용해 구분할 수 있다.
- 반례: `Group(isInvalid=true) > Group(isInvalid=false) > Text`에서 RAC callback은 바깥과 안쪽 상태를 각각 참조할 수 있다. SSR에서 false/false, false/true, true/false, true/true 네 조합이 독립적으로 렌더링된다. 그러나 바깥 상태를 요청한 `from:"Group"`에 어느 Group인지 담을 수 없으며, 가까운 일치 type으로 해석하면 바깥 true를 요청해도 false를 읽는다. 먼 일치를 고르는지 가까운 일치를 고르는지조차 문장에 정의되지 않았다. R12가 말하는 명시적 상태 주체 지정이 이 경우 해결책이 되지 않는다.
- 해결 방향: from의 type 중복 시 규칙을 고정하고, 더 바깥의 같은 type을 지정할 수 있는 안정된 조상 참조/경계 식별을 제공하거나 이를 명시적인 지원 제한으로 결정한다. G0 인벤토리/테스트 수 부족 지적이 아니라 현재 표현 형식의 식별력 문제다. 임의 표현식 요구는 아니다.

### l1 — LOW deferred · 빈 값 판정의 경계가 아직 명시되지 않았다
