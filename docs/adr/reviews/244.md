## Findings

1. **HIGH — 이전 탭 부팅 실패를 성공 Gate로 두었다.** ADR 244:153은 빌드 N+1 배포 뒤 옛 탭의 부팅 실패와 새로고침 복구를 PASS로 정의한다. `.github/workflows/deploy.yml:192-199`에는 이전 자산 보존 설정이 없다. action의 기본 동작은 이전 파일 제거이므로, 이미 열려 있던 dashboard 탭이 배포 후 builder에 들어가면 구 해시 wasm 404로 Canvas를 못 띄운다. 이는 본문의 ‘정합성만 개선’ 결정에서 사용자 가시 기능 회귀다. 옛 버전 자산 보존 또는 구 탭의 안전한 reload 경로를 D의 배포 전제와 Gate에 포함할지 결정해야 한다. [actions-gh-pages 문서](https://github.com/peaceiris/actions-gh-pages#%EF%B8%8F-keeping-existing-files-keep_files).
2. **MEDIUM — G0의 30% 판정 분자가 모호하다.** `SkiaCanvas.tsx:609-610`과 `wasm-bindings/init.ts:15-52`는 engine/CanvasKit을 병렬 초기화한다. breakdown 244:27-28은 자산별 Resource Timing으로 wasm 받기를 계산하지만 합산하면 중첩된 전송 시간을 두 번 센다. 카드 press에서 부팅이 실제로 기다린 네트워크 critical path의 겹치지 않는 구간을 계산하고, 폰트 순차 구간과 합쳐야 A 착수 분기가 유효하다.

## Round 3 — 2026-10-05 (reviewer: codex)

2026-10-05 개정본·breakdown과 HEAD 248a0e112 + 현재 dirty 코드 대조. 이번 라운드는 사용자 요청으로 열었다. 제품 코드·ADR 본문·Status는 변경하지 않았다.

1. **HIGH — 선택적 폰트 warmup이 재방문 부팅에 새 네트워크 의존을 만든다.** breakdown:75-81은 wasm·engine·폰트를 받는 결과 promise 하나를 initCanvasKit이 기다리게 한다. 실제 fontManager:90-100은 IndexedDB hit면 fetch를 건너뛴다. HTTP 폰트 캐시는 축출됐지만 IndexedDB 폰트가 살아 있는 느린 망 재방문에서 wasm은 준비돼도 필요 없는 폰트 받기가 끝날 때까지 CanvasKit을 못 시작한다. 같은 promise 구조의 격리 브라우저 반례: wasm 완료 Chrome 202.2ms / WebKit 203ms, 전체 완료 2001.8ms / 2004ms, 추가 대기 약 1.8초. 제품 성능 실측은 아니다. 자산별 promise로 기다릴 의존을 분리하고, IDB hit 폰트를 예열·대기에서 빼거나 진입 때 불필요한 예열을 취소해야 한다.

2. **MEDIUM — engine 소비자는 warmup을 기다리지 않는다.** breakdown:80의 변경 위치는 initCanvasKit뿐이다. initAllWasm:31-46은 그보다 먼저 initEngineWasm을 시작하고 engineWasm:111-112가 동적 import로 wasm을 요청한다. warm engine 요청 시작 200ms 뒤 동일 URL을 소비하는 격리 실험에서 Chrome은 200 전송 1회였지만 WebKit은 2회였다. 양쪽 로더가 자기 자산의 promise를 실패·상한 시간 처리 후 기다리도록 해야 G2의 진행 중 wasm 전송 1회가 설계상 성립한다. 실제 제품 엔진 모듈 부팅은 UNVERIFIED.

3. **MEDIUM — 만료 모사 조건이 fresh cache를 유지할 수 있다.** breakdown:18 및 본문 G0:161은 서버 max-age=0 + ETag를 10분 뒤 방문 모사로 둔다. Chrome 154에서 max-age=600으로 prime한 뒤 서버 값을 0으로 바꿔 동일 URL을 재요청해도 서버 기록은 최초 200 한 건뿐이었다. 대조로 처음부터 0으로 prime한 자산은 200→If-None-Match→304였다. 만료 arm은 같은 origin·URL을 처음부터 만료 헤더로 prime한 독립 profile로 만들거나 실제 age를 경과시키고, 서버에 조건부 요청이 도착한 것을 사전 조건으로 확인해야 한다. 캐시 전체 삭제는 cold arm이므로 대체할 수 없다.

이전 라운드: 병렬 구간 합집합과 옛 탭 복구의 오류 전달·buildId probe·404.html 설계는 현재 본문에 반영됐다. 새 복구 구현과 재배포 Gate 통과를 확인한 뜻은 아니다.

근거: /private/tmp/adr244-review-server.mjs, /private/tmp/adr244-review-run.cjs. 유효 최소 wasm 바이트·application/wasm·Content-Length·동일 URL·same-origin credentials·max-age/약한 ETag의 격리 HTTP 서버. Chrome 154 / 설치된 WebKit Safari 26.6; WebKit은 CLI 최신 기본 바이너리가 없어 기존 webkit-2336 executable을 명시했다. WebKit 실험은 순차 fetch도 캐시 재사용하지 않았으므로 캐시 만료 비교 판정은 Chrome 근거로 한정한다. engine 동시 전송 결과 역시 이 환경의 관찰이며 전체 Builder 재현과 동일시하지 않는다.

**UNVERIFIED**: 실제 Builder warmup 구현·첫 프레임 p50/p95·G0 30%·D 재배포 복구·initial gzip·실제 GitHub Pages. 공식 HTTP 캐시 계약 참고: https://www.rfc-editor.org/rfc/rfc9111.html. 새 pending HIGH 1 / MEDIUM 2로 설계 수리 필요.
