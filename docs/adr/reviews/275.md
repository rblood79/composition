### H1 — 부모보다 넓은 자식에서는 A1이 가로 Center를 표현하지 못한다 (open)

- 대상: `docs/adr/275-position-section-figma-rules-framer-fields-layout-insets.md:132-134`, Decision 2의 Center 대응 및 축 대칭 주장.
- 입력 → 잘못된 결과: LTR containing block 폭 100px, Fixed 자식 border-box 폭 200px, `left:0; right:0; margin-left:auto; margin-right:auto`. 가로 Center 0의 기대 좌표는 -50px이지만 CSS는 margin-left=0, margin-right=-100으로 풀어 x=0이 된다. 반면 현재 엔진 `packages/engine/src/tree.rs:7459-7469`는 free/2를 사용하므로 x=-50이다. 부모 폭을 줄이는 일반 breakpoint/resize만으로 Canvas와 Preview가 갈린다. 현재 F10은 has_w/has_h만 대상으로 하므로 이 문제를 닫지 않는다.
- 독립 근거: [CSS Positioned Layout §4.2](https://www.w3.org/TR/css-position-3/#abspos-margins), [CSS 2 §10.3.7](https://www.w3.org/TR/CSS2/visudet.html#abs-non-replaced-width). inline 축의 음수 잉여 공간은 두 auto margin에 반씩 배분되지 않는다. 세로와 가로가 이 경우 대칭이 아니다.
- 해결 방향: 선택한 margin-auto 저장 방식의 overflow 동작을 Center 계약에 명시하고 두 소비자를 같은 CSS 의미로 맞추거나, overflow에서도 기하학적 중앙을 유지해야 한다면 대응식을 다시 결정해야 한다. G0/G1에 W < w 및 breakpoint 축소 입력을 포함한다. 사용자에게 이미 확정받은 저장 방식을 검토자가 임의로 변경하지 않는다.
- 검증: 표준 및 현재 함수 본문에서 산술 추론. 실제 Chrome/Builder 재현은 **UNVERIFIED**.

### H2 — has_w/has_h 확장은 기존 content-box → border-box 보정까지 꺼 버린다 (open)

- 대상: `docs/adr/design/275-position-section-figma-rules-framer-fields-layout-insets-breakdown.md:65`, Phase 1의 intrinsic keyword 수리.
- 근거: `packages/engine/src/tree.rs:2153-2163` 및 `:2503-2512`에서 fit-content 컨테이너 solve 반환은 content-box다. `:2838-2850`은 현재 !has_w/!has_h일 때 padding/border를 더하거나 leaf의 border-box layout을 읽는다. 같은 bool은 `:2899-2905`에서 stretch 여부에도 사용된다.
- 입력 → 잘못된 결과: 폭 400px 부모, 내용 폭 60px인 absolute fit-content 컨테이너, 좌우 padding 각 12px, border 각 2px, 좌우 inset 0 + margin auto. 올바른 border-box는 88px, x=156px이다. 문서대로 keyword에 대해 has_w=true로 넓히고 기존 keyword 해소 반환을 그대로 사용하면 +28 보정을 건너뛰어 폭 60px, x=170px로 최종 layout을 덮어쓴다. padding 없는 Hug 60 케이스는 이를 드러내지 못한다.
- 해결 방향: stretch에서 제외할 크기인지와 solve 반환이 border-box인지의 판정을 분리한다. intrinsic keyword도 최종 border-box를 복원하고 leaf/container 및 양 축의 기존 반환 계약을 유지하도록 Phase 1에 명시한다. G1은 부모뿐 아니라 **자식 자체**에 padding/border를 준 Center × Hug 입력으로 확인한다.
- 검증: 제안된 판정 변경을 현재 호출 경로에 대입한 정적 반례다. 제품 수정·Rust/브라우저 실행은 **UNVERIFIED**이며 아직 발생한 구현 회귀로 판정한 것은 아니다.

### M1 — effective out-of-flow와 저자가 지정한 absolute를 같은 술어로 치환하면 이동 금지 부품이 이동 대상이 된다 (open)

- 대상: `docs/adr/design/275-position-section-figma-rules-framer-fields-layout-insets-breakdown.md:76`, `isAuthoredOutOfFlow(node) = layout.position === absolute`로 placement 소비자 전부 교체.
- 근거: `packages/shared/src/catalog/resolution/resolver.ts:1203-1211`은 definition/part rule을 layout에 먼저 합친 뒤 authored layout을 별도 축적한다. `packages/shared/src/catalog/document/manualBoxRules.ts:980-990`의 ListBoxItem icon은 저작 placement 없이도 rule이 position:absolute를 준다. `apps/builder/src/builder/catalogRuntime/canvasGesture.ts:482-488`은 이 경우 이동을 명시적으로 거부하고, `:500-505`는 저작 placement만 absolute move에 포함한다.
- 입력 → 잘못된 결과: ListBoxItem에 저자가 추가한 Icon(slot=icon) 노드를 선택하여 Canvas drag. 현재는 rule이 위치를 소유하므로 beginMove=false다. 지정된 술어로 저작 여부까지 일괄 대체하면 effective absolute라는 이유만으로 이동 대상으로 포함되어 rule 부품에 author inset을 쓴다. 반대로 effective absolute를 전부 금지하면 새 저작 absolute도 이동할 수 없다.
- 해결 방향: layout 데이터 하나로 통일하는 결정은 유지하되, **effective out-of-flow** 판정과 **authored position/편집 가능 여부** 판정을 구분한다. 현재 record의 authoredLayout 및 field source를 사용해 기존 rule 소유 경계를 보존하고 inventory에 이 분기를 명시한다. 새 placement 필드가 필요한 문제는 아니다.
- 검증: 현재 rule·resolver·beginMove 경로를 대조한 정적 반례. 새 술어/실제 Builder drag는 **UNVERIFIED**.
