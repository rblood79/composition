### 보충 권고 1 — 자동 생성 연결의 재편집·해제·되돌리기 계약

근거: `docs/adr/284-data-view-filter-sort-group-query.md:110`, `docs/adr/design/284-data-view-filter-sort-group-query-breakdown.md:90`. 지금은 처음 생성과 개별 편집을 규정하지만 같은 연결로 다시 진입했을 때 기존 묶음을 찾는 기준, 기존 변수·규칙을 사용하는 기준, 연결 해제의 범위와 Undo 단위는 명시하지 않는다.

반례 시나리오: 기존 RadioGroup→변수→조건 연결을 가진 상태에서 동일 대상·필드를 다시 연결하면, 기존 연결을 고치려던 사람이 중복 변수·규칙·조건을 만들 수 있다. 공유 변수를 쓰는 조건 하나를 해제하면서 변수를 함께 지우면 다른 목록도 영향을 받는다. 이는 아직 구현 재현이 아닌 설계상 허용될 수 있는 실패 경로다.

본문 Decision 7에 추가할 원칙: 생성된 연결은 재발견하여 편집할 수 있고, 기존 연결의 재사용·추가·교체를 구분하며, 생성·교체·해제는 문서와 외부 데이터 상태를 포함해 한 번에 되돌릴 수 있다. 재사용은 타입·소유 범위가 맞는 명시적 연결에 한정하고 기존 규칙을 임의로 덮어쓰지 않는다. 공유 변수·보기를 해제할 때 다른 사용처를 보존한다.

breakdown Phase 3/G3에는 생성→재진입→비교 변경→해제→Undo→저장·재열기 시나리오와 공유 연결 보존을 명시한다. 동일 버튼 클릭이 새 연결인지 기존 연결 편집인지 구분하는 UI는 상세 설계 사항이다. 기존 `.claude/rules/state-management.md:131` 이하의 `workspace.execute`, history, 외부 상태 `recordExternal` 계약을 그대로 사용한다.

### 보충 권고 2 — 계산 범위와 표시 범위, 결과 수의 의미

근거: 본문 105행의 결과 schema, 109행의 로컬/API 실행, 114행의 행 100 상한에 근거한 위험 수용, 155행 G4. 현 코드 `packages/shared/src/collections/resolveCollectionItems.ts:36`의 100은 투영 상한이고 `getFlatProjectionRows` 524~534행은 원본을 slice한다. `packages/shared/src/catalog/runtime/dataBinding.ts:160`의 `catalogBoundRows`는 items 경로에 상한을 적용하지만 records 경로는 전체 행을 읽는다. `apps/builder/src/types/builder/data.types.ts:153` 이하에는 pagination `totalPath`·cursor 설정도 별도로 있다.

반례 시나리오: 로컬 200행 중 101번째 이후의 행만 필터에 일치하거나, API 전체 일치 1,000건 중 첫 20건만 로드된 상태에서 결과 수를 표시한다. 투영 뒤 계산하면 로컬 결과가 0건으로 보일 수 있고, 로드된 길이를 전체 count로 제시하면 API 결과 수가 20건으로 보일 수 있다. 새 계산기가 아직 없으므로 실제 ADR-284 구현의 오류로 단정하지 않는다.

본문 Decision 3/6에 계산 대상과 결과 완전성 원칙을 명시할 것을 권고한다. 로컬 필터·집계는 표시 투영 전 원본 범위에서 계산하고 표시 상한은 그 뒤 적용한다. API 전체 수는 서버가 해당 조건에 대한 total/집계를 제공한 경우에만 확정하며, 그 외에는 로드된 범위의 수 또는 전체 수 미확인으로 표시한다. 선택 수의 `all`도 같은 대상 범위를 명시해야 한다. 부분 로드 데이터를 조용히 전체 조회처럼 재계산하지 않는다.

breakdown Phase 1/2/4에는 100행 초과 로컬 fixture, API cursor·total 유무 fixture, 결과 완전성 표기를 추가한다. 필터 변경 시 이전 cursor와 늦은 응답을 새 조건 결과에 섞지 않는 계약도 확인한다. 성능 측정의 행 수는 표시 상한만으로 계산 대상의 상한이라고 단정하지 않는다.

### 보충 권고 3 — 연결의 현재 값과 결과 설명

근거: 본문 110행, breakdown 92행은 생성 직후 설정 확인을 규정한다. 본문 111행 및 157행 code view는 구조 확인을 제공하지만 현재 변수 값이나 행 제외 이유를 보여 주는 기능과 같지 않다.

Phase 3 상세에 재진입 가능한 연결 요약을 권고한다: 컨트롤의 값→변수의 현재 값→조건과 건너뜀/적용 상태→대상 목록. 각 항목은 기존 State·Interactions·조건 편집으로 연결한다. 로컬 또는 확보한 행은 조건별 일치/불일치/건너뜀을 같은 계산기 결과로 설명할 수 있다. API가 반환하지 않은 행의 제외 사유는 클라이언트가 확정할 수 없으므로 요청 조건·응답·로드 범위·오류 상태까지만 설명한다. UI 설명을 위해 두 번째 판정기를 만들지 않는다.

이 항목은 UX 상세 보강이며 별도 그래프 편집기나 새 DSL을 도입할 이유가 아니다. 행별 상세 판정 UI는 생성 연결 재편집과 범위 표기보다 우선순위가 낮다.

### 보충 권고 4 — 제작자 부재 상태의 인계·수정 검증

근거: 본문 158행 G7은 기능 live, 159행 G8은 사용자의 직접 확인이다. 연구 541~545행은 모델 walkthrough와 실제 신입 검증을 구분하고, 563행은 사람 간 결과 편차와 제작자 부재 시 유지보수 비용을 지표로 제시한다. 따라서 신입 사용성과 인계 가능성이 검증됐다고 볼 수 없다.

Context에 신입 개발자를 보조 페르소나로 명시하고, breakdown 검증 시나리오에 다른 사람이 만든 화면을 처음 연 뒤 조건 하나 수정, 제외 원인 설명, 다른 목록과 공유 여부 확인을 넣는 것을 권고한다. 성공 여부·도움 횟수·잘못된 결과를 성공으로 오인한 횟수·다른 목록에 의도치 않은 영향·수정 시간을 기록한다. 신입 2~3명 관찰은 연구 제안이며 현재 수행이나 승인 사실이 아니다. 임의의 시간 수치나 모델 추정을 통과 실적으로 쓰지 않는다. 새 사용자 승인 gate를 추가할 필요는 없다.
