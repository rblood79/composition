# ADR-280 Review Log

## Round 1 — 2026-10-22 (reviewer: codex)

## 판정

HIGH 3건. 현재 문서대로는 구현 착수 또는 종결을 승인하기 어렵다. 제품 코드와 ADR 본문은 수정하지 않았다.

1. **HIGH — G1/G2 prop 계약 충돌.** ADR:136-137과 breakdown:71은 손 등록표의 capability prop까지 동치로 요구한다. 현재 `capabilityRegistry.ts:220-246`에서 ListBox/GridList `selectItem`의 prop은 `defaultSelectedKeys`다. 그러나 ADR:96 및 breakdown:85-86은 이를 `selectedKeys` controlled prop으로 전환하고 `default*`를 제거한다. Button→ListBox `selectItem` 입력에서는 이전 prop을 보존하면 값이 RAC에 닿지 않고, 새 prop으로 바꾸면 G1 테스트가 실패한다. G1 동치 대상에서 명시적인 `default* → controlled` 전환 목록을 빼고, G2에 새 prop과 RAC 도달성 검사를 둬야 한다.

2. **HIGH — 상태 제한 우회.** ADR:41은 `isReadOnly`, `isDisabled`, `disallowEmptySelection`의 변경 금지를 Hard로 선언한다. 하지만 `dispatcher.ts:187-219`는 target type과 capability만 확인한 뒤 값을 patch하고, `catalogPreviewInteractions.ts:363-373`은 override를 저장한다. G2(ADR:137)는 prop/callback 도달성만 확인한다. 예를 들어 disabled Checkbox에 다른 Button의 `check` 규칙을 걸면 외부 `isSelected=true` override가 들어가 RAC의 사용자 입력 제한과 무관하게 선택 상태가 변한다. capability 실행 전 상태 제약을 검사하고 실패를 report하며, disabled/readOnly 및 빈 선택 금지의 실제 Preview/Publish 반례를 G2에 포함해야 한다.

3. **HIGH — Form 특례 실행 누락.** ADR:94,112는 Form `submit`/`reset`을 현행 imperative 특례로 유지하고 G2(ADR:137)는 모든 등재 capability의 도달성을 요구한다. `capabilityRegistry.ts:370-389`는 둘을 공개하지만 `dispatcher.ts:199-207`는 `imperative`에 항상 실패를 반환한다. Button→Form `submit` 규칙은 보고만 남기고 form submit은 일어나지 않는다. 이 ADR에서 ref 기반 실행과 결과 oracle을 추가하거나, 실제 구현 전 두 capability를 deferred로 내려 노출을 막아야 한다.

## 검증 범위

ADR, breakdown, 현재 shared dispatcher/registry/runtime의 정적 소비 경로를 대조했다. **UNVERIFIED:** 설치 RAC context 우선순위, test-utils API, 실제 Builder/Preview/Publish browser 동작, 성능/번들 게이트. 위 3건은 실행 전 문서와 코드의 계약 충돌에 근거한다.

## Round 2 — 2026-10-22 (reviewer: codex)

## 수리 검증 판정

Round 1 h1은 전환 5건을 코드와 맞춰 분리했고 G2에서 새 prop 도달을 검사하므로 해소됐다. h2와 h3도 실행 방향은 정했지만 아래 두 production 경로가 남아 HIGH 2건이다. 제품 코드와 ADR 본문은 수정하지 않았다.

1. **HIGH — 선택 집계값 없이 집합 조작/제약을 계산함.** ADR:105-110의 guard 입력은 `getElement`의 대상 record 선언값+override와 그룹 제약이다. 현재 `catalogPreviewInteractions.ts:225-242`의 `getElement`도 그 둘만 돌려준다. 그러나 ListBox/GridList의 시작 선택은 `delegatedDom.runtime.ts:308-337`이 자식 `isSelected`를 순회해 집계하며 대상 record.props에는 없다. 다중 ListBox에서 A가 이미 선택된 상태로 `selectItem(B)`를 실행하면 현재 선택을 읽지 못해 A를 잃거나, `disallowEmptySelection`의 마지막 항목 `deselectItem(A)`를 막지 못한다. breakdown:91은 guard를 `resolveValue`보다 앞에 두면서 이미 계산된 `value`를 입력으로 요구한다. controlled helper와 dispatcher가 동일한 유효 선택값을 읽는 API를 명시하고 값 해소→결과 집합 계산→guard→patch 순서를 정해야 한다. G2에는 기존 선택 A가 있는 다중 선택의 B 추가와 마지막 선택 해제 반례를 넣어야 한다.

2. **HIGH — authored Form action 회귀.** ADR:113은 Form `onSubmit`에서 무조건 `preventDefault`를 요구한다. 하지만 `Form.binding.ts:95-129`는 `action`·`method`·`target`을 작성 가능한 prop으로 제공하고, `delegatedDom.runtime.ts:2691-2707`이 그대로 RAC Form에 전달한다. 사용자가 action URL을 지정한 Form에서 submit 버튼을 누르면 현재 HTML 제출 경로는 그 목적지로 가지만 Decision 9대로 구현하면 무조건 차단된다. 목적지 없는 Form만 이동을 막고, authored action이 있는 Form의 기존 동작을 어떻게 보존할지 명시해야 한다. G2에는 action이 있는 제출 대조군도 필요하다.

## 검증 범위

수정된 ADR/breakdown과 현재 registry·dispatcher·collection selection·Form binding의 정적 경로를 대조했다. 리뷰 기록 validator 172/172 PASS. **UNVERIFIED:** 실제 Preview/Publish 브라우저 제출, RAC reset/context 동작, 성능·번들 게이트.
