# ADR-245 Review Log

## Round 1 — 2026-09-27 (reviewer: codex)

## 판정 기준과 범위

- 범위: Phase 0 go/no-go만 우선 검토한다. 동일한 사용자 요청과 기기에서 수정 후 Ollama D1/D1', Ollama one-shot B1, Chrome Prompt API+Translator A의 지연·정답률·프레임을 비교한다. 원격 provider 프록시, Agent 확장, Preview/publish AI는 범위 밖이다.
- 기준: 서버 경로가 사용자가 정한 절대 p95 목표 이내면 A no-go; 아니면 A p50 ≤ 서버 절반, p95 ≤ 서버, 정답률 차 ≤5%p, 프레임 G5 통과 시 go. 제안된 5초는 사용자 제품 정책으로 확정 전이다. 요청·정답표도 계측 전 독립 고정이 필요하다.

## Findings

1. **HIGH — on-device 선택이 실제 one-shot 호출에 닿지 않는다.** breakdown 245:78-84는 `composition.ai.onDevice`를 main과 분리하고 레지스트리에 동적 import를 둔다. 현재 `compiler/runtime.ts:69-74`는 `resolveProvider("main")`만 조회하며 `agentProfiles.ts:77-87`과 `AgentProfileRegistry.ts:199-202,222-239`는 동기 provider 팩토리다. 저장 키를 추가하는 것만으로는 A가 선택되지 않고, 동적 import도 동기 반환 계약과 맞지 않는다. one-shot 전용 provider resolver의 비동기 선택 순서와 off/unavailable 시 기존 main 반환 경로를 명시해야 한다.
2. **HIGH — 무효 출력 fallback이 실행되지 않는다.** breakdown 245:69-76과 ADR 245:44,145는 schema/파싱 실패 때 legacy Ollama로 넘기겠다고 한다. 현재 `runtime.ts:43-50,94-95,130-133`은 모든 오류를 `handled:true`로 돌려주며 `useAgentLoop.ts:132-150`는 그 자리에서 ‘이해 못함’을 표시하고 종료한다. 별도 `legacy` 반환 분기와 실패 종류·재시도 횟수·중복 적용 방지를 설계해야 G2가 의미 있다.
3. **HIGH — G0 지연 지표에 정의되지 않은 표본이 있다.** breakdown 245:29-42는 ‘표현 불가=빈 operations’를 정답으로 포함하면서 모든 arm에 ‘첫 명령 canonical 적용’ p50/p95를 요구한다. `contracts.ts:53-58,67-73`은 빈 operations를 실행 불가로 두고 `runtime.ts:94-96`에서 거부한다. 그 표본에는 첫 적용 시각이 존재하지 않는다. 지연 표본은 적용 가능한 요청에만 정의하고, 표현 불가 요청은 거부·fallback 정확도와 종료 시간으로 별도 채점해야 한다.
4. **MEDIUM — no-go 상태 전이가 정의되지 않았다.** ADR 245:103-108은 Rejected 또는 Deferred로 닫겠다고 하지만 `.agents/rules/adr-writing.md`의 Status 전이는 Proposed·Accepted·Implemented·Deprecated·Superseded만 정의한다. no-go 기록을 기존 상태 안에서 표현할지 상태 계약을 확장할지 먼저 정해야 README와 검증기가 일치한다.

- R1 h2 **미해소 (HIGH)**. breakdown 245:77은 on-device의 `validateProgram` 거부 전체를 mutation 전 legacy fallback으로 보낸다. 그러나 `manifest.ts:134-137`은 body 삭제에 `protected-target`을 반환한다. 이 경우 현재 `runtime.ts:94-95`에서는 안전 거부로 끝나는데 새 설계에서는 Agent로 넘긴다. 사용자 수리 설명의 ‘삭제 차단 같은 안전 거부는 넘기지 않는다’와 모순이다. 구조·출력 오류만 allowlist로 fallback하고 `protected-target` 등 정책·안전 거부는 명시적으로 막아야 한다.
- R1 h3 **미해소 (HIGH)**. 적용 가능 16개와 표현 불가 4개 분리는 빈 operations에 첫 적용 시간이 없다는 원래 결함을 해결했다. 그러나 breakdown 245:40은 적용 가능 요청의 무적용·거부 결과도 지연 표본에서 제외하면서 ‘arm별 n≥16×3’ p95를 요구한다. A가 16개 중 빠른 2개만 적용하고 서버가 16개를 처리하면 서로 다른 성공 표본의 p95를 비교한다. 실패를 포함한 terminal latency와 적용 성공률을 쌍으로 판정하거나 성공 표본 수·공통 요청 집합을 Gate에 고정해야 한다.

## Round 3 — 2026-10-05 (reviewer: codex)

2026-10-05 개정본·breakdown과 현재 one-shot·consumer·Agent·도구 쓰기 경로를 대조했다. 이번 라운드는 사용자 요청으로 열었다.

1. **HIGH — 추론 예외와 선택 변경이 겹치면 context-changed 거부를 우회해 legacy가 시작된다.** breakdown:82는 호출 예외를 포함하는 invalid-or-unavailable-output을 mutation 전 legacy fallback 허용 목록에 넣는다. 그러나 runtime:92-93의 identity 검사는 provider가 정상 반환했을 때만 실행된다. runtime:130-133 catch는 signal만 확인한다. 입력·상태: A 선택에서 요청 → Nano/Translator 대기 중 B 선택 또는 페이지 변경 → provider 예외. 결과: invalid-or-unavailable-output + toolExecutions=0이므로 새 분기가 handled:false로 반환하고, useAgentLoop:168-202는 selection 재검사 없이 :115에서 만든 이전 context로 Agent를 시작한다. AgentService:64-68도 받은 context를 prompt에 싣고, updateElement:118-129는 실제 id로 쓰므로 선택 일치 보장이 복구되지 않는다. 현재는 handled:true로 끝나므로 이 경로는 새 fallback이 여는 회귀다.

해결: fallback을 반환하는 공통 함수에서 signal 및 요청 시작 identity와 최신 readCompilerState().identity를 먼저 검사한다. abort/context 변경은 호출·파싱·resolver 실패 종류와 무관하게 handled:true 거부가 우선이다. consumer도 legacy 시작 직전에 선택·페이지를 확인할 수 있다. provider throw + identity 변경 반례를 회귀 조건으로 고정한다.

반증 검사: 임시 인접 Vitest에서 provider가 identity를 바꾼 뒤 throw하도록 주입. 실제 runtime은 context-changed 대신 invalid-or-unavailable-output을 반환하고 executor 0회를 기록했다. 기존 runtime.test.ts 15개 + 반례 1개 = 16/16 PASS. 반례 테스트는 증거 확인 후 제거했다. 이 PASS는 현재 catch 분류의 관찰이며 새 on-device 제품 구현이나 Gate 통과가 아니다.

이전 HIGH 2 및 MEDIUM 1의 설계 수리 확인: one-shot 비동기 resolver 소비 경로, protected-target 등 안전 거부 제외 + 형식 오류 allowlist, 공통 요청 분모 + 실패 60s 채움, 보류는 Proposed 유지가 현재 본문에 반영돼 있다. 신규 HIGH 1 때문에 승인 판정은 보류한다.
