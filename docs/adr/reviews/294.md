### H1 — 접힌 컴포넌트의 이벤트 수신 경계를 잃는다

- 위치: `docs/adr/design/294-component-event-variable-properties-breakdown.md:62-63`, ADR Decision 2.
- 입력 → 결과: Outer의 template root가 Inner instance J이고 page가 Outer instance I를 그린다. Inner 루트의 규칙이 `emit select`를 실행하면 제안한 record.instancePath 역순 탐색은 Inner instance를 찾지 못해 `listeners: 0`으로 버린다. 실제 `collapseLayers`/`consumerRecord` 호출 결과 I/J/Inner body가 한 record로 합쳐지고 instancePath에는 I만 남는다.
- 근거: `packages/shared/src/catalog/runtime/compositionRoot.ts:3295-3318,3363-3367`. 경로 탐색만 고쳐도 `Map<recordId, Map<key, rules>>`는 Outer/Inner의 같은 `select`를 구분하지 못한다. Inner 수신 규칙이 Outer select로 전달하는 정상 wrapper에서 오발행/재진입 위험이 남는다.
- 해결: 렌더 record와 별도로 논리 instance 경계(정의 + instance 위치 + 반복 행 문맥)를 보존하고, receiver와 listener 색인 및 재발행 문맥이 그 경계를 사용하도록 명시한다. G1에 다른 컴포넌트를 루트로 감싼 wrapper와 같은 event key 재발행을 추가한다.
- 검증: 현재 resolver와 실제 collapse/consumer 메서드로 경계 손실을 확인했다. 미래 emit 구현의 종단 실행은 UNVERIFIED.

### H2 — variable 값을 저장하는 prop 계약이 없다

- 위치: `docs/adr/design/294-component-event-variable-properties-breakdown.md:58`, ADR Decision 1.
- 입력 → 결과: 사용자 property `roleFilter`를 만들고 instance에 리터럴 `admin` 또는 `!var.<id>`를 쓰면, 설계에서 accepts에 포함하지 않으므로 transaction이 `PROP_NOT_ACCEPTED`로 거절한다. 기존 RAC prop과 우연히 같은 이름인 경우에도 number/boolean 참조 문자열의 타입 계약은 해결되지 않는다.
- 근거: `packages/shared/src/catalog/document/componentProperties.ts:14-30` → `library.ts:174-178` → `graph.ts:1290-1295,1583-1601`. `componentPropertyAccepts`는 현재 text/boolean만 계약으로 내보내며 breakdown은 이 표를 유지한다고 명시한다.
- 해결: variable의 선언 타입과 참조 표현을 instance prop 계약/검증에 연결한다. 리터럴 타입, 참조 대상 존재·가시성·타입, object/array/date를 포함한 저장 표현을 정하고 리터럴/참조의 저장·직렬화 왕복을 G1에 넣는다.
- 검증: 현재 accepts 함수가 variable key를 내보내지 않는 것과 동일한 accepts 누락 상태에서 실제 setFields transaction의 `PROP_NOT_ACCEPTED`를 확인했다. 새 kind의 스키마 구현 검증은 아니다.

### H3 — 세션 readState fallback만으로 입력 변수의 소비·갱신을 연결할 수 없다

- 위치: `docs/adr/design/294-component-event-variable-properties-breakdown.md:64`, `docs/adr/294-component-event-variable-properties.md:103,111,134`.
- 입력 → 결과: template 루트 변수 `role`의 기본값은 guest, instance 입력은 admin 또는 page 변수 roleFilter이다. 제안대로 세션 readState만 확장하면 보기 조건은 role을 찾지 못하고, 규칙의 `!var.role`은 기본값 경로를 계속 읽으며, roleFilter 변경은 내부 `{{ role }}` 독자를 갱신하지 못한다.
- 근거:
  - `viewQuery.ts:139-145` → `stateTemplate.ts:357-401`: 보기 입력은 page/project만 찾는다. template element 변수는 read callback에 도달하지 않는다. 현재 probe에서 values/names는 빈 값이고 read 호출은 0이다.
  - `catalogPreviewSession.ts:744-751`: 규칙은 readState 메서드 대신 state.read를 직접 부른다. `state/runtimeState.ts:369-375`는 미기록 scope에도 기본값을 반환해 “없으면 prop” fallback의 판별 API도 없다.
  - `catalogPreviewSession.ts:1791-1800`, `compositionRoot.ts:2049-2059,2087-2095`: 갱신은 변경 변수의 이름/id와 내부 독자의 이름/id를 직접 비교한다. `variableReferences.ts`는 문서 사용처/이름 변경 유틸리티이며 런타임 전이 의존성 색인이 아니다.
  - `stateTemplate.ts:19-30,196-219`: Canvas는 runtime read 없이 기본값을 읽으므로 variable 입력의 작성 값 반영도 별도 공통 경로가 필요하다. Canvas “해당 없음”은 event 표식에만 적용할 수 있다.
- 해결: instance 입력을 공통 변수 해석 경로로 만들고 기본값/리터럴/부모 참조의 우선순위 및 입력 변수 쓰기 거절을 정한다. template 보기에는 instance/행 scope를 전달하고 parent→input→내부 독자의 의존성을 연결한다. Canvas 작성 값·Preview/Publish 실행 값·규칙 읽기가 같은 입력 의미를 사용해야 한다.
- G1 보강: 서로 다른 조건의 instance 둘, 최초 리터럴, 부모 참조 변경, 내부 텍스트·보기·emit 값의 동시 일치 및 저장/재로드를 검증한다.

### H1 잔여 — 내부 instance의 문서 id는 렌더 위치 식별자가 아니다

- 위치: ADR Decision 2 (`294-component-event-variable-properties.md:113`), breakdown `:74-75`.
- 입력: Outer의 template root가 Inner instance J. 같은 페이지에 Outer instance I1·I2를 일반 배치한다(바운드 행 아님). J의 `property:select` 규칙은 두 렌더 위치에 각각 적용된다.
- 현재 소스에서 얻은 경계: 실제 resolver 및 `collapseLayers`/`consumerRecord`를 실행하면 I1의 경계는 `[I1,J]`, I2의 경계는 `[I2,J]`. 두 J는 같은 문서 node id이고 rowIndex는 모두 undefined이다.
- 제안 알고리즘의 결과: `instanceId + "\\u0000" + rowKey`는 둘 다 같은 J 키다. 규칙 목록을 누적하면 I1에서 발생한 이벤트가 I1·I2의 수신 규칙을 모두 실행하고, 덮어쓰면 한쪽이 다른 쪽의 규칙을 실행한다. 기존 `catalogPreviewInteractions.ts:93-114,133-146`는 규칙을 record마다 변환하며 capability 대상도 해당 record 문맥으로 미리 해석하므로 다른 instance의 대상까지 실행될 수 있다.
- 수정 방향: 각 경계에 **그 경계까지의 전체 논리 instance 경로 + 반복 행 문맥**을 포함한 occurrence key를 둔다. 예: I1/J와 I2/J. 수신 색인과 재진입 가드는 같은 occurrence key를 쓰고, wrapper 재발행은 바깥 경계의 occurrence key로 이동한다. 문서 instanceId는 graph 조회용으로 별도 보존한다.
- G1: 기존 “instance 둘”과 “접힌 중첩”을 결합하여, 같은 Outer 둘 안의 같은 J가 같은 이름 이벤트를 전달해도 눌린 쪽만 한 번 실행되는지 검사한다.
- 실행 증거: `.agent/runs/2026-10-30-review-adr294/repair-probe.test.ts` **1/1 PASS**. 현재 실제 resolver로 경계를 얻고 수정안의 경계 추출·색인 키를 적용해 충돌 및 전체 경로 키의 분리를 확인했다. 새 emit 구현의 종단 실행을 확인한 것은 아니다.
