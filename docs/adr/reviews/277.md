# ADR-277 Review Log

## Round 1 — 2026-10-20 (reviewer: codex)

## Round 1 — 설계 리뷰 (2026-10-20)

판정: HIGH 1건. ADR의 핵심 사용자 흐름인 새 Table 배치 → 데이터 연결이 임의 스키마에서 빈 칸을 만든다.

### HIGH — starter 열과 Quick Connect 기본 정책 충돌

- ADR Decision 2와 G3는 starter 열 3개를 가진 Table을 데이터에 연결해 행을 투영한다고 한다 (`docs/adr/277-table-tableview-merge.md:83,116`).
- 새 Table에는 기존 열이 있으므로 `resolveColumnMode`가 `replaceColumns=false` 기본값에서 `preserve`를 돌려준다 (`apps/builder/src/builder/panels/datatable/utils/quickConnectPlan.ts:38-52`). Quick Connect는 `create` 또는 `replace`일 때만 schema 열을 삽입한다 (`apps/builder/src/builder/panels/datatable/usage/catalogQuickConnectHost.ts:122-162`). `projectTableRows`는 기존 열 key에 해당하는 `row.values[key]`를 읽는다 (`packages/shared/src/catalog/resolution/resolver.ts:1373-1380,1459-1465`). starter `Name/Type/Status`의 key는 `name/type/status`가 된다 (`packages/shared/src/collections/resolveCollectionItems.ts:637-649`).
- 재현 입력/상태: 새 Table을 놓고 `{title: 'A', price: 10}` 필드의 collection을 Quick Connect 기본값으로 연결 → 투영 행은 생기지만 `name/type/status` 칸은 빈 값이다. 핵심 약속인 '놓고 그대로 데이터 연결'이 깨진다.
- 해결 방향: 새 starter 열을 첫 연결에서 schema 열로 자동 교체하는 조건을 명세하고, 기존 사용자가 편집한 열에는 preserve 정책을 유지한다. 또는 starter와 데이터 열을 구분해 사용자에게 교체를 명시적으로 선택하게 한다. G1/G3는 이름이 다른 스키마의 실제 셀 값을 검증해야 한다. `replace`를 선택하면 현재 `insertTableColumns`는 정적 Row의 Cell을 정렬하지 않아(`packages/shared/src/catalog/commands/collections.ts:1294-1313`) 바인딩 해제 후 셀 수가 맞지 않을 수 있으므로 이 경로도 설계에 포함해야 한다.

### 확인 범위와 한계

- 문서 Decision/Gates 및 현재 Quick Connect, 열 key, 행 투영, 저장 contract 거부 경로를 코드로 대조했다. 변경 구현이나 브라우저 실행은 하지 않았다.
- 비차단 정정: `generate-css.ts`는 현재 목록의 CSS를 쓰기만 하고 삭제된 rule의 이전 파일을 제거하지 않는다 (`packages/rendering/scripts/generate-css.ts:104-132,422-451`). Decision 3/G2의 '재실행으로 TableView.css 삭제'는 실행 절차와 다르다. 기존 파일은 import 제거 후 런타임 영향이 확인되지 않아 LOW deferred로 둔다. 삭제는 생성 명령 개선 또는 별도 정리 절차가 필요하다.
- 사용자 결정 2건(이름, starter)은 ADR §사용자 결정 2건에 남아 있다. 사용자 정책 승인과 기술 gate를 구분한다.

## Round 2 — Round 1 수리 검증 (2026-10-20)

판정: HIGH 1건. 첫 연결을 replace로 바꾼 설계 방향과 정적 Row Cell 재정렬, 실제 셀 값 게이트는 적절하다. 그러나 breakdown의 구체 전달식이 첫 연결 여부를 잘못 계산하므로 h1 사용자 흐름이 그대로 깨진다.

### HIGH — binding snapshot의 envelope를 binding으로 판정

- breakdown §2c-2는 `resolveColumnMode(plan(target), replaceColumns, target.binding != null)`을 명세한다 (`docs/adr/design/277-table-tableview-merge-breakdown.md:56-57`).
- 현재 `bindingSnapshot`은 언제나 `{ props: nodeOf(id)?.binding }` 객체를 반환하고, capture가 이를 `QuickConnectTarget.binding`에 담는다 (`apps/builder/src/builder/panels/datatable/usage/catalogQuickConnectHost.ts:67-69,92-105`). `QuickConnectTarget.binding` 타입도 필수 객체다 (`apps/builder/src/builder/panels/datatable/types/editorTypes.ts:28-34`). 따라서 binding이 없는 새 Table에서도 `target.binding != null`은 true다.
- 재현 입력/상태: starter Table은 `node.binding`이 없고 `target.binding`은 `{props: undefined}`다. 문서의 전달식을 구현하면 hasBinding=true → 기존 열 3개라 `resolveColumnMode`은 preserve → `{title, price}`를 연결해도 실제 칸이 빈다.
- 해결 방향: `target.binding.props != null`처럼 envelope 내부의 실제 binding을 읽도록 Decision/breakdown에 정확히 적는다. G1은 `target.binding={props: undefined}`와 `{props: validBinding}` 두 입력에서 각각 replace/preserve를 반증해야 한다. precheck의 snapshot 동등성은 그대로 사용할 수 있다.

### 비차단 정합

- README의 ADR-277 항목은 아직 '사용자 결정 2 · 새 단위 5'라 본문과 breakdown의 '3 · 6'과 다르다 (`docs/adr/README.md:435`). 구현 범위 파악 시 고치면 된다.
- 이번 판독은 설계 문서와 현재 코드의 정적 경로 대조다. 제품 구현 및 브라우저 검증은 하지 않았다.
