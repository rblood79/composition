# ADR-241 Review Log

## Round 1 — 2026-09-24 (reviewer: codex)

merge를 막는 문제 3건입니다. 현재 HEAD `74f1eaefb` 기준으로 확인했으며 파일은 수정하지 않았습니다.

1. **[severity HIGH] [category: evidence-missing] Row ref 이관에 기존 셀 편집 경로를 보존하는 계약이 없습니다.**

   - **근거:** [본문:38](/Users/admin/work/composition/docs/adr/241-table-column-row-origins.md:38), [상세:60](/Users/admin/work/composition/docs/adr/design/241-table-column-row-origins-breakdown.md:60)은 기존 셀들을 Cell 템플릿 1개를 가진 Row origin의 `descendants`로 옮깁니다. 그러나 해석기는 실제 origin 자식을 순회하고 **일치하는 경로에만** patch를 적용합니다([canonicalRefResolution.ts:928](/Users/admin/work/composition/apps/builder/src/adapters/canonical/canonicalRefResolution.ts:928), [canonical/index.ts:328](/Users/admin/work/composition/apps/builder/src/resolvers/canonical/index.ts:328)). `descendants`의 글자 patch만으로 추가 셀이 생성되지는 않습니다. ADR-234는 기존 instance 편집과 자식 식별자 보존을 명시합니다([234:37](/Users/admin/work/composition/docs/adr/completed/234-variant-instances-and-slot-filled-collections.md:37)).
   - **실패 시나리오:** 기본 TableView의 셀 3개 중 세 번째를 instance에서 편집한 문서 → Row를 단일 Cell 템플릿의 ref로 교체하고 문서에 적힌 글자 patch만 이관 → 두 번째·세 번째 셀의 대상 경로가 없어지며, 바깥 TableView instance의 기존 세 번째 셀 override도 적용되지 않습니다.
   - **해결 방향:** 열 수만큼 Cell을 보유하는 저장 모양을 결정하고, 기존 셀 식별자를 유지하거나 바깥·중첩 instance의 경로를 재매핑하는 계약을 명시해야 합니다. 대응 불가능한 문서는 이관 보류 대상으로 정의하고 G5에 기존 셀 override 보존을 포함하세요.

2. **[severity MEDIUM] [category: other] `width` reader 통일만으로는 두 leg의 열 폭이 같아지지 않습니다.**

   - **근거:** [본문:34](/Users/admin/work/composition/docs/adr/241-table-column-row-origins.md:34)는 폭 일치를 요구하지만, [상세:50](/Users/admin/work/composition/docs/adr/design/241-table-column-row-origins-breakdown.md:50)의 공용 정의는 `key·글자·width`뿐입니다. Preview는 `minWidth/maxWidth`도 넘기고([TableRenderer.tsx:88](/Users/admin/work/composition/packages/shared/src/renderers/TableRenderer.tsx:88)), TanStack의 보정된 `getSize()`를 렌더합니다([Table.tsx:521](/Users/admin/work/composition/packages/shared/src/components/Table.tsx:521), [Table.tsx:1480](/Users/admin/work/composition/packages/shared/src/components/Table.tsx:1480)). Canvas는 `col.width`를 그대로 씁니다([canvasSceneNode.ts:2095](/Users/admin/work/composition/apps/builder/src/builder/workspace/canvas/scene/canvasSceneNode.ts:2095)).
   - **실패 시나리오:** 데이터가 있는 Table의 Column에 `width:80, minWidth:120` 설정 → 제안된 reader가 양쪽에 80을 전달해도 Canvas 셀은 80px, Preview는 120px입니다. 설치된 TanStack 함수 호출에서도 **80 → 120**을 확인했습니다. 열 개수만 비교하는 G1은 이를 놓칩니다.
   - **해결 방향:** 기본값과 min/max를 포함한 **유효 열 폭** 계산을 공용 계약으로 정하고, G1에서 제한값에 걸리는 열의 실제 폭을 비교하세요. RAC 전환 없이도 필요한 D3 수리입니다.

3. **[severity MEDIUM] [category: other] 초과 셀 보존 규칙과 ‘셀 수 = 열 수’ 계약이 충돌합니다.**

   - **근거:** [본문:36](/Users/admin/work/composition/docs/adr/241-table-column-row-origins.md:36)은 모든 정적 행의 셀 수·순서를 열과 같게 요구합니다. 반면 [본문:99](/Users/admin/work/composition/docs/adr/241-table-column-row-origins.md:99)의 R2는 “남는 셀 유지”를 요구합니다. 현재 TableView는 행의 모든 자식을 그대로 렌더하므로 초과 셀이 자동으로 제외되지 않습니다([LayoutRenderers.tsx:2420](/Users/admin/work/composition/packages/shared/src/renderers/LayoutRenderers.tsx:2420)).
   - **실패 시나리오:** 열 3개·내용이 있는 셀 4개인 기존 행 → R2대로 보존하면 열 3개·셀 4개가 남아 구조 계약 위반 → 열 수에 맞춰 마지막 셀을 제거하거나 숨기면 내용 또는 이관 전 픽셀 보존 위반입니다. 이후 같은 index의 열·셀을 삭제해도 불일치는 유지됩니다.
   - **해결 방향:** 초과 셀이 있는 문서는 자동 이관을 보류할지, 별도 보존 방식으로 전환할지 결정해야 합니다. 선택한 정책에 맞춰 hard constraint와 G3/G5의 기대 결과를 일치시키세요.

검증 범위는 코드·문서 추적과 TanStack 폭 계산 확인입니다. 브라우저·DB·history 실행 결과는 **UNVERIFIED**이며, Phase 닫힘은 판정하지 않았습니다.

## Round 2 — 2026-09-24 (reviewer: codex)

**merge 차단 문제 1건이 남습니다.** HEAD `74f1eaefb`와 두 문서의 개정 diff를 확인했으며, 파일은 수정하지 않았습니다.

1. **[HIGH] 셀 편집 경로 보존 — 부분 해소: 자기 자식 저장 모양을 중첩 ref 해석기가 지원하지 않습니다.**

   [상세:65](/Users/admin/work/composition/docs/adr/design/241-table-column-row-origins-breakdown.md:65)의 Cell 노드·id 보존과 [상세:66](/Users/admin/work/composition/docs/adr/design/241-table-column-row-origins-breakdown.md:66)의 경로 전치·이관 보류는 기존 지적을 반영했습니다. 그러나 새 저장 모양에는 **경로 전치만으로 해결되지 않는 소비 경로 문제**가 있습니다.

   - Canvas는 중첩 Row ref를 만나면 [canonicalRefResolution.ts:1071](/Users/admin/work/composition/apps/builder/src/adapters/canonical/canonicalRefResolution.ts:1071)에서 **Row origin의 자식만** 펼칩니다. 개정안의 Row origin은 셀이 없으므로, Row instance 자신의 Cell들은 바깥 TableView instance에 생성되지 않습니다.
   - Preview는 자기 자식을 표시하지만, [canonical/index.ts:222](/Users/admin/work/composition/apps/builder/src/resolvers/canonical/index.ts:222)에서 해당 자식을 `descendants` 적용 없이 해석합니다. 따라서 기존 셀 override의 경로만 바꿔도 적용되지 않습니다.

   **실패 확인:** 실제 두 해석기를 파일 생성 없이 메모리에서 실행했습니다.

   - `TableView origin → plain Row → Cell 3개`를 참조하는 instance → Canvas Cell **3개**.
   - 같은 Row를 `빈 Row origin의 ref + 자기 Cell 3개`로 변경 → Canvas Cell **0개**, Preview Cell **3개**.
   - 바깥 instance에 세 번째 셀의 `"Edited"` override 추가 → Preview는 여전히 **`"Cell 3"`**.

   기존 문서는 이관 보류로 보호할 수 있지만, **개정 구조로 만든 새 TableView origin을 팔레트에서 배치하는 경우**에도 셀이 사라집니다. 이관 보류만으로 막을 수 없습니다.

   **필요한 수리:** 중첩 ref의 자기 자식을 두 해석기가 펼치고, 바깥 instance override도 그 자식에 적용하도록 하는 계약을 포함해야 합니다. 이는 개정이 도입한 저장 모양의 실행 결함이며, 단순 커버리지 지적이 아닙니다.

2. **열 폭 불일치 — 해소.**

3. **초과 셀 보존과 셀 수 계약 충돌 — 해소.**

   [본문:36](/Users/admin/work/composition/docs/adr/241-table-column-row-origins.md:36)과 [상세:68](/Users/admin/work/composition/docs/adr/design/241-table-column-row-origins-breakdown.md:68)이 불일치 TableView 전체를 이관·동기화에서 제외하도록 일치합니다. 열 3개·셀 4개 문서는 원형을 유지하며, G3/G5도 같은 결과를 요구합니다.
