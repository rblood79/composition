## Round 1 — 2026-11-12 (reviewer: codex)

### h1 — Calendar 다중 선택의 읽기·쓰기 경계를 단일 날짜 경계로 유지할 수 없다 (HIGH)

- 위치: `docs/adr/309-date-value-authoring.md:104` (Calendar 날짜 목록 + DOM 전달 방식 유지), `docs/adr/design/309-date-value-authoring-breakdown.md:44-45` (단일 날짜·시각·범위 파서 교체).
- 근거: `packages/shared/src/catalog/runtime/delegatedDom.runtime.ts:1547-1551`, `:3914-3920`. 현재 `dateValue`는 문자열만 파싱하고 배열은 그대로 RAC로 보낸다. 반대 방향 `dateToOverride`는 모든 비어 있지 않은 값을 `String(next)`로 만든다. 읽는 파서 교체만으로는 콜백의 배열 손실이 해결되지 않는다. 실행 중 focus도 같은 배열을 `focusedDateProps`로 넘긴다.
- 입력 → 결과: `selectionMode: multiple`, `value: ['2026-11-12', '2026-11-14']`를 현재 DOM delegate에 넣어 설치 RAC로 SSR → `TypeError: Cannot use 'in' operator to search for 'timeZone' in 2026-11-12`. 반대 방향 RAC `onChange([parseDate(...), parseDate(...)])` → runtime override `{value: '2026-11-12,2026-11-14'}`. ADR의 `calendarValue` 목록 표기와 달라 다음 렌더에서 선택을 읽을 수 없다. 같은 SSR에 파싱된 날짜 배열을 주면 예외가 없다.
- 보완 방향: Calendar의 단일/다중 값에 맞는 양방향 변환과 최초 focus의 첫 날짜 추출을 Decision·Phase 1 범위에 명시한다. 배열 원소별 ISO→DateValue, 콜백 DateValue[]→ISO[]를 보장하고 empty 목록·clear·selectionMode 전환의 값 처리도 정한다. G1에서 해당 DOM 경계를 실행해 판정한다. 이는 테스트 개수 지적이 아니라 그대로 유지하겠다는 현재 경계가 새 값 표기를 처리하지 못하는 반례다.

### m2 — picker의 Placeholder가 선택 값보다 먼저라는 월 결정 규칙은 RAC와 다르다 (MEDIUM)

- 위치: `docs/adr/309-date-value-authoring.md:110`, `docs/adr/design/309-date-value-authoring-breakdown.md:59`.
- 근거: 설치 `apps/builder/node_modules/react-aria/dist/private/datepicker/useDatePicker.mjs:167`은 `defaultFocusedValue: state.dateValue ? undefined : props.placeholderValue`; `useDateRangePicker.mjs:211`도 `state.dateRange`가 있으면 Placeholder를 주지 않는다. 선택 값이 없을 때만 Placeholder가 초기 focus를 정한다. standalone Calendar의 `defaultFocusedValue` 순서를 picker Placeholder에 그대로 적용할 수 없다.
- 입력 → 결과: DatePicker `value=2026-11-12`, `placeholderValue=2030-03-15` (DateRangePicker도 시작=2026-11-12). 설치 RAC hook→calendar state SSR은 둘 다 `focusedDate=2026-11-12`, `defaultFocusedValue=undefined`. ADR 순서대로 기존 Canvas 모델에 Placeholder를 `defaultFocusedValue`로 매핑하면 제목 `March 2030`이다. Preview는 2026년 11월이고 Canvas는 2030년 3월이 되어 본문의 Hard constraint와 충돌한다.
- 보완 방향: standalone 달력과 picker를 구분한다. picker는 선택 값(범위 시작) → Placeholder → 오늘이며, 명시 focus가 있는 standalone 달력은 해당 focus를 우선한다. G2(a)에 값과 Placeholder가 서로 다른 달인 경우를 넣는다.

### m3 — 숨긴 defaultValue를 수용해도 5종 소비자는 그것을 시작 값으로 읽지 않는다 (MEDIUM)

- 위치: `docs/adr/309-date-value-authoring.md:104`, `docs/adr/design/309-date-value-authoring-breakdown.md:47`.
- 근거: `packages/shared/src/catalog/runtime/delegatedDom.runtime.ts:2589`, `:2603`, `:2628`, `:2653`, `:3939`는 모두 `props.value`만 파싱한다. 6종 중 Calendar만 `props.defaultValue` fallback이 있다 (`:3917`). Phase 1은 binding 수용과 파서 교체를 지정하지만 어느 값을 고르는지는 바꾸지 않는다. 공식 RAC의 [DatePicker 값 계약](https://react-aria.adobe.com/DatePicker#value)은 `value`와 `defaultValue` 둘 다 받는다.
- 입력 → 결과: `value` 없이 날짜/시각/범위 `defaultValue`만 delegate에 넣으면 DateField·TimeField·DatePicker·DateRangePicker·RangeCalendar 모두 RAC에 전달하는 `defaultValue`가 `null`이다. 제안된 accepts 추가 후 Code/AI/API가 해당 속성을 저장하면 검증을 통과해도 초기 입력/선택은 비어 있게 된다.
- 보완 방향: 6종 공통 작성 초기값 선택 규칙을 명시하고 DOM·Canvas·Code 왕복에 적용한다. 실행 중 override(특히 clear의 명시 `null`)와 작성 초기값 fallback의 우선순위를 분리해 초기값이 되살아나지 않게 한다. 패널에 `defaultValue`를 추가 노출할 필요는 없다.
