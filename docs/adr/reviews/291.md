# ADR-291 Review Log

## Round 1 — 2026-10-29 (reviewer: codex)

설계 리뷰 판정: HIGH 2 · MEDIUM 1 · pending 3. 구현 착수 전 아래 계약 보완 필요. 제품 코드·ADR 본문·Status는 변경하지 않았다. 기존 미커밋 spike와 다른 작업자의 dirty 변경을 보존했다.

### H1 — 계산 필드 집계의 서버 전송

- 위치: ADR Decision 5–6 (`291-data-query-vocabulary-computed-fields.md:114–115`), breakdown:74–75.
- 입력 → 잘못된 결과: 원본 두 행 `{price:10,qty:2}`, `{price:11,qty:2}`, 계산 열 `total=price*qty`, 일반 필드로 groupBy하고 `sum(total)`을 지정한다. 계산 필드 조건·정렬·묶기 키는 없어서 명시된 COMPUTED 규칙에 해당하지 않는다. body 서버는 total 원본도 식도 받지 않으므로 기대 합계 42를 산출할 수 없다(서버 정책에 따라 null/0/거절). 집계 응답에는 price/qty도 없어 응답 후 계산으로 복구할 수 없다.
- 현행 근거: `catalogPreviewSession.ts:1252`는 모든 집계를 로컬로 남긴다. 이 ADR이 이를 서버로 확장한다. `evaluate.ts:489`의 aggregateOf는 field의 cellOf 값을 집계하므로 로컬에서는 계산 열 read를 사용한다.
- 해결: aggregates.field와 참조 경로의 계산 의존성을 COMPUTED 판정에 포함. 하나라도 서버에서 계산 불가능하면 원시 행 전체를 상한 안에서 로드하고 로컬 전체 query를 실행하거나 명시적으로 거부한다. 원시 행과 서버 집계 결과의 응답 모드를 구분한다. G4에 `groupBy(raw field)+sum(computed field)` 반례 추가.
- 검증: 실제 엔진의 두 행 곱 합계 42 확인. 미래 서버 어댑터는 미구현이므로 잘못된 서버 응답 자체는 UNVERIFIED; 요청에 필요한 정보가 없다는 설계 판정이다.

### H2 — 식별자 범위를 잃는 이름/ID 치환

- 위치: breakdown:58–59.
- 입력 → 잘못된 결과: collection에 `items` 배열과 최상위 `price`가 있고 items는 `[{price:10},{price:20}]`. `sum(items[*].price)`는 30이다. 모든 Identifier를 collection field id로 치환해 `sum('fld_items'[*].'fld_price')`로 저장하면 실제 2.1.0 엔진에서 0이다. 최상위 price가 없으면 유효한 JSON 하위 속성이 모르는 필드로 거절된다.
- 근거: 실제 compile AST의 projection 양쪽은 모두 Identifier이다. Lexer token 종류만으로 scope를 알 수 없다. schema는 object/array와 children을 허용한다(`types.ts:1320`). 공식 spec의 projection/current-node/pipe 규칙도 평가 컨텍스트 이동을 정의한다: https://opensource.adobe.com/json-formula/doc/output/json-formula-specification-2.1.0.html
- 해결: root field 참조를 AST scope로 판정하고 해당 token만 치환한다. JSON 하위 key·객체 생성 key·projection/pipe/고차 함수의 현재 항목을 구분하며 의존성·순환 탐색도 같은 판정을 공유한다. 지원하지 않는 문법은 명시적으로 제한해야 한다. G1에 위 배열 합 및 root field rename 왕복을 포함한다.
- 검증: 설치본 엔진 실행에서 원식=30, root만 치환=30, 전부 치환=0. 실제 names.ts 구현은 아직 없으므로 이 결과는 제안된 치환 규칙의 반례다.

### M3 — 코드 보기에서 결과 타입 유실

- 위치: ADR Decision 2·9 (`291-data-query-vocabulary-computed-fields.md:111,118`), breakdown:68–69.
- 입력 → 잘못된 결과: 동일한 expression에 resultType number 또는 string을 지정한 두 계산 열은 서로 다른 셀·비교 의미를 갖는다. 제안된 `formula: "price"` 출력은 동일하고 UI type을 formula로 저장하면 기존 type도 동일하다. 역변환은 어느 resultType인지 결정할 수 없어 날짜 타입이나 비교 목록을 바꾸거나 적용을 거절하게 된다.
- 현행 근거: Builder codeView.ts:74–80은 schema id/key/type/reference를 전달한다. 새 resultType을 내보낼 경로는 제안에 없다.
- 해결: 코드 보기에서 formula 객체에 expression/resultType을 함께 보존하거나 기존 type을 결과 타입으로 사용하고 formula 유무로 계산 열을 식별하는 계약을 명시. 동일 expression에 서로 다른 resultType을 둔 왕복 fixture로 식뿐 아니라 타입의 불변을 검증한다.
- 검증: 제안 출력 형식의 정보 손실을 명세 모델로 확인. 실제 신규 생성기·역변환은 UNVERIFIED.

### h1 — fixed (설계)

Decision 5 (`291-data-query-vocabulary-computed-fields.md:114`)와 breakdown Phase 3는 aggregates[].field 및 계산 의존 전이를 COMPUTED 입력으로 포함한다. 하나라도 있으면 보기 사슬 전체를 원시 행 모드로 실행하고 서버 집계 결과와 구분한다. G4에 groupBy(raw)+sum(total)=42, group 요청 없음, 상한 거부를 추가했다. 기존 문제를 해결하는 계약이다. 실제 서버 어댑터는 UNVERIFIED.

### h2 — HIGH 유지: 루트 행을 유지하는 @ 참조를 제외

- 위치: `docs/adr/291-data-query-vocabulary-computed-fields.md:111`, `docs/adr/design/291-data-query-vocabulary-computed-fields-breakdown.md:60`.
- 원래 `sum(items[*].price)` 반례는 루트 items만 치환하면 30을 유지한다. 이 부분은 수리됐다.
- 남은 재현: `{price:10,qty:2}`의 식 `@.price * qty`는 20이다. 설치본 AST는 `ChainedExpression(Current, Identifier(price))`이다. 새 규칙(ChainedExpression 첫 자식만 루트)은 qty만 참조로 수집하고 price는 제외한다. 저장식은 `@.price * 'fld_qty'`가 된다. price를 unitPrice로 rename한 행 `{fld_price:10,fld_qty:2,unitPrice:10,qty:2}`에서 설치 엔진 결과는 **0**이다. 숫자 계산이 조용히 바뀌고 price의 의존성 탐색도 누락된다.
- 근거: 설치본 `TreeInterpreter.js:103`은 왼쪽 결과를 오른쪽 평가 컨텍스트로 쓰고, `:379`의 Current는 현재 value를 그대로 반환한다. 따라서 루트 @ 뒤의 price는 JSON 하위 객체 속성이 아니라 collection 루트 필드다.
- 토큰 쪽도 점 뒤를 하위로 분류하므로 양쪽 다중집합은 `[qty]`로 일치한다. 일치 검사는 공유하는 의미 오류를 검출하지 못한다.
- 해결: 문법 노드 위치만으로 하위 범위를 단정하지 말고 현재 값이 루트 행인지, 하위 JSON인지, 새로 생성된 값인지 전달해 판정한다. 최소한 root @를 보존하는 chain/pipe를 처리하고, 판정할 수 없는 문법은 검증에서 명시적으로 거절한다. `@.price * qty`의 값·rename·의존성 fixture를 고정한다. 미래 범용 지원이 요구되는 것은 아니며, 지원 불가 구문을 조용히 통과시키지 않는 계약이면 충분하다.
- 검증: `.agent/runs/2026-10-29-review-adr291/repair-probe.mjs` 6 assertions PASS. 제안 AST 판정은 명세 모델이며 치환 뒤 수치 변화는 실제 json-formula 2.1.0 엔진 실행이다. 미구현 scope.ts가 실제로 배포됐다는 주장은 아니다.
