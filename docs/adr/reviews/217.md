### 발견 사항

#### h1 · HIGH · 산점도가 극값 fallback에서 원본에 없는 점으로 바뀐다

- 설계 근거: `docs/adr/design/217-chart-reference-line-scatter-breakdown.md:62`는 행마다 원본 점을 보존하고, `:66`은 aggregate를 거부하면서 기존 211/216 예산과 넓힌 창 재추출을 그대로 재사용한다.
- 실제 경로: `packages/specs/src/chart/budget.ts:467-474`는 실제 존재하는 점 수가 아니라 `S × |U|`로 예산을 판정한다. `:803-810`은 마지막 bucket에서도 초과하면 `aggregateBuckets`를 호출하며, 넓힌 창도 `:870-873`에서 같은 집계를 한다. `:384-389`는 집계 점의 x를 bucket 첫 위치로 옮긴다.
- 반증: 설계의 group scatter 형태로 60시리즈 × 각 10점 = 600행을 구성했다. 각 행 i의 x=i, 시리즈=i%60, y=floor(i/60)+1이다. 현재 공용 예산 함수에 line의 extrema 경로(설계가 재사용하겠다고 한 경로), 기본 metrics, 폭 400을 넣으면 `fitEff=13`, 마지막 `B=1, U=120, pathPoints=7200`, `fallback=true`, `applied=aggregate`다. 시리즈 0의 원본 `(60,2)`가 `(47,2)`로 바뀐다. 원본 600점은 P=5000 아래인데 희소 격자를 조밀하게 계수하여 fallback을 발생시킨다.
- 영향: 옵션 목록에서 aggregate만 숨겨도 내부 fallback은 살아 있다. 원본에 없는 좌표를 관측값처럼 그려 산점도의 의미가 바뀐다. 넓힌 window 역시 같은 위험이다.
- 필요한 수정: scatter의 점 계수와 overflow/fallback을 명시하고, 모든 결과 `(x,y,series)`가 원본 관측점에 속하도록 해야 한다. 집계를 금지한 채 예산을 지키는 축소 또는 명시적 진단 계약을 정한다. 6종 기존 경로의 변경 여부는 별도 구분한다.
- 검증 범위: 신규 scatter 구현을 실행한 것이 아니라, 설계한 입력 형태를 현재 production 공용 변환 함수에 직접 넣어 재사용 전제를 반증했다.

#### h2 · HIGH · 구버전의 설정 오류 fallback은 현재 코드에 없다

- 설계 근거: `docs/adr/217-chart-reference-line-scatter.md:16`, `:45`, `:115` 및 breakdown `:98`은 구버전 dist가 scatter를 `Check chart settings`로 표시하고 데이터를 보존한다고 단정한다.
- 실제 경로: `packages/specs/src/chart/computeChartScene.ts:325`는 설정 오류 검사(`:351`)보다 먼저 모델을 만들고, `packages/specs/src/chart/budget.ts:174-177`의 `slotFit`은 미지원 종류를 throw한다. 이 예외를 설정 진단으로 바꾸는 동작은 해당 경로에 없다.
- 반증: 기본 props에 `chartType:'scatter', dimension:'x', metric:'y'`, 한 행 `{x:1,y:10}`, 400×300을 넣으면 현재 TS 소스와 현재 로컬 `packages/specs/dist/index.js` 모두 `Error: unhandled chartType: scatter`를 반환한다. 설정 오류 scene이 반환되지 않는다.
- 영향: 이미 배포된 구버전은 신규 코드 변경으로 고칠 수 없다. 문서의 G3/T12 통과 조건은 현재 rollback 대상과 양립하지 않는다. 이 결과가 저장 데이터 삭제를 입증하는 것은 아니다; 안전한 렌더 fallback 주장이 반증된 것이다.
- 필요한 수정: rollback 대상 revision을 고정하고, 실제 가능한 호환/다운그레이드 절차 또는 지원하지 않는 구버전 경계를 기록한다. 안전 fallback을 보장하려면 먼저 그 기능을 가진 호환 버전을 배포하는 순서가 필요하다.
- 검증 한계: 로컬 dist의 build SHA는 고정하지 않았다. TS 소스 HEAD에서도 동일 예외를 확인했으며, 구버전 완제품 UI와 저장 roundtrip은 실행하지 않았다.

#### m3 · MEDIUM · 같은 시리즈의 겹친 점은 두 렌더러에서 농도가 달라진다

- 설계 근거: breakdown `:65`는 시리즈당 path 하나, `:67`은 점마다 Recharts Scatter shape에 `fillOpacity=0.85`, `:68`은 Skia 변경 0을 정한다. `:75`의 예제도 같은 시리즈에 `(4,40)` 중복점을 포함한다.
- 실제 경로: `packages/specs/src/chart/marks/dots.ts:33-44`는 모든 원을 단일 path로 합친다. `packages/specs/src/renderers/skiaPrimitives.ts:3551-3553`는 그 path에 `fillAlpha=0.85`를 한 번 적용한다. 설치된 `packages/shared/node_modules/recharts/es6/cartesian/Scatter.js:309`는 점마다 ScatterPoint를 렌더한다.
- 독립 브라우저 반증: 흰 배경에 같은 검은 원 두 개를 놓고, 단일 path에 두 subpath를 둔 경우와 개별 원 두 개를 둔 경우를 Chromium SVG→canvas로 비교했다. 중심 픽셀은 각각 `[38,38,38,255]`와 `[6,6,6,255]`였다. 좌표·반지름·fill-opacity가 같아도 합성 단위가 달라 결과가 다르다. 개별 점의 유효 alpha는 `1-(1-0.85)^2=0.9775`다. [W3C SVG 합성 규칙](https://www.w3.org/TR/SVG11/masking.html#SimpleAlphaBlending)과 일치한다.
- 영향: 밀집·중복점이 흔한 산점도에서 Preview만 더 짙게 보인다. `cx/cy`와 축 문자열만 비교하는 현재 HC4/G3는 이 차이를 검출하지 못한다.
- 필요한 수정: 두 leg의 합성 단위를 맞추거나 공통 불투명도 정책을 정한다. 선택한 방식의 점별 hover와 성능 비용을 함께 평가한다.
- 검증 범위: production Builder Skia와 신규 Scatter UI의 live 비교가 아니라, 현재 Skia path 표현과 제안한 DOM 표현을 비교한 독립 브라우저 프로브다.
