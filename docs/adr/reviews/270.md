## Round 1 — 2026-10-17 (reviewer: codex)

판정: **설계 승인 보류 — HIGH 3 / MEDIUM 2, 모두 open (pending 5)**.

범위: HEAD `94c9a0d521bd8477046cb9fc8992734022c7fe4d`의 ADR-270 Proposed 본문과 breakdown 설계 리뷰 1회. 제품 코드와 ADR 본문·Status는 수정하지 않았다. 아래는 제안한 변경을 현재 소비 경로에 적용했을 때의 차단 문제이며, 아직 없는 구현을 현재 제품 결함으로 단정하지 않는다.

### H1 — DRAW 소비자까지 갱신되지 않음 (open)

- 위치: breakdown:39. 이 행은 node data만 다시 등록하고 명령 스트림은 건드리지 않는다고 명시한다.
- 근거: `renderCommands.ts:1937-1951`, `:1991-2001`은 registry data를 spread한 파생본을 DRAW에 저장한다. `:2843`은 그 `cmd.skiaData`를 그린다. `useSkiaNode.ts:74-81`의 등록은 registry 교체와 picture 무효화만 수행한다. picture MISS도 `renderCommands.ts:3027`의 `recordSelfSpan`이 기존 명령을 다시 기록한다.
- 반례: `src=A`인 Image가 cache miss로 bind되어 DRAW의 `image.skImage=null` → A 완료 → 새 데이터만 등록하고 해당 bounds를 damage로 표시 → 기존 DRAW는 여전히 null을 소비하므로 placeholder가 남는다. picture를 꺼도 동일하다.
- 해결 방향: 해당 element의 self DRAW 구간을 갱신하거나 명시적인 paint-data 참조 슬롯을 도입한다. 공간 인덱스·layout은 보존할 수 있지만 DRAW 데이터 교체까지 금지하면 안 된다. 실제 command 실행 결과가 이미지로 바뀌는 조건을 G2에 고정한다.

### H2 — 미로딩 URL의 identity 소실 (open)

- 위치: breakdown:33. `registerSkiaNode(id,data)`가 data의 src를 모은다는 계약의 입력이 현재 존재하지 않는다.
- 근거: `specShapeConverter.ts:1195-1197`에서 `shape.src`로 조회/로드한 뒤 `:1223-1229`에는 `skImage`, content rect만 저장한다. `nodeRendererTypes.ts:119-127`에도 src 필드가 없다. rule image는 `ruleShapes.ts:393`의 변환을 거쳐 내부 children으로 등록된다.
- 반례: 서로 다른 URL A/B의 동일 크기 미로딩 Image 두 개 → 두 data 모두 null SkImage와 같은 content rect → 등록 시 URL을 복구할 수 없음 → A 완료 통지에서 A의 elementId를 찾을 수 없어 갱신 0. 두 노드가 같은 URL을 공유하는 경우도 완료 전에 연결할 수 없다.
- 해결 방향: 변환 단계에서 원본 cache key (`asset:` ref 포함)를 미로딩 상태에도 보존하고 내부 children을 포함한 의존성을 소유 elementId에 연결한다. register/move/unregister/clear에서의 제거·교체 규칙도 이 입력에 맞춰 명시한다. 캐시 핸들 역조회로 대체하지 않는다.

### H3 — 이미지 완료와 편집의 같은 프레임에서 pending 변경 유실 (open)

- 위치: breakdown:37-42의 syncScene 교체 계약.
- 근거: `CatalogCanvas.tsx:898-904`는 명령 commit 시 `sceneStale=true`를 세운다. 현재 `:774-775`는 전체 rebind가 최신 문서 변경까지 반영한 직후 stale을 지운다. `:796`은 false면 즉시 return하고 `:799`의 `scene.sync()`를 건너뛴다. scroll/preview/rows도 같은 stale 경로를 사용한다.
- 반례: 다음 RAF 전에 이미지 A 완료와 다른 노드 B의 색/텍스트 편집이 같이 도착 → imagesStale와 sceneStale가 모두 true → 제안대로 imageLoaded를 A만의 재등록으로 바꾸고 현재 stale 해제를 유지 → B의 dirty delta를 sync하지 않고 return → B는 다음 독립 변경까지 옛 픽셀·bounds를 유지한다. 기존 전체 rebind 경로는 이 입력을 반영하므로 도입 시 회귀다.
- 해결 방향: 완료 처리가 문서·property dirty를 소비한 것으로 간주하지 않도록 순서를 명시한다. pending scene.sync를 먼저 적용한 뒤 현재 의존성·bounds로 이미지 갱신하고 damage를 합치거나 동등한 트랜잭션 규칙을 둔다. 같은 프레임 편집/삭제/scroll과 이미지 완료의 최종 상태를 fresh bind와 대조한다. load-edit 성능 수치만으로 이 상태 보존을 증명할 수 없다.

### M4 — Phase 3a API의 실제 비용·픽셀 경로가 설명과 다름 (open)

- 위치: 본문 F8:27, breakdown:57-61.
- 근거: 설치된 CanvasKit 0.42.0의 `types/index.d.ts:413-418`은 이 API가 canvas에 그린 뒤 readback한다고 명시한다. 실제 `bin/canvaskit.js:66-67`도 `drawImage → getImageData → MakeImage → _malloc/HEAPU8.set`이다. 반면 texture-backed API는 `types/index.d.ts:335-349`의 `MakeLazyImageFromTextureSource`로 별개이며 source 소유권도 다르다. `MakeImageFromEncoded`는 `:403-410`에서 실제 사용 시점까지 decode를 지연할 수 있다고 명시한다.
- 반례 입력: 2,048×2,048 PNG 한 장을 3a로 완료시키면 메인에서 16 MiB RGBA readback과 WASM 복사를 거친 뒤 GPU에서 그릴 때의 업로드도 남는다. `imageDecodeMain=0`과 새 API 호출 수만으로 메인 decode/업로드 비용 제거를 증명할 수 없다. 이 구조상 추가 작업은 확정이지만 실제 ms 회귀와 픽셀 차이는 **UNVERIFIED**다.
- 해결 방향: 코덱 호출·실제 decode·canvas readback·WASM 복사·GPU upload를 구분해 F3/F8과 HC4 비용 모델을 바로잡고, 선택한 primitive와 source 해제 계약을 명시한다. 직접 texture 경로를 채택하면 `bitmap.close()` 즉시 호출을 그대로 복사하면 안 된다. 기존 encoded 경로와 새 decoder를 직접 비교하는 픽셀 arm을 둔다. 현재 setImagePartialOff는 rebind만 바꾸므로 Phase3에서 양쪽이 같은 새 decoder를 쓰면 decoder 회귀를 검출하지 못한다. 설계 착수 자체를 새 측정 승인에 묶으라는 지적은 아니다.

### M5 — 업로드 ratchet 조건의 모순 (open)

- 위치: 본문 G3:129, breakdown:22/26/59/62.
- 반례: Phase0의 기존 경로에서 새 `MakeImageFromCanvasImageSource` 호출 수=0 → Phase3 이미지 한 장에서 호출 수=1, 바이트/시간도 양수 → G3의 '업로드 호출·바이트·프레임당 업로드 시간이 Phase0 이내'는 정상 변경도 실패시킨다. 반대로 Phase0에 존재하지 않던 작업을 측정하지 않으면 HC4 비용 이동 검증이 비어 있다. 같은 입력을 반복해도 실제 ms는 결정적이지 않으며 `perf-ratchet-gate.mjs:450-455`의 `--add-keys`는 완전 일치만 A로 받는다.

### 신규 H1 — context 복원 뒤 이미지 재획득·DRAW 교체가 없음 (open)

- 위치: `docs/adr/design/270-image-load-path-partial-update-off-thread-decode-breakdown.md:67-69`, 본문 R8 (`270-image-load-path-partial-update-off-thread-decode.md:129`). 새 수리는 webglcontextlost에서 clearImageCache를 호출하고 generation 증가만 검사한다.
- 현재 소비 경로: `imageCache.ts:326-337`은 모든 cached SkImage를 destroyCachedImage로 폐기하고 pending을 비우지만 재요청이나 완료 통지를 만들지 않는다. `CatalogCanvas.tsx:1551-1557`의 restore는 renderer.resize/invalidateContent/clearFrame만 수행한다. `SkiaRenderer.ts:1389-1399`의 resize도 surface만 재생성한다. `surfaceLost`는 상태 표시용이고 scene effect의 의존성이 아니다 (`CatalogCanvas.tsx:1638,1740`). registry와 DRAW에는 폐기된 이미지 핸들이 남는다. `nodeRendererImage.ts:54-130`은 삭제된 핸들을 만나면 placeholder를 그리고 return하며 loadSkImage를 호출하지 않는다. 재로드는 converter 재진입 때만 일어난다 (`specShapeConverter.ts:1195-1197`).
- 반례 입력/순서: 이미지 A를 완전히 로드하고 편집·네트워크가 없는 idle 상태 → GPU context 소실 → 제안한 clearImageCache가 A를 폐기하고 generation 증가 → context 복원 → 기존 resize+redraw → 기존 DRAW가 폐기된 핸들을 만나 placeholder. 완료 통지·owner dirty·새 fetch 어느 것도 발생하지 않아 추가 편집 또는 수동 rebind 전까지 이미지가 복구되지 않는다. 이것은 '복원 검사가 부족하다'는 커버리지 지적이 아니라, 새 clear 동작이 추가될 때의 복구 경로 단절이다. 실제 브라우저 context loss 실행은 **UNVERIFIED**이며, 현재 함수 본문을 연결한 정적 설계 반례다.
- 해결 방향: 새 backend/surface가 준비된 restore 시점에 현재 문서의 이미지 소유자를 재획득시키는 계약을 추가한다. 단순한 선택은 복원 시 scene 전체 rebuild 1회를 허용해 cache miss 재요청과 DRAW 교체를 보장하는 것이다. 또는 현재 imageOwners 전체를 dirty로 seed하여 같은 일을 보장한다. sceneStale=true만 세우면 binding dirty가 비어 있으므로 충분하지 않다. 소실 중 시작된 요청과 이전 generation 결과를 구분하고, 새 surface 준비 뒤 요청을 재시작해야 한다.
- 완료 기준: 'clear 호출·generation 증가'에서 끝내지 않고, 로드된 이미지 → loss → restore → 추가 사용자 편집 없이 재요청 완료 → 정상 이미지 DRAW·픽셀 복구까지 명시한다. 기존 5건을 재개할 필요는 없다.
