### H1 — fillSlot 보존만으로 새 instance의 slot 내용을 보존할 수 없다

- 위치: `docs/adr/260-component-origin-in-place.md:92`, `:97`; breakdown `:14`의 resolver 무변경 분류.
- 입력 → 결과: Card 원본에 소유 text를 `fillSlot`으로 넣고 그 노드를 project definition의 template으로 삼는다. 원본을 직접 resolve하면 text가 나오지만 그 정의의 instance를 resolve하면 text가 없다. ToggleButtonGroup·Card·Tabs를 Create component한 뒤 새 instance를 넣는 정상 흐름에 해당한다.
- 코드 근거: `packages/shared/src/catalog/resolution/resolver.ts:1514`는 투영 중인 template의 `descendantOverrides`가 아니라 바깥 `owner.descendantOverrides`에서만 주소를 찾는다. `:1828`의 nestedScope는 library template의 `descendantPatches`·`slotFills`만 옮기며 project NodeEntry의 fillSlot을 옮기지 않는다. `:1962`는 그렇게 찾은 change만 적용한다.
- 실행: 실제 `createG1Fixture`와 `CatalogGraph`·`resolveCatalogNode` 사용. 동일 graph의 원본에는 `slot-owned-marker`가 있고 instance에는 없다. page 참조 edge 구현은 아직 없으므로 기존 소유 모양 template으로 resolver의 소유자 비의존 주장을 반증했다.
- 해결 방향: project template 노드 자체의 patch·replace·fillSlot을 새 instance의 주소 공간으로 투영하는 계약을 명시하고 resolver·positions·materializer 소비자를 분류한다. 바깥 instance의 override 우선순위, 소유 node와 projected 자리의 선택·편집 경계도 유지해야 한다. 원본 보존뿐 아니라 새 instance·detach 결과의 slot 내용을 G2/G3에서 확인한다.

### H2 — 중첩 원본 삭제 시 숨은 template 소유권과 page 불변식이 충돌한다

- 위치: `docs/adr/260-component-origin-in-place.md:91`, `:96`, `:99`; breakdown `:25`, `:37`.
- 입력 → 결과: page에 원본 A가 있고 A의 자식 B도 다른 정의의 원본이다. A 또는 page를 삭제하여 A 정의가 A 서브트리를 그대로 소유하면 B의 소유 사슬 top은 page가 아니라 A 정의가 된다. B를 참조 모양으로 남기면 ADR의 page-only 검증에 실패한다. B 정의도 `originOnPage:false`로 바꾸어 B를 소유하게 하면 A 노드의 children과 B 정의가 B를 동시에 소유하여 `DUPLICATE_OWNERSHIP`이 된다. A에서 B를 빼면 살아 있는 A instance의 구조를 잃는다.
- 코드 근거: `packages/shared/src/catalog/document/graph.ts:76`의 ownedChildren 및 `:544`의 단일 소유 검사; `commands/structure.ts:890`의 subtree는 소유 서브트리를 수집한다. 현재 코드에 없는 page 참조 모델의 문제이므로 기존 graph에서 live 결함으로 재현했다고 주장하지 않는다.
- 실행: ADR의 삭제 변환 그대로 적용한 최소 ownership 모델에서 non-page origin과 중복 소유의 두 결과를 확인했다.
- 해결 방향: 숨은 바깥 template 안의 안쪽 정의가 참조를 유지할 수 있는 상태·검증·Restore 계약을 정한다. 또는 소유 중복과 instance 구조 손실 없이 변환하는 다른 정책을 정한다. 중첩 삭제·page 삭제·안쪽/바깥 각각 Restore·undo가 같은 정책으로 동작해야 한다. 본문의 `originOnPage?:true`와 breakdown의 boolean 세 상태 표기도 이에 맞춰 통일한다.

### H3 — clipboard에 원본 정체성이 없어 clone 한 곳 변경으로 붙여넣기 계약을 구현할 수 없다

- 위치: `docs/adr/260-component-origin-in-place.md:98`; breakdown `:39`.
- 입력 → 결과: 원본을 복사하여 같은 프로젝트의 다른 탭에 붙여넣는다. copyNodes는 노드와 소유 interaction/stateVariable만 저장하여 그 노드를 원본으로 지정한 정의를 담지 않는다. pasteNodes의 clone은 대상 graph가 아니라 clipboard만으로 만든 source reader를 받으므로 `originOnPage` 정의나 역색인을 볼 수 없다. 일반 노드 사본이 되고 요구한 INSTANCE가 되지 않는다.
- 추가 반례: 기존 project instance P를 새 원본 Q로 만든 뒤 다른 프로젝트에 붙여넣는다. Q 원본의 definitionId=P를 그대로 복사하면 대상에 P가 없어 보통 사본 대신 `DANGLING_DEFINITION`으로 실패한다. 원본 루트의 변환만으로 참조 정의에 의존하는 하위 노드까지 보통 사본으로 만들 수 없다.
- 코드 근거: `packages/shared/src/catalog/commands/structure.ts:1164` copyNodes, `:1203` clipboard entries로만 source 구성, `:1219` clone 호출; `document/clone.ts:13`은 정의 참조를 그대로 유지한다. `apps/builder/src/builder/catalogRuntime/clipboardText.ts:12`의 직렬화도 rootIds·entries만 저장한다.
- 실행: production copyNodes 출력의 필드는 rootIds·entries뿐이고 entry는 node 하나였다. project 정의를 참조하는 해당 노드를 빈 대상 graph에 pasteNodes로 넣으면 `DANGLING_DEFINITION`이 발생했다.
- 해결 방향: 원본→정의 식별 정보·source project 정체성과 대상 정의 유무를 copy/serialize/parse/paste 경계에 전달한다. 타 프로젝트는 정의 의존성을 materialize하는 일반 사본 정책을 정한다. 복사 후 원본 삭제·정의 해체·reload·다른 탭에서도 snapshot과 현재 정의를 어떻게 사용할지 고정한다.

### H4 — DEFINITION_CYCLE 걷기 무변경은 slot을 통한 자기 instance를 거부하지 않는다

- 위치: `docs/adr/260-component-origin-in-place.md:91`; breakdown `:25`.
- 입력 → 결과: Card 기반 원본의 fillSlot 소유 자식에 자기 정의의 instance를 넣는다. graph 전체 검증은 이를 허용한다. 같은 자기 instance를 children으로 넣으면 `DEFINITION_CYCLE`로 거부한다. 새 설계가 소유 fillSlot을 보존하면서 허용하는 정상 삽입 경로인데, 자기 instance 삽입 거부라는 Hard 계약을 지키지 못한다.
- 코드 근거: `packages/shared/src/catalog/document/graph.ts:1096`의 walk는 `node.children`만 걷는다(`:1103`). `ownedChildren(:76)`에 포함되는 replace·fillSlot 자식은 정의 순환 검사에서 빠진다. 증분 검증의 호출 여부와 full 검증의 보행 범위를 모두 맞춰야 한다.
- 실행: 실제 fixture library를 쓰는 full CatalogGraph 생성에서 children cycle은 거부되고 fillSlot cycle은 ACCEPTED였다. resolver가 stack overflow한다는 가설은 반증되어 채택하지 않았다. 현재는 H1 때문에 template의 fill이 누락된다. 순환 허용 자체와 Hard 계약 위반만 판정했다.

### H5 — HIGH: 정의 snapshot과 detachInto만으로 project token을 다른 프로젝트에 옮길 수 없다

- 위치: `docs/adr/260-component-origin-in-place.md:110-114` (Decision 13), `docs/adr/design/260-component-origin-in-place-breakdown.md:41`.
- 왜 틀렸는가: snapshot의 닫힌 집합은 project **정의**와 template 소유 서브트리뿐이다. template의 authored prop·visual이 참조하는 project token은 그 집합에 없다. `detachInto`는 template의 visual을 복사하며 token을 값으로 확정하지 않는다 (`commands/components.ts:59-66`, `:85-91`; `commands/materialize.ts:173-178`, `:329-341`). `cloneNodeSubgraph`도 이 외부 참조를 그대로 유지한다 (`document/clone.ts:13`, `:138-149`). 따라서 정의 참조를 모두 library 노드로 물질화했어도 대상 transaction은 `document/graph.ts:953-960`에서 `DANGLING_TOKEN`으로 거부된다.
- production 입력·상태 → 잘못된 결과: 사용자 색 token `project:token:brand`를 template의 `visual.color`에 지정한 component instance를 복사한다. 대상은 다른 projectId의 프로젝트이며 그 정의와 token이 없다. r1에 명시된 정의+template snapshot을 reader에 겹친 뒤 production `detachInstances`가 호출하는 `detachInto` → `cloneNodeSubgraph` → `insertNodes`/transaction을 실행하면 `DANGLING_TOKEN`. 정의 참조는 이미 `lib:definition:text`로 풀려 있으므로 H3의 원본 식별 문제와 다른 반례다. 정상적인 token 사용이 붙여넣기 자체를 막는다.
