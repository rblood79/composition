# ADR-253 Review Log

## Round 1 — 2026-10-06 (reviewer: codex)

판정: 원본을 재사용 단위로 삼는 방향은 타당하다. 다만 HIGH 2건과 MEDIUM 2건이 남아 현재 실행 계획 전체를 승인하기에는 보완이 필요하다. 기준 HEAD는 `3ebccf938`이며 ADR Status는 Proposed 그대로 유지했다.

### h1 — HIGH: Phase 4가 Phase 5의 선택적 library 확장에 의존한다

- 대상: `docs/adr/design/253-base-ui-origin-reuse-breakdown.md:122`, `:129`; 본문 Decision 8 / G4 / G5 (`docs/adr/253-base-ui-origin-reuse.md:134`, `:173`).
- 입력 → 결과: Select의 네 항목을 ListBox 원본 instance의 slot에 넣으려 한다. 현재 LibraryTemplateNode는 children 및 단일 경로 patch만 표현하고 slot 채움은 표현하지 못한다. children으로 대체하면 ListBox의 기존 세 항목은 원본 루트 안에 남고 Select의 네 항목은 그 루트의 형제로 붙는다. 따라서 목록이 중복되거나 원본 루트가 잘못된 항목 집합을 렌더한다.
- 코드: `packages/shared/src/catalog/document/types.ts:654` (LibraryDescendantPatch), `:661` (LibraryTemplateNode); `document/library.ts:316` (patch 검증); `resolution/resolver.ts:1118` (원본 root 투영), `:1182` (template.children 별도 투영), `:1223` (프로젝트 fillSlot만 지원).
- 반례: 실제 code library를 buildCatalogLibrary로 재검증한 뒤 Select 안에 ListBox composite와 네 항목 children을 넣었다. resolveCatalogNode 결과 ListBox root 안에는 component-listbox__item-1~~3, root 밖에는 component-select__item-1~~4가 남았다. 새 fillSlot 형식을 구현한 증거가 아니라 현재 children 대체안이 slot 채움이 아님을 확인한 반례다.
- 해결: slot 채움 표현·검증·해석의 최소 확장을 Phase 4 선행으로 옮기고 G4에 해당 unit을 포함한다. Phase 5에서 선택적으로 미룰 대상은 Dialog/Popover 바탕 재작성으로 한정한다. 또는 Phase 4의 실제 표현 방식을 별도로 명시하고 원본 재사용·항목 편집 양립을 증명한다. ADR 분리는 필요하지 않다.

### h2 — HIGH: field Button 재사용에 RAC slot 및 context 계승 계약이 빠졌다

- 대상: `docs/adr/design/253-base-ui-origin-reuse-breakdown.md:113`; `docs/adr/253-base-ui-origin-reuse.md:129`, `:172`.
- 입력 → 결과: NumberField 증감 버튼을 일반 Button instance로 직접 그리면 현행 DOM binding은 slot을 전달하지 않아 RAC NumberField가 slot 오류를 던진다. slot만 보완해도 원본의 isDisabled:false와 binding의 boolean 강제 전달이 RAC 부모/증감 한계 context를 덮는다. 부모가 disabled이거나 값이 maxValue에 도달한 상태에서도 버튼이 enabled로 표시된다.
- 코드: `packages/shared/src/components/NumberField.tsx:93` (slot=decrement/increment); `catalog/document/generated/reusableOriginLibrary.ts:2981` (Button 기본 isDisabled:false); `catalog/runtime/domBinding.tsx:485` (slot 누락, :496 false 전달); `components/Button.tsx:51` (isDisabled 전달). 설치 RAC 1.21.0 dist/private/utils.mjs의 useContextProps는 mergeProps(contextProps, props)로 명시 prop을 우선한다.
- 반례: 설치 RAC + 현재 shared Button을 SSR로 렌더했다. NumberField 아래 slot 없는 Button은 slot 오류. ButtonContext isDisabled:true는 prop 생략 시 disabled, isDisabled:false 명시 시 enabled. NumberField defaultValue=10/maxValue=10의 increment도 같은 결과였다.
- 해결: 사용처별 increment/decrement/clear/trigger slot·행동 역할을 template/binding에서 유지하고, context가 정하는 disabled 값과 기본 false를 구분한다. G3에 disabled·readOnly·min/max 경계 및 증감/열기/지우기 실제 동작을 추가한다. 현재 DOM 구조 matrix는 disabled·수치 경계가 없다 (`breakdown:142`).

### m1 — MEDIUM: FieldError의 동적 validation 및 ARIA 연결을 계승하는 Gate가 없다

- 대상: `docs/adr/design/253-base-ui-origin-reuse-breakdown.md:112`, `:142`; 본문 Decision 5 및 R1.
- 입력 → 결과: field에서 renderChild로 현재 FieldError binding을 사용하면 RAC FieldError가 아닌 span.role=alert가 나온다. invalid/errorMessage를 문서 props와 Canvas presence로만 결정하면 Preview의 blur/submit으로 생긴 validation은 갱신되지 않고, 오류 DOM의 id와 errorMessage slot도 연결되지 않는다.
- 코드: `packages/shared/src/catalog/runtime/domBinding.tsx:473` (정적 span); `packages/shared/src/components/TextField.tsx:115` (현재 RAC FieldError); `packages/shared/src/catalog/runtime/presence.ts:204` (문서 record 기반 resting presence). 설치 RAC FieldError.mjs는 FieldErrorContext의 isInvalid/validationErrors를 읽고 Text slot=errorMessage를 반환한다.
- 반례: RAC TextField isInvalid 아래 실제 RAC FieldError와 현재 binding 형태의 span을 SSR 대조했다. input의 aria-describedby는 같은 error ID를 가리키지만 span에는 그 ID 및 slot=errorMessage가 없어 참조 대상이 소실된다.
- 해결: FieldError binding을 RAC context consumer로 전환하고 부모 원본 prop 문자열과 RAC 동적 오류 생성의 책임을 구분한다. G3에 required/email/pattern 입력 → blur/submit → 오류 표시 및 수정 후 해제, 실제 aria-describedby 대상 존재 검사를 추가한다. 정적 invalid 구조 대조만으로 동적 validation 보존은 입증되지 않는다.
- 공식 근거: [React Aria Forms — constraint validation](https://react-aria.adobe.com/forms), [FieldError 공식 구현](https://github.com/adobe/react-spectrum/blob/main/packages/react-aria-components/src/FieldError.tsx). 판정의 runtime 근거는 설치된 1.21.0 소스와 SSR다.

### m2 — MEDIUM: G1이 명시한 stateRules 전파를 base 스타일 검사로 놓칠 수 있다

- 대상: `docs/adr/design/253-base-ui-origin-reuse-breakdown.md:95`, `:97`; `docs/adr/253-base-ui-origin-reuse.md:170`.
- 입력 → 결과: Button 원본에 hover fill=#123456을 쓰면 composite 외부 record는 바뀌지만 실제로 그리는 template root는 기존 hover fill=#c3c3c3을 유지한다. stateRules는 자식 투영 뒤에 적용되므로 base visual의 키 전달만 늘리는 수정으로는 해결되지 않는다. G1 예시는 padding/배경 base 편집만 요구해 stateRules가 끊겨도 그 예시를 통과한다.
- 코드: `packages/shared/src/catalog/commands/components.ts:139` (stateRules 쓰기); `resolution/resolver.ts:681` (instanceRoot 전달), `:710` (그 뒤 state 적용); `:1135` / `:1234` (중첩 경로도 같은 순서).
- 반례: 실제 catalog 명령 setLibraryDefault → transaction으로 origin-component-button의 hover fill을 쓴 뒤 resolveCatalogNode(..., hover)를 실행했다. outer=#123456, paintedRoot=#c3c3c3을 확인했다.
- 해결: 상태별 원본→template root→중첩 root 전파 순서 및 instance state patch의 우선순위를 명시하고 G1에 hover/pressed/disabled stateRules 편집의 원복 RED 검사를 포함한다. Preview의 실제 hover/press computed style도 별도로 검사한다. 현행 G3 하니스가 프로젝트 원본의 state override 소비를 덮는다고 확인하지 않았다.
