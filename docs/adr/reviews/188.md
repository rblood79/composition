#### H1 — 기전 확보 (round 1/2 대비 보강)

엔진 증분 skip 게이트가 **메모이즈되지 않은 재귀 walk** 다: `subtree_has_dirty(handle)` 는 자기 dirty 를 확인한 뒤 자식 전체를 재귀 순회한다 (`packages/composition-engine/src/tree.rs`). `propagate_dirty` 가 조상 체인을 root 까지 dirty 로 올리므로, dirty leaf 1개여도 root 는 재solve 되고 **clean 형제 서브트리마다 그 크기만큼 walk 를 지불**한다 → `compute_layout()` 1회의 노드 방문은 `O(N)` 이다. `computeDirtyLayoutForIds()` 는 이 호출을 그대로 감싼다 (persistentTaffyTree.ts:447).

따라서 breakdown:124 의 G1 counter("layout input node visits: O(k+promotedAncestors)")를 JS 경계에서만 세면 **엔진의 N 비례 항이 남은 채 GREEN 이 된다**. breakdown:62-64 는 이 비용을 "계측하되"로 허용만 하고 상한을 두지 않으므로 HC1(ADR:32-33)이 닫히지 않는다.

수정 방향(택1 명시 필요): (a) HC1 을 "JS 경계 + 엔진 내부 walk 항"으로 분해하고 N=5,000 에서의 엔진 walk 예산을 G0 에 수치로 고정, (b) `TreeNode` 에 subtree-dirty 요약 플래그를 두어 skip 판정을 O(1) 화하는 엔진 선행 작업을 Phase 1 범위로 편입.

#### H2 — 선례 확보

paint lane 은 이미 stale 거부 계약을 갖는다: `SessionProjectionState`(skiaEditorPresentationBridge.ts:22-28)의 `sequence` + `terminalRevision`, 그리고 `renderedDocumentRevision >= state.terminalRevision` 비교(:79-80)와 `committedDocumentRevision` 소비(:133). ADR-187 타입도 `layoutRevision`/`structureRevision` 을 이미 노출한다 (editorPresentationTypes.ts:67-69).

즉 H2 의 수정은 "revision 신설"이 아니라 **paint lane 선례를 layout publication union 에 이식**하는 것이다. breakdown:70-80 의 `LayoutPublication` 에 `presentationRevision` / `baseCanonicalRevision` 을 필드로 넣고, G4 통과 조건(ADR:162)을 "draw span 과 hitBoundsMap 이 동일 revision 값을 실제로 보유"로 서술해야 검증 가능해진다. 현재 lane 인터페이스에는 해당 필드가 전혀 없다 (editorPresentationLayoutLane.ts:20-33).

#### H3 — targeted publish 가 map 전체를 복사 (신규)

`publishPresentationLayout()` 첫 줄이 `const layoutMap = new Map(input.previousLayoutMap);` 이다 (editorPresentationLayoutLane.ts:96). value/reference 는 보존되지만 **map write 수는 `O(N)`** 이고, publish 마다 새 map 참조가 생긴다.

- HC1 은 "map write 비용은 N 이 아니라 k 에 비례해야 한다"고 단정한다 (ADR:32-33).
- breakdown:125 도 "published map writes: `O(k)`" 를 성공 수식으로 못박는다.
- 반면 breakdown:87 은 "이전 map 의 비영향 node value/reference 를 보존"만 요구해 **복사 자체를 금지하지 않는다** — 현행 구현이 이 조항은 만족하면서 HC1/§6 을 위반하는 상태다.

ADR:21-23 이 이 함수를 기존 publisher 에 연결하는 것을 논의 대상으로 삼으므로, 복사 전략을 그대로 두면 G2("publication write O(k)", ADR:160)를 통과시킬 수 없다. overlay map(base map + affected delta 조회) 또는 구조 공유 map 중 어느 쪽을 계약으로 삼을지 §4.2 에 명시해야 한다. N=5,000 드래그 프레임마다 5,000 entry 삽입은 HC3 의 4ms 예산 안에서도 N 비례 항으로 남는다.

#### M2 — index-shift 기전 추가

현행 stream 은 `commands: RenderCommand[]` 평면 배열이고 `selfSpans` 는 그 배열의 `{start,end}` 인덱스다 (renderCommands.ts:145-164, 666-669). 즉 서브트리 커맨드를 **길이가 다르게** 교체하면 뒤따르는 모든 selfSpan 인덱스가 무효화된다. breakdown:95-97 의 "span 길이 보존 실패 시 patch 거부"는 이 문제를 부분적으로만 막는다 — 거부 조건은 있으나, 길이 보존이 성립하는 descriptor 집합이 무엇인지, 그리고 boundsMap/hitBoundsMap 을 어떤 단위로 재계산하는지가 정의되지 않았다. 현재 hitBoundsMap 은 DFS 중 조상 clip 교차로만 생성된다 (renderCommands.ts:573-576).

#### M3 — parent promotion 판정의 SSOT 가 없다 (신규)

`createPresentationLayoutPlan` 의 `shouldPromoteParent` 기본값은 `() => false` 다 (editorPresentationLayoutLane.ts:62). 승격이 없으면 affected set 은 대상 자신의 서브트리로 한정되고, **in-flow 형제**는 포함되지 않는다 (:78-81). flex/block 흐름에서 한 자식의 used-size 변경은 형제 위치를 바꾸므로 형제 커버리지는 전적으로 이 술어에 달려 있다.

그런데 판정 근거가 될 registry 는 하향 전파축만 갖는다: `EditorMutationEffectPropagation = "self" | "inherited-subtree"` (editorMutationEffectRegistry.ts:6,24) — 상향(used-size) 축이 없다. breakdown:59-61 은 "parent used-size 전파가 확인된 경우에만 상향한다"고 쓸 뿐 **무엇이 그 '확인'의 정본인지** 지정하지 않는다. R1 의 대응(ADR:148, "G1 에서 parent promotion fixture 를 고정")은 fixture 를 만들 뿐 런타임 판정 규칙을 만들지 않으므로 위험이 닫히지 않는다.

수정 방향: registry 에 `usedSizePromotion` 축을 추가하거나(property 단위), promotion 술어를 layout container display 별 규칙 테이블로 §4.1 에 고정.

**반증 시도 1건 (기각)**: "폭 변경 시 텍스트 재배치로 커맨드 수가 달라져 §4.3.2 전제 2(길이 보존)가 자주 깨지고 allowlist가 크게 줄 것"이라는 가설을 세우고 확인한 결과, `updateTextChildren`은 1:1 map이라 자식 수가 보존되고(renderCommands.ts:258-290) 커맨드 방출의 조기 종료 경로도 layout이 아닌 `skiaData` 부재(:537)와 드래그 유예(:546)뿐이다. 순수 geometry 변경에서 커맨드 수는 안정적이므로 **가설 기각** — 전제 2는 과도한 제약이 아니다.

### 신규 이슈 (LOW 2건)

| ID | 이슈 | 증거 | 심각도 |
| --- | --- | --- | --- |
| L2 | hit bounds 재계산이 **entry 제거**를 다루지 않음 | breakdown:264-268; renderCommands.ts:573-576 | LOW |
| L3 | 거부된 그룹의 revision 처리 미정 | breakdown:201-207, 226-228 | LOW |

**L2** — 현행 `hitBoundsMap`은 조상 clip 교차가 비면 **아예 등재하지 않는다**(renderCommands.ts:573-576). §4.3.2의 재계산 단위는 "서브트리의 모든 element에 대해 다시 만든다"이나, 이를 set-only 루프로 구현하면 patch 후 완전히 clip 밖으로 나간 자손의 **기존 entry가 남아** 빈 영역 클릭이 그 요소를 선택하는 ghost hit이 된다. "재계산 시 자격을 잃은 entry는 삭제한다"를 §4.3.2에 한 줄 추가하면 닫힌다.

**L3** — §4.2.2는 그룹 중 하나라도 거부되면 전체 미적용으로 규정하고, §4.3.1은 `presentationRevision` 역행 patch를 거부한다. 두 규칙이 만나는 지점이 비어 있다: 그룹이 거부됐을 때 이미 검사를 통과한 publication의 revision을 "적용됨"으로 기록하면, 같은 plan의 재시도가 역행으로 오판돼 영구 거부될 수 있다. "거부된 그룹의 revision은 적용 상태로 기록하지 않는다"를 §4.2.2에 명시하면 닫힌다.

두 건 모두 계약 문장 1줄 규모이고 Accepted 승격을 막지 않는다 — Phase 2/3 착수 시 흡수 대상으로 **deferred** 처리한다.
