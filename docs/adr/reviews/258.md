### h1 — HIGH: defaultValue 편집·undo가 Preview 상태에 적용되지 않는다

위치: `docs/adr/258-color-controls-canvas-gradient.md:95` (Decision 1), `docs/adr/design/258-color-controls-canvas-gradient-breakdown.md:56` (ruleDom 경로 유지).

입력·상태 → 결과: 동일 id의 ColorArea/ColorSlider/ColorWheel을 `defaultValue="hsl(0, 100%, 50%)"`로 마운트한 후 `hsl(120, 100%, 50%)`로 바꾸면 Canvas 함수는 새 색을 읽지만 RAC state는 이전 빨강을 유지한다. 같은 방식의 undo도 불일치하며 reload 때만 새 초기값이 들어간다. Preview에서 먼저 끌고 문서 기본값을 바꾸면 끌기 결과가 그대로 남는다.

근거: 설치 `useColorAreaState.mjs:27`, `useColorSliderState.mjs:26`, `useColorWheelState.mjs:56`가 `useControlledState`를 사용하고 `utils/useControlledState.mjs:19`는 최초 값으로 `useState`를 초기화한다. 현재 `runtime/domBinding.tsx:1644`의 Color key는 node.id다. JSDOM + React act로 세 hook 모두 같은 key에서 새 defaultValue 후 `hsla(0, 100%, 50%, 1)` 유지, 새 key 후 `hsla(120, 100%, 50%, 1)` 반영을 재현했다.

해결 방향: 작성 초기값 변경 시 RAC owner subtree를 다시 초기화하는 key/state reset 계약을 명시한다. Preview 자체 끌기와 관계없는 prop 편집에서는 상태를 유지하고, 문서 defaultValue 편집·undo/redo에서는 새 문서 기본값으로 초기화한다. G3에 끌기 후 작성 기본값 변경·undo를 연결한다. `delegatedDom.tsx:1755`의 기존 Slider가 참고 경로다.

### h2 — HIGH: 일반 CSS 색과 편집 중간 문자열이 두 consumer에서 예외를 만든다

위치: `docs/adr/258-color-controls-canvas-gradient.md:95`의 “string — CSS 색”, breakdown `258-color-controls-canvas-gradient-breakdown.md:46`, `:48`.

입력·상태 → 결과: 문서 defaultValue에 유효한 CSS인 `red` 또는 `rgb(255 0 0)`를 넣으면 설치 ColorArea SSR이 각각 `Invalid color value: red`, `Invalid color value: rgb(255 0 0)`를 던진다. `garbage`도 ColorWheel에서 같은 방식으로 던진다. 일반 문자열 필드의 편집·AI/import로 이 값이 commit되면 계획상 shared resolver의 parseColor와 Preview RAC가 모두 그 값을 받는다. 잘못된 값을 저장한 문서의 재열기에서도 반복된다.

근거: 현재 `document/valueType.ts:16`의 string 검사에는 색 파싱이 없다. 계획은 채널 검증만 추가하고, 공용 함수에는 parseColor 사용을 명시한다. 설치 RAC renderToString으로 위 입력들의 예외를 실행 확인했다. RAC가 실제 받는 범위는 [ColorArea 공식 Value 설명](https://react-aria.adobe.com/ColorArea)의 parseColor 기반 값이다.

해결 방향: “설치 parseColor가 받아들이는 색 문자열”로 D2 범위를 한정하거나 지원 CSS 구문을 명시적으로 변환한다. graph/library/default/AI/import 경계에서 같은 파싱 검사를 적용하고 실패는 transaction 전 거부한다. 패널은 입력 중 draft를 유지하고 유효한 값만 commit한다. 빈 값의 의미도 fallback/거부 중 정하고, 실패 시 revision 불변을 확인한다.

### m1 — MEDIUM: 필드별 편집과 조합 거부만으로는 색 공간 전환이 완결되지 않는다

위치: breakdown `258-color-controls-canvas-gradient-breakdown.md:48`, ADR `:137` (G3 실패 대안).

입력·상태 → 결과: 기본 ColorSlider의 `channel=hue` · `defaultValue=hsl(...)`에서 사용자가 rgb/red로 바꾸려 한다. 먼저 colorSpace=rgb를 고르면 hue는 rgb에서 무효, 먼저 channel=red를 고르면 현재 HSL에서 red가 무효다. 조합 검증을 지키면 두 직접 전환이 모두 거부되고, 검증을 생략하면 RAC가 `Unknown color channel: hue/red`를 던진다. alpha 등 임시 채널을 경유하는 우회가 필요하며 “검증기 메시지로 안내”만으로 일반적인 색 공간 선택이 동작하지 않는다. 명시 x/y 축을 가진 ColorArea도 같은 전환 문제를 갖는다.

근거: `CatalogPropertiesPanel.tsx:333`는 `handlePatch({ [key]: value })`로 단일 prop을 쓴다. 설치 ColorSlider SSR에서 (hsl defaultValue + red), (hsl defaultValue + colorSpace rgb + hue)는 예외, (hsl defaultValue + colorSpace rgb + red)는 정상임을 확인했다. 공식 [ColorSlider API](https://react-aria.adobe.com/ColorSlider)의 colorSpace와 channel은 함께 유효한 조합이어야 한다.

해결 방향: colorSpace 변경 시 무효 channel/xChannel/yChannel을 유효한 기본 축으로 바꾸거나 해제하는 하나의 CatalogCommand/transaction을 정한다. 미지정 colorSpace는 parseColor(defaultValue)의 유효 공간으로 검사한다. 저장된 값을 유지할 전환 정책과 undo 단위를 명시한다. 의존 enum 필터를 포기하더라도 원자적 전환은 필요하다.

### m2 — MEDIUM: ColorSlider의 값 출력이 빈 텍스트로 고정된다

위치: breakdown `258-color-controls-canvas-gradient-breakdown.md:55`의 `Label {label} + SliderOutput + SliderTrack > ColorThumb`, `:56`의 기존 DOM 경로 재사용.

### r2-h1 — HIGH: hexa key는 Color 채널 초기값의 identity를 보존하지 않는다

위치: `docs/adr/258-color-controls-canvas-gradient.md:104` (Decision 7의 `canonical = parseColor(v).toString('hexa')` 예시), `docs/adr/design/258-color-controls-canvas-gradient-breakdown.md:64` (같은 key), `docs/adr/258-color-controls-canvas-gradient.md:149` (R10/G3 기본값 편집·undo 재시작).

입력·상태 → 잘못된 결과:

1. ColorWheel/ColorSlider(hue)를 `defaultValue="hsl(0, 0%, 50%)"`로 시작한다. ColorArea는 같은 값에 xChannel=hue, yChannel=saturation을 지정한다.
2. 문서 기본값을 `hsl(120, 0%, 50%)`로 바꾼다. 두 입력 모두 새 racColor의 허용 구문이며 채널이 모두 유한하다. 색 공간과 채널 조합도 유효하므로 정규화가 차단할 입력이 아니다.
3. 두 값의 canonical hexa는 모두 `#808080FF`다. 문서 값은 바뀌지만 React key는 같아 RAC state의 hue가 0에 남는다.
4. Canvas는 새 문서 hue 120에 따라 thumb 위치/색·값 글자를 만들고, Preview는 hue 0의 thumb 위치/색·값 글자를 유지한다. 무채색이어도 Wheel과 hue Slider의 display thumb는 saturation=100, lightness=50으로 표시하므로 빨강/초록 차이가 눈에 보인다. ColorArea도 hue 축의 thumb 위치가 다르다. 저장 후 새 mount에서는 120이 되어 다시 불일치한다.

실행 근거: 설치 RAC가 사용하는 react-stately 3.50.0의 세 hook을 JSDOM + React act로, 문서에 적힌 hexa key를 가진 동일 컴포넌트에 마운트했다. 모두 편집 전/후 key=`node:#808080FF`, 편집 후 hue=0(기대 120)을 재현했다. Wheel/Slider의 display thumb는 `hsla(0, 100%, 50%, 1)`에 남았다. `useColorWheelState.mjs:98`은 원래 hue로 위치를 계산하고 `:121-122`는 표시색에 hue를 유지한다. 원래 HSL hue는 RGB 변환으로 복원할 수 없다.

반증 대조: key를 색 공간 + 원래 채널 전체 + alpha의 수치 tuple로 만들면 `["hsl",0,0,50,1]` → `["hsl",120,0,50,1]`로 달라져 Wheel이 hue 120과 초록 display thumb로 재시작한다. 파일 없는 실행 프로브이며 제품 수정은 아니다.

해결 방향: canonical은 **RGBA의 눈에 보이는 색뿐 아니라 RAC가 소비하는 원래 색 공간·모든 채널·alpha와 정밀도를 보존**해야 한다. 예를 들면 parse된 getColorSpace/getColorChannels/getChannelValue의 tuple을 key로 쓰고, 다른 표기의 같은 채널 tuple만 합친다. hexa 변환과 색 문자열 출력의 반올림으로 동등성을 판정하지 않는다. 원래 채널 값을 RGB로 변환해 버리는 방식도 두 consumer에서 hue 위치 의미를 잃으므로 해결이 아니다. G3에 무채색 hue 기본값 변경/undo를 포함한다.

### r2-l1 — LOW deferred: AI의 실제 호출은 구현 gate로 남긴다

사용자가 지목한 AI 경로를 현재 코드에서 추적했다.

- `CatalogBuilderCore.tsx:476`가 `createCatalogAiWriteHost(workspace)`를 등록한다.
- AI 수정: `services/ai/tools/updateElement.ts:118`의 host.update → `catalogRuntime/aiHost.ts:602`의 writeCommands → `:357`의 **catalogSemanticPatchCommand** → `editContract.ts:170`의 setFields.
- AI 생성: `aiHost.ts:540`의 insertNodes에 `catalogCreationProps(..., props)`를 넣는다. 수정용 writeCommands에는 style/fills만 전달하므로 생성 props는 이 경로도 별도로 점검해야 한다.
- 패널: `editContract.ts:233`의 **catalogPropertiesPatchCommand** → catalogSemanticPatchCommand → setFields. AI는 이 패널 wrapper를 통과하지 않는다.

따라서 패널 wrapper에만 정규화를 넣으면 AI에 닿지 않는다. 다만 Decision 8은 “패널과 AI가 같이 호출”을 명시하고 Phase 0/1도 경로 전수와 두 caller의 배선을 요구한다. 현재 racColor/isRacColorString/normalizeColorControlPatch는 **문서에만 있고 제품 구현이 없다**. 이 상황에서 AI 호출 부재를 새 HIGH로 간주하거나 기존 코드에 없는 신규 prop으로 production 결함을 만든다고 주장하지 않는다.

구현 시점에 AI update/create 각각의 실제 host 호출과 한 transaction의 결과/undo, AI compiler manifest의 새 색 kind 판정까지 확인할 항목으로 남긴다. 실제 호출·거부·revision 무결성은 **UNVERIFIED**, 이 항목은 round 재개 사유가 아니다.

### 수정분의 나머지 판정

- Decision 1/R9: 설치 parseColor가 받는 색만 허용, draft/transaction 전 거부, 양 consumer 동일 fallback으로 round 1 h2의 일반 string 수리 방향은 반영되어 있다. 새 predicate와 문서 경계 구현은 없으므로 통과를 증명한 것으로 읽지 않는다.
- Decision 8: 공간 밖 채널은 colorSpace 동반 변경, 공간 변경은 채널/축 동반 정리, setFields 한 step으로 기존 m1의 중간 무효 조합을 없애는 설계다. 원자적 결과를 실제 RAC에 주면 정상적인 조합이며, 배선 검증과 설계 판정을 구분한다.
- Decision 9/R11/G1·G3: 소유자별 label/output 포맷, DOM children 생략, ColorSlider dependent/owners 확장이 명시되어 round 1 m2의 누락을 다룬다. 이 수정분의 별도 merge blocker는 발견하지 않았다.
- 사용자 우려인 “다른 prop 편집 중의 끌기 상태”: 설치 ColorSlider hook에서 setValue로 실행값을 hue 120으로 바꾼 뒤 orientation·label·isDisabled를 편집하고, channel=red/colorSpace=rgb 및 hue/hsl로 전환했다. 문서 defaultValue만으로 만든 같은 key에서는 실행값이 유지되고 색 공간 전환만 적용됐다(초록 유지). 이어 다른 defaultValue(hue 240) key를 주면 재시작했다. **hook 실행값 유지에 추가 반례 없음**이며 실제 pointer capture/진행 중 drag interaction까지 검증했다는 뜻은 아니다.
- round 1의 h1 수리 방향인 기본값 key 자체는 타당하지만 새 hexa canonical 예시에는 위 HIGH가 남는다. round 1의 historical body와 실행자가 fixed로 기록한 상태는 보존하고, 수리 중 새로 발견한 결함을 이번 round의 r2-h1로 기록한다.
