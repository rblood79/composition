# ADR-269 Review Log

## Round 1 — 2026-10-17 (reviewer: codex)

판정: **설계 보완 필요 — HIGH 2건 open, closed 0건**. 현재 제품 결함을 새로 선언하는 것이 아니라, Proposed 설계의 변경을 현재 소비 경로에 적용했을 때 발생하는 반례다. 제품 코드와 ADR 상태는 변경하지 않았다.

### H1 — 종료 명령에 남은 상태까지 property 계약에 포함해야 한다 (open)

- 설계 위치: `docs/adr/design/269-render-command-property-node-separation-breakdown.md:70`, `:88`. Phase 1·2는 BEGIN의 scroll·clip 필드 제거와 테이블 조회를 지정하지만 END의 대응 변경은 지정하지 않는다.
- 현재 경로: `renderCommands.ts:1849-1859`의 `CHILDREN_END`에 `hasScrollOffset`, `hasClip`, `scrollbar`, `scrollbarNode`가 별도로 기록된다. 실행기 `:2919-2940`은 이 값으로 restore하고 scrollbar를 그린다. `canvasBinding.ts:1462-1472`의 재등록이 현재 scrollbar와 scrollOffset을 함께 갱신한다.
- 입력 → 잘못된 결과: 최초 offset 0에서 150으로 스크롤하면서 BEGIN만 새 값을 읽으면 END는 false를 유지해 save 하나가 남는다. 150→0에서는 restore가 하나 초과한다. visible→clip도 같은 불균형이 생긴다. 명령과 등록 노드를 유지한 채 offset만 바꾸면 thumbY는 0에 남고 cold rebuild는 50이다 (높이 100, 내용 300, offset 150).
- 실행 근거: 실제 builder/executor로 만든 스트림에서 BEGIN의 읽는 값만 바꿔 제안된 분리를 모사했다. `save−restore`는 각각 +1, −1, +1이며 같은 최종 상태의 full build는 모두 0이다. END의 scrollbar snapshot도 0 대 50으로 다르다. 이는 table 구현 자체를 실행한 증거는 아니다.
- 해결 방향: BEGIN에서 실제로 연 clip·scroll 프레임을 END가 동일한 런타임 스택으로 닫거나, 양쪽 모두 동일한 property 상태를 읽도록 규정한다. END의 baked flags를 제거하고 scrollbar geometry도 최신 offset/range에서 파생한다. clip off/on, scroll 0↔nonzero, 중첩 및 형제 뒤 그리기와 scrollbar를 G1에 명시한다.

### H2 — 테이블 변경을 scene.sync의 변경 판정과 content invalidation까지 전달해야 한다 (open)

- 설계 위치: `docs/adr/design/269-render-command-property-node-separation-breakdown.md:31`, `:71`. `scrollBy`는 테이블·맵·damage를 바꾸고 dirty seed로 보내지 않도록 정하지만, `canvasScene.ts`와 Canvas 소비자의 변경은 inventory에 없다.
- 현재 경로: `canvasScene.ts:138-145`는 `update.rebound.length || update.patchRoots.length`만 변경 판정에 사용한다. `CatalogCanvas.tsx:799-804`는 `unchanged`이면 `renderer.invalidateContent`, overlayVersion, cellsVersion을 건너뛴다. 휠 경로 `:914-918`의 scheduler.invalidate만으로는 content surface가 dirty가 되지 않는다 (`SkiaRenderer.ts:361`).
- 입력 → 잘못된 결과: 문서 편집 없이 요소를 휠 스크롤해 테이블과 자손 맵을 변경하되 subtree patch를 만들지 않는다. `damage`와 `translated`를 채워도 `rebound=[]`, `patchRoots=[]`이면 sync는 unchanged다. 히트 맵은 이동했는데 화면은 직전 cached content를 유지하고 overlay 버전도 그대로다.
- 실행 근거: 실제 `CatalogCanvasScene.prototype.sync`에 property-only update를 넣으면 damage·translated가 있어도 unchanged다. 같은 update에 patchRoots만 추가하면 patched다. 이후 invalidate 분기의 미실행은 현재 caller의 정적 소비 추적으로 확인했다. 실제 Builder 휠 픽셀 재현은 미실행이다.
- 해결 방향: pending property 변경·damage·revision을 다음 sync에서 함께 발행하고 소비하는 계약을 추가한다. 명령 쓰기 0이어도 patched/별도 변경 kind로 content와 overlay가 무효화되어야 한다. 여러 wheel 합산, 다음 sync에서 1회 소비, 문서 dirty와 동시 변경의 damage 병합, full 우선순위도 정의한다. 기존 offsets의 재바인드 보존도 유지한다.
