# ADR-319 Review Log

## Round 1 — 2026-11-26 (reviewer: codex)

**설계 승인 보류.** HIGH 3건, MEDIUM 3건. 대안 A의 목표와 ADR-318에서 분리한 범위는 타당하다.

1. **H1 · G2 줄 높이 상속.** 줄 높이를 지정하지 않은 100px 폭 Text에서 부모 Frame의 lineHeight를 `previewRecord`로 1.5에서 3으로 바꿨다. 자식 record는 같은 객체였고 현재 엔진의 wrapHeight는 72 → 144px, wrapBaseline은 9 → 18px였다. record 단독 메모는 이전 leaf의 폰트와 측정 키를 사용한다. 실제 상속값을 키에 포함하거나 record 고유 입력만 메모한다. 부모 미리보기와 원복을 G2에 포함한다. 근거는 `compositionRoot.ts:1486`, `:6934`, `:7479`, breakdown:44.
2. **H2 · G1 칠 비교.** 같은 Frame의 배경만 바꾼 뒤 Skia fillColor는 빨강 [1,0,0,1]에서 파랑 [0,0,1,1]으로 변했지만 기존 서명은 완전히 같았다. `canvasPageSplice.test.ts:77`은 명령의 종류와 기하를 기록한다. `canvasScene.ts:269`, `:345`의 rebuild도 같은 root를 쓰므로 root 수명 메모는 두 경로가 공유한다. G1은 메모를 우회한 독립 경로와 실제 칠 값(또는 픽셀)을 비교해야 한다. 정상 메모를 껐을 때 그림 비교는 GREEN, 무효화 입력을 누락해 낡은 색을 만들면 RED, 정상 메모를 끄면 호출 수 상한이 RED가 되도록 조건을 구분한다. G2의 수정 전 기하 스냅샷에도 같은 구분이 필요하다. 본문:136–137, breakdown:29–37.
3. **H3 · G0/G3 끌기 유효성.** 저장된 production harness dist와 원래 zigzag로 빈 Panel을 headed Chrome에서 연속 세 번 끌었다. 첫 회는 x=600에서 손잡이를 잡아 50 → 45, 다음 두 회는 손잡이 중심이 x=540.05인데 시작점은 계속 600이어서 hit=false, 45 → 45였다. 현재 집계는 이 두 회도 포함한다. 기존 1,000개 별도 로그에서도 Publish 끝값이 45/45/45였다. 각 표본의 초기 비율을 복원하고 손잡이 좌표를 다시 구한다. Canvas와 Publish 모두 실제 크기 변화와 복원을 검증한 표본만 집계한다. G0에서 유효한 기준선을 다시 확보한다. `adr318-heavy-panel-frame.mjs:255`, `:343`, `:388`, `:418`.
4. **M1 · G2/G3 측정 캐시.** fixture는 모든 노드에 같은 문장을 넣는다. 실제 workspace 측정 캐시에 동일 폰트로 폭 450px와 456px를 넣은 결과, 폭당 1,000개 요청에서 측정 원천은 같은 문장일 때 총 2회, 서로 다른 문장이면 2,000회 호출됐다. 폭이 바뀔 때 모든 노드가 원천 측정을 한다는 F4 해석과 잔여 비용 추정은 이 자료로 확인할 수 없다. 같은 문장 fixture를 유지하고 서로 다른 문장 fixture에서 원천 호출과 키 직렬화를 분리해 A/B를 비교한다. `adr318-heavy-panel-frame.mjs:216`, `textMeasureCache.ts:13`, `workspace.ts:225`, 본문:53, 67, 140.
5. **M2 · G2 묶음 조회량.** 한 Frame 안에 부모 폭을 따르는 virtual GridList가 여럿 있으면 각 격자가 중간 computeLayout을 실행할 수 있다. 실제 GridList 계산에서 폭 600 → 620px에 두 열이 각 282 → 292px로 변했다. 이때 남은 후보 전부를 매번 다시 읽으면 격자 K개만 세어도 K(K+1)/2개의 rect를 요청한다. 격자 100개면 기존 100개가 5,050개가 된다. 격자에서 배치를 끊어 소비할 구간만 읽고, WASM 호출 횟수와 함께 요청한 handle 총합을 검증한다. 이 값은 설계의 조회량 계산이며 wall-clock 측정은 하지 않았다. `compositionRoot.ts:6890–6906`, `persistentLayoutTree.ts:434`, breakdown:42.
6. **M3 · G3 판정표.** 1,000개·4x에서 p95 20.9ms, p99 40ms, LoAF 1을 대입하면 기존 p99 60.3ms·LoAF 299보다 개선되고 p95 21.7ms도 통과한다. 다른 조건이 통과하면 G3는 닫히지만 hard constraint의 LoAF 0은 미달이고 사용자 결정 1도 열리지 않는다. 절대 기준 미달을 p95 초과 또는 LoAF 잔존으로 명시하고 기술 통과와 사용자 수용 여부를 따로 기록한다. 본문:61, 119, 138.

**확인 범위.** 기존 canvasPageSplice·textMeasureCache와 임시 반증 프로브를 합쳐 Vitest 10/10 통과. 기존 production 결과 텍스트와 dev CPU 프로파일의 인용 수치를 대조했다. 보관된 `dist-heavy/perf-build.json`의 빌드 HEAD는 `8143ccbe8`이었고 본문이 명시한 `ddb1d307e`와 달랐다. G0에서 각 결과에 실제 dist 식별자와 변경 내역을 연결해야 한다. 기존 모든 수치와 동일 빌드의 대응, 300/1,000개 4x 재측정, 개선 후 A/B, 번들 및 힙 변화는 UNVERIFIED.

## Round 2 — 2026-11-26 (reviewer: codex)

**기존 여섯 지적은 해소됐다. 추가된 측정 문단 재사용은 승인 보류다.** Round 1의 정합·측정 설계를 다시 확인했고, Round 2에는 이후 확장한 Decision 3의 HIGH 2건과 MEDIUM 1건을 기록한다.

### Round 1 수리 확인

- H1·H2. leaf 키에 실제 상속 줄 높이가 들어갔고 부모 미리보기와 원복이 G2에 포함됐다. G1은 칠 메모를 우회한 전체 `SkiaNodeData`와 비교한다. 색이 잘못된 경우와 메모를 꺼서 호출 수가 늘어난 경우를 각각 검출하도록 명시했다. [breakdown §3 Phase 0–2](../design/319-canvas-resize-preview-paint-reuse-rewrap-batching-breakdown.md)
- H3. 하니스가 매 실행마다 초기 크기와 손잡이 좌표를 확인하고, 움직인 표본 세 개만 집계한다. 보관된 production dist `63da87971`의 빈 Panel·1x 셀을 headed Chrome에서 다시 실행해 Canvas 기본→43.4 세 번, Publish 50→45 세 번, 페이지 오류 0을 확인했다. `adr318-heavy-panel-frame.mjs:389,447,480`. Status 인용문 중 “Publish 다시 열기”는 실제로 손잡이 키로 초기 비율을 복원하는 동작을 가리킨다.
- M1·M2·M3. 서로 다른 문장 1,000개의 production 원본 로그에서 4x p95 360.7ms와 유효 표본 세 개를 확인했다. 측정 키 직렬화와 원천 호출은 별도 카운트로 정의했다. G2는 중간 레이아웃 전 구간만 조회하고 총 요청 handle을 검사한다. G4는 p95 충족 뒤에도 LoAF가 남으면 사용자 결정으로 보낸다. [ADR Gates G0·G2·G4](../319-canvas-resize-preview-paint-reuse-rewrap-batching.md)

### 새로 확인한 문제

1. **H4 · 편집 중 문단 수가 입력 횟수만큼 늘어난다.** 인라인 텍스트 편집도 매 입력마다 `previewRecord`를 호출한다(`CatalogTextEditor.tsx:253,469,555`). 단일 Text에서 편집을 닫지 않고 512회 입력한 root 프로브에서 실제 측정 원천에 서로 다른 `[text,font,runs]` 키 512개가 도달했다. 별도 CanvasKit 0.42 프로브로 ADR의 Map에 한 글자씩 늘어나는 초안 1,536개를 넣으니 문단 1,536개가 동시에 남았고 WASM 선형 메모리 용량은 128 → 153.625MiB로 성장했다. 즉시 해제 대조군은 128MiB였다. 이 값은 할당 용량이며 개별 문단 크기의 합은 측정하지 않았다. **수정 방향**은 폭 변경 제스처에서만 보유를 시작하거나 내용·서체가 바뀌면 해당 leaf의 이전 문단을 해제하는 것이다. G3에 종료 전 최대 보유 개수도 둔다. [breakdown Phase 3](../design/319-canvas-resize-preview-paint-reuse-rewrap-batching-breakdown.md)
2. **H5 · 드래그 도중 화면 이탈이 네 종료 조건에서 빠진다.** 위 production dist에서 Text 하나를 가진 Panel의 손잡이를 누른 채 브라우저 뒤로가기로 대시보드에 이동했다. 관찰한 호출은 `preview → preview → preview → workspace.dispose`였고 patch 없는 종료 호출은 0회였다. Canvas cleanup은 pointer 리스너를 해제하고 renderer를 폐기한다(`CatalogCanvas.tsx:2024,2062`, `workspace.ts:1348`). `scheduleWasmDisposal`은 큐에 넣기만 하고 실제 delete는 drain에서 수행한다(`deferredDisposal.ts:32,37`). **수정 방향**은 Canvas teardown·workspace dispose에서 보유 주체를 멱등적으로 닫고 안전한 프레임 밖 drain까지 보장하는 것이다. G3은 다음 프레임이 없는 라우트 이탈에서 소유 개수·미처리 폐기 건수·실제 해제를 확인해야 한다. 여기서 관측한 것은 제품의 종료 경로다. 제안된 문단 보유 코드는 아직 구현 전이다.
3. **M4 · G3의 폭 키 원복 조건이 모호하다.** Decision 3과 breakdown은 문단 키에서 폭을 제외한다. G3 표는 “폭을 키에 넣지 않으면” 결과가 달라져야 한다고만 써서 어느 캐시에 적용되는지 구분할 수 없다. 실제 CanvasKit 0.42와 Pretendard로 한·영 혼합 문단 하나를 95 → 400 → 95px에서 반복 layout하니 7 → 2 → 7줄, 높이 133 → 38 → 133px였다. 새 문단 대조군과 세 폭의 높이·줄 수·첫 baseline·intrinsic 폭이 일치했다. **수정 방향**은 문단 키에서 폭을 빼고 재배치한 결과는 GREEN, 재배치 생략이나 수치 결과 캐시에서 폭을 뺀 경우는 RED로 명시하는 것이다. 측정 결과 캐시의 현재 키는 `textMeasureCache.ts:13`이다. [G3](../319-canvas-resize-preview-paint-reuse-rewrap-batching.md)

**검증 범위.** 실제 root 입력 프로브와 기존 측정 캐시·지연 폐기 테스트를 합쳐 Vitest 11/11 통과. Chrome에서 H3 수리와 H5 종료 호출을 확인했다. 300/1,000개 결과와 프로파일은 보관된 원본을 대조했다. 17,522ms는 `paragraphMetrics` 전체의 포함 시간이며 shaping만의 비율은 G0 시제품에서 분리해야 한다. RichText·chip을 포함한 전체 G0, 구현 후 A/B·힙·번들 및 G1–G4 통과는 UNVERIFIED다.

- **H5.** Canvas cleanup에서 진행 중인 제스처를 취소하고 workspace 폐기에서도 같은 보유분을 멱등적으로 정리한다. 현재 `textMeasure.ts:234–244`는 수치와 클러스터를 반환하고 측정 문단을 직접 삭제한다. 개정 설계는 보유 문단이 측정 모듈 밖으로 나가지 않도록 검사한다. 이 조건에서는 즉시 삭제가 가능하다. 끌기 중 뒤로가기를 포함해 다음 프레임 없이 보유 0과 생성 수 = 삭제 수를 확인하는 G3 조건이 기존 이탈 사례를 덮는다. - **M4.** CanvasKit 0.42·Pretendard와 현재 수치 측정 캐시를 사용해 같은 한·영 문단을 95 → 400 → 95px로 측정했다. 정상 경로는 7 → 2 → 7줄, 높이 133 → 38 → 133px로 폭마다 새로 만든 문단과 일치했다. 재배치를 생략한 변형과 수치 캐시의 키에서 폭을 뺀 변형은 각각 7 → 7 → 7줄이어서 둘 다 넓은 폭에서 검출됐다. [G3](../319-canvas-resize-preview-paint-reuse-rewrap-batching.md)
