### H1 — contract 45 증가 뒤에는 기존 문서의 무변경 로드가 불가능하다 (open)

- 위치: `docs/adr/completed/278-overlay-body-slot-local-component.md:57`, `:95`, `:107`, `:143`; `docs/adr/design/278-overlay-body-slot-breakdown.md:45-46`.
- 입력·상태 → 잘못된 결과: 현재 contract 44로 저장된 프로젝트를 contract 45 빌드에서 연다 → slot의 기본 내용 해석 전에 `CatalogStorage.load`가 `UNSUPPORTED_PROJECT_FORMAT`을 던진다. 따라서 G1의 “옛 문서 로드 = 변화 0”, breakdown의 “로드 전후 resolved record 동일”은 성립하지 않는다. 오버레이 보유 여부와 관계없이 모든 44 문서가 해당한다.
- 코드 근거: `packages/shared/src/catalog/document/types.ts:123`은 현재 44다. `packages/shared/src/catalog/runtime/storage.ts:297-300`은 프로젝트 목록의 supported를 버전 동등 비교로 정하고, `:369-374`는 로드 자체를 거부한다. JSON 문서도 `packages/shared/src/catalog/document/validation.ts:1505-1506`에서 `UNSUPPORTED_LIBRARY_CONTRACT`로 거부한다.
- 원인: “새로 해석할 때 fillSlot이 없으면 기본 채움”과 “옛 버전 문서를 새 빌드가 허용”을 같은 사실로 취급했다. 구조 변경 계약 Step 3(`.claude/skills/composition-patterns/rules/domain-structure-change-audit.md`)과 ADR-277은 버전 증가 뒤 옛 개발용 프로젝트 거부·재생성, 자동 변환 없음으로 정한다.
- 해결 방향: 기존 정책대로 contract 증가와 변환 코드 0을 유지하되, Decision 2·위험·G1을 “44 문서 거부 및 재생성 안내 / 45로 새로 생성한 미채움 instance는 기본 내용 / 새 slot fill 저장·재열기 보존”으로 고친다. fixture의 버전을 45로 바꾼 비교는 옛 문서 호환성 증거로 쓰지 않는다.
- 상태: **fixed (실행자, 2026-10-21 같은 날)** — Decision 2 · Risk Threshold 마이그레이션 · R6 · G1 · Consequences 를 「44 거부 · 재생성, 변환 0, 45 새 fill 보존」 으로 고침. breakdown Phase 1 옛 문서 항목 → 거부 테스트 (i)(ii)(iii).

### H2 — Menu의 기존 slot picker에는 Local 컴포넌트 후보가 없다 (open)

- 위치: `docs/adr/completed/278-overlay-body-slot-local-component.md:103`, `:108`, `:145`; `docs/adr/design/278-overlay-body-slot-breakdown.md:44`, `:68`.
- 입력·상태 → 잘못된 결과: MenuItem을 루트로 하는 Local 컴포넌트를 만들고, 제안대로 Menu 내부 노드에 Items slot을 선언한 뒤 그 slot의 Fill slot 목록을 연다 → Local 컴포넌트가 후보에 없어서 G3의 “Items에 Local 항목 컴포넌트 넣기”를 해당 UI에서 수행할 수 없다. slot 선언 추가만으로 달라지지 않는 분기다.
- 코드 근거: `packages/shared/src/domain/componentTraits.ts:269-280`과 `packages/shared/src/catalog/nesting/nestingRules.ts:115-120`에서 Menu는 `items` 종류다. `apps/builder/src/builder/catalogRuntime/slots.ts:291-303`의 items 분기는 `catalogPaletteDefinitionId`를 통해 Library 정의만 후보로 만든다. `:335-353`의 `project.definitionIds` 순회는 free-content인 else 분기 안에만 있다. `CatalogSlotSection.tsx`는 이 후보 목록을 그대로 표시·선택한다. 기본 MenuItem 삽입이나 직접 fill 명령의 성공은 Local 컴포넌트 picker 성공을 증명하지 않는다.
- 원인: Dialog의 자유 내용 slot에서 가능한 Local 후보 노출을 Menu의 collection slot에도 일반화했다. ADR-261 Status에서도 “항목만 받는 slot의 project 추천 미노출”은 deferred로 남아 있다. ADR-278은 이를 핵심 사용자 흐름으로 요구하므로 이 범위에서는 구현 항목이 필요하다.
- 해결 방향: Phase 1에 `catalogSlotInsertOptions`의 collection 후보 확장을 명시한다. Local 정의의 해석된 루트 타입으로 기존 `assertNestable` 판정을 통과하는 것만 제공하고, MenuItem 루트 Local 컴포넌트는 노출·삽입되며 frame/Button 루트는 제외되는 실제 선택→명령→Preview 경로로 G1·G3을 확인한다. Layers drop만 지원하려는 결정이라면 Decision 3과 G3의 조작 경로를 그에 맞춰 명시해야 한다.
- 상태: **fixed (실행자, 2026-10-21 같은 날)** — Decision 3 · R7 · G1 · G3 에 `slots.ts` `items` 분기의 project 정의 후보 추가 (거름은 기존 `allowed` 의 `assertNestable` — `definitionTypeName` 이 Local 루트 type) 를 Phase 1 구현 항목으로 명시. breakdown Phase 1 항목 · Phase 3 live 5 단계 (MenuItem 루트 노출 · frame 루트 제외) · 추정 규모 +1 파일.
