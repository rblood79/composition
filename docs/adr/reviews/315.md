## Round 1 — 2026-11-19 (reviewer: codex)

판정: **설계 수정 필요 — HIGH 3, LOW deferred 1, pending 3**.

대상은 main `23b1c802b` 위의 미커밋 ADR 본문과 breakdown이다. 제품 구현 판독이 아니라 설계 판독이며, 제품 코드·ADR 본문·Status·README는 수정하지 않았다. 새 기능이 아직 없다는 사실 자체는 결함으로 세지 않았다.

### H1 — suffix 서버에서 두 번째 정렬을 버리면 페이지의 행 집합부터 달라진다

- 위치: `docs/adr/design/315-table-data-grid-state-model-breakdown.md:122`, 본문 `:197` (R2). 본문 HC2 `:82`와 G2 `:214`는 로컬·서버의 같은 결과를 요구한다.
- 입력: 서버 원본 `[s1(team=A, score=1), s2(A,2), s3(A,9)]`, 페이지 크기 2, 요청 정렬 `team ASC, score DESC`.
- 결과: 설계대로 첫 정렬만 보내면 `_sort=team&_order=asc&_page=1&_limit=2`가 되어 `[s1,s2]`를 받는다. 정답은 `[s3,s2]`다. 받은 페이지를 재정렬해도 `[s2,s1]`일 뿐 s3를 복원하지 못한다. 경고 표시는 잘못된 정렬의 실행을 막지 않는다.
- 현재 경로: `packages/shared/src/collections/view/serialize.ts:419`는 정렬 뒤 페이지 파라미터를 보낸다. `packages/shared/src/catalog/runtime/dataBinding.ts:225`는 served 응답을 결과로 취급하고 다시 필터링하지 않는다. `catalogPreviewSession.ts:1990`의 서버 정렬 경로도 서버 순서를 유지한다.
- 확인: probe에서 실제 serializer가 위 요청을 만들고, 현재 stable sorter로 서버의 합법적인 응답을 모사해 행 누락을 확인했다. 실제 네트워크 호출은 하지 않았다. 새 다중 정렬 구현의 버그를 주장하는 것이 아니라 문서가 명시한 축약 규칙의 반례다.
- 수정 방향: endpoint가 전체 정렬 목록을 담을 수 있을 때만 다중 정렬을 실행한다. 미지원이면 두 번째 정렬 추가를 거부하고 상태도 단일 정렬로 유지하거나, 별도 승인된 전체 원본 로드 정책을 사용한다. 일부만 보내면서 전체 정렬이 적용된 상태를 유지하지 않는다.

### H2 — 숨긴 열을 검색에서 제외하는 규칙은 열 변경의 재조회 0회 계약과 충돌한다

- 위치: `docs/adr/design/315-table-data-grid-state-model-breakdown.md:132`, 같은 문서 `:119`, `:143`; 본문 HC4 `:84`, G1 `:213`.
- 입력: 원격 body 조회, 검색어 `needle`, 검색 열 `name,note`, 페이지 크기 2. 원본은 `r1(apple,needle)`, `r2(pear,needle)`, `r3(needle,plain)`, `r4(banana,needle)`이다. 첫 응답은 `[r1,r2]`. 이제 note 열을 숨긴다.
- 결과: 새 조건은 name만 검색하므로 전체 정답은 `[r3]`다. 열 투영만 바꾸면 `[r1,r2]`가 남고, 이미 받은 두 행만 다시 필터링하면 빈 결과가 된다. 서버 요청의 fields 자체가 바뀌므로 행 source를 다시 읽지 않는 규칙으로는 올바른 새 페이지·total을 얻지 못한다. 로컬에서도 검색 결과 캐시 무효화가 필요하다.
- 현재 경로: 실제 `runViewQueries`로 전환 전·후를 계산하고, `serializeViewQueries`로 body의 `where.items[0].fields`가 달라짐을 확인했다. `dataBinding.ts:225`의 served 경로는 이전 응답을 조건 변경 후의 결과로 만들 수 없다.
- 수정 방향: 검색 대상은 가시성과 독립된 `Searchable`로 고정하거나, 활성 검색 중 가시성 변경을 데이터 조각 변경으로 분류하여 query key 갱신·page/cursor 초기화·재조회·후보 값 무효화를 수행한다. 후자를 택하면 HC4/G1의 source 호출 0 조건은 검색 조건을 바꾸지 않는 열 조작으로 한정한다.
- 참고: 「TanStack 기본과 같음」이라는 근거도 정정이 필요하다. 공식 [global filtering guide](https://tanstack.com/table/latest/docs/framework/react/guide/global-filtering)는 필터 참여 여부를 `enableGlobalFilter` 등으로 제어한다. [getCanGlobalFilter 계약](https://tanstack.com/table/latest/docs/reference/static-functions/functions/column_getCanGlobalFilter)에는 가시성 제외가 기본 조건으로 없다. 검색 범위를 가시성과 연결하는 것은 이 ADR의 별도 정책이다.

### H3 — 서버 aggregate 응답에는 펼칠 원본 행이 없다

- 위치: `docs/adr/design/315-table-data-grid-state-model-breakdown.md:123`, `:179`; 본문 Decision 3 `:158`, Decision 6 `:161`.
- 입력: body endpoint에 team으로 묶고 count/sum을 요청한 Table에서 묶음 행을 펼친다. 원본 A=`[a1(A,10),a2(A,20)]`와 원본 B=`[b1(A,5),b2(A,25)]`는 모두 `{team:A,count:2,total:30}`을 응답한다.
- 결과: 같은 서버 집계 응답에서 어느 원본 key·값을 자식 Row로 그려야 하는지 결정할 수 없다. 로컬 평가기를 확장해서 원본과 묶음 행을 함께 내더라도 서버에서 원본을 받지 않았다면 복구되지 않는다. 현재 문서의 `body: group` 및 「원시 행 응답 모드와 섞지 않는다」만으로는 서버 Table의 펼침을 구현할 수 없다.
- 현재 경로: `packages/shared/src/collections/view/evaluate.ts:538`의 grouped 결과는 집계 필드만 남긴다. `serialize.ts:388`은 body.group을 보내며, `catalogPreviewSession.ts:1354`는 aggregate 모드로 분기한다. `dataBinding.ts:291`은 응답을 결과 schema의 행으로 소비한다. ADR-291 Decision 5·6도 집계 결과에서 원본을 복구할 수 없음을 명시한다.
- 확인: 두 원본을 현재 평가기로 실행해 같은 집계 결과와 원본 id 없는 schema를 확인했고, 실제 serializer의 group 요청에는 `load: all`이 없음을 단언했다. 이것은 기존 집계 동작의 결함이 아니라 그 응답을 그대로 확장 가능한 Table에 사용하려는 설계의 정보 손실이다.
- 수정 방향: 표 안 묶기에 필요한 원본 행을 상한 내 전량 로드해 로컬 실행하거나, 서버에 group key별 자식 조회/계층 응답 계약을 추가한다. 지원하지 않는 endpoint에서는 펼칠 수 없는 합계 표시로 제한한다고 명시한다. 선택한 방식에 query unit·group key·페이지 기준을 연결한다.
