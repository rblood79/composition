# ADR-283 Review Log

## Round 1 — 2026-10-25 (reviewer: codex)

판정: **설계 수정 필요 — HIGH 4건, pending 4건.** HEAD `f480895f9` 및 현재 dirty worktree의 코드를 기준으로 ADR·breakdown을 대조했다. 세 모양의 참조를 도입하는 방향은 가능하지만, 아래 실행 문맥·참조 생명주기 계약이 현재 결정과 충돌한다.

### H1 — 같은 행의 형제 대상도 instancePath 전체 일치 조건을 만족하지 않는다

- 대상: `docs/adr/283-interaction-capability-target-ref-picker.md:89`, `docs/adr/design/283-interaction-capability-target-ref-picker-breakdown.md:65`.
- 입력 → 잘못된 결과: 소유 GridListItem 행 template에 Delete Button과 형제 Text를 두고 3행으로 바인딩한다. 행 2의 Delete 규칙이 같은 행 Text를 대상으로 할 때, 제안된 `nodeId` 다중 record 분기의 `instancePath` 전체 일치가 후보를 전부 탈락시킨다. 첫 행을 바꾸는 결함을 no-op으로 바꾸게 된다.
- 코드 근거: `packages/shared/src/catalog/resolution/resolver.ts:1427-1439`는 소유 자식을 방문할 때 각 자식 ID를 instancePath에 더한다. 실행 Button의 경로는 `[list,row,delete]`, 대상 Text는 `[list,row,target]`다. 가장 가까운 행 record가 같아도 두 경로는 다르다. R5·breakdown §1b가 행 조상 helper를 추가하는 것만으로 이 조건은 고쳐지지 않는다.
- 실행 근거: 실제 code library·유효 CatalogGraph·현재 resolver로 3행을 투영했다. 행 2 Button과 Text의 행 조상은 동일하지만, 명시된 `동일 instancePath && 동일 행 record` 조건의 결과는 **0개**다.
- 해결 방향: source 자체까지 포함한 전체 path 일치 대신 대상의 lexical instance 문맥과 행 record의 identity를 분리해 판정한다. `address`도 `recordsOfOwner`의 suffix 비교만으로 반복 행을 구분할 수 없으므로, 세 ref 형식 모두 실행 행 문맥을 처리하게 한다. G1에 소유 행 template의 **서로 다른 형제 sourceId**를 대상으로 하는 입력을 고정한다. record 1개일 때만 허용하는 fallback은 요청한 같은 행 동작을 구현하지 못한다.

### H2 — root와 leaf만 색인하면 중간 instance/template 변경의 참조자를 찾지 못한다

- 대상: `docs/adr/283-interaction-capability-target-ref-picker.md:90`, `docs/adr/design/283-interaction-capability-target-ref-picker-breakdown.md:21`.
- 입력 → 잘못된 결과: 규칙 대상이 `address.instances=[outer,nested]`, `templatePath=[nestedRoot,target]`인 상태에서 nested instance를 swap하거나 중간 template 노드를 컴포넌트로 추출한다. 제안 색인은 outer와 target만 기록하므로 nested 또는 중간 노드의 referrers에 이 규칙이 없다. 명령의 대상 remap이 실행되지 않아 옛 주소가 남는다.
- 코드 근거: `packages/shared/src/catalog/commands/swap.ts:491-498`는 `reader.referrersOf(input.id)`로 holder를 찾고, `commands/components.ts:210-227`의 주소 추출 재작성도 `referrersOf(extracted)`에 의존한다. 기존 `document/graph.ts:112-117`은 이를 위해 instances·templatePath의 **모든 project ID**를 색인한다. 새 대상만 root·leaf로 줄이는 것은 같은 helper를 재사용한다는 Decision 3과 양립하지 않는다.
- 실행 근거: 실제 유효한 중첩 instance 주소의 interaction owner를 만들어 현재 graph가 nested를 역색인함을 확인했다. 같은 주소에 명시된 대상 색인 정책을 적용한 key 집합은 `[outer,target]`라 nested를 포함하지 않는다. 새 target 스키마의 실제 명령 구현은 아직 없으며, probe는 기존 명령이 요구하는 역색인과 제안 key 집합의 차이를 확인한 것이다.
- 해결 방향: 대상 `address`의 instances·templatePath 및 `local`의 경로에 들어가는 모든 project node ID를 같은 참조 walker로 색인한다. 중간 instance swap·중간 노드 추출·삭제에서 외부 주인의 규칙도 재작성/정리되는 것을 G1에 포함한다.

### H3 — local을 복사 시 그대로 두면 복제 컴포넌트가 원본 template ID를 가리킨다

- 대상: `docs/adr/design/283-interaction-capability-target-ref-picker-breakdown.md:23`, `docs/adr/283-interaction-capability-target-ref-picker.md:90`.
- 입력 → 잘못된 결과: Local 컴포넌트 Card의 Edit가 같은 template의 Save를 `local` 대상으로 가리킨다. Card를 Duplicate component로 복제하면 Edit·Save·template root는 새 project ID를 받지만, breakdown의 `local 무변경` 규칙은 복제 interaction의 경로를 원본 Card에 남긴다. 새 Card instance에서는 대상이 해소되지 않는다.
- 코드 근거: `packages/shared/src/catalog/commands/components.ts:424-445`의 duplicateDefinition은 cloneNodeSubgraph로 소유 template 전체를 새 ID에 복사한다. `local`의 TemplateId는 lib ID만이 아니라 project NodeId도 허용한다 (`document/validation.ts:1828-1840`). 따라서 “상대 참조”라는 이유로 ID 재매핑을 생략할 수 없다. 같은 문제는 함께 복사된 project template ID가 `address.instances[1...]` 또는 templatePath에 들어 있을 때도 난다.
- 실행 근거: 실제 duplicateDefinition을 commit한 뒤 원본 local 경로를 복제 instance에 그대로 적용했다. 새 루트는 `project:node:copy-1`이지만 경로는 `project:node:origin-root`여서 현재 주소 해석은 `TEMPLATE_ROOT_MISMATCH`다. 새 action.target의 실제 clone 구현을 실행했다고 주장하지 않는다.
- 해결 방향: 복사 map에 있는 project ID를 ref의 **모든 instances/templatePath**에서 재매핑한다. 복사 범위 밖의 ID·lib ID는 유지한다. G1의 복사 테스트에 원본 정의의 local 규칙 → duplicateDefinition → 복제 instance의 대상이 복제 Save임을 포함한다.

### H4 — swap 후 “대상 없음”을 저장할 유효한 문서 모양이 없다

- 대상: `docs/adr/283-interaction-capability-target-ref-picker.md:88-90`, `docs/adr/design/283-interaction-capability-target-ref-picker-breakdown.md:20,27`.
- 입력 → 잘못된 결과: Card.Save를 대상으로 하는 규칙을 만든 뒤 Save가 없는 컴포넌트로 swap한다. Decision 3은 규칙을 남기고 대상 없음으로 표시하라고 하지만, target은 세 유효 참조 중 하나만 가능하고 G1/검증 설계는 templatePath 존재를 강제한다. 옛 주소를 남기면 swap transaction/재로드가 거부되고, target을 지우거나 undefined로 쓰면 스키마를 위반한다.
- 코드 근거: 현재 `packages/shared/src/catalog/resolution/address.ts:81-87`은 현재 정의의 루트·부모/자식 경로가 맞지 않으면 거부한다. 현재 swap은 매핑 실패 시 주인 interaction 자체를 삭제한다 (`commands/swap.ts:498-505`). 이를 “남긴다”로 바꾸려면 명시적인 미연결 상태가 필요하며, runtime resolver가 undefined를 돌려주는 것만으로 저장 검증을 통과하지는 않는다.
- 실행 근거: 실제 swapInstance로 Card → 빈 컴포넌트를 commit한 뒤 보존한 옛 target 주소를 검사하니 `TEMPLATE_ROOT_MISMATCH`다. 새 target 필드의 validator/transaction은 미구현이므로, 이 probe는 제안한 strict 검증과 stale 주소 보존이 양립하지 않는 주소 계약의 반례다.
- 해결 방향: 사용자 결정 3의 “규칙 유지”를 채택한다면 capability target에 명시적인 미연결 상태를 표현한다. 이 상태의 저장 모양·참조 색인·재지정·실행 report를 정하고, 정상 ref의 dangling 거부와 구별한다. G1/G2에 target 소실 swap을 **실제로 commit → 저장/로드 → 대상 없음 표시 → 재지정 → undo/redo**하는 조건을 추가한다.

### H1 — local의 반복 조상 검사 면제로 행별 후보가 하나로 좁혀지지 않는다

- 대상: `docs/adr/283-interaction-capability-target-ref-picker.md:91` Decision 2(c), `docs/adr/design/283-interaction-capability-target-ref-picker-breakdown.md:48` §1b step 3.

- 입력 → 잘못된 결과: GridList의 소유 행 template가 Local 컴포넌트 Row의 instance이고, Row 원본 안 Edit·Save 두 Button이 있다. 원본 Edit 규칙이 같은 Row의 Save를 `local: { instances: [], templatePath: [rowRoot, save] }`로 가리킨다. 데이터 3행 중 행 2의 Edit를 누르는 문맥에서 해소하면 Save의 세 record가 같은 source·같은 instancePath를 가져 모두 이름 붙인 사슬 비교를 통과한다. local의 반복 조상 검사를 생략하면 후보는 **3개**로 남아 Decision 2(d)의 설계 위반이 된다. "누른 행의 Save만 변경"을 실행할 수 없다.
- 코드 근거: `packages/shared/src/catalog/resolution/resolver.ts:260-267`의 withRowKey는 행별 key를 별도 필드에 찍고 instancePath를 바꾸지 않는다. `runtime/compositionRoot.ts:494-498`은 record identity에 별도로 `#row:<key>`를 붙인다. 따라서 같은 instance source ID의 경로를 공유한다는 사실이 같은 runtime 행 record를 공유함을 뜻하지 않는다.
- 실행 근거: 현재 code library·유효 CatalogGraph·resolver로 위 컴포넌트 행을 실제 3행 투영했다. Edit의 실행 경로는 `[project:node:list, project:node:row-instance]`이고 Save의 세 행도 모두 같은 경로다. 개정 step 2 및 local 면제 후 후보는 3개, 실행 record의 행 조상 identity를 비교한 뒤에는 **행 2의 1개**다. 원본 전체 반례를 재실행한 것이 아니라, 개정된 local 예외가 맞는지 단일 반증을 실행했다.
