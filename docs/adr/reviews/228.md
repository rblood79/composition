# ADR-228 Review Log

## Round 1 — 2026-09-20 (reviewer: codex)

판정: **설계 보완 필요 — HIGH 1 / MEDIUM 2**. Proposed 유지. 리뷰 기준 HEAD `a7c85b70f`; 제품 코드 변경 없음.

### H1 — Chart 생성 preset이 ref 전환에서 사라진다

위치: `docs/adr/228-palette-wide-reusable-origins.md:81`.

현재 Chart는 canonical type 하나에 여러 생성 진입점을 둔다. `packages/shared/src/catalog/componentCatalog.ts:457-462`의 creationVariants가 chartType별 initialProps를 만들고 `apps/builder/src/builder/panels/components/paletteItems.ts:304-313`가 이를 UI 항목에 전달한다.

그런데 ADR이 그대로 재사용한다는 `useElementCreator.ts:242-275`의 ref 분기는 `props: {}`만 저장한다(:266). initialProps를 적용하는 코드는 plain 생성의 `composeCreationProps`(:355-361)와 complex 호출에만 있다. Chart를 reusable 등록하면 서로 다른 chart 메뉴를 골라도 모두 origin 기본 차트가 된다. reusable panel 메타를 옮길 때 creationVariants 자체가 빠져도 여러 진입점이 사라진다.

해결: reusable entry에도 creationVariants를 보존하고, 선택한 진입점의 initialProps만 instance override로 기록한다. origin 기본값 전체를 instance에 복사하면 origin 편집 전파를 막으므로 두 값의 소유권을 구분해야 한다. G1/G2에 Chart 생성 진입점 각각의 생성→저장→새로고침→origin 변경 시나리오를 넣는다. 직접 호출 시 initialProps를 전달하는 AI 경로도 같은 계약을 사용해야 한다.

### M2 — catalog default와 factory default는 동일하지 않다

위치: `docs/adr/design/228-palette-wide-reusable-origins-breakdown.md:37-41`.

`defaultPropsFrom(contract)`를 기존 factory와 같은 함수라고 적었으나, 실제 기본값은 `apps/builder/src/types/builder/defaultPropsDerivation.ts:8-16`의 catalog base + builder-local overlay다. 예를 들어 `Button.binding.ts:56`의 children에는 default가 없고 Button 텍스트는 `defaultPropsDerivation.ts:44`의 overlay에서 온다. Badge/Link/ToggleButton도 같은 패턴이다. contract만 읽으면 빈 origin이나 링크 초기값 차이를 만든다.

해결: 새 유사 함수를 정의하지 말고 실제 `getDefaultProps(type)`/기존 합성 진입점을 재사용한다고 명시한다. origin이 가진 root props와 기존 신규 plain 노드의 초기 유효 props를 비교한다. 자식 구조형도 기존 definition과 순수 seed 생성 경계를 확인한 뒤 재사용 대상을 적어야 한다.

### M3 — 58종/58노드 gate가 제외 정책과 맞지 않는다

위치: `docs/adr/228-palette-wide-reusable-origins.md:79,108-110`, breakdown :88.

현재 PALETTE_ORDER를 read-only로 집계하면 66 type이고, 명시한 primitive 8종에 IllustratedMessage까지 제외하면 **57 type**이다. Toast는 이 66에 없다. 따라서 현 정책을 지키는 구현은 origin 58을 요구하는 G1/G3를 통과할 수 없다. Chart의 여러 표시 항목과 underlying type도 구분해야 한다.

또한 자식 구조형을 origin으로 옮기면서 문서 증가량을 “origin 58 노드뿐”으로 제한할 수 없다. 기존 IconButton도 root에 Icon/Text 자식이 있으며(`iconButtonTemplateOrigins.ts:101-136`), 새 복합 origin은 더 많은 자식을 가진다. 기존 5 reusable 및 template origin은 이미 존재하므로 추가 root 수와 최종 root 수도 다르다.

해결: Phase 0의 확정 집합을 gate의 입력으로 삼아 eligible type 수, palette entry 수, 최종 origin root 수, 신규 root 수, descendant 포함 총노드·직렬화 byte 증가를 분리한다. 사용자 결정 ②③의 범위를 바꿀 필요는 없고 집계/게이트 정정으로 해결할 수 있다.

### 검증 범위와 한계

- VERIFIED: 66 type 및 제외 9 type → eligible 57 집계, Chart의 initialProps 전달/누락, factory-local defaults, 기존 origin subtree 구조.
- UNVERIFIED: 신규 ref 전수의 live 편집·drag·복제·Undo, Canvas/Preview 픽셀, 600요소 +1ms 성능 예산은 구현 후 측정 대상이다. 필드 목록의 정적 일치는 실제 편집 쓰기 경로의 동등성을 대신하지 않는다.
- Publish가 ref를 전혀 못 읽는다는 주장은 하지 않는다. `packages/shared/src/utils/export.utils.ts:297-313`에 origin lookup/props merge 경로가 있다. ADR-148 R9의 slot provider 미소비는 별도의 기존 한계로, 이 리뷰에서 새 회귀로 확정하지 않았다.
- ADR-148 → 228과 227/228의 직교 관계, 기존 plain 공존 방향 자체에는 이견 없다.
