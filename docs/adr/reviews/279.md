### H1 — 중첩 컴포넌트 추출이 바깥 instance의 기존 주소를 끊는다 (fixed — 설계 수리 2026-10-21)

- 설계 위치: `docs/adr/completed/279-component-origin-on-local-page.md:95` (Decision 8), `docs/adr/design/279-component-origin-on-local-page-breakdown.md:60` (createComponent 소유권 이전). Status의 ADR-261·262 무변경 주장도 이 경계를 고려해야 한다.
- 입력·상태 → 잘못된 결과: 정의 A의 template이 `R > C > T`이고, page instance I가 T의 글자를 `instances: [I], templatePath: [R,C,T]`로 override한 상태에서 Local 카드의 C를 Create component한다. 설계대로 C를 정의 B의 template으로 옮기고 R의 C 자리에 새 instance J를 두면 R의 자식은 J다. I의 기존 주소는 여전히 R→C를 요구하므로 `TEMPLATE_STEP_NOT_OWNED`로 생성 transaction이 거부된다. 주소를 제거해서 통과시키면 사용자 override가 사라진다.
- 코드 근거: `packages/shared/src/catalog/document/graph.ts:805-863`은 변경 노드의 referrer를 재검증하고, `:1027-1033`은 각 descendantOverride에 validateInstanceAddress를 호출한다. `packages/shared/src/catalog/resolution/address.ts:73-88`은 중첩 instance 단계와 template 자식 관계를 실제 소유 트리로 검증한다. `packages/shared/src/catalog/resolution/templateOwners.ts:84-88`도 주소를 완전 일치시켜 적용하므로 ID가 살아 있다는 것만으로 보존되지 않는다. 기존 move 경로도 `commands/structure.ts:920`의 dropAddressesLeftOrigin에서 주소 영향을 별도로 처리한다.
- 해결 방향: 소유권 이전과 같은 transaction에서 영향받는 바깥 instance·상위 template의 주소를 새 경계로 재작성한다. 예시의 T 대상은 `instances: [I,J], templatePath: [C,T]`가 되어야 한다. C 자체를 가리키는 주소는 새 J 자리로 연결해야 한다. patch뿐 아니라 fillSlot·replace·interaction.address 등 같은 주소 형식의 소비자도 포함하고, 기존 override를 유지한 채 생성·undo·저장·재열기가 성립하도록 Decision과 G1에 명시한다. 이 처리가 없으면 Decision 8의 허용 약속을 충족하지 못한다.
- 검증 수준: 현재 validator·referrer·resolver의 정적 경로로 도출한 설계 반례. ADR-279 구현 및 executable RED는 UNVERIFIED.

### H2 — base 위치만 instance로 옮기면 breakpoint 위치가 base에 덮인다 (fixed — 설계 수리 2026-10-21)

- 설계 위치: `docs/adr/design/279-component-origin-on-local-page-breakdown.md:60`, 본문 Decision 2 (`docs/adr/completed/279-component-origin-on-local-page.md:89`).
- 입력·상태 → 잘못된 결과: 선택 노드의 `layout`에 `position=absolute, insetLeft=10px`, `responsive.mobile.layout`에 `insetLeft=20px`가 있다. 명시된 positionLayout/withoutPositionLayout 방식으로 base 위치만 새 instance로 옮기고 template의 base 위치만 지우면, Mobile의 template이 계산한 20px 위에 instance의 base 10px가 적용된다. Create 직후 Mobile 위치가 20px에서 10px로 바뀐다. 위치가 Mobile에만 있는 경우에는 위치 write가 template에 남아 이후 새 instance에도 원래 page 배치가 새어 나간다.
- 코드 근거: `packages/shared/src/catalog/document/absoluteLayout.ts:40-52`의 두 helper는 LayoutWrites 하나만 읽고 responsive layer를 처리하지 않는다. `packages/shared/src/catalog/resolution/resolver.ts:436-439`는 활성 breakpoint의 층을 수집하고 `:1198-1204`에서 instance 자신의 layout을 계산한다. template은 `:1772-1778`에서 base+responsive layout을 적용한 뒤 `root.layout`(instance)을 덮어쓴다. `NodeResponsiveLayer.layout`은 `document/types.ts:551-554`의 정식 문서 필드다.
- 해결 방향: base와 tablet/mobile 각각에서 POSITION_LAYOUT_KEYS를 분리해 새 instance의 대응 층으로 옮기고 template의 대응 층에서는 제거한다. 내부 layout·시각 write는 template에 남긴다. base absolute+Mobile inset 변경, base relative+Mobile absolute, 층별 pin 해제를 G1의 생성 전후 resolved 동일 조건에 포함한다.
- 검증 수준: 현재 layout helper와 resolver의 병합 순서로 도출한 설계 반례. 실행·Canvas/Preview 픽셀 검증은 UNVERIFIED.
