### 판정

HIGH 2 · MEDIUM 2 · LOW 1. Accepted 전에 Decision 4 와 Phase 2 (InlineAlert) 설계를 고쳐야 한다.

### 이슈

- **h1 (HIGH)** Dialog 제목의 `slot="title"` 만으로는 접근성 이름이 연결되지 않는다. `S/components/Dialog.tsx:33-35` 가 `aria-labelledby` prop 이 없으면 `aria-label="Dialog"` 를 넣고, react-aria 3.52.0 `useDialog` 는 `aria-label` 이 있으면 `titleId` 를 undefined 로 만든다. RAC Dialog 가 HeadingContext 의 `title` slot 에 주는 `titleProps` 에 id 가 없다. 실패를 보이는 방법: 제목 Heading 에 `slot="title"` 을 넘긴 Dialog 를 열면 section 에 `aria-label="Dialog"` 가 남고 `aria-labelledby` 는 없다 → G2 실패. 해결 방향: Dialog.tsx 의 폴백 조건을 바꾸는 설계 (제목 존재를 binding 이 알려 주거나 폴백 제거 + RAC 경고 수용) 를 Decision 4 와 영향 파일에 넣는다.
- **h2 (HIGH)** InlineAlert 의 제목 · 설명 크기는 InlineAlert size 를 따른다 (`T:5763-5797` → Canvas `rulePartRules.ts:918-975`, DOM `InlineAlert.css:148-173`). breakdown Phase 2 는 size 전달을 쓰지 않고 자리 patch 로 정한다고 적었는데, 고정 patch 는 size 별 값을 표현하지 못한다. 실패를 보이는 방법: InlineAlert size lg → 지금 제목 18px · 700, 설명 16px. 적힌 대로 전환하면 제목은 Heading rule md (16px · 600) 또는 고정 patch 값, 설명은 Description rule 기본값 (12px) 이 size 와 무관하게 나온다. 해결 방향: InlineAlert → Heading · Description 의 size 전달과 단계 대응 (InlineAlert md 설명 14px = Description lg) 을 Decision 에 넣는다. 아니면 InlineAlert 를 이 ADR 범위에서 뺀다.
- **m1 (MEDIUM)** 팔레트에 Heading 이 없다 (`paletteItems.ts:201-292`). Heading 이 문서에 들어오는 실제 경로는 AI (`layoutTemplates.ts:31-55` · `builderHost.ts:33`) 다. - **m2 (MEDIUM)** Popover · Tooltip 은 `CATALOG_DOM_OVERLAY_BINDINGS` 라 DOM 이 항상 0 이고, DialogTrigger 안 Dialog 는 닫혀 있는 동안 0 이다 (`domBinding.tsx:757-772`). 그래서 G0 · G2 의 SSR 마크업 대조는 이 셋에서 vacuous 하다. ### m1 — MEDIUM: Heading의 primitive 유지와 원본 전파 약속이 양립하지 않는다

- 위치: `docs/adr/254-base-part-chain.md:91` (Decision 1), `:100`, `:141`; `docs/adr/design/254-base-part-chain-breakdown.md:49`, `:67-70`.
- Decision 1은 AI Heading을 primitive로 유지하고 placeable 예외만으로 manifest를 보존하겠다고 한다. 그러나 `apps/builder/src/services/ai/compiler/builderHost.ts:31-36`은 `getReusableOriginId`로 `creationMode`와 `reusableId`를 정하고, `apps/builder/src/services/ai/tools/compositeMode.ts:11-14`은 원본이 있으면 placeable과 무관하게 `reusable`을 돌려준다. `packages/shared/src/catalog/componentCatalog.ts:1519-1520`의 조회 역시 placeable을 검사하지 않는다.
- 반증 1: 원본 등록이 만드는 `getReusableOriginId("Heading") = "component-heading"`만 인메모리 mock하고 실제 `readCompilerState()`를 호출했다. placeable은 그대로인데 `creationMode`가 `leaf → reusable`, reusableId가 `undefined → component-heading`으로 바뀌었다. 따라서 문서의 placeable 예외만으로는 manifest 불변을 만족하지 않는다. 이 프로브는 전체 등록 구현을 실행한 것이 아니라 그 등록의 조회 효과를 고정한 것이다.
- 반증 2: Decision 1대로 페이지 Heading을 `lib:definition:heading` primitive로 유지하고 Card 제목만 새 원본 instance로 만든 library를 검증·해석했다. `setLibraryDefault(origin-component-heading, visual.color, #ff0000)` 후 Card 제목은 빨강이 되지만 페이지 primitive는 원래 색을 유지했다. `resolver.ts:1053-1059,1157`의 원본 override는 그 원본의 instance root에만 적용된다. 따라서 Positive의 「page에 놓은 Heading도 같이 바뀐다」와 breakdown의 live 완료 조건은 충족되지 않는다.
- 해결 방향: 페이지/AI Heading을 primitive로 유지할지 원본 instance로 전환할지 하나로 고정한다. 전자라면 AI 생성 mode·creation contract까지 보존하고 페이지 Heading 전파를 완료 조건에서 제외한다. 후자라면 Decision 1과 manifest 불변 조건을 실제 전환에 맞춘다. 생성, 편집, 검증이 같은 정책을 따라야 한다.

### m2 — MEDIUM: 부모 prop 소유를 registry에 추가하는 것만으로는 제목·설명 편집을 제어하지 못한다

- 위치: `docs/adr/254-base-part-chain.md:95` (Decision 5); `docs/adr/design/254-base-part-chain-breakdown.md:30,58-59`.
- Card 제목·설명의 직계 부모는 각각 CardHeader·CardContent다 (`reusableOriginLibrary.ts:2394-2447`). `catalogRuntime/subpart.ts:35-40`은 직계·조부모 type을 넘기지만 `resolveDelegatedChildFontSize.ts:214-218,300-307`은 SelectTrigger·Button만 건너뛴다. 따라서 `TEXT_ONLY_SUBPART_PARENTS`에 Card만 넣어도 소유자는 null이다. `CatalogPropertiesPanel.tsx:90-99,132-140`은 이 값으로 편집 대신 부모 안내를 보여줄지 결정하므로 Card 자식의 독립 글자 편집 surface가 남는다.
- Canvas 인라인 경로는 그 술어를 아예 읽지 않는다. `CatalogCanvas.tsx:1203-1213`은 글자 prop 유무로 진입하고 `catalogRuntime/canvasText.ts:41-56`은 선택 자식에 `children` patch를 쓴다. 따라서 InlineAlert처럼 Properties 소유자가 올바르게 판정되는 경우도 글자 정본이 갈라진다.
- 반증: 메모리 library에서 Heading/Description 자리를 원본 instance로 바꾸고 TEXT_ONLY 표에 Card·InlineAlert를 추가했다. Card 두 부품의 owner는 `[null, null]`. InlineAlert 제목 owner는 `InlineAlert`로 맞았지만, 두 컨테이너 모두 실제 `catalogTextCommand`로 자식 제목을 "Child title"로 편집한 뒤 부모 `title`을 "Changed parent"로 바꾸어도 화면 record는 "Child title"로 남았다. 이는 명령·resolver 경로 재현이며 실제 브라우저 더블클릭 재현은 아니다.
- 해결 방향: Card의 bound 제목/설명을 wrapper 너머로 판정하고, 인라인 편집도 부모 `title`/`description`에 쓰거나 같은 소유 규칙으로 제한한다. 자유 slot에 사용자가 넣은 독립 텍스트까지 부모 소유로 묶지 않는다. 부모 prop 편집 → 자식 편집 시도 → 부모 재편집 및 undo를 검증 조건에 포함한다.

### 이전 리뷰 반영과 추가 확인

- Round 1의 Dialog 폴백 축소, InlineAlert 크기 대응표, 팔레트 Heading 전제 삭제, DOM oracle 대상 축소, IllustratedMessage 범위 설명은 문서에 반영되어 있다. 기존 outcome은 변경하지 않았다.
- F4의 예제 구조는 공식 [Popover 문서](https://react-aria.adobe.com/Popover)와 [Modal 문서](https://react-aria.adobe.com/Modal)에서 확인했다. Popover 예제의 자유 내용과 Modal 안 Dialog/Heading 구성이 부품 단위 선택 근거와 일치한다.
- InlineAlert 설명 sm/md/lg → Description md/lg/xl의 목표 값 12/14/16px은 현재 rule과 일치한다. 현재 `CATALOG_SIZE_PROPAGATION`은 type 목록이고 `resolver.ts:610-629`는 같은 size 문자열만 복사하므로, 구현 시 표의 확장과 resolver 변환이 함께 필요하다. 단순 등록 프로브는 12/12/14px이었다. 문서가 단계 대응 자체를 이미 요구하고 G1에서 이를 검증하므로 별도 신규 결함으로 세지 않는다.

### m1 — MEDIUM: 새 Heading 원본 등록 시 AI 생성 계약에서 size가 사라진다

- 위치: `docs/adr/design/254-base-part-chain-breakdown.md:49-50`; `docs/adr/254-base-part-chain.md:93`.
- Phase 1은 `accepts: { children }`인 원본과 `lib:definition:heading` 루트를 등록해 나머지 props를 루트에서 상속하는 구조다. 하지만 `apps/builder/src/builder/catalogRuntime/creationContract.ts:23-29`의 `definitionOf`는 `lib:definition:type-*`만 해석한다. `heading`은 이 접두사가 없어 undefined가 된다.
- `packages/shared/src/catalog/document/library.ts:156-160`의 `instanceContract`는 루트 정의를 못 찾으면 원본 자체의 accepts만 돌려주며, `creationContract.ts:40-48`은 그 accepts에 없는 semantic field를 제거한다. Heading primitive가 제공하는 size (`codeCatalogLibrary.ts:150-152`)가 manifest에서 빠진다. AI 경로 `builderHost.ts:31-36` → `manifest.ts:43-50,146-149`에서 size를 사용한 생성 요청을 거부한다.
- **재현**: 문서가 제안한 Heading definition/template를 모듈 mock에 추가하고 원본 등록 조회 효과(`getReusableOriginId("Heading") = "component-heading"`)를 켰다. 실제 `catalogCreationEditFields("Heading")`는 등록 전 size를 포함하지만 등록 뒤에는 빠진다. 실제 `readCompilerState()`와 `validateProgram()`에 같은 `create_element`, `type: "Heading"`, `props: { children: "Title", size: "lg" }`를 넣으면 등록 전 성공 → 등록 뒤 `{ ok: false, error: "unknown-semantic-field:size" }`다. 현재 production이 이미 실패한다는 뜻이 아니라, 계획한 등록 변경이 기존 소비자에 만드는 회귀를 인메모리로 재현한 것이다.
- 영향: 기존 AI Heading 크기 지정이 실패하고, Phase 1의 「manifest props 불변」 게이트를 통과하지 못한다.
- 해결 방향: Phase 1 영향 범위에 `creationContract.ts`를 넣고 `lib:definition:heading` 같은 code-catalog primitive id도 실제 library 계약과 같은 방식으로 해석하게 한다. size를 원본 accepts에 중복 선언하기보다 루트 계약을 올바르게 상속한다. 기존 `size: "lg"` 생성 요청이 전후 모두 성공하고 size 선택지가 유지되는 회귀 조건으로 검증한다.
