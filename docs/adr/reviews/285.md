### HIGH h1 — 변경 가능한 내용과 부모별 순서만으로는 기존 요소의 identity를 보존할 수 없음

- 위치: `docs/adr/285-code-view-closed-vocabulary-round-trip.md:94`, `docs/adr/design/285-code-view-closed-vocabulary-round-trip-breakdown.md:69`.
- 입력 → 결과: 스타일을 지정한 `<Text>A</Text>`를 `<Text>B</Text>`로 고치면 `(종류, 글자, 식별 prop)` LCS 키가 달라진다. 명시된 “짝 없음 → 추가/삭제”를 적용하면 단순 글자 편집이 삭제·재생성이 되어 코드에 없는 스타일·override·참조를 잃는다. 부모를 옮기는 경우에도 부모별 LCS만으로는 이동 전후가 짝지어지지 않는다. 순서 fallback으로 바꾸어도 같은 JSX인 두 요소 중 하나를 삭제할 때 어느 문서 ID를 남길지 확정할 수 없다.
- 근거: `packages/shared/src/codeView/generate.ts:1835`의 `writeNode`는 문서 ID와 visual을 출력하지 않는다. 실제 `CatalogGraph` fixture에서 빨간 Text A와 파란 Text B를 만들고 `removeTargets`로 각각 A 또는 B를 삭제하면, 남은 문서 ID·색은 다른데 생성 코드는 동일했다. 실제 `setFields`로 글자만 바꾸면 기존 ID·빨간색을 보존할 수 있음도 확인했다. `apps/builder/src/builder/catalogRuntime/attributes.ts:173`의 자동 HTML ID도 `metadata.htmlId`여서 이 생성 경로의 식별 prop으로 자동 제공되지 않는다.
- 해결: 편집 세션의 source range → 문서 ID/주소 대응과 명확한 identity 유지 규칙을 정하고, 글자·prop 변경을 identity와 분리해야 한다. 부모 간 이동도 전역 대응 후 `moveNodes`로 처리해야 한다. 변경 이력/표식 없이 여러 대응이 가능한 입력은 임의 삭제하지 말고 모호성을 거절하거나 사용자가 대상을 식별할 수 있게 해야 한다. G2에 글자만 변경, prop만 변경, 부모 간 이동, 같은 JSX·다른 스타일의 첫째/둘째 삭제를 넣고 ID·참조 보존을 검증한다. 동일 코드 무편집 왕복이나 서로 다른 Button 순서 변경만으로는 이 문제를 닫지 못한다.

### HIGH h2 — 초안의 page/revision 기준점이 없어 이후 변경 또는 다른 페이지를 덮어쓸 수 있음

- 위치: `docs/adr/design/285-code-view-closed-vocabulary-round-trip-breakdown.md:68`, `docs/adr/design/285-code-view-closed-vocabulary-round-trip-breakdown.md:79`.
- 입력 → 결과: 코드 편집을 시작한 뒤 Canvas에서 요소를 추가하고 원래 초안을 Apply하면, 최신 문서에만 있는 요소를 “코드에서 삭제됨”으로 해석할 수 있다. 페이지를 전환한 뒤 남은 초안을 적용하면 다른 페이지를 이전 페이지의 구조로 바꾸는 위험도 있다. 새 파서의 lazy 로딩 중 문서가 바뀌는 경우도 같은 문제다.
- 근거: 현재 `CatalogCodeViewPanel.tsx:53-77`은 pageId/revision에 따라 result를 재생성하지만 draft는 문자열 하나로 유지한다. `:104`에서 최신 result와 draft를 비교하고, 편집 시작 시에는 `:194`에서 문자열만 복사한다. `packages/shared/src/catalog/runtime/compositionRoot.ts:1802`는 **실행 직전** revision을 잡고 재시도한다. 따라서 transaction의 REVISION_CONFLICT는 편집 시작 이후의 변경을 감지하는 장치가 아니다. 실제 transaction probe에서도 이전 revision을 전달하면 거절되지만 실행 시 최신 revision을 쓰면 오래된 값으로의 덮어쓰기가 성공했다.
- 해결: `{projectId, pageId, baselineRevision, baselineResult, draft}`를 편집 세션으로 저장하고 현재 문서와의 불일치를 Apply 시점과 비동기 parse 이후에 확인해야 한다. 기본은 초안 보존 + 충돌 안내 + 적용 0이며, 자동 병합하려면 baseline/edited/current의 3-way 정책이 필요하다. G2/G3에 Canvas 추가·수정 후 Apply, 페이지 전환, parse 대기 중 revision 변경을 넣는다. dry-run과 한 transaction만으로는 유효하지만 오래된 명령을 막을 수 없다.

### MEDIUM m3 — 파생 실행 코드를 무조건 건너뛰면 어휘 밖 코드를 포함한 Apply가 부분 수용됨

### HIGH h1 — anchor를 추가했지만 줄 LCS의 대응 실패·모호성을 그대로 identity로 확정함

위치: `docs/adr/285-code-view-closed-vocabulary-round-trip.md:95`, `docs/adr/design/285-code-view-closed-vocabulary-round-trip-breakdown.md:73`.

수리된 상위 계약은 적절하다: anchor를 문서 ID/주소와 연결하고, 내용을 바꿔도 ID를 보존하며, 모호한 경우 거절한다. 그러나 breakdown의 실행 규칙인 “여는 태그 줄이 살아 있으면 같은 ID → 삭제/추가 범위만 정규화 텍스트로 재대응 → 남은 범위는 삭제/추가”는 다음 두 기존 반례를 해결하지 못한다.

1. **글자만 수정:** 한 줄짜리 `<Text>A</Text>`를 `<Text>B</Text>`로 변경한다. 현재 생성기 `packages/shared/src/codeView/generate.ts:1987-1992`처럼 여는 태그·본문·닫는 태그가 한 줄이면 줄 LCS의 대응은 0이다. 2차 정규화 텍스트도 A와 B가 달라 이동 대응 0이며, 3차는 삭제 1 + 추가 1이 된다. 따라서 “글자만 바꾸면 같은 ID”라는 Decision 및 RED ⑥의 기대와 실제 제시한 알고리즘이 충돌한다. anchor는 원본 ID를 알려주지만 수정 후 대응을 스스로 만들지 않는다. 한 줄 JSX의 prop 수정도 같은 문제다.
2. **동일 코드·다른 스타일의 삭제:** 빨강 A와 파랑 B가 각각 `<Text>Text</Text>` 한 줄로 출력되고, 편집본에는 한 줄만 남는다. 단일 LCS는 둘 중 하나를 이미 대응시킨다. 남는 것은 삭제 1·추가 0이므로 2차의 N:1·1:N 검사에 들어가지 않고 3차에서 한쪽을 삭제한다. 어느 줄을 지웠든 최종 문자열은 같으므로 이 LCS의 tie-break는 문서 identity의 근거가 아니다. “모호하면 거절” 검사는 삭제/추가 후보만이 아니라 1차에서 대응된 후보까지 포함해야 한다.

**해결 방향:** 글자·prop을 바꾼 replacement hunk에서 원래 anchor를 유지하는 명시적 규칙을 추가해야 한다. 편집 연산으로 범위를 추적하거나, baseline/edited AST의 구조와 변경 구간으로 유일한 수정 대응을 결정하는 방법이 가능하다. 줄 LCS 결과는 후보로만 사용하고, identity를 확정하기 전에 중복된 기존 anchor를 포함한 대체 대응을 검사해야 한다. 후보 문서 상태가 다르면 거절하며, 그 검사를 통과하기 전에는 `matched`에도 삭제/수정 identity를 확정하지 않는다. 이미 추가한 RED ⑥·G2 반례가 이 두 실제 분기에서 통과해야 하며, 기대 테스트 항목 추가만으로 현재 알고리즘의 모순이 해소된 것은 아니다.

**실행 근거:** `.agent/runs/2026-10-27-review-adr285-round2/identity-probe.mjs`는 breakdown:73의 세 단계만 옮긴 명세 모델이다. 결과는 글자 수정 `matched=0, removed=1, added=1, moves=0`, 동일 줄 삭제 `matched=1, removed=1, added=0, ambiguous=0`. 두 반례 단언 PASS. 제품 inverse는 아직 없으므로 제품 구현 실패를 재현했다고 주장하지 않는다. ### HIGH h1 — 붙여넣기 구간의 순서 기반 대응이 이동을 내용 교환으로 확정함

- 위치: `docs/adr/285-code-view-closed-vocabulary-round-trip.md:97`, `docs/adr/design/285-code-view-closed-vocabulary-round-trip-breakdown.md:75`.
- 입력: 같은 부모 아래 빨간 `<Text>A</Text>`(id a), 파란 `<Text>B</Text>`(id b)를 둔다. 두 줄을 선택하고 `<Text>B</Text>` / `<Text>A</Text>` 순서로 붙여넣는다. 새 명세의 `replaced` hunk에 해당하며, 각 요소의 JSX는 그대로이고 순서만 바뀐다.
- 잘못된 결과: 2차가 `(부모, 종류, 순서)`로 먼저 대응하면 첫째 자리 a에는 B, 둘째 자리 b에는 A를 쓴다. 결과는 **빨간 B(id a) · 파란 A(id b)**다. 순서 변경을 `moveNodes`로 처리하면 **파란 B(id b) · 빨간 A(id a)**여야 한다. A·B 모양의 개수는 각각 1→1이라 “같은 모양 수가 줄었을 때”라는 모호성 검사에 걸리지 않는다. 이미 수정으로 소비된 두 요소는 3차 삭제/추가 후보 기반 이동 검사에도 도달하지 않는다.
- 근거: breakdown:75는 이 대응 순서를 명시한다. 본문 G0의 RED ⑤ 및 G2는 요소 순서 변경을 이동으로 처리하고 스타일·규칙을 보존하도록 요구한다. 현재 생성기 `packages/shared/src/codeView/generate.ts:1987-1997`도 위 Text를 한 줄 JSX로 출력한다. 편집기가 교체 범위를 정확히 아는 것은 유효하지만, 통째 교체된 범위 안의 두 ID를 순서로 확정해도 된다는 근거는 아니다.
- 해결: `replaced` hunk에서도 **유일한 정규화 JSX 대응을 먼저** 찾아 기존 ID를 보존하고 위치 변화는 이동으로 처리한다. 그 뒤 남은 후보에만 단순 내용 수정 대응을 적용한다. 여러 대응이 가능하고 ID별 문서 상태·참조가 달라지는 입력은 임의 대응하지 말고 거절해야 한다. 모호성 검사를 개수 감소에만 한정하지 않는다. 기존 G2 순서 변경 사례를 “선택 구간 붙여넣기” 입력으로도 실행하여 ID·색·규칙 보존을 단언하면 이 분기를 검증할 수 있다.
- 실행 확인: `.agent/runs/2026-10-27-review-adr285-round3/identity-probe.mjs`에서 명시된 순서 기반 대응을 모델링했다. 제안 규칙의 결과 `[[a,B,red],[b,A,blue]]`, 이동의 결과 `[[b,B,blue],[a,A,red]]`, 모양 개수 감소 0을 단언했다. 반례 확인 **PASS**. 이는 명세 모델 실행이며 아직 없는 제품 inverse나 CodeMirror 통합을 실행한 결과가 아니다.
