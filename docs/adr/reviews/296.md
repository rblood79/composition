# ADR-296 Review Log

## Round 1 — 2026-10-30 (reviewer: codex)

판정: HIGH 3건, pending 3건. 현재 설계 그대로의 착수는 보류 권고. 검토 기준 HEAD fe576e8b2. 제품 코드 및 ADR 상태는 변경하지 않았다.

1. **HIGH — instance 전용 규칙을 원본으로 투영하면 적용 범위를 보존할 수 없다.** ADR Decision 4 (docs/adr/296-code-view-project-file-tree-projection.md:94), breakdown:69,128, inventory:39-40. 동일 원본 A/B 중 A 내부 버튼에만 address 규칙을 만들거나, 같은 onPress 원본 규칙 둘 중 하나만 off 하면, 원본 함수의 handler / instance onPress={null}만으로는 instance·내부 위치·규칙 ID를 구별할 수 없다. 그대로 원본 규칙으로 읽으면 B까지 바뀌고, A 전용 address를 숨겨 보존하면 원본 파일이 A의 page 변수/소유 범위를 표현하지 못한다. 현재 InteractionEntry는 ownerId+address를 보유하고(types.ts:1212-1217), Preview는 instance chain을 필터링한다(catalogPreviewInteractions.ts:59-90). off/대체는 trigger가 아니라 주소별 ruleId 맵이다(types.ts:558-563, effectiveInteractions.ts:76-91). pushInstanceOverrides는 patch 편집 명령이 아니라 원본에 전파하는 명령이다(instanceOverrides.ts:362-384); breakdown:40의 off/대체 역명령으로 쓰면 B도 영향을 받는다. 해결: 원본 규칙과 instance 주소 규칙을 분리하고, instance 쪽에 주소+ruleId를 유지하는 닫힌 문법 및 기존 catalogInheritedRuleEnabledCommand/catalogReplaceInheritedRuleCommand 경로를 명시한다. G4에 A/B 격리, 내부 버튼 2개, 동일 trigger 규칙 2개 중 하나만 off/대체, page 변수 참조, Library 읽기 전용 원본 사례를 넣는다.

2. **HIGH — themeOverride를 테마 조건부 CSS 스타일로 잘못 모델링하고 존재하지 않는 쓰기 API를 지정한다.** breakdown:30,120,122; ADR Decision 3 (:93). 실제 NodeThemeOverride는 조건별 스타일 맵이 아니라 노드에 강제할 {mode, tint}다(types.ts:909-913). light 프로젝트에서 한 노드에 {mode:"dark", tint:"blue"}를 설정한 입력은 [data-theme="dark"] .c {…}로 투영하면 전역 dark일 때만 매칭하는 조건으로 바뀌며, mode 강제와 tint 선택을 역으로 복구할 수 없다. setFields의 입력에는 theme 인자가 없고(fields.ts:44-52), 실제 명령은 setWholeField({field:"themeOverride", value})다(:193-218). 해결: mode/tint 지정과 조건별 CSS를 분리하고 mode/tint 각각 및 해제의 닫힌 표현을 정의하여 setWholeField로 매핑한다. G3에 global light + node dark/tint, global dark + node light, unset 왕복에서 원본 필드 자체를 보존하는 반례를 추가한다. styleOf는 resolver.ts의 함수가 아니라 runtime/compositionRoot.ts:990의 비공개 함수이므로 실제 oracle 진입점도 고정해야 한다.

3. **HIGH — 파일별 계획 후 합치는 순서만으로 신규 파일 간 참조와 rename을 처리할 수 없다.** breakdown:106-108. 새 data/users.ts 정의와 page의 users 바인딩을 한 Apply로 추가하면, page 역문법이 baseline reader로 참조를 검사하는 시점에는 users가 없어 unknownReference가 된다. 다른 파일에서 함께 바꾼 이름도 같은 문제다. 현재 planner는 baseline symbols 및 input.data를 사용하며(codeViewEdit.ts:305-307,341-346,1497-1501), 파일별 재생성 대조까지 끝난 뒤 command를 반환한다(:249-274). composeCommands가 staged reader를 주는 것은 command 실행 시점뿐이다(compose.ts:23-38). 따라서 파일별 역문법/검증을 모두 끝낸 뒤 compose하는 명세는 이 문제를 해결하지 못한다. 또한 같은 transaction이라 순서가 결과에 무관하다는 설명은 위 staged 계약과 맞지 않는다. 해결: 전체 dirty 파일의 선언/rename 및 ID 배정을 먼저 수집하고, 공통 심볼 표와 staged reader로 정의·사용처를 해석한 뒤 모든 파일의 재생성 대조를 최종 stage에서 수행한다고 명시한다. G2에 새 collection+사용처, 새 component+instance, 새 page+navigate, 정의+사용처 동시 rename을 한 Apply로 검증하는 반례를 추가한다.

검증: 기존 adr281InstanceRules.test.tsx 7/7 PASS, nodeAuthoring.test.ts 및 fields.test.ts 10/10 PASS (합계 17/17). 이는 현재 문서/명령/Preview 계약 확인이며 ADR-296 구현 성공의 증거는 아니다. 정적 설계 반례를 검토했으며 신규 투영/역문법의 실행 재현, 브라우저, 번들, 생성 시간, G0~G6는 UNVERIFIED. 별도 제품 수정이 없으므로 typecheck/전체 preflight는 실행하지 않았다.

**HIGH h1 — 원본 노드 이름 하나로 중첩 instance 경로를 복원할 수 없다.**
근거: docs/adr/design/296-code-view-project-file-tree-projection-breakdown.md:163,182 및 ADR Decision 4 (:97). 키를 원본 파일의 노드 이름(동명은 -2)과 같게 두지만 InstanceAddress는 instances 체인과 templatePath의 두 부분이다(types.ts:530-535). 바깥 instance outer 안에 같은 UserPicker 원본의 left-picker / right-picker 두 template instance를 배치하면 다음 두 위치가 동시에 존재한다.

- L = {instances: [outer, left-picker], templatePath: [picker-root, save-button]}
- R = {instances: [outer, right-picker], templatePath: [picker-root, save-button]}

두 위치의 원본 파일과 원본 노드 이름(save-button)은 동일하다. 따라서 문서대로면 overrides의 키 둘 다 save-button이 된다. -2는 원본 파일 안에서 동명 노드를 구별하는 규칙이라 동일 template가 두 instance 경로로 등장한 이 경우를 복원하지 못한다. 한 키로 합치면 한쪽 규칙/patch가 사라지거나 다른 위치에 적용되며, anchor를 유지해 기존 항목을 보존해도 사용자가 두 위치를 새로 저작하는 문법은 생기지 않는다. CSS의 .outer .save-button도 같은 두 위치를 구별하지 못한다. 이것은 h1이 다루던 instance 주소·적용 범위 문제의 잔여 반례다.

실행 근거: 현재 catalogPreviewInteractions.ts:59-90의 recordsOfOwner 함수 텍스트를 TypeScript transpile로 추출해 그대로 호출했다(주소 분기, graph/root 입력은 최소 stub). 동일 source의 두 record에 대해 L 규칙은 left-record만, R 규칙은 right-record만 반환했다. 즉 production consumer는 instances 체인을 구별한다. 제안된 두 코드 키가 충돌한다는 판정은 설계 정적 반례이며, 아직 없는 ADR-296 역문법의 실행 실패로 주장하지 않는다.
