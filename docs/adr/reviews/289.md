### H1 — JSON 기본값의 직렬화 손실

- 위치: `docs/adr/289-data-grid-row-form-column-editor-selection-actions.md:108`, `docs/adr/design/289-data-grid-row-form-breakdown.md:49`.
- 입력·상태 → 잘못된 결과: 새 열 기본값에 `{ "enabled": true }` 또는 `[1, 2]`를 타입별 입력으로 저장 → 읽을 때 `String(defaultValue)`가 각각 `[object Object]`, `1,2` → 현행 `coerceCellValue`는 `ok:false, value:null`. 빈 배열 `[]`는 빈 문자열로 바뀌어 **성공으로 null**을 돌려준다. 따라서 설계대로 구현하면 행 추가가 기본값을 잃거나 유효한 기본값 때문에 검증을 실패한다. 구 문서만의 문제가 아니라 새로 만든 값도 해당한다.
- 근거: `apps/builder/src/builder/panels/datatable/grid/cellValue.ts:17-18`, `:43-58`; 문서는 JSON 기본값을 허용한다 (`packages/shared/src/catalog/document/validation.ts:466-467`). Boolean 글자 기본값은 대조군에서 정상.
- 해결 방향: `resolveFieldDefault`에서 이미 타입이 맞는 값은 보존하고, 글자 기본값은 타입 강제를 거친다. 공용 raw 변환이 필요하면 structured 값은 JSON으로 직렬화하는 `formatCellValue`를 사용한다. object·array·빈 배열의 저장→placeholder→행 삽입을 함께 고정한다.

### H2 — id 대조를 통과한 다른 행 덮어쓰기

- 위치: `docs/adr/design/289-data-grid-row-form-breakdown.md:38`, 본문 R2 `docs/adr/289-data-grid-row-form-column-editor-selection-actions.md:127`.
- 입력·상태 → 잘못된 결과: `id`가 없는 A/B/C 행에서 B(index 1) 수정 양식을 열고 A를 삭제 → index 1은 C가 되지만 열린 id와 현재 id가 모두 `undefined`라 제안된 guard 통과 → `set_cell(rowIndex:1)`이 C를 B의 수정 값으로 덮어쓴다. 중복 id도 같다.
- 근거: `validateCatalogEntry`가 id 없는/중복인 행을 모두 수용 (`packages/shared/src/catalog/document/validation.ts:2019-2021`); CSV/JSON import도 일반 행을 받는다 (`apps/builder/src/builder/panels/datatable/grid/DataGrid.components.tsx:646-669`). `normalizeCollection`은 필드 id만 부여하며 행 정체성을 보장하지 않는다. 실제 reducer의 `remove_rows` 후 `set_cell` 실행에서 C 덮어쓰기를 확인 (`apps/builder/src/builder/stores/utils/dataChange.ts:737-746`, `:776-783`).
- 해결 방향: 고유하고 비어 있지 않은 키가 보장된 경우에만 그 키를 신뢰한다. 그 외에는 열린 시점의 행 집합/collection revision을 저장해 변경 시 충돌로 거절하거나 안전하게 재탐색하는 규칙을 명시한다. 문서 스키마 변경 없이도 보수적 충돌 거절은 가능하다. 저장 직전 최신 상태에 대해 같은 규칙을 적용한다.

### M3 — Update에서 명시적 비움이 기본값으로 치환됨

- 위치: `docs/adr/289-data-grid-row-form-column-editor-selection-actions.md:107`, `docs/adr/design/289-data-grid-row-form-breakdown.md:34-37`.
- 입력·상태 → 잘못된 결과: 선택 string 열의 기본값이 `fallback`, 기존 셀은 `custom`인 행을 열고 값을 지운 뒤 저장 → 명세의 빈 입력→기본값 규칙을 적용하면 null 대신 `fallback`을 저장한다. boolean의 ‘비움’도 기본값이 켬이면 true가 된다. 현행 셀 편집의 빈 입력→null 계약과 달라 새 행 양식에서 값을 지울 수 없다.
- 근거: 현행 `coerceCellValue`는 빈 문자열을 성공/null로 변환 (`apps/builder/src/builder/panels/datatable/grid/cellValue.ts:17-18`). ADR은 Insert·Update를 같은 양식으로 묶고 빈 칸에 기본값을 대입하지만 Update 예외를 명시하지 않는다.
- 해결 방향: Insert의 미입력=기본값 사용과 Update의 무수정=보존/명시적 비움=null을 구분한다. 필요하면 ‘기본값 사용’을 별도 상태로 두고 required는 최종 저장 값에 대해 판정한다.

### HIGH — H2: 행 객체 보존 가정이 실제 쓰기 경로와 다르고, id fallback이 다른 행을 선택한다

- 위치: `docs/adr/design/289-data-grid-row-form-breakdown.md:39`, `docs/adr/289-data-grid-row-form-column-editor-selection-actions.md:66`, `:109`, `:129`, `:143`.
- 입력·상태 → 잘못된 결과: B=`{id:"same", name:"shared", note:"B"}`, C=`{id:"same", name:"shared", note:"C"}`. B 양식을 열어 name을 `B edited`로 바꿔 둔 뒤 B를 삭제한다. 최신 목록에서 id=`same`은 C 한 행뿐이고, 이번에 쓰는 name은 열 때 값 `shared`와 같으므로 명세의 ②가 C를 수정 대상으로 돌려준다. 그 index로 실제 `set_cell`을 호출하면 **C가 `{id:"same", name:"B edited", note:"C"}`로 덮어써진다**. 열 때의 중복 여부를 저장하지 않고 최신 목록의 유일성만 확인해서는 같은 행이라는 보장이 없다.
- 실제 경로의 차이: `reduceDataOps`가 미수정 행 객체를 보존한다는 부분은 맞지만, Builder 쓰기는 거기서 끝나지 않는다. `catalogDataStore.ts:64-81`의 `toCollectionEntry`는 JSON 왕복으로 **모든 행을 복제**하고, `:301-302`에서 매 collection 쓰기마다 이 변환을 호출한다. graph commit도 바뀐 객체 필드를 소유 복사하며 (`packages/shared/src/catalog/document/graph.ts:389-407`), store는 그 entry의 mockData를 다시 투영한다 (`catalogDataRead.ts:50-51`).
- 두 번째 관찰: id 없는 A/B/C에서 B를 열고 A를 삭제하면, 최종 store의 B는 값만 같고 원래 객체와 다르다. 명세의 ①은 실패하고 id fallback도 불가능해 저장을 거절한다. 이는 G1의 ‘B 새 자리에서 저장 성공’ 및 본문의 ‘다른 행 변경에도 객체로 찾음’ 주장과 어긋난다. 삭제 Undo도 값은 복원하지만 열 때 객체 참조는 복원하지 않는다. reducer-only 테스트로는 이 경계를 검증할 수 없다.
- 해결 방향: 현행 JSON·catalog 투영 경계를 넘어서 행 객체가 유지된다는 전제를 제거한다. 현재 목록의 id 유일성만으로 대체 대상을 정하지 말고, 문서 스키마를 유지하려면 열린 시점 이후 collection 변경을 snapshot/revision으로 감지해 보수적으로 충돌 거절하는 방식을 명시한다. 더 넓은 변경 허용이 필요하면 실제 commit·Undo·재투영을 통과하는 안정 식별 계약이 먼저 필요하다. G1도 선택한 정책에 맞춘다.
- 확인된 부분: `createApplyDataChangeAction`은 `Promise.resolve(applyNow(...))`이므로 호출 순간 `get().collections`를 reduce하고 commit한다 (`dataChange.ts:1087`, `:1156-1163`). 대상 찾기와 호출 사이 await를 두지 않는다는 변경은 타당하다. 이 부분이 H2의 잔여 원인은 아니다.

### H1 — fixed (설계)
