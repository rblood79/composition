# ADR-324 Review Log

## Round 1 — 2026-11-26 (reviewer: codex)

설계 승인 보류. HIGH 6건이 남았다. 검토 기준은 `da32fc4e2`이다.

### H1. 행별 2xx만으로 접수와 저장 완료를 구별하지 못한다

PATCH가 빈 202를 반환한 뒤 작업이 실패하면 변경 표시가 먼저 사라진다. POST가 서버 키를 Location에만 담아 201로 응답한 경우에도 임시 키로 확정하면 다음 수정의 대상을 잃는다.

저장 전용 실행 결과에 status·headers·body를 보존하고 동작별 확정 조건을 정한다. 202는 완료를 확인할 때까지 보류하고, 서버 생성 키가 필요한 넣기는 ref와 실제 키를 대응한 뒤 확정한다. G3에 빈 202·204와 Location만 있는 201을 각각 둔다. [RFC 9110 §15.3.3](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.3.3)

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:131`, `packages/shared/src/collections/executeCollectionEndpoint.ts:243`이다.

### H2. 응답 유실 뒤 목록에서 행을 못 찾으면 삭제 여부를 오판한다

2쪽의 행을 고친 뒤 1쪽에서 저장하고 응답을 잃으면 1쪽 재조회에는 그 행이 없으므로 정상 반영도 충돌이 된다. 실제 DELETE가 성공해 단건 조회로 부재가 확인된 경우까지 같은 충돌 분기로 들어간다.

수정과 삭제의 판정표를 나눈다. 페이지·필터 범위 밖은 결과 확인 필요로 두고, 연결이 대상 부재를 보증하는 단건 조회에서만 삭제의 목적 상태 달성을 확정한다. G3에서 같은 키를 단건 조회와 다른 페이지 조회로 각각 확인한다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:139`, `apps/builder/src/preview/catalog/__tests__/adr310Pages.test.tsx:242`이다.

### H3. 재조회 뒤에도 유지할 수정·삭제의 기준 버전이 없다

v17에서 삭제를 예약한 뒤 주기 조회가 다른 사용자의 수정본 v18로 행을 교체한다. remove에는 seq만 있으므로 현재 행의 v18로 DELETE를 보내면 충돌 없이 타인의 수정본을 지운다. 갱신도 편집 시 버전을 보존하지 않으면 같은 문제가 있다.

최초 편집 시 원본 버전을 변경에 고정하고 보내는 요청에도 복사한다. 충돌 해결에서 사용자가 다시 저장을 선택했을 때 기준을 바꾼다. 묶음은 항목별 본문 버전, 단건은 해당 리소스의 버전 조건으로 제한한다. 하나의 If-Match는 묶음 속 행별 조건을 표현할 수 없다. [RFC 9110 §13.1.1](https://www.rfc-editor.org/rfc/rfc9110.html#section-13.1.1)

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:74`, `docs/adr/design/325-collection-runtime-store-three-layers-breakdown.md:66`이다.

### H4. 기존 즉시 저장 규칙을 알려 주는 것만으로 수동 저장의 편집 중 쓰기를 막지 못한다

Cells change에 쓰기 callEndpoint가 있는 Table에서 모아서 저장을 켜면, 두 설정 위치를 표시해도 첫 편집 이벤트가 기존 규칙을 실행한다. ACK 전부터 HC1의 원격 쓰기 0회가 깨진다. 폼 submit도 독립 진입점이다.

동시 활성 구성을 명령·로드/Publish 검증에서 거절하거나, 실행 시 충돌하는 쓰기 동작을 차단할 계약을 정한다. G1/G2는 두 위치 표시와 함께 편집 직후 원격 쓰기 0회, 명시 저장 뒤 1회를 각각 센다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:64`, `packages/shared/src/interactions/bindings.ts:124`이다.

### H5. 원격 수정·삭제가 안정적인 행 식별자 없이 활성화된다

keyField·id·key·value가 모두 없는 조회에서 첫 행의 로컬 식별자는 row-1이다. 경고 뒤 수정·삭제를 허용하면 /orders/row-1로 요청해 404가 나거나 이름이 같은 다른 서버 행에 쓴다.

로컬 편집에 대한 325 U1을 유지하면서, 원격 update/remove는 서버 식별자를 얻은 행에만 허용한다. 불가 사유와 남은 변경을 표시하고 G2에서 전송 0회를 검사한다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:64`, `packages/shared/src/collections/resolveCollectionItems.ts:349`이다.

### H6. 행 전체 PUT과 변경 필드만 검사하는 사전 조회가 다른 열을 덮어쓴다

사용자가 수량만 고친 사이 서버에서 메모가 A에서 B로 바뀐다. 저장 직전 조회에서 수량의 수정 전 값은 같으므로 통과한다. 화면에 남은 행 전체를 PUT하면 메모도 A로 돌아간다. 두 요청 사이의 경합이 없어도 발생한다.

전체 행 전송은 버전 조건을 사용하거나, 사전 조회로 얻은 원시 행에 변경 필드만 합쳐 본문을 만든다. 충돌 감지 없는 전체 전송은 다른 열까지 덮어쓸 수 있음을 표시한다. G4에서 동료가 수정한 열 B의 보존을 검사한다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:120`, `docs/adr/design/324-collection-manual-batch-save-breakdown.md:75`이다.

### 검증 범위

현재 제출 함수를 fetch 대역으로 실행했다. 빈 202, 빈 204, Location만 있는 201 모두 undefined를 반환했다. 편집·저장 표시에 관한 기존 테스트와 쪽 이동 테스트를 포함해 두 ADR의 관련 Vitest 5파일 29건이 통과했다. 제안된 저장소·수동 저장·Publish 브라우저 동작·고객 서버 및 성능 Gate는 UNVERIFIED다.

## Round 2 — 2026-11-27 (reviewer: codex)

설계 승인 보류. 기존 h2·h3·h4·h5·h6 수리 확인, h1 부분 수리, 신규 h7·h8. 현재 HIGH 3건이다.

Round 1에서 h2의 단건·부분 목록 구분, h3의 최초 버전, h4의 명령·로드·Publish 거절, h5의 행별 식별자 검사, h6의 원시 행 병합을 확인했다. h2에서 목록 전체를 근거로 부재를 판정하는 경로는 ADR-325 h6 해결에 의존한다. 원자적 검증·undo를 전제로 한 즉시 저장 규칙 동시 구성 거절은 HC1과 맞고, 전송 종료 후 202·결과 확인 대기 행만 제외하는 방식도 행별 판정과 맞는다. 보낼 때 3→5였고 응답 전에 3으로 되돌린 경우와 버전 v17/v18·다른 열 보존은 판정표 대입으로 확인했다.

### H1. 넣기에서 요청의 key가 서버가 반환한 key보다 먼저 확정된다

저장소의 crud-endpoint-stub에 id=draft-42를 POST하면 201 본문의 id는 u4였다. 단건 GET은 draft-42가 404, u4가 200이었다. 본문 Decision 5의 본문 → Location 순서와 상세 설계의 요청 key 우선 규칙이 충돌한다.

응답이 식별한 실제 행을 우선한다. 클라이언트 key는 서버가 그 key를 채택하는 연결에서만 대체값으로 쓴다. 세션 append/insert가 생성하는 item-*도 명시한 서버 key와 구별한다. 빈 202와 204의 분리는 수리됐다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:161`이다.

### H7. 행별 200 응답에 errorsPath가 있어도 변경을 확정한다

현행 submitCollectionEndpoint에 HTTP 200과 {errors:{quantity:["out of stock"]}}를 주면 EndpointSubmitError로 거절한다. 개정 표는 행별 고침에 confirmed를 주고 400·422에서만 필드 오류를 판정한다. 이 연결에 수동 저장을 켜면 거절된 칸의 표시가 사라진다.

완료 상태 코드에서도 선언된 errorsPath를 먼저 판독해 해당 변경과 오류를 남긴다. 근거는 packages/shared/src/collections/executeCollectionEndpoint.ts:254다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:150`이다.

### H8. 서버 key를 돌려주지 않은 넣기의 후속 편집을 자동 폐기한다

이름 A로 전송한 뒤 응답 전에 이름 B를 입력한다. 서버는 A를 저장하고 201을 주지만 key는 없다. serverKey=null 분기를 대입하면 B가 미저장 목록에서도 사라진다. 같은 문제가 보낸 뒤 예약한 삭제에도 생긴다.

성공한 생성 요청은 닫고, 후속 변경은 임시 행에 남겨 키 연결 또는 명시적 폐기를 제공한다. 확인 전에 임시 키로 쓰는 요청은 0이어야 한다. 폐기 건수 알림은 사용자 선택을 대신할 수 없다. 325 상세 설계 179행과 함께 맞춘다.

근거는 `docs/adr/design/324-collection-manual-batch-save-breakdown.md:164`이다.

### 검증 범위

검토 대상은 HEAD `da32fc4e2` 위의 2026-11-27 개정 설계다. 기존 함수와 CRUD 대역의 응답은 실행으로 확인했고, 새 저장소와 수동 저장의 결과는 문서의 규칙에 입력을 대입해 판정했다. 새 기능의 제품 구현·Publish 브라우저·고객 API는 UNVERIFIED다.
