## Context

### 도메인

데이터 층 · 저작 (ADR-284 의 연장). 코드의 JSX 요소 이름 · prop 이름은 D1 (RAC 컴포넌트) · D2 (S2 prop 표면) 의 이름을 그대로 쓰고 (생성기가 이미 그렇다 — `writeNode` 가 catalog type 을 `react-aria-components` import 로), 시각 값 (D3) 은 코드에 나오지 않는다. 경계 교차 없음 — 역변환은 코드에 나온 것만 문서에 쓰고, 코드에 없는 D3 값 (style · layout · 크기) 은 건드리지 않는다.

### 현재 (실측 2026-10-27, main `29af87ee0`)

### 사용자와 인계 상황

- 사용자 (비개발자, 기능 단위로 생각 — 메모리 `user-non-developer-list-first-mental-model`) 가 코드 보기를 「레퍼런스와 같은 코드」 로 받았으면 그 코드를 고치는 것도 레퍼런스처럼 되어야 한다고 기대한다. 자리 밖 거절은 「오류」 로 읽혔다.
- 개발자 인계 (ADR-284 §8a): 넘겨받은 개발자가 코드를 고쳐 문서에 반영하는 길이 지금은 자리 5 종뿐이다. 요소 하나 더하기 · 조건 하나 더하기 · 변수 하나 더하기는 캔버스 · 패널로 돌아가야 한다.
- AI 의 코드 입력 (연구 §8.5 의 4 번째 효용): AI 가 RAC 코드를 내면 빌더가 문서로 환원되는 부분만 받는다 — 이것도 같은 역변환이다 (이 ADR 은 그 층을 만들고, AI 패널 연결은 범위 밖).

### 제약

- **Hard — 닫힌 어휘 = 생성기 어휘와 1:1**: 역변환이 읽는 모양은 `generate.ts` 가 내는 모양 전부이고 그 밖은 없다 (연구 §3 어휘표 · 부록 A). 임의 함수 호출 · 계산식 · 새 hook · 조건 밖 JS 는 받지 않는다 (사용자 결정 10-26 · 10-27 · 원칙 「불가 → 스크립트 escape 금지」). 생성기 어휘가 늘면 역변환도 같은 커밋에서 는다 (왕복 게이트가 강제).
- **Hard — 왕복 불변식**: 문서 → 코드 → 문서가 **변경 0** 이어야 한다 (어떤 문서에서든 생성 코드를 그대로 Apply 하면 명령 0). 수용 집합 5 종 (284 breakdown §7a) 과 생성 golden 5 를 역방향으로도 돌린다.
- **Hard — 차이로 적용**: 코드에 없는 것 (id · 스타일 · 레이아웃 · 크기 · override) 은 보존. 바뀐 것만 명령으로 — 요소 추가는 팔레트와 같은 경로 (origin instance), 삭제는 삭제 명령 (참조하는 규칙 · 파생 보기 포함 — 284 의 `removeUnreadDerivedViews`), 이동은 `moveNodes`, 그 밖은 기존 명령. Apply 한 번 = history 한 항목 (Undo 한 번) · 저장 · Preview 는 기존 파이프라인.
- **Hard — 조용한 실패 금지**: 받지 못하는 줄은 줄 번호 · 이유 · **대신 할 것** (「요소의 크기 · 색은 Design 패널에서」 · 「이 식은 조건 비교 표 밖 — 비교 방식 N 가지」) 을 한국어 (i18n KO/EN) 로. 한 줄이라도 거절이면 전체 적용 0 (지금과 같음 — 부분 적용으로 문서와 코드가 어긋나지 않게).
- **Hard — 마이그레이션 코드 0** (사용자 지시 2026-10-14): 저장 형식 변경 없음 (contract 50 그대로). 역변환은 문서 모델을 바꾸지 않는다.
- **Hard — 번들**: 파서 · 역변환은 Builder 의 lazy chunk (「코드」 패널 편집 진입 때 `import()`) · Preview 증분 0 (Preview 는 코드 보기를 모른다). Builder initial Δ ≤ +1 KB gz (패널 진입 코드만). 상한 ADR-201 재승인 (Builder ≤ 1,390,000 · Preview ≤ 320,000, 만료 2026-11-25).
- **Hard — 안전**: 코드는 파싱만 하고 **실행하지 않는다** (`eval` · `new Function` 0). 문서에 스크립트를 저장하지 않는다.
- **Hard — 편집기 (확인 항목 3)**: 「코드」 패널의 편집은 CodeMirror 6 (lazy chunk · Builder 전용 · worker 없음). 편집 연산 (`ChangeSet`) 이 identity 의 1차 근거다 — 편집기 없이 문자열만 받는 경로는 두지 않는다 (textarea 폴백 없음 · 편집기 chunk 를 못 불러오면 읽기 전용 + 안내). 자동완성 · 스니펫 · 줄 안 진단은 **닫힌 어휘에서만** 채운다 (임의 JS 제안 0 — TS 언어 서비스 류 미사용).
- **Soft**: 「적용 · 취소」 흐름은 유지. 자리 강조는 「확실히 되는 것」 표시로 남긴다.

## Alternatives Considered

### 대안 A: 자리 (slot) 를 늘려 요소 추가 · 삭제도 자리로

- 설명: 지금의 projection 편집을 유지하고, 자리 종류를 늘린다 — 「요소 사이의 빈 자리」 (여기에 `<Text>…</Text>` 를 적으면 추가) · 「요소 전체」 (지우면 삭제) · 「prop 목록」 · 「변수 선언 블록」 · 「filter 항 사이」. 파서 없음, 텍스트 diff 만.
- 근거: 지금 코드와 가장 가깝다. 그러나 자리는 「생성된 텍스트의 고정 위치」 라 **새 요소의 자식 · 새 변수를 읽는 규칙 · 새 조건의 변수** 처럼 자리가 서로를 가리키는 변경을 표현하지 못한다 (추가한 `useState` 와 추가한 `onChange={setX}` 를 짝지으려면 결국 코드를 읽어야 한다). 자리 종류마다 regex 문법이 하나씩 생겨 생성기와 둘로 갈라진다.
- 위험: 기술(M — 자리 간 의존을 regex 로) / 성능(L) / 유지보수(**H** — 어휘마다 자리 문법 · 생성기와 이중) / 마이그레이션(L)

### 대안 B: 코드를 파싱 → 생성기 어휘의 역문법으로 「의도 트리」 → 현재 문서와 차이 → 기존 명령 한 트랜잭션 (채택)

- 설명: 「코드」 패널 편집 진입 때 lazy 로 ESTree 파서를 부르고 (`@babel/parser`, JSX + TS), AST 를 **생성기가 내는 모양의 역문법** 하나로 읽어 「의도 트리」 (page 의 요소 트리 + 변수 + 보기 조건 · 정렬 · 묶기 + 규칙 + API 호출 — 문서 스키마의 부분집합, id 없음) 를 만든다. 생성기가 현재 문서에서 만든 의도 트리와 대조해 (요소는 위치 + 종류 + 글자 + prop 로 짝짓기, 변수는 이름, 조건은 필드 · 비교 · 값, 규칙은 노드 + When) 차이를 기존 명령 목록으로 바꾸고 한 트랜잭션 (`compose`) 으로 실행한다. 역문법 밖 노드 (임의 식 · 모르는 hook · 모르는 컴포넌트) 는 줄 · 이유 · 대안으로 거절하고 전체 적용 0.
- 근거: 판정 스크립트가 이미 같은 방식 (TypeScript 파서 → 사실 추출) 으로 레퍼런스와 생성 코드를 비교한다 — 역문법은 그 추출기의 「문서 쪽」 판이다. 어휘 하나 = 생성기 emit 하나 = 역문법 read 하나 = 판정 사실 하나로 한 표에 묶인다 (왕복 게이트). 코드에 없는 것은 「차이」 에 나오지 않아 자동으로 보존된다.
- 위험: 기술(M — 역문법의 짝짓기 규칙 · 파서 안정성은 높음) / 성능(M — 파서 ~100 KB gz, lazy · Builder 만 · Preview 0) / 유지보수(M — 어휘표 하나 · 왕복 게이트가 생성기 변경을 역문법에 강제) / 마이그레이션(L — 스키마 0)

### 대안 C: 코드 전체를 문서로 다시 만들기 (코드 = 정본)

- 설명: 코드를 파싱해 page 를 새로 생성하고 기존 page 를 버린다.
- 근거: 역변환은 단순해지나 코드에 없는 것 (id · 스타일 · 레이아웃 · 크기 · override · 슬롯) 이 전부 사라진다 — 사용자가 Design 패널에서 한 일이 Apply 한 번에 지워진다. 코드 = 정본은 10-26 결정 (「code view 는 문서를 읽고 고치는 창」) 과 반대다.
- 위험: 기술(**H** — 손실 없는 재생성이 불가) / 성능(L) / 유지보수(**H** — 문서의 모든 필드를 코드에 실어야 함) / 마이그레이션(**H** — 문서 손실)

### 대안 D: 어휘 밖 코드를 스크립트로 저장해 Preview · Publish 에서 실행

- 설명: 역문법이 못 읽는 부분을 문자열로 문서에 저장하고 런타임이 실행한다.
- 근거: 사용자가 기각했다 (10-27 확인 항목 1, 10-26 「자유 코드 escape 아님」). walkthrough A 경로 (사람마다 다른 결과 · 코드 층 조용한 실패) 가 돌아오고, Publish 에 사용자 코드가 들어가며 (보안 · 번들), 패널 · Canvas 가 그 부분을 못 본다.
- 위험: 기술(**H** — 실행 샌드박스) / 성능(M) / 유지보수(**H**) / 마이그레이션(**H** — 스키마 · 실행 모델 변경)

## Decision

**대안 B.** 「코드」 패널의 편집을 자리 5 종에서 **생성기 어휘 전체** 로 넓힌다 — 요소 (추가 · 삭제 · 이동 · 글자 · prop) · 변수 (추가 · 삭제 · 이름 · 시작값) · 보기 (조건 추가 · 삭제 · 비교 · 값 · 「또는」 묶음 · 건너뜀 guard · 정렬 · 묶기 · 집계) · 규칙 (When · Do 목록 — `setX` · list 명령 · toast · endpoint 호출) · API (`useAsyncList` 의 요청 매개변수 · 본문 · 응답 경로). 코드는 파싱만 하고, 생성기 어휘의 역문법으로 「의도 트리」 를 만들어 현재 문서와의 차이만 기존 명령으로 적용한다.

1. **파서** (사용자 결정 4 — Phase 0 실측 뒤 2026-10-27): **`@lezer/javascript`** (`dialect: 'jsx ts'`) 하나 — 편집기 (CodeMirror 6) 가 이미 싣는 파서라 추가 번들 0, 편집기와 Apply 가 같은 구문 트리를 읽는다. 오류는 던지지 않고 오류 노드로 표시되므로 역문법이 오류 노드 = `unparsable` 거절로 읽는다. `@babel/parser` (+78.9 KB gz) 는 추가하지 않는다. acorn 은 생성 코드의 TS 구문 (`import {type Selection}` · `useState<SortDescriptor>()`) 을 못 읽어 부적합, typescript 는 크기로 부적합.
2. **역문법 = 어휘표 하나**: 생성기의 emit 지점마다 역문법 read 한 줄이 짝으로 있는 표 (breakdown §1a) — 생성기 · 역문법 · 판정 스크립트의 사실 추출기가 같은 표를 읽는다. 표에 없는 AST 노드는 거절.
3. **identity 는 내용과 분리 — 편집기가 어느 범위를 고쳤는지 알려 준다** (리뷰 round 1 · 2 h1): 생성기가 코드와 함께 **anchor 표** (`CodeViewResult.anchors` — JSX 요소 · 변수 선언 · `filter` 항 · 정렬 · 규칙 핸들러 · `useAsyncList` 블록 · 파생 구문마다 「텍스트 범위 → 문서 id / 주소」) 를 낸다. 편집기 (CodeMirror 6) 는 anchor 를 **편집 연산마다 따라가는 범위** (`RangeSet` · `mapPos` · 통째 삭제 추적) 로 들고 있어, Apply 때 각 anchor 의 결말을 **추측 없이** 안다 — 범위가 남아 있으면 (안의 글자 · prop · 자식이 바뀌었어도) **같은 id · 수정**, 범위가 통째로 지워졌으면 **삭제**, anchor 밖에 입력된 텍스트는 **추가**. 줄 단위 LCS 는 쓰지 않는다. 한 줄짜리 `<Text>A</Text>` 안에서 A 를 B 로 치면 anchor 가 남아 수정이고 (id · 스타일 · 참조 보존), 같은 코드 둘 중 둘째 줄을 지우면 둘째 anchor 만 지워진다 (tie-break 없음). **붙여넣기로 anchor 를 통째로 덮은 구간** (선택 → 붙여넣기 · 전체 교체) 은 편집기가 「이 anchor 들이 지워지고 이 텍스트가 들어왔다」 만 알므로 그 구간 안에서 대응을 하되 **순서는 identity 의 근거가 아니다** (리뷰 round 3 h1). 차례 — ① **정규화 JSX 가 같은 짝 먼저**: 지워진 anchor 의 baseline 정규화 텍스트와 새 요소의 정규화 텍스트가 같으면 같은 id, 자리가 달라졌으면 `moveNodes` — 빨간 `<Text>A</Text>` · 파란 `<Text>B</Text>` 두 줄을 골라 B · A 순서로 붙여넣으면 파란 B · 빨간 A 가 이동한다 (빨간 B · 파란 A 가 아니다). 같은 텍스트가 양쪽에 같은 수면 순서대로 짝짓고 (코드 결과가 같아 구별할 것이 없다), 수가 다르고 그 모양의 후보 (그 부모의 **같은 정규화 모양 요소 전부** — 이미 남아 있는 anchor 포함) 의 문서 상태 (스타일 · 규칙 · 자식 · 참조) 가 다르면 `ambiguousIdentity`. ② 남은 지워진 anchor 와 남은 새 요소만 **수정 대응**: 그 부모 안에서 종류가 같은 남은 것이 **양쪽 다 하나** (1:1) 일 때 같은 id · 수정. anchor 쪽이 둘 이상이면 문서 상태가 같을 때만 순서대로, 다르면 `ambiguousIdentity`; 새 요소 쪽이 둘 이상 (한 줄을 두 줄로 교체 — 어느 줄이 원래 것인지 코드가 말하지 않음) 도 `ambiguousIdentity` 로 전체 적용 0 (「붙여넣기로 바뀐 구간에 구별되지 않는 요소가 있습니다 — 그 줄만 고치세요」). ③ 남은 것은 삭제 · 추가. 부모 간 이동은 ① 과 같은 규칙 — 「통째 삭제된 anchor」 와 「다른 곳의 추가 텍스트」 가 정규화 텍스트로 1:1 일 때 `moveNodes`, N:1 은 후보 문서 상태가 같을 때만. 어느 단계든 한 요소에 문서 상태가 다른 후보가 둘 이상이면 거절한다 — 임의로 하나를 고르지 않고, 모호성 검사를 수 감소에만 두지 않는다. 코드에 `id` prop 은 내지 않는다 (코드 = 레퍼런스 모양, 10-26). 변수 · 조건 · 규칙 · 파생 구문의 anchor 도 같은 규칙.
4. **편집 세션 = baseline** (리뷰 round 1 h2): 「코드 고치기」 진입 때 `{projectId, pageId, baselineRevision, baselineResult (code · anchors · intent), draft}` 를 잡는다. 차이는 **baseline 의 의도 트리 ↔ 편집본** 으로 계산하고, Apply 직전 (lazy parse 가 끝난 뒤) 현재 문서의 `pageId` · revision 이 baseline 과 다르면 적용 0 — 「편집을 시작한 뒤 문서가 바뀌었습니다 (Canvas 편집 · 페이지 전환). 초안은 남아 있습니다 — 「다시 불러오기」 로 지금 코드와 나란히 봅니다」. 3-way 자동 병합은 하지 않는다. 트랜잭션은 `baselineRevision` 을 기대 revision 으로 실행해 (`REVISION_CONFLICT`) 이중으로 막는다 — 실행 직전 revision 을 새로 잡는 재시도 경로는 쓰지 않는다. 페이지를 바꾸면 그 page 의 초안은 보관만 하고 다른 page 에 적용하지 않는다.
5. **적용**: 차이 → 명령 목록 → `compose` 한 트랜잭션 · history 한 항목. 요소 추가는 팔레트의 origin instance 경로 (사용자 결정 1), 삭제는 참조하는 규칙 · 파생 보기와 함께 (사용자 결정 3). Apply 뒤 코드는 문서에서 다시 생성해 보여 준다 (사용자가 적은 텍스트를 그대로 두지 않는다 — 정본은 문서).
6. **거절 — 모든 줄이 검증 대상** (리뷰 round 1 m3): 코드 전체가 파싱되어야 하고 모든 식별자가 알려진 이름 (변수 · setter · collection · hook · 컴포넌트) 이어야 한다. 역문법 밖 노드 · 짝지을 수 없는 참조 (없는 변수 · 없는 필드 · 없는 collection) · 모호한 identity · baseline 불일치 · 문서가 거부한 명령 (검증 오류) 은 줄 · 이유 · 대안을 모아 보여 주고 전체 적용 0. **파생 구문** (import · `useFilter` · `useCollator` · `useEffect(… reload …)` · `let people = users.items` · 주석) 은 문서 변경 계획에서만 빠질 뿐 검증에서는 빠지지 않는다 — 소유자 (collection · 변수) 와 함께 canonical AST 와 같거나 (공백 · 주석 · import 순서 무시) 소유자가 삭제되어 함께 사라진 경우만 받고, 그 밖의 변경 (effect 본문을 임의 호출로 · import 원본 경로 변경) 은 `derivedChanged` 로 거절 — 「이 줄은 문서에서 만들어집니다. 되돌리거나, 데이터 원본은 `items={…}` 에서 바꾸세요」. 혼합 입력 (effect 임의 변경 + 허용되는 `<Text>` 추가) 은 명령 0. 문구는 i18n KO/EN.
7. **편집기 · 자동완성 · 스니펫 · 줄 안 진단** (확인 항목 3): CodeMirror 6 (JSX · TS 강조 — lezer · 접기 · 괄호 · 검색 · 다중 커서). 자동완성 소스는 **어휘표에서만** — 팔레트 요소 이름 (RAC import 가능한 것) · page 변수 · setter · collection 이름 · `item.` 뒤 필드 key · `contains` 류 비교 · 비교 연산 · `useDragAndDrop` 핸들러 이름. 스니펫은 **저작 동작 하나 = 코드 묶음 하나** — 「검색 추가」 (useState + SearchField + filter 항) · 「라디오로 거르기」 · 「정렬 따라가기」 · 「결과 수 표시」 · 「API 요청 매개변수」 — 스니펫으로 만든 문서는 패널의 같은 동작이 만든 문서와 같다 (단언 테스트). 거절은 목록이 아니라 **줄 안 진단** (lint 밑줄 · 마우스 올리면 이유 · 대안) 으로도 보이고, 입력 중 300 ms 뒤 dry-run 으로 미리 판정한다 (Apply 전에 안다). 자리 강조는 「확실히 1:1 인 자리」 표시로 남긴다.

**기각 사유**: A — 자리 간 의존 (새 변수 ↔ 새 규칙 ↔ 새 조건) 을 텍스트 자리로 표현할 수 없고 어휘마다 regex 문법이 생겨 생성기와 이중이 된다. C — 코드에 없는 문서 필드 (스타일 · 레이아웃 · id · override) 를 잃는다. D — 사용자 기각 (자유 코드 escape 아님).

**위험 수용 근거**: B 의 잔존 M 은 (성능) 파서가 lazy · Builder 전용이라 initial 에 안 실리고, (기술) 짝짓기 규칙은 왕복 불변식 게이트 (문서 → 코드 → 명령 0) 와 수용 집합 5 종의 역방향 판정으로 묶이며, (유지보수) 어휘표 하나가 생성기 · 역문법 · 판정을 같이 묶어 어느 하나만 바뀌면 게이트가 RED 다.

## Consequences

### Positive

- 코드 보기가 「읽는 창」 에서 「고치는 창」 으로 — 요소 · 변수 · 조건 · 규칙 · API 를 코드로 더하고 지울 수 있고, 결과는 캔버스 · 패널에서 한 것과 같은 문서다 (Undo 한 번 · 저장 · Preview 그대로).
- 어휘표 하나가 생성기 · 역문법 · 판정 스크립트를 묶어, 생성기가 바뀌면 역문법 · 판정이 같은 커밋에서 바뀐다 (왕복 게이트).
- 개발자 인계 · AI 코드 입력의 공통 층이 생긴다 (연결은 별도 결정).

### Negative

- CodeMirror 6 패키지 (lazy 168.5 KB gz 실측 — lezer 파서 포함, Builder 전용). 역문법은 lezer 의 구체 구문 트리 (CST) 를 읽어 ESTree 보다 코드가 길다 (결정 4 의 대가).
- 생성기에 어휘를 더할 때마다 역문법 · 판정 · 어휘표가 함께 바뀐다 — 한 항목이 세 곳.
- 코드에 없는 것 (스타일 · 레이아웃 · 슬롯) 은 여전히 코드로 못 고친다 — 거절 문구가 Design 패널로 안내한다. 이것은 10-26 결정 (코드 = 데이터 층의 RAC 코드) 의 결과이지 결함이 아니다.
