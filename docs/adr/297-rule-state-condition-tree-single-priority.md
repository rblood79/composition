## Context

### 도메인

- **D3** (시각 스타일) 안의 결정이다. 바꾸는 것은 `COMPONENT_RULES_TABLE` 이 상태별 값을 **적는 형식** 과 두 consumer (Builder Skia · Preview/Publish CSS) 가 그 값을 **고르는 판정기**. 값 자체 · 토큰 이름 · 테마 출력 (`resolveThemeSnapshot`) 은 바꾸지 않는다.
- **D1 · D2 경계 이동 없음**. 조건 어휘 (`isHovered` · `isSelected` · `isDisabled` …) 는 RAC render prop 이름이고 (D1 이 주는 사실을 소비), D2 prop (`variant` · `fillStyle` · `isQuiet` · `staticColor` · `isEmphasized`) 은 binding `accepts` 그대로. 조건 트리는 DOM 구조 · ARIA 를 지정하지 않는다 — compiler 가 내는 선택자는 RAC 가 이미 찍는 `data-*` 다.
- **Generator 확장 선언** (adr-writing 선차단 #2): `generate-css.ts` + `CSSGenerator.ts` 의 상태 분기 (variant 안 `&[data-hovered]` … rootSelectors) 를 **새 compiler 가 대체** 한다. Generator 가 자식 selector · variant emit 을 지원하는가 — 지금도 한다 (`CSSGenerator.ts:296-685` 출력 순서) 이고, 이 ADR 은 그 출력을 트리에서 유도하도록 바꾼다. 생성 CSS 103 파일은 커밋돼 있어 (`packages/shared/src/components/styles/generated/`) diff 가 곧 회귀 지표다.

### 문제

rule 은 상태를 **5가지 방식** 으로 나눠 적는다 (연구 §2.1): ① `fill.<style>.<state>` ② `colors.textHover` · `selected*` · `emphasizedSelected*` 접미사 키 ③ `structure.states.{hover,…}` ④ `composition.rootSelectors` 의 `&[data-*]` 키 56 ⑤ variant 이름 `selected` · `selectedEmphasized`. 이 값들 사이의 **우선순위는 데이터에 없다**. Canvas 는 `resolveCatalogPaint.ts:79-143` 의 삼항 사슬이, DOM 은 `CSSGenerator.ts:296-685` 의 출력 순서 + cascade specificity 가 각자 정한다. 그 결과 상태 11종 중 **9종의 우선순위가 두 쪽에서 다르다** (연구 §2.3 — hover · pressed · selected · disabled · invalid · staticColor(hover) · quiet · outline · subtle. 같음은 emphasizedSelected 하나, DOM 전용은 focusVisible · touch). 예: Canvas 는 selected > quiet > outline, DOM 은 같은 0-3-0 블록이 뒤에 나오는 순서라 subtle > quiet > outline · selected. Canvas 는 invalid 가 늘 이기고 DOM 은 hover · focus 가 specificity 로 invalid 를 이긴다.

D3 대칭 원칙 (`ssot-hierarchy.md` §1 「두 경로가 동일 SSOT 로부터 동일 시각 결과」) 이 **구조적으로 보장되지 않고** 사람이 두 코드를 맞춰야 하는 상태다. ADR-295 가 값을 S2 에 맞춘 뒤 남은 비대칭의 큰 몫이 이 우선순위 층이다.

### Hard constraints

- **생성 CSS diff 0** (Phase 1 · 2, 형식 전환 단계): 조건 트리로 옮긴 rule 의 compile 결과가 현행 `CSSGenerator` 출력과 선언 단위로 같다 — 선언 순서 · 선택자 · 값. 우선순위를 **바꾸는** 단계 (Phase 3) 만 diff ≠ 0 이고 그때는 before/after 를 적는다 (ADR-295 R3 교훈 — 「Δ 0」 어법을 값 변경 단계에 쓰면 vacuous).
- **Skia paint 동일** (Phase 1 · 2): evaluator 결과 == 현행 `resolveCatalogPaint` 결과 (팔레트 전수 × 상태 5 × fillStyle × staticColor × quiet 조합, 숫자 비교).
- **성능**: evaluator 는 Canvas 프레임 경로 (`canvasBinding.ts:822, 869` → `rulePaint`) 에 있다. 결정적 카운트 ratchet (`pnpm gate:perf-ratchet`, ADR-246) 과 `perf:baseline --lane frame --fixed-inputs` 로 호출 수 · 프레임 시간 p95 가 전환 전과 같다 (상한: 현행 + 0). 트리 평가 결과는 (rule · 조건 집합) 키로 memo.
- **번들**: Builder initial gz ≤ 1,390,000 · Preview ≤ 320,000 B (ADR-201 상한, 2026-11-25 만료) — compiler 는 빌드 스크립트 (Preview 번들 0), evaluator 는 shared 런타임 (Preview 에도 실림 — Preview DOM 은 evaluator 를 쓰지 않으므로 tree-shake 로 0 이 목표, 측정).
- **문서 스키마 무변경** (F1 · F2): 문서 · instance override · unlock fork · 패널 쓰기 경로는 손대지 않는다. 투영기 3 만 새 형식을 읽는다.
- **마이그레이션 코드 금지** (개발 단계 — 메모리 `feedback-no-document-migration-code-dev-stage`): 문서 쪽이 안 바뀌므로 해당 없음. 표 변환은 codemod 1 회 + 커밋.

### Soft constraints

- 표는 직접 편집 정본 (ADR-912) — codemod 가 낸 결과를 손으로 다듬는 자리가 남아야 한다. 조건 트리는 사람이 읽을 수 있는 중첩 객체여야 하고 (S2 `Button.tsx` 모양), 별도 DSL 문자열 금지.
- Styles 패널 미리보기 (F8 ④) 도 같은 evaluator 를 쓰게 해 패널 · Canvas · DOM 삼자 일치.
- `.button-base` · 수동 CSS 층 (F8 ③) 은 **이 ADR 의 Phase 3 범위** 에 넣되 사용자 결정으로 폭을 정한다 (아래 결정 2).

## Alternatives Considered

### 대안 A: 현행 5 방식 유지 + 우선순위 대조 테스트만 추가

- 설명: 형식은 그대로 두고, Canvas `resolveCatalogPaint` 와 생성 CSS 를 상태 조합별로 대조하는 정적 테스트 (조합 × 컴포넌트) 를 만들어 「다름 9」 를 하나씩 손으로 맞춘다.
- 위험: 기술 LOW / 성능 LOW / 유지보수 **HIGH** (우선순위가 여전히 코드 두 곳 — 새 상태 · 새 컴포넌트마다 두 곳 수정 + 테스트 행 추가, 5 방식도 그대로) / 마이그레이션 LOW
- 근거: 지금까지의 방식이다. ADR-923 (34 라운드) · ADR-295 후속 11 건이 이 층의 비대칭을 개별 수리로 좇았다.

### 대안 B: 조건 트리 하나 + evaluator (Canvas · 패널) + compiler (CSS) — S2 style macro 의 **형식** 만 (채택)

- 설명: rule 의 상태 관련 속성 (`backgroundColor` · `color` · `borderColor` · `borderWidth` · `opacity` · `boxShadow` …) 을 S2 모양의 조건 트리로 적는다 — `backgroundColor: { fillStyle: { fill: { variant: { accent: { default, isHovered, isPressed } } }, outline: { default: 'transparent', isHovered: … } }, isDisabled: …, isStaticColor: { … } }`. 우선순위 = 트리 키 순서 (F10 의 S2 규칙 그대로). evaluator 는 조건 집합을 넣어 값 하나를 돌려주고 (Canvas · Styles 패널), compiler 는 같은 트리에서 선택자 블록을 낸다 (생성 CSS). 조건 어휘는 Canvas 가 그릴 수 있는 것으로 닫는다: `variant` · `size` · `fillStyle` · `isHovered` · `isPressed` · `isFocusVisible` · `isDisabled` · `isSelected` · `isEmphasized` · `isStaticColor` · `isQuiet` · `isInvalid` · `touch`. DOM 전용 조건 (`forcedColors` · `:focus-within` · 형제 선택자) 은 `domOnly` 가지로 표시해 compiler 만 읽는다.
- 위험: 기술 **MEDIUM** (evaluator · compiler 신규 — 단 S2 가 같은 구조를 1,343 줄 macro 로 증명, 우리는 atomic class 없이 선택자 블록만 내므로 더 작다) / 성능 **MEDIUM** (Canvas 프레임 경로에 트리 평가 — memo 로 (rule · 조건) 당 1 회) / 유지보수 LOW (우선순위 한 곳 · 타입 1 벌 · 어댑터 0) / 마이그레이션 **MEDIUM** (표 14,484 줄 codemod · 정적 테스트 oracle 경로 문자열 ~65 개 · 투영기 3 · 소비자 ~40 파일 — 단 문서 스키마 0)
- 근거: S2 `Button.tsx:105` · `style-macro.ts:558` (F10). Panda · vanilla-extract 의 `recipe` / `styleVariants` 도 같은 「조건 → 값」 트리이고, 런타임 판정기와 정적 생성기 두 소비자를 둔다.

### 대안 C: S2 `style()` macro 를 그대로 — 빌드 때 atomic class, Skia 는 생성 CSS 를 파싱

- 설명: rule 을 S2 macro 호출로 바꾸고 Skia 가 생성된 class 규칙을 읽어 paint 로 변환.
- 위험: 기술 **CRITICAL** (Skia 가 CSS 를 읽는 구조 — `ssot-hierarchy.md` §6 「CSS 가 기준」 금지 패턴, ADR-295 대안 E 와 같은 사유) / 성능 MEDIUM / 유지보수 HIGH / 마이그레이션 HIGH
- 근거: ADR-295 대안 E 기각 기록.

### 대안 D: 트리는 도입하되 compile 만 — Canvas 는 compiler 가 내는 평평한 상태 표 (JSON) 를 읽는다

- 설명: 빌드 때 트리 → (조건 조합 → 값) 전개표를 JSON 으로 내고 Canvas 는 그 표를 조회. 런타임 evaluator 없음.
- 위험: 기술 LOW / 성능 LOW (조회만) / 유지보수 **MEDIUM** (빌드 산출물이 하나 늘고, 조합 폭발 — 조건 13 × variant × size 전개표가 rule 당 수백 행) / 마이그레이션 **HIGH** (Styles 패널 · instance 미리보기가 빌드 산출물에 묶임 · 사용자 override 를 나중에 트리로 받을 길이 막힘)
- 근거: 조합 전개는 S2 가 피한 방식 (런타임에 render prop 으로 class 를 고른다 — F10).

## Decision

**대안 B.** 위험 수용 근거: evaluator · compiler 는 S2 가 이미 증명한 구조의 축소판이고 (조건 ≤ 13, atomic class 없음), 성능은 memo 로 (rule · 조건 집합) 당 1 회 평가라 현행 삼항 사슬과 같은 차수이며 ratchet 이 잡는다. 마이그레이션은 문서 스키마 0 이라 codemod + 커밋 1 회로 끝나고, 전환 단계의 회귀 기준 (생성 CSS diff 0 · Skia paint 동일) 이 기계적이다.

기각 사유 — A: 우선순위가 여전히 두 곳 (문제 미해결). C: Skia 가 CSS 를 읽는 구조 (대칭 원칙 위반, 295-E 와 같음). D: 조합 전개 + 패널 · override 가 빌드 산출물에 묶임.

### Decision 1 — 형식: 속성 → 조건 트리, 우선순위 = 키 순서

- rule 의 상태 의존 속성은 `ConditionalValue<T> = T | { [condition]: ConditionalValue<T> }` 트리로 적는다. 키는 `default` 와 조건 이름. S2 규칙 (F10) 그대로 — 같은 깊이에서 **나중 키가 이기고**, 부모의 나중 조건이 자식 가지의 조건을 덮는다.
- 조건 어휘 (닫힌 집합, 타입으로 고정): `variant` · `size` · `fillStyle` (값 분기) · `isHovered` · `isPressed` · `isFocusVisible` · `isDisabled` · `isSelected` · `isEmphasized` · `isStaticColor` · `isQuiet` · `isInvalid` (boolean) · `touch` (기기 — ADR-295 Decision 2 의 조건과 같음).
- **DOM 전용 조건 어휘** (리뷰 round 2 h3 — 닫힌 두 번째 집합, 타입 `DomCondition` 으로 분리): `isFocused` · `isFocusWithin` (마우스 포커스 — Canvas 가 안 그리지만 DOM 이 지원하는 상태, 표에 `&:is([data-focused],[data-focus-within])` 12 건) · `isDropTarget` · `isEmpty` · `forcedColors` · `inPopover`. 이 조건들은 **트리 안의 보통 조건과 같은 자리** 에 적는다 — `borderColor: { isHovered: "{border-hover}", isFocused: "{accent-content}", isInvalid: { default: "{negative}", isFocused: "{negative}" } }`. 우선순위는 키 순서 그대로 (invalid 가 focus 보다 뒤 = 둘 다 참이면 invalid — 현행 `&[data-invalid]:is([data-focused],…)` 블록의 뜻). compiler 는 선택자 맵 (`isFocused` → `:is([data-focused],[data-focus-within])`) 으로 `:where()` 안에 낸다. evaluator 는 Canvas 의 조건 집합이 이 키를 **절대 포함하지 않으므로** 거짓 가지로 지나간다 — 코드 분기 없이 어휘 분리만으로 「Canvas 가 못 그리는 것」 이 드러난다 (R4). 현행 rootSelectors 의 `:not([data-focus-within])` 부정은 트리에서 불필요하다 — hover 뒤에 focus 를 적으면 「focus 아닐 때만 hover」 가 순서로 표현된다.
- **`domOnly` raw 선택자 가지** 는 **다른 대상** (자손 · 형제 · `::before` — ListBox 구분선 `…:has(+[data-selected])` · Toast `& > .toast-close-button` · Switch `.indicator::before`) 에만 쓴다. `&` 자신을 대상으로 하는 상태 분기는 전부 위 두 어휘로 적는다. compiler 는 트리 블록 뒤에 선언 specificity 그대로 낸다 (대상이 달라 트리와 cascade 로 겹치지 않는다).
- 5 방식 ① ~ ⑤ 는 전부 이 트리로 흡수된다: ① `fill.<style>.<state>` → `backgroundColor: { fillStyle: {…: { isHovered … } } }` · ② 접미사 키 → `color` · `borderColor` 의 같은 트리 · ③ `structure.states` → `opacity` · `outline` · `boxShadow` 트리 · ④ rootSelectors 의 `&` 대상 상태 키 (quiet · invalid · disabled · hovered · focused · focus-within · focus-visible) → 트리 (공통 조건 + DOM 전용 조건), 다른 대상 (자손 · 형제 · pseudo) → `domOnly` · ⑤ variant 이름 `selected` · `selectedEmphasized` → `isSelected` · `isEmphasized` 조건. F6 의 죽은 경로 (`selectedHover` · `selectedPressed`) 는 트리에서 `isSelected: { isHovered }` 로 표현 가능하되 **값은 넣지 않는다** (0 건 그대로).
- 값 leaf 형식은 현행 그대로 (TokenRef · `var(--…)` · helper 호출 · `color-mix` — 연구 §1.3). 값은 바꾸지 않는다 (ADR-295 몫).

### Decision 2 — 두 소비자 + 패널: evaluator 와 compiler 는 한 모듈의 두 함수

- `packages/shared/src/catalog/rule/conditionTree.ts` (가칭) — `evaluate(tree, conditions): T | undefined` 와 `compile(tree, property, selectorMap): CssBlock[]`. 같은 순회 코드가 두 함수의 뼈대다 (순서 규칙을 한 곳에).
- Canvas: `resolveCatalogPaint` 의 삼항 사슬 (`:79-143`) 과 `rulePaint` 의 variant 교체 (`:290-309`) · `quietStyles` · `disclosureBorders` 의 축소판 매처 (F7) 를 evaluator 호출로 바꾼다. 조건 집합은 `displayState` (F5) + props (`variant` · `fillStyle` · `isQuiet` · `staticColor` · `isEmphasized` · `_fieldInvalid`) 에서 만든다.
- DOM: `CSSGenerator` 의 variant 블록 · outline · quiet · subtle · `states` · rootSelectors 상태 키 출력 (`:296-685`) 을 compiler 출력으로 바꾼다. 선택자 맵은 한 표 (`isHovered` → `[data-hovered]`, `isFocusVisible` → `[data-focus-visible]`, `touch` → `@media` + `:root[data-catalog-touch]` (295) …).
- **compiler 의 specificity 계약 (리뷰 round 1 h1)**: CSS cascade 는 source order 보다 specificity 를 먼저 비교하므로 ([css-cascade-5 §cascade-sort](https://www.w3.org/TR/css-cascade-5/#cascade-sort)) 조건 선택자를 날것으로 내면 트리 순서가 cascade 와 갈린다 — `borderColor: { isQuiet: { isHovered: red }, isInvalid: blue }` 에서 evaluator 는 blue, raw `.X[data-quiet][data-hovered]` (0-3-0) 는 뒤의 `.X[data-invalid]` (0-2-0) 를 이겨 red (Chromium 반례). 따라서 compiler 는 **모든 조건 선택자를 `:where()` 로 감싸** 블록마다 specificity 를 컴포넌트 클래스 하나 (0-1-0) 로 고정하고, 블록의 source order = 트리의 조건 평가 순서 (깊이 우선, 같은 깊이는 나중 키가 뒤) 로 낸다. 그러면 cascade 는 source order 만으로 갈리고 evaluator 와 같은 값이 이긴다. 선례: `stateStyles.ts:98` (`:where(predicate)`) · `CSSGenerator.ts:513` (quiet hover `:where`). S2 macro 도 raw 순서가 아니라 `@layer` 우선순위 + 조건 역순 분기 (`style-macro.ts:471-474, 1002-1006`) 로 같은 보장을 한다.
- **층 사이의 상대 우선순위** (한 표로 고정): ① compiler 출력 (`@layer components`, 전부 0-1-0 + `:where`) < ② `domOnly` raw 가지 (같은 layer, 선언한 specificity 그대로 — 트리 블록 **뒤**. 대상이 `&` 가 아니라 자손 · 형제 · pseudo 뿐이라 트리와 cascade 로 겹치지 않는다 — `&` 대상 raw 선택자가 트리와 같은 속성을 선언하면 G3 (e) 가 막는다. DOM 전용 **조건** (`isFocused` 등) 은 ① 안에 있다) < ③ 수동 CSS (Phase 3 까지 남는 것 — 흡수 대상) < ④ 작성 stateRules 시트 (`stateStyles.ts`, `!important`) — 사용자가 쓴 값이 catalog 를 이긴다 (현행 그대로).
- **evaluator ↔ computed style 대조 게이트** (G1 (e)): 중첩 깊이가 다른 겹침 조합 (quiet+hover+invalid · selected+static+hover · outline+disabled 등) 을 브라우저에서 실제 computed 값으로 재고 evaluator 결과와 같은지 본다 — 생성 CSS diff 0 은 **옛 출력과 같음** 만 증명하고 트리 의미와 같음은 증명하지 않으므로 (measurement-validity Q5) 별도 oracle 이 필요하다.
- Styles 패널 미리보기 (F8 ④) 는 같은 evaluator 를 `interactionState` 대신 조건 집합으로 호출한다.
- 타입은 `catalog-style.types.ts` 한 벌로 — `VariantSpec` · `ComponentVisualRule` · 어댑터 2 벌 (F4) 삭제.

### Decision 3 — Canvas 상태 모델: 단일 상태 유지, 결합 상태는 DOM 전용으로 표시 (사용자 결정 1 로 열어 둠)

- 지금 Canvas 는 한 번에 상태 하나 (F5). 이 ADR 은 **그 모델을 바꾸지 않는다** — 조건 집합은 `displayState` 하나 + props 로 만든다. 트리에 `isSelected: { isHovered: … }` 처럼 결합 가지를 적으면 compiler 는 내고 evaluator 는 `displayState` 가 하나라 바깥 조건만 맞춘다.
- `displayState` 를 상태 집합으로 넓히는 일은 scope 변경 (CLAUDE.md §전제 4) — 사용자 결정 1.

### Decision 4 — 우선순위 통일의 방향: 트리 순서 = **Canvas 의 현행 순서** 를 기본으로, 차이 9 건은 Phase 3 에서 건마다 확정 (사용자 결정 2)

- 전환 단계 (Phase 1 · 2) 는 두 소비자의 **현행 출력을 각각 재현** 한다 — 트리는 조건별 값만 옮기고, compiler 는 현행 CSS 출력 순서를 그대로 낸다 (diff 0). 이때 Canvas 와 DOM 의 우선순위 차이는 **아직 남아 있다** (트리 한 벌이지만 compiler 가 옛 순서로 재배열).
- Phase 3 에서 compiler 의 재배열을 끄고 트리 순서 하나를 두 소비자가 따른다 — 그때 「다름 9」 가 한쪽 방향으로 닫힌다. 어느 쪽 순서가 맞는지는 S2 소스 (`Button.tsx` 의 키 순서 = `isDisabled` 최후 · static 이 variant 바깥 · `isFocusVisible` 이 hover 와 같은 단) 를 oracle 로 건마다 적고, S2 에 없는 조합 (quiet · invalid · subtle 의 상대 순서) 은 사용자 결정 2.

### Decision 5 — `.button-base` · 수동 CSS 층 (F8 ③) 의 처리

- `cssEmitMode: "button-base"` (F9) 는 Button 류의 hover · pressed · disabled 색을 트리가 아니라 `.button-base` 의 color-mix 에 맡기는 **두 번째 우선순위 체계** 다. Phase 3 에서 Button · ToggleButton 의 트리에 `isHovered` · `isPressed` · `isDisabled` 값 (S2 `Button.tsx` 의 `baseColor(…)` 단 — 이미 토큰 `accent-hover` 등이 있다) 을 적고 `button-base` 모드를 지운다. 흡수하는 것은 **`.button-base` 의 자체 color-mix** (`utilities.css:24-46`, `--button-color` 85% / 75% 섞기) 뿐이다. `tintToSkiaColors.ts:304-305` 의 `mixWithBlackSrgb(accent, 85 | 75)` 는 Canvas 사본이 아니라 **양 leg 가 읽는 `accent-hover` · `accent-pressed` 토큰의 생성원** 이다 (`resolveThemeSnapshot.ts:263-278` 이 seed 위에 펼쳐 Canvas 색 맵을 만들고 `:487-495` 가 그 맵을 DOM `--accent-hover` 로 내보낸다 — 리뷰 round 1 h2: 두 항목을 빼면 기본 테마 hover 가 `#2e52cc` → `#1f54c8` 로 양쪽 다 바뀐다). **유지한다** — breakdown §1 의 `resolveThemeSnapshot` 무변경 계약과 같다. 트리는 그 토큰을 **참조** 할 뿐 생성 로직을 대체하지 않는다. 생성원을 옮기려면 동등한 공용 생성원을 먼저 두고 preset · 명시 accent · light/dark 의 `colors` · `cssVars` 무변경을 게이트에 넣는다 (이 ADR 범위 밖).
- static-color 수동 CSS 42 건은 `isStaticColor` 가지로 옮긴다 (Canvas 는 이미 `resolveCatalogPaint:89-158` 에서 static 을 판정하므로 트리로 가면 두 쪽이 같은 자리에서 읽는다). selected 79 · focus 72 수동 CSS 는 컴포넌트별 **인벤토리 뒤** 폭을 정한다 — 사용자 결정 3.

### Decision 6 — 순서

Phase 0 (인벤토리 freeze · 「다름 9」 Compare Mode 실측 · RED · 기준선) → Phase 1 (트리 타입 + evaluator · compiler + Button 가족 한 벌 — diff 0 · paint 동일) → Phase 2 (표 전수 codemod · 투영기 3 · 소비자 · 타입 통합 · 어댑터 삭제 — diff 0 · paint 동일) → Phase 3 (우선순위 통일 — compiler 재배열 끔 · button-base 흡수 · static 수동 CSS 흡수 — before/after) → Phase 4 (live · 문서 · 종결).

### 사용자 결정 3건 (execute-adr 가 닿을 때 묻는다)

1. **Canvas 상태 집합** — `displayState` 를 단일 상태에서 집합 (`selected` + `hover` 동시) 으로 넓힐 것인가. 넓히면 `selectedHover` 류 결합 가지를 Canvas 도 그리고, 패널에 state 선택기가 필요해진다 (scope 확장). 기본 권고: **이 ADR 에서는 단일 유지** (Decision 3), 결합은 후속.
2. **S2 에 없는 조합의 우선순위** — quiet · invalid · subtle 의 상대 순서 (연구 §2.3 「다름」 중 S2 oracle 이 없는 건). Phase 0 실측 표를 보고 건마다 Canvas 쪽 / DOM 쪽 / 제3 안.
3. **수동 CSS 흡수 폭** — static 42 는 흡수 (Decision 5). selected 79 · focus 72 (17 + 파일) 는 Phase 0 인벤토리 뒤 「전부 / 상태 색만 / 이번엔 두고 후속」.

## Consequences

### Positive

- 상태 우선순위가 **데이터 한 곳** (트리 키 순서) — Canvas · DOM · Styles 패널이 같은 자리에서 읽는다. 새 상태 · 새 컴포넌트는 트리 한 가지 추가로 세 표면에 닿는다 (메모리 `project-feature-unit-spans-catalog-canvas-code-panels`).
- 상태 표현 5 방식 → 1 · 타입 3 벌 → 1 · 어댑터 2 → 0 · Canvas 쪽 축소판 CSS 매처 2 → 0 · `selectedHover` 죽은 경로 소멸 · `.button-base` 의 두 번째 파생식 (color-mix) 소멸 — 토큰 생성원 (`tintToSkiaColors`) 은 유지.
- rule 이 S2 `Button.tsx` 와 같은 모양이 되어 `d3S2Alignment` (295 G4) 같은 S2 대조 게이트를 **상태 값** 으로 넓힐 수 있다 (지금은 치수만).
- 후속 「토큰 모델 A」 (패널 입력기 + 노드 토큰 참조) 가 사용자 override 를 받을 때 트리 형식을 그대로 쓸 수 있다 (F3 의 잠자는 통로를 살리거나 지우는 결정이 명확해진다).

### Negative

- 표 14,484 줄 codemod 1 회 — 리뷰 불가능한 크기의 diff 가 한 커밋에 (G1 의 기계 검증이 리뷰를 대신한다).
- 전환 단계 (Phase 1 · 2) 에는 compiler 가 옛 출력 순서를 재현하는 코드가 **일시적으로** 있다 — Phase 3 에서 지운다. Phase 3 를 안 하면 트리 한 벌이지만 우선순위 두 벌이 남는다 (이 ADR 의 목적 미달).
- 정적 테스트 ~65 oracle 경로 수정 — 값은 안 바뀌지만 손이 많다.
- Phase 3 의 우선순위 변경은 사용자-가시 (hover · selected 색이 바뀌는 컴포넌트가 생긴다) — CHANGELOG 필수.
