## Context

### 도메인

- **문서 모델 (D1 · D2 · D3 무관)** — `InteractionEntry.action` (capability) 의 **대상 참조 형식**과 그 참조를 읽고 쓰는 모든 곳. 시각 값 0 · RAC prop 이름 0 · 생성기 질문 해당 없음.
- **D1 접점 하나** — Canvas 지정에서 「클릭한 부품 → 상태를 소유한 부모」 로 올리는 판정은 RAC 의 소유 사실 (field 가 Label · Input 의 상태를, trigger 가 overlay 의 `isOpen` 을 소유) 을 **읽기만** 한다 — `resolveDelegatedSubpartOwnerType` (`packages/shared/src/catalog/resolvers/resolveDelegatedChildFontSize.ts:338`) · dispatcher 의 `stateOwnerOf` (`packages/shared/src/interactions/dispatcher.ts:630`). 새 소유 규칙을 만들지 않는다.
- 빌더 시스템 UI 는 ADR-163 패널 표준 · 선택기는 기존 `CatalogComponentPicker` (`apps/builder/src/builder/panels/properties/catalog/CatalogSwapPicker.tsx`) 를 재사용한다.

### 현재 (실측 2026-10-25, main `6db027780` + ADR-282 Phase 3 작업 트리)

1. **대상 참조는 page 노드 하나뿐이다.** capability action 은 `targetId: NodeId` (`packages/shared/src/catalog/document/types.ts:1016-1021`) · 검증은 `id(action.targetId, "project:node:")` + 참조가 `node` entry 인지 (`document/validation.ts:1549-1552` · `document/graph.ts:1330-1334` `DANGLING_TARGET`). instance 안의 template 자리 (OrderCard instance 의 Save Button) · 원본 template 안의 자리 (원본 규칙이 같은 template 의 형제를 대상으로) 는 **표현할 수 없다**. AI 도구도 같은 이유로 거부한다 (`apps/builder/src/builder/catalogRuntime/aiHost.ts:744-746` `CAPABILITY_TARGET_NOT_A_NODE`).
2. **같은 문서 안에 세 모양의 참조 선례가 이미 있다.** `showWhen` 의 상태 주체 `CatalogStateOwnerRef.ancestor` = `{ nodeId } | { address: InstanceAddress } | { local: { instances, templatePath } }` (`types.ts:781-792`) — 검증 (`validation.ts:1811`) · 실행 (`runtime/presence.ts:2901` `isStateOwner`) · 주소 재작성 (`commands/components.ts:186` `rewriteAddressesThroughExtracted`) 이 있다. 대상 참조만 옛 모양이다.
3. **잠재 결함 — 실행은 대상의 첫 record 만 쓴다 (코드 읽기로 찾음, 아직 재현 테스트 없음).** 규칙의 주인 쪽은 모든 instance · 모든 행의 record 를 받고 instance 별 끄기를 거른다 (`runtime/catalogPreviewInteractions.ts:46-70` `recordsOfOwner` — ADR-281 Decision 4). 대상 쪽은 `root.recordsOfSource(action.targetId)[0]` (`:115`) — 어느 record 가 실행했든 **첫 record 하나**를 바꾼다. 영향: 원본에 둔 규칙 (281 상속) 이나 행 template 안의 규칙이 같은 template 안 노드를 대상으로 하면 모든 instance · 모든 행에서 눌러도 첫 instance · 첫 행만 바뀐다. 지금은 대상이 page 노드뿐이어서 (1) 대상이 행 template 안에 있을 수 있는 경우 (Collection 의 행 template 이 page 노드일 때) 에만 드러난다.
4. **패널 대상 목록은 평평한 `PropertySelect` 다.** `catalogCapabilityTargets` (`catalogRuntime/interactions.ts:161-185`) 는 page 노드를 깊이 우선으로 모으고 (instance 안쪽 0) · `CatalogRuleRow.tsx:426-460` 이 `PropertySelect` 하나에 나열한다 (검색 0 · 경로 0 · Canvas 강조 0 · 라벨 `targetOptionLabel` 은 이름 또는 `type (id 8자)`). 대상을 바꿀 때 옛 capability 가 새 대상의 `exposedCapabilities` 에 없으면 **말없이 `"hide"`** 로 바꾼다 (`:444-446` · 새 규칙 기본값도 `hide` — `interactions.ts:358-360`). 선택을 바꾸면 패널이 통째로 바뀌므로 (`CatalogInteractionsPanel.tsx:84` `key={targetKey(first.target)}`) 「Canvas 에서 대상을 클릭」 하면 편집 중인 규칙이 사라진다.
5. **대상 참조를 읽고 쓰는 곳 (전수 — breakdown §1a 표의 출발점)**: 참조 색인 `graph.ts:137` · 검증 `validation.ts:1552` · `graph.ts:1330` · 복사 `clone.ts:135` · 삭제 `structure.ts:1073-1100` `removeWithReferrers` (`referencedIds` 가 대상을 포함) · Preview 변환 `catalogPreviewInteractions.ts:115` · AI `aiHost.ts:744` · 패널 `CatalogRuleRow.tsx:156 · 222 · 429 · 441 · 461 · 465` · 기본값 `interactions.ts:360` · dispatcher (`dispatcher.ts:598-638` — record id 를 받으므로 **무변경**). **대상을 보지 않는 곳**: detach `materialize.ts:1019` `reanchorInteractions` (주인 `address` 만) · createComponent `components.ts:225` (주인 `address` 만) · swap `swap.ts:493` (주인 `address` 만) — 지금은 대상이 page 노드라 볼 필요가 없었고, 이 ADR 뒤에는 `{ address }` 대상이 이 세 명령을 지나야 한다.
6. **Canvas 는 hit-test · hover 를 이미 노출한다.** `pickTopmostRecord` (`catalogRuntime/canvasPick.ts:50`) · record 의 `sourceId` · `parentId` (`CatalogPickRecord`) · 세션 `hover` (`catalogRuntime/session.ts:29 · 197-201`). record 는 `instancePath` · `rowIndex` 를 가진다 (`runtime/compositionRoot.ts:252 · 297`).
7. **record 의 `instancePath` 는 「같은 문맥」 의 표지가 아니다 (리뷰 Round 1 H1).** 소유 자식 (page 노드 · 행 template 의 노드) 은 자기 id 를 path 끝에 더한다 (`resolution/resolver.ts:1427-1429` `childPath = [...instancePath, childId]`) — 같은 행의 Delete 와 Text 는 path 가 `[…, row, delete]` · `[…, row, target]` 로 다르다. instance 안 template 노드의 record 만 path 가 instance 사슬이다 (`compositionRoot.ts:3980`). 「같은 instance · 같은 행」 은 **`parentId` 체인의 조상 record** (`compositionRoot.ts:226 · 815`) 로만 판정할 수 있다 — 행 record 는 `rowIndex`, instance 루트 record 는 source 가 instance 노드.
8. **참조 생명주기의 현재 계약 (리뷰 Round 1 H2 · H3 · H4).** 참조 색인은 주소의 `instances` · `templatePath` 에 든 **모든** project id 를 든다 (`graph.ts:112-117` — swap `swap.ts:491` · createComponent `components.ts:210-227` 이 `referrersOf(중간 id)` 로 holder 를 찾는다). `local` 의 `TemplateId` 는 lib id 뿐 아니라 project 노드 id 다 (`validation.ts:1828-1840`) — `duplicateDefinition` (`components.ts:424-445`) 은 template 전체를 새 id 로 복사하므로 상대 참조도 재매핑 대상이다. swap 은 주인 주소를 remap 못 하면 규칙을 **삭제** 한다 (`swap.ts:498-505`) — 옛 주소를 남기면 `resolution/address.ts:81-87` 이 `TEMPLATE_ROOT_MISMATCH` 로 거부해 「남긴다」 에는 유효한 저장 모양이 따로 필요하다.

### 제약

- **Hard — 스키마**: `InteractionEntry` 의 규칙 모양 (한 줄 · `ownerId` · `address` · `trigger` · `action`) 무변경 (ADR-158). → 이후 ADR-284 (contract 50) 가 `action` 을 Do 목록 `actions[]` 로 바꿨다 — `target` 은 각 capability Do 의 필드. 바뀌는 것은 capability action 의 대상 필드 하나 — `targetId: NodeId` → `target: CatalogNodeRef | { unset: true }` (`CatalogStateOwnerRef.ancestor` 의 세 모양을 공용 타입으로 꺼낸 것 + 명시적 「대상 없음」). `LIBRARY_CONTRACT_VERSION` 48 → 49 (`types.ts:133`). **마이그레이션 코드 0** (사용자 지시 2026-10-14) — 옛 개발용 프로젝트는 거부, fixture 는 직접 고친다.
- **Hard — 실행 동등성**: Preview 와 Publish 는 같은 공유 runtime (`catalogPreviewInteractions.ts`) — 분기 0. 대상 해소는 **실행한 record 기준** (같은 instance · 같은 행) 이어야 하고, 패널의 「이 규칙의 대상」 표시와 실행이 같은 함수를 읽는다 (281 R2 와 같은 모양 — 판정 함수 하나).
- **Hard — 상태 주인 이전은 dispatcher 그대로**: overlay 본체를 대상으로 고르면 실행 시 `stateOwnerOf` 가 trigger 로 보낸다 (280 사용자 결정 2). 이 ADR 은 **저장 시점에 미리 바꾸지 않는다** — 다만 Canvas 지정의 올림 규칙 (Decision 5) 과 표시가 같은 사실을 쓴다.
- **Hard — Esc = 문서 변경 0 · 확정 = History 1 step**: Canvas 지정 모드는 선택 · hover · 편집 context 를 바꾸지 않는다 (세션 상태만).
- **Hard — 번들**: Builder initial ≤ 1,390,000 B gz · Preview ≤ 320,000 B gz (ADR-201 재승인, 만료 2026-11-25). Preview 쪽 증분은 해소 함수 하나.
- **Soft**: Interactions 패널 모듈 ≤ 15 파일 (ADR-158 G4 — 지금 11 + 이 ADR 의 선택기 1 · 지정 모드 1).

## Alternatives Considered

### 대안 A: UI 만 — 검색 선택기 · Canvas 지정 (page 노드 한정) · instance 안쪽은 「가장 가까운 조상」 으로 올림

- 설명: 참조 모델 무변경. 선택기와 Canvas 지정을 더하고, instance 안쪽을 클릭하면 page 노드인 가장 가까운 조상 (instance 루트) 을 대상으로 삼는다. 스키마 0 · contract 0.
- 근거: 외부 분석의 P1 범위 · 첫 제안.
- 위험: 기술 LOW / 성능 LOW / 유지보수 **HIGH** (모델 한계를 UI 가 덮는다 — OrderCard 의 Save 를 숨기려는데 OrderCard 전체가 숨는다. 사용자가 그 차이를 패널에서 알 수 없고, 잠재 결함 3 이 남는다) / 마이그레이션 LOW.
- 기각: 사용자 원문 「필요해지면 이아니라 처음부터 모든 설계를」. 조상 올림은 RAC 소유 부품에만 맞는 규칙이고 (사용자 원문 1 의 전제가 그것) 일반 자손에는 틀린 답이다.

### 대안 B: 대상 참조 = `CatalogStateOwnerRef.ancestor` 와 같은 세 모양 · 실행 record 기준 해소 · 전 소비자 정합 · 선택기 + Canvas 지정 (채택)

- 설명:
  1. **참조**: `target: CatalogNodeRef = { nodeId } | { address } | { local }` — `showWhen` 이 쓰는 모양 그대로 공용 타입으로. `local` 은 규칙 주인과 같은 instance 문맥의 상대 위치 (원본 template · 행 template 안 규칙).
  2. **해소**: 실행한 record 를 기준으로 대상 record 를 고른다 — 참조가 이름 붙인 instance 사슬로 후보를 좁히고, 참조가 이름 붙이지 않은 **반복 조상 record** (행 record · instance 루트 record — `parentId` 체인) 는 실행 record 와 공유해야 한다. 경로 문자열 전체 일치는 쓰지 않는다 (현재 7). 판정 함수 하나 (`resolveCapabilityTarget`) 를 Preview 변환과 패널 표시가 읽는다.
  3. **문서 정합**: 참조 색인 (`referencedIds` 가 `address` · `local` 의 **모든** project id 를 든다 — 주인 주소와 같은 helper) · 검증 · 복사 (세 모양의 모든 project id 재매핑) · 삭제 · detach (대상 자리가 물질화되면 사본 노드 id 로) · createComponent (`rewriteAddressesThroughExtracted` 에 대상 holder 추가) · dissolve · swap (자리 없으면 **규칙은 남기고 `{ unset: true }`**) · AI host (instance 안쪽 record → `{ address }`).
  4. **패널**: 검색 선택기 (page 노드 + instance 안쪽 자리, 경로 `OrderCard ▸ Save`, 이름 중복 시 짧은 id, 50 개 넘으면 RAC 가상화) · hover ↔ Canvas 강조 양방향 · 대상 없음 행 「다시 지정」 · capability 가 바뀌면 한 줄 안내 (말없는 `hide` 금지) · Local page 의 원본 규칙은 같은 template 안 대상이 자동으로 `local`, page 노드 대상 거부.
  5. **Canvas 지정**: 규칙 행의 조준 버튼 → 세션 `targetPick` 상태 → Canvas 클릭을 선택 전에 가로채 record 를 참조로 바꿔 규칙에 쓴다 (History 1) · Esc 는 0 · 클릭한 컴포넌트 자체가 대상, RAC 가 상태를 부모에게 맡긴 부품 (field 부품 · overlay 본체) 만 그 부모로 올리고 이름표에 두 이름.
- 근거: 세 모양의 참조는 검증 · 실행 · 주소 재작성이 이미 있는 선례다 (현재 2). 대상 쪽만 옛 모양이어서 생긴 결함 (현재 1 · 3) 을 같은 모양으로 닫는다. Framer 의 「Component 안 요소를 대상으로 하는 상호작용」 · Figma 의 「프로토타입 대상 = 레이어 어디든」 과 같은 범위.
- 위험: 기술 **MEDIUM** (대상 해소가 record 문맥 — `parentId` 체인의 행 · instance 루트 record — 을 읽어야 하고, 반복 조상 표지 (`rowIndex` · instance source) 가 모든 record 에 있는지는 Phase 0 inventory) / 성능 LOW (해소는 규칙 실행 시 1 회 · 선택기는 선택 시 1 회 + 가상화) / 유지보수 **MEDIUM** (대상 참조를 지나는 명령이 7 개 — 하나라도 빠지면 dangling 주소. grep 게이트로 묶음) / 마이그레이션 **MEDIUM** (contract 49 — 기존 개발용 프로젝트 거부 · 변환 0).

### 대안 C: 대상이 instance 안쪽이면 그 instance 를 detach (물질화) 해 page 노드로 만든다

- 설명: 참조 모델 무변경. instance 안쪽을 대상으로 고르는 순간 instance 를 사본으로 풀어 자리를 page 노드로 바꾼다.
- 위험: 기술 LOW / 성능 LOW / 유지보수 **HIGH** (규칙 하나 때문에 컴포넌트 연결이 끊긴다 — 253 · 279 의 목적 역행 · 원본 규칙은 표현 불가) / 마이그레이션 LOW.
- 기각: 사용자 원칙 「origin · instance = pen.dev · Figma · Framer 참조」 — 어느 도구도 대상 지정이 instance 를 깨뜨리지 않는다.

### 대안 D: 대상을 runtime record id 로 저장

- 설명: Preview 가 쓰는 record 식별자 (`instancePath/…::sourceId`) 를 문서에 그대로 넣는다.
- 위험: 기술 **HIGH** (record id 는 문서가 아니라 runtime 의 파생값 — 행 수 · 바인딩이 바뀌면 사라짐) / 성능 LOW / 유지보수 HIGH / 마이그레이션 MEDIUM.
- 기각: 문서는 runtime 식별자를 알지 못한다 (ADR-248 경계).

## Decision

**대안 B 채택.**

> 구현 상세: [283-interaction-capability-target-ref-picker-breakdown.md](design/283-interaction-capability-target-ref-picker-breakdown.md)

1. **대상 참조는 상태 주체 참조와 같은 세 모양 + 명시적 「대상 없음」 이다.** `CatalogNodeRef = { nodeId: NodeId } | { address: InstanceAddress } | { local: { instances: TemplateId[]; templatePath: TemplateId[] } }` 를 `types.ts` 공용 타입으로 꺼내 `CatalogStateOwnerRef.ancestor` 와 capability action `target` 이 같이 쓴다. capability 의 `target` 만 `CatalogNodeRef | { unset: true }` — `unset` 은 자리가 사라진 규칙의 **유효한 저장 모양** (리뷰 H4): 참조 0 (색인 · dangling 검사 대상 아님) · 해소 `undefined` + report `TARGET_UNSET` (dispatcher 에 넘기지 않음) · 패널 「대상 없음 · 다시 지정」 · AI 도구는 만들 수 없음 (`CAPABILITY_TARGET_REQUIRED`) · 명령 (swap · detach · dissolve) 만 쓴다. 검증은 `validation.ts:1811` 의 `ancestor` 검사를 함수로 나눠 둘이 공유하고 `unset` 분기는 capability 쪽만. contract 49.
2. **해소는 실행한 record 기준이다 — 비교 단위는 경로가 아니라 반복 조상 record 다.** `resolveCapabilityTarget(root, firingRecordId, ref): recordId | undefined` 하나 (shared). (a) 후보 = 참조가 가리키는 source 의 record 전부 (`nodeId` 는 그 노드 · `address` · `local` 은 `templatePath` 끝). (b) 참조가 **이름 붙인 instance 사슬**로 좁힌다 — `address` 는 `recordsOfOwner` 와 같은 instancePath tail 비교 (`instances`) · `local` 은 실행 record 의 instancePath 에 `local.instances` 를 이은 것 · `nodeId` 는 좁히기 0. (c) 남은 후보 T 마다 T 의 **반복 조상 record** (record 를 여럿으로 늘리는 조상 — `rowIndex` 를 가진 행 record · source 가 instance 노드인 instance 루트 record, `parentId` 체인으로 수집) 중 참조가 이름 붙이지 않은 것 전부가 실행 record 의 조상-또는-자기 여야 한다 — **세 모양 모두, 면제 없음**. 참조가 이름 붙이는 것은 instance 루트 record 중 source 가 `address.instances` · `local.instances` 에 든 것뿐이다. **행 record 는 어느 모양도 이름 붙이지 않으므로 항상 실행 record 와 공유해야 한다** — instance 사슬이 같아도 행이 다르면 다른 record 다 (record identity 는 `instancePath::sourceId` 에 `#row:<key>` 가 붙고 `instancePath` 는 행마다 같다 — `compositionRoot.ts:494-498` · `resolver.ts:260-267` `withRowKey`). 예: Local 컴포넌트 Row 를 행 template 으로 3 번 반복할 때 원본 Edit 의 `local` 규칙 (→ Save) 은 (b) 뒤 후보 3 (instancePath 동일) → (c) 에서 행 2 의 Edit 와 행 record 를 공유하는 하나만 남는다 (리뷰 Round 2). (d) 남은 후보 1 = 그것 · 0 = `undefined` + report `TARGET_OUT_OF_CONTEXT` (다른 행 · 다른 instance 에서 이 자리를 가리킬 수 없음) · 2+ = 설계 위반 (테스트 단언). 같은 행의 **형제** (Delete → Text, path 가 다름) 가 (c) 에서 같은 행 record 를 공유해 한 후보로 남는 것이 G1 의 첫 반례다 (현재 7). `ruleOf` 의 `[0]` 은 삭제. 패널의 대상 표시도 같은 함수로 「이 규칙이 Preview 에서 바꿀 것」 을 보인다.
3. **대상 참조를 지나는 명령 7 개가 같은 커밋에서 바뀐다.** 참조 색인 (`graph.ts:137` — `nodeId` 는 그 노드, `address` · `local` 은 `instances` · `templatePath` 에 든 **모든** project id — 주인 주소의 `address()` helper (`graph.ts:112-117`) 그대로. 중간 instance 의 swap · 중간 노드의 추출 · 삭제가 `referrersOf` 로 이 규칙을 찾아야 하므로 root · leaf 만으로는 안 된다 — 리뷰 H2) · 삭제 (`removeWithReferrers` — 대상 사슬의 어느 층이 지워져도 규칙 삭제, 지금 규칙 그대로) · 복사 (`clone.ts:135` — 세 모양 모두 `instances` · `templatePath` 의 `project:node:` id 를 사본 map 으로 재매핑, 주인 `address` 의 `:142-148` 과 같은 코드. `local` 도 — `duplicateDefinition` 이 template 을 새 id 로 복사하므로 「상대 참조라 무변경」 은 틀리다 — 리뷰 H3. map 밖 id · lib id 유지) · detach (`reanchorInteractions` 가 대상 `address` 도 — 물질화된 자리는 `{ nodeId: 사본 }` · 바깥 instance 주소는 그 층 제거 · 재주소 불가면 `{ unset: true }`) · createComponent (계획: `rewriteAddressesThroughExtracted` 의 holder 에 interaction `action.target` — 구현은 별도 `rewriteTargetsIntoComponent`, `commands/components.ts`) · dissolve (전부 detach 와 같음) · swap (`remapThrough` 를 대상에도 — 자리가 없으면 규칙은 남기고 `target: { unset: true }`, swap 보고에 `targetsUnset` 카운트 — 주인 규칙 삭제를 뜻하는 `dropped` 와 구별). AI host 는 `positionOfRecord` 가 돌려주는 instance 자리를 `{ address }` 로 쓴다 (`CAPABILITY_TARGET_NOT_A_NODE` 삭제).
4. **패널 — 검색 선택기.** `catalogCapabilityTargets` 가 page 노드에 더해 **instance 의 template 자손** (capability 를 가진 type) 을 `{ address }` 후보로 모은다 (경로 라벨 `OrderCard ▸ Save`). 선택기는 `CatalogComponentPicker` 모양 (Autocomplete · 검색 · 그룹 「이 페이지」 / 「컴포넌트 안」) · `#` 는 그 요소의 DOM id (Accessibility ID — Preview 가 그리는 `id=""`): page 노드는 자기 것 (`Save (Button) #button_1`), instance 안쪽 자리는 자기 id 가 없어 instance 의 것 (`OrderCard #ordercard_1 ▸ Save`), DOM id 가 없을 때만 이름이 겹치거나 없으면 짧은 id (`· a1b2`) (2026-10-26 사용자 지적 — 내부 id 꼬리보다 작성자가 보는 id 가 일반적) · 50 개 넘으면 RAC `Virtualizer`. hover · focus · 화살표 = 세션 `hover` 로 Canvas 강조, Canvas hover 는 목록 강조 (양방향). 대상이 바뀌어 capability 가 바뀌면 행 아래 한 줄 「X 는 ‘Disable’ 을 받지 않아 ‘Hide’ 로 바꿨습니다」 (시안 ③ — 말없는 폴백 0). 참조가 풀리면 (대상 없음 — swap · 삭제 뒤) 행에 「대상 없음 · 다시 지정」. Local page 에서 원본을 편집할 때 같은 template 안 후보는 `{ local }` 로 저장되고 page 노드 후보는 목록에 없다 (template 은 page 를 모른다).
5. **Canvas 지정.** 규칙 행의 조준 버튼 → 세션 `targetPick: { ruleId }` (저장 0) → Canvas 는 배너 「대상으로 쓸 요소를 클릭 · Esc」 를 띄우고 pointer 를 선택 gesture 앞에서 가로챈다 (`canvasGesture` 분기 — 선택 · drag · context 진입 0). hover 는 점선 강조 + 이름표 (`type · name · #DOM id`, 없으면 짧은 id · 경로). 클릭 = record → 참조: page 노드 record 는 `{ nodeId }`, instance 안 record 는 `{ address }` (Local page 의 원본 안이면 `{ local }`), **클릭한 컴포넌트 자체**. 올림은 둘뿐 — (a) `resolveDelegatedSubpartOwnerType` 이 부모를 돌려주는 field 부품 (Label · Input · 증감 Button …) → 그 field, (b) `CATALOG_OPEN_BODY_TYPES` 의 overlay 본체 → `catalogOpenOwnerOf` 의 trigger. 올림이 일어나면 이름표가 「Input → TextField (상태 소유)」 두 이름. capability 가 없는 type (Text · frame) 은 클릭해도 지정되지 않고 이름표에 「capability 없음」. 확정 = 규칙 patch 1 step (`capabilityId` 가 새 대상에 없으면 Decision 4 의 안내와 같이) · Esc · 다른 패널 클릭 = 0.
6. **재판단 — 유지**: dispatcher 의 `stateOwnerOf` 이전 (overlay 본체 → trigger) 은 실행 시점 그대로 (280 결정 2) — Decision 5(b) 는 저장 전 올림이지만 결과 record 가 같아 두 경로가 한 답. Do 대상 = 같은 페이지 (280 결정 7) — `address` 의 `instances[0]` 도 같은 페이지 노드.

**위험 수용 근거**: 기술 M 은 Phase 0 inventory 가 반복 조상 표지 (행 record 의 `rowIndex` · instance 루트 record 의 source) 와 `parentId` 체인이 모든 record 에 있는지 먼저 재고 (없는 record 종류가 있으면 그 종류의 표지를 record 에 더하는 것이 Phase 1 — 「record 하나일 때만」 으로 줄이는 폴백은 같은 행 동작을 구현하지 못하므로 쓰지 않는다), 이관 M 은 contract bump 가 표준 절차 (277 · 278 · 279 · 281 · 282). 유지 M 은 G1 의 grep 게이트 (대상 참조를 읽는 자리 전수 = breakdown §1a 표) 와 명령별 원복 RED 로 묶는다.

**기각 사유**: A — 모델 한계를 UI 로 덮음 · 사용자 원문 2 반대 · 결함 3 잔존. C — instance 연결 파괴. D — runtime 식별자를 문서에.

## Consequences

### Positive

- 규칙의 대상이 문서가 표현하는 모든 자리에 닿는다 — page 노드 · instance 안 자리 · 원본 template 안 자리. 상태 주체 참조와 한 모양이라 새 형식 0.
- 원본 규칙 · 행 규칙이 **누른 instance · 누른 행**을 바꾼다 (첫 것만 바뀌던 잠재 결함 종결).
- 대상을 검색하거나 Canvas 에서 클릭해 고른다 — 요소 100 개 페이지에서도 한 번에. 대상이 바뀌어 기능이 바뀌면 안내가 보인다.
- AI 도구가 instance 안쪽을 대상으로 규칙을 만든다.

### Negative

- contract 49 — 기존 개발용 프로젝트는 열리지 않는다 (변환 0).
- 대상 참조를 지나는 명령이 7 개로 는다 — 새 명령이 instance 주소를 바꾸면 대상도 봐야 한다 (`rewriteAddressesThroughExtracted` 의 holder 표가 그 자리).
- 패널 모듈 +2 파일 (선택기 · 지정 모드) — ADR-158 G4 상한 15 안.
