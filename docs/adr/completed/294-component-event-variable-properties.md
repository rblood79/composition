## Context

### 도메인

D2 (Props/API) 의 **composition 확장** — 사용자 컴포넌트의 property 는 사용자가 정의하는 prop 표면이다 (ADR-261 Decision 4, `d2Provenance.ts` 의 S2 · RAC 대조 밖 — 레퍼런스에 없는 컴포넌트의 props). D1 은 무관하다 — `emit` 은 RAC 콜백이 아니라 composition 규칙 층의 Do 이고, RAC 컴포넌트 안을 바꾸지 않는다. D3 은 무관하다 — 시각 없음. Canvas 는 event 에 대해 그릴 것이 없고, variable 의 작성 값은 기존 `{{ }}` 환경으로 반영된다 (Decision 5 · 7).

### 현재 (실측 2026-10-30, main `2cbb83de9`)

- **컴포넌트 property 종류는 셋이다** — `text` · `boolean` · `instance` (`packages/shared/src/catalog/document/types.ts:953` `COMPONENT_PROPERTY_KINDS`). 값은 instance 루트 props 의 `key` 에 쓰이고 원본 노드의 `prop` · `enabled` 로 투영된다 (`componentProperties.ts` `componentPropertyWrites` · `resolution/resolver.ts:961-963` `propertyScopes`). 검증은 그 셋만 받고 target 1 개 이상을 요구한다 (`validation.ts:374-376`). Properties 패널의 종류 선택지도 셋 (`panels/properties/catalog/CatalogComponentPropertiesSection.tsx:60-65` · `:183-201`), instance 쪽 값 편집은 `CatalogInstancePropertiesSection.tsx`. 모두 **입력** 이다 — 원본이 밖으로 값을 내보내는 선언이 없다.
- **instance 루트 props 의 key 는 `accepts` 계약이 있어야 저장된다** — project 정의의 `accepts` = 루트 계약 ⊕ 정의 `accepts` ⊕ `componentPropertyAccepts(properties)` (`library.ts:174-178`) 이고 `componentPropertyAccepts` 는 text → `string` · boolean → `boolean` 만 낸다 (`componentProperties.ts:14-30`). 계약에 없는 key 의 쓰기는 `PROP_NOT_ACCEPTED`, 타입이 다르면 `PROP_TYPE_MISMATCH` (`graph.ts:1583-1601` `validatePropWrites` — 예외는 `PropVar` 와 `{key}` 템플릿 바인딩 둘). 리뷰 probe 가 variable key 의 리터럴 쓰기 거절을 확인했다 (h2).
- **규칙은 RAC 콜백 이름이 When 이다** — `InteractionEntry { ownerId, address?, trigger, actions[] }` (`types.ts:1182`). `trigger` 는 등록표에서 만든 집합 안이어야 한다 (`graph.ts:1458` `UNKNOWN_TRIGGER_ID` ← `executionVocabulary.ts:60`). Preview 는 `trigger` 를 RAC prop 이름으로 핸들러에 건다 (`interactions/bindings.ts:80-108` `createElementHandlers` — `handlers[trigger]`). 컴포넌트가 정의한 이벤트가 들어갈 자리가 없다.
- **instance 의 When 목록 = 원본 루트 type 의 RAC 이벤트** — 패널은 `catalogTargetTypeName` → `definitionTypeName` (`commands/context.ts:98-119`) 로 type 을 얻는데, composite 정의는 **template 루트의 type** 으로 풀린다. 루트가 Popover · frame 이면 이벤트가 없고, 안쪽 ListBox 의 선택은 instance 바깥에서 보이지 않는다.
- **render record 는 논리 instance 경계를 접는다** — composite instance 의 record 는 template 루트 (와 그 루트가 다시 composite instance 면 그 루트 …) 와 한 record 로 합쳐진다 (`compositionRoot.ts:3295-3318` `collapseLayers` · `:3324-3370` `consumerRecord`). record 의 `instancePath` 는 바깥 instance 만 남고 (`top.instancePath`), 접힌 층은 `collapsedIds` · `collapsedSourceIds` 로 따로 남는다. Outer 의 template 루트가 Inner instance J 일 때 page 의 Outer instance I 의 record 는 `instancePath = [I]` · `collapsedSourceIds = [J, Inner 루트]` 다 (리뷰 probe, h1). `instancePath` 만 걷는 수신 판정은 Inner 경계를 못 본다.
- **원본 규칙에서 바깥으로 쓰는 두 길이 다 막혀 있다**:
  - Set state 의 변수 후보는 소유자 사슬 → page 에서 끝난다 (`panels/interactions/StateActionFields.tsx:73` ← `catalogRuntime/interactions.ts:521` `catalogVisibleVariables` ← `stateVariables.ts:121` · `:75-87` `ownerChain`). 원본은 Local page 에 있어 (ADR-282) 사용 page 의 변수가 후보에 없다. 문서 검증은 존재만 본다 (`graph.ts:1486` `DANGLING_VARIABLE`) 고 실행은 변수 소유자의 scope 로 쓴다 (`catalogPreviewSession.ts:725-781` `variableScope`) — 즉 **저장 · 실행은 받고 패널만 막는** 상태다.
  - 원본 규칙의 capability 대상은 같은 template 안만 (`graph.ts:1927` `TARGET_IN_TEMPLATE`, ADR-283 설계) — page 의 DialogTrigger 를 닫을 수 없다.
- **변수 읽기 경로는 세 곳이고 전부 page · project 변수만 안다** — (a) 보기 조건 · 정렬의 `!var` 는 `pageAndProjectStates` (`stateTemplate.ts:357-401` — 소유자 사슬에서 page 를 만나면 그 page 변수, 그리고 project 변수; template 루트 소유 element 변수는 닿지 않는다 — probe: read 호출 0) · (b) 규칙의 `!var` 는 세션 `readVariable` 이 `state.read` 를 직접 부르고 (`catalogPreviewSession.ts:744-751`), runtimeState 는 기록이 없는 scope 에도 **기본값을 돌려준다** (`runtimeState.ts:369-375` — 「없으면 prop」 폴백을 가릴 판별이 없다) · (c) Canvas 는 `read` 없이 기본값 (`stateTemplate.ts:19-30` · `:196-219`). 갱신은 변경된 변수의 **이름 · id** 와 독자의 템플릿 이름을 직접 비교한다 (`compositionRoot.ts:2049-2095` `stateReaders` · `refreshState`, `catalogPreviewSession.ts:1791-1800`) — 전이 의존성 (부모 변수 → 입력 변수 → 안쪽 독자) 색인은 없다.
- **유일한 우회 = instance 가 원본 규칙을 자기 규칙으로 대체** (`types.ts:555-560` `DescendantPatchFields.interactions` — `"off"` | 자기 규칙, ADR-281 Decision 4; 실행 `catalogPreviewInteractions.ts:52-85` `recordsOfOwner`, 패널 `catalogInheritedInteractionsOf`). instance 마다 다시 짜야 하고 원본에는 「여기서 고른 값이 나간다」 는 의도가 남지 않는다. 다른 우회는 프로젝트 변수 (모든 사슬의 끝) 인데 두 instance 가 같은 전역을 덮는다.
- **실행기는 Do 마다 주입 함수다** — `dispatcher.ts:39-168` `DispatchDeps` (`writeState` · `callEndpoint` · `append` … 미주입 = 실패, 조용한 no-op 금지) · `:546` `executeInteractionRule` · `:170-181` `DispatchContext { instanceKeyFor, event, itemsOf, singleSelection }`. 새 Do 하나는 deps 함수 하나 + `actionOf` 분기 하나 (`catalogPreviewInteractions.ts:117-235`) 다.
- **code view** 는 page 의 노드가 주인인 규칙만 핸들러로 낸다 (`codeView/generate.ts:413-417` · `:2174-2210`). instance 는 루트 type 이름으로 나오고 (`:209-214` `typeOf` = `definitionTypeName`) 원본 안은 보이지 않는다 (연구 §1c E6 — ADR B 범위).
- **시나리오는 수용 fixture 와 같은 모양이다** — `codeView/__fixtures__/reference/emoji-picker.tsx.txt` (Button → Popover → SearchField + 필터된 ListBox → 선택). 패널로는 팝오버 (ADR-278 slot) · API 목록 · 검색 (ADR-284 `!var` 보기 조건 · Autocomplete) 까지 되고, **「선택값 → 부모 page」 만** 위 우회다.

### 외부 패턴

- Framer code component — `addPropertyControls` 의 `ControlType.EventHandler`: 컴포넌트가 이벤트 prop 을 선언하고 instance 가 캔버스에서 동작을 건다. Design component 에는 이벤트가 없다 (variables 만 — 메모리 `reference-framer-components-model-2026-10`).
- Plasmic code component — `eventHandler` prop 종류 (인자 이름 선언) · instance 가 Interactions 에서 받는다.
- Retool Module — inputs · outputs 를 선언하고 부모 앱이 outputs 를 읽는다.
- Figma — 컴포넌트 property 는 text · boolean · instance swap · variant 뿐, 이벤트 없음 (디자인 도구). composition 의 지금 셋은 이 집합이다.

### 제약

- **Hard — 스키마**: `ComponentPropertyKind` 에 종류 추가 · `InteractionAction` 에 opcode 추가 · trigger 집합에 property 이벤트 허용 · `StateVariableEntry.input` 표지 → `LIBRARY_CONTRACT_VERSION` 51 → 52 한 번 (Phase 1 커밋). 마이그레이션 코드 0 (사용자 지시 2026-10-14) — 옛 개발용 문서는 거부 · 재생성.
- **Hard — 조건 · 분기 없음 유지** (ADR-158): 이 ADR 은 제어문을 넣지 않는다. `emit` 은 Do 하나, 받는 쪽은 규칙 하나다. 제어문은 ADR C (연구 §9b).
- **Hard — 패널 동등**: 코드 전용 기능 0 (사용자 결정 2026-10-27 · 연구 결정 3). 다섯 표면 중 Canvas 는 event 에 「해당 없음」 을 명시하고, 나머지 넷은 같은 커밋 묶음에서 닫는다.
- **Hard — 패널 = 실행**: Do · When 의 노출 판정과 문서 검증이 같은 술어 (ADR-281 `declaredRefusal` 원칙) — 보이는데 거절 · 안 보이는데 실행 금지.
- **Hard — 하나의 해석 함수**: 입력 변수의 값 (리터럴 · 부모 참조 · 기본값) 은 shared 함수 하나가 정하고 Canvas · Preview/Publish · 보기 · 규칙 네 독자가 그것만 읽는다 (리뷰 h3). 경계 (논리 instance 사슬) 도 shared 함수 하나 (리뷰 h1).
- **Hard — 조용한 생략 0**: `emit` 에 받는 규칙이 없으면 React 의 미전달 콜백처럼 **성공** 이되 outcome 에 `listeners: 0` 을 싣는다 (사용자 결정 3). 미주입 deps · 수신 경계를 못 찾음 (◆ 직접 실행이 아닌데 경계가 없음) 은 실패. 입력 변수에 쓰기는 거절 (`INPUT_VARIABLE_READ_ONLY`).
- **Hard — 번들**: Preview initial gzip Δ ≤ +1,024 B (shared dispatcher · 세션 증분) · Builder ≤ +4,608 B (2026-10-30 사용자 결정으로 +2,048 → +4,608 정정 — 늘어난 몫이 문서 검증 · 경계 · 해석 · property 명령 · Properties 패널이고, 넷은 Canvas 의 동기 경로라 lazy 로 뺄 몫이 작다 · 패널 몫을 빼도 상한 아래로 안 내려간다). 절대 상한은 ADR-201 그대로.
- **Soft**: 새 어휘는 Do 1 (`emit`) · When 종류 1 (property 이벤트) 뿐. 레퍼런스 코드 모양 = React 의 콜백 prop (`<UserPicker onSelect={(item) => …} />` · `function UserPicker({ onSelect })`) 이라 code view 는 새 문법이 아니다.
- **Generator 질문 (반복 패턴 #2)**: 이 ADR 은 CSS 생성기와 무관하다. 바뀌는 생성기는 code view 생성기 (`generate.ts`) · 역문법 — Phase 3 어휘표 2 행.

## Alternatives Considered

### 대안 A: 우회를 공식화 — instance 규칙 대체 + 원본 패널에 사용 page 변수 노출

- 설명: ADR-281 의 `interactions` 대체 맵을 「값 내보내기」 의 공식 길로 두고, 원본 편집 중 Set state 후보에 모든 page 의 변수를 보인다 (가시성 사슬을 page 너머로).
- 근거: 스키마 변경 0.
- 위험: 기술(M — 원본은 어느 page 에서 쓰일지 모르므로 「모든 page 변수」 는 이름 충돌 · dangling 을 낳는다) / 성능(L) / 유지보수(**H** — instance 마다 규칙 복제, 원본에 의도 없음, 변수 가시성 사슬 (ADR-288 이름 규칙) 이 깨진다) / 마이그레이션(L).

### 대안 B: 프로젝트 변수 경유

- 설명: 원본 규칙이 프로젝트 변수에 쓰고 page 가 그것을 읽는다. 지금도 된다.
- 근거: 변경 0.
- 위험: 기술(L) / 성능(L) / 유지보수(**H** — 컴포넌트 재사용 = 전역 이름 하나를 두 instance 가 덮는다, Framer · Plasmic · Retool 어디도 이 모양이 아님) / 마이그레이션(L).

### 대안 C: property 종류 확장 — `event` (출력) · `variable` (입력), 원본 Do `emit`, instance When = property 이벤트 (채택)

- 설명: 정의의 `properties` 에 `event` (이름 · 선택적 값 타입, target 0) 와 `variable` (template 루트 소유의 **파생 변수** — 값은 instance 가 준다) 를 더한다. 원본 template 노드의 규칙에 Do `emit <property> value` (값은 기존 Value 칸 — `!item` · `!event` · `!var` · 리터럴). instance 노드의 규칙에 When `property:<key>` (인자 `value`) — 받는 쪽은 기존 Do (setState · capability `close` · navigate …) 그대로. 실행은 `deps.emit` 하나: 실행 record 의 **논리 instance 경계 사슬** (`instancePath` ⊕ `collapsedSourceIds` — 리뷰 h1) 을 안쪽부터 걸어 그 정의의 가장 안쪽 instance 경계를 찾고 그 경계에 걸린 `property:<key>` 규칙을 `event = { value }` 로 실행한다.
- 근거: Framer `ControlType.EventHandler` · Plasmic `eventHandler` · Retool outputs — 컴포넌트 경계의 표준 모양. 레퍼런스 코드 (React 콜백 prop) 와 1:1.
- 위험: 기술(M — 수신 경계 판정: 접힌 중첩 컴포넌트 · 바운드 행 · 같은 정의의 instance 둘, 입력 변수의 instance 단위 해석) / 성능(M — 입력 변수를 읽는 보기는 instance 마다 행이 다르므로 그 bound node 의 행 소스가 record 단위가 된다, 다른 보기는 무변경) / 유지보수(M — 어휘 +2, 검증 · 패널 2 · code view 가 같이 움직여야 한다 · property 이름이 RAC prop 과 겹치면 code view 역변환이 갈린다) / 마이그레이션(M — contract 52, 개발 단계라 코드 0).

### 대안 D: 코드 전용 — code view 에서 `onSelect` prop 을 쓰면 문서가 따라 생긴다

- 설명: 패널 없이 code view 만 props 선언 · 핸들러를 받고, 문서에는 그 결과를 기록한다.
- 위험: 기술(M) / 성능(L) / 유지보수(**H** — 패널에 없는 기능 = 비개발자 경로 상실, 사용자 결정 「코드 전용 기능은 두지 않는다」 위반) / 마이그레이션(L). **기각 (제약 위반)**.

### 대안 E: 루트 type 의 RAC 이벤트를 instance 이벤트로 (지금 상태 유지)

- 설명: instance 의 When 은 루트 type 의 RAC 이벤트 — 루트가 ListBox 면 `onSelectionChange` 가 보인다.
- 위험: 기술(L) / 성능(L) / 유지보수(**H** — 루트가 Popover · frame · Dialog 인 컴포넌트 (시나리오) 는 이벤트 0 · 안쪽 요소의 이벤트를 올릴 수 없다 — 부분해) / 마이그레이션(L). 루트 type 이벤트는 C 에서도 그대로 남는다 (제거 아님).

## Decision

**대안 C 채택.** 다섯 표면 열로 적는다 (사용자 원칙 2026-10-30).

1. **catalog (문서)** — `ComponentPropertyKind` 에 `event` · `variable` 을 더한다 (contract 52).
   - `event`: `{ key, name, kind: "event", targets: [], valueType?: "string" | "number" | "boolean" | "object" | "array" }` — target 없음 (검증 분기), `valueType` 은 패널 · code view 표시용 (없으면 「값」).
   - `variable`: `{ key, name, kind: "variable", targets: [], variableId }` — 정의가 template 루트 소유의 `StateVariableEntry` 하나를 가리키고, 그 변수는 `input: { propertyKey }` 표지를 갖는 **파생 변수** 다 (ADR-292 타입 그대로 — string · number · boolean · date · object · array, 기본값 = 정의의 기본값). template 안에서는 `{{ name }}` · `!var.<id>` 로 읽는 보통 변수이고 **쓰기는 거절** 된다 — 문서 검증 (`setState` Do 의 `variableId` 가 입력 변수면 `INPUT_VARIABLE_READ_ONLY`) · 실행 (`writeState` 같은 사유) 둘 다.
   - **variable 의 prop 계약 (리뷰 h2)**: `componentPropertyAccepts` 가 variable key 를 그 변수의 선언 타입으로 낸다 — string · number · boolean · date (date 는 ISO 글자라 `string` 계약 + `isDateValueText` 검사) 는 리터럴 또는 참조, object · array 는 **참조만** (`AuthoredValue` 가 JSON 을 담지 않는다 — 리터럴은 `PROP_TYPE_MISMATCH`). 참조 표현은 규칙 값과 같은 `"!var.<변수 id>"` 문자열이고, `validatePropWrites` 가 variable key 의 참조 문자열을 `PropVar` · `{key}` 바인딩과 같은 자리의 **셋째 예외** 로 받되 참조 대상이 있고 (`DANGLING_VARIABLE`) · 그 instance 노드에서 보이는 변수이며 (소유자 사슬 → page → project — `catalogVisibleVariableEntries` 와 같은 술어를 shared 로 옮긴다, ADR-288) · 타입이 같을 (`STATE_VALUE_TYPE`) 때만. 참조 id 는 `referencedIds` 에 든다 — 참조된 변수 삭제가 instance 쓰기를 찾는다 (ADR-288 의 「사용처가 같이 간다」).
   - Do `emit`: `{ opcode: "emit", propertyKey, value?: Scalar }` — 검증: 규칙 주인이 어떤 project 정의의 template 안 노드이고 (`catalogOriginRootOf`) 그 정의의 `properties` 에 `event` 인 `propertyKey` 가 있다. `value` 는 capability 의 `value` 와 같은 자리 · 같은 표기.
   - When `property:<key>`: trigger 문자열에 접두 `property:` 를 허용 — 검증: 규칙 주인이 project 정의의 instance 노드이고 그 정의에 `event` 인 `key` 가 있다 (등록표 집합 밖이지만 이 조건으로 통과). 인자는 `value` 하나 (`!event.value`).
   - 그 밖 무변경: 변수 가시성 사슬 (page 에서 끝) · `TARGET_IN_TEMPLATE` · ADR-281 대체 맵 — 받는 쪽 page 규칙이 변수 쓰기 · 닫기를 하므로 고칠 필요가 없다.
2. **실행기 — 수신 경계는 render record 가 아니라 논리 instance 경계이고, 수신자는 경계 **경로** 로 식별한다 (리뷰 h1 · Round 2)**. shared 함수 하나 `componentBoundariesOf(record)` 가 record 의 `instancePath` (바깥 instance) 와 `collapsedSourceIds` (접힌 층 — Outer 의 루트 J 처럼 **그 자체가 instance 인** 층) 를 합쳐 바깥 → 안쪽 순서의 경계 목록을 돌려준다 (resolver 의 `collapseLayers` 와 같은 판정 — 두 곳에 두지 않는다). 각 경계는 `{ instanceId, definitionId, occurrence }` 이고 **`occurrence` = 그 경계까지의 논리 instance 경로 전체 + 반복 행 문맥** (`I1/J` · `I1/J@row-3` — record identity `instancePath.join("/") + "::" + sourceId` 와 같은 모양). 문서 `instanceId` 는 graph 조회용이고 식별자가 아니다 — Outer 의 template 노드 J 는 모든 Outer instance (I1 · I2) 에서 같은 id 로 그려지므로 (Round 2 반례). `DispatchDeps.emit(propertyKey, value, context)` 의 세션 구현: 실행 record 의 경계 사슬을 **안쪽부터** 걸어 규칙 주인의 정의 (`catalogOriginRootOf(graph, entry.ownerId)`) 와 `definitionId` 가 같은 첫 경계 = 수신 경계. 규칙 주인이 **그 정의의 instance 노드 자신** (중첩에서 Inner instance J 의 규칙이 Outer 의 event 를 다시 올리는 wrapper) 이면 J 의 경계 자신은 건너뛰고 그 바깥부터 찾는다. 수신 색인은 `occurrence` → `key` → 규칙 목록 (Preview 규칙 변환 때 `property:` 규칙을 핸들러 색인이 아니라 여기에 넣는다 — 규칙은 지금처럼 record 마다 변환되므로 그 record 의 경계 `occurrence` 로 등록된다) — Outer · Inner 가 같은 이름 `select` 를 가져도, 같은 Outer 가 I1 · I2 로 두 번 놓여도 `occurrence` 가 다르므로 섞이지 않는다. 재진입 가드: 진행 중 `(occurrence, key)` 집합 — 같은 수신자 · 같은 key 가 자기 실행 중에 다시 오면 실패 (`EMIT_REENTRANT`, 조용한 무시 금지). 받는 규칙 0 = `{ ok: true, kind: "emit", listeners: 0 }`. 수신 경계 없음 (Local page 에서 ◆ 를 직접 실행) = 성공 · `listeners: 0`. `effectiveInteractionsOf` (끈 규칙 · 대체) 는 수신 규칙에도 그대로 적용.
3. **Design / Properties 패널** — 원본 (◆) 의 Component properties 절: 종류 선택지 5 (Text · Boolean · Instance · **Event** · **Variable**). Event 는 이름 (+ 값 타입 선택) 만 — 대상 노드 선택 없음 · 「받는 instance N」. Variable 은 ADR-292 의 변수 행 (이름 · 타입 · 기본값) 모양. instance (◇) 의 절: Event 행은 값 칸 대신 「Interactions 에서 받기」 (해당 노드의 Interactions 로 이동), Variable 행은 타입별 값 입력 (object · array 는 입력 없이 참조만) + 「값 고르기」 (`!var` 참조 — `valueOptions.ts` 재사용, 후보 = 그 instance 노드에서 보이는 같은 타입 변수).
4. **Interactions 패널** — (a) 원본 template 안 노드의 Do 목록에 「Emit <이름>」 — 그 노드가 든 정의에 `event` property 가 있을 때만 (`exposure` 와 검증이 같은 술어) · 값 칸 = 기존 `ValueField`. (b) instance 노드의 When 목록에 그룹 「컴포넌트」 아래 `event` property 이름들 (루트 type 의 RAC 이벤트 그룹은 그대로 유지) · 인자 `value`. (c) 안내 1줄: 원본 노드의 Set state 후보에 사용 page 변수가 없는 자리에 「컴포넌트 밖으로 보내려면 Event property」. (d) Set state 의 변수 후보에서 입력 변수는 빠진다 (읽기 전용 — 후보에 없음 = 검증 거절과 같은 술어). 라벨 키는 `interactions.trigger.component.<key>` 유도 — 손 목록 0.
5. **Canvas** — event 는 **해당 없음** (시각 · 배치 · 선택 · Layers 무변경, 사용자 결정 4 = 표식 없음 권고). variable 은 **작성 값이 반영된다** — Canvas 의 `{{ }}` 환경이 Decision 7 의 같은 해석 함수로 instance 의 리터럴 (또는 참조한 변수의 **기본값**) 을 읽어 template 안 글자 · 보기 조건을 그린다 (Preview 와의 비대칭은 ADR-214 의 「Canvas = 기본값 env」 그대로). 새 그리기 코드 0.
6. **Code view (ADR-285 어휘, 1:1)** — page 파일: instance 요소에 핸들러 속성 `on<Name>={(value) => { …받는 Do… }}` (이름 규칙 = 사용자 결정 2 · R3) — 역변환은 속성 이름이 그 instance 정의의 `event` 이름이면 `property:<key>` 규칙으로 읽는다 · 거절 사유는 기존 `outsideVocabulary`. `variable` property 는 instance 속성 `<key>={리터럴 | 변수 이름}` (`!var.<id>` 참조 ↔ 그 변수의 코드 이름). 원본 쪽 `emit` 은 `props.on<Name>?.(value)` 로 — Local page 가 code view 에 열리면 거기서 (Phase 0 확인), 열리지 않으면 ADR B Step 6 (`components/*.tsx`) 이 같은 어휘표 행으로 투영한다. 어휘표 (`vocabulary.ts`) 행 2 는 이 ADR 에서 적는다 — 「어휘표에 있는데 read 가 없음」 은 ADR B G1 필드 대조 게이트가 막는다.
7. **입력 변수의 해석 · 갱신 경로 — 함수 하나 · 독자 넷 · 의존성 색인 하나 (리뷰 h3)**.
   - **해석 함수** `resolveInputVariable(graph, variableId, boundaries, env)` (shared `catalog/runtime/inputVariable.ts`): 변수의 `input.propertyKey` 로 그 정의의 경계를 `boundaries` (Decision 2 의 사슬) 에서 찾고 → 그 instance 노드 (경계의 `instanceId`, 행이면 그 행의 override 포함) 루트 props 의 key 값 → 리터럴이면 그 값 · `"!var.<id>"` 면 **바깥 경계의 env** 로 그 변수를 재귀 해석 (바깥 입력 변수 → 또 그 바깥 … → page · project 변수의 값) · 없으면 정의 기본값. 재귀 깊이는 경계 수로 유한.
   - **독자 넷이 같은 함수를 읽는다**: ① Canvas · Preview 의 `{{ }}` 환경 (`catalogStateEnv` — `byId` · `get` 에서 `input` 변수는 `read` 대신 이 함수, Canvas 는 env 가 기본값이라 참조 변수의 기본값이 나온다) · ② 보기 조건 · 정렬의 `!var` (`pageAndProjectStates` → `visibleStatesAt(graph, ownerId, source, boundaries)` 로 — 소유자 사슬이 template 루트를 만나면 그 루트의 입력 변수를 element scope 로 더한다; `catalogBindingQuery` 가 `boundaries` 를 받는다) · ③ 규칙의 `!var` (세션 `readVariable` → runtimeState 의 `read` 가 `input` 정의에는 **저장 값을 보지 않고** 세션이 주입한 `derive(scope)` 를 부른다 — `runtimeState` 정의에 `derive?` 가 있고 `write` 는 `input-read-only` 거절) · ④ Properties · Interactions 패널의 값 표시 (「지금 이 instance 에서는 admin」).
   - **의존성 색인** `inputVariableDependencies(graph)` (shared) — instance 루트 props 의 `!var.` 참조에서 `바깥 변수 id → 입력 변수 id` 맵을 만든다. `refreshState(names)` (`compositionRoot.ts`) 와 세션의 `state.subscribe` 는 바뀐 이름 · id 집합을 이 맵으로 **전이 폐쇄** 한 뒤 비교한다 — 부모 `roleFilter` 가 바뀌면 `role` 을 읽는 안쪽 글자 · 보기도 다시 읽힌다. 문서 변경 (instance 의 리터럴 편집) 은 보통 step 이라 그 instance 를 그리는 root 가 다시 해석된다 (`dataReaderRoots` 와 같은 길).
   - **instance 단위 행 소스 (R6)**: 입력 변수를 읽는 보기의 bound node 는 instance 마다 행이 다르다. compositionRoot 의 행 감싸개 (`rows`) 는 그 query 가 입력 변수를 읽을 때만 키를 `(sourceId, 경계 사슬)` 로 나눈다 — 읽지 않는 보기는 지금처럼 source 하나.

**위험 수용 근거**: C 의 MEDIUM 넷은 전부 「패널 · 검증 · 실행 · code view · Canvas 가 같은 함수를 읽는가」 로 귀결되고, 이 저장소는 그 모양을 이미 두 번 만들었다 (ADR-281 `effectiveInteractionsOf` · ADR-283 `resolveCapabilityTarget`). 같은 방식 (shared 함수 하나 + 반례 unit + live) 으로 R1 · R2 · R4 를 게이트에 건다. 입력 변수의 비용 (R6) 은 그 보기를 가진 bound node 에만 국한된다.

**기각 사유** — A: 원본에 의도가 남지 않고 변수 이름 규칙이 깨진다. B: 전역 하나를 instance 들이 덮는다 (우회로는 남겨 둔다 — 막지 않는다). D: 패널 동등 위반. E: 루트가 오버레이 · frame 인 컴포넌트에 이벤트가 0 (시나리오 자체가 그 모양).

## Consequences

### Positive

- 컴포넌트가 값을 내보내고 (event) 받는 (variable) 경계를 **원본이 선언**한다 — instance 마다 규칙을 복제하지 않고, 원본을 보면 무엇이 나가고 들어오는지 보인다. 시나리오 (팝오버 picker → 부모 page) 가 패널만으로 우회 없이 끝난다.
- 새 어휘는 Do 1 · When 종류 1 이고 레퍼런스 코드 모양 (콜백 prop · 속성) 과 1:1 이라 ADR B 가 `components/*.tsx` 를 만들 때 그대로 투영된다.
- 변수 가시성 · 대상 범위 (`TARGET_IN_TEMPLATE`) 의 기존 경계를 넓히지 않는다 — ADR-283 · 288 의 불변식 유지. 논리 instance 경계 함수 (`componentBoundariesOf`) 는 ADR-283 의 대상 해소 · ADR-281 의 상속 판정이 뒤에 같이 쓸 수 있는 공용 술어다.

### Negative

- contract 52 — 옛 개발용 문서 거부 (정책).
- Properties 패널의 종류 선택지 3 → 5, Interactions 의 When 그룹 1 추가 — 비개발자 화면 어휘가 둘 는다 (「Event」 · 「Variable」, i18n KO/EN).
- `emit` 의 수신은 RAC 핸들러 경로가 아니라 수신 색인 경로다 — 규칙 실행 경로가 둘 (`createElementHandlers` · receiver) 이 된다. 둘 다 `executeInteractionRule` 하나를 부르므로 Do 의미는 같다.
- 입력 변수를 읽는 보기는 instance 단위 행 소스가 되어 그 bound node 의 비용이 instance 수에 비례한다 (R6 — 읽지 않는 보기는 무변경).
