- base/detail 2단계 · 소비자별 수요 · GPU 업로드 큐 · 현재 필요 없는 detail 해제 — **C 등급**: 메모리를 두 벌 보관하고 전환 깜빡임이 생기며 이득은 이미지 많은 문서에서만. Phase 0 의 이미지 fixture 측정이 「메인 스레드 이미지 처리 잔여가 프레임 예산을 넘는다」 고 보일 때 별도 ADR.
- Picture 재생에서 이미지 명령을 다시 방문하지 않는 문제 (수요 수집을 draw 함수에 두면 캐시가 잘 될수록 수요에서 빠짐) — 수요 관리가 없으면 생기지 않는다. 위 C 등급 ADR 의 Context 로 넘긴다.
- ADR-266 L2 재바인드 인계 (`page-grid` · `root` 사유) — 이 ADR 은 image-loaded 사유를 재바인드에서 **빼는** 것이고 재바인드 자체는 고치지 않는다.
- Preview (DOM) 이미지 로딩 · 이미지 편집 명령 · 업로드 엔진 (ADR-201 · 235) — 바뀌지 않는다. 캐시 키 · `asset:` 해석은 그대로 (HC7).

### Hard constraints

- **HC1 픽셀 동일**: 이미지 로드가 끝난 뒤 새 경로의 픽셀이 같은 상태의 전체 재바인드 (`rebind` + 캐시 끔) 와 0 px 차 — object-fit 결과 (cover · contain · fill · none · scale-down) 포함. 로드 **전** placeholder 픽셀도 지금과 같다. **디코더 arm 을 따로 둔다** (r1 M4): 같은 노드를 옛 `MakeImageFromEncoded` 경로 ↔ 새 디코더 경로로 그려 0 px 차 (반투명 PNG 포함) — `setImagePartialOff` 는 splice 만 끄므로 디코더 회귀를 못 본다.
- **HC2 상태 보존** (r1 H3): 이미지 완료는 문서 · property dirty 를 **소비한 것으로 치지 않는다**. 같은 프레임에 도착한 편집 · 삭제 · 스크롤 · 이미지 완료의 최종 상태가 fresh bind 와 같다 (G2 가 명령 · 맵 · 픽셀로 대조).
- **HC3 카운트 먼저**: Phase 0 이 이미지 fixture 변형에서 아래 지표를 등급 A 로 고정하고, 수정과 같은 커밋에서 ratchet 상한이 내려간다 (ADR-246 · `--add-keys`). 목표: **image-loaded 재바인드 0 · 그 사유로 해제되는 picture · paragraph 0 · `MakeImageFromEncoded` 호출 0** (Phase 3a 뒤).
- **HC4 비용 이동 금지 — 세 집행 경로** (r1 M5): ① **A 결정적 카운트** (before/after 에서 같은 일을 센다 — 코덱 호출 수 · 이미지 처리 횟수 · splice 명령 쓰기 수 · hover · pan · pick 카운트) 는 ratchet. ② **B 예산** (Phase 0 에 없던 새 작업 — readback 바이트 · WASM 복사 바이트 · 텍스처 생성 수 · 프레임당 완료 처리 수) 은 Phase 0 **이내가 아니라** fixture 로 계산되는 명시 상한 (이미지당 1 회 · 프레임당 N 개) — 결정적이므로 ratchet A 로 등록하되 상한은 fixture 산식. ③ **wall-clock** (프레임당 이미지 처리 ms) 은 A 로 고정하지 않는다 — G4 production 짝에서 방향만. 기존 0 을 조용히 올리지 않는다.
- **HC5 D3 대칭 · 문서 형식 변경 0**: Skia 전용 시각 효과 0 · 문서 · 저장 schema · `asset:` ref · 캐시 키 변경 0.
- **HC6 initial 번들 상한**: Worker 를 두면 lazy chunk 로만 — Builder initial gzip ≤ 1,421,000 B (ADR-201 재승인, 만료 2026-10-25). `adr201-bundle-gate.mjs` 는 pre-push 가 아니라 **G4 에서 수동 실행** 한다 (`.githooks/pre-push` 는 ADR-246 ratchet 만 돈다 — r1 확인).
- **HC7 수명 계약 유지**: ADR-153 R2 (해제 순서 Picture → Image · `destroyCachedImage` 단일 경로 · 지연 큐) · ADR-174 (paragraph 수명 = 노드 수명) · `cacheGeneration` in-flight 무효화 (I-H5) · `asset:` 해석 (ADR-235) · ADR-263/264 splice 계약 (`applyCommitSubtreeCommandPatch`) 은 손대지 않는다. 역참조는 캐시 핸들이 아니라 **node data 의 `src`** 에서 만든다 (F2b).

### Soft constraints

- 측정 무결성 5-질문: Q1 이미지 fixture 는 합성물 — **규모 전용** (이미지 수 · 바이트 · 완료 분산). Q2 불리 = 완료가 여러 프레임에 걸치는 상황에서 편집 · 줌 · 같은 프레임 편집 + 완료. Q3 대조군 = 같은 fixture 의 HEAD worktree 빌드. Q4 소비 경로 = 콜백 → dirty seed → `scene.sync()` → splice → damage 가 실제 배선됐는지 G2 unit + live. Q5 oracle = 전체 재바인드 픽셀 · 옛 디코더 픽셀 (시스템 자신이 아닌 **다른 경로** 둘) + object-fit 손계산 1 건.
- 어휘 · 금지: 「O(1)」 주장 금지 — splice 는 소유 요소 서브트리 명령 수 k 에, damage 는 영역에 비례한다. Pen 의 수치는 비교 자료일 뿐 목표가 아니다.

## Alternatives Considered

### 대안 A: 단계적 — 카운트 → 완료 = 소유 요소 dirty seed (splice) → 치수 분리 → 디코딩 이동 (채택)

- 설명: Phase 0 이 이미지 fixture 변형으로 F4 · F5 · F3 (첫 그리기 디코딩) 의 몫을 세고 (go/no-go — F4 가 코드로 확정이라 사실상 go), Phase 1 이 node data 에 `src` 를 남기고 (F2b) binding 이 **URL → 소유 요소** 맵을 bind · splice · 해제와 같은 자리에서 유지한 뒤, 완료 통지를 **소유 요소의 dirty seed** 로 바꾼다 — 다음 `scene.sync()` 가 다른 pending 변경과 **같은 트랜잭션**으로 `patchSubtree(owner)` 를 돌려 node data 재구성 (이번엔 cache hit) · DRAW self span 교체 · picture 무효 · damage 합집합을 낸다 (F5c 경로 재사용, 재바인드 0). Phase 2 가 `image` 필드를 `{ src, naturalWidth, naturalHeight, bitmap }` 로 나눠 object-fit 입력을 원본 치수로 고정한다. Phase 3 이 디코딩을 메인 밖으로: **3a** `createImageBitmap(blob)` (브라우저 코덱, 메인 밖) → GPU surface 면 `MakeLazyImageFromTextureSource(bitmap, info, premul)` (texture-backed, 소유권 이전 — `close()` 안 함) · SW surface 폴백은 `MakeImageFromCanvasImageSource` (readback — 폴백 카운트), **3b** Worker 는 3a 뒤에도 메인 프로필에 코덱 · 리사이즈가 남을 때만 (사용자 결정 1). 완료 처리는 프레임당 상한 (B) 으로 나눈다.
- 위험: 기술 **L** (splice · ImageBitmap · texture API 모두 기존 경로 · 플랫폼 API, Worker 는 조건부) / 성능 **M** (splice 는 소유 서브트리 k 명령 · 텍스처 생성은 첫 그리기 프레임 — HC4 로 셈) / 유지보수 **L** (image-loaded 가 별도 경로가 아니라 **기존 dirty 경로의 seed 하나**) / 마이그레이션 **L** (문서 무변경 · 플래그 off 면 재바인드로 복귀).

### 대안 B: ADR-266 L2 의 재바인드 인계 (retire → bind → releaseRemaining) 를 image-loaded 에 적용

- 설명: 재바인드는 그대로 두고, 같은 내용으로 재등록되는 노드의 picture · paragraph 를 인계한다 (F5 의 미구현 L2 를 이제 구현).
- 위험: 기술 **M** (ADR-266 리뷰 r1 H1 의 교체 순서 문제 그대로) / 성능 **M** (명령 스트림 · 맵 · 공간 인덱스 재구성은 N 회 그대로) / 유지보수 **M** / 마이그레이션 L.
- 기각: 이미지 하나 때문에 무관한 노드 전부의 명령 · 맵을 다시 만드는 일 자체가 남는다. 인계는 다른 재바인드 사유에는 값어치가 있으나 ADR-266 꼬리이지 이 ADR 이 아니다.

### 대안 B2: 노드 재등록 + damage 만 (명령 스트림 불변) — Round 1 전 초안

- 설명: 완료 시 해당 노드 data 를 `registerSkiaNode` 로 바꾸고 bounds 를 damage 로.
- 위험: 기술 **H** (F5b — DRAW 는 파생 복사본이라 placeholder 가 남는다 · F2b — 미로딩 노드에서 URL 을 복구할 수 없다 · F4 — `sceneStale` 선지움을 유지하면 같은 프레임 편집 유실) / 성능 L / 유지보수 M / 마이그레이션 L.
- 기각: r1 H1 · H2 · H3 — 소비 경로가 registry 가 아니라 명령이다. 대안 A 가 그 자리를 splice 로 대체한다.

### 대안 C: 디코딩만 바꾸고 (`createImageBitmap`) 완료 통지는 그대로

- 설명: F3 의 `MakeImageFromEncoded` 만 바꾼다.
- 위험: 기술 L / 성능 **H** (F4 의 재바인드 N 회 그대로) / 유지보수 L / 마이그레이션 L.
- 기각 (단독으로는): 재바인드가 남는다. 디코딩 이동은 대안 A 의 Phase 3a 로 **흡수**.

### 대안 D: Pen 자산 관리자 전체 (소비자별 수요 · base/detail · 업로드 큐) 를 한 번에

- 위험: 기술 **H** (수요 수집이 picture 재생과 어긋남 · idle 미리 기록의 화면 밖 참조 구분) / 성능 **M** / 유지보수 **H** (소비자 5 종 중 Thumbnail · export 가 아직 없다) / 마이그레이션 M.
- 기각: C 등급 — 이득이 이미지 많은 문서에서만이고 F7 처럼 측정이 0 이다. Phase 0 fixture 측정 뒤 별도 ADR.

### 대안 E: 완료 통지만 모아 재바인드를 1 회로 (debounce)

- 위험: 기술 L / 성능 **M** (재바인드 1 회 잔존 · 창 동안 로드 지연이 보인다) / 유지보수 L / 마이그레이션 L.
- 기각: 낭비의 **횟수**만 줄이고 종류는 그대로. 로드 지연이 사용자 가시.

## Decision

**대안 A** — 단계적. 순서는 Phase 0 fixture · 카운트 → Phase 1 `src` 보존 + URL → 소유 요소 맵 + **완료 = dirty seed (splice)** → Phase 2 치수 분리 → Phase 3a texture-backed 디코딩 이동 → (사용자 결정 1) 3b. 위험 수용 근거: 완료 처리가 새 경로가 아니라 **이미 편집이 지나가는 dirty → `update()` → splice 경로의 seed 하나**가 되므로 같은 프레임의 다른 변경과 순서 · damage · 후퇴 규칙을 공유한다 (HC2). 문서 · 캐시 키 · 수명 계약 (HC7) 은 그대로다. splice 가 틀리면 전체 재바인드로 돌아가는 플래그 (dev 전역 `__composition_RENDER_PATH_DEBUG__.setImagePartialOff`) 와 옛 디코더로 돌아가는 플래그 (`setImageDecoderLegacy`) 가 live oracle 이자 롤백이다.

기각 사유 요약: B 는 재바인드 자체가 남고, B2 는 소비 경로 (명령) 를 놓쳤고, C 는 재바인드가 남아 3a 로 흡수, D 는 C 등급 (측정 0), E 는 횟수만 줄인다.

**사용자 결정 N 건** (execute-adr 가 닿을 때 묻는다):

1. **Phase 3b Worker 진입** — **답 (2026-10-18): 생략** (3a 뒤 메인의 decode 이벤트 0 — breakdown §7 Phase 3a). 원 조건: 3a 뒤에도 메인 프로필에 코덱 · 리사이즈가 남을 때만 (`createImageBitmap` 은 Chrome · WebKit 에서 메인 밖 디코딩이지만 리사이즈 옵션은 구현에 따라 메인). 남지 않으면 3b 생략.
2. **이미지 fixture 의 출처** — 생성 PNG 를 `asset:` ref (IndexedDB) 로 넣을지, 하니스 `page.route` 정적 URL 로 둘지. 기본은 **둘 다 한 변형씩** (`app-pages-images` · `app-pages-images-asset`).
3. **종결 미달** — HC4 ③ wall-clock 참고 목표 (로드 중 편집 p99 ≤ 20 ms · drop < 1 %) 미달 시 측정 기록으로 종결할지, Phase 를 더할지.

## Consequences

### Positive

- 이미지 하나의 완료가 scene 전체 (명령 스트림 · 맵 · picture · paragraph) 를 다시 만들지 않는다 — 로드 중 편집 · 줌이 이미지 수에 비례해 느려지지 않는다.
- 완료 처리가 편집과 같은 dirty 경로를 타므로 같은 프레임의 다른 변경을 잃지 않는다 (지금의 `sceneStale` 선지움 부수 효과를 설계로 대체).
- 코덱이 메인 스레드에서 빠지고 (Preview 와 같은 조건), GPU surface 에서는 readback 없이 텍스처로 간다.
- 원본 치수와 표시 bitmap 이 분리돼, 뒤의 C 등급 ADR (base/detail) 이 object-fit 를 깨지 않고 들어올 자리가 생긴다.
- 이미지 경로가 처음으로 하니스 · ratchet 에 들어간다 (F7 해소).

### Negative

- node data 에 `src` 필드 하나, binding 에 URL → 소유 요소 맵 하나가 는다 — bind · splice · 해제와 같은 자리에서 관리해야 한다 (R2).
- 텍스처 생성 · SW 폴백의 readback 은 여전히 메인 스레드 — 비용이 0 이 되는 것이 아니라 **코덱 몫이 빠지고 자리가 바뀐다** (HC4 가 세 경로로 세는 이유).
- ~~texture-backed 이미지는 GL context 수명에 묶인다 (R8) — context 소실 처리가 는다.~~ Phase 3a 실측으로 반증 — lazy texture 이미지는 복원된 context 에 다시 올라간다 (소실 처리 0).
- Worker 를 두게 되면 (3b) builder 에 새 실행 표면이 생긴다 — 사용자 결정 1 로 묶어 둔다.
