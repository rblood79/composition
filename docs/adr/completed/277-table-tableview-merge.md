## Context

**Domain**: D2 (표 컴포넌트의 이름 · prop 표면 — S2 `TableView` 의 축을 받는 catalog type 이 둘) + D3 consumer 정합 (같은 RAC `Table` 을 두 rule · 두 CSS · 두 DOM 렌더러로 그린다). D1 (RAC Table DOM) 은 건드리지 않는다 — 두 type 모두 이미 RAC `Table` (+ `ResizableTableContainer`) 이고 부품 (TableHeader · Column · TableBody · Row · Cell) 은 같은 노드 · 같은 RAC 부품이다 (ADR-256 Phase 5i · ADR-257 Phase 5).

같은 RAC 컴포넌트를 두 type 으로 두어 생기는 비용: 소스 47 파일 · 테스트 26 파일이 TableView 를 참조하고, 표 하나를 고칠 때마다 두 rule · 두 CSS · 두 DOM 렌더러 · 두 origin template · `"Table" || "TableView"` 쌍 14 자리를 같이 고쳐야 한다. 그리고 두 표의 기능이 어긋나 있다 — 데이터를 묶을 수 있는 표 (Table) 는 열 · 행이 빈 채로 나오고, 열 · 행이 보이는 표 (TableView) 는 데이터를 묶을 수 없다. S2 1.8.1 (D2 정본) 에는 `TableView` 하나뿐이고 RAC (D1 권위) 에는 `Table` 하나뿐이다 — 이 저장소는 S2 TableView 의 prop 축을 이미 Table 에 다 옮겨 두었다 (ADR-257 Phase 3, `d2S2Alignment` 가 Table ↔ S2 TableView 로 대조).

**이름의 선례**: catalog type 이름은 RAC 컴포넌트 이름이다 (D1 — `.react-aria-<Type>` class · RAC 부품 매핑). S2 가 다른 이름을 쓰는 컴포넌트도 RAC 이름을 둔다 — GridList (S2 ListView) · ToggleButtonGroup (S2 ActionButtonGroup) · Tree (S2 TreeView). 반대 선례는 없다 — TableView 는 「RAC 에 없는 S2 전용 이름」 으로 남아 있던 유일한 표 이름이고, ADR-257 Phase 5 가 그 DOM 을 RAC Table 로 옮긴 뒤로는 이름만 다르다.

**이력**: TableView 는 ADR-030 (2026 상반기) 의 「강화 Table 컨테이너 (`@tanstack/react-table`)」 로 시작해 ADR-912 R7 G1-b (2026-06-15) 에서 catalog shell 로, ADR-256 Phase 11 (2026-10-12) 에서 RAC 컬렉션으로, ADR-257 Phase 5 (2026-10-10) 에서 RAC Table 위로 옮겨졌다. 각 단계가 Table 과의 차이를 하나씩 지웠고, 남은 차이는 위 표가 전부다.

### 제약

- **D3 대칭**: 통합 뒤 표 하나가 Canvas · Preview 에서 같은 상자 · 같은 열 트랙 · 같은 행을 그려야 한다 (`/cross-check` · ADR-257 parity 테스트).
- **ADR-257 결정 보존**: 열 트랙 (`_tableTracks`) · Column `allowsSorting` · `allowsResizing` (조절 열이 있는 Table 만 RAC container 안) · `selectionStyle` · `overflowMode` 전파 · 바운드 행 정렬 (`tableSort`) 은 그대로다. 「TableView 는 늘 container 안」 (Phase 5) 은 TableView 가 없어지면서 사라진다 — Table 의 Phase 4 규칙 하나만 남는다.
- **마이그레이션 코드 금지** (사용자 2026-10-14): TableView instance 가 든 옛 문서를 Table 로 바꾸는 변환은 넣지 않는다. origin 정의 삭제 + Table template 구조 변경이므로 구조 변경 계약 Step 3 에 따라 contract 를 올려 옛 개발용 프로젝트를 거부한다 (`UNSUPPORTED_LIBRARY_CONTRACT` · `UNSUPPORTED_PROJECT_FORMAT` — ADR-276 Decision 7 과 같은 경로). TableView 정의를 지우면 옛 문서는 `DANGLING_DEFINITION` 이 되지만 contract 거부가 먼저다.
- **저장된 문서 영향**: ADR-257 Phase 0 (2026-10-10) 집계 — 로컬 프로젝트의 Table · TableView 0. 개발용 프로젝트 (adr276-live 등) 는 재생성.
- **D2 게이트**: `d2S2Alignment.static.test.ts` 의 Table ↔ S2 TableView 대조는 그대로 통과해야 한다 (Table 의 accepts 는 바뀌지 않는다).
- 성능: initial 번들 상한 (ADR-201 재승인) · ratchet (ADR-246) 안 — 삭제만 있어 감소 방향.

## Alternatives Considered

### 대안 A: 두 type 유지 + 기능 차이를 서로 채운다

- 설명: TableView accepts 에 `dataBinding` · `heightMode` · `height` · `size` 를 더하고 `projectTableRows` · `catalogTableHeight` 가 TableView 도 받게 하며, Table origin template 에 starter 열 · 행을 넣는다. 팔레트는 둘 그대로.
- 위험: 기술(M) — `projectTableRows` · `catalogTableHeight` · DOM 렌더러 둘 · rule 둘이 같은 기능을 두 번 갖게 된다 / 성능(L) / 유지보수(H) — 비용의 원인 (같은 RAC 컴포넌트의 type 둘) 이 그대로 남고 둘 사이의 어긋남이 다시 쌓인다 (이번에 발견한 「데이터는 Table · 열은 TableView」 어긋남이 그 결과다) / 마이그레이션(L) — 문서 변경 0.

### 대안 B: TableView 를 Table 에 통합 — type · origin · rule 은 Table 하나 (RAC 이름), TableView 의 starter template 을 Table origin 이 받는다

- 설명: TableView 의 origin 정의 · template (노드 12) · binding · rule · 생성 CSS · DOM 렌더러 · 팔레트 항목 · 카탈로그 entry · `"Table" || "TableView"` 쌍 14 자리 · 로드 전환 (`s2PropAlignment` TableView 2 줄) 을 삭제한다. Table 은 지금 accepts 그대로 (S2 TableView 축 5 + 높이 2 + 데이터 + size — TableView 의 축은 이미 전부 Table 에 있다). 팔레트 「table」 의 origin template 은 TableView 의 starter (Column ×3 Name · Type · Status + Row ×1 Cell ×3) 를 받아 놓는 순간 표가 보이고, 데이터를 묶으면 `projectTableRows` 가 TableBody 의 자식을 바운드 행으로 바꾼다 (지금 규칙 그대로 — 1486 ~ 1500행, body 의 children 을 투영 행으로 교체). 상자 모양은 Table rule (fill base · S/M/L · `heightMode` · quiet = `containerVariants`) 하나, DOM 은 `CatalogTable` 하나 (조절 열이 있을 때만 container — ADR-257 Phase 4). TableView 의 rule 값 중 Table 에 없는 것 (fill `layer-1` · height auto · 늘 container · 생성 CSS) 은 버린다 — S2 TableView 의 시각은 어느 쪽도 그대로 옮기지 않았고 (둘 다 house 값), Table 쪽이 수동 `Table.css` 와 Canvas 가 같이 읽는 정본이다. contract +1.
- 위험: 기술(M) — 참조 47 파일 · 테스트 26 파일의 삭제 · 재작성 (대부분 집합에서 이름 한 줄 빼기 · 주석) 과 Table template 구조 변경 (노드 +7) / 성능(L) — 번들 · rule 표 감소 / 유지보수(L) — 표 하나 · rule 하나 · CSS 하나 · 렌더러 하나 / 마이그레이션(M) — contract 증가로 옛 개발용 프로젝트 거부 (변환 0 · 저장 문서 영향 0).

### 대안 C: Table 을 TableView 에 통합 — type 이름은 S2 의 TableView

- 설명: 반대 방향. Table 의 데이터 바인딩 · 높이 축 · rule · `Table.css` 를 TableView 이름으로 옮기고 Table 을 지운다 (전 세션 조사가 「S2 는 TableView 하나뿐」 을 근거로 적은 방향).
- 위험: 기술(H) — 「Table」 이름에 묶인 코드가 훨씬 많다: `projectTableRows` 의 `"Table"` 판정 · `catalogTableHeight` 의 `bindingId === "table"` · `tableBinding` 참조 5 파일 · `Table.css` 889줄 (`.react-aria-Table` 선택자 — RAC class 라 바꿀 수 없다: DOM 요소는 RAC `Table` 이므로 class 는 `react-aria-Table` 로 남고 type 이름만 TableView 가 되어 type ↔ class 가 어긋난다) · `[data-node-table]` · ADR-241 · 257 본문 / 성능(L) / 유지보수(H) — catalog type = RAC 이름 선례 (GridList · ToggleButtonGroup · Tree) 를 표만 깨고, 부품 (TableHeader · Column · Row · Cell) 은 RAC 이름인데 부모만 S2 이름 / 마이그레이션(M) — contract 증가는 B 와 같다.

## Decision

**대안 B** — 표는 Table 하나다. TableView 의 type · origin · binding · rule · CSS · DOM 렌더러 · 팔레트 항목을 삭제하고, 팔레트 Table 의 origin template 이 TableView 의 starter (열 3 · 행 1) 를 받는다. Table 의 prop 표면은 바뀌지 않는다.

- 위험 수용 근거: 기술 M 은 Phase 0 의 참조 전수 인벤토리 (G0 — 소스 47 · 테스트 26 을 「삭제 / 집합에서 제거 / 주석 / 재작성」 으로 분류) 와 Phase 1 단위 (G1 — 새 Table instance 의 해석 자식 = 열 3 · 행 1, 바인딩하면 투영 행) 로 흡수한다. 마이그레이션 M 은 「변환 코드 없음」 원칙 안에서 contract 증가 하나로 닫는다 (저장 문서 영향 0 — ADR-257 Phase 0 집계).
- 기각 사유: A 는 비용의 원인 (같은 RAC 컴포넌트의 type 둘) 을 남기고 이번에 드러난 어긋남 (데이터 ↔ 열) 을 두 번 구현한다. C 는 RAC class (`react-aria-Table`) 와 type 이름이 어긋나고 「catalog type = RAC 이름」 선례 (GridList · ToggleButtonGroup · Tree) 를 표만 깬다 — S2 이름은 팔레트 라벨 · D2 게이트의 대조 대상 (`Table: "TableView"`) 으로 이미 남아 있다.
- 결정 내용:
  1. **type · origin**: `origin-component-tableview` 정의와 template 노드 12 (`lib:template:component-tableview*`) 삭제. `TableView.binding.ts` · `bindings/index.ts` 등록 · `componentCatalog.ts` entry (470행) · `PALETTE_REUSABLE_ORIGIN_TYPES` 의 "TableView" · `paletteItems.ts` overlay (202 · 292행) · `metadata.ts` · `unified.types.ts` `createDefaultTableViewProps` · `factories/constants.ts` · `composition-vocabulary.ts` · i18n `tableView` 삭제.
  2. **Table origin template**: `lib:template:component-table` 의 TableHeader 에 Column ×3 (`Name` · `Type` · `Status`), TableBody 에 Row (table-row origin instance) ×1 + Cell ×3 (`Item 1` · `File` · `Active`) — TableView template 의 자식을 그대로 옮긴다 (노드 +7). 루트 props (`selectionMode none · size S · height 400`) 는 그대로 (사용자 결정 2 의 「starter 넣음」 전제). 놓는 순간 slot 내용은 소유 노드가 된다 (`ownSlotContents`) — 즉 놓은 Table 에는 **기존 열 3 이 있다**.
     - **첫 연결 (Round 1 h1)**: 데이터를 묶으면 `projectTableRows` 가 TableBody 의 자식을 바운드 행으로 바꾸지만 (지금 규칙), 칸 값은 Column 의 `key` 로 `row.values` 를 읽으므로 starter 열의 key (`name` · `type` · `status` — `resolveTableColumnKey` 의 글자 소문자 규칙) 는 `title` · `price` 같은 schema 와 맞지 않아 전부 빈다. 그리고 Quick Connect 의 `resolveColumnMode` (`quickConnectPlan.ts` 38 ~ 52행) 는 기존 열이 있으면 기본 `preserve` 라 schema 열을 넣지 않는다 (`catalogQuickConnectHost.ts` 122 ~ 162행 — `create` · `replace` 때만 `insertTableColumns`). 그래서 규칙을 하나 더한다: **binding 이 없던 Table 의 첫 Quick Connect 는 `replace`** (starter 열 → schema 열, 사용자 결정 3) 이고, 이미 묶인 Table 의 재연결은 지금처럼 `preserve` 기본 + 「교체」 스위치 (`DataTableCreator` 가 안 맞는 열 key 를 실행 전에 보인다 — `unmatchedColumnKeys`). `resolveColumnMode` 가 「현재 binding 유무」 를 입력으로 받는다 — 판정은 **`target.binding.props != null`** 이다 (Round 2 h1: `QuickConnectTarget.binding` 은 `bindingSnapshot` 이 늘 돌려주는 `{ props: nodeOf(id)?.binding }` 객체라 미연결 Table 에서도 객체 자체는 있고, 실제 `DataBindingRef` 는 그 `props` 다 — `catalogQuickConnectHost.ts` 67 ~ 69행).
     - **`replace` 경로의 정적 행**: 지금 `insertTableColumns({ replace: true })` 는 header 만 바꾸고 TableBody 의 정적 Row 는 건드리지 않는다 (`collections.ts` 1294행 `body = input.replace ? undefined : …`) — 바운드 상태에서는 투영 행이 body 를 가려 보이지 않지만, 바인딩을 해제하면 Row 의 Cell 3 ↔ Column N 이 어긋나 RAC 가 던진다 (ADR-256 Phase 5i G0 ⑨). `replace` 는 정적 Row 마다 Cell 을 새 열 수만큼 다시 만든다 (옛 Cell 삭제 · 새 열마다 빈 Cell — `tableAlignedIn` 이 참).
     - starter 를 안 넣는 선택 (사용자 결정 2 (b)) 이면 이 절은 비어 있고 지금 `create` 경로 그대로다.
  3. **rule · CSS · DOM**: `COMPONENT_RULES_TABLE.TableView` 삭제 · `generated/TableView.css` 는 **`git rm`** (Round 1 비차단 정정 — `generate-css.ts` 는 목록의 CSS 를 쓰기만 하고 지운 rule 의 옛 파일을 지우지 않는다, 104 ~ 132행; `--check` 는 남은 목록만 검사) · `index.css` import 제거. `CatalogTableView` · `INTERNAL_RENDERERS.tableview` 삭제. `Table.css` 의 `.react-aria-TableView` 선택자 (resizer) 제거. Table 의 상자는 지금 Table rule + `Table.css` 그대로 — 조절 열이 있을 때만 RAC container (ADR-257 Phase 4).
  4. **`"Table" || "TableView"` 쌍 14 자리**: `TRACK_TABLE_TYPES` · `TABLE_OWNERS` · `presence.ts` 3 · `domBinding.runtime.ts` 5 · `sizePropagation.ts` · `collectionItems.ts` · `componentTraits.ts` · `nestingRules.ts` · `requiredParts.ts` · `ruleDefinition.ts` · `itemInsert.ts` · `ariaLabelNeed.ts` 에서 "TableView" 만 뺀다 (동작 변경 0 — Table 쪽은 그대로).
  5. **로드 전환**: `s2PropAlignment.ts` 의 TableView 2 줄 (`CATALOG_BOOLEAN_VARIANTS` · `variant: quietOf`) 삭제 — contract 거부가 옛 문서를 막으므로 전환 대상이 없다.
  6. **옛 문서**: `LIBRARY_CONTRACT_VERSION` 을 1 올린다 (구조 변경 계약 Step 3 — 지금 43, 구현 시 소스 상수를 읽는다). 변환 · dual-write 0. 개발용 프로젝트는 재생성.
  7. **D2 게이트 · 문서**: `d2S2Alignment.static.test.ts` 의 `Table: "TableView"` 대조는 그대로 (Table 의 S2 정본 타입이 TableView 라는 사실은 변하지 않는다). `.claude/rules/catalog-subparts.md` 의 「Table · TableView」 서술 · binding 주석 (TableHeader · TableBody · Row · Column · Cell) 을 Table 하나로 고친다.

## Consequences

**Positive**

- 표 type 하나 · origin 하나 · rule 하나 · CSS 하나 (`Table.css`) · DOM 렌더러 하나 — `"Table" || "TableView"` 쌍 14 자리와 생성 `TableView.css` · `s2PropAlignment` 전환 2 줄이 없어진다.
- 팔레트에서 「table」 하나로 열 · 행이 보이는 표를 놓고 그대로 데이터를 묶는다 — 「데이터는 Table · 열은 TableView」 어긋남이 사라진다.
- catalog type = RAC 이름 선례가 표에도 적용된다 (S2 이름은 D2 게이트의 대조 대상 · 팔레트 라벨에만).

**Negative**

- contract 증가 — 개발용 프로젝트를 다시 만든다.
- 옛 TableView 의 모습 (fill layer-1 · height auto · 늘 container) 은 없어진다 — Table 모양 (fill base · fixed 400 기본 · 조절 열 때만 container) 하나. 높이는 `heightMode` 로 auto 를 고를 수 있다.
- 조절 열이 있는 quiet Table 은 RAC container 상자의 테두리 1 px 가 남는다 (quiet 는 radius 만 0) — ADR-257 Phase 4 부터의 동작으로 이 ADR 이 바꾸지 않았다 (live 관찰 2026-10-21, 후속 판단).
