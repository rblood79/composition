### 제약

- **HC1 시각 결과 동일**: 모든 page 가 채워진 뒤의 record · 배치 · 그리기 명령은 지금의 일괄 빌드와 같다.
- **HC2 편집 파이프라인**: 명령 → `workspace.execute` → 검증 · commit → consumer → 저장 → History 의 순서와 원자성 (consumer 가 던지면 문서도 되돌아감) 을 바꾸지 않는다. 채움은 문서 · History · 저장을 쓰지 않는다.
- **HC3 초기 로드 < 3초** (CLAUDE.md 성능 기준).
- **HC4 프레임**: 사용자가 요청하지 않은 채움 (idle · 화면 진입) 은 입력 (pan · 선택 · 편집) 을 밀지 않는다 — 한 task 에 채움 단위 하나, 단위 사이에 양보한다. 사용자가 그 page 의 내용을 요구한 동작 (page 전환 · 그 page 의 노드 선택 · 명령 대상) 의 채움은 그 동작의 응답 시간에 속하고, 상한은 G4 가 정한다.
- **HC5 문서 · 저장 형식 변경 0** — 문서 변환 코드 없음.
- **HC6 번들**: ADR-201 Builder 초기 상한 (1,414,000 B, 만료 2026-11-25) 안.
- 측정 불가능한 제약: 실문서 분포 미상 · 사용자 Chrome 은 CPU 4x.

## Alternatives Considered

### 대안 A: 단계별 빌드 — page 틀을 먼저, 현재 · 화면 안 page 를 채우고 나머지는 idle 에

- 설명: root 는 처음에 page 마다 **틀** (page root record 하나 + 엔진의 frame 크기 잎) 만 세운다 (F4 — 자리는 내용 없이 정해진다). 세션의 현재 page 와 화면에 걸친 page 를 바로 채우고, 나머지는 idle 조각으로 문서 순서대로 채운다. page 전환 · 화면 진입 · 그 page 를 가리키는 선택은 즉시 채움을 요청한다. 채움은 문서 revision 을 움직이지 않는 region 재해석이다 (F5 선례). 끝나면 지금과 같은 전체 상태.
- 근거: Figma 는 2024-02 부터 파일을 page 단위로 불러온다 — 현재 page 만 먼저, 다른 page 는 요청 때 (plugin 계약 `documentAccess: "dynamic-page"` · `page.loadAsync()` · 전체 순회는 `loadAllPagesAsync()` 를 먼저 — [Figma: Migrating Plugins to Dynamically Load Pages](https://developers.figma.com/docs/plugins/migrating-to-dynamic-loading)). 브라우저의 `content-visibility: auto` 는 화면 밖 subtree 의 배치 · 그리기를 건너뛰고 자리는 `contain-intrinsic-size` 로 잡는다 ([web.dev: content-visibility](https://web.dev/articles/content-visibility)) — 「자리 먼저, 내용 나중」 이 같은 구조다.
- 위험:
  - 기술: **HIGH** — 채움은 증분 경로 (`apply` · 엔진 `addNode`) 를 page 단위로 쓰는 첫 사용이다. 일괄 빌드와 결과가 같은지 (F11), 채우는 중의 편집 · undo 가 틀 page 를 만났을 때의 처리, 글꼴 도착의 전체 교체 (F7) 가 미검증.
  - 성능: **MEDIUM** — 열기는 page 수와 무관해지지만 총 CPU 는 그대로거나 늘 수 있다 (증분이 일괄보다 노드당 비쌀 수 있음). page 한 장의 비용은 열기 시간 기울기로 4x 약 95 ms 로 추정될 뿐 실제 채움 1회는 재지 않았다 — 나눌 수 없는 큰 단위 (바운드 collection 행 · 깊은 instance) 는 한 task 가 길어진다 (R6).
  - 유지보수: **MEDIUM** — root 에 「틀 / 채워짐」 상태가 생기고, 전체를 순회하는 소비자 (F8) 가 그 상태를 알아야 한다.
  - 마이그레이션: **LOW** — 문서 형식 변경 0. 스위치 하나로 지금 경로 (전부 즉시 채움) 로 돌아간다.

### 대안 B: 화면 범위만 빌드 + 멀어진 page 내리기

- 설명: A 의 요청 채움만 두고 idle 채움을 하지 않는다. 화면에서 멀어진 page 는 record 와 엔진 노드를 내린다. record 수가 화면 넓이에 묶인다.
- 근거: Figma dynamic page loading 의 원형 (전체 접근은 명시적 `loadAllPagesAsync()`).
- 위험:
  - 기술: **HIGH** — A 의 위험 전부 + 전체 문서를 전제하는 소비자 (F8, 선택 identity 확인, 원본 편집의 instance 전파, 데이터 갱신의 독자 탐색) 가 「없는 page」 를 영구 상태로 다뤄야 한다. 내리기는 선택 · 미리보기 · 끌기 중인 record 와 충돌한다.
  - 성능: **LOW** — 열기 · 메모리 모두 문서 크기와 무관.
  - 유지보수: **HIGH** — 「전부 채워짐」 이라는 종착 상태가 없어 새 전체 순회 소비자마다 부분 상태 계약이 필요하다.
  - 마이그레이션: **MEDIUM** — 소비자 계약이 바뀌어 되돌리기 범위가 넓다.

### 대안 C: 빌드를 Worker 로 옮긴다

- 설명: `flatten` · 글자 측정 · 엔진 배치를 Worker 에서 돌리고 main 은 결과를 받는다.
- 근거: OffscreenCanvas · Worker 기반 편집기의 일반 패턴.
- 위험:
  - 기술: **CRITICAL** — consumer 는 transaction 안에서 동기로 돌고 실패하면 문서를 되돌린다 (HC2). 엔진 트리가 Worker 에 있으면 편집마다 비동기 왕복이 되거나 엔진을 둘 두어야 한다. 글자 측정은 CanvasKit paragraph 가 oracle 이라 Worker 에도 CanvasKit · 글꼴이 필요하다.
  - 성능: **MEDIUM** — main 은 비지만 record · geometry 전송 비용과 메모리 2배.
  - 유지보수: **HIGH** — 두 실행 환경의 상태 동기.
  - 마이그레이션: **HIGH** — 파이프라인 순서 계약 변경.

### 대안 D: 빌드 결과를 저장해 두고 다시 쓴다

- 설명: record · 엔진 입력 (또는 geometry) 을 IndexedDB 에 문서 revision · 테마 · 글꼴 · 엔진 버전 키로 저장하고, 열 때 맞으면 `flatten` · 측정을 건너뛴다.
- 근거: 빌드 캐시 일반 패턴.
- 위험:
  - 기술: **HIGH** — 키가 빠지면 틀린 배치가 조용히 나온다 (글꼴 도착 · DPR · locale · 데이터 행 · 엔진 수정). 저장 크기는 문서의 몇 배.
  - 성능: **MEDIUM** — 첫 열기 · breakpoint 전환 · 테마 변경 (F3) 에는 효과가 없고, 읽기 · 역직렬화가 다시 page 수에 비례한다.
  - 유지보수: **HIGH** — record 에 필드가 늘 때마다 캐시 형식 · 무효화가 따라간다.
  - 마이그레이션: **MEDIUM** — 저장소에 새 store.

### 대안 E: 구조는 두고 노드당 비용을 더 줄인다

- 설명: `flatten` · `styleOf` · 글자 측정의 상수를 계속 깎는다 (1단계 H1 과 같은 종류).
- 근거: 1단계가 열기를 13 ~ 19 % 줄였다.
- 위험:
  - 기술: **LOW**.
  - 성능: **HIGH** — 비례 관계가 남는다. 30 % 를 더 줄여도 4x 는 22 장에서 3초를 넘고, 넘는 장수만 뒤로 밀린다. HC3 를 문서 크기와 무관하게 만족할 수 없다.
  - 유지보수: **LOW**.
  - 마이그레이션: **LOW**.

### Risk Threshold Check

| 대안 | 기술     | 성능 | 유지보수 | 마이그레이션 | HIGH+ |
| ---- | -------- | ---- | -------- | ------------ | :---: |
| A    | HIGH     | MED  | MED      | LOW          |   1   |
| B    | HIGH     | LOW  | HIGH     | MED          |   2   |
| C    | CRITICAL | MED  | HIGH     | HIGH         |   3   |
| D    | HIGH     | MED  | HIGH     | MED          |   2   |
| E    | LOW      | HIGH | LOW      | LOW          |   1   |

- 모든 대안에 HIGH 가 있다 → 루프 1회: A 의 기술 HIGH 를 없애는 변형 **A′ (틀 없이 시간만 쪼개기 — 모든 page 를 지금 순서로 빌드하되 page 사이에 양보)** 를 검토했다. root 가 완성되기 전에는 workspace · session · Canvas 가 설 수 없어 (`workspace.ts:210` — 생성자가 root 를 요구) 첫 화면은 그대로 늦다. 응답성만 얻고 HC3 는 못 얻는다 → 기각.
- 루프 2회: E 의 성능 HIGH 는 구조에서 온다 (비례). 피하려면 A · B · C · D 중 하나가 필요하다.
- 결론: A 의 HIGH 1 (기술) 을 **수용하고 Gate 로 관리**한다 — 위험이 검증 가능한 명제 (동치 · 채움 중 편집 · 글꼴 · 단위 비용) 로 나뉘고, 되돌리기가 스위치 하나다.

## Decision

**대안 A — 단계별 빌드.**

1. **page 마다 공개 상태 둘**: 틀 (page root record + 엔진의 frame 잎) / 채워짐. 채우는 중인 page 는 자식 일부만 가진 틀이다 — 공개 판정은 `채워짐` 하나이고, 비공개 준비 상태를 두지 않는다. 높이가 내용에 달린 page root (F4) 는 틀로 둘 수 없으므로 첫 단계에서 채운다.
2. **채움 단위와 반영 경계**: 채움의 단위는 page 가 아니라 **region** 이다 — page root 의 직계 자식 subtree 하나, 문서 노드 수가 상한을 넘으면 그 자식들로 내려간다 (F5 의 `ownedChildren` 선택으로 「지금까지 반영한 자식 + 이번 단위」 를 해석). 단위 하나는 해석 · 엔진 반영 · 전달까지 **한 task 안에서 원자적으로** 끝나고, 단위 사이에는 이벤트 루프에 양보한다. 다음 단위는 「문서의 자식 − record 의 자식」 에서 매번 다시 구한다 — 이어 갈 준비물이 없으므로 문서 revision 이 바뀌어도 버릴 것이 없고, root 교체는 큐를 버리는 것으로 끝난다. 더 나눌 수 없는 단위 (바운드 collection owner 의 행 · 접힌 instance) 의 비용은 지금 그 owner 를 편집 · 데이터 갱신할 때의 재해석 비용과 같다 (새 지연이 아니다) — 그 최악값은 G0 ⑥ 이 잰다.
3. **요청은 둘로 나눈다**:
   - **비동기 (우선순위만 올림)**: idle 채움과 **화면 진입**. 순서는 세션의 현재 page → 화면에 걸친 page → 나머지 (문서 순서). 프레임마다 시간 예산 안에서 단위를 처리하고, 예산을 넘는 단위는 그 프레임에 하나만 한다. 여러 page 가 한꺼번에 화면에 들어와도 (축소) 큐의 순서만 바뀐다.
   - **동기 (상한 안에서)**: 사용자가 그 page 의 내용을 요구한 동작 — page 전환 · 그 page 의 노드를 가리키는 선택 · 명령 대상. 요청 대상 (선택한 노드 · 명령 대상까지의 조상 사슬과 그 subtree) 과 화면에 걸친 단위를 먼저 동기로 채우고, 시간 상한 (**4x 에서 150 ms** — 사용자 결정 2026-11-11) 에 닿으면 그 page 의 나머지는 큐 맨 앞의 비동기로 넘긴다. 요청 대상 자체는 상한과 무관하게 끝까지 채운다 (선택 · 명령이 없는 record 를 가리키지 않게). 처음 안 (「남은 단위를 끝까지」) 은 Phase 0 실측 (4x 최대 287 ms) 으로 상한을 넘어 바꿨다.
4. **채움은 문서 밖의 일**: revision · History · 저장 대기열 · Preview delta 를 움직이지 않는다 (F5 의 `refreshRows` 와 같은 지위). 실패는 둘로 나눈다:
   - **해석 · 엔진 반영 실패** (단위의 apply 가 던짐): journal 로 그 단위를 되돌린다 — record · 엔진 · 채움 상태가 단위 이전과 같다. 같은 문서 revision 에서는 그 단위를 다시 시도하지 않고 (반복 실패 방지) page 를 「채움 실패」 로 표시해 알린다. 문서가 바뀌거나 동기 요청이 오면 다시 시도한다.
   - **전달 실패** (apply 는 성공, 구독자 · Canvas 반영이 던짐): record 를 되돌리지 않는다 — 단위는 반영된 것으로 남는다 (`refreshRows` 의 지금 경계와 같다: record · 엔진이 정본, 구독자는 뒤따른다). 오류는 모아 호출자에게 던지거나 (동기 요청) 보고하고 (비동기), Canvas 는 다음 sync 에서 장면을 다시 묶어 맞춘다.
5. **root 교체도 같은 경로** (F3): breakpoint 전환 · 테마 · 글꼴 · DPR · 정의 보기 복귀가 현재 page 부터 채운다. 정의 보기 자체 (root 하나) 는 지금대로.
6. **종착 상태는 「전부 채워짐」**: 전체를 순회하는 소비자 (F8) 는 그 신호를 구독해 다시 읽거나, 필요한 page 의 채움을 요청한다. 화면 밖 page 를 내리지 않는다.
7. **글꼴**: 새 face 도착이 채움마다 root 전체 교체를 부르지 않게 한다 — 방법 (문서에서 요청을 미리 읽기 / 도착 시 그 글꼴의 글자만 다시 측정) 은 Phase 0 측정이 고른다.
8. **스위치**: dev 스위치로 「전부 즉시 채움」 (지금 동작) 을 남긴다 — 동치 게이트의 대조군이자 되돌리기 경로.

**위험 수용 근거**: A 의 HIGH 는 네 명제로 나뉘고 각각 게이트가 있다 (R1 동치 → G1, R2 채움 중 편집 → G2, R3 글꼴 → G3, R6 단위 비용 → G0 ⑥ · G4). R6 는 구현 전에 Phase 0 이 실측으로 먼저 판정한다 — 최악 단위가 상한을 넘으면 단위 상한 · 행 창이 Phase 1 범위에 들어간다. 틀은 F4 로 자리가 확정되어 채움이 다른 page 를 옮기지 않으므로, 채움 한 단위의 영향 범위가 page 하나 안의 region 이다. 문서 형식을 건드리지 않아 스위치로 되돌아간다.

**기각 사유**:

- **B**: 열기 목표 (HC3) 는 A 로 닿는다. B 가 더 주는 것은 메모리 상한인데, 지금 근거가 없다 (66 장에서 메모리 문제 실측 없음). 「전부 채워짐」 종착 상태를 없애면 전체 순회 소비자마다 영구 부분 상태 계약이 필요하다. A 의 틀 · 요청 채움 위에 나중에 얹을 수 있다 (사용자 결정 4).
- **C**: consumer 의 동기 · 원자성 계약 (HC2) 을 깨거나 엔진을 둘 두어야 한다 — CRITICAL.
- **D**: 틀린 배치가 조용히 나오는 실패 방식이고, 첫 열기 · root 교체 (F3) 에는 효과가 없다.
- **E**: 비례 관계가 남는다. 따로 계속할 수 있지만 이 ADR 의 목표를 대신하지 못한다.
- **A′**: 첫 화면 시간이 그대로다.

**범위 밖**: Preview · Publish root 의 page 범위 (F10 — 사용자 결정 3) · 화면 밖 page 내리기 (B) · 노드당 비용 절감 (E) · page 수와 무관한 몫 (≈ 0.6 s / 4x 2.6 s — 번들 · CanvasKit 초기화 · React mount) · **문서 읽기 · 검증** (`storage.load` · `createCatalogGraph` — page 당 1x 4.5 · 4x 15 ms, Phase 0 에서 드러난 둘째 비례 자리. 사용자 결정 2026-11-11: 후속).

### 사용자 결정 4건 (2026-11-11 답: 1 = (b) · 2 = (a) · 3 = (a) · 4 = (a))

1. **틀 page 의 모습** — (a) 빈 page (배경만 — 권고: 채움이 수 초 안에 끝난다) · (b) 옅은 「불러오는 중」 표시.
2. **절대 목표의 조건** — (a) 「66 장 · 4x 열기 ≤ 3.0 s」 를 게이트로 (권고 — 사용자 Chrome 이 4x) · (b) 1x 만 게이트, 4x 는 기록. page 수와 무관한 몫이 4x 에서 이미 ≈ 2.6 s 라 (a) 는 여유가 page 4 장분이다 — Phase 0 가 닿는지 먼저 잰다.
3. **Preview · Publish 포함 여부** — (a) 이 ADR 에서 제외, 후속 (권고 — publish 는 기능 링크만 유지 중) · (b) Preview 만 포함 (보이는 route 의 page 만 채움).
4. **화면 밖 page 내리기 (B)** — (a) 범위 밖, 메모리 실측이 요구할 때 새 ADR (권고) · (b) 이 ADR 의 마지막 Phase 로.

**실행자 (2026-11-11, Chrome MCP — 사용자 Chrome · dev 서버 5173 · DPR 2 · CPU 1x)**

- `perf-s1-live` (32 장 · record 410) 열기: 현재 page 채워짐 653 ms (record 32 · 틀 31) → 전부 채워짐 1,471 ms · 명령 버퍼 1 조각 · 오류 0.

**사용자 확인 (G6, 2026-11-11 — 본인 Builder)**: ① 현재 page 가 먼저 뜨는가 — 「한번에 뜨지는 않는다」 → 뜻 확인 「1번 맞다」 (현재 page 가 바로 뜨고 나머지가 차례로 채워진다) ② 축소 때 — 「zoom, in,out 시 달라지는건 없다」 (zoom 은 채우는 순서만 바꾼다 — 채움 뒤에는 변화 없음이 의도, 설명 뒤 이의 없음) ③ 채우는 중 page 전환 · 편집 · undo — 「되는듯하다」.

## Consequences

### Positive

- 열기 시간이 page 수와 무관해진다 — 66 장 1x 2.3 s → ≈ 0.7 s, 4x 8.9 s → ≈ 2.8 s (추정: page 수와 무관한 몫 + page 몇 장. G0 가 확인).
- breakpoint 전환 · 테마 · 글꼴 · DPR 변경 (F3) 도 같은 이득을 얻는다.
- Canvas 묶기 · 글꼴 동기처럼 record 수에 비례하던 열기 비용이 함께 줄어든다.
- 「틀 · 요청 채움」 은 화면 범위 빌드 (B) 의 토대가 된다.

### Negative

- root 에 「틀 / 채워짐」 상태 · region 단위 채움 · 스케줄러가 생긴다 — `compositionRoot.ts` · `workspace.ts` · `canvasScene.ts` · `CatalogCanvas.tsx` · `CatalogBuilderCore.tsx`.
- 열고 수 초 동안 화면 밖 page 는 비어 있고, 채우는 중인 page 는 내용이 단위별로 나타난다 (사용자 결정 1).
- 채움이 끝나기 전의 page 전환은 화면에 걸친 단위를 동기로 채우는 만큼 늦고 (지금은 0 — 4x 150 ms 상한, G4 동기 경로), 큰 page 는 전환 직후 나머지 내용이 단위별로 나타난다.
- 전체를 순회하는 새 소비자는 「채워짐」 신호를 알아야 한다 (정적 게이트가 막는다).
- 전부 채워지기까지의 총 CPU 는 줄지 않고, 늘 수 있다 (R5).
- 하니스의 `ready` 정의가 바뀌어 이전 기준선과 직접 비교하려면 old 빌드를 같은 정의로 다시 잰다.
