## Alternatives Considered

### 대안 A: 패널 어휘만 — 상속 · instance 규칙 · Form 목적지는 각각 별도 ADR

- 설명: 이 ADR 은 When 그룹 · 조건부 노출 · 숨은 이벤트 토글 · `!event` 선택 · 라벨 키만. 조상 상속 · instance 규칙 상속 · Form 목적지 · colorScheme 은 ADR 세 개로.
- 근거: 각 축의 저장 층이 다르다 (패널 = 저장 0 · 상속 = 노드 prop · instance 규칙 = patch 필드 · Form = 실행기). 리뷰 라운드가 짧다.
- 위험: 기술 LOW / 성능 LOW / 유지보수 **MEDIUM** (네 축이 같은 등록표 · 같은 패널 행 · 같은 dispatcher deps 를 건드린다 — 따로 가면 패널 행을 네 번 고친다) / 마이그레이션 LOW.
- 기각: 사용자가 Q4 에서 「B 하나」 로 답했다 (280 Status). 분리는 결정 지점 ① 이라 이 요청으로 열 수 없고, 열 이유도 없다 — 네 축이 Phase 로 나뉘면 각 Phase 가 커밋 가능 상태라 리뷰 부담은 같다.

### 대안 B: 네 축을 한 ADR · Phase 4 개 — 등록표 소비 · Provider 상속 · patch 필드 하나 · 기존 실행기 (채택)

- 설명:
  1. **패널 어휘** — When 은 개념 단위 그룹 (RAC 문서 절 — press · selection · value · open …) 으로 묶어 보이고, 개념 `conditions` ∩ 대상 선언값으로 **지금 RAC 가 받을 수 있는 것만** 보인다 (`selectionMode: "none"` → selection 그룹 숨김, `isReadOnly` → value 쓰기 Do 숨김). 숨은 이벤트는 행 단위 토글 「RAC 전체 보기」 로 열린다 (keyboard 제외 — Q3). 값 칸은 「리터럴 / 이벤트 인자」 둘 중 고르고 (2026-10-26 개정: 리터럴 또는 `!event` · `!item` · `!var` 참조 — Decision 2), 이벤트 인자 목록은 개념이 선언한 `args` (지금 `EVENT_ARG_NAMES` 를 개념 파일로 옮김). 라벨 키는 개념 단위 (`interactions.trigger.<concept>.<event>`) 로 유도 — 손 목록 삭제.
  2. **조상 → 자손 상속** — page 루트 (와 frame, 사용자 결정 1) 에 상속 prop 축 (`isDisabled` · `isReadOnly` · `isRequired` · `locale` · `colorScheme`). Preview/Publish 는 그 노드에서 RAC `Provider values={[[XContext, {…}], …]}` 를 그린다 — context 목록은 설치 d.ts 에서 「그 prop 을 받는 context」 로 `satisfies` 고정 (`RAC_PROVIDER_CHECK`). Canvas 는 resolver 파생값으로 같은 선언값을 읽어 disabled 표시만. dispatcher 의 `getConstraintContext(id).inherited` 가 조상의 값을 포함해 guard 가 같은 답을 낸다 (280 Decision 8). page 루트는 Do 대상 (set · toggle · clear). `colorScheme` 은 `applyTheme` 의 colorMode 를 세션 override 로 덮는다 (사용자 결정 4).
  3. **원본 → instance 규칙 상속** — 패널이 instance 를 고르면 원본의 규칙을 「원본에서 상속」 행으로 보이고, 행마다 끄기 · 바꾸기. 저장은 `DescendantPatchFields.interactions?: Record<원본 규칙 id, "off" | instance 규칙 id>` 하나 (사용자 결정 2) — `recordsOfOwner` 가 그 record 의 address 층을 읽어 꺼진 규칙은 빼고 바꾼 규칙으로 대체. ADR-262 의 원본 반영 · Reset all 전수 표에 이 필드를 넣는다 (Reset all 이 상속 상태로 되돌림).
  4. **Form 제출 목적지** — `callEndpoint` 규칙을 Preview 규칙으로 변환하고 dispatcher 에 `callEndpoint` 분기 (`DispatchDeps.callEndpoint(endpointId, body)`) 를 더한다. Form `onSubmit` 의 이벤트 인자 `formData` (RAC Form 의 `name` 수집 → `Object.fromEntries(new FormData(form))`) 를 개념 `form` 이 선언하고, Do 「endpoint 호출」 의 body 칸이 `!event.formData` 를 고를 수 있다. 실행은 기존 `executeApiEndpoint` 에 body 인자를 더한 것 (`createCollectionEndpointExecutor` 의 `bodyTemplate` 자리에 넘김). 결과는 `onSubmit` 다음 규칙이 아니라 toast · 변수 쓰기로 받는다 (응답 → 변수 쓰기는 사용자 결정 3 의 2 차).
  5. **게이트** — 280 하니스 재사용: 규칙 실행 뒤 RAC tester · DOM 이 관측한 상태, 패널은 role 쿼리. Publish 번들 상한.
- 근거: 네 축 모두 **이미 있는 것** 을 잇는다 — 등록표 (280) · RAC `Provider` (설치본) · address 층 patch (248 · 262) · endpoint 실행기 (152 · 201). 새 저장 구조는 patch 필드 하나뿐. 사용자 원칙 「RAC 표면을 UI 로 전달」 — 그룹 · 조건부 · 인자 선택은 RAC 문서 절 · modifier · callback 시그니처를 보이는 것이지 새 어휘가 아니다.
- 위험: 기술 **MEDIUM** (RAC `Provider` 가 RAC 컴포넌트 안쪽 context 공급 — Select 의 trigger `ButtonContext` 등 — 와 겹칠 때 어느 쪽이 이기는지는 설치본 probe 로 가족별 확정 · `colorScheme` override 가 theme 의 CSS 변수 세트와 어긋날 수 있음) / 성능 LOW (Provider 1 ~ 소수 · 패널 그룹 계산은 선택 시 1 회) / 유지보수 LOW (라벨 · 인자 · 그룹이 개념 파일 한 곳) / 마이그레이션 **MEDIUM** (contract 47 — 기존 개발용 프로젝트 거부 · 변환 0).

### 대안 C: 규칙 모델 확장 — 조건부 · 다중 액션 · 응답 체인으로 상속 · Form 흐름을 표현

- 설명: `InteractionEntry` 에 `when` 조건 · `actions[]` · `onSuccess/onError` 를 더해 「disabled 면 건너뛰기」 · 「제출 → 응답 → 페이지 이동」 을 규칙으로 쓴다. 상속은 규칙 복제 (instance 마다 복사본).
- 위험: 기술 MEDIUM / 성능 LOW / 유지보수 **HIGH** (ADR-158 이 은퇴시킨 DAG 가 돌아온다 — 조건 평가 · 체인 · 복제 규칙 동기화) / 마이그레이션 **HIGH** (스키마 · 패널 · dispatcher · 검증 전부).
- 기각: 사용자가 Q2 에서 「한 줄 유지 + 값 소스만」 으로 답했다. 상속은 RAC `Provider` 가, 조건은 RAC modifier 가, Form 흐름은 `onSubmit` When + endpoint Do 한 줄이 이미 표현한다.

## Decision

**대안 B 채택.**

> 구현 상세: [281-interactions-panel-vocabulary-inheritance-form-destination-breakdown.md](../design/281-interactions-panel-vocabulary-inheritance-form-destination-breakdown.md)

1. **패널의 When · Do 는 등록표를 그대로 보이되 RAC 가 지금 받을 수 있는 것만 보인다.** 그룹 = 개념 (RAC 문서 절) · 노출 = `events` − (조건 불충족 개념의 events) · Do = `capabilities` − (guard 가 선언값만으로 이미 막는 것: `isDisabled` · `isReadOnly` 선언, `selectionMode: "none"`). 선언값이 바뀌어 숨겨진 규칙은 **삭제하지 않고** 행에 「지금 RAC 가 받지 않음 (isReadOnly)」 표식 — 실행 시 report 와 같은 문구. 숨은 이벤트 (`hiddenEvents`, keyboard 제외) 는 행의 「RAC 전체 보기」 토글로 열리고, 토글 상태는 저장하지 않는다 (규칙이 숨은 이벤트를 쓰면 그 행은 늘 열림).
2. **값 칸은 소스를 고른다.** 「리터럴 / 이벤트 인자 / 변수」 — 이벤트 인자 목록은 When 의 개념이 선언한 `args` (`EVENT_ARG_NAMES` 를 개념 파일의 `args: { onSelectionChange: ["keys"] }` 로 옮기고 `bindings.ts` 가 등록표에서 읽음). 저장은 지금 그대로 문자열 `"!event.keys"` (스키마 0). 소스는 「리터럴 / 이벤트 인자」 둘뿐 — 변수를 값으로 읽는 소스 (`!var.<id>` 류) 는 넣지 않는다 (ADR-214 의 변수는 `{{ name }}` 글자 바인딩과 `setState` 쓰기로 닿고, 읽기 소스는 사용자 결정 3 의 2 차와 함께 판단). **2026-10-26 개정** (`729c44749`): 값 칸 「값 고르기」 — 리터럴 또는 값 전체 참조 `!event.<인자>` · `!item.<key 인자>[.필드]` · `!var.<변수 id>[.경로]`, 해석은 `interactions/valueRef.ts` `resolveRuleValue` 하나, 선택지는 `panels/interactions/valueOptions.ts` 가 유도.
3. **조상 상속은 RAC `Provider` 로.** page 루트 (`body`) 와 frame (사용자 결정 1) 의 binding `accepts` 에 `isDisabled` · `isReadOnly` · `isRequired` (출처 `v3`) · `locale` (`composition` — 기존 공통 출처) · `colorScheme` (출처 S2 `Provider`) 를 더한다. DOM 은 그 노드에 `Provider` 를 그린다 — `values` 는 「그 prop 을 받는 RAC context 전수」 표 (`providerContexts.ts`) 에서 만들고, 표의 각 항목은 설치 d.ts 에 `satisfies` (`RAC_PROVIDER_CHECK` — context 의 props 타입에 그 prop 이 없으면 컴파일 오류). RAC 컴포넌트가 안쪽에 자기 context 를 공급하는 자리 (Select 의 trigger · 그룹 안 항목) 는 RAC 규칙대로 안쪽이 이긴다 — Phase 0 probe 로 가족별 기록. Canvas 는 resolver 파생값 (`derivedProps.isDisabled` 확장) 으로 같은 선언값을 읽는다. dispatcher 는 `getConstraintContext(id).inherited` 에 조상 상속값을 합쳐 guard (280 Decision 8) 가 Preview 와 같은 답을 낸다. page 루트는 Do 대상 (`set` · `toggle` · `clear`) — `pageRoot` 표식은 유지하되 기본 대상 제외 규칙 (`interactions.ts:247`) 은 그대로.
4. **instance 규칙 상속은 address 층 필드 하나.** `DescendantPatchFields.interactions?: Readonly<Record<EntryId<"interaction">, "off" | EntryId<"interaction">>>` — 키는 원본 (template 노드) 규칙, 값은 끄기 또는 이 instance 의 자기 규칙 (address 있는 `InteractionEntry`, 지금 스키마). `recordsOfOwner` 는 record 의 address 층을 읽어 꺼진 규칙을 빼고 바꾼 규칙을 대신 싣는다. 패널은 instance 선택 시 「원본에서 상속」 행 (읽기 전용 요약 + 끄기 + 「이 instance 에서 바꾸기」) 을 자기 규칙 위에 보인다. ADR-262 의 `pushInstanceOverrides` · `resetInstance` 전수 표에 이 필드를 더한다 — 반영 = 바꾼 규칙을 원본 규칙으로 (원본 규칙 trigger · actions 교체 — `commands/instanceOverrides.ts`), 끄기는 반영 대상 아님 · Reset all = 필드 제거. contract 47.
5. **Form 제출 목적지 = endpoint 호출.** 세 층을 한 커밋 묶음으로 정한다 (review round 1 h1 · h2 · h3).
   - **저장**: `callEndpoint` action 에 `body?: Scalar` (`types.ts:879` → `{ opcode: "callEndpoint"; endpointId; body?: Scalar }`) — capability `value` 와 같은 자리 · 같은 표기 (리터럴 문자열 또는 `"!event.formData"`). 검증은 `exact(action, ["opcode", "endpointId", "body"])` + **`body !== undefined` 일 때만** `scalar(body)` (capability `value` 와 같은 조건 분기 — `validation.ts:326-330` 의 `scalar` 는 `undefined` 에 `SCALAR_REQUIRED` 를 내므로 무조건 부르면 body 없는 규칙이 거부된다, review round 2), library 허용 목록 · 명령 · 패널 값 칸 (Decision 2) · Preview 변환 (`ruleOf` → `{ kind: "callEndpoint", endpointId, body? }`) 이 같은 커밋. contract 47 (제약 §스키마).
   - **실행**: dispatcher 가 값 해소 (`!event` · 리터럴 — 280 Decision 8 ①) 뒤 `DispatchDeps.callEndpoint(endpointId, body)` 를 부르고, Preview/Publish 공용 runtime 이 세션 서비스의 **새 함수** `apiEndpointService.submitApiEndpoint(endpointId, body, signal)` 로 넘긴다. 구현은 `submitCollectionEndpoint(endpoint, body, signal)` — `executeCollectionEndpoint` 의 fetch 조립 (URL · headers · method · timeout) 을 함수로 나눠 같이 쓰되 **요청 공유 0** (`createCollectionEndpointExecutor` 의 pending map 을 거치지 않음 — 제출마다 fetch 1) · body 는 받은 값을 JSON (`Content-Type: application/json` 이 headers 에 없으면 추가) · `GET` · `HEAD` endpoint 는 report (body 를 보낼 수 없음). 조회 경로 (`executeApiEndpoint` · pending 공유 · `responseMapping`) 무변경.
   - **응답**: `response.ok` 가 성공이다 — `204` · `Content-Length: 0` · 비어 있는 본문 · JSON 아닌 `Content-Type` 은 본문 없이 성공 (`undefined`), JSON 이면 파싱값. 실패 (`!ok` · 네트워크 · timeout) 는 `report` + toast (사용자 결정 3 기본안). 응답값 → 변수 쓰기 · collection 행 추가는 사용자 결정 3 의 2 차.
   - body 의 출처 — Form `onSubmit` 의 `!event.formData` (개념 `form` 이 `args: { onSubmit: ["formData"] }` 선언 · `bindings.ts` 가 `FormEvent.currentTarget` 의 `FormData` 를 `Object.fromEntries` 로 — 같은 `name` 여러 값은 배열). 네이티브 제출 차단은 280 Decision 9 그대로 (목적지 없는 Form 만) — endpoint 규칙이 있어도 `action` 을 쓴 Form 은 HTML 제출도 한다.
6. **colorScheme 전환은 page 루트 상속 prop.** Do 「set colorScheme」 → override → 세션 `applyTheme({...state, colorMode})` 재호출 (theme 의 CSS 변수 세트는 그대로, 색 모드만). 앱 액션 (`APP_ACTIONS`) 으로 두지 않는다 — prop 이 S2 이름 그대로이고 (`Provider colorScheme`) 상속 prop 의 Do 어휘 (set · toggle) 로 충분하다 (사용자 결정 4).
7. **재판단 결과 — 유지**: runtime override 수명 = 세션 (280 결정 5) · Do 대상 = 같은 페이지 노드 (280 결정 7, page 루트도 같은 페이지 — 이후 ADR-283 이 장소 참조로 바꿨다) · keyboard 노출 0 (Q3). 전역 overlay 는 이 ADR 에 없다.
8. **Publish 확인**: 네 축을 `apps/publish` 경로로 1 회 (Chrome MCP) — Preview 와 같은 runtime 이라 분기 0 을 확인하는 자리.

**위험 수용 근거**: 기술 M 은 Phase 0 probe (Provider vs RAC 안쪽 context — 설치본 `useContextProps` · Select · CheckboxGroup · Dialog slot) 가 가족별 사실을 먼저 재고 (R1), colorScheme 은 theme 변수 세트 무변경 · colorMode 만 바꿔 어긋날 자리를 없앤다 (R4). 이관 M 은 contract bump 가 이 저장소의 표준 절차 (ADR-251 · 277 · 278 · 279) 다.

**기각 사유**: A — 사용자 결정 Q4 (한 ADR) 와 반대, 네 축이 같은 패널 행을 공유. C — 158 이 은퇴시킨 DAG 복귀 · Q2 와 반대.

## Consequences

### Positive

- 패널이 RAC 문서의 절 구조로 읽힌다 — 55 type 의 When · Do 가 손 라벨 없이 개념 단위로 이름을 갖고, 지금 받을 수 없는 선택지는 보이지 않는다 (실행 시 report 가 첫 피드백이던 것이 저작 시점으로 당겨진다).
- `!event` 전달 규칙 (A 의 선택 → B 의 선택) 을 손으로 치지 않고 고른다.
- page · frame 하나의 `isDisabled` · `isReadOnly` · `locale` · `colorScheme` 이 자손 전체에 닿는다 — RAC 의 Provider 그대로이고 규칙 한 줄로 바꾼다.
- 원본 규칙을 instance 에서 보고 끄고 바꾼다 — Framer 의 컴포넌트 인터렉션 상속과 같은 자리, ADR-262 의 반영 · Reset all 과 한 표.
- Form 이 앱이 된다 — `onSubmit` → endpoint 호출, FormData 가 그대로 body.

### Negative

- contract 47 — 기존 개발용 프로젝트는 열리지 않는다 (변환 0, 개발 단계).
- 패널 모듈이 3 ~ 4 파일 는다 (그룹 · 소스 칸 · 상속 행 — ADR-158 G4 상한 15 안).
- 숨은 이벤트를 연 규칙 (hover 등) 은 S2 가 지운 표면이라 S2 레퍼런스에는 없다 — 행 표식으로만 안내한다.
- Preview 의 Form 제출이 실제 endpoint 를 부른다 (사용자 결정 5 기본안) — mock 이 필요하면 endpoint 쪽 설정이다.
