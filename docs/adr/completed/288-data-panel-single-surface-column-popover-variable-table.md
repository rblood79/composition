### 사용자와 제약

- 사용자 (비개발자 · 기능 단위) 는 「열 정보 바꾸기」 하나를 세 패널을 오가며 한다 — 원문 「불편하다」. 변수는 소유자마다 다른 화면 · 다른 타입 변경 규칙이라 같은 일이 자리마다 다르다.
- **Hard — 쓰기 경로 무변경**: 모든 편집은 ADR-286 대로 `applyDataChange` (프로젝트 변수 · 표) 와 `catalogVariableCommands` (페이지 · 요소 변수) → `workspace.execute` 한 step. 패널에서 graph 를 직접 만지지 않는다 (state-management §2 · §3).
- **Hard — 문서 스키마 무변경**: contract 51 유지. 이름 변경의 참조 재작성은 기존 필드 (string prop 의 `{{ }}` · `binding.key`) 안의 글자 교체다.
- **Hard — 참조 재작성은 필드별 런타임 해소 기준**: 같은 이름이 다른 소유자에 있을 수 있다 (페이지 변수 `a` 가 프로젝트 변수 `a` 를 가린다 — `catalogVariableNameConflict` 는 **사슬 안** 고유만 보장). 재작성은 문서 전체 치환이 아니라 **그 자리에서 런타임이 이름을 이 변수로 해소할 때만** — 해소 범위는 필드마다 런타임과 같다 (prop = 요소 사슬 `catalogRecordVariables`, `binding.key` · 보기 조건 = 페이지 · 프로젝트 `pageAndProjectStates`). `params` 는 변수로 해소되면 재작성, 변수가 없어 route 로 떨어지는 자리만 제외. 한 판정 모듈을 재작성과 사용처 세기가 같이 쓴다.
- **Hard — 새 이름이 기존 참조를 가로채지 않는다**: 이름 변경 명령은 새 이름이 (i) 가시 사슬의 상태 변수 · **프로젝트 변수** 와 충돌하거나 (ii) 변경 뒤 그 소유자 범위의 기존 `{{ new }}` 참조가 다른 변수 대신 이 변수를 읽게 되면 거절한다 (가림을 새로 만들지 않는다). 패널 · 코드 보기 · data sink 가 같은 명령을 지나므로 검사는 명령 하나에.
- **Hard — 구조 시작값은 소유자 계약대로**: 페이지 · 요소의 `object` · `array` 시작값은 contract 51 대로 `""` (규칙이 쓴다) — 표는 그 칸을 「규칙이 정함」 으로 표시하고 편집하지 않는다. JSON 시작값은 프로젝트 변수만. 세 소유자에 JSON 을 열려면 타입 · 검증 · 명령 · 런타임 · contract 를 함께 바꾸는 별도 결정이다 (이 ADR 범위 밖).
- **Hard — 패널 표준**: `.panel-contents > Section > .section-content` (ADR-163), 탭은 `panel-tabs` 단일 패턴, 라벨 액션은 `.control-button`, 행 보조 액션 2 개 이상은 `PropertyRowMenu` (⋮). 팝오버 · 표는 Builder RAC (`DialogTrigger` + `Popover` + `Dialog`, RAC `Table`).
- **Hard — 번들**: `datatable` 패널은 lazy (`panelConfigs.ts:86`) — 편집기 · 필드 패널의 내용이 그 chunk 로 옮겨도 initial 은 늘지 않아야 한다. Builder initial Δ ≤ +1 KB gz (`adr209-bundle-closure.mjs`, ADR-286 G5 와 같은 방식 — 이미 초과 상태라 이 ADR 몫 Δ).
- **Hard — 패널 id 삭제는 레이아웃 저장과 양립**: `datatableEditor` · `datatableField` 가 등록에서 빠져도 그 id 를 든 저장 레이아웃이 열려야 한다 (panel-structure 규칙 「패널 id 는 저장 키」 — 합칠 때 id 를 남기는 규칙의 반대 경우. Phase 0 에서 V4 검증의 미등록 id 처리를 실측하고, 버리는 쪽이면 그대로, 거부하면 무시 경로 추가).
- **Hard — 원본 파일 삭제는 승인 뒤**: `DataTableEditorPanel.tsx` · `DataTableFieldPanel.tsx` · `VariableEditor.tsx` · `VariableList.tsx` 등 옮긴 뒤 남는 파일은 사용자 승인으로만 지운다.
- **Soft**: 격자 (`DataGrid`) 의 셀 편집 · 붙여넣기 · 선택 동작 · API 편집 양식 (`ApiEndpointEditor.tsx` 1,108 줄) 의 내용은 그대로 — 자리만 바뀐다.

## Alternatives Considered

### 대안 A: 패널 3 겹 유지 + 크기 · 진입점만 손질

- 설명: `datatable` 에 `defaultWidth: "100%"` 만 주고 편집기 · 필드 패널은 그대로. 변수 편집기도 그대로.
- 리서치: 지금 구조 (ADR-212 · 214). 레퍼런스 표의 어느 도구도 3 패널이 아니다.
- 위험: 기술 **L** / 성능 **L** / 유지보수 **H** (3 패널 · 3 store 표시 경로 · 변수 화면 2 종 · 타입 규칙 2 종이 그대로 — 사용자 지적이 해소되지 않는다) / 마이그레이션 **L**.

### 대안 B: `datatable` 패널 하나 = 데이터 표면 (전체 폭) + 머리글 팝오버 + 공용 변수 표 + 이름 변경 참조 유지 (채택)

- 설명: `datatable` 패널의 본문을 **왼쪽 목록 열 + 오른쪽 본문** 으로 (목록 = 표 · API · 변수, 본문 = 고른 것의 격자 · API 양식 · 변수 표 · 만들기 양식). `defaultWidth: "100%"` (캔버스를 덮는다 — 패널 시스템 그대로, 새 층 없음). 편집기 · 필드 패널은 사라지고 `dataTableEditorStore` 의 모드는 본문 선택이 된다. 열 편집은 머리글 `DialogTrigger` + `Popover` (필드 패널 본문 이동 — 이름 · 타입 검색 목록 · 미리보기 「비움 / 유지」 · 참조 대상 · 필수 · 라벨 · 기본값 · 사용처 · 삭제). 변수는 공용 `VariableTable` (RAC Table — 이름 · 타입 · 시작값 · [유지] · 사용처 · ⋮) 을 **소유자** 로 받아 Data 본문 (프로젝트) · Design 패널 State 절 (페이지 · 요소) 이 같이 쓴다 — 요소의 RAC 상태 이름 행은 이름만. 이름 변경은 **참조까지 한 step** (`renameVariable` 명령 — `{{ }}` · `binding.key` 재작성, 가시 사슬 판정) 로 세 소유자 · 코드 보기 (`renameVariable`) 가 같은 명령. 타입 변경 규칙 하나 (사용자 결정 1).
- 리서치: Framer · Webflow (캔버스 위에 넓은 데이터 화면) · Airtable (머리글 팝오버) · Figma Variables (변수 표). 패널 작업 공간의 `%` 폭 · lazy chunk · `setPanelWorkspacePanelVisibility` 는 이미 있다.
- 위험: 기술 **M** (격자 · 양식 · 표를 한 본문에 — 표 셀 편집기가 행의 타입을 따라야 한다, R2) / 성능 **L** (lazy chunk 안 이동 · 표 행 수 = 변수 수) / 유지보수 **L** (패널 1 · 변수 화면 1 · 명령 1 · 규칙 1) / 마이그레이션 **M** (저장 레이아웃의 옛 id · 옛 폭 — R3 · R4).

### 대안 C: 캔버스를 대신하는 새 「데이터 작업 영역」 층 (Framer CMS 식 라우트)

- 설명: 패널이 아니라 Builder 본문 자체를 바꾸는 화면 (Components 탭처럼 별도 표면).
- 리서치: Framer · Bubble (Data 탭 = 별도 화면). composition 의 Components 탭은 문서의 page (ADR-282) 라 이 모양이 아니다.
- 위험: 기술 **M** / 성능 **L** / 유지보수 **M** (패널 작업 공간 밖의 둘째 표면 — 레일 · 단축키 · 레이아웃 저장을 따로) / 마이그레이션 **L**. 사용자 원문 「패널 사이즈를 100% 로 설정하면 되지 않나」 로 기각 — 패널 시스템이 같은 결과를 이미 낸다.

### 대안 D: 머리글을 ComboBox 로 (입력 = 열 이름, 팝오버 = 타입) — 사용자 첫 제안

- 설명: 열 이름 칸이 ComboBox 의 입력, 목록이 타입.
- 리서치: RAC `ComboBox` 는 입력 글자로 목록을 거르고 고른 항목으로 입력을 채우는 부품 (설치 RAC `useComboBoxState`) — 입력을 이름, 목록을 타입으로 쓰면 거르기 · 채우기를 둘 다 꺼야 하고 화면낭독기는 「입력값 = 고른 항목」 으로 읽는다 (D1). Enter · ↓ 가 이름 확정과 목록 조작에 겹친다. 타입 변경의 미리보기 · `reference` 대상 선택 · 필수 · 기본값 · 삭제가 들어갈 자리가 없어 패널이 어차피 남는다.
- 위험: 기술 **H** (RAC 동작을 거꾸로 — D1 위반) / 성능 **L** / 유지보수 **M** / 마이그레이션 **L**. 기각 (같은 대화에서 사용자에게 보고).

## Decision

**대안 B.** `datatable` 패널 하나가 데이터 표면이다 — 전체 폭 기본, 왼쪽 목록 · 오른쪽 본문. 열 편집은 머리글 팝오버, 변수는 세 소유자가 같은 표, 변수 이름 변경은 참조까지 한 step, 타입 변경 규칙은 하나. 편집기 · 필드 패널은 사라진다.

위험 수용 근거: 기술 M (R2 — 변수 표의 칸 편집기가 행 타입을 따른다) 은 격자를 재사용하지 않고 **변수 전용 RAC Table** 을 두어 피한다 — 행이 적고 (프로젝트 변수 수) 가상화가 필요 없다. 마이그레이션 M (R3 · R4) 은 레이아웃 저장의 옛 id · 폭 문제라 Phase 0 실측 + G3 로 닫는다.

기각 사유 — A: 사용자 지적이 그대로 남는다. C: 패널 시스템이 같은 결과를 낸다 (사용자 기각). D: RAC ComboBox 의 동작 · 접근성과 어긋나고 패널이 남는다.

### 결정 항목

1. **데이터 표면 = `datatable` 패널**: `defaultWidth: "100%"` (`maxWidth` 는 이미 `"100%"`), 본문은 `.panel-contents` 안의 목록 열 (지금의 세 탭 → 묶음 Section 셋) + 본문 영역 (`table-edit` 격자 · `api-edit` 양식 · `variables` 표 · 만들기 양식). `dataTableEditorStore` 의 `mode` 는 본문이 무엇을 그리는지 (패널 표시 호출 삭제). 패널 밖 진입점 2 (Quick Connect · CollectionBinding) 는 `datatable` 을 켜고 모드를 둔다. 레일 아이콘 · 단축키 · 전체 메뉴 무변경.
2. **열 편집 팝오버**: `ColumnHead` 의 라벨 · 타입 아이콘 → `DialogTrigger` + `Popover` + `Dialog` (머리글 아래). 내용 = 지금 필드 패널 본문 그대로 (`DataTableFieldPanelContent` 의 쓰기 · 미리보기 · 참조 대상 · 삭제 확인 재사용), 타입 아이콘은 타입 목록에 커서. 더블클릭 · F2 의 그 자리 이름 편집은 유지. 바깥 클릭 · Esc 로 닫힘 (RAC). `datatableField` 패널 · `fieldPanel` 상태 삭제.
3. **공용 변수 표 `VariableTable`** (RAC Table, 가상화 없음): props = 소유자 (`project` | `page` | `element`) · 행 · 명령 host. 열 = 이름 (칸 편집, Enter 확정) · 타입 (PropertySelect) · 시작값 (행 타입별 — 글자 · 숫자 · 스위치 · Object/Array 는 **프로젝트 변수만** JSON 팝오버, 페이지 · 요소는 「규칙이 정함」 표시 — contract 51 의 `""` 계약) · 유지 (프로젝트만 — 런타임 persist 는 project scope 뿐, state-management §5) · 사용처 수 · ⋮ (삭제 · 소유자로 이동). 좁은 폭 (Design 패널) 에서는 사용처 수를 ⋮ 안으로 (사용자 결정 4). 요소의 RAC 상태 이름 행 (`CatalogStateSource`) 은 이름 칸만 편집. Data 본문의 페이지 · 요소 **색인** 은 「모든 변수」 필터로 같은 표에 (읽기 전용 · 행 = 소유자로 이동 — 사용자 결정 2).
4. **이름 변경 = 참조까지 한 step**: shared 명령 `renameVariable(graph, variableId, name)` — entry `name` + **런타임이 이 변수로 해소하는** 자리의 `{{ old }}` 를 `{{ new }}` 로. 참조 site 모듈 (`variableReferences.ts`) 은 자리마다 **필드 종류** 를 들고 그 필드의 런타임 규칙으로 해소한다 — string prop 은 요소 사슬 (`catalogRecordVariables`), `binding.key` · 보기 조건 값은 페이지 · 프로젝트 (`pageAndProjectStates`); `\{{` 리터럴 · `env` root 제외, `params` 는 변수로 해소될 때만 (route fallback 자리는 제외). 두 사용처 카운터 (`dataVariables.ts:110` · `stateVariables.ts:149`) 는 이 모듈을 읽도록 바꾼다. **새 이름 검사** 도 명령 안: 가시 사슬 + 프로젝트 변수 충돌 (`catalogVariableNameConflict` 확장) · 변경 뒤 기존 `{{ new }}` 참조의 해소가 바뀌면 거절 (`VARIABLE_NAME_SHADOWS` — 안내 문구, 쓰지 않음). 프로젝트 변수 (`define_variable` 의 rename) · 페이지 · 요소 (`catalogVariableCommands.rename`) · 코드 보기 (`renameVariable`) 가 전부 이 명령.
5. **타입 변경 규칙 하나**: 사용자 결정 1 의 답을 세 소유자에 같이 적용 (`setType` · `define_variable`).

## Consequences

### Positive

- 열 정보 바꾸기 · 변수 편집이 각각 한 자리 · 한 동작이 된다 (사용자 지적 해소). 변수는 소유자가 달라도 같은 표 · 같은 명령 · 같은 타입 규칙.
- 변수 이름 변경이 참조를 끊지 않는다 — 지금도 있는 결함 (`{{ oldName }}` 노출) 이 세 소유자 · 코드 보기에서 함께 닫힌다.
- 패널 2 (`datatableEditor` · `datatableField`) · 변수 화면 2 (`VariableEditor` · `VariableList`) · 표시 경로 (`setPanelWorkspacePanelVisibility` 호출 3) 가 줄어 `panels/datatable/` 의 파일 수가 준다.

### Negative

- 데이터 작업 중 캔버스가 보이지 않는다 — ADR-286 R8 (셀 편집이 Canvas 에 바로) 을 **같은 화면에서** 보는 경험은 사라진다 (사용자 결정 — 폭을 줄이면 지금처럼 나란히).
- 기존 사용자의 저장 레이아웃은 `datatable` 폭이 옛 값이라 한 번 끌어야 한다 (R4).
- 팝오버는 머리글을 떠나면 닫히므로 필드 여러 개를 연달아 고칠 때 열기 횟수가 는다 (Airtable 과 같은 비용).
