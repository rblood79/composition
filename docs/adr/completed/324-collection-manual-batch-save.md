> **리뷰 round 1 반영 (2026-11-27, codex — HIGH 6, [기록](../reviews/324.md))** — 여섯 건 모두 코드로 재현을 확인하고 설계를 고쳤다. 대안 D 와 사용자 결정 5건은 그대로다.
>
> - h1 (2xx 의 뜻): 저장 전용 실행기가 status · 헤더 · 본문을 돌려준다. 202 는 접수일 뿐이라 확정하지 않고, 넣은 행의 서버 key 는 본문 → `Location` 순으로 읽으며 없으면 임시 key 로 남기지 않는다 (Decision 5).
> - h2 (응답 유실): 판정을 고침 · 지우기로 나누고, 목록에서 행을 못 찾은 것과 「없다」 가 보증된 것을 구별한다 (Decision 6).
> - h3 · h6 (동시 수정): 버전은 처음 고칠 때의 것을 보내고, 행 전체 전송은 버전 조건이나 방금 읽은 행 위에 합친 본문으로만 다른 칸을 지킨다 (Decision 4).
> - h4 (즉시 저장 규칙): 알리는 데서 그치지 않고 같이 켜는 구성을 검증이 거절한다 (Decision 1).
> - h5 (행 식별자): 서버 식별자가 없는 행의 고침 · 지우기는 보내지 않는다 (Decision 2).
>
> **수리 검증 Round 2 (2026-11-27, Codex)** — h2~h6 설계 수리 확인. h1의 잔여 반례와 신규 h7·h8로 HIGH 3건이 남아 설계 승인을 보류한다. [판독 기록](../reviews/324.md#round-2--2026-11-27-reviewer-codex)
>
> **Round 2 반영 (2026-11-27)** — 남은 세 건도 반례를 확인하고 고쳤다.
>
> - h1: 넣은 행의 key 는 응답의 것이 먼저다 (본문 → `Location`). 보낸 key 는 단건 확인 조회로 읽힐 때만 쓴다 — 저장소의 CRUD 대역이 `draft-42` 를 `u4` 로 바꿔 만든다.
> - h7: status 보다 먼저 `errorsPath` 를 읽는다. 2xx 여도 필드 오류가 있으면 그 행은 확정하지 않는다.
> - h8: 서버 key 를 모르는 넣기의 뒤 편집을 버리지 않는다 — 서버 행과 잇거나 사용자가 버릴 때까지 남는다.
>
> 판독은 상한 (판독 1 + 수리 검증 1) 을 넘었다.
>
> **사용자 결정 (2026-11-27)** — Round 3 는 열지 않는다. h1 · h7 · h8 의 다음 판정은 구현 Gate G3 에서 실제 동작으로 한다. 행 연결은 후보가 하나여도 자동으로 하지 않고 사용자가 대상 행을 고른다 — 생성 응답의 본문이나 `Location` 이 행을 식별하지 못하면 조회 결과 (보낸 key 의 단건 조회 포함) 는 선택 후보로만 쓴다. Round 2 반영의 「보낸 key 는 단건 확인 조회로 읽힐 때만 쓴다」 와 자동 연결은 이 결정으로 뺐다.

## Context

Table 의 칸 편집 · 붙여넣기 · 채우기는 세션의 편집 한 곳으로 들어온다. 지금 서버 저장은 작성자가 건 규칙이 한다 — 편집 이벤트 (`Cells change` · 칸 Form 의 submit) 에 `callEndpoint` 를 잇고, 성공하면 그 규칙이 보낸 편집이 「저장됨」 이 된다. 여러 편집을 모아 사용자가 누를 때 보내는 길은 없다. `Cells change` 는 고친 행 전체를 싣는다. [Table 편집](../../../packages/shared/src/catalog/runtime/catalogTableController.ts#L835) · [저장 표시](../../../packages/shared/src/interactions/bindings.ts#L119) · [제출 응답 처리](../../../packages/shared/src/catalog/runtime/catalogPreviewInteractions.ts#L696) · [행 전체 전송](../../../packages/shared/src/catalog/runtime/catalogTableController.ts#L904) · [ADR-317](317-table-editing-grid-paste-fill-status.md)

모은 편집을 어디에 두는가는 ADR-325 가 정했다 — Collection 마다 키로 든 「미저장 변경」 (필드별 수정 전 값 · 새 값) 이고 조회가 와도 남는다. 이 ADR 은 그 변경을 **언제 · 어떤 요청으로 보내고 결과를 어떻게 판정하는가** 다.

**서버 쪽 사실.** 요청은 브라우저가 고객 API 로 직접 보낸다 — 서버 실행 모드는 연결돼 있지 않고 저장소에 서버가 없다. 제출 실행기는 `response.ok` 를 성공으로 보고 빈 본문도 성공이다. 고객 API 는 대부분 Oracle · Java 다 — 조사에서 Spring 이 기본으로 주는 것은 페이지 · 정렬 파라미터, 단건 PATCH · PUT, `@Version` 과 `If-Match` (불일치 412) 이고, 묶음 endpoint · 집계 · 중복 요청 방지는 기본에 없다. [서버 모드](../../../packages/shared/src/collections/executeCollectionEndpoint.ts#L114) · [성공 판정](../../../packages/shared/src/collections/executeCollectionEndpoint.ts#L243) · [조사](../../explanation/research/COLLECTION_REMOTE_SAVE_2026-11.md) · [연결 능력 조사](../design/324-collection-manual-batch-save-breakdown.md#외부-조사--서버가-실제로-주는-것)

**측정 가능한 조건**

- HC1 편집 · 조회 중 원격 쓰기 0 회, 변경 0 건이면 저장 요청 0 회.
- HC2 저장 요청의 본문 크기는 변경량에 비례한다. 1,000 행 × 1,000 열 합성 표에서 두 행의 세 칸을 바꿨을 때 JSON 본문은 전체 13,784,992 B · 고친 두 행 전체 26,781 B · 바뀐 필드와 식별 정보 173 B 였다. [측정 방법](../design/324-collection-manual-batch-save-breakdown.md#본문-크기-기준선)
- HC3 편집 상태는 ADR-325 의 변경 층 하나 — 두 번째 편집 저장 자리 0.
- HC4 나가는 값은 필드의 값 표현 선언으로 되돌린다 ([ADR-313](313-external-data-intake-standard.md) — `outgoingRecord` · 큰 정수 literal). 보내지 않은 필드를 본문에 더하지 않는다.
- HC5 저장 설정이 없는 프로젝트는 지금과 같이 동작한다. 문서 계약 번호는 오르고 옛 파일을 바꿔 읽는 코드는 넣지 않는다.
- HC6 Preview 첫 화면 번들 증가 0 (저장 실행은 세션 chunk).

**측정할 수 없는 조건** — 사용자는 비개발자다: 요청 본문이나 재시도 규칙을 조립하지 않는다. 고객 서버가 실제로 무엇을 보장하는지는 Composition 이 검증할 수 없다.

**Domain** — 데이터 모델 층과 Interaction 이다. D2: Collection 의 저장 설정과 Do 둘 (「변경 저장」 · 「변경 취소」) 은 RAC · S2 에 없는 composition 확장이고 출처를 등록표에 적는다. D1: 저장 막대는 기존 Button · Text · Toast 를 놓는 것이고 새 ARIA 를 쓰지 않는다. D3: 새 시각 값 없음. [계약 정본](063-ssot-chain-charter.md)

## Decision

**D 를 제안한다. 미저장 변경을 사용자가 저장을 누를 때 보내고, 요청 모양과 보장은 연결이 선언한 능력을 따른다.** A 는 결과 판정과 충돌을 다룰 수 없어서, B 는 고객이 새 endpoint 를 만들어야만 켜져서, C 는 서버 운영과 원자성 한계 때문에 고르지 않는다.

> 구현 상세: [324-collection-manual-batch-save-breakdown.md](../design/324-collection-manual-batch-save-breakdown.md)

1. **저장 시점은 Collection 의 설정이다.** 없으면 지금 그대로 (규칙이 편집마다 보낸다). 「모아서 저장」 을 켜면 편집은 화면에만 반영되고 사용자가 저장을 누를 때 나간다. 두 방식 모두 ADR-325 의 변경 층을 쓴다. 한 Collection 에 「모아서 저장」 과 즉시 저장 규칙 (그 Collection 의 편집 이벤트에 걸린 쓰기 `callEndpoint`, 또는 그 Collection 을 편집하면서 쓰기 `callEndpoint` 를 같이 하는 규칙) 은 같이 둘 수 없다 — 검증이 거절하고, 패널이 두 위치를 보이며 「규칙을 지우고 켜기」 를 준다. 알리기만 하면 첫 편집에서 그 규칙이 실행돼 HC1 이 깨진다.
2. **보내는 것은 변경분이다.** 고친 행은 key 와 바뀐 필드 (연결이 행 전체만 받으면 행 전체 — 선언), 넣은 행은 그 행, 지운 행은 key. 값은 필드의 값 표현 선언으로 되돌린다. 고침 · 지우기는 서버 식별자 (key 필드의 값) 가 있는 행만 보낸다 — 위치로 만든 키 (`row-1`) 의 행은 요청 0 이고 변경과 사유가 남는다. 고침 · 지우기 연결을 두려면 Collection 에 key 필드가 있어야 한다.
3. **보내는 모양은 둘 중 하나다.** 묶음 — 변경 목록을 한 요청에 (참조 모양, 원자적인지는 선언). 행별 — 기존 REST endpoint 로 변경마다 한 요청 (고침 · 넣기 · 지우기 연결을 따로 가리킨다). 보낼 길이 없는 종류의 변경은 남고 사유를 센다. 묶음 요청은 연결이 「요청 압축을 받는다」 고 선언했을 때, 본문이 임계값 이상이고 압축한 결과가 더 작으면 gzip 으로 보낸다 — 작은 편집은 그대로 나간다 (사용자 결정 1).
4. **충돌 감지는 연결이 가진 수단이다.** 버전 필드 (묶음은 항목마다 본문, 행별은 본문 또는 `If-Match`) — 서버가 거절한다. 보내는 버전은 처음 고칠 때의 것이다 (ADR-325 가 변경에 고정한 기준 행): 편집 뒤 재조회가 다른 사람의 수정본을 받아도 그 버전으로 보내지 않고, 버전이 달라졌으면 보내기 전에 충돌로 보인다. 기준은 저장 확정과 사용자의 「내 값으로 다시 저장」 에서만 바뀐다. 저장 전 확인 조회 — 보내기 직전 key 로 다시 읽어 수정 전 값과 다르면 보내지 않는다. 없음 — 바뀐 필드만 덮어쓴다. 행 전체를 보내는 연결은 버전 조건을 달거나 확인 조회로 방금 읽은 행 위에 바뀐 필드만 덮어 보낸다 — 둘 다 없으면 다른 칸까지 덮을 수 있다. 화면은 지금 연결의 수준을 문구로 보인다.
5. **결과는 응답으로 판정한다.** 판정은 행마다 셋 중 하나다 — 반영됨 · 반영 안 됨 · 모름. 2xx 를 모두 「저장됨」 으로 읽지 않는다: 200 · 201 · 204 · 205 는 처리가 끝난 응답이고, 202 는 접수일 뿐이라 「처리 중」 으로 남기며, 그 밖의 2xx 는 모름이다. 묶음: 원자적 연결은 전부 반영 · 전부 남음 둘뿐이다. 행별: 성공한 행만 확정하고 실패한 행에 사유를 남긴다 — 한 번의 붙여넣기에 든 행이라도 행마다 갈린다. status 보다 먼저 응답의 필드 오류 (`errorsPath`) 를 읽는다 — 2xx 여도 오류가 있으면 그 행은 반영 안 됨이고 칸에 표시한다 (지금의 제출 실행기와 같다). 넣은 행의 서버 key 는 응답 본문 → `Location` 헤더 순으로 읽는다 — 보낸 행에 key 가 있어도 응답의 것이 이긴다. 응답이 행을 식별하지 못하면 보낸 key 도 조회 결과도 key 의 근거가 아니다 (그 key 의 행이 전부터 있던 다른 행일 수 있다) — 넣기는 닫고 (다시 보내지 않는다) 다시 조회해 서버가 준 행으로 보인다. 그 행을 보낸 뒤 다시 고쳤으면 그 편집은 버리지 않는다 — 사용자가 조회 결과의 후보에서 대상 행을 고르거나 버릴 때까지 미저장으로 남는다. 후보가 하나여도 자동으로 잇지 않는다 (사용자 결정 2026-11-27). 확정은 ADR-325 의 판정 함수로 — 보낸 뒤 다시 고친 칸 (원래 값으로 되돌린 칸 포함) 은 남는다.
6. **응답을 잃으면 다시 읽어 판정한다.** 자동 재전송은 하지 않는다. key 로 다시 읽어 — 고침은 내 값이면 완료, 수정 전 값이면 미반영 (다시 보내기를 제안), 그 밖이면 충돌. 지우기는 대상이 없으면 완료, 수정 전과 같으면 미반영, 달라졌으면 충돌. 「대상이 없다」 는 단건 확인 조회이거나 조건 없는 조회를 끝까지 모은 목록일 때만 믿는다 — 페이지 · 조건이 걸린 목록에서 행을 못 찾은 것은 범위 밖일 수 있어 「결과 확인 필요」 다. 읽을 길이 없어도 같다. 판정을 기다리는 행은 다음 저장에서 빠지고 다른 행은 저장된다. 넣기는 서버가 key 를 만들면 대조할 수 없으므로 「결과 확인 필요」 로 남기고, 연결이 중복 방지 키를 선언했을 때만 같은 키로 다시 보낸다.
7. **작성 표면은 기능 단위다.** Data 패널의 Collection 설정에 「저장」 구획 (저장 시점 · 쓰기 연결 · 충돌 감지). 켜면 그 Collection 의 편집 가능한 Table 에 저장 막대 (미저장 건수 · 저장 · 취소) 를 연결된 채 넣는다 (사용자 결정 5). 직접 만든 Button 에는 Do 「변경 저장」 · 「변경 취소」 를 잇는다. 미저장 건수와 저장 상태는 값으로 읽을 수 있다.
8. **떠날 때 알린다.** 미저장 변경이 있는 채로 탭을 닫거나 새로 고치면 브라우저 경고를 낸다. 변경을 브라우저에 보존하지는 않는다 (사용자 결정 2).
9. **하지 않는 것.** 편집 상태의 모델 (ADR-325) · 범용 중계 서버 · 오프라인 대기열 · 본문 서명과 메시지 암호화 (사용자 결정 1).

**「탈취 · 변조 뒤 재송신」 에 대해.** 전송 중 변조와 도청은 HTTPS 가, 누가 보낼 수 있는가는 고객 서버의 인증이 막는다 — Composition 이 더할 수 있는 것은 endpoint 에 적은 헤더뿐이다. 같은 요청이 다시 도착하는 경우는 버전 조건이 막는다 (버전이 이미 올라 거절된다). 버전이 없는 연결에서는 같은 값이 다시 쓰여 그 사이의 다른 편집을 덮을 수 있다 — 그래서 화면이 「충돌 감지 없음」 을 밝히고 버전 필드를 권한다. 넣기의 중복은 중복 방지 키가 있는 연결에서만 막힌다. 유효한 자격증명 자체를 빼앗긴 경우는 어느 수단으로도 이 층에서 막을 수 없다.

잔존 위험은 **결과를 응답과 다시 읽기로만 판정하는 것**과 **보장 문구를 연결의 선언 수준에 맞추는 것**으로 관리한다.

## Gates

## Consequences

### Positive

- 칸 편집은 화면에 바로 반영되고 쓰기는 사용자가 누를 때 한 번 (또는 고친 행 수만큼) 나간다. 본문은 바뀐 필드뿐이다.
- 고객이 새 endpoint 를 만들지 않아도 기존 단건 수정 API 로 켤 수 있다. 버전 필드나 묶음 endpoint 가 있으면 그만큼 보장이 올라간다.
- 저장소 안 대역 서버로 통과 조건을 닫을 수 있다.

### Negative

- 보장이 연결마다 다르다. 버전도 확인 조회도 없는 연결은 다른 사람의 편집을 덮을 수 있고, 화면이 그 사실을 문구로 알려야 한다.
- 행별 저장은 일부만 반영될 수 있다. 응답을 잃은 넣기는 사용자가 확인해야 한다.
- 문서 계약 번호가 오른다 — 그 전 계약의 프로젝트 파일은 열리지 않는다. [문서 검사](../../../packages/shared/src/catalog/document/validation.ts#L2679)
- 탭을 닫으면 미저장 변경은 사라진다 — 닫기 경고는 뜬다 (사용자 결정 2).
