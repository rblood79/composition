## Context

### 도메인

- **D1**: JSX 요소 · 이벤트 이름은 설치된 RAC 이름 그대로 (생성기가 이미 그렇다 — `generate.ts:19` 「types as RAC components」). 코드가 DOM · ARIA 를 지정하지 않는다. 컴포넌트 파일의 `export function <Name>(props)` 는 RAC 컴포지션 (레퍼런스 `photos-Sidebar.tsx.txt` 와 같은 모양) 이고 새 primitive 가 아니다.
- **D2**: prop 이름 · 값 = binding `accepts` (S2 정본 순서). 코드에 적은 prop 이 `accepts` 밖이면 거절 (지금 규칙 그대로).
- **D3**: 스타일 값의 정본은 계속 catalog 문서 (`NodeEntry` 의 `VisualField` `types.ts:303` · `LayoutField` `:366` · `SizingField` `:412` · `fills` `:1145` · `responsive` `:1147` · `stateRules` `:1104` · `themeOverride` `:1150` = `NodeThemeOverride {mode?, tint?}` `:910-913`) + theme/tokens. 이 ADR 이 내는 `*.css` 는 **그 투영**이고 독립 정의가 아니다 — 편집은 Design 패널이 쓰는 같은 명령 (`fields.ts` `setFields :88` · `setWholeField :215` (`WholeFieldValue` `:194-201` — fills · fillSizing · visibility · themeOverride · binding · enabled) · `setFillSizing :322`) 으로 돌아가므로 「수동 CSS 가 SSOT 에서 파생 아님」 (ssot-hierarchy §6) 에 해당하지 않는다. 컴포넌트 기본 rule (`COMPONENT_RULES_TABLE`) 은 사용자 문서가 아니라 코드에 **읽기 전용** 으로만 보인다. Builder (Skia) · Preview (DOM) 는 여전히 D3 의 대등 consumer 고, 코드는 셋째 consumer 가 아니라 **문서를 고치는 길** 이다.
- 경계 이동 없음. Generator 확장 선언 (adr-writing 선차단 #2): `generate-css.ts` (catalog rule → CSS) 는 건드리지 않는다 — 이 ADR 의 CSS 는 **사용자 노드 값** 의 투영이고 컴포넌트 rule 의 CSS 생성과 다른 층이다.

### 제약

- **Hard — 스키마 변경 0 · 새 명령 0**: 코드로 할 수 있는 저작 = 패널로 할 수 있는 저작 (문서 명령이 있는 것). 명령이 없는 변경은 거절 + 대안 문구 (285 G2 「새 명령 신설 금지」). 문서 `DOCUMENT_CONTRACT` 무변경 · 마이그레이션 코드 0 (`feedback-no-document-migration-code-dev-stage`).
- **Hard — 쓰기 경계 보존**: 원본 파일을 고치면 원본 (모든 instance) 이, page 파일의 instance 를 고치면 **그 instance 만** 바뀐다. instance 전용 규칙 (`address`) · 상속 규칙의 끄기 · 대체 · descendant patch 는 instance 쪽 명령으로만 가고 원본으로 번지지 않는다 — 문서 모델 (`ownerId` + `address` · 규칙 id 맵) 과 같은 해상도를 코드도 가진다.
- **Hard — 닫힌 어휘 1:1** (285): 파일마다 생성기가 내는 모양 전부에 역문법이 있다. 임의 JS · 외부 import · 계산식은 거절. 어휘가 늘면 같은 커밋에서 역문법도 는다 (왕복 게이트가 집행). **「어휘표에 있는데 read 가 없음」** (지금 E2 · E3 · E4) 을 정적 게이트가 막는다 — 이름 존재가 아니라 golden 조각을 실제로 읽는지.
- **Hard — 조용한 생략 0**: 문서 타입의 모든 필드가 (파일 · emit · read · 명령) 한 칸 또는 「코드에 없음」 목록 (이름 + 이유) 에 있다. 코드로 표현 못 하는 값은 생략이 아니라 **읽기 전용 표지** (`/* composition: mesh fill — Design 패널 */`) + anchor — 지우면 거절, 그대로면 보존.
- **Hard — 정본 = 문서 · Apply 한 번 = history 한 항목**: 여러 파일을 고친 Apply 도 `compose` 한 트랜잭션 · Undo 1. 하나 거절 = 전체 0 (285 R3). baseline 은 page 가 아니라 **프로젝트 revision** 이 된다. 같은 Apply 안에서 새로 선언한 것 (collection · 컴포넌트 · page · 이름 변경) 을 다른 파일이 쓸 수 있어야 한다 — 역문법이 **stage 문서** 를 본다.
- **Hard — 번들**: 파일 생성기 · 역문법 · 파일 트리 · 편집기는 전부 initial 밖 (285 가 그렇게 두었다 — CodeMirror lazy 168.5 KB gz · G4 Δ +269). Builder initial Δ ≤ **+1,024 B gz** (측정 `adr201-bundle-gate.mjs`, Δ 상한 4,096 · 절대 상한 1,390,000 / Preview 320,000, 만료 2026-11-25 — `adr201-bundle-gate.mjs:29-33`). Preview Δ = **0** (코드 보기는 Builder 전용, Preview 는 코드를 읽지 않는다).
- **Hard — 성능**: 트리를 여는 것은 파일을 생성하지 않는다 (이름 목록만 — 문서 entry 열거). 파일 생성은 **열 때 그 파일 하나**. 22 page · 17 collection 프로젝트 (`project-canvas-perf-levers-2026-10-21` 의 CMS 재현 문서) 에서 가장 큰 파일 하나의 생성 시간을 Phase 0 에 기록하고 그 값을 상한으로 ratchet (지금 page 생성과 같은 등급이어야 한다).
- **Hard — D3 왕복 = Canvas 해석과 같은 cascade**: `responsive` (desktop base → tablet → mobile) · `stateRules` · `themeOverride` 의 CSS 왕복 뒤 문서를 Canvas 가 실제로 읽는 해석 값으로 푼 결과가 변경 전과 같아야 한다 — oracle 은 CSS 문자열 대조가 아니라 **compositionRoot 의 해석 출력** (`runtime/compositionRoot.ts:990` `styleOf` 는 비공개 — Phase 0 에서 테스트가 쓰는 공개 진입점을 고정한다).
- **Soft**: 노드 class 이름은 표시용 (anchor 가 identity) · Library 원본은 읽기 전용 (ADR-282 — 고치려면 `unlockOrigin`) · 레퍼런스 fixture 와 같은 파일 구성 (`App.tsx` · `components/*.tsx` · `data/*.ts` · `*.css`).

## Alternatives Considered

### 대안 A: page 파일 하나만 넓히기

- 설명: 지금 `pages/<P>.tsx` 한 파일에 스타일 (`style={{…}}`) · 메타 (`<title>`) · instance 의 template 전개 · 데이터 행 · 사이트 설정을 전부 싣는다. 파일 트리 · 프로젝트 세션 없음.
- 평가: 세션 · identity · 패널 변경이 거의 없다. 그러나 `style={{}}` 은 `@media` (responsive) · `[data-hovered]` (stateRules) · token 참조를 담지 못해 D3 의 반 이상이 또 「코드에 없음」 이 되고, 원본 template 을 instance 자리마다 전개하면 원본을 고치는 명령 (한 곳) 과 코드 (N 곳) 의 대응이 깨진다 (어느 전개를 고쳐야 원본 변경인가 — identity 모호). 사이트 · 데이터 정의 · 라우팅은 page 에 자리가 없어 계속 패널 의존 — 지시 「모든 기능」 미충족. 레퍼런스 fixture 도 이 모양이 아니다.
- 위험: 기술 **M** / 성능 L / 유지보수 **H** (한 파일 N 천 줄 · 원본 전개 N 배) / 마이그레이션 L

### 대안 B: 가상 파일 트리 — 파일 = 문서 영역 · 모든 파일이 같은 왕복 규칙 (채택)

- 설명: 문서 전체를 표준 React 프로젝트 모양의 가상 파일 트리로 보여 준다 (`index.html` · `site.config.ts` · `src/App.tsx` · `src/theme.css` · `src/state/project.ts` · `src/data/<c>.ts` · `src/api/<e>.ts` · `src/components/<N>.tsx` + `.css` · `src/pages/<P>.tsx` + `.css` · `public/…` · `node_modules/@composition/library/*` 읽기 전용 — 연구 §2). 파일 하나 = 문서 영역 하나 · 파일마다 생성기 + 어휘표 + 역문법 + anchor. 285 의 규칙 (생성 → anchor → 편집 연산 추적 → 역문법 → 차이 → 명령 → 재생성 대조) 을 그대로 파일 단위로 돌린다. 편집 세션은 `{projectId, baselineRevision, files: {path → result}, drafts}` — 여러 파일의 차이를 **공통 심볼 표 + stage 문서** 위에서 해석해 명령 하나의 묶음으로 Apply. 스키마 · 명령 신설 0.
- 평가: 레퍼런스 fixture (photos 3 · plants 4 파일) 가 이 모양이라 수용 기준이 생긴다. 285 의 identity · baseline · 거절 모델이 파일마다 같이 서서 새 편집 모델이 없다. 지금 generate.ts (2521 줄) 는 page 생성기로 남고 다른 파일 생성기가 옆에 선다 (분할). 비용은 파일 수만큼의 어휘표 행 (~+25) 과 역문법 — 그래서 **필드 대조 게이트** (문서 타입 필드 전부 ↔ 표) 가 조용한 생략을 막는 장치로 같이 들어온다.
- 위험: 기술 **M** (파일 간 참조 — 같은 Apply 안의 새 선언 · 이름 변경은 stage 해석으로, Apply 뒤의 이름 변경은 문서 rename 명령 + 재생성으로) / 성능 **M** (파일별 lazy 생성 · 파서 공유 — Phase 0 실측) / 유지보수 **M** (어휘표 · 필드 대조 · golden 이 한 묶음) / 마이그레이션 L (스키마 0)

### 대안 C: 코드 = 정본 (코드에서 문서를 다시 만든다)

- 설명: Apply 가 파일 트리 전체를 파싱해 문서를 재구성.
- 평가: ADR-285 대안 C 와 같은 기각 — id · 스타일 · 참조 · 규칙의 identity 가 코드에 없어 (코드에 `id` prop 을 내지 않는다, 10-26) 매 Apply 가 삭제 + 재생성이 되고 Undo · Preview delta · 다른 패널의 선택이 끊긴다. 파일이 여럿이 되면 손실 범위만 커진다.
- 위험: 기술 **H** / 성능 L / 유지보수 **H** / 마이그레이션 **H**

### 대안 D: 읽기 전용 투영 — 파일 트리는 보여 주되 편집은 page 파일만

- 설명: 다른 파일 (스타일 · 데이터 · 컴포넌트 · 사이트) 은 생성만 하고 역문법 없이 읽기 전용. 편집은 지금 page 파일 범위.
- 평가: 위험이 가장 낮고 빨리 보인다. 그러나 「인터렉션 없이 … 모든 기능들을 code editor 에서」 지시의 반 (저작) 을 비우고, 「코드로 못 적는 기능 = 어휘에 채워야 할 결함」 원칙에 정면으로 어긋난다. 읽기 전용 파일은 사용자가 고치려 들 때마다 「패널에서」 로 돌려보내는 `notInCode` 를 늘리는 셈이다. 다만 **Library 원본** 만은 이 모양이 맞다 (ADR-282 — 읽기 전용 + unlock) 라 B 안에 그 한 조각으로 들어간다.
- 위험: 기술 L / 성능 L / 유지보수 **H** (지시 미충족이 debt 로 남음) / 마이그레이션 L

## Decision

**대안 B** 를 채택한다. 결정 항목:

1. **파일 = 문서 영역** (연구 §2 트리). 파일마다 (생성기 · 어휘표 행 · 역문법 · anchor) 한 묶음이고, Apply 는 초안이 있는 파일 전부를 **한 번에** 해석해 명령 하나의 묶음 · history 한 항목으로 실행한다. 순서 (리뷰 h3): ① 모든 초안 파일 파싱 → ② **선언 수집** — 정의 파일 (data · api · state · components · theme · App) 의 새 선언 · 이름 변경 · 삭제를 모아 공통 심볼 표 (이름 → entry id, 새 것은 임시 id) 를 만든다 → ③ **stage 해석** — 정의 파일의 명령을 `stageOver(baseline)` 에 먼저 적용하고, 사용처 파일 (pages · App 의 element) 의 역문법은 **그 stage reader + 공통 심볼 표** 로 참조를 검사한다 (baseline reader 가 아니다 — 같은 Apply 에서 추가한 collection 을 page 가 바로 쓸 수 있다) → ④ 전체 명령을 `compose` 한 트랜잭션 · `expectedRevision = baselineRevision` → ⑤ **재생성 대조는 최종 stage 에서 모든 초안 파일을 다시 생성해** 편집본과 비교한다 (파일 하나씩 끝내고 합치는 것이 아니다). 세션 baseline 은 프로젝트 revision (285 Decision 4 의 page 세션을 프로젝트로) — Apply 직전 revision 이 다르면 적용 0 · 초안 보존. 파일을 열 때 그 파일만 생성하고 트리는 이름만 열거한다.
2. **page 파일 결함 수리가 먼저** (E1 ~ E13 + 조용한 생략 4) — 파일 트리 전에 지금 파일의 「출력만」 · 「빠짐」 · 「의미 결함」 을 없애고 **필드 대조 게이트** 를 세운다. E9 는 같은 When 의 규칙 N 개를 **이름 붙은 handler 함수** (`function onSaveClick() {…}` 를 page 함수 안에, `onPress={() => { onSaveClick(); onLogClick(); }}`) 로 분리해 규칙 id · 독립 실행을 보존한다 (후속 C 의 제어문이 이 함수 본문에 들어간다). 이 함수 이름이 Decision 4 의 상속 규칙 끄기 · 대체의 **규칙 식별자** 가 된다. 숨김 When (hover · focus · keyboard) 은 코드에서 받는다 — 숨김은 패널 노출 정책이지 문서 제약이 아니다 (사용자 결정 4).
3. **스타일 = CSS 파일 + class** (사용자 결정 1 권고): 노드 하나 = 클래스 하나 (`.hero-title` — 노드 이름에서, anchor 가 identity · 이름은 표시용 + 결정적 접미사), 속성 = `VisualField` · `LayoutField` · `SizingField` 1:1, `@media (max-width: …)` = `responsive`, `[data-hovered]` · `[data-pressed]` · `[data-selected]` = `stateRules`, `var(--token)` = `TokenUse`, 여러 배경 = `fills` 레이어. **`themeOverride` 는 조건부 스타일이 아니라 노드에 강제하는 값** (`{mode?, tint?}`, 리뷰 h2) 이라 그 노드의 base 블록 안 선언 둘로 낸다 — `color-scheme: dark` (= `mode`) · `--theme-tint: <tint>` (= `tint`); 둘 다 없으면 해제 (`setWholeField({field: "themeOverride", value: undefined})`), 하나만 있으면 그 키만 (`setWholeField` 의 `WholeFieldValue.themeOverride`). `[data-theme=…]` 조건 선택자는 어휘에 없다 (쓰면 `outsideVocabulary`). 편집은 Design 패널이 쓰는 같은 명령. CSS 로 재현 불가한 값 (mesh fill 등) 은 읽기 전용 표지. 컴포넌트 기본 rule 은 `node_modules/@composition/catalog/*.css` 로 읽기 전용 — 사용자 CSS 가 그 위에 얹히는 모양이 Canvas 의 cascade 와 같다.
4. **컴포넌트 파일과 instance — 쓰기 경계가 파일 경계다** (리뷰 h1). `components/<Name>.tsx` = Local 원본 = `export function <Name>({…props}: <Name>Props)`, 본문 JSX = template (각 요소에 `className="<노드 이름>"` — 이 이름이 아래 `overrides` 의 키다), prop 사용 = property 바인딩 (text · boolean · variable 은 값, event 는 `props.on<Name>?.(value)` — 294 어휘표 행), `children` / `{header}` = slot, 원본 규칙 = 이름 붙은 handler 함수 (Decision 2 — 그 이름이 규칙 식별자). 이 파일을 고치면 **원본 명령** (모든 instance 에 미친다). page 파일의 instance 는 **이름 그대로** (`<UserPicker team={roleFilter} onPick={setPicked} />`) · 루트 prop = instance property (`setInstanceProperty`) · slot 채움 = children / 이름 붙은 prop · 루트 자신의 instance 규칙 = 지금처럼 `onX={…}`. **안쪽 노드** 에 대한 instance 몫은 `overrides` 객체 prop 하나로 — 키 = **안쪽 경로** `'<중첩 instance 이름>/…/<노드 이름>'` (= `InstanceAddress` — `instances` 체인의 중첩 template instance 이름을 `/` 로 잇고 끝에 `templatePath` 의 대상 노드 이름; 직접 자식은 `'save-button'`, 바깥 instance 안의 같은 원본 둘은 `'left-picker/save-button'` · `'right-picker/save-button'` — 리뷰 round 2 h1), 값 = 그 자리의 descendant patch (prop · `className` 은 CSS 파일 쪽) 와 이벤트별 규칙 묶음 `rules({ inherited: { <원본 handler 이름>: 'off' | () => {…} }, own: [() => {…}] })` — `inherited` 의 키가 **원본 규칙 id** (`DescendantPatchFields.interactions` 의 키), `'off'` → `catalogInheritedRuleEnabledCommand`, 함수 → `catalogReplaceInheritedRuleCommand` (대체 규칙은 이 instance 의 것이라 page 변수를 참조할 수 있다), `own` → **이 instance 의 `address` 규칙** (`InteractionEntry {ownerId: instance, address}` — 다른 instance 에 없다, E5). 같은 trigger 의 원본 규칙 둘 중 하나만 끄는 것은 `inherited` 키 하나로 표현된다. 역문법은 `overrides` 를 instance 패치 · address 규칙 명령으로만 읽고 **원본 명령을 내지 않는다** (`pushInstanceOverrides` 미사용). Library 원본은 `node_modules/@composition/library/<Name>.tsx` 읽기 전용 — 고치면 거절 + 「unlock」 (ADR-282 `unlockOrigin`) 스니펫 (사용자 결정 3). 294 의 「`<DialogTrigger />` · `<div />` 로만 나온다」 는 여기서 닫힌다.
5. **데이터 파일**: `data/<c>.ts` = `export type <Row> = {…}` + `export default [행 …]` (≤ 1,000 행, 286) + 계산 필드 (291) · `api/<e>.ts` = `export default endpoint({method, url, headers, query, body, response, timeout, retry, run})` — `endpoint()` 는 생성 코드가 import 하는 고정 도우미 (호출 = 선언, 실행 아님) · 비밀은 `secret('NAME')` 이름만 (E11 — 코드가 endpoint 를 **이름** 으로 부른다) · `state/project.ts` = 프로젝트 변수 한 객체 + `useProjectState()` (사용자 결정 5, E8). 지금 `derivedChanged` 로 막던 데이터 정의 편집이 이 파일의 어휘가 된다.
6. **`App.tsx`** = `createBrowserRouter([{path, element, children}])` (page 추가 · 삭제 · 이동 · route) · layout route = `<Outlet/>` 을 둔 레이아웃 원본 (286 `applyLayout`) · `<ToastRegion placement>` · `<ProjectStateProvider>` · 활성 theme. page 파일에 `useParams` 선언 · `<title>` · `<meta>` (meta) · 루트 `<Page isDisabled colorScheme>` 래퍼 (E7 — body 상속 prop · 규칙 · body 대상 Do 의 자리).
7. **사이트 파일** `index.html` (lang · title · description · favicon 밝은/어두운 · og:image · theme-color · appIcon) + `site.config.ts` (search · redirects · access — 리터럴 객체만, 비밀 0) — **ADR-286 Decision 8 「코드 보기는 사이트 설정을 코드에 내지 않는다」 를 뒤집는다** (사용자 결정 2). 뒤집는 이유: 그 결정은 「RAC 레퍼런스 코드에 `<head>` 가 없다」 였는데, 이번 지시는 page 코드가 아니라 **프로젝트** 를 코드로 보는 것이고 레퍼런스 앱도 `index.html` 을 가진다. 사용자가 결정 2 를 반대로 답하면 사이트 파일은 빠지고 「코드에 없음」 목록에 이유와 함께 남는다.
8. **필드 대조 게이트** (G1): 문서 타입 (`CatalogEntry` 13 + `DataEntry` 3 + `ProjectEntry.site` · `PageEntry.meta` · `NodeEntry` 스타일 필드 · `DescendantPatchFields`) 의 모든 필드가 표 한 칸 (파일 · emit · read · 명령) 또는 「코드에 없음」 (이름 + 이유 — Canvas 배치 `placement` · guide · `displayState` 같은 화면 도구 상태) 에 있어야 한다. 어휘표 정적 테스트는 이름 존재가 아니라 **각 형태의 golden 조각을 실제로 read** 한다 — 지금 E2 · E3 · E4 가 RED 가 되는 테스트다.
9. **편집기 기능은 최소**: 파일 트리 + 탭 + 파일별 자동완성 (어휘) 만. Apply 전 diff · 커서 ↔ Canvas · 스니펫 = 패널 전부 · 레퍼런스 통째 붙여넣기는 D (후속).

**위험 수용 근거**: 채택 대안의 MEDIUM 셋 (파일 간 참조 · 생성 비용 · 어휘 묶음) 은 각각 (stage 해석 + 공통 심볼 표 — Decision 1 · 파일 열 때 하나 생성 + Phase 0 ratchet · 필드 대조 게이트) 로 막히고, 모두 G1 · G2 · G5 가 기계적으로 잰다. 쓰기 경계 (원본 ↔ instance) 는 파일 경계와 같아 역문법이 파일을 보고 명령 종류를 고른다 — G4 가 A/B 두 instance 격리로 잰다. 스키마 · 명령 신설 0 이라 롤백은 코드 보기 chunk 만의 일이다.

**기각 사유**: A — D3 의 반 · 원본 · 사이트 · 데이터가 page 에 자리가 없다. C — 285 대안 C 와 같은 identity 손실. D — 지시의 저작 반을 비운다 (Library 조각만 흡수).

## Consequences

### Positive

- 패널로 할 수 있는 저작 전부를 코드로도 할 수 있다 — 문서 명령이 같으므로 결과도 같다 (원칙 「누가 해도 같은 결과」). 294 의 `<DialogTrigger />` · `<div />` 한계가 닫히고, 294 가 넣어 둔 원본 쪽 `props.on<Name>?.(value)` 가 처음 화면에 나온다.
- 쓰기 경계가 파일 경계라 「이 편집이 원본에 미치나, 이 instance 에만 미치나」 를 파일 이름이 말해 준다 — 패널 (Components 탭 vs page 의 instance) 과 같은 구분이다.
- 조용한 생략이 구조적으로 사라진다 — 문서 타입에 필드를 더하면 표를 채우기 전까지 게이트가 막는다. 「출력만」 어휘도 같은 게이트가 막는다.
- 레퍼런스 fixture 의 파일 분할 · CSS · 데이터 파일이 수용 기준으로 살아난다 (지금은 page 한 파일만 대조).
- 후속 C (제어문) 는 이름 붙은 handler 함수 본문에, D (편집기 UX) 는 파일 트리 위에 바로 얹힌다.

### Negative

- `generate.ts` 한 파일이 파일별 생성기 묶음으로 갈라지고 (page 생성기는 남는다), 어휘표가 26 행에서 ~50 행으로 는다 — 늘어난 만큼 역문법 · golden 이 같이 늘어 유지 비용이 있다 (그래서 G1 이 묶음으로 잔다).
- Apply 가 파일 하나씩이 아니라 **두 단계** (정의 stage → 사용처 해석 → 전 파일 재생성 대조) 가 된다 — 285 의 한 파일 dry-run 보다 Apply 한 번의 비용이 파일 수에 비례한다 (초안이 있는 파일만이라 보통 1 ~ 3).
- instance 의 `overrides` 객체 prop 과 `rules()` 도우미는 레퍼런스 앱에 없는 **composition 고정 도우미** 다 (`endpoint()` · `secret()` 과 같은 종류) — 문서 모델 (`address` · 규칙 id 맵) 을 코드에 그대로 담기 위한 최소 어휘이고, 임의 JS 가 아니라 역문법이 읽는 닫힌 모양이다.
- ADR-286 Decision 8 을 뒤집는다 (사용자 결정 2). 286 본문에 Superseded 표기 한 줄이 들어간다.
- E9 의 코드 모양이 바뀌어 golden 7 이 재생성된다 (의미 변경 0 을 같은 커밋에서 단언).
- 코드 보기 chunk 가 커진다 (initial 은 아님). CodeMirror 168.5 KB gz 위에 파일 생성기 · 역문법이 더해진다 — G5 가 initial 만 잰다는 뜻이고 lazy chunk 크기는 기록만 한다.
- 노드 class 이름 · 컴포넌트 함수 이름 · handler 이름 · endpoint 이름의 식별자 규칙이 코드 보기 전용으로 하나 생긴다 (문서 이름은 바뀌지 않는다).
