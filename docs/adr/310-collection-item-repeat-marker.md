### 문제

목록에 내용을 넣는 길이 둘이다 — slot 「+」 로 항목을 넣는 것과 데이터를 연결하는 것. 두 길이 서로 다른 규칙으로 구현돼 있어 섞을 수 없고, family 마다 예외가 있다.

레퍼런스 (RAC · S2 Collections) 에서 목록의 내용은 자식의 순서열이고, 자식 하나는 정적 항목이거나 `<Collection items>` 반복 구간이다. `<ListBox items>` 는 「반복 구간 하나가 목록 전체」 인 경우의 줄임 표기다. 정적 항목과 반복 구간은 한 목록에 섞인다 (「Combining collections」).

## Alternatives Considered

### 대안 A: 지금 모델 유지 + 결함만 수리

- 설명: 「첫 항목 = 템플릿」 규칙과 bound Table 합성 행을 그대로 두고, type 목록 불일치 (F4 · F5) 와 Tabs 를 노드 정본 (A2) 으로 되돌리는 것만 한다.
- 근거: 변경이 가장 작다. ReUI 조사는 저장 형식을 바꿀 근거를 주지 않았다.
- 위험: 기술 L / 성능 L / 유지보수 **H** / 마이그레이션 L
- 유지보수 H 의 이유: 암묵 규칙이 일곱 곳 (F3) 에 남고, 정적 항목과 데이터 행을 섞을 수 없으며 (「전체」 + 데이터), bound Table 셀을 편집할 수 없다 (F8). 목적 (레퍼런스 개념 활용) 에 닿지 않는다.

### 대안 B: 항목 노드에 반복 표시 — 데이터는 owner 에 둔다

- 설명: 항목 노드에 `repeat` 표시를 붙이면 그 자리에서 데이터 행마다 반복된다. 표시 없는 항목은 정적이다. 데이터는 지금처럼 owner 의 `binding` 이고, 한 목록에 데이터가 둘 이상일 때만 반복 항목이 자기 `binding` 을 갖는다. Tabs 는 Tab · TabPanel 둘 다 표시하고 기존 `id` ↔ `itemId` 로 짝을 맞춘다. bound Table 은 Row 템플릿 하나.
- 근거: RAC · S2 Collections 의 정적 항목 · `<Collection>` 구간 · 조합과 1:1. Builder 의 `children` 이 이미 같은 순서열이다.
- 위험: 기술 M / 성능 M / 유지보수 L / 마이그레이션 M
- 기술 M: resolver 의 반복 규칙 교체가 모든 bound 목록에 닿는다. 성능 M: Table 행이 합성 대신 템플릿 subtree 를 펼친다 (Builder 는 표본 행만, DOM 은 창 100). 마이그레이션 M: contract 를 올리면 그 전 문서는 열리지 않는다.

### 대안 C: 데이터를 항목 (anchor) 으로 옮기고 역할을 NodeId 로 참조 (Codex 안)

- 설명: 모든 반복 목록의 `binding` 을 owner 에서 anchor 항목으로 옮긴다. `repeat.roles` 가 템플릿 노드 (Tab · TabPanel · Row) 를 NodeId 로 가리킨다. 모든 소비자가 새 `CollectionSnapshot` (행 · 수 · revision) 을 읽는다.
- 근거: 한 목록에 데이터가 여럿인 경우를 처음부터 균일하게 표현한다.
- 위험: 기술 **H** / 성능 M / 유지보수 M / 마이그레이션 **H**
- 기술 H: owner 의 binding 을 읽는 코드가 넓다 — `boundOwnerOf` (`C/runtime/delegatedDom.runtime.ts:374`), 로딩 상태 · 더 불러오기 · 서버 정렬 (`C/runtime/catalogPreviewSession.ts`), 연결 명령 (`B/dataBindingCommand.ts`), Code 보기의 `items={…}` 와 역방향 적용 (`packages/shared/src/codeView/generate.ts:3447`), 보기 사용처 색인. 전부 주소가 바뀐다. 참조가 생기면 끊어진 참조 검증 (복사 · 삭제 · detach · swap) 도 새로 필요하다.

### 대안 D: 정적 항목도 배열 (`items`) 을 정본으로

- 설명: contract 65 의 Tabs 방식을 모든 family 로 넓힌다. 항목은 노드가 아니라 owner prop 의 배열 원소.
- 근거: RAC 의 `items` 형태와 저장이 같다.
- 위험: 기술 **H** / 성능 L / 유지보수 **H** / 마이그레이션 **H**
- 항목 안의 자유 내용 (Card · 입력 · 버튼) 을 배열 원소가 담지 못하고, 노드 편집 · slot · instance 가 항목에서 끊긴다. 사용자가 A2 로 기각했다.

## Decision

**대안 B**.

1. **저장** — `NodeEntry.repeat?: true`. collection 안의 항목 · section type 노드에만 붙는다. 그 밖의 저장 구조 (`children` · `fillSlot` · `binding` · 선택 prop) 는 그대로다.
2. **데이터 위치** — 반복 항목의 행은 처음 맞는 곳에서 온다: ① 그 노드 자신의 `binding` (`<Collection items={다른 목록}>`) → ② 반복 중인 바깥 행의 하위 행 (`<Collection items={item.children}>`) → ③ 가장 가까운 owner 의 `binding` (`<ListBox items>`). ③ 만 쓰는 목록에서는 owner 의 binding 을 읽는 코드가 그대로다. ① 이나 반복 section 을 쓰는 목록은 runtime 이 구간별 source 를 읽어야 한다 (Decision 11). `binding.key` (한 행 고정) 의 뜻은 유지하고 `repeat` 와 함께 쓰지 않는다.
3. **그리기** — 목록의 자식을 순서대로 그린다. 정적 항목은 그대로, 반복 항목은 그 자리에 행 수만큼. 「첫 항목만 그리고 나머지는 건너뛴다」 는 규칙을 없앤다.
4. **Tabs** — 정적은 Tab 노드 + 짝 TabPanel 노드 (A2). `props.items` · 전용 목록 UI · `tabsItems.ts` 를 지운다. 연결하면 Tab 과 TabPanel 둘 다 `repeat`, 짝은 기존 `id` ↔ `itemId`. Tab 삭제 · 복제는 짝을 같은 명령에서 처리한다.
5. **bound Table** — TableBody 아래 Row 노드 하나에 `repeat`, 그 안에 열마다 Cell. 합성 행을 없앤다. 템플릿이 보통 Row 노드라 기존 열-셀 맞춤 명령이 그대로 적용된다. 템플릿 Row 옆에 정적 Row (합계 행 등) 를 둘 수 있다.
6. **연결할 때 기존 항목** — 연결 UI 에서 고른다. 기본은 템플릿 하나만 남기기 (화면이 지금과 같다), 다른 선택은 전부 고정 항목으로 유지.
7. **판정을 한 곳에서** — 항목 type 목록 다섯 개를 표 하나로 합치고 나머지는 거기서 계산한다. 「이 목록의 자식 중 어느 것이 정적 항목 · 반복 항목 · 그 밖인가」 는 Graph 를 읽는 함수 하나를 resolver · Layers · 명령 · Code 보기가 같이 쓴다. 행 · 수를 담는 새 snapshot 타입은 만들지 않는다 (F11 로 이미 있다).
8. **runtime** — Preview · Publish 는 지금처럼 resolver 가 펼친 자식을 RAC 에 넘긴다. 문서 쓰기는 명령 → `workspace.execute` 뿐이고, 실행 중 편집은 세션의 key 기준 편집이다. 섞인 목록에서 고정 항목은 데이터 편집 · 정렬 · 필터의 대상이 아니다. 로딩 · 더 불러오기 · 선택 불러오기는 반복 구간의 source 마다 따로 돈다 (Decision 11).
9. **Code 보기** — 문서의 모양대로 레퍼런스 코드를 낸다: 정적 자식, `items` + 렌더 함수 (본문 = 템플릿 트리 전체), 섞이면 `<Collection>`, Tabs · Table · Tree 재귀, 그룹은 `array.map`, `LoadMoreItem` · `renderEmptyState` · `dependencies` · `useTreeData`.
10. **표시 방식은 목록마다 고른다** — owner 노드의 `rowDisplay?: { mode: "more" | "pages" | "virtual"; size?: number }`. 없으면 `more` · 100 이다. 컴포넌트 prop 이 아니라 문서 구조 필드다 (S2 에 대응 prop 이 없다). Builder Canvas 는 어느 방식이든 지금처럼 표본 행 + 「+N more」 다. 세 수를 구분한다 — 불러온 수 (서버 cursor), 표시 창 (DOM 에 놓는 범위), Builder 표본.
    - **더 보기 (`more`)** — 표시 창은 반복 구간마다 세션이 갖고 `size` 에서 시작한다. 구간 끝의 `LoadMoreItem` 이 닿으면: 불러온 행이 창 밖에 남아 있으면 창만 늘리고, 다 보였고 다음 페이지가 있으면 불러온 뒤 늘린다. 원격이 아닌 목록도 같은 sentinel 로 늘린다.
    - **페이지 (`pages`)** — 표시 창은 `[(page − 1) × size, page × size)` 이다. 페이지 방식의 목록은 **자기 조회 단위** 를 갖는다 (Decision 12) — 현재 쪽 · 받은 응답 · 요청 상태가 그 목록의 것이라, 같은 데이터를 읽는 목록 A 가 1 쪽, B 가 3 쪽을 동시에 보일 수 있다. 원격이 아닌 목록은 그 구간을 자르고, 원격 목록은 endpoint 인자 `page` · `pageSize` (새 인자) 로 그 페이지를 받는다 — endpoint 가 cursor 만 받으면 앞 · 뒤 이동만 된다. Pagination 노드가 목록을 가리키고 그 목록의 현재 페이지 · 페이지 수를 읽어 번호를 그린다 (연결 모양은 사용자 결정 6 — 확정: Pagination 이 목록을 가리키는 참조). 반복 구간이 하나인 목록에서만 고를 수 있다.
    - **가상 스크롤 (`virtual`)** — DOM 이 owner 를 RAC `Virtualizer` 로 감싼다 (보이는 행만 DOM). 행을 받는 방식은 더 보기와 같다. `Layout` 과 그 옵션 (행 크기 · gap · padding · 방향) 은 Canvas 가 읽는 것과 같은 catalog 값에서 낸다 — 두 화면의 행 위치가 같아야 한다 (G8). 고를 수 있는 조건: 목록에 정해진 높이가 있고, 배치가 한 줄 (세로 · 가로) 이거나 Table 이다. grid 배치 (GridList grid · CardView) 는 사용자 결정 7. 조건에 맞지 않으면 패널이 이유를 알린다.
11. **구간별 source** — runtime 은 `boundOwnerOf` 의 「owner 하나」 대신 그 목록의 반복 구간 목록 (구간 노드 · collection · binding) 을 읽는다. 구간마다 자기 `LoadMoreItem` (그 구간 바로 뒤, RAC 가 section · level 마다 여러 개를 허용) · 로딩 표시 · cursor · 표시 창을 갖는다. owner 에 하나뿐인 값은 이렇게 정한다: `loadingState` = 모든 구간이 idle 이면 idle, 아니면 가장 앞 구간의 상태 · 빈 상태 = 정적 항목 0 + 모든 구간 0 행 · 정렬 · 검색 글자 = 각 구간의 source 에 따로 적용하고 구간 사이 순서는 문서 순서 · 끌기 type = 구간의 collection (다른 collection 구간으로의 이동은 목록 간 이동 규칙).
12. **조회 단위** — collection 은 데이터의 정체성 (항목 key · 편집 기록 · 선택) 이고, 원격 조회의 상태 (요청 인자 · 받은 항목 · cursor 이력 · 로딩 상태 · 전체 수 · 취소와 순서) 는 조회 단위가 갖는다. 더 보기 · 가상 스크롤 목록은 지금처럼 collection 하나의 조회 단위를 같이 쓴다 (같은 데이터를 여러 목록이 이어 받는다). 페이지 방식 목록은 그 목록을 그리는 record 마다 조회 단위 하나를 따로 갖는다 — 다른 목록의 응답을 바꾸지 않고 다른 목록의 요청을 취소하지 않는다. 행을 읽는 감싸개는 어느 목록이 읽는지를 같이 넘긴다. 진행 중 요청을 공유하는 경로를 쓰게 되면 그 공유는 endpoint 가 아니라 풀린 요청 (주소 · 인자) 이 같을 때만 한다. collection 을 대상으로 한 동작은 이렇게 닿는다: 편집 (`append` · `update` · `remove`) 은 collection 의 편집 기록 하나를 각 조회 단위의 항목 위에 다시 적용, `reload` · 정렬 · 검색 글자는 그 collection 의 모든 조회 단위에 (페이지 목록은 1 쪽으로).

위험 수용 근거: B 의 처음 M 위험 셋은 모두 Gate 로 잰다 — 반복 규칙 교체는 family 별 Canvas = DOM 대조 (G3), Table 펼침 비용은 기준선 대비 측정 (G4), contract 올림은 사용자 결정 1 (확정 — 올린다).

기각 사유:

- **A** — 암묵 규칙과 Table 전용 경로가 남아 「전체」 + 데이터, 셀 편집을 할 수 없다. 다만 A 의 내용 (결함 수리 · Tabs A2) 은 B 의 Phase 1 · 2 로 그대로 들어간다.
- **C** — 데이터 위치를 옮기지 않아도 여러 데이터를 표현할 수 있다 (Decision 2 의 ①). 옮기는 비용 (주소 변경 · 참조 무결성) 만 남는다. ReUI 조사도 옮길 근거를 찾지 못했다.
- **D** — 항목의 자유 내용과 노드 편집을 잃는다. 사용자 기각.
- **runtime 에서 `items` + 렌더 함수로 넘기기** (레퍼런스 개념이지만 채택하지 않음) — Canvas 에는 RAC 가 없어 행 반복을 resolver 가 해야 하고, DOM 이 같은 결과 트리를 읽어야 두 화면이 같다. 렌더 기억의 이득은 record id 가 React key 라 이미 있다.
- **동적 열** (`TableHeader columns` + 함수) — 열은 디자인이고 Column 은 작성 노드다 (ADR-241).

### 사용자 결정 7건 — 6 건 확정 (1 ~ 6), 1 건 (7) 은 execute-adr 가 Phase 8 에서 묻는다

1. **계약 번호** — **확정 (2026-11-15)**: 번호를 올리고 그 전 문서는 열지 않는다 (ADR-308 과 같은 방식). 번호는 착수 시점의 다음 번호이고 Phase 2 에서 한 번 올린다 (breakdown §7). 영향: 그 전 계약의 프로젝트 전부.
2. **연결 UI 의 선택지** — **확정 (2026-11-15, Phase 3 착수)**: Design 패널 Collection 절의 연결 칸 안. 고정 항목이 2 개 이상인 목록에 데이터를 고르면 칸 아래에 「기존 항목 N개 — (•) 첫 항목만 템플릿으로 — 나머지 지움 / ( ) 모두 고정 항목으로 두고 데이터는 뒤에」 가 나온다 (기본 = 첫 항목만 템플릿). 연결 한 번 = Undo 한 단계. 기각: 연결 확인 대화상자 · 선택 없이 연결 뒤 바꾸기.
3. **반복 표시 모양** — **확정 (2026-11-15, Phase 3 착수)**: Layers 의 템플릿 행 앞에 반복 아이콘 · 뒤에 「× 행 수」, 고정 항목은 평소처럼. Canvas 는 템플릿을 고르면 반복된 행 전체에 얇은 점선 외곽. 기각: Layers 묶음 행 · 아이콘만.
4. **섞인 목록의 끌어 옮기기** — **확정 (2026-11-15)**: 데이터 행을 고정 항목 경계에 놓으면 반복 구간의 처음 · 끝으로 간다 (거절하지 않는다).
5. **번들 Δ 상한** — **확정 (2026-11-15, Phase 0)**: ADR-201 기본 Δ — ADR 전체 Builder +4,096 · Preview +3,584 B (G0 기준선 Builder 1,540,940 · Preview 152,371 대비). 넘으면 그 Phase 에서 lazy 분리로 줄이고, 못 줄이면 다시 묻는다.
6. **Pagination 과 목록의 연결 모양** — **확정 (2026-11-15)**: Pagination 노드가 목록을 가리키는 참조 하나를 갖고, 번호 Button 은 템플릿 하나가 페이지 수만큼 반복된다 (규칙 대상과 같은 장소 참조, 새 저장 필드 하나). 기각: interaction 규칙으로 잇기 · 목록의 부품으로 두기.
7. **가상 스크롤의 grid 배치** (Phase 8) — GridList grid · CardView 를 `GridLayout` 으로 지원 / 한 줄 목록과 Table 만. Phase 0 이 Canvas 가 `GridLayout` 의 칸 크기 계산을 같은 결과로 낼 수 있는지 판정한 뒤 정한다.

## Consequences

### Positive

- slot 「+」 와 데이터 연결이 같은 노드 모델이 된다. 「전체」 같은 고정 항목과 데이터 행을 한 목록에 둘 수 있다.
- 템플릿이 보통 노드라 선택 · 편집 · 복사 · 삭제 · Undo · Canvas 그리기가 기존 경로다. bound Table 의 셀을 노드로 편집할 수 있다.
- Tabs 의 배열 저장 예외와 bound Table 의 합성 경로가 없어진다. 항목 type 목록이 한 곳이 된다.
- Code 보기가 템플릿 내용을 담은 레퍼런스 형태의 코드를 낸다.
- 데이터를 owner 하나에만 둔 목록 (지금의 모든 연결) 은 저장 위치가 그대로다. Quick Connect · Code 보기의 `items={…}` 주소가 바뀌지 않는다.
- 100 행을 넘는 목록의 뒤쪽 행을 Preview · Publish 에서 볼 수 있게 된다 (지금은 못 본다 — F14).
- 많은 행을 다루는 화면 (대량 데이터 조회) 을 목록마다 맞는 방식으로 만들 수 있다 — 더 보기 · 페이지 · 가상 스크롤.

### Negative

- 저장 형식이 바뀌어 그 전 계약의 프로젝트는 열리지 않는다.
- 데이터 위치 규칙이 셋이라 「이 반복 항목의 데이터가 어디서 오는가」 를 패널이 보여 줘야 한다.
- bound Table 행이 템플릿을 펼치므로 합성보다 record 가 늘 수 있다 (G4 로 관리).
- ADR-234 · 241 · 256 · 308 의 해당 서술과 `state-management.md` · `catalog-subparts.md` 의 「첫 소유 항목을 행마다 반복」 문구를 같이 고쳐야 한다.
- runtime 의 로딩 · 더 불러오기 · 빈 상태 · 선택 불러오기 소비자를 「owner 하나」 에서 「구간 목록」 으로 바꿔야 한다 (F15, Decision 11).
- 표시 방식이 셋이라 패널이 「언제 무엇을 고르는가」 를 안내해야 하고, 가상 스크롤은 고를 수 있는 배치가 제한된다 (정해진 높이 · 한 줄 배치 또는 Table).
- Pagination 은 레퍼런스가 없는 자체 설계다 (F16).
